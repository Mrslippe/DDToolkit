# devlog 写作模板

> 提炼自真实 devlog：`001-20260804-v0.1.0-项目初始化与架构总结.md`、`097-20260915-R20托盘退出修复与设置窗口渲染.md`、
> `082-20260914-v1.0.0发布.md`、`045-20260909-增量抓取漏帖-置顶帖打乱流序.md`。
> 篇幅预算见 `docs/DEV-LOOP.md` §0.1（**≤40 行**）；别把"中位数 / 均值"这类快照抄进模板 —— 它会被直接抄进新 devlog。

## 一、标题与开头

```markdown
# NNN-YYYYMMDD-<版本|R编号> <主题>
```

- 文件名与 H1 同源，但**不要求逐字相同**：097 文件名是「…托盘退出修复与设置窗口渲染」，
  H1 写的是「托盘退出修不好 + 设置窗口渲染问题」——**用编号定位，不要靠标题匹配**。
- H1 之后紧跟一个 `>` 引用块交代**引子**，三种常见写法：
  - 用户原话：`> 用户："ok 把这个版本作为 1.0.0 打版推送到 release 上吧。"`（082）
  - 实测反馈：`> 用户实测反馈（2026-09-15，附设置窗口截图）：① … ② …`（097）
  - 起因交代：`> 起因（2026-09-08）：连续两个 bug …都只能靠 npm run release 出包后人工试出来`（DEV-LOOP）

## 二、骨架（按批次类型选）

### A. 需求批次（例：087 / 088 / 095）

```markdown
# 0NN-YYYYMMDD-R<n><主题>

> 用户原文（编号按约定重排）：**R<n>**「……」优先级 中/低/高。

## 一、<做了什么>
## 二、<关键决策 / 改法>
## 三、护栏：新探针 `--<mode>`（或：新增用例 N 条）
## 四、门禁
```

### B. 修 bug 批次（例：097 / 075 / 071→080）

```markdown
## 一、<现象一句话概括>：<根因一句话>

**根因（代码级）**：<贴出证明的命令或代码，例如 grep 结果>

### 修法：<一句话>

| 场景 | 行为 |
|---|---|
| … | … |

## 二、<第二处问题>
## 三、护栏：新探针 `--<mode>`
## 四、门禁
> ⚠️ 人工验收仍然要做：<哪些只能人做、怎么做>
```

> 修 bug 批次的灵魂是**根因取证**：写出「用户看到什么 → 根因是什么」，
> 并把反向验证（先让判据红、再修绿）记下来 —— 仓库里多篇 devlog 都在做这件事
> （071 的"卡死"结论在 080 被反转，理由就是判据读了旧 DOM 节点）。

```markdown
## 一、为什么是 <版本>
## 二、本批动作（版本号同步 / 发布说明 / 门禁 / 构建 / 发布 / 升级说明）
## 三、执行记录（YYYY-MM-DD 实测）

| 步骤 | 结果 |
|---|---|
| 门禁（构建前） | `pytest` **N passed**；`tsc` 0；`eslint --max-warnings 0` 0；`vitest` **N passed** |
| 版本同步复核 | `VERSION_FILES` 全部 = <版本>；`ddtoolkit.exe` FileVersion 实测 = <版本> |

| NSIS 布局校验 | 含 `_internal` 的 `oname` 行 N；**被打平的行 = 0** |
```

> 发布批次的执行记录表**可直接从 `dist-release/release-report-<版本>.md` 抄**（`release.py report` 步骤生成）。

## 三、固定小节：门禁（几乎每篇都有）

「门禁」一节只写真**跑出来**的数字 —— 用下面这个骨架（**占位符别照抄成旧数字**）：

```markdown
## 四、门禁

pytest **<实跑数>**（+N）· `cargo test` **<实跑数> passed** · vitest **<实跑数>** ·
tsc 0 · eslint 0 · doc_check 0 FAIL · **<N> 个探针模式全绿**（新增 `--close-ask`）·
主探针三档 `问题=0` · hero 签名与词云 sha 未变。
```

> ⚠️ **别在这里写死基线数字** —— 模板里的数字**会被直接抄进新 devlog**；
> 当前基线只在 `docs/TODO.md` §6.2「当前门禁基线」维护（见下一节）。

当前基线的完整对照表在 `docs/TODO.md` §6.2「当前门禁基线」。

## 四、篇幅与密度

- 一次改动一篇，**预算 ≤40 行**（真源：`docs/DEV-LOOP.md` §0.1；字母级微调并进现有篇）——
  不要为了凑长度灌水，也不要只写一句"修好了"；篇幅快照别抄进模板。
- 表格密度高：现象/行为对照、场景→行为、门禁数字，一律用表。
- 数值必须带**测量口径**（例：`徽标→分割线 57px → 10px`、`文本宽 114.3/150`、
  `日历签名 48519bae… → 50b78ec0…（数据漂移、非代码）`）。
- 踩过的坑用 `> ⚠️` 引用块单列，并写清**教训**而不只是现象。

## 五、写完立刻做的两件事

1. 回填 `docs/ROADMAP-DONE.md`「批次 → devlog 索引」表 —— **一行一个裸编号**（`| 167 |`）。
   无独立 devlog 的小批次写**提交短哈希**（`| c729ea3 |`）；范围行（`024–026`）只有早期批次才有。
   三种合法写法的完整说明见 `SKILL.md` §7。
2. 跑 `python scripts/doc_check.py` 确认 0 FAIL —— **条目表见 `scripts/doc_check.py` 的 `CHECKS`**
   （跑一次即逐条打印；别在这里再抄一份，也别写项数）。
