# 045-20260909-微博/ B 站增量抓取漏帖：置顶帖打乱流序导致提前停止

> 用户 2026-09-09 反馈：「微博帖子的抓取好像出问题了，执行更新动态后微博动态抓取不到，
> 先检查一下」。

## 一、定位过程

1. **日志**：`更新未归档 weibo:7471118487 / 7198559139` 都发了 `mymblog` 请求且
   `HTTP 200`，但 `details` 里 stored=0，也没有任何告警 —— 不是网络/登录问题。
2. **接口直连**（用 dev 目录里的 cookie，只读）：`mymblog?uid=7198559139&page=1`
   返回 25 条，**前两条 `isTop=1`（置顶）**，第三条才是 2026-09-09 09:32 的新帖：
   ```
   [0] id=5339848496125575 isTop=1  Sep 05 2026   ← 已在库
   [1] id=5311295767188692 isTop=1  Jun 18 2026   ← 已在库
   [2] id=5341169661510821 isTop=None Sep 09 2026 ← 新帖，库里没有
   ```
3. **库内核对**：该账号 277 条微博，最新一条就是 `5339848496125575`（置顶那条），
   9/9 的三条新帖确实一条都没进来。

**根因**：增量模式（`stop_on_existing`）的停止条件是「遇到已入库的帖子 ⇒ 更早的必然
已入库」，并且只对**流首第 1 条**做了豁免（当年为 B 站单条置顶加的）。微博 `mymblog`
会把**多条置顶帖**排到流首且时间顺序被打乱：

```
idx0 置顶(已入库) → 豁免
idx1 置顶(已入库) → 不豁免 → 立即 break   ← 新帖全在 idx2 之后，整页漏抓
```

B 站同样存在该隐患（`modules.module_tag.text == "置顶"`，实测 mid=1203217682 的置顶是
2025-08、其后才是 2026-09 的新帖），只是「单条置顶 + 首条豁免」侥幸没暴露。

## 二、修复

两条循环（`_fetch_posts_core` 动态流 / `_fetch_platform_posts` 单流）改成同一套规则：

1. **平台侧标记置顶帖**：
   - 微博 `fetch_post_page` → 返回 `pinned_ids`（`isTop` 非空）；
   - B 站 `fetch_bilibili_dynamics` → 返回 `pinned_ids`（`module_tag.text == "置顶"`）。
   （放在**页面级**字段里，不塞进 item dict —— item 会直接 `Post(**d)` 入库。）
2. **置顶帖不参与停止判定**：命中已入库但它在 `pinned_ids` 里 → 继续扫。
3. **整页扫完再停**：不再当场 `break`，而是把「本页第一条已入库且非置顶的帖子」记成
   `known_hit`，循环走完这一页后再停。这样即使某平台没给置顶标记，
   同页里排在已入库帖之后的新帖也不会漏（停止边界 `stop_existing_pid` 仍是 `known_hit`，
   墓碑窗口语义不变）。

顺带删掉了「首页首条豁免」这个只对单条置顶有效的特例。

## 四、经验

- **「已入库即停」是拿流序换请求数**：一旦平台在流首插了乱序条目（置顶、推广卡、
  直播预约），这个不变量就断了。豁免名单要按平台**数据驱动**（`isTop` / `module_tag`），
  不能靠「第 1 条」这种位置假设。
- **停止判定放在整页之后**成本几乎为零（该页本来就要拉），却能把「同页乱序」这一类
  问题一次性挡掉；真正的省请求发生在**翻页**上。
- 增量抓取「stored=0 且无告警」= 高危信号：正常增量应该至少报 skipped 数或
  `stopped_early`，本次就是靠 `details` 里 stored 恒为 0 才被用户发现的。
