# 203-20260926-S1 连带：四个开发态工具漏带 token

真机验证（用户跑 `npm run tauri:dev`，1/2/4/5 项眼见为实）之后去翻日志收尾，**没查到 S1b 的问题，
却查出 S1 的一串连带**：所有"打自己后端"的**开发态脚本**都没带 token。

## 一、症状表（四个工具，四种伪装）

| 工具 | 表现 | 看起来像什么 |
|---|---|---|
| `dev_check.py` | 后端冒烟 `POST /auth/bilibili/qr/start` 401 ⇒ 整体 FAIL | **"当前网络不可达"**（它把 HTTPError 和 URLError 归成一类） |
| `smoke_upstream.py` | 5 腿里 4 腿 `HTTP Error 401` | **"上游挂了"** |
| `perf_report.py` | `PUT /settings/prefs` 401 ⇒ 没切成托盘语义 | 深休眠那一段量到的是"窗口还开着"的树（**假数字**） |
| `smoke_delete.py` | 手动起后端后逐条 401 | "后端坏了" |

四个都不是"像门禁问题"的样子 —— 这就是它挂了一整批没人发现的原因。
（S1b 只修了探针与 `probe.ts`；`ui_probe.py` 那条**在 A 档门禁里**，所以它红了会被立刻看到，
其余三个不在任何门禁里。）

## 二、根因：同一个固定值被各写一遍 + 谁都没被问"你打的是哪个后端"

修法不是"在四个文件里各加一行"，而是先给这个值一个**真源**：`scripts/dev_token.py`
（`DEV_TOKEN` / `HEADER` / `ENV` / `token()` / `headers()` / `backend_env()`）。
然后四个调用方全部改走它。

⚠️ 其中 `backend_env()` 还顺手堵了一个洞：它把 `DDTOOLKIT_API_TOKEN` **清成空** ——
`api_auth._expected_token()` **优先读它**，所以 shell 里任何一次手动运行留下的残留
都会让"脚本起的后端"选另一个 token，而脚本发的是 dev token ⇒ 又是 401
（本仓"本地残留环境恰好满足条件"的老毛病，第 N 次）。

## 三、机器判据（`tests/test_dev_token.py`，4 条）

1. **三处字面量同值**：`dev_token.py` ←→ `vite.config.ts` 的 `define` 默认值 ←→ `api.ts` 的
   fallback（TS 侧读不到 Python 常量，只能结构扫描）。
2. **两个名字对账**：头名 == `api_auth.TOKEN_HEADER`；env 名 == `config.py` 里读的那个。
3. ⚠️ **谁起后端谁就得给后端 token**：判据是"文件里有 `DDTOOLKIT_PORT` **且** 有 `Popen(`"
   —— 那才等于"我在起一个后端服务器"（`build_backend.py` 只是打包，不算）。
4. 四个调用方都得接 `dev_token`。

**反向验证**：把 `dev_check.py` 里的 `**backend_env(),` 删掉 ⇒ 第 3 条立刻红并点名该文件。
⚠️ 第一版判据写成"文件里出现过 `backend_env(`"——**反向验证当场发现它假绿**
（只留 import 也照样过）。判据改成匹配"并入 env 这个动作"（`**backend_env()`）才咬得住。

## 四、验证

- `dev_check.py`：**全绿**（`qr/start → qr_id=…`、`qr/check #1/#2 → waiting`）。
- `smoke_upstream.py`：**5 ok / 0 skip / 0 FAIL**（原先 4 FAIL）。
- `tests/test_dev_token.py` 4 条 + `tests/test_gate.py` 新增 1 条（这四个脚本落 A 档，
  否则"判据写了但 C 档不跑 pytest"）。
- 真机侧（用户实跑）：主窗/小窗注入、图片链路、托盘退出**均正常**；
  `app.log` 与 `shell.log` 里**零条** `拒绝未授权请求`，小窗的 `已注入后端端口 60349/53517`
  证明 `get_api_token` 在 `widget` 窗口上真的拿到了令牌。
  ⇒ S1/S1b 那两批的门在这台机器上**真的关上了**（此前"真机未验"的那一格现在有证据了）。

## 五、顺手确认的一件事（不是本批的 bug）

日志里那 4 条 `danmakus channel 失败 HTTP 302` **不是回归**：danmakus 的 API 主机早就是
`ukamnads.icu`（`DANMAKUS_BASE`，2026-09-07 起），旧域名 `danmakus.com/api/**` 现在整片
302 到新主机。同一轮里 6 个账号有 2 个成功（`刷新 1363 / 1207`）⇒ 是**上游间歇性**的
那类（同 `DEV-LOOP.md` §二·六 记过的"danmakus 间歇性变慢"），当天没有可动作项。
