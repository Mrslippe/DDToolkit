# 312-20261004 S2：B站播放内核换成 MSE（默认），渐进式退路两条

> 计划：`docs/plans/bili-mse-kernel-execution.md` §五 S2。S1 的 spike 证明"段表成立 + MSE 能跑"
> （`devlog/311`），这一批把它接进生产。**用户口径**：「默认 MSE、开关只作为退路。
> 因为当前卡顿太频繁了，几乎 90% 会出现」—— 所以默认值直接切，不再先 opt-in。

## 一、做了什么

| 侧 | 变化 |
|---|---|
| 后端 | `GET /bili/segments/{post_id}?qn=` 下发**段表**（`app/services/bili_segments.py::stream_tables`）：音视频各取 64KB 头部解析 `ftyp/moov/sidx`，带 110s 缓存；`mime_of()` 拼 `MediaSource.isTypeSupported` 要的**精确 codecs 串**。两条流缺一不可 —— 只有视频走 MSE 就又是"两个钟" |
| 前端内核 | 新 `utils/mseKernel.ts`：双 `SourceBuffer` 喂**同一个** `<video>`、**串行泵**、按段表 `Range` 取段、`WANT_AHEAD=20s` / `KEEP_BEHIND=25s` 淘汰、配额重试、镜像轮换、代数守卫 |
| 前端接线 | `VideoPlayer` 的 `segments` prop：给了就走 MSE（`dualTrack` 为假 ⇒ 独立音轨、漂移纠正、seek 音轨对齐**整段不进代码**）；`BiliVideo` 起播前先取段表（上限 4s） |
| 退路 | 新 `utils/videoKernel.ts`：默认 `mse`（localStorage，与音量/倍速同族）；**自动**熔断（不支持/取不到段/append 报错 ⇒ 当场退渐进式并熔断本次会话）+ **手动**开关（设置 → 外观 → 视频播放） |

## 二、五个真踩到的坑（都留了判据）

1. **同一个 SourceBuffer 同时只能有一个操作**。`appendBuffer`/`remove` 撞上就是
   `InvalidStateError`（spike 第一版就这么把泵打死的）。用例里的**假 SourceBuffer 会照样抛**
   —— 不然"单飞"这条只是注释，测不出来。
2. **`remove()` 的区间是秒，`init.end` 是字节**。第一版写成
   `keepFrom = Math.max(init.end + 1, currentTime - KEEP_BEHIND)` ⇒ `keepFrom` 恒 ≈948 秒 >
   缓冲起点 ⇒ **淘汰一次都没发生过**，长播必然撞配额。判据：80 秒的表 + 跳到 60s，
   必须出现 `remove:`。
3. **退回渐进式时别把 React 刚换上的 `src` 擦掉**。提交顺序是"DOM 变更 → effect 清理"，
   内核 `destroy()` 里无脑 `removeAttribute('src')` 会把新地址一起抹掉 ⇒ 元素永远没源、
   表现为"点了播放没反应"。现在只在我们**还是那个 blob** 时才摘。
4. **连续拖拽要靠"代数"作废在飞的取数**：晚回来的旧段会挤进新位置的计划里，
   轻则白取 1.5MB，重则和当前操作撞成第 1 条那个错误。
5. **CSP 的 `media-src` 不放行 `blob:` ⇒ MSE 在真机上等于没上**。MSE 把 `MediaSource` 挂成
   **blob URL**（`el.src = URL.createObjectURL(ms)`），而 `tauri.conf.json` 的 `media-src` 里只有
   `'self' http://127.0.0.1:* *.xhscdn.com` —— 真机上每条 MSE 流都会被 CSP 挡掉，内核当场判
   "不成立"退回渐进式：**功能静默失效、观感还是旧内核那样卡**。⚠️ 而**无头探针看不见**：
   它跑的是 vite 页面（没有 Tauri 那份 CSP 头）。已补 `blob:` + 一条反向验证过的用例
   （`test_csp_allows_blob_urls_for_media`；删掉 `blob:` 就红）。
6. **`useSyncExternalStore` 的快照必须引用稳定**：`mseSessionOff()` 第一版每次现造
   `{off, why}` ⇒ 快照永不相等 ⇒ **无限重渲染**，整个应用壳崩成
   "页面渲染出错：Maximum update depth exceeded"（无头探针第一条抓到的就是这个 —— 这一批里
   唯一被**现有门禁**当场抓住的错）。规律：快照要么是原始值，要么只在变化时换引用。

## 三、诚实记两笔

1. **无头环境判不了"能不能治"**（`devlog/311` 已记过一次）：真机那个 2–4 秒冻帧在这里复现不出来，
   所以 `docs/TODO.md` §1 把"你真机验一次"列为下一步；不能治就切设置里那个开关，零风险。
2. **段表是起播前取的**（多一次往返，实测几百毫秒）：不给它就先渲染，会"先用旧内核起播、
   再被 MSE 接管"—— 用户看到画面重来一次。所以宁可等（上限 4s，超时就走旧内核，不报错）。
