# 207-20260926-升级与迁移安全与诊断包

批次 16。**"很多人用 + 继续发版"之后，这一类故障的严重度超过本文档里任何一条**：
每次升级都会跑 schema 迁移，而档案在用户自己机器上 —— 你看不见、够不着、无法远程诊断。

## 一、之前的现状（三条都是"用户看见的样子"）

| 面 | 之前 | 后果 |
|---|---|---|
| 启动期迁移 | 唯一保护是"迁移在事务里"，**没有任何备份** | 中途失败（磁盘满 / 断电 / SQLite locked）⇒ **打不开 + 没有退路** |
| 失败时的库 | 就躺在原地 | 应用起不来，用户不知道"数据其实没坏" |
| 启动失败文案 | 一句"内置后端服务未能在时限内就绪……请关闭应用后重新打开" | **分不清**"迁移失败 / 端口占用 / 杀软首扫慢 / 后端崩了" |
| 诊断材料 | `bootDiag` / `sidecar.log` / `app.log` 散在三处 | **没有"一键导出成一份能发给开发者的东西"** |

## 二、这一批做了什么

1. **迁移前自动备份**（不变量 27）：`backups/vtuber-<head>-<时间戳>.db`，
   **复制 `-wal`、不复制 `-shm`**（WAL 里是已提交数据；`-shm` 是索引，SQLite 会重建）；
   **快路径不备份**（常态启动不付这个代价）；保留 3 份 / 300MB 封顶 / 按最旧淘汰 /
   **永远留最新那份**。
   ⚠️ 排序用**文件名里的时间戳**，不用 mtime —— 第一版用 mtime，复制/还原过的备份会让
   "最旧"变随机；而且写测试时当场发现"体积超限"那条分支把**最新**那份删了（判据抓的）。
2. **失败绝不留下打不开的库**（不变量 28）：坏库隔离成 `vtuber.db.failed-<时间戳>`
   （**连同 `-wal`**；`-shm` 删掉），**用空库继续启动** ⇒ 应用可用、档案没丢。
   隔离前必须 `engine.dispose()`（Windows 上句柄没放就改不了名）。
3. **分类告知**：`/healthz` 新增 `migration` 字段（**唯一能在还没拿到 token 时带出启动期
   故障的通路**），前端 `utils/bootFailure.ts` 把它变成人话，并且**只有 schema 迁移失败
   才允许说"数据可以找回"**——端口占用/超时误报成数据问题会诱导用户去动数据目录。
4. **诊断包**（`GET /settings/diagnostics`）：版本 / OS / Python / 迁移结局 / 库形态
   （schema 版本 + 表 + 行数）/ 备份与隔离库清单 / 占用 / 三个日志的尾部，
   总量封顶 + 截断标注。**绝不含凭据**（`.env`、cookie、token 一律不读）。
5. **界面**：迁移失败时挂一条**非阻塞横幅**（应用能用就别挡屏）+「打开数据目录」
   （Rust `open_data_dir`，路径取自壳自己的状态，前端传不了路径）+「导出诊断」
   （弹窗里全选复制 —— WebView 剪贴板权限不保证，只靠 `navigator.clipboard` 等于按钮不存在）；
   启动幕的失败页按分类文案 + 同样一个「打开数据目录」。存储面板多一行「迁移备份」。

## 三、判据（`tests/test_migration_safety.py`，16 条）

- 备份：带 `-wal` / 不带 `-shm` / 不留 `.part` / 没库时说 skipped / 保留份数 / **体积超限** /
  **永远留最新** / 淘汰时连 `-wal` 一起删 / 计入存储体检；
- 真跑迁移：**快路径不备份**、落后一版 ⇒ **真跑 + 备份里的库是迁移前那一版**（能回退才有意义）；
- 失败路径：坏库被隔离、原路径上有一本能打开的新库、被隔离的库**没被动过**、
  `/healthz` 把失败报出来；
- 备份失败（磁盘满）⇒ **继续迁移但状态里带 error**；
- 诊断包：四个 section 齐、**植哨兵凭据断言不出现**、库读不动也不抛、超长截断并标注。

**反向验证（四条，各自对应一句承诺）**：

| 改法 | 结果 |
|---|---|
| 去掉迁移前备份 | `test_real_migration_backs_up_first` 红 ✓ |
| 去掉隔离 + 空库重建（= 今天之前的行为） | `test_migration_failure_quarantines_and_keeps_the_app_usable` 红（RuntimeError 直接冒出来）✓ |
| 把 `.env` 也打进诊断包 | `test_diagnostics_never_leaks_credentials` 红 ✓ |
| 删掉诊断包里的"迁移结局"段 | `test_diagnostics_carries_the_sections_support_needs` 红（已作为该用例 docstring 的反向验证）✓ |

前端另有 6 条（`bootFailure.test.ts`）：迁移失败 ⇒ 说"数据没有丢"并给出两个位置；
没有备份 ⇒ 明确说出来；**后端没应答 ⇒ 不得说成数据问题**（断言里不许出现"找回"字样）；
迁移正常 ⇒ 不显示横幅（不给常态启动加噪音）。

## 四、实测踩到的两个坑

1. **`prune_backups` 第一版按"最新在前"正着遍历** ⇒ 体积超限时删掉的是**最新**那份、
   留下更旧的 —— 是"体积上限"那条断言把它咬出来的（现在从最旧那端删，并写明为什么）。
2. **排序键选错**：`list_backups()` 一开始按 mtime 排序，而测试里同一秒创建的几份备份
   mtime 顺序不稳定 ⇒ 用例红。真因不是测试写得不好，而是**"最旧"不该由 mtime 定义**
   （复制/还原/同步都会改它）⇒ 改成按文件名里的时间戳。
