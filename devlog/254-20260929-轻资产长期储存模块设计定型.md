# 254-20260929-轻资产长期储存模块（设计定型）

起因是用户头像那次事故的**收尾提问**：「头像这种轻资产可以作为固定资源保留在本地，然后每次更换
就不用重新发请求了；同理未归档帖子或体积小的轻资产可以固定在数据储存路径中，降低请求频率」
—— 于是 C（"允许选项指向本地文件"）从"补一列"升级成**一个模块**。

## 一、设计结论（全文见 `docs/design-light-assets.md`）

四条硬结论，都是查实之后才写的（2026-09-29 实测，证据在文档 §0）：

1. **稳定键**：微博头像 URL 带 `Expires`/`ssig` 签名，**同一张图每次抓取都是新 URL**
   ⇒ 索引/去重/查盘一律按「**去掉签名参数后的 URL**」。实测反证：`weibo_7471118487.jpg` 与
   `..._3d2b0b8a.jpg` 的 **sha256 完全相同**（2026-09-29）。
2. **文件名用 URL 摘要（可预测），内容摘要另存一列**：后者当文件名就必须先下载才知道 ⇒
   恰好废掉"少发请求"这个主收益。两条都要：一条负责预检、一条负责去重与校验。
3. **本地兜底走派生字段，不给 `vtubers.avatar` 塞两种形状**：`VTuberOut.avatar_local`（现查 assets）+
   `ProxyImage` 的 `fallbackSrc`（回落链加一级："直连 → 代理 → **本地** → 占位"）。
   ⇒ 微博那张签名过期的头像（V#16，**已过期 21 小时**，今天靠 `/img-proxy` 缓存续命）从此闭环。
4. **`static/assets/` 与 `static/img-cache/` 不合并**：前者"认定的长期资源"（有索引、有 pin、有引用保护），
   后者"任意远端图的临时缓存"（7 天 / 300MB / 可随时清）。判据：**清空 img-cache 后外观不变**。

## 二、批次

**L1**（索引 `f009` + `services/assets.py` + 头像接入 + `avatar_local`/`fallbackSrc` + 账本按稳定键归并
+ 回填本次丢失的那条）→ **L2**（stats/prune/pin + 设置页读数）→ **L3**（未归档帖封面固化 + `cover_local`）
→ L4（其他 kind，可选）。

⚠️ **L3 的收益必须实测后再写结论**：浏览器与 `/img-proxy` 本来就有缓存，确定性收益是
"离线可看 + 源站死了也能看 + 缓存淘汰后不回源"，**不是**"大幅降低请求频率"。
