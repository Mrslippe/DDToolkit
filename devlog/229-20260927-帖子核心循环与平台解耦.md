# 229-20260927-帖子核心循环与平台解耦

第 4 阶段的 ①（`EXECUTION.md` §1.4「调研结论回来后顺序固定为」第 ① 条）：
**把 B站专属双流逻辑从 `_fetch_posts_core` 隔离成平台适配器**。
目标照计划原文 —— **不是"支持新平台"，而是"让 scheduler 不再假设自己是 B站"**。

## 一、原来"假设自己是 B站"长什么样

`_fetch_posts_core`（约 270 行）里混着两层东西：

- **编排**：双流翻页、批量落库/内存去重、归档边界、风控断点续抓、置顶豁免、增量停止、
  `limit_latest`、`natural_end` 记账 —— 这些**与平台无关**；
- **B 站协议细节**：`fetch_bilibili_videos` / `fetch_bilibili_dynamics` 直调、`Post.platform == "bilibili"`
  写进去重与**归档**查询、`_cooldown_for_rate_limit("", "bilibili")`、直播卡路由、opus/专栏详情补全、
  bvid 合并、置顶刷新。

⇒ 后果不是崩溃，是**静默错误**：拿这个"核心"去跑别的平台，**归档边界永远不触发**
（它查的是 B 站那份帖子），帖子会被反复重取。

## 二、这一刀做了什么

**新增 `app/services/platforms/streams.py`** —— 一个纯数据类 `PostStreams`：

```python
PostStreams(platform, fetch_video_page, fetch_dynamics_page,
            bvid_index?, absorb_video_dynamic?, route_non_post?, enrich_item?, refresh_pinned?)
```

两条流回调必填，**五个平台专属台阶可选**（B 站需要，单流平台多半不需要）。
模块**刻意不 import scheduler / fetcher**（否则成环），代价是载荷用 `Any` 描述。

**`scheduler.py` 里只有一处绑定**（`BILIBILI_STREAMS`，紧挨着核心函数上方），
把 B 站那套实现接上去；核心函数签名多一个 `streams: PostStreams = BILIBILI_STREAMS`
⇒ **调用方零改动**（默认值就是 B 站），风险面被压到最小。

核心函数里 10 处替换：两处查询用 `streams.platform`、两条流走回调、冷却平台名走
`streams.platform`、直播卡路由 / bvid 索引 / bvid 合并 / 详情补全 / 置顶刷新各走一个回调。

## 三、判据（`tests/test_posts_core_platform.py`，5 条）

机器判据分**行为层**与**结构层**，缺一不可：

1. **行为**：注入 `platform="weibo"` 的假适配器后，**归档边界必须按微博的帖子触发**
   （库里一条 `platform=weibo` 的已归档帖子 + 假动态流返回它 ⇒ `archived_stop is True`
   且 `stored == 0`）。旧实现此时归档集合恒为空 ⇒ 这条**必红**。
2. **行为**：注入的两条流回调**真的被调用**（否则第 1 条可能只是"恰好"成立）。
3. **结构**（AST）：核心函数的源码里**不许出现 `"bilibili"` / `"weibo"` 字面量，也不许直调
   `fetch_bilibili_*`** —— 这条直接编码了本刀的目标。
4. **结构**：B 站绑定必须完整（平台名 + 两条流 + 五个台阶都在）——少一个就是"运行时静默少做一步"：
   详情不补全、bvid 不合并、置顶不刷新，都不会报错。
5. **契约**：`streams` 的默认值就是 `BILIBILI_STREAMS`（调用方零改动）。

**反向验证三刀全红**：归档查询退回写死 `"bilibili"` ⇒ 第 1、3 条红；动态流退回直调
`fetch_bilibili_dynamics` ⇒ 第 2、3 条红；绑定里删掉 `enrich_item` ⇒ 第 4 条红。

## 四、⚠️ 这是第一刀：边界如实交代

| 还留着什么 | 为什么留给下一刀 |
|---|---|
| B 站专属**实现**（`_enrich_dynamic_item` / `_absorb_video_dynamic` / `_route_live_item` / `_video_bvid_index` / `_refresh_pinned_post`）仍在 `scheduler.py` | 搬它们要动 ~250 行 + 若干 monkeypatch 点（计划里"整体拆分搁置"的理由就是这个）；**先把接口切出来、行为不变**，再搬实现 |
| `uid` 仍是 `int`（`platform_uid = str(mid)`） | 泛化成字符串要同时改 `_fetch_posts_for_account` 的取整校验与 B 站批量接口的调用方；单独一刀 |
| 双流形状（先视频后动态）仍在核心 | 它是**编排**不是协议；真要做单流/多流平台时再抽 |
