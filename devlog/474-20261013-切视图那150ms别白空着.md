# 474-20261013 切视图那 150ms 别白空着：把日历那一发抢跑出去

> 用户追问：「现在切换到数据视图要等到动画结束之后才能出现日期格的内容，**这也是我们的
> 工作引入的吗**」。查清了：**不是** f016/f017 引入的（那两批都在后端数据层，前端一行没动），
> 但现象是真的，而且原因很具体 —— **一段本可以重叠的等待，被排成了串行**。

## 一、一次切视图实际发生什么

| 阶段 | 耗时 | 内容 |
|---|---|---|
| ① 退场动画 `.scene-exit` | **150 ms**（`EXIT_MS`） | 旧视图 fall-out |
| ② 提交 + 新视图入场 | ~50–150 ms | `LiveCalendar` 这时才**挂载** |
| ③ 卡片挂载后才取数 | **176 ms**（实测中位） | `GET /live-sessions` |
| ④ 渲染日期格 | ~10 ms | |

⇒ **①+②+③ ≈ 350–400 ms**，而 **③ 整段落在动画之后** —— 用户看到的就是"等动画播完，
日期格才慢慢填上"。

根因在 `useSceneTransition`：**预取只在账号变化时发起**（`if (accChanged) startPrefetch(...)`），
切视图时它什么都不预取，只播 150ms 退场就提交。横向对比：场景预取里那一发
`GET /vtuber/{id}` 只要 **6.4 ms** —— 快的是它，慢的那发根本不在预取清单里。

## 二、改法：窗口里抢跑 + 首帧种子

1. `useSceneTransition`：视图变化也发起预取，**但不进"等就绪"的门**（换 V 才等）——
   退场定时器照旧 150ms，抢到就用、抢不到就算了（卡片自己取，与改动前等价）；
2. ⚠️ **预取的复用键从 `acc` 改成 `(acc, view)`**：切视图时账号不变、要的数据却不同，
   只按账号复用会拿到上一轮给别的视图准备的那份；
3. `PostsPage::prefetchScene`：目标是 `archive` 时并发预取 `liveSessions(account)`；
   `onCommit` 经 `seededSessionsKeyRef` 交给日历（**同一个 refreshTick 只播种一次**，
   "没抢到"要**置空** —— 留着上一轮的种子，症状是"数据没更新"，其实只是旧的）；
4. `useLiveSessions`：种子当**首帧初值**，并**跳过首拉** —— 种子就是几毫秒前上游给的那一份
   （预取刚打完），再打一遍等于同一屏发两个一模一样的请求。之后 `refreshTick` 一变照旧自己取。

## 三、判据

`components/LiveCalendar.seed.test.tsx` 三条（jsdom + `createRoot`，同 `coverSource.wiring` 的写法）：

- 给了种子 ⇒ 首帧文本里就有那一场，且 `api.liveSessions` **一次都没调**；
- 没种子（预取没赶上/失败）⇒ 照旧自己取一次并渲染出来（与改动前等价）；
- `refreshTick` 变了 ⇒ **必须真重取**（种子只顶首帧，不是"永远不取"）。

**反向验证**：把 `seedSessions` 掐成 `null` ⇒ 前两条立刻红（第三条仍绿，正是它该有的形状）。
⚠️ 变异要用 `edit` 工具做 —— 这一轮先用 PowerShell `Get-Content/Set-Content` 改，
把 UTF-8 中文写坏了（`esbuild` 报解析错），本仓记过的那个坑又踩了一次。

数：vitest **1369 / 115 文件**（+3）· tsc 0 错 · `ui_probe` 两档全过。

## 四、诚实记一句取舍

种子是"切视图那一刻"的数据 ⇒ 最坏比实时**旧几十秒**（下一次 `fetch-idle` 就会刷新，
而它每轮都会 bump `refreshTick`）。用户口径是「感觉没什么损失」，所以按这个做了；
想要"首帧必须最新"就只能接受那 176ms 的等待 —— 两者不可兼得。
