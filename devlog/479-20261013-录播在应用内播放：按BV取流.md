# 479-20261013 录播能在应用里播了：按 BV 取流 + 播放器

> 上一批（`devlog/478`）把录播入口搬到了封面，但 `▶` 还只是"交给系统浏览器"——
> 因为缺一条"按 BV 取流"的路。这一批把它补上：现在是**应用内播放**。

## 一、为什么必须新开端点，而不是改老的

`/bili/play/{post_id}` 的前提是"这条视频是一个**帖子**"：`_bili_bvid_of(db, post_id)`
要查库把 post_id 翻成 bvid。而**录播不是帖子** —— `live_sessions.vod_url` 指向的多半是
录播组发的视频，我们库里根本没有那一条 post ⇒ 那条路走不通（真走会 404「Post id=… 不存在」，
用户看到一句莫名其妙的话）。

服务层本来就吃 bvid（`bili_play.play_info(bvid, …)`），所以这一批只是补上**入口那一层**：

| 新增 | 与谁同口径 | 差别 |
|---|---|---|
| `GET /bili/play-by-bvid?bvid=&qn=&fallback=&cid=` | `/bili/play/{post_id}` | bvid 从**参数**来（收 BV 号或链接，与入库同一个抠号函数 `bvid_of`） |
| `GET /bili/segments-by-bvid?bvid=&qn=&cid=` | `/bili/segments/{post_id}` | 同上 |

顺手把四处重复的错误分类抽成 `_play_error_to_http()`（`not_found` 404 / `forbidden` 403 /
`risk_control` 429 / 其余 502）——**抽的理由不是少几行**：四处各写一遍时，以后补一类 kind
必然漏掉某一条路，而症状是"同一种失败、两条路给不同状态码"，前端按状态码分的分支就跟着错。

## 二、前端

- `api.biliPlayByBvid` / `api.biliSegmentsByBvid`；三条老/新调用点共用一个 `biliPlayQuery()`
  （`qn`/`fallback`/`cid` 的口径只写一份 —— 少一个参数就是"段表与播放地址不是同一条流"）。
- `BiliVideo` 多了一个 **`bvid` 入口**：`postId` 与 `bvid` 用**联合类型**二选一（`tsc` 保证
  "恰好给一个"）。⚠️ 踩到一个坑记在这里：`interface Props extends Source`（Source 是联合）
  **不合法**，而且报出来的错在**测试文件**里（`Property 'postId' does not exist`）——
  正解是 `type Props = Source & {...}`。
- 新增 `VodPlayerDialog`（`.vodp` 面板，比详情窗宽）+ `vodTarget()`（纯函数：地址 → `{bvid, page}`）。
- **分P**：`vod_url` 里的 `?p=N` 拆成 `initialPage` 往播放器传，`BiliVideo` 拿到 `pages` 之后
  按那一 P 的 cid **再取一次**（只跳一次，有闸门）。不拆的后果是"多 P 录播只播第一段"——
  与 `devlog/329` 在帖子播放上修过的是同一类问题，录播这条路上不能再来一遍。
- 面板右上角留了**「在浏览器打开」**的退路：真机上偶有播不动（风控/权益/内核），
  别让用户没有出路。

## 三、判据

- 后端 **+13 条**（`tests/test_vtuber_api.py`）：绑定/链接两种入参、抠不到号 **400 且是中文原因**
  （不是 500）、四种 `PlayError.kind` → 状态码**四条路由同一套**、段表 `cid` 原样接到服务层。
- 前端 **+12 条**：`BiliVideo` 的 bvid 分支 3 条（★`initialPage=3` 真会按第 3 P 的 cid 再取一次；
  给 bvid 时**不打**按 postId 那条）、`VodPlayerDialog` 5 条（bvid/分P/标题/认不出就不开/退路）、
  `vodTarget` 4 条（含 `?p=1` 与不传等价）。
- ⚠️ **这一批没有探针判据**：真播一段 B 站录播要联网且要登录态，放进门禁会变成"看上游脸色"
  的假红。所以覆盖到"接线递对了参数"为止；**真机播放**仍在 `TODO.md` §1.3 的人工清单里。
