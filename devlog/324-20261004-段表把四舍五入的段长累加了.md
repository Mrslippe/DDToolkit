# 324-20261004 长视频跳转根因（二）：段表把四舍五入的段长累加了

> 用户复现（`devlog/323` 之后）：「点击跳转后缓冲 3s 开始播放，然后又一直卡住转圈，复现了两次」。
> 这次日志 + 真机数据把根因钉死了 —— 与 322/323 是**同一处现象的最后一环**。

## 一、现象与现场

```
15:56:25 跳转 2664.6s 落地：用时=2.6s 缓冲=3.7s 段取=20次
15:56:25 跳转 2664.6s：等了 2.6s 只有 3.7s 缓冲（取数跟不上实时码率）
```

"取数跟不上实时码率"是**误判**：代理侧每段 2MB / 0.2s、**9–10MB/s**（吞吐富余十倍）。
真正发生的是音频轨把**同一段连取 3 次**（`57338658-57456839` ×3，每次 0.03s、字节数正确）
而缓冲不长。

## 二、钉死根因的两步实测

1. **认出视频**：`BV1esa36qEPX`（泽音 Melody 最新那条，动态视频 `#4919`，库里标称 02:13:30）——
   拿真机的音频字节区间当指纹在段表里比对，918 段 / 4586.97s / 音频 total=100,503,128 全对上。
2. **读段自己的 `tfdt`**（段表说的时刻 vs 段里写的时刻）：

   | 真机取的字节区间 | 段表说它从 | 段自己 `tfdt` 说 |
   |---|---|---|
   | video `403662616-405705578` | 2680.00s | **2680.00s** ✓ |
   | audio `57338658-57456839` | 2663.50s | **2663.24s** ✗ 偏晚 0.26s |

   **数据是对的，表是偏的**：`dur_s` 是四舍五入过的（音频 5.0155 → 5.016，每段多算 0.0005s，
   531 段累计偏晚 0.26s）。视频轨段长正好 5.000s ⇒ 不偏 ⇒ **真机上只有音频轨坏**。

后果：`nextSegmentAfter(table, 缓冲末尾)` 里那个"结尾越过 time 的第一段"永远是**刚取过的那一段**
⇒ 泵反复重取同一段（`grew=false`、缓冲不长）⇒ 播 3 秒饿住 ⇒ **一直转圈**。
（这也是 322/323 里 `重复=2` 冻死与"音频轨从开播后再没取数"的上游原因。）

## 三、修法：不许累加四舍五入值

1. **后端**（`services/bili_segments.segment_table`）：每段下发**精确起点 `t`**，
   按**原始 tick 累加**得出（不累计舍入），并给整表一个 `duration_exact_s`；
2. **前端**（`utils/mseKernel`）：`segmentStarts` 优先用 `t`（缺了才退回累加，老后端仍能播）；
   `nextSegmentAfter` 把**下一段的起点**当作这一段的结尾（`starts[i] + dur_s` 是两个舍入值相加，
   与真实边界能差零点几秒）。

## 四、判据

- 后端 `test_segment_starts_do_not_accumulate_rounding`：用**除不尽**的段长
  （80010/16000 = 5.000625 ⇒ 写成 5.001）证明 `t` 是按 tick 累加的（0 / 5.001 / 10.001 而不是
  0 / 5.001 / 10.002），旧断言在 5.000s 整除的夹具上看不出这个问题；
- 前端两条**互为正反**：同一张"表里写 5.0（四舍五入）、真实 4.99"的段表 ——
  **带 `t`** ⇒ 续播必须往前走（缓冲过 30s、取到 3 个以上不同段）；
  **不带 `t`**（老后端）⇒ 现象可复现（卡在 25s）。第二条就是这次反向验证的常驻版本。

## 五、为什么三批才修到根上（诚实记一笔）

322 修的是"收手把播放点挪进洞里"（现象层的死循环），323 修的是"防打转计数器把一条轨永久冻死"
（把 322 暴露出的状态冻死堵住），这一批才是**上游原因的本身**：段表时刻偏了 0.26s。
三次都是用户复现 + 一行现场日志推着往前走 —— 没有 322 加的 `seekDetail`、没有 323 的
"守卫触发要说一句"，就看不到 `重复=2`，也就找不到这里。
