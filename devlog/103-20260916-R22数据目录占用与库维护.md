> 方案确认后："预期看来并不会太大，目前阶段就加上 **A、B、D**"（C = raw_json 瘦身，暂缓）。

## 一、实测：到底谁在占地方

| 项 | 实测（开发档：8 个 V / 11 账号） | 说明 |
|---|---|---|
| 库 | **54.3 MB** ⇒ 约 **6.8 MB/V** | 其中 `posts.raw_json` **24.8 MB（46%）**，平均 **5.9 KB/帖** |
| 图片缓存 | **101.7 MB / 271 文件** | 只管时间（TTL 7 天、文件留到 14 天），**完全没有上限** |
| 日志 | 5.7 MB | 按天轮转 + 保留 7 份 ✓ 已受控 |
| 遗留备份 | 一个 **54.3 MB** 的 `vtuber.db.bak-20260913-141254` | **不是程序生成的**，纯占地方 |
| 库设置 | `auto_vacuum=0`（NONE） | 删数据只进 freelist（实测 554 页 / 2.2 MB），**文件永不缩小** |
| C 盘 | 剩 **7.9 GB** | 用户现状 |

**结论**：会挤占，而且**图片缓存比库涨得更快** —— 所以这一批先把它管住。

## 二、A：图片缓存的容量上限（`app/routers/img_proxy.py`）

- 新增 `IMG_CACHE_MAX_MB`（**默认 300**，环境变量 `DDTOOLKIT_IMG_CACHE_MAX_MB` 可覆盖）；
- `prune_cache()` 两段清理：① **过期**（`mtime > TTL × 2`）② **超上限**时按 **mtime 最旧优先**淘汰到上限以下；
- **命中缓存会刷新 mtime** ⇒ mtime 就是"最后使用时间"，淘汰近似 **LRU** ——
  左栏头像、常看的封面这类热图不会因为"抓得早"被误删（这正是判据容易写错的地方，用例钉住了）；
- `bin` 与 `json` **成对删**（只删一个会留下"有元数据没图"的坑）；
- 上限设 **0 = 只按时间清**（给"我不想让它自动删"留退路）；
- 新增 `cache_stats()`，给日志与下一批的「关于」页用。

> **为什么不做成设置项**：这是"多大算大"的运维参数。设置窗口刚因为"选项太多"精简过（R21），
> 再塞一个没人看得懂的旋钮是倒退 ⇒ 放环境变量 + 让「关于」页把占用**显示出来**就够了。

## 三、D：库维护（新模块 `app/services/db_maintenance.py`）

| 函数 | 干什么 |
|---|---|
| `dir_stats()` | 体检：库（含 `-wal`/`-shm`）/ 图片缓存 / 日志 / 其余，各自字节数与文件数 + **磁盘剩余** + **遗留备份清单** |
| `sqlite_stats()` | 页大小、页数、freelist 页数、`auto_vacuum` 模式 |
| `ensure_incremental_autovacuum()` | 一次性把库切成 `auto_vacuum=INCREMENTAL`（幂等；**超过 512 MB 就不动手**，只记日志） |
| `incremental_vacuum()` | 把 freelist 的空闲页还给系统 |

两个调用点：
1. **启动时**（`app/main.py` lifespan，紧跟迁移之后）：切换 auto_vacuum。失败只留日志 —— 它是体验优化，不能挡启动；
2. **破坏性清理之后**（解除订阅 V / 删除账号，`app/routers/vtuber.py`）：调 `incremental_vacuum()`。
   只有这类操作才会一次产生大量空闲页，所以**不做成"每次写都调"**。

⚠️ 两个技术要点（都用真库跑过用例，不是想当然）：
- `PRAGMA auto_vacuum` 与 `VACUUM` **不能在事务里**执行 ⇒ 绕过 SQLAlchemy 的隐式事务，
  用 DBAPI 连接的 autocommit（`driver_connection.isolation_level = None`）；
- 切换 auto_vacuum 需要一次**全库 VACUUM**（临时空间约等于库大小）⇒ 512 MB 门槛 +
  只在启动时做一次，不做成用户点一下就整库重写。

## 六、真源复核（只有真库才会暴露的两件事）

拿**真实的开发库**（54.3MB / 8 个 V）跑了一遍维护逻辑，抓到两个临时库测不出来的问题：

1. **切换确实有效**：`auto_vacuum 0 → 2`，freelist **551 页 → 0**，库文件 **54.3MB → 50.9MB**；
2. **⚠️ WAL 会胖到 ≈ 库大小**：WAL 模式下 `VACUUM` 会把**整库重写进 WAL** —— 切换后
   `dir_stats()` 显示 database 组 **105.4MB**（库 50.9 + WAL 54.4）。它不会自己消失：
   **只有最后一个连接关闭**时 SQLite 才自动 checkpoint，而应用自己就握着一池连接
   ⇒ 新增 `checkpoint_wal()`：启动时显式 `PRAGMA wal_checkpoint(TRUNCATE)`
   （**对"已经切换过"的库同样要跑**，否则上次留下的胖 WAL 会一直躺着）。
   实测回收 **54.4MB**（105.4 → **51.0MB**），数据目录总量 267.5 → **213.1MB**。

> **教训**：这类"删了数据、文件却没变小"的问题**必须在真库上看一眼** —— 临时库太小，
> WAL 那一步的量级完全显不出来（临时库跑完 WAL 是 0 字节，看起来一切正常）。
