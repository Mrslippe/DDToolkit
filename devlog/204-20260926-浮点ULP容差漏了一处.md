# 204-20260926-浮点ULP容差漏了一处（CI Windows 腿偶发红）

`f88c66c` 推上去之后 **Linux 腿绿、Windows 腿红**，红的不是本批改的东西：

```
tests/test_dynamics_backoff.py::test_next_due_honours_idle_floor
E   assert (698.031 - 398.031) >= 300
```

`698.031 - 398.031 = 299.99999999999994` —— 又是**浮点 ULP**，也就是 devlog/200 那一次。

## 一、为什么第一次没修干净

devlog/200 修的是同一个类：`_dynamics_next_due` 内部是 `due = max(due, since + idle_floor)`，
所以"再减回 `since`"会掉几个 ULP。当时的修法是**给几处下限断言加 `FLOOR_EPS = 1e-3`**
（写了一处命名常量 + 四处引用），**但漏了 `>= 300` 那一处** —— 它长得跟别处一样，
只是没被点到名。

⇒ 教训不是"再加一个容差"，而是「**靠人把同一族的每一处都点到名**」这件事本身不可靠：
这次补完必须**让机器去数**。

## 二、这次怎么修的

1. 漏掉的那处补上 `- FLOOR_EPS`；
2. 文件头写清"**这一族下限断言一律写 `>= N - FLOOR_EPS`**"，并记下第二次事故；
3. **新增判据 `test_every_lower_bound_uses_the_ulp_tolerance`**：扫本文件与
   `test_quiet_hours.py` 的源码，凡是"`- <名字> >= <数字>`"的形状里没带
   `FLOOR_EPS`/`1e-3` 的，**红并点名行号**。
   反向验证：把那处改回裸比较 ⇒ 只有 137 行被点名（第一次写的时候把**自己的 docstring**
   也扫进去了 —— 判据的举例文字会命中判据本身，本仓已记过一次同类坑）。

## 三、为什么它只在 CI 上红（本地复现不出来）

要不要红取决于 `time.monotonic()` 的**绝对值与小数部分**：

- 本地/干净 clone 实测 **641 passed / 1 skipped**（我把 `f88c66c` 克隆到临时目录、
  `uv sync --frozen`、`uv run pytest tests/ -q` 跑过一遍，红不了）；
- CI 那台机器当时 `since ≈ 398.031`（有小数）⇒ `(since + 300) - since` 落在 300 的下方。

⇒ 这一类**判据不许靠"多跑几次看看"**来确认，只能靠机器扫描（上面第 3 条）。

## 四、附带确认

- 失败与 S1/开发态 token 那批**无关**：`git bisect` 意义上，前一条 `571874d` 只是当时
  `monotonic` 的取值恰好不在坑里。
- 这一批其余部分（devlog/203 的四个工具）在 Windows 腿上**都跑过了**：Rust 单测、
  uv 装环境都绿，红的只有这一条断言。
