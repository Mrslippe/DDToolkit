# 211-20260926-R1调度生命周期可停止

接 devlog/210。批次 6 = 计划 §R1：**lifespan 退出后不再有线程在跑；重复启动不产生双份**。

## 一、改前的事实（计划 §2.10 核实，逐条复核过）

| 线程 | 睡眠（逐字） | 能不能停 |
|---|---|---|
| APScheduler 工作线程 | `_wait_for_manual_tasks` 里 `time.sleep(poll_seconds)`，最坏 **1800s** | 只能 `shutdown(wait=False)` |
| `startup-external` | 无 | 一次性 |
| `t0-live-poller` | `time.sleep(STARTUP_CHAIN_DELAY)` + `time.sleep(_tier_delay(...))` | 只能靠 `LIVE_POLL_SECONDS<=0` 在 while 判断处退出 |
| `tier-scheduler` | 同上，`while True` | ❌ **无任何手段** |

全模块 `Event.wait` **零命中**；`start_scheduler` / `start_live_poller` / `start_tier_scheduler`
每次调用**无条件再起一份** ⇒ 连续两次 `TestClient(app)` lifespan 会真的双跑
（两套线程各跑各的轮次，抢同一把抓取锁）。

**用户看到什么**：退出应用后后台仍在按预算打平台接口；开发态里"上一轮测试起的线程"
抓着 `_fetch_lock` 不放，泄漏给后面所有用例（`tests/test_real_fixtures.py` 那条
"不要写 `with TestClient(app)`"的警告就是它的化石）。

## 二、改了什么

- 新增 `SchedulerRuntime`（`app/services/scheduler.py`）：统一持有 `threading.Event`
  停止事件、三个线程句柄、APScheduler、**在飞事件循环登记表**。`start()` / `stop()` 幂等。
- 5 处 `time.sleep` → `rt.wait(...)`（可中断）；`asyncio.run` → `rt.run(...)`
  （循环登记在册 ⇒ 停止时能取消在飞轮次，而不是等一次网络往返）。
- **stop 顺序**：不接新任务（`accepting()`）→ 置停止事件 → 取消在飞轮次 →
  join（**超时告警**，daemon 只作兜底）→ 关 APScheduler。
- `main.py`：四个 `start_*()` → 一个 `scheduler_runtime.start()`；关停时**先 stop 再关共享
  HTTP 客户端**（反过来，被取消的轮次会在一个已关闭的 client 上收尾）。
- `_wait_for_manual_tasks` 进停止语义（否则"关闭"最坏要等半小时）。
- 删掉 `start_live_poller` / `start_tier_scheduler` / `start_external_catchup` /
  `shutdown_scheduler` 四个别名，只留 `start_scheduler()`（旧入口，返回 APScheduler）。
  **四个名字做同一件事 = 四处要找的地方**；文档同步改指运行时。

## 三、两个真实踩到的坑

1. **"置停止"与"登记循环"之间有竞态**：第一版 `stop()` 先置位、再取在册循环；线程若在
   "置位之后、登记之前"把轮次跑起来，那一轮**永远等不到取消** —— 症状是 `stop()` 白等到
   join 超时才返回（第一版就红了 2 条用例，5.45s 那两条）。修法：登记与置位**共用
   `_loops_lock`**，于是只有两种结果 —— 要么被取消，要么压根不跑。
2. **停止事件不许留成"这个进程永远完了"**：第一版让"从未启动"的 `stop()` 也置位，
   结果 `_wait_for_manual_tasks()` 之后一律返回 False —— **毒到了后面两条与本批无关的
   用例**（`test_services.py` 的外部批次排队，红了才发现）。现在：没启动过 = 不广播；
   全部停干净 = **收回**；只有留下 straggler 时才留着（让它们在下一个检查点退出）。

## 四、判据（`tests/test_scheduler_lifecycle.py`，12 条）

线程各只有一份 + `start()` 幂等 · stop 后归零且幂等 · **等待中可停** ·
在飞轮次被取消 · 手动等待可叫停（返回 False，不照跑）· start-stop-start 不留上一代 ·
**真 lifespan 连跑两次不双跑、退出后线程归零** · 运行时不许持有 asyncio 原语（§6 第 15 条）。

**反向验证（5 种改法，实测全红）**：

| 改法 | 红的那条 |
|---|---|
| `rt.wait(...)` 退回 `time.sleep(...)` | 等待中可停 ✓ |
| 去掉 `start()` 的幂等守卫 | 线程各只有一份 ✓ |
| `run()` 退回裸 `asyncio.run` | 在飞轮次被取消（join 超时）✓ |
| `_wait_for_manual_tasks` 退回 `time.sleep` | 手动等待可叫停 ✓ |
| lifespan 关停时不再 `stop()` | 两次 lifespan 不留线程 ✓ |

⚠️ 真 lifespan 那条**不用 `with TestClient(app)`**：测试进程里 `DATA_DIR` = 仓库根，
真 lifespan 会在**开发者那本真库**上跑迁移 / 备份 / auto_vacuum（devlog/200 那一类
"用例碰了真实数据目录，而它不会红"）。改成直接驱动 `app.main.lifespan`，把碰盘碰网的四件事
（迁移 / 库维护 / 设置覆盖层载入 / WBI 预热 + auth 心跳）换替身，只验接线。
