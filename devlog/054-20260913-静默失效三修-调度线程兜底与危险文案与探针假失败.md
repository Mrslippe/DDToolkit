## 一、`_tier_loop` 心跳无兜底 → 调度线程静默死亡（最高危）

### 现象与根因

`app/services/scheduler.py::_tier_loop` 是综合档守护线程（动态流 + 账号流）。
**053 修掉了越界本身，但兜底始终没加**：

```
_dynamics_next_due()              心跳首轮   ← 旧代码在任何 try 之外
_run_combined_tier()              在 try 内   ← 唯一被保护的一段
_next_dynamics_cost()             心跳每轮   ← 无保护
_drain_pending_fetches()          心跳每轮   ← 无保护
_dynamics_next_due()              轮末重算   ← 无保护
```

抛错 → 线程函数返回 → **综合档线程死亡且不会自我重启** → 动态流与账号流
**永久停摆**；而 T0 直播轮询是独立线程仍然活着，**界面看起来「部分正常」**；
安装版无控制台，只能翻 `logs/sidecar.log` 才发现。

### 修法

1. 新增 `_dynamics_due_or_retry(db, *, why)`：**不可抛错**的小原语，失败时记日志并
   返回 `time.monotonic() + DYNAMICS_MIN_GAP_SECONDS`。首轮与轮末排期共用它。
2. 心跳 `while True` **单轮整体包 try**：任何异常 → 记 `exc_info` 日志 + 排下一轮 →
   继续跑。
3. 排期块**移到 try 之外但一定执行**：`if due_dynamics is not None and time.monotonic()
   >= due_dynamics` → 重算。这样异常路径也不会让 `due_dynamics` 停在过去（否则心跳
   退化成每 tick 重试一次的**忙循环**）。

### 一个自己踩的坑（记下来）

第一版把 `next_cost = _next_dynamics_cost(db) if run_dynamics else {}` 留在原位，
而 `next_cost` 首次绑定只发生在「有到期」之后 —— 于是「账号流到期但动态流未到期」时，
下一句 `_dynamics_budget.charge(next_cost)` 会 `UnboundLocalError`，
**正好被新加的兜底吞掉**：线程不死了，但那几轮的预算记账静默失效。
已在循环头初始化 `next_cost: dict = {}`。

教训：**给一段代码套兜底之前，先确认它的变量绑定不依赖「上一句成功」**。
兜底会把「响亮失败」变成「安静降级」，而安静降级更难发现。

## 三、`ui_probe.py` 加固只完成一半（且引入一个必然假失败）

`a463a14`（2026-09-13）加固了假通过路径。复核发现**还剩 5 处静默空转**，
以及一处**新引入的必然失败**：

| # | 位置 | 问题 |
|---|---|---|
| 1 | `_assert_topbar` | `if not tb or not tb.get("ok"): return []` —— `/vtuber/fetch-status` 取不到时，**顶栏展示策略整段空转**且完整性检查不要求「顶栏必须被采样到」 |
| 2 | `_assert` | `v.get("overflowing", [])` / `v.get("scrollers", [])` 缺键 → 空列表 → 静默通过（同一次加固里 `scrollbarPx` 用「缺键也判失败」，口径不一致） |
| 3 | `_assert_cards` | `max_w == "none" or (max_w and ...)` 在 `max_w is None` 时**两个分支都不成立** → 静默通过（上面 12 行的 contract 分支对 `None` 是判失败的，口径不一致） |
| 4 | `_assert_cards` | `if not cards or not cards.get("n"): return bad` —— 卡片段「量不到」时整段跳过 |
| 5 | `--first-run` | **必然退出 1**：该模式路由固定 `/` → 页面是 `EmptyState`、**本来就没有视图光条** → 探针 `degraded.push('no-view-btn')` + 只 emit 一段 `empty` → 完整性检查判「退化 + 空置页 + 缺 8 段」三条失败。`docs/DEV-LOOP.md` 记录的该命令从此恒红 |

### 修法

- 1：把「顶栏没采到」提升为**契约失败**（`_assert_probe_integrity` 里判），
  `_assert_topbar` 保持「非 quiet 情形空过」的语义不变。
- 2：两个列表型字段改为**先要求 `isinstance(items, list)`**，缺键即判「未量到」。
- 3：`max_w is None` 显式判失败。
- 4：卡片段无内容时报「未量到」（不再静默 return）。
- 5：给探针加**独立 mode**：`?probe=first-run`（`probe.ts` 新分支，不产 views），
  脚本在 `--first-run` 下走**独立契约** ——只断言登录浮窗（`_assert_first_run`）+
  探针未退化，不做布局断言。两种契约互不污染。
- 顺带：主/archive 模式的 JSON 都补上 `mode` 字段，脚本可分辨来源。

> 「降级方案本身也要被断言」（050 §五）在这里第二次应验：`--first-run` 的降级路径
> 正是没人量过的那条。

## 八、经验

- **兜底会把「响亮失败」变成「安静降级」**：套 try 之前先确认被保护代码的变量绑定
  不依赖「上一句成功」（本批 §一 的 `next_cost` 就是这个坑，且正好被新兜底吞掉）。
- **「必然假失败」比「假通过」更容易被忽略**：假通过会让人以为验过了，
  假失败则被人当成「环境问题」直接略过 —— `--first-run` 恒红就是这个下场（§三.5）。
- **加固要成体系，不能逐点打补丁**：同一个 `_assert` 里三种空值口径并存
  （缺键判失败 / 缺键当空 / `None` 两分支都不成立），说明加固时是「照着报告改点」
  而非「统一判据」（§三.2/3）。
- **产物验证要 grep 产物本身**：改文案后「重建过了」不等于「产物里没有旧串」，
  直接 `Select-String frontend/dist/assets/*.js` 才是证据（§二）。
- **测试基建的真正价值在于它会立刻抓到 bug**：vitest 落地的同一批就抓到
  `system` 类型标签漏项（§四）——而且它是个**用户可见**的 bug，不是内部质量问题。
