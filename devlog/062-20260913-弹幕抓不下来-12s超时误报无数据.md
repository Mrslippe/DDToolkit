# 062-20260913-弹幕"抓不下来"的真相：12s 超时把「上游慢」误报成「本场无数据」

> 用户报「弹幕数据好像还是没有能够抓取下来」。本批**不改功能设计**，只修一个误报：
> `_LIVE_TIMEOUT` 12s → 30s + 3 次重试 + 前端文案不再断言「本场无弹幕」；
> 顺带修掉自建词云**串到别的场次**的静默错数据，并留下一个只读取证脚本。
> 无迁移、无接口契约变更。

---

## 一、先排除的两种可能（都不是原因）

### 1. 用户没点过「用弹幕自建」按钮

`%APPDATA%\com.ddtoolkit.app-dev\logs\app.log` 里 **`/api/v3/lives` 一次都没出现** ——
那是自建词云专用的端点（`fetch_raw_danmakus`）。所以"抓不下来"不是自建路径坏了，
而是**详情端点那一次请求本身没拿到数据**。

### 2. 不是上游断供，也不是本场真的没弹幕

同一场次（`021f61b2-…《明朝那些事儿》`，库里记着 13857 条弹幕）库里/app 里
`wc_status=upstream`、40 个词条 —— 后端逻辑是通的。**问题出在"某些时刻拿不到"**。

---

## 二、复现：最近 5 个场次 100% 失败，更早的场次 100% 成功

直接打 `fetch_live_summary`，按 `start_at` 倒序取样：

| 场次 | 弹幕数 | 修复前 | 说明 |
|---|---|---|---|
| `94634f4f` 暴雪嘉年华 | 19986 | **15.6s → None** | 响应体 223KB |
| `c5a81d83` 教堂狂小菲 | 29110 | **→ None** | |
| `021f61b2` 明朝那些事儿 | 13857 | **→ None** | |
| `0f91329f` 虚一小度 | 16257 | **→ None** | |
| `f664557b` 明科大讲堂 | 26060 | **→ None** | |
| 更早的场次（多个） | — | 5–9s → OK | 响应体 45KB |

同一个 `liveId` **再打一次却在 3.7s 返回了 100 个词**。三条线索合起来指向同一个解释：

- **该上游会间歇性变慢**（同一请求 3.7s / 15.6s 都实测到过）；
- **近期场次的响应体明显更大**（223KB vs 老场次 45KB）；
- 而代码里写死的是**单次 12s 超时、不重试** —— 稍慢一点就直接放弃，
  再把"放弃"渲染成「本场无弹幕记录」。

> 场次越新越容易中招，所以症状看起来像"最近的数据抓不下来了"。

## 三、修法

| 位置 | 改动 |
|---|---|
| `danmakus._LIVE_TIMEOUT` | **12.0 → 30.0**，并留注释**禁止调回 12s**（写明成因与实测日期） |
| `fetch_live_summary` | 拆出 `_fetch_live_summary_once`（单次、失败返回 None），外层 `@retry(stop_after_attempt(3), wait_exponential(1, max=6), retry_if_result(is None))` |
| `fetch_live_events` | 同款 3 次重试（同源、同样会慢）；失败返回 `[]` |
| 收尾回调 | `retry_error_callback` 显式返回 `None` / `[]` —— tenacity 8.x **默认抛 `RetryError`**，那会把「上游慢」变成路由层 500 |
| `LiveSessionDialog.tsx` | 删掉「本场无弹幕记录」的断言，改为「弹幕数据未取到（上游 danmakus 超时或未收录该场次；可稍后重试）」+「尝试拉取弹幕」按钮 |

重试口径沿用本仓既有习惯（`fetcher.py` 的 B 站请求同款：3 次 + 指数退避 + 结果为 None 即重试）。

**用户 D1 未被破坏**：仍然**不自动回退**到自建词云；拉取失败时只是把按钮给用户，
由用户决定要不要走自建路径。

### 顺带修掉一个静默错数据：自建结果会串到别的场次

写这条路径时注释里的假设是「切换场次/重开弹窗会卸载重建，本地状态自然归零」——
**假设是错的**：弹窗里有一排**场次页签**（`onSwitchIdx`），切页签时父级渲染位置没变、
也没给 `key`，所以组件**不会卸载**。于是 `selfWc`（自建结果）会留在下一场的界面上：
**在 A 场点了「用弹幕自建」，切到 B 场看到的是 A 场的词云**，页面上没有任何东西提示它是错的。

修法：本地状态连同 `live_id` 一起记账 —— `selfWc = { liveId, data }`，
只有 `liveId === 当前场次` 时才生效；切走自动失效、切回来还在。
`building` 同理改成 `busyWc`（场次 id），免得 A 场的在途请求把 B 场的按钮冻住。

### 新增取证脚本 `scripts/check_danmaku_fetch.py`（只读）

上面那些数字是用临时脚本量的，本批把它固化下来，下次再遇到"弹幕抓不下来"能一条命令定性：

```
$env:DDTOOLKIT_DATA_DIR = "$env:APPDATA\com.ddtoolkit.app-dev"
python scripts/check_danmaku_fetch.py [场次数=6] [--self]
```

- 挑**最近的 N 个 danmakus 场次**逐个真打上游，打印 `status` / 上游词条数 / 事件数 / 耗时；
- `--self` 追加跑一次自建路径（v3 + jieba，**很慢**，默认不跑）；
- 全绿退出 0、有失败退出 1（可当探针）；**只读**（sqlite `mode=ro`，不写库）；
- 库路径从 `settings` 推导（跟随 `DDTOOLKIT_DATA_DIR`，不硬编码机器路径 —— 同
  `scripts/smoke_delete.py` 的教训），未设该变量时告警说清用的是哪个库。

## 五、已知代价与未做

- **最坏耗时**：上游彻底不可用时，详情端点是 `summary`/`events` 并发 `gather`，
  单个最坏 ≈ 3×30s + 退避 ≈ 93s（不是 186s）。前端没有超时，表现为弹窗一直转圈，
  最后拿到降级结果 + 按钮。**这是刻意的取舍**：宁可等，也不要再给出错误结论。
- 未给详情端点加缓存：每次开弹窗仍会真打上游（与旧行为一致）。
- `--archive` 探针 3s 采样窗口可能落在弹幕区异步填充之前（058/061 已记），本批未改。

## 六、教训

1. **超时值是有保质期的**：12s 是照 45KB 响应体定的；上游变慢/变大后，
   同一个数字就从"够用"变成"系统性误判"，而且**看起来像数据问题而不是超时问题**。
   凡是"拿不到就降级"的路径，都该问一句：降级文案会不会被读成"客观事实"？
2. **别让 UI 替上游下结论**：`danmaku === null` 同时意味着"没拉到"和"确实没有"，
   旧文案直接写成「本场无弹幕记录」—— 这是**把不确定性渲染成事实**。
   三态（有/无/没拉到）必须在文案上分开。
3. **"最近的数据都坏了、老数据都好" 先怀疑时间相关的实现**（超时、限流、缓存、TTL），
   而不是"上游对新产品线断供"。
