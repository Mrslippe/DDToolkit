# 357-20261006 「正在拉取第三方数据」没有出现在通知面板里

> 用户（附面板截图：`通知（2）` / 最近（0） / 需要处理（0） / 正在进行（1））：
> 「我点击了全量拉取第三方数据，但是顶部状态胶囊下拉通知面板中没有显示这条正在拉去的消息，
> 同时通知数量却显示有两条，**是否是第三方拉取没有在事件中心进行注册**」

**不是没注册**——先回答这个问题，再记真因（在第 2 节）。

## 一、先取证据：后端到底有没有那条（真机 + 原始 JSON）

同款现场（真机数据目录**副本** + 独立后端 + 开发态 token），点一次
`POST /vtuber/batch/fetch-externals` 然后连采 60 秒：

```
起始 external = {"running": false, ...}
POST /vtuber/batch/fetch-externals → {"status": "started"}
t+  0.1s  ext.running=True auto=False label='第三方数据（全量）'  notices=['progress-external(state/progress)']
t+ 40.9s  ext.running=False ...                                  notices=['msg-…(notice/message)']
```

原始响应（**这一行是本次的关键**）：

```json
{"id":"progress-external","kind":"progress","text":"正在同步第三方数据（全量）",
 "sticky":false,"expiresAt":null,"createdAt":1791220921297,"form":"state", ...}
```

后端**注册了**、也**一直在报**（`external_task_started(auto=False)` → `_progress_notices`）。
用户在面板里看不到，是**前端**这一格的事。

## 二、真因：JSON 的 `null` 不是 `undefined`（`expiresAt: null` 被判成"已过期"）

`notificationHub.isLive()` 原来写的是 `n.expiresAt === undefined || n.expiresAt > now` ——
而服务端契约 `NoticeOut.expiresAt: int | None` 把 None 序列化成 **`null`**：
`null === undefined` 为假、`null > now`（= `0 > now`）也是假 ⇒ **"没有过期时刻"被当成"已经过期"**。

后果正好是用户看到的两件事：

| 现象 | 机制 |
|---|---|
| 面板里没有那条「正在同步…」 | `sectionNotices` 按 `isLive` 过滤 ⇒ 它进不了任何一组。⚠️ 它**不是完全不画**：会以"正在退场"的身份在列表里闪 ~220ms（`exiting` 那一路）—— 所以**肉眼容易漏、探针只看"点完看得见"也会假绿** |
| 计数写 2 而屏幕只有 1 条 | `.si-count` / `通知（N）` 数的是**合并后的原始数组** `notices.length`，里面含这条"不画但仍在列"的条目 |

**影响面比第三方那一条大**：`_normalize` 给所有没有 TTL 的条目填 `expiresAt: None` ——
三个手动进度条目（`progress-post` / `progress-account` / `progress-external`）全中，
也就是说"点了抓取、胶囊亮了、面板里却没有进度"这类现象**一直都在**。

## 三、修法（两件，各配判据）

1. **一处判据**：新增 `expiresAtOf(n)`（`null`/`undefined`/`NaN`/`Infinity` 一律 = 不过期），
   `isLive` / `countdownFraction` / `noticeStream` 的自写过期过滤 / `TopBar` 的本地清理
   **全部走它**（分叉的那两份判据就是 bug 本身）；`Notice.expiresAt` 类型如实改成 `number | null`。
2. **计数 = 画出来的条数**：徽章与面板标题改用 `drawnGroups` 的行数（活着的 + 排队/正在滑出的），
   不再数原始数组 —— "数了没画"这一类从此不可能。

判据（先在旧代码上确认**会红**，再修）：

- `notificationHub.test.ts` 2 条：`expiresAt: null` 不许判过期；`NaN`/`Infinity` 同理不判过期；
- `noticeBoard.test.ts` 1 条：服务端形态的 state 条目要进「正在进行」；
- `StatusIsland.test.tsx` 3 条：**等退场队列跑完**它还要在（不然只是那个 220ms 的幽灵）、
  标题计数 == 画出的行数、列表里剩一条已过期的也不许算进计数。

## 四、顺带挖出来的第二个 bug：体检 effect 每拍都调度更新 ⇒ `Maximum update depth exceeded`

加完真机判据（`NoticeLab` 新增第 ⑫ 行「服务端形态的状态条目（没有 TTL）」+ 探针
`--notice-lab` 专门点它并**等退场队列跑完**）之后，探针报 **3 条页面报错**：

```
Uncaught Error: Maximum update depth exceeded ... at StatusIsland
React will try to recreate this component tree from scratch using the error boundary you provided
```

根因在「定时体检」那条 `useLayoutEffect`：依赖含 `now`，而 `now = Math.max(nowProp, Date.now())`
—— **只要两次渲染之间过了 1ms**，依赖就变、effect 再跑、**再调一次 `setRows`**；
而"在 commit 阶段调度更新"本身会被 React 计进 `nestedUpdateCount`，攒够 50 次就抛 ——
**即使 updater 每次返回同一个引用**（原来那句 `changed ? next : prev` 的 bail-out 救不了它）。
探针跑在**虚拟时间**下（时钟随每拍往前跳）时必炸：实测 600+ 次渲染，
`ErrorBoundary` 重建整棵树 ⇒ **顶栏连同它的 dev 口一起消失**，之后探针读什么都是空
（第一版还把它误读成"条目被滤掉了"，因为读到的 `[]` 长得一样）。

修法：**先自己判有没有要改的，没有就一次 `setState` 都不调**。这条在 jsdom 里
**复现不出来**（bail-out 不产生新 commit，环第二步就断）⇒ 判据落成**源码级结构判据**
（早退必须在 `setRows` 之前），并**反向验证过**：把组件改回旧写法，那条当场红。
真机那一侧由 `ui_probe --notice-lab` 的"页面报错"判据守着（它在 A 档门禁里）。

同一轮还试过两版"用 `shownCount`/活着的条数当徽章动画触发器"，两版都把这条环重新点着
（它们都含 `now`）—— 最终把触发器钉回 `notices.length`（只由输入决定），并把理由写进注释。

## 五、探针侧的两处诚实化

- `--notice-lab` 的「正在进行不许变少」判据原来**会被 TTL 带走**：④⑤ 推的 `pushed-progress`
  真身只有 8 秒寿命，而那一轮跑完要十几秒 ⇒ 常在"全部已读"那几拍里自己过期，
  红在产品没坏的地方。现在点「全部已读」**之前先重发一次**（让那 8 秒从此刻起算）。
- 新增第 ⑫ 行与它的判据（上面第四节），并把 `NoticeLab` 的 ⑫ 写成**不套 `LAB_TTL_MS`** ——
  ④⑤ 之所以一直没抓到这次的 bug，正是因为它们给注入了数字 TTL。
