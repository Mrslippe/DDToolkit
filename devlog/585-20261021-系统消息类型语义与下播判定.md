# 585-20261021-系统消息的类型语义（实测）与下播判定

用户指出两条：① "消息必须在最后一条弹幕之后"太严（下播后观众还在聊）；
② 类型要区分，先验证语义。

## 一、类型语义（实测 4 个 V 的场次）

| 类型 | 出现位置 | 判定 |
|---|---|---|
| **11** | 距开始 0.0–5.3 分（也有中途几条） | **开播/提醒** |
| **7** | 距结束 ~5 分 | **结束相关** |
| **8** | 距结束数十分 | **结束相关** |
| **12** | 距结束 ~5 分 | **结束相关（直播中止/录制结束）** |

结论：`11 = 开播`，`7/8/12 = 下播`。

## 二、规则改成

```python
STOP_TYPES = {7, 8, 12}
stops = [e.ts for e in sys_events if e.type in STOP_TYPES]
end_at = max(stops) + 1 分钟        # 取最晚的下播消息
```

- **去掉**"消息必须在最后一条弹幕之后"——下播后观众继续聊是常态；
- **去掉**"间隔 ≤2 小时"——同上，没有意义了；
- 仍然**只允许变短**（防止把错误消息当成延长依据）。

## 三、优先级

```
系统消息（type 7/8/12）> 率降裁尾 > 平台 stopDate > 弹幕跨度
```

## 四、用例

`test_sys_end_uses_stop_type_and_ignores_start_signal`：
只有 type 11 时不动；有 type 12 时收口；**下播消息早于最后一条弹幕时照样以它为准**。
