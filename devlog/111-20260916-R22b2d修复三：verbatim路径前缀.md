# 111-20260916-R22b2d修复三：canonicalize 的 \\?\ 前缀让后端打不开库

> 真机第三次尝试（dev 模式）仍报 `新目录启动失败：后端 60 秒内没有就绪（已回退到原目录）`，
> 但用户提到"新目录中确实有东西，控制台也打印了一些内容" —— 那句话就是破案的关键。

## 一、根因（本地复现坐实）

对比两份 `sidecar.log`，唯一可疑差异是**数据目录路径**：

| | 失败那次（壳启动） | 我的复现（手工启动，成功） |
|---|---|---|
| 数据目录 | **`\\?\E:\test\DDToolkit-data`** | `C:\Users\zx\...\ddtk-repro` |
| 进度 | 停在"准备监听"→ lifespan 卡住 | 正常就绪 |

于是我把同一份数据目录**加上 `\\?\` 前缀**再启动一次后端，立刻复现：

```
boot: data_dir=\\?\C:\...\ddtk-repro
[perf] 准备监听 127.0.0.1:54322
sqlalchemy.exc.OperationalError: unable to open database file
ERROR:    Application startup failed. Exiting.
```

**`\\?\` 是 Rust `std::fs::canonicalize()` 在 Windows 上的产物**（它返回 verbatim 路径）。
我在 `plan_migration` 里把规范路径**当成了数据目录**：写进指针 → 作为 `DDTOOLKIT_DATA_DIR`
传给后端 → 拼进 `DATABASE_URL`（`sqlite:///\\?\E:\...`）→ SQLAlchemy/SQLite **打不开库**。

用户控制台看到的正是那段 Python 报错；而应用日志里只剩两行（"启动中 / lifespan 开始"），
所以我前两次都误判成"等锁"。**教训：壳与 Python 之间传递的路径必须是"用户看到的那个"**，
规范路径只能用于**比较**（消除 `..`、大小写、8.3 短名），不能当值用。

## 二、修法

`plan_migration`：
- `canonicalize` 的结果改名为 `src_c` / `dst_c`，**只用于包含关系判定**；
- `Plan.source` / `Plan.target_root` / `Plan.data_dir` **一律用传入的原始路径**；
- 新数据目录的"在源里面"判定也改用原始 `source` 比较。

## 三、护栏

`dirty_target_dir_...` 用例新增断言：**对外路径绝不能带 `\\?\` 前缀**
（`!plan.data_dir.to_string_lossy().starts_with(r"\\?\")`）—— 这条正是真机死因的机器判据。

`cargo test` **21 passed / exit 0**。

## 四、这一串修复的复盘（三次真机失败，三个不同的 bug）

| 次 | 现象 | 根因 |
|---|---|---|
| 1 | 复制校验失败（源 38 / 目标 78） | 目标里**早有一份完整数据目录** → 嵌入一层同名目录 ⇒ 加 `pick_data_dir()`（非空就换带时间戳的） |
| 2 | 新目录启动失败（30s） | 复制了 **`-shm`**（WAL 共享内存索引）⇒ 跳过它；探活窗口 30→60s；超时杀子进程 |
| 3 | 新目录启动失败（60s） | **`canonicalize` 的 `\\?\` 前缀**进了 `DDTOOLKIT_DATA_DIR` ⇒ 对外用原始路径 |

三次都**没有丢数据**（旧目录全程未动、每次都回滚成功）—— 这是 R22 那两条纪律（旧目录不动 +
探活成功才算成功）真正发挥了作用。但也说明：**打包版没有壳侧日志**让我每次都只能靠后端日志
反推，这一条必须尽快补上（`<数据目录>\logs\shell.log`）。
