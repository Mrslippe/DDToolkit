# 483-20261013 表情解析率 28% → 99%：答案本来就在我们自己库里

> 用户第 7 条：「查一下 github 上有没有开源项目可以获取全量的表情包图床地址 / 如果没有的话，
> 或许可以检索一下 bilibili 官方解析表情包的方法 / 再或者解析一个动态的完整 json 结构，
> 其中包含图床地址的那种，猜测一下怎么能解析全部表情包」。
>
> 三条路我都查了，**结论是第三条**：不用找第三方数据、也不用逆官方的 gRPC 服务 ——
> B站 的载荷**自带**每个表情的图床地址，而我们抓帖子时**已经把整个载荷存进了 `posts.raw_json`**。
> 所以这批一行网络请求都没加，解析率从 28% 变成 99%。

## 一、三条路的调查结果（先写结论，细节留在下面）

| 路 | 结果 | 为什么不用 |
|---|---|---|
| ① GitHub 现成全量表 | 有：`lrhtony/BiliEmoji` + `-cron`，Actions 每 12h 抓一次，`list/<包id>-<包名>.json`，`text` 与我们的 token **逐字相同** | **仓库没有 LICENSE**；数据靠一个不在仓库里的扫描脚本（要 `ACCOUNT`/`ACCOUNT_DB_URI`/`SCAN_CONFIG` 三个 secret）产出 ⇒ 拿它当主源是"把渲染押在别人的账号和许可上" |
| ② 官方解析方法 | `modules.module_dynamic.desc.rich_text_nodes[*].emoji` 就是官方的"解析结果"；而 `x/emote/package`、`x/emote/user/panel/web` 只是**包列表**（且账号相关）；`/bapis/main.community.interface.emote.EmoteService/PackageDetail` 要 **gRPC-web/protobuf**（POST 405；GET 试了 7 种参数组合全是 `{"code":-400}`） | 逆 protobuf 能拿到"整包"，但**我们已经有更好的**：载荷里带的就是这枚表情在这条帖子里用的那张图 |
| ③ 从载荷里抠 | ✅ **这条** | —— |

## 二、③ 长什么样（真机数据）

```json
modules.module_dynamic.desc.rich_text_nodes[1].emoji = {
  "type": 11, "size": 2,
  "text": "[UPOWER_1891335475_闪亮]",                 // 与正文 token **逐字相同**
  "icon_url": "https://i0.hdslb.com/bfs/garb/….png",  // ← 图床地址
  "gif_url": "", "webp_url": "",
  "package_id": "18626", "id": "287839"               // 包 id + 表情 id
}
```

（opus 型帖在 `modules.module_dynamic.major.opus.summary.rich_text_nodes[*].emoji`，字段一样。
所以解析器是**递归**找 `{emoji: {...}}`，不写死路径 —— 上游换个位置也还能用。）

**实测覆盖**（真机 5,058 帖；`scripts/check_emoji_coverage.py` 一条命令可复现）：

| 口径 | 覆盖 |
|---|---|
| 种类（498 个 token） | 493 / 498 = **99.0%** |
| 次数（6,172 次出现） | 5,975 / 6,172 = **96.8%** |

缺的 5 个是 `1P`(114) · `▓▓`(76) · `0P`(4) · `9P`(2) · `2P`(1) —— **一个带下划线的都没有**
（分P 标记、被屏蔽词），它们本来就该保持原样文字（`devlog/482` 的口径）。
⇒ 也就是说：**真表情一枚没漏**。

**⚠️ 口径对账**（本批唯一一处"两个数看着像打架"的地方，写下来免得下次当 bug 查）：

| 字段 | 种类 / 次数 | 是什么 |
|---|---|---|
| `body_json.text` | **498 / 6,172** | **前端详情页真正渲染的那个字段**（`PostText` 拿的就是它）⇒ 判据按它 |
| `body_text` | 506 / 6,448 | 列表摘要 / 全文检索那一列，多出 `[3P]`…`[13P]` 八个分P 标记 |

`482` 那批记的 **501 / 6,180** 是当时另一次扫描（那个 devlog 没写明口径）—— 与本批的 498/6,172
**不是同一把尺子**，别读成"涨了/跌了"。所以探针脚本把两个字段都印出来，并标注该按哪个判。

**⚠️ 顺带修正 `482` 的一条直觉**：那里写"无下划线 ⇒ 多半不是表情"。真机数据说**按 token 数
恰恰相反** —— 无下划线 token 里绝大多数是**官方裸名表情**（`打call`/`爱心`/`笑哭`/`给心心`/
`捂脸`/`脱单doge`/`洛天依`…），只有 5 个是 `1P`/`▓▓` 那类非表情。但**结论仍然成立**：
载荷把这些裸名表情**全解析出来了**（探针实测"没解析出来的里面带下划线的 = 0 个"），
兜底规则只作用在"两级都没解析出来"的残余上，而那个残余**全是非表情**
⇒ "不带下划线 ⇒ 原样文字"在本机数据上**一次都没误伤**。

## 三、两级解析（这是本批的架构决定）

```
token ──▶ ①第一源：我们自己载荷（离线、99%） ──命中─▶ 画图
              │ 没命中
              └▶ ②第二源：上游整表（出网、28%、账号相关） ──命中─▶ 画图
                        │ 还是没命中
                        └▶ 名字 chip（"这是表情，只是本机没有它"）
```

第一源**必须先查**：它不出网、覆盖高，而且真机数据里"载荷命中的 token 再问上游也不可能多出东西"。
第二源留着当兜底（老数据、只出现在视频标题里的 `石化R` 那类）。

⚠️ **一个关键口径：索引的键用原样名（含 `UPOWER_<uid>_` 前缀），不归一化。**
归一化（去掉前缀让"同一个名字"跨 UP 通用）看着更划算，真机数据说**不划算**：

| 口径 | 覆盖（498 个 token） | 同名不同图 |
|---|---|---|
| 原样 | 493 = 99.0% | 0 |
| 归一化 | 493 = 99.0%（**多救回 0 个**） | **14 组** |

那 14 组是 `打call`/`爱你`/`干杯`/`喜欢`/`嘘`… 各有 2 张不同图 —— 不同 UP 各自的自定义表情。
归一化唯一的效果就是**把 A 的表情画成 B 的**。覆盖一样、风险更大，所以不归一化。

## 四、实现（三个地方，都很小）

- `app/services/bili_emote.py`：
  - `collect_emotes()` 递归抠 `{emoji:{text,icon_url,package_id}}`（深度上限 14 层兜底）；
  - `scan_payloads()` 纯函数（坏 JSON 跳过 —— 库里真有历史遗留的畸形行，不能让一条毁掉整个索引）；
  - `warm_raw_index()` **启动期**热索引：扫 `posts.raw_json` 实测 **0.71s / 5,058 行**
    （取行本身 0.09s）⇒ 太慢，**不能放读路径**（`devlog/473`：读端点不许干重活）。
    按本仓既有做法（`devlog/475`"启动期只在真需要补时才扫 + 记号"）：索引与
    **扫到哪个 post id** 一起存 `app_meta`；启动期只扫 `id > 记号` 的新行（平时 0 行）；
  - `resolve_all()` 两级解析（**同步**：第一源读内存、第二源只读缓存 —— 不在读路径上 `asyncio.run`）；
  - `resolve_all_async()` 端点用的版本：第一源没盖住时**按需**去拉第二源（见下面第六节第 3 条）。
- `app/routers/emoji.py`：`/emoji/resolve` 多返回一个 `origin`（哪个 token 是哪一级给的，
  排查"为什么这枚没画出来"一眼看出）；新增 `/emoji/packages`（两级各有多少名字 + 载荷里见过的
  74 个包 id —— 包 id 是"将来要整包"时的种子，扫的时候顺手存下来了）。
- `app/main.py`：lifespan 里 `bili_emote.warm_raw_index(db)`（包在 try 里 —— 启动不许被它挡）；
  启动日志改成**每次都报索引规模**（`names=0` 就是"第一源没热上"，光看"没扫新行"看不出来）。

**前端一行没改**：命中就是 `<img class="post-emoji">`，没命中就是原来的 chip / 原样文字。

## 五、判据

- pytest **+13**（`tests/test_emoji.py` 12 → 25 条）：★`scan_payloads` 抠节点/跳过坏 JSON/丢空地址 ·
  ★**键保留 uid 前缀**（并钉住"不跨 UP 猜"：`UPOWER_2_打call` 不拿 `UPOWER_1_打call` 的图顶上）·
  同一枚换过图 ⇒ 后扫到的赢 · ★`warm_raw_index` **第一遍全扫、第二遍零扫描**（marker 幂等）·

  而**两种塌法都不报错**（帖子里就是退回一串方括号）。一条命令量出来，别等用户来报。
  它还会点出"没解析出来的里面带下划线的有几个" —— 那个数才是**真漏了**（现测 0）。
- vitest / cargo：**+0**（前端与壳都没动）。

## 六、踩到的三个坑（写下来免得下次当 bug 查）

1. **`warm_raw_index` 的早返回分支漏了回填内存缓存**：没有新行是"第二次之后的每次启动"的**常态**，
   而那个分支只 `return` 统计、没把从 `app_meta` 读回来的索引放进 `_raw_cache`
   ⇒ 症状是"**第一次启动有表情，之后每次启动都没了**"（静默退化成 28% 的第二源）。
   用例 `test_warm_raw_index_scans_once_then_only_new_rows` 当场抓到。
2. **模块级缓存必须给用例一个 `reset_caches()` 出口**：两级索引都是模块级的，同文件多条用例
   共用一个模块实例 ⇒ 不清就会"上一条用例留下的载荷索引让下一条该问上游却一次没问"
   （断言随机地过/不过）。已加 `autouse` fixture。
3. **写完"兜底"一定要找它的调用点**：第二源最初写成 `prefetch_panel_index()` 并注明"启动期做掉"，
   但**没有任何地方调它** ⇒ 文档里写着有兜底、运行期其实永远命中不了，而且**一声不响**
   （`/emoji/resolve` 返回的 `why` 还是 `None`，看起来一切正常）。改成端点里的
   `resolve_all_async()` **按需**拉之后才有真正的兜底：载荷漏了才出网，拉回来缓存 30 分钟。
   ⚠️ 顺带补的一道闸：失败时 `at` 不更新（只在真拿到索引时才写）⇒ 只看 `at` 的话上游一挂就
   **每个**带漏项的请求都打一次上游；所以另记 `last_try` + `RETRY_AFTER=60s`，
   并且**在调用点记账**（不是在 `emote_index` 里）—— 用例里正是因为"记账在被调方"而红了一次：
   替换掉第二源的实现，退避就失效了。
   ⇒ 教训：**兜底路径要有判据同时钉住"该走时走了"和"不该走时没走"**，只钉一侧的兜底等于没有。

## 七、已知取舍（不修，写下来）

- **冷漏项那一次请求会等上游**（按需拉 ⇒ 最多 ~15s 超时）。为什么接受：载荷覆盖 99%
  ⇒ 平时不走这条路；`_panel_needs_fetch` 保证 60s 内只有一个请求真的等；
   而且**前端渲染不等它** —— 正文与 chip 立刻画出来，地址回来才换成图（`PostText` 的取数是副作用）。
- **前端"取不到就当没有"是永久的**（`PostText.tsx` 里失败也写 `null` 缓存）。所以那次 15s 超时
  一旦发生，那几枚表情在本次会话里就一直是 chip（重启才好）。这是 `devlog/482` 的既有行为、
  且兜底方向是"更朴素"不是"错"，本批不动它 —— 真要修就让"失败"不写缓存（而不是写成 `null`）。
- **第二源不搬去启动期**：离线时会挂在 15s 超时上（启动路径上不能有这个）。
  真要"宁可启动慢一点也不让第一个请求等"，就调 `prefetch_panel_index()` —— 它留着，默认不接。
