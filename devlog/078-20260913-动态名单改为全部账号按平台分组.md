# 078-20260913-动态流名单改为「全部账号按平台分组」（R10，修正 R6 的理解偏差）

> 用户澄清：**"我的意思是，每个 V 可能都有多平台的账号 …… 应该设计为：将库中所有 V 的
> 所有平台账号按照平台分类成几个名单，然后不同名单并行，名单内串行抓取，例如假设现在的库中
> 有七海（B站，微博）、明前奶绿（B站、微博）、泽音（B站），那么抓取逻辑应该是两条并行，
> B站：七海、奶绿、泽音，微博：七海、明前奶绿。然后抓取频率仍旧是标定在一分钟。"**
>
> 即 R6 当初"分平台并行"的**名单口径**理解偏了：我按"每 V 一个主账号"分组，
> 而用户要的是"**库里所有账号**都进名单"。本批修正，并把"名单内串行 + 一分钟"写成不变量。

---

## 一、R6 到底错在哪（用用户库里的真实数据说话）

```
7 个 V / 10 个账号：bilibili 8（恬豆发芽了 有两个 B 站号）+ weibo 2
平台组合：泽音(B) · 七海(B,W) · 明前奶绿(B,W) · 菜菜子(B) · 恬豆(B,B) · 永雏塔菲(B) · 弥月(B)
```

R6 用 `_primary_accounts()`（每 V 取 `PRIMARY_PLATFORM_ORDER` 里第一个）⇒

| | R6 | 用户要的 |
|---|---|---|
| 一轮账号数 | 7（每 V 一个主账号） | **10**（全部账号） |
| 微博账号 | **只有"该 V 没有 B 站号"时才会被抓** —— 七海/明前奶绿的微博**从未进过 60s 轮** | 每轮都抓 |
| 同平台多账号 | 只抓优先级最高的那个 | 都抓 |
| 名单内 | 并发 3 + 平台级起跑闸门 | **串行** |

所以现象是"微博动态要等手动/全量抓取"—— 这不是 bug 而是名单口径的差异，
但用户的意图一直是前者。

## 二、新形态（R10）

```
_dynamics_lanes(db) → {bilibili: [(七海,acc), (明前奶绿,acc), (泽音,acc), (恬豆,acc), …],
                       weibo:    [(七海,acc), (明前奶绿,acc)]}
   · 全部账号（platform_uid 非空 + 平台有 fetcher），名单内按 (V.id, Account.id) 稳定排序
   · _primary_accounts() 保留 —— 但**只给第三方历史回填**用（startup_external_catchup）

一轮：每条名单一个协程 → 名单之间 asyncio.gather 并行；名单内部逐个抓（per_platform=1）
      每条名单一个独立会话（沿用原有的 sessions[pf]）
```

**名单内间隔：自适应摊平**（新增，替代原先固定的 3~5s）：

```
gap = clamp((DYNAMICS_LANE_TARGET_SECONDS − N × FETCH_ESTIMATE) / N, GAP_MIN, GAP_MAX)
    = clamp((50 − N × 1.5) / N, 2.0, 5.0)
```

| N（名单长度） | gap | 预计轮长 | 说明 |
|---|---|---|---|
| 1–4 | 5.00s | ≤26s | **短名单直接命中上限**（与账号流同款节流，最保守） |
| 8（你现在的 B 站） | 4.75s | 50s | 摊到目标时长 |
| 12 | 2.67s | 50s | 开始压紧 |
| 17 | 2.00s（触底） | ≈60s | **1 分钟还能容纳的上限** |
| 20 / 30 | 2.00s | 70s / 105s | 装不下了 → 周期自然变长（不为凑一分钟猛发请求） |

±10% 抖动（固定节拍太"机器"）。

**为什么"名单内改串行"没有代价**：周期下限本来就是 60s，一条 8 账号的名单
串行跑 50s 还是并发跑 26s，**下一轮都要等到 60s**。串行换来的是用户要的名单语义，
并且顺手**消掉了 076 那类跨事件循环隐患**（串行不需要平台级起跑闸门）。
`DYNAMICS_CONCURRENCY` 保留为**紧急开关**（默认 1；>1 回到 R6 的"并发 N + 闸门"）。

## 三、一起处理的三件事（不处理就是"上线即踩"）

1. **微博未登录 → 整条 weibo 名单跳过**（`_lane_skip_reason`）：Cookie 失效时若不判登录态，
   会变成**每分钟 2 条警告 + 2 个必失败请求**。
   ⚠️ 实现口径在 devlog/079 里改过一次：**不做每轮探测**（探测本身就是一次上游请求，
   每轮探一次 = 每分钟白打一个 `profile/info`），改为**抓取自己发现 `ok=-100` 就标记失效**，
   下一轮起跳过；重新扫码走 `apply_cookie()` 自动恢复。
2. **`_next_dynamics_cost()` 必须同口径**：它给速率预算做**轮前记账**，原来按"每 V 主账号 1 次"
   算 ⇒ 与实际请求数不符（少算会顶到预算上限，多算会白等一轮）。现在按名单长度算，
   跳过的名单不计入。
3. **进度文案带平台**：多名单并行时「动态轮询中 · V名 · i/N」看不出是哪条名单在跑，
   改成「V名·平台」。

## 四、实测（开发库副本 + 真实上游，2 轮）

```
名单：bilibili 8 个账号（间隔 4.75s，预计轮长 50s）· weibo 2 个账号（间隔 5.00s）
第 1 轮 43.6s  请求 {bilibili: 8, weibo: 2}  入库 {dynamics:112, stored:0, skipped:112}  0 风控
第 2 轮 40.2s  请求 {bilibili: 8, weibo: 2}                                            0 风控
周期：按 R10 口径（轮**开始**计）63~70s = max(60s 下限, 预算等待 ±15s 抖动)
```

对比 R6：一轮 7 请求 / 25.7s（但微博完全没覆盖）。R10 把覆盖面补齐，代价 +3 请求/轮；
**墙钟只由最长的那条名单决定**，所以"多一个平台"不会让一轮更慢。

> 实测轮长 40~44s 略小于公式里的 50s：`FETCH_ESTIMATE=1.5s` 是保守估计，
> 实测单账号抓取约 0.7s（`112 条已入库 → stop_on_existing` 即刻停），属正常余量。

## 七、遗留与取舍

- **单平台账号数 > 17 时一分钟不再可达**：这是物理约束（间隔下限 2s），届时周期自然变长，
  日志会打印每条名单的长度与间隔，便于判断该调 `DYNAMICS_LANE_GAP_MIN`（更激进）
  还是接受更长的周期。
- **跨流并发同一平台**：账号流（约每日一次）与动态流可能同时对同一平台发请求 ——
  现状如此，未在本次范围；要更严可把平台级闸门提升为**跨流共用**（留作可选）。
- **微博的额外开销**：`fetch_post_page` 1 次请求/账号，长文才会再打一次 `enrich`
  （`limit_latest=2` 下最多 2 次）——按你库里 weibo 2 个账号算，最坏 6 请求/分钟，
  仍在预算内。
