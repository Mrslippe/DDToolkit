# 337-20261005 自节流不该记成失败：顺手挖出第三个"闸门没问平台"

> 接 `devlog/336`（D4 真机端到端）。那批在日志里留下一句
> `[douyin] 账号 Sulli … 抓取完毕: 0 成功, **1 失败**` —— 平台什么都没说，是我们自己没发。
> 本批把它连同**同一类的两处**一起修掉，并在真机上复现验收。

## 一、自节流不再记成"失败"（就是那句 1 失败）

`user_profile` 的令牌桶 0.2/s、容量 1：收录那一步先花掉令牌，收录后台在 ~0.6s 后再问一次
⇒ 只能补回 0.12 个 ⇒ **必然被挡**。原先账号那条路不看这个信号，一律 `failed += 1`。

修法：账号两条路（顺序 `_fetch_accounts_by_ids`、平台并行 `_run_platform_rounds`）都复用
现成的 `identity_limit.throttled(pf)`（帖子那条路 `devlog/237` 早就接了）⇒ 记 **skipped**
+ 明细「本轮没发（自己的节奏：bucket，还需 X.Xs）」。

**真机对照**（同一个账号、同一天、同样流程）：

```
修前： [douyin] 账号 Sulli … 抓取完毕: 0 成功, 1 失败
修后： 抓取完毕: 0 成功, 0 失败, 1 跳过
```

## 二、失败原因要能到**报告那一层**（新平台原先永远说"网络"）

`_account_fail_text()` 靠两个信号分工：`platform_outcome.last_failure()`（kind）与
`was_rate_limited()`。**这两个都只有 `fetcher.py`（B 站/微博）在写** ⇒ 适配器框架那两家
（小红书/抖音）不管真因为什么失败，永远落到兜底那句「更新失败（**网络**）」：
cookie 失效、风控、自节流全说成网络 —— 而 `devlog/239` 立这条规矩的原话就是
「分工不同就别用同一句话」（用户该做的事完全不同）。

- 适配器新增 `_note(kind, msg=…)`：**一个口子写两处**（`last_error` 给调用方/诊断，
  `outcome.set_failure` 给报告文案）⇒ 两处不可能再漂。抖音 8 处、小红书 5 处赋值全部收敛过去；
- `_account_fail_text()` 补三类文案：cookie 失效 → 「登录态失效（到「设置 → 登录」重新粘贴）」、
  签名不可用 → 「签名不可用（我们这侧没发请求）」、总开关关着 → 「抖音总开关关着（设置 → 抓取设置）」；
- `identity_limit._KIND_TO_OUTCOME` 显式加 `identity_throttled → network_error`：
  ⚠️ 没有它，兜底 `risk_control` 会把自节流说成**"更新失败（风控）"**（比"网络"更吓人且是假的）。

## 三、⚠️ 第三个"闸门没问平台"（真机才撞出来）

复跑时日志里出现 `首屏抓取跳过（account#1）：抓投稿/动态需要登录 B 站` —— 而这是**抖音**账号：

| 位置 | 原来 | 后果 |
|---|---|---|
| `async_fetch_posts(platform, uid, …)` | 手里有 `platform` 却调 `content_fetch_allowed()` | 抖音/小红书账号的"抓取帖子"被**"未登录 B 站"**挡下；B站登录着时又**越权放行** |
| `async_fetch_first_screen(account_id)` | 连平台都没有，同样不带参数 | **收录一个抖音账号后首屏抓取被跳过**，被启动链的动态流接管 |

这与 `devlog/228`（端点级判据拿 B站登录态放行）和 `devlog/320`（闸门漏了小红书）**是同一类，第三次**。
修法：前者传 `platform`；后者先 `_platform_of_account(account_id)` 查一次（查不到按默认 B站口径 ——
宁可严不可宽）。判据打在**传给闸门的那个参数**上（`test_content_gate_asks_the_accounts_platform`）。

> ⚠️ 教训：**"闸门要问谁"这件事必须跟着调用点走一遍**。三次都发生在"新加/复用一条路径"时，
> 而症状一律是**静默跳过**（日志里还写着别家平台的理由）。真实证据（复跑后）：
> `收录首屏抓取 douyin:MS4wLjABAAAA… (Sulli) ...` —— 这条路径第一次真的跑起来了。

## 四、顺带钉住一条**事实**：`outcome` 的 ContextVar 是**任务级**的

`app/core/outcome.py` 用的是 `ContextVar`，而 `asyncio.create_task` **复制**当前上下文 ⇒
**子任务里的写入，父任务读不到**。平台并行那条账号路（worker 子任务）原先在父任务里调
`_account_fail_text()` ⇒ 恒读到空（B 站也一样，属既有洞）。修法：`_RoundOutcome` 多一个
`fail_text`，**在 worker 内部**算好带出来。并补一条判据把这个事实钉住，免得下次又有人跨任务读它。

## 五、⚠️ 我自己的验证脚本也有竞态（记下来，别再犯）

第一次复跑报"图片固化 0 张"，而盘上其实有 1 张封面 —— 因为脚本**一看到帖子就断言**，
而固化在抓取轮的**末尾**，紧接着 `proc.terminate()` 把后端掐了。**是验证脚本抢跑，不是产品坏了。**
改成"轮询等固化收尾（≤180s）"后：`3/3 条有本地副本、共 7 张 / 1.53MB`，
`GET /static/assets/post_image/p1_11918091.webp` → 200 image/webp 616KB。

> ⚠️ 教训：**验收脚本自己也要能"等"**。断言一个"稍后才成立"的事实，等于给产品报假失败 ——
> 而假失败会浪费掉真机上最贵的那几发请求（这一轮我多跑了一次）。
