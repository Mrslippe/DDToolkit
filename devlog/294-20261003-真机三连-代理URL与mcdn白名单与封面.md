# 294-20261003 真机三连：代理 URL 落到前端自己身上 + mcdn 不在白名单 + 封面裸 img

> 用户真机复验（2026-10-03 21:45，开发态壳 + `localhost:5173`）报了两件事：
> ① 详情页**封面不显示**（黑底 + "图片"占位）；② 点播放后**每一路都失败**，
> 报告里还刷了 6 条同一条"全部播放源都失败"。三条根因，都是"能过单测、过不了真机"那一类。

## 一、代理 URL 落在**前端自己**身上（主因）

报告的时间线里写得很清楚：

```
[resource:self-healing] http://localhost:5173/video-proxy?url=https%3A%2F%2Fxy58x58…mcdn.bilivideo.cn…
```

`VideoPlayer` 当初把代理写成**相对路径** `/video-proxy?url=…` ⇒ 它按**页面来源**解析：
开发态是 vite 的 `5173`（vite 只代理 `/api`）、桌面端是 `tauri://localhost` —— **两者都不是后端**。
所以每一路都 404，而症状（"全部播放源都失败（含本机代理）"）看起来像 CDN 挂了。

同一个仓里 `imgProxyUrl()` 一直是 `apiBase` + 路径（图片那条从没出过这个问题）。视频这条漏了。

**修**：`api.ts` 新增 `videoProxyUrl()`（与 `imgProxyUrl()` 同款，拼 `apiBase`），
`VideoPlayer` 的 DASH 轨、音轨、直连兜底链全部改用它；
判据把 URL **完整前缀**钉死（`/api/video-proxy?…`），并显式断言"不是裸相对的 `/video-proxy`"。

## 二、CSP 的 `media-src` 没放行后端来源（同一条链上的第二个坑）

修好 URL 之后，媒体请求变成**跨源**（页面在 `tauri://localhost` / `localhost:5173`，
后端在 `127.0.0.1:<port>`），而 CSP 是：

```
media-src 'self' https://*.xhscdn.com http://*.xhscdn.com      ← 没有 127.0.0.1
```

⇒ 即便 URL 拼对了，**所有经代理的流仍会被 CSP 挡掉**（控制台一句 `Refused to load media`），
症状与"CDN 挂了"一模一样。**修**：`media-src` 加 `http://127.0.0.1:*`（直连那两级保留），
并加一条判据直接读 `tauri.conf.json` 断言这件事（这类配置最容易在下一次改 CSP 时被顺手删掉）。

## 三、白名单只认 `.com`，而 B站的 `baseUrl` 常常是 mcdn

用户那条视频（`BV16tHY6UEid`）实测：**每一条流的 `baseUrl` 都是 `xy*.mcdn.bilivideo.cn`**，
`backupUrl` 里才有 `upos-*.bilivideo.com`；durl 的 `url` 更是 `*.edge.mountaintoys.cn`。
我们的白名单当时只有 `bilivideo.com` ⇒ 就算 URL 与 CSP 都对了，代理还会回
**400「主机不在白名单」**。

**修**（两侧一起）：

| 侧 | 改动 |
|---|---|
| 代理 | `ALLOWED_HOSTS` 加 `bilivideo.cn`（B站自家 mcdn 镜像，与 `.com` 同款 Referer 策略）；`host_allowed` 拆出纯函数 `is_allowed_url()` 给取流侧复用 |
| 取流 | `parse_dash` / `parse_durl` 把 `[baseUrl, *backupUrl]` 排成 `urls`：**先能过代理的、且优先普通 CDN**（mcdn 是 P2P，排白名单里的后面；`mountaintoys.cn` 这类第三方 P2P 不进白名单，只在没别的可选时兜底） |
| 前端 | `base_url` 之后的镜像进 `videoFallbacks` / `audioFallbacks`，**一条挂了换下一条**（不必回后端重取）；音轨也有自己的链，两条流互不牵连 |

⚠️ 排序是**稳定**的：同档里保持上游给的顺序，所以"哪个镜像先试"是可复现的，不是随机的。

## 四、封面：裸 `<img>` + `http://`

详情页封面来自 `body_json.cover_url`，B站给的是 `http://i1.hdslb.com/…`。
`BiliVideo` 的懒加载封面当时是**裸 `<img src={poster}>`** —— 混合内容 + 不带 `no-referrer`，
于是破图（就是截图里那条黑底"图片"）。全站其它封面都走 `ProxyImage`（https 化 +
`no-referrer` + 失败转 `/img-proxy`），只有这一处没走。

**修**：懒加载封面改 `ProxyImage`；`<video poster>` 那个位置也过 `normalizeImageUrl`。

## 五、顺带：报告刷屏 6 条

`reportUserError('视频播放', …)` 原来写在 `.vp-dead` 的**渲染分支**里 —— 一次失败会随
重渲染反复上报，用户看到的是同一句 ×6，把真正的原因淹了。**修**：挪进 `useEffect`，
依赖只放 `[dead, src, video.url]`（字符串/布尔；`sources` 每次渲染都是新数组，
放进依赖就又变成每渲染必跑）。判据：`reportEntries()` 里"视频播放"必须**恰好一条**。

## 七、修完的实测（真上游 + 真库，用户那条视频 `post id=5034`）

```
GET /bili/play/5034            → 200 kernel=dash quality=80（1080P）
  每条流首选 = upos-sz-*.bilivideo.com（原来是 xy*.mcdn.bilivideo.cn）
  链 = [upos-*.bilivideo.com, xy*.mcdn.bilivideo.cn, *.edge.mountaintoys.cn]
[无头] /video-proxy upos…视频流 → 206 bytes 0-1023/62367205
[无头] /video-proxy mcdn…（第 2 条镜像）→ 206
[无头] /video-proxy mountaintoys…（第 3 条）→ 400（**有意**：第三方 P2P 不进白名单）
[无头] /video-proxy upos…音轨   → 206 bytes 0-1023/5311692
```

⚠️ **一个当时的疑点，已经量掉了**：上游对 `.m4s` 回的是 `application/octet-stream`（不是 `video/mp4`），
而"浏览器会不会因此不认"只能实测。做法：起一个 dev 后端 + 用**无头 Edge**（与 WebView2 同族的
Chromium）打开一个最小页面，把真实地址经 `/video-proxy` 喂给 `<video>`/`<audio>`：

```
proxy content-type: application/octet-stream   range: bytes 0-1023/62367205
video → { ok: true, readyState: 4, w: 1920, h: 1080, dur: 263, ms: 1155 }
audio → { ok: true, readyState: 3,             dur: 263, ms: 1332 }
```

⇒ **Chromium 按内容嗅探，`octet-stream` 照样解码**（`readyState 4` = 已能顺放），
所以**不改**代理的 Content-Type（没有证据就不动它）。
这也顺带证明了代理那条链（Range 直通 + 按主机 Referer + 排序后的首选主机）在真浏览器里可用。
