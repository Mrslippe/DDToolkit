## 一、方案核实：两处按实际情况改了方案

| 方案原写 | 核实结论 | 改成 |
|---|---|---|
| 新增 `app_settings` 表 + 迁移 | `app_meta` 就是"进程外需要记住的少量状态"的 KV 表（v0.9.8），同构新表只是多一处漂移面 + 一次迁移 + 一次 `MIGRATION_HEAD` 变更 + 要让 purge 知道它 | **复用 `app_meta`**（键前缀 `settings.`），**零迁移**（`MIGRATION_HEAD` 仍是 `f004`） |
| 把"每轮读取"的调用点逐个切过去（约 10–15 处） | 实测这些键**全部**在 `services/scheduler.py` 里、且都是"每轮/每账号读一次"（`grep` 出 25 处调用点，没有一处是模块级快照） | 不做调用点迁移：在 `config.Settings.__getattribute__` 上开一个**拦截层**，读的时候先问覆盖层 |

第二处是关键设计决定，值得展开：

```
优先级：实例属性  >  覆盖层（runtime_settings）  >  类属性（默认值）
```

- **实例属性优先是刻意保留的后门**：仓库里测试与脚本一直用
  `monkeypatch.setattr(settings, "REQUEST_INTERVAL_MIN", 0.0)` 把流程压快，那些值常常
  在界面的合法范围之外（0 秒）。若把热更键改成 `property`，这条路会被直接堵死
  （第一版就是这么写的，5 条既有用例立刻报 `property has no setter`，`measure_dynamics_round.py`
  也会挂）—— 那是**为迁就新机制去改老用法的坏味道**，所以退回类属性 + 拦截。
- 拦截只对 `SPECS` 里的 19 个键生效（`_HOT` 是模块级 frozenset，热路径不重建集合）；
  其余键（数据目录/凭据/日志/CORS/cron 时刻…）行为**一个字节都没变**。

## 二、可热更 vs 只读（这张表就是这一批的边界声明）

| 分区 | 键（19 个可热更） | 生效时机 |
|---|---|---|
| 抓取节奏 | `REQUEST_INTERVAL_MIN/MAX` · `FETCH_BATCH_SIZE` · `FETCH_BATCH_COOLDOWN` · `RATE_LIMIT_COOLDOWN` · `MANUAL_FAST_INTERVAL_MIN/MAX` | 下一轮 / 下一个空闲轮次 |
| 动态流与轮询 | `DYNAMICS_BUDGET_RPM` · `DYNAMICS_MIN_GAP_SECONDS` · `DYNAMICS_MIN_CYCLE_SECONDS` · `LIVE_POLL_SECONDS` · `ACCOUNT_SWEEP_STALE_HOURS` · `ACCOUNT_SWEEP_MIN_GAP_SECONDS` | 下一轮 |
| 收录首屏 | `FIRST_SCREEN_VIDEO_PAGES` · `FIRST_SCREEN_DYNAMICS_PAGES` · `FIRST_SCREEN_DYNAMICS_LIMIT` | 下一次收录 |
| 第三方数据 | `EXTERNAL_ENABLED` · `EXTERNAL_ZEROROKU_ENABLED` · `EXTERNAL_DANMAKUS_ENABLED` | 下一次运行（`_source_enabled` 每次运行都查） |

**只读并对用户说明理由**（10 条，见 `/settings` 的 `readonly`）：数据目录 · 端口 · 数据库 ·
CORS · 日志级别与保留 · `MIGRATION_HEAD` · `TIER_TICK_SECONDS` · `EXTERNAL_RUN_HOUR`
（cron 启动时注册）· `DYNAMICS_LATEST_INTERVAL_MINUTES`（只在关掉自适应预算时才有意义）·
`STARTUP_*` / `PRIMARY_PLATFORM_ORDER`（只在启动链那一次读）。

**为什么把 `EXTERNAL_*` 三个开关收进来、却把 `EXTERNAL_RUN_HOUR` 留在只读**：
`externals/runner.py::_source_enabled` 每次运行都查一遍开关，所以关掉之后连
"已经注册好的 cron 空跑"都不会有副作用 —— 它是**真热更**；而 run hour 刻在
APScheduler 的 trigger 里，改了不重启就是不生效，放进"可保存"的界面等于骗人。

## 三、写入路径只有一条（校验都在后端）

`PUT /settings` → 白名单 → 类型 → 闭区间 → **跨字段**（上限 ≥ 下限）→ 落库成功后才替换内存快照。
任何一步不过 → **400 + 中文原因**（前端直接把 detail 显示出来）。

跨字段那条不是洁癖：`scheduler` 里算间隔是 `MIN + uniform(0, MAX − MIN)`，
`MAX < MIN` 时它变成"减"，实际间隔**比下限还短** —— 不报错、只是悄悄变密。

前端只做"提前告诉你会被拒"的即时校验（`utils/settingsDraft.ts`，11 条单测），判定的真源仍在后端；
范围/单位/生效时机**全部由后端下发**（界面不抄一份阈值，否则两边慢慢分叉）。

### 一次被反转的结论（诚实记录）

探针第一版判"弹窗关没关"用的是**节点在不在**，于是 Esc 看着永远关不掉，我据此认定
"radix 自带的 Esc 在本应用里没生效"，还在组件里自己挂了一条 document 级 Esc 监听。
改成看 `data-state` 后复测：**radix 那条一直是好的** —— 关掉之后 `Presence` 会留着节点播
退场动画，而虚拟时间下动画不跑完，节点就一直挂在那儿。自挂的那条已删除，判据的坑写进了
DEV-LOOP。教训与 devlog/071→080 那次"卡死"反转同类：**先怀疑判据，再怀疑被测对象**。
