# 729-20261028-分析完还得等十秒（缓存键不一致）+ 进度条改版

## 一、为什么"分析完成了还要再读十秒"

**根因：同一份数据被算了两遍——因为两次请求的缓存键不一样。**

`_compute` 的键是：

```python
key = (v.subdir, window, since, until, tuple(sorted(live_ids)) if live_ids else None)
```

而两边的参数不同：

| 谁 | `live_ids` |
|---|---|
| 后台分析任务（`POST /fan/{v}/analyze`） | **`None`**（我上一版没传窗口清单） |
| 页面随后取结果（`GET /fan/{v}/ranked`） | **`ids=[…25 个 live_id]`**（窗口切片） |

⇒ 分析任务算的是一份"整个区间"的 payload，页面要的是"窗口切片"的 payload，
**键不同 ⇒ 缓存不命中 ⇒ 从头再算一遍**（实测十秒级）。所以用户看到"分析完成，
页面还在读取结果…"。

### 修法

把**窗口清单一起发**给分析端点：

- 后端 `POST /fan/{v}/analyze` 新增 `ids`（逗号分隔 live_id）参数，透传给 `_compute`；
- 前端 `api.fanAnalyzeStart(..., { ids })`；
- `useFanTask.startAnalyze({ ..., liveIds })`；
- 工作台「分析」按钮传 `slice.map(live_id)`。

这样两个请求的键**逐字相同** ⇒ 分析完页面取结果是**命中缓存**（毫秒级）。

> 这也解释了 `devlog/727` 里那张"卡片在、内容全空"的图：那一刻页面正在**重算**，
> `ranked` 还是旧的、`rows` 已经清了，于是空壳 + "正在读取结果"。

## 二、进度条改版（用户口径）

| 要求 | 做法 |
|---|---|
| 与上下卡片间距太近 | 那一行改成 `margin: 10px 0 14px`（原来上下各 2/4px） |
| 最左标注"这是什么进度" | `<span class="wb-progress-label">采集进度 / 分析进度 / 读取进度</span>`（按当前任务类型） |
| 最右标注进度数字 | `<span class="wb-progress-num">42%</span>`（不确定进度时显示 `—`，不编数字） |
| 完成后渐隐退场、下方卡片顶上 | 完成后保持挂载 320ms，加 `.is-leaving` ⇒ `opacity: 0` + `max-height: 0` + `margin: 0` 过渡，卡片平滑上移（**不再瞬间消失把卡片顶上跳一下**） |

实现方式：页面里 `barActive = running || busy || taskAnalyzing`，
`barLeaving` 由"从出现过 → 现在没了"的边沿触发（`barWasActive` ref），
CSS 过渡时长与 `setTimeout` 的 320ms 对齐。
