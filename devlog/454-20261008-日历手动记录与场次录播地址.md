# 454-20261008-日历手动记录一场 + 场次录播地址

需求 2 / 2.1（用户 2026-10-08）：「日历上能手动补一场（时间、标题），并且给场次存**录播地址**
（BV 号或链接）」。B2 批（`docs/plans/requests-2026-10-execution.md` §B2）。A 档：碰模型 + 迁移 + 路由契约。

## 口径（决定写在这儿，代码里只留一句"为什么"）

| 决定 | 为什么 |
|---|---|
| 「谁写的」沿用 `live_sessions.source` 的第四个值 `manual`（f013 **不加列**） | 再加个 `is_manual` 布尔列就有**两个真相**：`source=danmakus` 与布尔=true 谁对？合并后是 `feed+manual` 组合串 ⇒ 判据是**分词**（`is_manual_source`），且前端不自己拆（响应里带服务端算的 `manual`） |
| 手动行**必须有 id**（`manual-<uuid4>`） | 分类校正、详情/上游/词云端点**全以 `live_id` 为键**。没有 id ⇒ 用户补的这场既不能分类、也点不开详情 |
| 冲突只拦「表内已有记录」（409）；**self 快照重叠放行** | self 推导的场次没有 id、改不了也删不掉 —— 放行是"给自动观测到的场次补标题/录播地址"**唯一**做得到的路径（合并会把快照并进手动组，日历上仍是一条）。表内已有记录则相反：两条真实记录并存正是用户说的"静默重复" |
| 自动抓来的场次**只允许**补录播地址 | 时间/标题下一次同步会被平台数据覆盖回去（`_upsert` 每次刷新非空字段）⇒ 用户看到"我改的又变回去了"。录播地址反过来：**没有任何自动源**，只有用户手上有 |
| 删除只对 `manual` 开放 | 自动行删了下一次同步会放回来 ——「删了又回来」比「不许删」更像故障 |
| 录播地址**入库前**收敛成 `https://www.bilibili.com/video/BV…[?p=N]` | 壳的外链白名单只放行 https + **精确主机**（`docs/desktop/SHELL.md` 不变量 30）。原样存 = 把"能不能点开"推迟到用户点击那一刻。`b23.tv` / `http:` / 非 B 站主机**明确拒绝并说明**，每个拒绝分支都有一句能照着改的中文 |
| 不带时区的时间按**本机本地时区**解释 | `datetime-local` 给的就是墙上时间。当 UTC 存 ⇒ 东八区用户填的 20:30 显示成次日 04:30 —— 用户说不清、代码里也看不出 |
| 录播地址在合并里**只增不减** | 合并的高优分支是 `g.update(_row_dict(row))`，而自动行的 `vod_url` 是 `None` ⇒ 一次合并就把用户手填的地址抹成空（静默丢数据）。这是全表唯一"用户手写、没有任何自动源会重新给出来"的字段 |

## 顺手抓到 / 修掉的三处（都不属于本需求，但都在本批的判据面上）

1. **`LiveSessionRepo._merge_row_into_group` 往元组写 `grp[2]`** ⇒ 执行到就是 `TypeError`，
   也就是**打开日历直接 500**（B2 之前就在）。此前没暴露有两个原因：它只在 `room` 分支
   （双源同 room 同场）且后一行优先级更高时走到，而那个槽位（第三个元素）**全仓没有读者**。
   已删掉那句死写，并补一条用例真的走这条分支（见下表的 ②）。
2. **`ui_probe.py --app-settings` 的 `want_sections` 期望里还留着「平台抓取」**：那一组
   2026-10-08 已从「抓取设置」挪到「数据源」（需求 9/9.1，`devlog/451`）—— 代码改了、期望没改，
   于是这**整步**一直红着（A 档门禁里跑它时才看见）。已摘掉并写清"挪到哪去了"。
3. **探针的「跟随系统」卡片判据会在滚动偏移上假红**：切页不重置 `.aps-pane-scroll`，
   而这一步紧跟在「关于」（只读项 11 + 信息行 14）后面 ⇒ 卡片被裁在视口外，
   `getBoundingClientRect` 照样给坐标、`elementFromPoint` 命中不到，于是报「卡片点不着」。
   修法与同文件 ③d 步进条那条**逐字相同**（先 `scrollIntoView` 再量）——那个坑早就记在注释里，
   只是这一处没照做。修完 `--app-settings` 15 项全绿。
