# 712-20261028-删掉 compose 的绝对值黄金值

## 起因

`tests/test_fan_compose.py::test_outputs_match_golden[明前奶绿]` 在收尾时红：

```
类型分布 got {出勤 911, 互动 773, 付费 1165, 综合 2456}
        want {出勤 904, 互动 783, 付费 1181, 综合 2437}
```

池 `5305 == 5305` **完全一致**（所以第一个断言 `len(t)` 是过的），净变化 **0**
（`+7 −10 −16 +19`）。触发源是 `pilot_v3_mingqian/stats` 里最新一场采于当天 17:16。

用户看完给了一句判词：**「不同的时间窗口分析出的黄金值本来就是不同的」** —— 并据此决定
**黄金值不需要**。这句是对的，而且它判的不是"要不要重录"，是设计本身。

## 为什么钉不住

`GOLDEN` 是三元组：`(入选池, 类型分布四档, 强度前 3)`。而这三样全都是**窗口的函数**：

- 分位是**窗口内**的经验分位（`empirical_percentile`）；
- 池是**窗口内**的 3×ACV（`pool_size_for`）；
- 类型是分位与 0.15 门槛算出来的。

而它用的窗口是 `load_window(V, 75)` —— 每次跑都重新解析"最近 75 场"。于是断言的语义变成
「这个随输入滑动的函数，输出必须等于上次的常数」：**每天红一次，红的时候没有信息量**，
而唯一修复办法是"更新数字" ⇒ 训练所有人别去看它，真正的模型回归反而被淹掉。

## 关键发现：仓库里早就修过一半

`tests/test_fan_loader.py` 的同一类冻结值**已经修好了**，注释里写的就是这个教训：

```python
FROZEN_UNTIL = "2026-10-26"       # ← 差额就在这一个参数上
s = summary(load_window(v, 75, until=FROZEN_UNTIL))
```

"用户在应用里点一次采集，窗口就会滑动，本用例随即变红" —— 于是用截止日把窗口身份锁死。
**compose 那份只是漏了这一步**（它从 2026-10-20 起一直按裸的"最近 75 场"冻结）。

所以两条路都成立：给 compose 补 `until=`（2 行 + 重录一次），或者按用户口径直接删。
用户选了**删** —— 理由是绝对值本来就不是这个模型的契约（窗口相对分位没有"绝对正确值"）。

### 接手的两条不变量（数据无关 ⇒ 永不重录）

- **⑧ 类型判定不漏也不重**：四档计数之和 == 池人数；`set(labels) == set(t.uids)`；
  顺带钉住 **ACV 池裁剪的接线**（`len(t) == pool_size_for(w)`）——
  这一条正是 04-validation 原来写"由 L2/L3 覆盖"的那块。
- **⑨ 强度与次序自洽**：强度覆盖全池、落在 `[0,1]`；`rank()` 是池的**排列**（长度、无重复、
  同一批人）；次序与强度**同序**（不增）—— 最后一条专防"算一套、排另一套"。

判据写坏（分支漏 `return`、四档阈值不再互斥、排序用了另一个分数）会当场红；
而数据怎么变都不会红。**这就是原来那两条断言真正该测的东西。**

## 保留 loader 的绝对值

`test_fan_loader.py` 的冻结聚合值**没动**：它钉的是 `until=FROZEN_UNTIL` 的窗口，
输入是冻结的 ⇒ 绝对值这时是有效契约。残留脆弱点写在该文件注释里（冻结区间内被补采要重记）。

## 判据（写给以后想加回绝对值的人）

> **先问"输入冻结了吗"。** 冻结了（合成夹具 / 截止日 / `live_ids`）⇒ 绝对值有意义；
> 没冻结 ⇒ 只能钉关系。

已把这条写进 `test_fan_compose.py` 的原地注释与 04-validation §7.2，避免以后有人
"为了恢复覆盖率"把 `GOLDEN` 加回来。
