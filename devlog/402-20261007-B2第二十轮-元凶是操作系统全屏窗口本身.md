# 402-20261007-B2第二十轮 元凶是"操作系统全屏窗口"本身

两个回答（2026-10-07）：

1. **应用窗口最大化也没放大视频播放器，所以依旧流畅**
   —— 窗口/合成表面**确实**变成了整屏（1920×1080），视频仍只有 `678×381`（它被详情抽屉的
   宽度卡住，与 `max-height:60vh` 无关）。**⇒「合成表面够大」出局。**
2. **全屏状态下任务栏消失了，窗口盖住整个屏幕**
   —— 确认 `requestFullscreen()` 经 wry 把**宿主窗口**设成了真全屏窗口。

## 拆完了：五格对照，只有一个变量还对得上

| 窗口状态 | 画面大小 | 结果 |
|---|---|---|
| 窗口态（~700px 宽） | `678x381` | **0.0%** |
| **最大化**（表面 1920×1080） | `678x381` | **0.0%** |
| 真全屏 | `678x381`（`size` 格） | **7.7%** |
| 真全屏 | `1920x1080` | **10~13%** |
| 真全屏 + 透明底（`surface` 格） | `1920x1080` | **10.2%** |

⇒ **元凶是「操作系统把窗口当成全屏窗口」这件事本身**，与视频多大、底色透不透明、
合成表面多大**都无关**。合起来就是一句：**只有真正进了 OS 全屏的那条呈现路径会丢帧。**

## 还差一格没解释（如实留着）

**seek 能把状态清掉**（`devlog/398`：两次 seek 之后全屏下也是 0.0%），而 seek 并不改变窗口状态。
⇒ 说明全屏窗口只是**把呈现路径换成了会丢帧的那条**，而 seek 能把它换回去（流水线重建 ⇒
DWM/驱动那条路退回去）。这个"怎么换回去"目前是黑盒，但**它是可用的**（用户的现成绕过办法）。

## 下一步：先免费试两格 Chromium flag（不用改代码）

既然病灶在"全屏窗口的呈现路径"，最该先试的是**换掉那条路径**（口径见 `PROBE.md` §6.22）：

```powershell
# ⚠️ 这个环境变量是**整串替换** wry 的默认参数，所以三条默认值必须自己拼回来
$env:WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS='--disable-direct-composition --disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection --autoplay-policy=no-user-gesture-required'
npm run tauri:dev
```

- `--disable-direct-composition`：不走 WebView2 的 DirectComposition 呈现（最贴近嫌疑）；
- 若无效再试 `--disable-gpu-compositing`（退到软件合成 —— 它还卡就基本能排除"GPU 呈现路径"）。

⚠️ 注意 `--disable-direct-composition-video-overlays` 早就试过、零效果 —— 那条只关"视频覆盖层"，
与"整个 WebView 的 DC 呈现"不是一回事。

## 如果确认了，修法是"假全屏"

不再进 OS 全屏状态，改成**无边框 + 铺满显示器**的普通窗口（Tauri 侧改窗口，而不是
`requestFullscreen()`）。⚠️ 风险要提前说：Windows 的"全屏优化"对**恰好铺满屏幕的无边框窗口**
同样会生效，所以这条也不是稳赢，得实测。`pseudo` 因此复活 —— 但它**必须真的改变 OS 窗口**
（单纯 CSS 放大画面量到的是另一个东西，`devlog/400` 已经栽过）。
