# 327-20261004 长视频跳转根因（三）：段表比媒体自己的 tfdt 偏晚几十毫秒

> 用户复现（`devlog/326` 之后）。326 加的"追加后缓冲没变"那一行这次**没被节流掉**，
> 一句话就把最后一环指出来了。

## 一、那一行现场

```
16:43:08 video 追加段 803 后**缓冲没变**：
        区间=[0.0–30.0, 4015.0–4020.0]×2 目标=4015.6s duration=4587.41 时长表=4587.0s
16:43:15 video 段 804（bytes=640394188-641038359）连取 3 次仍没落地（区间=…×2 目标=4020.4s）
```

- `duration=4587.41` **正常**（不是时长截断）；
- 区间里已经有 803（= 4015–4020），**追加它当然不变** —— 所以问题不是"数据没落地"，
  而是**泵在反复取一段已经有的段**。

## 二、为什么它会去取 803

拿真机的段逐个读 **媒体自己的 `tfdt`**（不是段表）：

| 段 | 段表说它从 | 媒体 `tfdt` 说 | 差 |
|---|---|---|---|
| 249 | 1245.007s | 1245.000s | **+7ms** |
| 536 | 2680.013s | 2680.000s | **+13ms** |
| 803 | 4015.021s | 4015.000s | **+21ms** |
| 804 | 4020.021s | **4020.000s** | **+21ms** |

⇒ **sidx 的累计时刻一律比媒体自己的时间戳偏晚**，且随索引缓慢增长（≈0.025ms/段）。
于是"缓冲末尾（**真实**时刻 4020.000）之后该取哪一段"算出的是**刚取过的 803**
（表内它的结尾是 4020.021 > 4020.000）⇒ 泵反复重取、缓冲一点都不长 ⇒
真机症状：「跳转后画面播放一小段卡住、声音依旧」（音频轨有数据，元素继续走时钟）。

⚠️ 324 那批修的是"**累加四舍五入**"（531 段 0.26s），这一批是它的**上游**：
即使按时长精确累加，sidx 与媒体之间**本来就有**几十毫秒的固定偏差。两批是叠加的两层。

## 三、改法（`utils/mseKernel.ts`）

判"下一段"时加一条**很窄**的兜底：

```ts
let next = nextSegmentAfter(table, runway)
const endOfNext = segmentEndAt(table, next)
// 算出来的正是刚取过的那一段，且它的表内结尾只比缓冲末尾晚一点点（< SEG_END_TOL=0.5s）
if (next === tr.lastIdx && endOfNext !== null && endOfNext - runway < SEG_END_TOL) next += 1
```

- 只在这两个条件**同时**成立时才往后推一段 ⇒ 不会跳过真正缺的那一段（真缺的那一段，
  它的表内结尾离缓冲末尾有半个段长那么远）；
- 阈值 0.5s：远大于观测到的偏差（≤ 数十毫秒），远小于段长（5s）。

## 四、判据（`mseKernel.test.ts`，反向验证过）

「缓冲末尾落在表内结尾前一点点 ⇒ 必须往后推一段」：段表用整数秒、媒体帧时间戳统一提前 21ms
（真机实测值）⇒ 断言续播必须过 30s、且取到 3 个以上不同的段。
反向：把这条兜底去掉 ⇒ 红（`续播卡在 24.979s`，与真机同形）。

一起兜住了。判据改成"两道防线各自都够用"（真正的反向验证在 327 这组）。
