# 115-20260916-R23c更新检查的代理兜底

> 用户（2026-09-16）："检查更新自动检查是否开启有代理应用在运行，防止实际上用户能用代理打开
> github 但应用内直连失败"。这条提得对，而且我先把事实查清了 —— **一半已经被覆盖，另一半是真漏洞**。

---

## 一、事实（不是猜的）

| 查什么 | 结论 |
|---|---|
| Tauri 更新器用的 HTTP 客户端 | `reqwest 0.13.4` |
| 它启用的特性 | `cargo tree -p reqwest -f "{f}"` ⇒ **含 `system-proxy`**（底层 `client-proxy-system`）⇒ **系统代理模式本来就走代理** |
| 这台机器的系统代理 | `ProxyEnable=1`、`ProxyServer=127.0.0.1:7897` ⇒ Clash 开着系统代理时，应用内检查更新**不会**直连失败 |
| 配置里有没有代理项 | `gen/schemas/*.json` 里没有 proxy 相关配置 ⇒ 只能靠"系统代理 / 环境变量"两条路 |

**所以真漏洞只剩一种情形**：代理进程在跑，但**没设成系统代理**（只配在浏览器扩展 / git / 别的工具里）
—— 用户以为"我有代理"，应用却直连超时。

## 二、补的兜底（失败路径上重试一次）

```
check()  ──成功──► 完成（系统代理模式就走这条）
   │失败
   ▼
probe_local_proxy()   ← Rust：TCP 探 127.0.0.1 的 7890/7891/7897/10809/1080/2080/8889
   │探到
   ▼
set_process_proxy(url) ← Rust：把 HTTPS_PROXY/HTTP_PROXY 设进**本进程**（不动系统设置）
   │
   ▼
check() 再试一次 ──成功──► 记下"本次走了代理"；失败 ⇒ 错误信息里写清"试过代理仍失败"
```

三条设计取舍：

1. **只在失败后试**（不在每次检查前探测）：不打扰任何进程、不增加正常路径的延迟，
   系统代理模式下根本走不到这条分支；
2. **只改本进程环境变量**，不写注册表、不改系统设置 —— 对用户环境零副作用；
   ⚠️ `set_var` 非线程安全，所以只在这条窄路径上调用，且它只影响**新构造**的 HTTP 客户端
   （reqwest 在建 client 时读环境变量 ⇒ 重试的那一次会读到）；
3. **错误信息必须能区分三种失败**：直连失败且**没有**本地代理（"也没检测到本地代理在监听"）、
   直连失败但**试过**代理仍失败（把两个原因都写出来）—— 用户才能判断是自己去开代理，
   还是干脆走「打开发布页」手动下载。

## 三、用例

`cargo test` **26 passed**（+1）：起一个真的本地监听 → 能探到该端口；**没监听的端口（9）返回 `None`**
—— 判错的代价是"把没有代理当成有"（更新检查被导向死地址）或反之（错过能用的代理）。
