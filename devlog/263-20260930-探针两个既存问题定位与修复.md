# 263-20260930 探针两个既存问题：定位与修复

上一轮收尾时记下两条"与本线无关的既存问题"。这一轮把它们查到底 —— 结论是**两条都不是
"环境抖动"，各有具体根因，其中一条是本次轻资产批次的真 bug**。

## 一、`--status-island` 的「面板里的条目不可命中」= DEV 覆盖层压住了命中测试

**量到的事实**（给探针加临时诊断，采 `elementFromPoint` 的真身）：
`item rect=[372,75,333,50]`、面板矩形正常、`pointer-events: auto`、而 `elementFromPoint(center)`
返回 **`pre.`** —— 那是 DEV 的 `#boot-diag`（资源加载失败 ≥3 次才弹，里面是 `<pre>` 堆栈），
它整块压在界面之上。**生产里没有这个元素**，所以这不是产品的问题，是判据被 dev-only 干扰。

**修法**：`hits()` 改成遍历 `elementsFromPoint` 并**跳过 `#boot-diag` 子树**，取"生产里真正会
接住这一击"的那个元素（4 处同款 `hits()` 一起改）。与 R48 把 `#boot-diag` 从 scroller 清单里
排除是同一条纪律的第二次现身。修后 `--status-island` **[ok]**（`首条=True`）。

## 二、`--app-settings` 的保存偶发不生效 = 三件事叠在一起

拆开看是三条互不相干的毛病，**症状一模一样**（界面回显对、服务端没变、没有「已改过」标记）：

1. **等待不会产生真实时间**（虚拟时间坑，M4 记过一次）：`waitFor` 用 `performance.now()`+`sleep`，
   在虚拟时间下几乎立即返回 ⇒ PUT 还在飞、探针就去读服务端了。**主题那半就是它** ——
   改成"每轮打一发真请求当进度条"之后稳定通过（3/3）；
2. **探针把 `-shm` 也拷过去了**：`_SEED_FILES` 里有 `vtuber.db-wal`/`-shm`，而 `-shm` 是
   进程内共享内存（锁表），拷过去会让 SQLite 以为"别的进程持着锁"。改成 **SQLite 在线备份 API**
   拷一个自洽单文件（顺带修掉"只拷主库会漏 WAL 里已提交事务 ⇒ 探针拿陈旧库跑判据"）；
3. **真根因（本批的 bug）**：`_pin_account_covers` **从第一张 `put` 起就持有写事务，跨着后面
   所有图片下载**（每张几秒，慢的 ReadTimeout 15s）才提交一次 ⇒ 同一进程里**所有别的写**
   全部 `database is locked`（后端日志：设置保存失败、`local_assets.last_used_at` 写不进去、
   `_seed_accounts` 直接崩）。**修法**：每张落盘即 `db.commit()`（锁内不做网络/重 IO —— 与
   `_status_lock` 那条纪律同源）；判据用"下载第 N 张时另开会话能看见前 N-1 张"钉住，反向验证
   去掉逐张提交 ⇒ 当场红。

## 三、顺带抓到 M5-2b 的一个真回归（探针抓的）

修好上面三条之后，默认探针立刻报红：**「推了一条『任务已受理』进度，顶栏面板里没有它」**。
根因是我在 M5-2b 写的让位规则**按 kind 判**（"服务端只要有 progress 就让位"）—— 于是
**外部同步**那条进度（`progress-external`，与手动动作无关、还常常一直在跑）把本地那条
"任务已受理"顶掉了 ⇒ 点按钮的人又得等 3–10s 轮询，**M2 的收益整个没了**。
**修法**：按**任务**让位（只有 `progress-post`/`progress-account` 才顶掉本地那条，与旧口径
`status.manual_running` 同粒度）；判据补"服务端只有外部同步 ⇒ 本地那份留着"。

⚠️ 这条为什么上一轮没红：那时探针的库副本是**原样拷贝**（可能停在旧 WAL 上），外部同步恰好
没在跑；改成在线备份之后数据更新、外部同步在跑 ⇒ 立刻现形。**判据的现场比判据本身更容易陈腐**。
