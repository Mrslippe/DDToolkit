# 540-20261019-「窗口 75 场 / 已有 77 场」

用户报：窗口场次 **75**，已有 **77**，待采 **1** —— 三个数加起来 78 ≠ 75。

## 根因：两套口径

| 数字 | 口径 |
|---|---|
| 窗口场次 75 | 按**场次**切出来的 75 条（滑杆的 `size`） |
| 已有 77 / 待采 1 | 拿这 75 条首尾的**日期区间**，回库里再数一遍 |

日期区间是**整天**的。窗口首尾那两天各有额外场次，于是区间内有 **78 场** —— 比窗口多 3。
所以"已有 + 待采"按区间算，永远可能超过"窗口场次"。用户采完 4 场（3 成 1 跳过）后，
库里那两天更满，77 / 1 就露出来了。

> 这就是我早先在文档里写的"0~1 场边界漂移"的真实规模：不是 0~1 场，
> **取决于边界日当天有几场**，多的时候能到 +3。

## 改法

**窗口内的数字一律从切片上数**：

```ts
const slice = activity.recent.slice(win.start, win.start + win.size)
const alreadyInWin = slice.filter((s) => s.c).length
const toCollect = win.size - alreadyInWin
```

`/activity` 的 `recent` 每条本来就带 `c`（该场是否已采）—— 不用再打一次 `/sessions` 预估。
于是 `已有 + 待采 ≡ 窗口场次` 恒成立。

**副作用**：`待采` 不再存在"未知"状态（窗口只在 `activity` 到了之后才有），
原来那条"未知 ≠ 0"的用例失去意义 —— 换成**不变量**用例：已有 + 待采 = 窗口场次。
