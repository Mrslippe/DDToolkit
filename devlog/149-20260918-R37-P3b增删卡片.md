## 二、三个设计口径（都写进注释与规格 §11）

1. **菜单只列"不在板上"的 kind** —— 同一种卡片放两份，显示的是同一份数据（卡片跟随的账号由页面上下文决定），
   所以重复加没有意义。全部都在板上时按钮**禁用并写明原因**（"点了没反应"是最糟的空态）。
   ⚠️ 这条也意味着：**默认布局已经把三种内置卡都摆上了**，所以本批在真机上最直观的用法是
   "先移掉一张、再加回来"。它真正的价值要等卡片类型变多（以及下一批的自定义卡）。
2. **删卡不塌陷**：其余卡片位置一动不动。用户是**自己摆过**这些卡的，塌陷会把辛苦排好的位置全部重排 ——
   留个空洞用户自己拖一下就能补上，比"删一张、全乱"友好。
3. **不弹删除确认**：本批删的只是**卡片**（帖 / 场次 / 大事记都还在库里），随时能加回来；
   而"拿下来"这件事本身可逆，弹窗只会拖慢排布。

## 四、护栏（反向验证 2 红 → 0）

新探针 `--board-cards`（一档宽度，1440）：

| 步骤 | 判据 |
|---|---|
| 编辑态 | `data-board-editing=1`、每张卡头部有 `.pcard-remove` |
| 移除 | 卡片数 −1、被删的 key 不在 DOM 里、删完**零重叠** |
| 菜单 | 列出的是**恰好**刚删掉的那一种（`data-kind` 列表逐项比） |
| 加回 | 卡片数回到初始、**默认尺寸**（大事记 6×3）、**零重叠**、key 与原来一致 |
| 按钮态 | 删掉一张后可点；全部在板上时**禁用** |
| **后端对账** | `GET /vtuber/{id}/profile-cards` 的 key 集合与界面**逐个一致**（只看 DOM 的话"界面删了但库里还在"照样绿） |

实跑：`初始 3 张 → 删后 2 张 → 加回 3 张`，菜单 `['anniversary']`，后端 `['anniversary','events','top-posts']` ✓。
