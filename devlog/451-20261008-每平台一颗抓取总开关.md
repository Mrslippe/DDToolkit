# 451-20261008-每平台一颗抓取总开关（数据源 → 平台抓取）

用户 2026-10-08 口径（需求 9 / 9.1）：

> 在设置中把平台抓取功能的开关做出来，并且放在**数据源**那一项中。
> 9.1 开关应该只影响是否启动抓取。
> （补充答复）**全都拦住**，不过用户启动手动抓取后**给提示**。

## 改法：把"只有抖音那一条"泛化成单一真源

抖音当年只有**一处**闸门（适配器内部，`devlog/335`），于是别的路（手动端点、批量、
自动档）**照样会发请求** —— 这次顺着需求把闸门收成一处真源：

| 位置 | 角色 |
| --- | --- |
| **`services/platform_switches.py`**（新） | 唯一真源：`enabled(platform)` / `disabled_reason(platform)` / `states()` / `settings_path()` |
| `capabilities.content_fetch_allowed` | **手动档**的闸门（`_require_content_fetch` ⇒ 端点 403 + 原因 ⇒ 前端 toast **就是用户要的"提示"**）；**总开关排在登录检查之前、且对每个平台都问** |
| `capabilities._disabled_reason` | 能力矩阵把"我们自己关的"报成 **`disabled`**（不是 `requires_login`，`devlog/338` 的教训） |
| `scheduler.platform_accounts_of` | **自动档**唯一的按平台入口：关着就挑不出账号 ⇒ 一个请求都不发 |
| `runtime_settings` | 四颗开关都挂 `group="数据源" / section="平台抓取"`（用户指定的位置） |

⚠️ **默认值按平台不同**：抖音默认**关**（协议禁止自动化），其余三家默认**开** ——
新增开关时顺手把它们默认关掉等于**把用户已有的功能关掉**。
⚠️ **读设置失败退回该平台的默认值**（不是一律 False）：一次读设置异常不该把四个平台全停掉。
⚠️ **路径文案只有一份**：`settings_path()` 从 `runtime_settings.spec(...)` 的 `group`/`section`
**拼**出来，不再写「设置 → 数据源 → 平台抓取」这种字面量（改分组时提示自动跟上）。

## 判据（新增 `tests/test_platform_switches.py` 10 条）

① 默认值（并**与设置声明对账**：`SWITCH_KEYS` 里每个键的 `Spec.default` 必须与 `DEFAULTS` 一致）；
② 读设置异常 ⇒ 退回默认（＋正对照"抖音仍然关"）；③ 未知平台按开（不因为没登记就停功能）；
④ 关掉时的理由含**平台名 + 设置路径 + "一个请求都不发"**；⑤ 手动档被拦（正对照：同平台开着且登录齐 ⇒ 放行）；
⑥ 能力矩阵报 `disabled`（含理由）；⑦ 自动档挑不出账号（正对照：开着时照旧、别家不受影响）；
⑧ **四颗开关都在「数据源 → 平台抓取」**（结构判据 —— 分组改名时它会红）。

**反向验证**（四组，全部杀死）：手动档不再问开关 ⇒ ⑤ 红；把微博那颗挪去「抓取设置」⇒ ⑧ 红；
读失败一律当关 ⇒ ② 红；自动档闸门失效 ⇒ ⑦ 红。

## 顺带修的一处"判据静默失效"

`tests/test_capabilities.py` 里四处 `monkeypatch.setattr(C, "_douyin_enabled", ...)`：
真源搬走后那个函数**只是转发** ⇒ patch 它**等于没 patch**，而失败信息长得跟以前一样
（"四家都就绪后不该还有受限项"），很容易误判成产品坏了。改成 patch 真源
（`platform_switches.enabled`），并在辅助函数上写清这段缘由。
⚠️ **搬家真源时，先全局搜一遍"谁在 patch 那个旧入口"** —— 那是测试层最隐蔽的漂移。
