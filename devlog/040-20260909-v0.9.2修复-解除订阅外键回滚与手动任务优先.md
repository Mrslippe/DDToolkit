# 040-20260909-v0.9.2 修复-解除订阅外键回滚·手动任务优先于定时档

> 用户 2026-09-09 两条反馈：①「解除订阅失败了，先查找一下原因」；
> ②「应该让用户手动任务的优先级高于自动任务，例如刚启动应用的时候如果我添加了一个
> 新 vtuber，那么这个时候添加行为拉起的抓取任务就会被正在运行的自动任务挤占掉
> 导致账号信息获取不到」。

## 一、解除订阅失败：账号子表没清，外键把整次删除挡回去了

**定位**（用户开发数据目录副本 + 真机复现）：删除日志只打印了一行
「解除订阅 VTuber#19 (永雏塔菲)：连带清除帖子 0/2 条」就没了下文，V 一直还在。
直接用 repo 跑一遍删除，异常立刻现形：

```
sqlalchemy.exc.IntegrityError: (sqlite3.IntegrityError) FOREIGN KEY constraint failed
[SQL: DELETE FROM accounts WHERE accounts.id = ?]   [parameters: (22,)]
```

**根因**：`app/core/database.py` 给 SQLite 开了 `PRAGMA foreign_keys=ON`，而
`accounts` / `vtubers` 之下有 6 条外键，ORM 只给 `VTuber.accounts` 配了级联：

| 表 | 外键 | 原删除路径是否清理 |
|---|---|---|
| posts | 无外键（按 platform+uid 显式清） | ✅ |
| account_stat_snapshots | accounts.id | ❌ ← 1630 行 |
| live_sessions | accounts.id | ❌ ← 1350 行 |
| live_gift_days | accounts.id | ❌ |
| live_category_overrides | accounts.id | ❌ |
| vtuber_events | vtubers.id | ❌ |

只要账号有一行快照/场次，`DELETE FROM accounts` 就被外键挡下 → 事务回滚 →
接口 500 → 前端「解除订阅失败」。之前没暴露是因为旧数据里没删过带场次的 V。

**修复**：

- 新增 `app/services/purge.py`：`purge_account()` / `purge_vtuber()` 把「删干净」
  的清单收在一处（帖子按 uid、4 张子表按 account_id、活动条目按 vtuber_id），
  **不提交**，由调用方同一事务 commit（失败整体回滚，不会删一半）；
- 两个入口（`DELETE /vtuber/{id}`、`DELETE /account/{id}`）改走它，并捕获
  `IntegrityError` → 409 + 明确日志（不再 500 哑失败）；
- repo 层补 5 个 `delete_by_account/delete_by_vtuber` 批量删除（`synchronize_session=False`）。

**验证**：真实数据副本上 `DELETE /vtuber/19` → 204，日志
`清理 {'events': 0, 'posts': 2, 'snapshots': 1630, 'live_sessions': 1350, ...}`，
删除后 6 张表残留全为 0。测试侧同时把 `tests/test_vtuber_api.py` 的测试引擎
加上 `PRAGMA foreign_keys=ON`（与生产同口径）——这样「漏清子表」以后跑测试就会红。

## 二、手动任务优先：定时档在断点给手动任务让位

**根因**：`_fetch_lock` / `_post_fetch_lock` 的既有约定是「自动档起跑时见手动任务
就跳过」，但反方向没做——手动任务拿不到锁就直接 `skipped`。启动链
T1→T2→T3a 会连续占锁几十秒到几分钟，这期间收录新 V 拉起的 `async_fetch_vtuber`
必然失败，账号信息一直空白。

**修复**（`app/services/scheduler.py`）：

- 新增抢占协议：`_preempt_account` / `_preempt_post`（手动侧置位）+
  `_auto_account_active` / `_auto_post_active`（自动侧声明持锁）；
- 手动侧 `_acquire_manual_account()` / `_acquire_manual_post()`：空闲直接拿；
  占用者是**自动档**则置位信号并轮询等锁（上限 `MANUAL_PREEMPT_WAIT_SECONDS=120s`）；
  占用者是另一个手动任务则不抢（手动之间不互相打断）；
- 自动侧在**断点**（账号之间）调用 `_maybe_preempt_account/post()` → 释放锁、
  等信号清除、重新拿锁、**从原序号续跑**，并保存/恢复 `_fetch_scope`；
- 手动端点 409 判定改用新的 `manual_task_running()`：自动档持锁**不再**把用户
  请求挡在门外；外部数据批次（T4）仍用 `any_fetch_running()` 跳过；
- 顺带修掉 `_fetch_scope` 的真 bug：`async_fetch_and_update` / `async_fetch_vtuber`
  / `run_main_account_sweep` 里赋值却漏了 `global`，导致这个模块级标记一直是
  `None`（旧让位函数 `_yield_account_wait` 读取它还会直接 `UnboundLocalError`）。

**验证**（`tests/test_services.py` 新增 6 个用例）：

- 端到端：T1 自动档正在抓老账号（假网络 0.5s）→ 手动 `async_fetch_vtuber(新V)`
  → 抓取顺序实测 `["100", "200", "200"]`（自动档先跑、让位、手动抓到新账号、
  自动档续跑），手动结果 `success=1`，新账号粉丝数落库 + 落一条快照；
- 让位锁舞（账号/帖子两侧各一）：自动侧在独立线程的事件循环里让位 → 手动拿到
  → 跑完 → 自动侧恢复并持有锁；`_fetch_scope` 让位后恢复为本任务标记；
- 语义边界：自动档持锁时 `manual_task_running()=False`（手动可抢）、手动档持锁
  时为 `True`（拒绝并发手动）；无请求时断点检查是空操作。

## 四、经验

- 表关系有外键就要有**一处**权威的清理清单；把清单散在路由里，漏一张表就是
  「接口 500 但日志只有半句」这种最难查的失败。测试库必须开
  `PRAGMA foreign_keys=ON`，否则这类 bug 在 CI 里永远绿。
- 并发优先级别只做一半：既要有「自动让手动」，也要有「自动起跑时让位」，
  并且两把锁各自独立（账号/帖子互不牵连）。
- 让位/抢占这类锁舞一定要有**断点**（账号之间）和**超时兜底**，否则一次卡死
  就是整个抓取链路永久停摆。
