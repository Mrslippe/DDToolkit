# 463-20261011-多平台按名字搜人（B1）：四家全部做得到

原计划 A–D 四批里，A、B2、B3、C2、C3 都已落地，**下一步是 B1 多平台模糊检索** ——
它卡的正是"微博 / 小红书 / 抖音的搜人接口可不可行"这几条 spike。
用户 2026-10-08 的口径：输入名字时**同时在"已开启的平台"上做模糊检索**，
有结果就展示，**全都没有**才显示一行「没找到」。

## 一、spike：四家全部做得到（真机实测）

| 平台 | 接口 | 结果在哪 |
|---|---|---|
| B 站 | `wbi/search/type?search_type=bili_user` | `data.result[]` —— 已有实现，转发即可 |
| 微博 | `weibo.com/ajax/side/search?q=` | `data.users[]`（`idstr`/`screen_name`/`followers_count`/`description`） |
| 小红书 | `POST /api/sns/web/v1/search/usersearch` | `data.users[]`（`id`/`name`/`fans`(串)/`image`） |
| 抖音 | `/aweme/v1/web/discover/search/?search_channel=aweme_user_web` | `data.user_list[].user_info`（`sec_uid`/`nickname`/`follower_count`） |

**这一轮最大的价值是三个"差点得出错误结论"的坑**（每个都先得出过"做不到"）：

1. **微博**第一轮打 `m.weibo.cn`（移动站）恒定 `ok=-100`，我一度以为"微博搜人做不到"。
   真因**本仓早就写过**（`platforms/weibo.py` 文件头）：扫码产出的 SUB cookie **只对 PC 域有效**，
   移动站要 wapssowb 链路。换到 `weibo.com` 立刻就通了。
   ⚠️ 顺带发现：`check_valid()` 探的是 PC 域（`weibo.com/ajax/profile/info`），
   所以它说"有效"而 m 站路全 -100 —— 两者不矛盾，但**别拿它当"m 站也能用"的证据**。
   ⚠️ 另一个形态差异：它是**建议型接口，只回最匹配的 1 条**（不是分页结果列表）。
   这一条如实带到界面上（`best_match_only` → 「微博命中 1 条（该接口只给最匹配的一个）」），
   否则用户会以为"全网就这一个人"。
2. **小红书**我猜的三个路径全是 404。真路径是从**官网前端 bundle 里 grep 出来的**
   （`/api/sns/web/v1/search/usersearch`）；请求体还是**嵌套**的
   （`{"search_user_request": {...}}`），里面 `biz_type` 与 `request_id` 都必填 ——
   这两个不是猜出来的，是**接口一条条"要"出来的**（少一个就 400 并点名缺谁）。
3. **抖音** `general/search/single` 配 `search_channel=aweme_user_web` 回的是**视频卡**
   （9 视频 + 1 相关词），用户卡在**另一个端点**：`discover/search` → `user_list[]`，
   而且每条**包了一层** `user_info`（直接当用户对象读会一个字段都取不到 —— 第一版就这么写的，
   用例当场抓到）。

## 二、落地：一个入口、四家分组

- **后端** `services/name_search.py`：四家的"按名字搜人"统一成一条流水线 ——
  统一条目形状（与 `bili_search.map_search_item` **逐字同形**，前端只有一条渲染路径）、
  每平台 1s 间隔 + 5 分钟缓存、失败分类（`not_logged_in` / `upstream_degraded` /
  `network_error` / `not_found` / `unsupported` / `empty_kw`）。
  ⚠️ **签名/身份/UA 的管道一律复用各平台适配器**（小红书 `_signed_headers`、
  抖音 `_base_params`/`_signed`）—— 另起一份请求实现就是长出第二个签名源。
- **端点** `GET /vtuber/users/search?kw=&page=&platforms=`：按平台分组返回，
  每条带 `in_library`（前端据此置灰）。⚠️ 路径**两段**（一段式会被 `/vtuber/{vtuber_id}` 吃掉 → 422）。
- **平台关着 ⇒ 一个请求都不发**：结果里 `skipped=true` + 「去哪打开」那句
  （`platform_switches.disabled_reason`，与能力矩阵/自动档同源）。
  ⚠️ `skipped` 与 `error` **必须分开**：关着是用户的设置，不是故障，界面文案也不同
  —— 合成一个"空"就等于把"你关了开关"说成"没这个人"。
- **纯数字（≥5 位）只搜 B 站**：那是一条 UID（"按 UID 添加"的既有能力），
  另三家拿数字当关键词搜只会白发三发请求、还可能排上无关的人。
- **前端**「添加 V」把入口从"只搜 B 站"换成**一次搜四家**（同一个按钮，文案不变档：
  非 uid 时「搜索」、uid 时仍是「按 UID 添加」）；结果按平台顺序分组展示，
  `load more` 按平台分别拼接；每平台一行状态（关着 / 失败 / 没结果 / 命中几条 / 只给一条）。
- **一键收录**：`_VERIFY_BY_PROFILE` 补上 **微博** ⇒ **四家都能池外收录**
  （后端拿 uid 实查一次主页信息才建库，不信请求体）。
  ⚠️ 那张表的注释原写着"两家**没有**可用的搜索接口" —— 那句今天不成立了，已改。
  按 uid 收录的两个老按钮**保留**（搜索要登录态，而"用户手上就一条主页链接"是常态），
  但文案里的"没有搜索接口"一起改掉了。

## 三、判据（**5 个变异逐个杀死**）

| 判的东西 | 判据 |
|---|---|
| 关着不发请求（★） | `test_disabled_platform_is_skipped_without_any_request`：把 searcher 换成"被调用就炸"，同时 `enabled=False` ⇒ `skipped=True`、`error=None`、**没被调用** |
| 抖音用户卡解析 | `test_douyin_parses_user_list`：★**忘了拆 `user_info` 那层包装**就是它抓到的 |
| 微博 -100 | `test_weibo_minus_100_means_logged_out`：`not_logged_in` + "去登录" + 让认证单例记住 |
| 小红书 `fans` 串 | `test_xhs_parses_users_and_fans_string`：`"17.3万"` → 173000（`int()` 会抛，抛了当 0 就是把 17 万粉的大 V 显示成 0 粉） |
| 单平台失败不拖垮其余 | `test_one_platform_raising_does_not_kill_the_rest` |
| 纯数字只搜 B 站 | `test_uid_input_only_queries_bilibili` |
| 缓存 | `test_results_are_cached`：同关键词第二次不打上游 |
| 端点分组/三态/in_library | `test_users_search_endpoint_groups_hits_and_flags_in_library`（在 `test_vtuber_api.py`，那里有全套隔离夹具） |
| 前端三态 | `addVtuberSearch.test.ts`：★**只有"发了、没报错、没被跳过、真没结果"才说「没找到」**；每平台五态文案 |

探针（`ui_probe --add-v`）那条"敲键不打上游"的判据也顺手补了：
入口改成 `/vtuber/users/search` 之后，只数旧的 `/vtuber/bili/search` 会让它**空转**
（按钮早就改道了）—— 现在两个端点都数。
