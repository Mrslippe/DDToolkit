# 189-20260925-R45F 工具条允许覆盖标题 + 横向让位量退役

> 本批是**用户一句话的口径变更**落成的：删掉一个写死的数、换两条能红的判据。
> 真正值得记的不是那行 CSS，而是 **反向验证告诉我"其中一条断言根本咬不动"**（见 §四）。

## 一、这一批改了什么

用户口径（2026-09-25）：

> **「我希望工具条直接覆盖在标题上，遮住也没关系」**

对应两个文件的改动 + 两条新判据：

| 改动 | 位置 |
|---|---|
| `.page-title` 的 `max-width`：`calc(50% - 116px)` → **`calc(100% - 32px)`** | `frontend/src/styles/posts.css` |
| 新字段 `pageTitle.zIndex` / `glow.toolbarZoneZ` / `glow.viewBodyZ` / `glow.panelRect` | `frontend/src/dev/probe.ts` |
| 新判据 ⑤c 两条（不出面板 / 条压标题） | `scripts/ui_probe.py` |

**触发它的是我上一轮问的一个问题**：标题的 `max-width: calc(50% - 116px)` 里
**写死了工具条半宽 88** ⇒ 加第 5 个视图钮就会让标题钻到工具条底下，而**没有任何判据拦它**。
我提议加一条"标题不得与工具条相交"的断言 —— 用户没有接受那个方向，而是**把前提取消了**：
不要拦相交，**相交本来就是允许的**。

> **这一句话改的是"需求"本身，不是"判据"** —— 它把 R45-B/E 那条
> 「标题要给工具条让路」整条前提**作废**了。判据跟着意图走：该退役的退役（§三），
> 该新立的新立（§三），而不是想办法保住旧的那条。

## 二、为什么删掉那个数不是"简化"，而是修一个假守卫

`116 = 88`（工具条半宽）`+ 16`（`left`）`+ 12`（安全距）。它的问题不是"不好看"，是：

1. **88 是工具条的半宽** —— 条宽**由内容决定**（`posts.css` 里明写"宽度不写死"，
   因为按钮尺寸/间距改过）。加一个视图钮、把 `gap: 8px` 调成 10、按钮 34 → 36，
   **这个数就错了**；
2. 它错了的样子是"标题被工具条压住"—— 而**这正是现在允许的事**（旧口径下也是允许的：
   压住只是难看，不影响功能）⇒ **看不出坏了**；
3. 更关键：**它从来没有任何东西在守**。上一轮我查过 `_assert_glow` ⑤ / ⑤b，
   两条判的量分别是"标题在不在、占不占流"和"内容留白"，**横向一个字节都没量**。
   那 116 只是一行 CSS 加一段注释 —— 注释里那句"少减这 28px 就会在窄档压上工具条"
   **是推导，不是判据**。

⇒ 删掉它，同时把"它本来想守的那件事"换成**真的能红**的两条（§三）。
**判据从 0 条变 2 条** —— 这才是本批的实际收益。

## 三、判据：⑤c 两条（并退役一条早就该退的）

### 3.1 新增

| 判据 | 量什么 | 为什么 |
|---|---|---|
| **不出面板** | `pageTitle.rect` 右缘 ≤ `glow.panelRect` 内缘 − 16 | 允许被盖，**不许出界**（`max-width` 写错 / 有人改成 `none` + 显式宽度） |
| **条压标题** | `glow.viewBodyZ < glow.toolbarZoneZ` | "遮住也没关系"**以"条在上"为前提**才成立；反过来（标题浮在条上）比被遮住难看得多 |

**"是否重叠"不判**：现有四个标签都只有 4 个字（20px 字号 ≈ 80px），1100 档也够不着条左缘
（`50% − 88`），判它等于判一个今天恒为假的条件。

### 3.2 层叠的**真正机制**不在标题身上（这条差点写错）

第一版判据我写的是"标题 `z-index` < 工具条 `z-index`"，探针去读 `.glow-bar` 的
`z-index` —— **读到 `auto`**（`z-index: 3` 写在它的**父级** `.view-toolbar` 上）⇒ 8 帧全红、
报"读不到 z-index"。**字段名是对的，元素选错了** —— 与 DEV-LOOP §6.6 那类尺子坑同源。

改正之后才看清**机制是怎么起作用的**：

```
.view-toolbar { z-index: 3 }        ← 条所在的层叠区
.view-body    { z-index: 1 }        ← 标题的**包含块**，非 auto ⇒ 自成层叠上下文
  └ .page-title { z-index: 2 }      ← 只是**它内部**的层级
```

⇒ 标题的 `z-index` **爬不出** `.view-body`。也就是说**就算有人把 `.page-title` 的
`z-index` 改成 9999，工具条照样盖着它**；唯一能破坏这条口径的是动
`.view-body` / `.view-toolbar` 的 `z-index`。判据因此改成主判
`viewBodyZ < toolbarZoneZ`（机制），标题自己那个只作补充（拦"标题被移出 `.view-body`"）。

> **可提炼**：判"谁盖住谁"时要找**层叠上下文的那一层**，不是你以为的那个元素。
> 一个元素能不能压过另一个，取决于**各自所属的层叠上下文**，不是各自 `z-index` 的大小。

### 3.3 退役

`_assert_glow` ⑤ 的判据表里还挂着一条「archive：导航标题 == 卡片内渲染的标题（两份真源）」
—— 它在 R45-E2 就已经**退役**了（用户把标题改成写死的「数据卡片」，卡片自己渲染「直播日历」，
"必须相等"的前提消失），代码里删掉了，但 **`docs/UI-MAP.md` 的判据表还列着它**。
本批顺手删掉：**文档里列着一条不存在的判据**，与"留一条必红的假判据"是同一类问题的两面 ——
都是让人以为这块有守卫。

## 四、⚠️ 反向验证暴露的：**其中一条断言咬不动**

按 §6.4 的纪律，两条新判据都要能人为破坏到红。第二条（层叠）一次就红了（改
`.view-body { z-index: 5 }` ⇒ 8 帧红）。**第一条改不动**：

| 破坏手法 | 期望 | 实测 |
|---|---|---|
| `max-width: none`（长标题） | 红 | ❌ **照样绿** |
| `max-width: none` + `width: 200%` | 红 | ✅ 红：`右缘 1626 越过面板内缘 1060（面板 542..1076）` |

原因：绝对定位元素没写 `width` 时是 **shrink-to-fit**，可用宽 = 包含块宽 − `left`
⇒ **`max-width` 再大，盒子也越不出包含块**。那条 `max-width` 买到的其实只是右边那 16px 余量，
"不出面板"是**shrink-to-fit 白送的**。

**这条经验比本批的代码值钱**（已写进 `docs/DEV-LOOP.md` §6.4 的新段）：

- **反向验证要挑"真的能破坏它的那个改法"**：改不动就用更极端的手段（显式尺寸 / 负偏移 /
  直接改被测元素）**直到它红 —— 红不了就说明这条断言是装饰**；
- 找不到任何能破坏它的改法时，**这条断言现在没有牙齿**（哪怕将来可能有用）——
  要么改成能咬的，要么在注释里写明"它守的是哪一类改动"。

> 也就是说：**"加了一条判据"与"多了一层守卫"不是一回事**。
> 只有反向验证能把这两者分开 —— 而这一步**不能靠读代码完成**。

## 五、实测：长标题到底长什么样（我自己截图看了）

用户说"遮住也没关系"，但**"遮住"和"切断"不是一回事**。为了看清是哪一种，
我临时把 list 的标题换成一句 26 字的长文案，在 1100 档（最窄）截图
（`python scripts/ui_probe.py --shot-toolbar --width 1100 --vtuber 15`）：

> 截图：`_ui_probe_tmp/r45-list-1100.png`

实际效果是**被切成两段**（不是整段被盖住）：

```
帖子列表 · 临时长标 [ 工具条 ] 住标题时的观感
```

因为条只有 176px 宽且居中，标题**从条的两侧都露出来**。三个前提一起决定了它的后果有限：

1. 条是**不透明白卡**（`--pill-bg: #ffffff`）⇒ 压住的那一段是**真没了**，不会透出半截字；
2. 条**自动隐藏**（R45-A）⇒ 条隐去后整句自己就露出来了；
3. **今天的标签只有 4 个字**，够不着条左缘 —— 也就是说这个观感**当前不可达**。

⇒ 按用户口径**保持现状**（允许覆盖，不额外处理）。若以后出现长标签，再决定是
"到条左缘截断 + 省略号"还是"给条加一层遮罩渐隐" —— 两个都要动 `.page-title` 的
横向算式，现在做属于给一个不可达的状态写代码。

**用户拿到那张截图后的回复：「保持现状，不动」**（2026-09-25）。⇒ 这条**已知且已接受**，
写进 `docs/UI-MAP.md` B1.0.1 并注明"别把它当 bug 修；要改先问用户" ——
否则下一次有人看到长标题的截图，会当成新问题再修一遍。

**诊断用的长标题已撤回**（`git diff` 对 `PostsPage.tsx` 为空）。
