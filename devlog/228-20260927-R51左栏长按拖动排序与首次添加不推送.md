# 228-20260927-R51左栏长按拖动排序与首次添加不推送

用户口径（2026-09-27，两条）：

1. 「增加新功能：**长按鼠标左键可以拖动主播进行排序**」；
2. 「修改弹窗通知逻辑：**首次添加账号抓取数据时不进行弹窗推送**」。

## 一、左栏长按拖动排序

### 顺序必须落库（这是本轮的主要决定）

左栏原来的"默认顺序"其实就是**数据库返回顺序**（等价 id 序），而前端没有 localStorage
约定（P8-B 平台徽章那条纪律：用户手改的顺序一律落库，否则刷新/重装就回到原样）。
所以照 `accounts.sort_order`（f002）的先例给 `vtubers` 加一列：

| 层 | 改动 |
|---|---|
| 模型 | `vtubers.sort_order`（Integer NOT NULL DEFAULT 0，**迁移 f008**） |
| 仓库 | `VTuberRepo.all()` 按 `(sort_order, id)` 升序；新增 `reorder(ids)` |
| 接口 | `PUT /vtuber/order`（提交整串新顺序；未列出的排在其后） |
| 前端 | 左栏 `VtuberSidebar` 长按 350ms → 拖动 → 松手提交一次 |

默认 0 ⇒ 没排过的仍按 id 序，**老数据行为不变**（与 f002 同款）。

### 交互照 P8-B 平台徽章的既有手法

- **350ms 长按**才进入拖动（普通点击仍然是"进这个主播"）；
- 拖动期间用 `document.elementFromPoint().closest('[data-vtuber-idx]')` 反查指针落在第几行，
  行随拖动**实时重排**（列表按本地 `order` 渲染，不重拉服务端）；
- **松手才提交一次**：边拖边发请求会被服务端顺序刷回去（手指还按着就跳回原处）；
- 失败回退服务端顺序 + toast 报错（与徽章同款）；
- 拖动期间禁掉文本选中、悬停高亮让位、被拖的行抬高（`box-shadow` + 1.02 放大）；
- 刚拖完的那一下 click **不进入主播**（`dragMoved` 抑制）—— 从"排序"变成"误进直播间"是这类
  交互最常见的误伤。

### 筛选开着也能拖

`utils/reorder.applyVisibleOrder`：只重排"看得见的那几个"，**被筛掉的条目留在原来的槽位**
（而不是整体沉底）。纯函数 + 单测（`utils/reorder.test.ts`，含"长度对不上就原样返回"——
宁可这次不生效，也不按错位的 id 写库）。索引下标越界/原地不动也都有用例。

⚠️ 只有「默认」排序能拖：粉丝数 / 名称是**算出来的**顺序，手排对它们没有意义。

## 二、首次添加账号不再推送

原来的闸门只有"抓取前这个账号有没有帖子"（`count == 0` 就不通知）。它挡不住这一种：
**收录首屏只收前 N 条**（`FIRST_SCREEN_DYNAMICS_LIMIT`，默认 3），随后例行轮询会
**往回补更老的内容** —— 它们入库晚、id 更大，于是被当成"新动态"推送
（用户实测：刚加完账号就收到"X 更新了动态"）。

修法：在 id 水位之外再加一道**发布时间水位** —— 只对"比抓取前已有的最新一条还新"的帖子开口：

```python
rows = db.query(Post).filter(
    Post.id > mark,                       # 这一轮入库的
    Post.published_at.isnot(None),
    Post.published_at > newest_before,    # 且比已有的最新一条更新
).order_by(Post.id.asc())...
```

两道闸门的分工：`count == 0`（一次都没抓过）直接不通知；`newest_before is None`
（库里一条都没有发布时间）也不通知。**没有发布时间的一律不算新帖** —— 宁可不弹，
也不要把回填的老内容当"更新"打扰用户。

| 用例 | 钉什么 |

## 四、顺带修：一批"假红"的根因（测试隔离）

本批跑测试时撞见一次**顺序相关**的假红：把 `tests/test_services.py` 放在
`tests/test_runtime_settings.py` **前面**跑（非字母序），后者有 5 条断言读到默认值而红；
按仓库惯用的全量顺序（字母序）跑却是全绿。

根因是**运行时设置的进程级状态没被全局隔离**：

1. 覆盖层（`runtime_settings._overrides`）原来只在 `test_runtime_settings.py` 的
   **文件内**夹具里清 —— 别的文件的用例写进去就留给后面；
2. 更隐蔽的是**实例属性**：`monkeypatch.setattr(settings, "DYNAMICS_BUDGET_RPM", 2)` 的撤销
   是"有旧值就 `setattr` 回去"，而 SPECS 键**永远有旧值**（类属性）⇒ 撤销后
   `settings.__dict__` 里留下一条**优先于覆盖层**的实例属性，之后任何 `rs.apply()`
   都改不动这个键（仓库里有 6+ 个用例文件是这么改设置的）。

**修法**：把清理提到 `tests/conftest.py` 做成全局 autouse 夹具
（`_isolate_runtime_settings`），每个用例前后都 `rs.clear()` **并**抹掉 SPECS 键的实例属性；
同时删掉 `test_runtime_settings.py` 里那份文件内夹具（避免两处口径）。

验证：故意打乱文件顺序跑 6 个文件 → **273 passed**；全量 → 绿。

> 顺带记一条判读经验：「红」有三种 —— 真红（产品坏了）、**假红·环境**（本机缺网络/凭据、
> 版本漂移）、**假红·顺序**（本例）。只有第一种要改代码；后两种要么换环境跑，
> 要么像这次一样把隔离补上。反过来还有"假绿"（该红却悄悄通过），所以本仓宁可
> 让用例**响亮地失败**，也不写"断言没抛异常"这种空判据。

## 五、没做的

- 左栏**拖到手感层面**的自动化断言只有纯函数那几条（真实指针拖拽要真浏览器 + 长按计时，
  探针在虚拟时间下量不准 350ms 这个阈值）—— 真机确认过，不假装有机器判据；
- 顺序目前是**全局一份**（所有人共用一个 `sort_order`），没有"按筛选分组各存一份"的概念。
