## 一、小体量 UP 加不进去：B 站新 mid 是 **16 位**，我们卡在 12 位

用户报的样本：条目名 `bili_7963188677`、真实 mid `3537112928356578`。真机直查之后真相很清楚：

```
uid=3537112928356578（16 位）→ error=None  name=bili_7963188677  followers=1010  avatar=…
uid=7963188677（10 位）      → B 站 -404「啥都木有」
```

即 `bili_7963188677` **不是**第三方占位名（我一开始这么猜过），而是那位 UP 的**真实昵称**；
能收录 TA 的唯一路径就是那把 16 位 mid，而它被两道关卡挡着：

| 关卡 | 位置 | 原判据 | 后果 |
|---|---|---|---|
| 后端分流 | `bili_search.looks_like_uid` | `isdigit() and 5 ≤ len ≤ 12` | `bad_uid` ⇒ `/vtuber/adopt` 归到 **404「B 站查不到这个 UID」**（提示完全指错方向） |
| 前端分流 | `addVtuberSearch.inputLooksLikeUid` | `^\d{5,12}$` | 16 位被当**关键词**搜，而 B 站搜索接口搜不到 uid ⇒ 界面显示"搜不到这个人" |

**规模**：用户库里第三方索引 `thirdparty_vtubers` 共 9141 条，其中 **2206 条（24%）** 的
`platform_uid` 是 16 位 ⇒ 这条 bug 之前把约四分之一候选挡在门外。

修：两侧上界放宽到 **20**（下界 5 不变；20 位只作"显然不是 mid"的护栏），文案改「5~20 位数字」，
两侧各加 16 位回归 + 21 位仍拒。**真机验**：`exact_user('3537112928356578')` 返回真实姓名/粉丝数/头像 ✓。

## 二、切 V 时背景闪白：背景层被 `key` 强制重挂，中间没有东西兜底

`PostsPage.tsx` 原先是单层 + `key={backdropSrc}`：换 V 时 React **卸载旧层、挂载新层**，
新层再从 `opacity: 0` 淡入（`animation: backdrop-in`）⇒ 那一帧底下只剩面板底色（用户看到的
「100% → 0 → 100%」）。

修：新增 `components/common/BackdropCrossfade.tsx` —— **双层交叉淡入**：

1. 新图先 `new Image()` **预加载**，`onload` 之后才交换（否则网图慢时会出现"旧的没了、新的没来"）；
2. 交换后**新层在下、旧层在上淡出**（`.is-prev` 的 `backdrop-out`）⇒ 任何一帧都至少有一层不透明；
3. **预加载失败就什么都不做**（宁可显示旧图，也不闪一下白）；
4. 首层不做淡入（面板本来就没有背景可交叉）；
5. CSS 侧把不透明度收敛成**单一真源** `--backdrop-opacity`（`is-prev` 的关键帧读它）——
   写死两份的症状是自定义背景（1）淡出时**先跳到 0.18 再淡出**，一次肉眼可见的变暗。

判据 8 条（jsdom 里用可控 `Image` 桩，专测"**加载完成前绝不动旧层**"这条时序）+ 一条
CSS↔常量同值的契约用例；**反向验证**：CSS 时长改 400ms ⇒ 判据红（`expected 400 to be 250`）。

## 三、通知「已读」让位时机：口径反转（先滑出 60–80%，下面再顶上来）

旧口径（2026-10-05，写在 `StatusIsland.tsx` 注释里）：退场那条**当拍**浮起来让位，
「下面那条**同时**往上顶」；用户 2026-10-06 改成「**滑出 60%–80% 之后**再顶上来」。

- 状态机从三态变四态：`queued → sliding（在流内播滑出动画，**仍占位**）→ leaving（浮起让位）→ 移除`；
- `EXIT_YIELD_AT = 0.65`（≈143ms）是让位点；**移除仍是放行后 220ms**（总时长不变，只是把"腾位置"往后挪）；
- 每条**各自一个让位表**（与移除表一样，共享表会被 70ms 的逐条放行反复重排）；
- 几何**在让位那一拍才冻**（它在流内多待 143ms，期间可能被上面让位的行顶上去；放行就冻会偏一整行）；
- ⚠️ 让位时 `.is-out` **只做定位、绝不带 `animation`**：动画挂在 `.is-sliding` 上、两个类同时在场，
  动画计算值一个字节都不变 ⇒ 不会重播（否则从 sliding 切 leaving 时动画从头播 = 那条往回跳一下）；
- ⚠️ 退场动画改走**独立变换属性 `translate`**（不再用 `transform`）：CSS 里 `translate` 与 `transform`
  是**合成**关系 ⇒ `transform` 空出来给 FLIP，"正在滑出的那条"**同时**还能被平滑补位。
  若动画也动 `transform`，它在层叠里压过内联样式 ⇒ FLIP 写了也被吃掉、那条当场跳一行。

判据：`StatusIsland.test.tsx` 新增「让位时机」（+80ms 下面那条 **offsetTop 不动** / +160ms 才上移）
与「滑出中的那条也要被补位」，另有两条**读真 CSS** 的结构判据（主动画只能在 `.is-sliding`、
`.is-out` 不许含 animation、keyframes 必须动 `translate`）；探针 `--notice-lab` 改成
+80ms/+200ms 双采样并新增"下面那条到底判没判"的 `ackBelowJudge`（**空过必须看得见**）。
**反向验证两处**：`EXIT_YIELD_AT → 0` ⇒ 新用例红；把 `animation` 塞回 `.is-out` ⇒ CSS 结构判据红。

## 四、下一批（B2）：播放器卡顿 = **只在全屏**

用户的复现口径把范围收窄到：**B 站本身不卡 · 应用内不全屏不卡 · 小窗不卡 · 全屏卡**，
且显示器是 240Hz。日志读数（`logs/app.log` 的 `[video]` 行）证明**取数与解码都不是瓶颈**：
渐进式那次 `最低缓冲=136.3s · 停顿次数=0 · 后段=30.0fps`（= 该 30fps 源的原生帧率）。

⇒ 嫌疑落在**全屏时的合成成本**，已在 CSS 里找到两个"只在全屏变贵"的机制：
`.vp { border-radius: 8px; overflow: hidden }` 在 `:fullscreen` 里**没复位**（圆角/裁剪会阻止视频
提升到硬件覆盖层），以及空闲控件只用 `opacity: 0` 藏而它们带 `backdrop-filter: blur(4px)`
（压在视频上的玻璃片同样会把视频踢出覆盖层）。修法与验证方式见用户会话，下一批落地。
