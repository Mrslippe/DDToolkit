## 一、这台机器守的是什么

一条贯穿全页的不变量：**账号的身份是 `platform:platform_uid`，不是对象引用**。

| 事实 | 为什么 |
|---|---|
| `accountKey` 是**稳定代理**，所有"按账号"的 effect 依赖它 | `fetch-idle` 回填换的是**新对象**（新快照）而 key 不变 ⇒ 统计/帖子/筛选重置那些 effect 不该重跑 |
| 所以「增量快照」未命中时**必须原样返回旧引用**（`Object.is` 级） | 否则每次广播都让依赖 `accountKey` 的 effect 白跑一轮 |
| 而「抓取回填」**要**换新对象 | 头部直接读 `selectedAccount`，保留旧引用就一直显示抓取前的空快照（2026-09-05 实修） |

两条方向相反、都对的规则，现在住在同一个文件里 —— 这正是它值得成一台机器的理由。

### ⚠️ 反向验证暴露了**判据自己的漏洞**（这刀最值钱的一条）

五刀全红之前，**第一版"同 uid 换新对象"是空转的**：我把命中项放在了列表**首位**，
于是"永远取第一个"这种坏实现也能通过 —— 刀 A（`return list[0]`）**跑出了 11 passed**。
修法：命中项挪到**第二位**，并加一条 `expect(attr('uid'), '要按 uid 认人，不是永远取第一个')`；
`reconcileById` 那条同款（补刀 E 验证）。修完五刀各自精确报红：

| 刀 | 改法 | 期望红的用例 |
|---|---|---|
| A | E7 对账永远取第一个 | 同 uid 换新对象 |
| B | 增量未命中时也换新对象（引用抖动） | 未命中 ⇒ 引用不变 |
| C | 把两条口径"统一"（设置保存也没选过就选） | 没选过 ⇒ 保持不选 |
| D | `accountKey` 只取平台（丢 uid） | key 派生 |
| E | 设置保存对账永远取第一个 | 同 id 换新对象 |

**教训（与上一刀互补）**：上一刀是"我的**预判**错了"，这一刀是"我的**判据**本身
区分不出好坏实现"。**反向验证不是走形式 —— 它两次都捞到了真东西。**
