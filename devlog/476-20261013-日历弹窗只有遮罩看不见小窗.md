# 476-20261013 日历弹窗「只有灰色遮罩、看不见小窗」：一行 CSS 造出两个 bug

> 用户先后报了两件看似无关的事：
> 「点击日期格之后有灰色遮罩但是没看见小窗」和「新建预约弹窗把页面挤上去了」。
> **它们是同一个根因**，而且是这一批我自己引进的。前四轮的诊断**全错**，本文记结论与错法。

## 一、真根因（`.lc-ms` 写了 `position: relative`）

面板的 `position: fixed` 来自 `DialogContent` 的基础类（Tailwind 的 `.fixed`），
而 `posts.css` 是**无层级**样式、Tailwind v4 的 utilities 在 `@layer utilities` 里 ——
层叠顺序是**层级先于特异性**（无层级胜分层级）⇒ `.lc-ms{position:relative}` **压掉了** `fixed`。

于是面板根本不是浮层，而是 Radix portal div 里**普通流**的一块；那个 div 排在
`#root{height:100%}`（= 满视口高）**之后** ⇒ 面板整块落在**首屏下方**，于是：

| 用户看到 | 量到的 |
|---|---|
| 有灰色遮罩、没有小窗 | 面板 `412×335 @(332,772)`，而视口只有 **621** 高 |
| 弹窗把页面挤上去了 | 面板在视口外 ⇒ Chrome 为把聚焦的日期框滚进视口，**把 body 滚了 486px**（`body.scrollTop 0→486`、卡片上缘 `100 → -386`） |

对照：`.lc-dlg`（场次详情窗）**一个字都没写 `position`**，所以它一直是好的 ——
用户那句「不能让这个窗口和正常的直播场次详情窗口的层级一样吗」正是这个意思。

**修法**：删掉那一行（`posts.css` 里 `.lc-ms` 现在有完整成因注释），并补两条护栏 ——
vitest 的 CSS 契约（`.lc-ms` 不许声明 `position`；`DialogContent` 基础类里必须有 `fixed`）
＋探针判据（面板必须 `fixed`、在视口内、终态不透明度 ≥0.99、`body.scrollTop` 必须为 0）。

## 二、顺手删掉三套补丁（病根没了，它们就是负担）

诊断期间我在 `dialogScroll.ts` 攒了三套"滚了之后想办法"：钉 `body.scrollTop=0`、
给 body 上 `position: fixed`、`freezeBodyScroll`（body-scroll-lock）。前两套还会把面板
推到 `y=761` —— 也就是**亲手造出**用户报的第①条。修完 CSS 后整套删除，
**重跑探针确认判据仍绿**（`body 0→0`、卡片上缘不变、面板 `fixed` 且居中）：
那不是"顺手清理"，是"证明它本来就不需要"。保留的只有 `noScrollAutoFocus`
（`preventScroll: true`，防窄窗下聚焦把内层 `.os-scroll` 滚一下）。

## 三、前四轮为什么全错（每一轮的尺子都只量了一半）

| 轮次 | 我的结论 | 错在哪 |
|---|---|---|
| 1 | 「页面被滚了」（`body.scrollTop=486`） | 症状不是病因：486 是**结果**，因为面板在视口外 |
| 2 | 钉回 `scrollTop` / 给 body `position:fixed` | 治症状，且第一版直接把面板推出视口 |
| 3 | 「遮罩容器比视口高 486px」 | 量到的是**被滚之后**的遮罩盒；`doc 621/621` 根本没超屏 |
| 4 | 「量到了预约窗的残留节点」 | 那是**探针点错了格子**（见下），不是产品 |

两条元教训（已提炼进 `docs/frontend/PROBE.md` §6.27）：

1. **只量"它在哪儿"不够，要量"它凭什么在那儿"** —— 前四轮全在量 `y/scrollTop/盒高`，
   直到把 `position`、父链、`data-state` 一起打出来，答案一行就出来了。
2. **判据可能量错对象**：探针的"未来空格"是按**第一个空格**找的，而本月第一个空格在
   **过去** ⇒ 两段（预约窗/记录窗）点的其实是**同一格**、量的是**同一个窗**
   （归档读数里两处 `isReservation=false`、标题都是「手动记录一场直播」两处都写着）。
   分岔口径必须与产品逐字一致（`LiveCalendar.onCellClick` 的 `c.key < todayKey`）。

⚠️ 另外，`opacity` 的原始读数**恒为 0** 是**尺子**不是产品：虚拟时间下入场动画冻在
`from` 帧。判据只认 `finish()` 之后的 `opacitySettled`。

## 四、反向验证（判据真的会红）+ 一件没解释的事

把 `position: relative` 加回去再跑 `--archive`：两段各报三条（卡片上缘被挤动 / 面板不是
`fixed` / `body.scrollTop` 非 0），报的正是**开着的那一个**窗 —— 判据有牙。
这一步还顺手抓出我自己的第二个判据 bug：`.lc-ms` 是两个窗共用的类名，而 Radix 的 Presence
要 `animationend` 才卸载、虚拟时间下退场动画不跑完 ⇒ **上一个窗的尸首留在 DOM 里**，
`querySelector('.lc-ms')` 拿到它（`data-state=closed`、终态 opacity 0），判据却报成
"这个窗看不见"。⇒ 取节点只认 `data-state='open'`、身份查询按**挑中的节点**算、
关窗时**分几拍 `finish()`** 把尸首送走（进 `PROBE.md` §6.27）。

⚠️ **一件没解释的事**：第一次 C 档门禁红在 `ui_probe`（默认三档那一步），而我**没留原文**
（管道只截了尾部）。之后同一步连跑 5 次全绿，也复现不出"`--shot-resv` 留下的
`_ui_probe_tmp/` 污染"那条猜测。教训是机械的：**门禁输出要落盘**（`gate.py ... | Tee-Object`），
否则一次不明红就只剩"再跑一次看看"。另外多步门禁共用 `_ui_probe_tmp/`，**后面那步成功会把
前面那步的现场删掉** —— 这也是那次证据丢失的直接原因。
