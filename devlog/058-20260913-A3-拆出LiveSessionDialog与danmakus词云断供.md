## 一、拆出 `components/live/LiveSessionDialog.tsx`

### 搬什么

`renderDetail()` 整块（直播信息 / 分类校正下拉 / 弹幕信息 + 词云 / 直播动态 / 内容分析预留），
外加**三块只服务于该弹窗的状态**：`cloudBubbles`（top40 派生）、`cloudPopped`（破泡计数）、
`cloudRestoreTick`（恢复信号）。它们原来住在 `LiveCalendar` 顶层 —— 于是"弹窗的局部状态"
与"日历的状态"混在同一作用域。搬进组件后父级少 3 个 hook 与一个 267 行函数。

`LiveCalendar.tsx` **734 → 465**（−269）；新增 `LiveSessionDialog.tsx` 340。

### 行为保持的要点

- **portal target 仍是 `document.body`**（层级/z-index 语义不变）；
- **状态重置时机等效**：`cloudPopped` 原来不随 `detail` 重置，现在随本组件挂载初始化 ——
  而本组件**仅在 `detail` 非空时渲染**，即"每次打开弹窗"= 一次挂载 ⇒ 打开时归零。
  这正是原行为的等效表达（原实现里关掉再打开，`MosaicCloud` 重建后旧计数本来也失去意义）。
- **DOM 结构逐字保留**（`.lc-dlg*` 类名一个没动）——探针直接查这些选择器；
- CSS 归属仍为 `styles/posts.css`（A 路线决策 (a)：拆分不搬 CSS）。

`tsc` 顺带抓出 7 个因此变成未使用的导入（`ChevronDown`/`X`/`LiveSessionDetail`/`ProxyImage`/
`MosaicCloud`/`isFreshSession`/`CloudWord`）——正是"拆巨件"最容易留下的垃圾，已全部清掉。

### 新增 `--archive-day`（探针能力）

`--archive` 固定点"最近一个**有场次**的格子"。但最近一场常常刚下播、danmakus 还没收录
（`danmaku: null`）⇒ **弹幕/词云那两段等于没验**却仍然退出 0。
新增 `--archive-day <N>` 可点指定日号的格子，回到几天前有收录的场次。
（这条同时兑现了 055 记下的探针待办①的一个变体。）

## 三、⚠️ 意外发现：danmakus 的词云数据已经断供（功能静默失效）

> ## ⚠️ 本节结论已被 devlog/061 推翻
>
> **不存在断供**：`/api/v2/live` 仍返回 100 个热词（12/12 场复核）。
> 本文的"`extra` 缺失"来自探查脚本**读错嵌套层级**（响应是双层信封 `data.data.live`）。
> 当时观察到的 `词云格: 0` 也是**探针时序**问题（弹幕区异步填充，3s 采样窗口可能太早），
> **不是词云坏了**。详见 061 §〇。**本节以下内容请勿引用。**

排查"为什么详情弹窗 `词云格: 0`"时，逐层验证后确认这**不是**前端或本次重构的问题：

### 证据链

1. **直打上游**（公开免鉴权端点）：`GET /api/v2/live?liveId=<uuid>&includeExtra=true`
   —— 对库内 **2021-10 → 2026-09 的 24 个场次**（含弹幕数 5k~72k 的场次）全部返回
   `code=200` 但 **`extra = {}`（空对象）**，`wordCloud` 词数恒为 0。
2. **对照 devlog/052 的实测记录**：文档明确写着同一个场次
   `c99fb5a9-e266-4e15-8f3c-437e8a5a0969` 在 2026-09-10 实测是
   「`uuid → ✅ total=31767 / 40 热词`」。今天重测同一 uuid：`extra 键= [] 热词数= 0`。
   ⇒ **同一个接口、同一个场次，10 天前有热词、现在没有**，是上游行为变化。
3. 后端解析逻辑没变（`_parse_live_summary` 仍从 `extra.wordCloud` 取），
   所以前端必然拿到空 `top_words` → 渲染「暂无热词数据」占位。

### 影响与判断

- **用户可见影响**：场次详情弹窗的「弹幕信息」区只剩弹幕总量，「热词词云」整块消失
  （显示"暂无热词数据"）。**弹幕总量仍正常**，所以功能看起来"还在"，只是少了词云 ——
  属**静默降级**，不报错。
- **不是本地缺陷**：所有缓存/解析/渲染路径逐一排除；`raw_json` 与库内数据完好。
- **可能原因**（无法从本地确认）：上游改为需登录才有 `extra`（024 记录的
  `DANMAKUS_TOKEN` 配置位）、或该字段被下线/迁移到 v3。
  **建议后续动作**：① 试 `DANMAKUS_TOKEN` 是否恢复 `extra`；② 探 `/api/v3/lives/{liveId}`
  是否仍带热词；③ 若确实下线，则把「词云」从"功能"降级为"上游可用时展示"，
  并在 UI 上区分「上游未提供」与「本场确实没有热词」。

> 这件事与 devlog/003「上游延迟与本地缺陷要在 UI 上分开」是同一类教训的延伸：
> 当时是**延迟**，这次是**断供**。文案说「暂无热词数据」，用户无法分辨
> 是我们坏了还是上游没了。

## 五、经验

- **"看起来通过"的断言比"失败"更危险**：`--archive` 打出 `词云格: 0` 并退出 0，
  而 0 既可以是"上游没数据"，也可以是"组件没渲染" —— 两者在退出码上无法区分。
  本批能定性，是因为**去直打了上游并拿 devlog/052 的旧实测做了对照**；
  否则很容易把上游断供误判成自己重构搬坏了（或反过来，把搬坏了当成上游问题）。
- **验证要追到"数据源头"再收工**：`词云格 0` 这个数字本身没有信息量，
  有价值的是"上游有没有给我们数据"这一层。以后遇到"某块内容为空"，
  先分层确认（上游 → 本地库 → 接口 → 渲染），再决定是不是自己的问题。
- **拆巨件后必看未使用导入**：7 个垃圾导入是 `tsc` 抓的，不是人眼 ——
  这也是"只搬不改"里最容易顺手留下痕迹的地方。
