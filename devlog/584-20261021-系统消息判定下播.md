# 584-20261021-系统消息（直播中止/录制结束）作为下播依据

用户指出：弹幕流里其实带着「直播中止 / 录制结束」这类系统消息（`uId = -1`，type 7/8/11/12），
但**不是每场都有** —— 没有时要能回退到原逻辑。

## 改动

1. `aggregate` 收集 `sys_events`（只留 `type` + 时间戳，最多 200 条），写进 `stats`；
2. 新增 `fan/sysmsg.py::apply_sys_end`：**有就用，没有就不动**；
3. 采集链路的顺序改为：回放裁剪 → 率降裁尾 → **系统消息收口**。

## 保守规则（三条同时满足才采纳）

- 系统消息出现在**最后一条弹幕之后**；
- 与最后一条弹幕的间隔 ≤ **2 小时**（防止把隔天的消息当成本场下播）；
- 只允许把 `end_at` **变短**。

不满足任何一条 ⇒ 完全退回率降/平台时间的结论，行为与之前一致。

## 为什么它比 stopDate 硬

`stopDate` 会偏长（实测有场报 12.9h、实际 6h），而「直播中止」是**平台在直播结束时推的事件**，
时刻天然准确。所以顺序是：系统消息 > 率降 > 平台 stopDate > 弹幕跨度。

## 用例

`test_sys_end_prefers_system_message`：有消息时收口、无消息时不动、间隔 >2h 不采纳。

## 遗留

- 历史数据没有 `sys_events`（字段是这次才加的），需要重采才有；
- 四种类型（7/8/11/12）的确切语义没有逐一验证，当前规则只取"最后一条、且在弹幕之后"，
  不依赖类型区分 —— 这样即使语义猜错也不会误判。
