# 064-20260913-上游取数可取消（切场次/关弹窗即 abort）

> 承接 devlog/063 的遗留项（记在 `docs/TODO.md` §1.1）。改动很小，但补上了
> "把上游取数拆成独立请求"之后**欠缺的那一半**：既然它慢（最坏 90 多秒），
> 就得能在用户不要它的时候停下来。
> 无迁移；无接口变更（前端内部管道）。

---

## 一、问题

devlog/063 把上游取数拆出来后，`useLiveUpstream` 仍**只做了防回写**（`seq`：
旧响应不许覆盖新场次），没有取消在途请求。后果：

- 用户在 A 场点了「重试」、又切到 B 场 —— A 那一发还在跑，最坏 90 多秒；
- 关掉弹窗后那一发照样跑完（拿到的东西**没有任何人会用**）；
- 上游本来就会间歇性变慢、还有平台预算这回事，让"没人要的请求"继续占着并不划算。

（`seq` 确实挡住了"错误数据写回"，所以这**不是数据正确性问题**，是浪费与体感问题：
切回来时那两格会先是"加载中"，随后被**旧场次**的响应点亮成"已完成"。）

---

## 二、改法：三行管道 + 一处语义

| 位置 | 改动 |
|---|---|
| `api.liveSessionUpstream(accountId, liveId, signal?)` | 把 `signal` 交给 `request()` 既有的 `init.signal`（**`request()` 本来就吃 `RequestInit`，不需要改签名**）；不传时不构造 `init`，其余调用方行为不变 |
| `useLiveUpstream` | 每次 `load()` 先 `ctrl.current?.abort()` 掐掉上一发，再 `new AbortController()` 并把 `signal` 传下去；**effect 清理函数里 abort** —— 依赖变化（切场次/切账号）与卸载（关弹窗）都会走到 |
| `catch` 分支 | `AbortError`（或 `signal.aborted`）**直接 return**：不置 `failed`、不写"拉取失败"降级态 |

最后一条是关键：不这么写，切场次时新旧两发的竞态会让**新场次**的界面上闪一下
「弹幕拉取失败（网络或上游不可用）」—— 明明是被我们自己掐掉的。

## 三、验证

新增 `frontend/src/api/api.test.ts`（4 条，vitest 纯 node 环境，不引入组件测试栈）：

```
✓ 把 signal 透传给 fetch（取消才可能生效）        ← 管道契约：中途被吞就静默失效
✓ live_id 仍要 encodeURIComponent
✓ 不传 signal 时不造 init.signal（其余调用方行为不变）
✓ 取消时抛出 AbortError（调用方据此区分"主动取消"与"请求失败"）
```

把 `signal` 透传这件事**值得单独立测**：它失效时不会报错，只会"点了没反应"
（最坏的表现形式）。hook 自身的状态机（abort 后不置 failed）需要组件测试环境，
本仓暂未引入 —— 记在 §四。

**门禁**：`tsc` 0、`eslint --max-warnings 0` 0、`vitest` **93 passed**（89 → 93）、
`npm run build` 通过。

## 四、已知与未做

- **StrictMode 下 dev 会发两次**（React 18 开发态 effect 双调用：第一次立刻被我们 abort）：
  这是预期行为，生产构建只发一次。后端有 10 分钟缓存兜底，第二次通常命中缓存。
  排查时看到"两个 upstream 请求"别误判成泄漏。
- **hook 没有组件级测试**：本仓 vitest 只跑纯函数（`FRONTEND-ARCH` P3 的既定范围），
  要覆盖"abort 后不置 failed"得引入 `@testing-library/react` + jsdom —— 这是独立决策，
  本次没做（用探针 + 真机确认替代）。
- 详情端点（`liveSessionDetail`）**不需要取消**：它已经不过网（devlog/063），
  一次 DB 查询 + 分类推断，0.1s 级。
- 自建词云（`/wordcloud`）**没有取消**：它由用户点按钮触发且只在弹窗内用，
  同样的管道可以照搬（`api.buildLiveSessionWordCloud` 加 `signal`），
  但它最长也就 120s 且用户明确点了才发 —— 留作后继，未记入 §1.1（优先级低于已完成项）。
