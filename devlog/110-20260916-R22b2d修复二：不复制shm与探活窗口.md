# 110-20260916-R22b2d修复二：不复制 -shm，探活窗口不再贴着 busy_timeout

> dev 模式重试的报错（用户 2026-09-16 截图）：`迁移未完成：新目录启动失败：后端 30 秒内没有就绪（已回退到原目录）`
> —— 规划/复制/校验这次全过了（上一批修复生效），卡在"用新目录启动后端"。

## 一、根因（现场坐实）

新目录里 `logs\app.log` 只有两行：

```
[17:54:41] 启动中...
[17:54:41] [perf] lifespan 开始 +76ms
```

新后端**确实启动了，但卡死在 lifespan 的 `_run_migrations()`**，然后我在 30 秒处判超时。

对照新目录里的 sqlite 伴生文件：`vtuber.db` 53MB、`-wal` 1MB、**`-shm` 32KB 也被复制了过去**。

`-shm` 是 SQLite WAL 的**共享内存索引**（锁状态 + WAL 索引），**必须由每个进程自己重建**，
官方明确要求不要复制它。带着源进程留下的锁状态，新进程在打开库时要等锁，而
`database.py` 里设的 `busy_timeout=30000` **恰好也是 30 秒** —— 我的探活超时同样是 30 秒，
于是差几毫秒输掉这场竞态：其实它再等一会儿就能自己恢复。

## 二、修法

| 改动 | 说明 |
|---|---|
| `migrate.rs` 新增 `SKIP_FILES = ["vtuber.db-shm"]` | 复制时**跳过 `-shm`**（`-wal` 仍要复制：里面可能还有没 checkpoint 的写入，丢了就是丢数据；新进程会用 `-wal` 恢复并自建 `-shm`，这是 SQLite 支持的路径） |
| `lib.rs` 探活窗口 30s → **60s** | **不能贴着 `busy_timeout`**：留出恢复时间 |
| `lib.rs` 超时后**杀掉那个没起来的子进程** | 否则它会继续占着库与端口（这次因为端口被回滚进程拿走而自己退了，属于运气） |

## 三、用例（`cargo test` 21 passed / exit 0）

`fake_data_dir` 里加了 `vtuber.db-shm`，并断言：
- 目标目录**没有** `-shm`（回归护栏：这条正是真机死因）；
- `-wal` **在**（512 字节，不能因为怕麻烦就丢最近的写入）；
- 源目录的 `-shm` 与 `vtuber.db` 都**没被动过**（纪律：全程不动旧目录）。
