# 532-20261018-边车还没监听就发请求：网络级重试

用户贴了 dev 窗口里的 `__ddtoolkitAuthDiag()`：
```
base = http://127.0.0.1:8765   tokenLen = 64   hasToken = true
```
这**排掉了三个猜想**，剩下的才是真因。

## 一、逐条排除
| 猜想 | 实测 | 结论 |
|---|---|---|
| 前端走 `/api` 代理（8000） | `base` 已是 `8765` | ❌ 不经过代理 |
| token 没注入 | `hasToken=true tokenLen=64` | ❌ 注入正常 |
| 后端是旧构建、没有新路由 | 无 token 探 `/fan/{v}/profile` → **401**（不是 404） | ❌ 路由是新的 |
| 跨域被挡 | `OPTIONS` 预检 **200**，`allow-origin: *`、`allow-headers: x-ddtoolkit-token` | ❌ CORS 正常 |
## 二、★ 真因：`tauri:dev` 是「先开窗、后起 sidecar」

`request()` 的闸门（`awaitApiReady`）只等 **base 与 token 注入**，**不等后端真的开始监听**。
于是窗口一挂载就发的那批请求会打到"还没 listen 的 8765" ⇒ fetch 抛
`TypeError: Failed to fetch`。

这也解释了它的**间歇性** —— 晚一点才发的请求就正常，看着像"有时能用有时不能"。

## 三、修法：只对**网络层**失败重试

新增 `utils/netRetry.ts`：`withNetRetry()` 在消息命中
`Failed to fetch / NetworkError / Load failed / fetch failed` 时重试，间隔 300/400/500ms
（合计约 1.2s，够 sidecar 起监听）。

**HTTP 错误不重试** —— 那些已经拿到响应，重试只会把"后端明确说了原因"变成"重试三次再报同一个原因"。

工作台四处接上：`fanVtubers` / `fanActivity` / `fanSessions` / `fanRanked`，档案卡的
`fanProfile` 同办。

## 验收

前端 **1562 passed / 133 文件**、lint 0、`tsc` 干净。

⚠️ 回归用例里"取不到预估"那条要等重试跑完（约 1.2s）才断言 —— 这不是放宽，
是**新行为本身**：网络失败要先重试几次才报错。用例注释写明了这一点。
