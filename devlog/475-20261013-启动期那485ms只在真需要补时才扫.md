# 475-20261013 启动期那 485ms：只在"真需要补"时才扫

> 上一批（`devlog/473`）把场次身份的补齐从读路径搬到了启动期，代价是**每次开应用都要
> 全库扫一遍比对**：真机实测 **485ms**（14 账号 / 8,527 行，而 `written=0` ——
> 一次都不写却每次都要付）。用户：「那就改成只在检测到有未补齐的行时才扫」。

## 一、怎么知道"需不需要补"：记号

在 `app_meta` 里给每个账号留一个**已装配**的记号：

```
live_identity_v<IDENTITY_VERSION>:<account_id>   # 值 "1"
```

- **键里带版本号**（`IDENTITY_VERSION`，当前 1）⇒ 改了代表行的选法/类型来源就把版本 +1，
  老账号**自动**重补一次（这是记号唯一的"主动失效"路径，也是它不会骗人的关键）；
- 启动期只处理**没记号**的账号：一次 `GROUP BY account_id` + 一次 `WHERE key IN (…)`
  ⇒ 实测 **0.65–1.17ms**（旧版 485ms）；
- 写点装配完就**补上**记号（`danmakus.sync_account` 收尾 / 手动增删改的回执）。

## 二、⚠️ 真正的风险不是"慢"，是"跳过 ⇒ 永久陈旧"

记号的错法只有一种：**行变了、记号还在** ⇒ 那台机器从此**跳过**这个账号，
症状是按类型统计少算 —— 而两处都不报错。所以本批的重点是**作废点**：

| 行变了？ | 谁作废 | 为什么 |
|---|---|---|
| 同步写了一批（成功） | 装配完补记号（`mark=True` 的默认路径） | 这一批的组当场重算过 |
| **同步装配抛错** | `materialize_account(..., mark=False)` 清记号 | 补不成 ⇒ 下次启动还得来，绝不"跳过" |
| **手动新增 / 编辑 / 删除** | 端点里 `mark_identity_dirty` → 装配 → 补记号 | 顺带把"手动改过"的那一场当场算进身份（原来只作废、不装配，卡片统计会少算） |
| **purge（解订阅 / 删账号）** | `purge_account` 里 `mark_dirty` | 行没了而记号还在；那个账号之后若被重新同步，新行会没身份 |

判据（`tests/test_vtuber_api.py::test_startup_materialize_skips_marked_accounts`）：
没记号 ⇒ 要扫且真写 · 有记号 ⇒ `{"accounts": 0, …}`（**跳过的直接证据**）·
**版本变了 ⇒ 重新要扫** · 手动增删改三条路之后记号仍在（当场装配过）· purge 之后记号没了。

## 三、数

| | 旧版（无条件扫） | 现在 |
|---|---|---|
| 正常启动 | **485ms** | **0.65–1.17ms** |
| 升级后的第一次启动（要补） | 709ms | 709ms（只发生一次） |

## 四、留下的边界（如实记）

- 记号的正确性**只由那几个作废点保证**：将来若出现"绕过它们改 `live_sessions`"的新代码，
  症状就是上面那条"永久陈旧"。⇒ 加新的场次写点时，**必须同时作废记号**
  （`identity_mark_key` / `mark_dirty` 就是给这个用的）。
- 真机升级到本版后**第一次启动仍会扫一遍**（约 0.7s，因为老库没有记号）——
  之后才是毫秒级。
