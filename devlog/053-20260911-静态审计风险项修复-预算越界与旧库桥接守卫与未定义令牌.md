## 一、`_PlatformBudget` 空窗口越界 → 综合档线程启动即死（最高危）

### 现象与根因

`app/services/scheduler.py` 的 `_PlatformBudget.wait_seconds()`：

```python
need = n - room                      # 需要腾出的名额数
idx = min(need - 1, len(dq) - 1)     # ← 窗口为空时 len(dq)-1 == -1
waits.append(max(0.0, self.window - (now - dq[idx])))   # dq[-1] → IndexError
```

触发条件：**单个平台一轮的请求数 > `DYNAMICS_BUDGET_RPM`（12）**，且该平台窗口
恰为空（进程刚起来，或静默超过一个窗口）。现实形态＝**同一平台主账号数 ≥ 13**
（`PRIMARY_PLATFORM_ORDER` 让 B 站优先，所以 V 基本都算 bilibili）。
devlog/049 实测用的是 8 个主账号，因此这条路径从未被走到。

### 为什么它是最危的一条：抛出点全在兜底之外

```
_dynamics_next_due()            (:2675-2676)  预算启用时无条件调用
  └─ _tier_loop 首轮            (:2702)       ← 在 try 之外（该 try 只包住启动链那一小段）
  └─ _tier_loop 心跳 while True (:2740)       ← 整个循环无异常兜底
```

抛出 → **综合档线程死亡** → 动态流与账号流**永久停摆**（T0 直播轮询是独立线程，仍活着，
所以界面看起来「部分正常」）→ 安装版是无控制台程序，只能去 `logs/sidecar.log` 才看得到。

### 修法

```python
if not dq:                 # 空窗口 + 名额不够 = 一轮请求数 > rpm，等待换不来名额
    waits.append(self.window)
    continue
idx = min(need - 1, len(dq) - 1)
```

**为什么不是「加个 `max(0, …)` 夹取」**：夹取救不了空表 —— `need == 1` 时
`min(0, -1)` 得 -1（越界），夹到 0 后 `dq[0]` 同样不存在。必须**先判空**。
（第一版就是只加了夹取，被新用例当场证伪。）

### 语义与连带影响

- `cost > rpm` 是**退化输入**：该请求在任何时点都凑不出名额，等待是唯一合理语义。
  返回一个窗口（而不是抛错）既保证不死线程，又自然限速到 ≤ rpm。
- 现实含义：单平台主账号数一旦 > 12，**动态流每轮都会空等一个窗口**（速率从
  ~6 次/min 掉到 ~12 次/min 上限内）。限速是对的，但若主账号数远超 rpm，
  应考虑把预算改成按账号数自适应 —— 已写进 `_PlatformBudget` 的 docstring。
- 顺手修正了原来的一处**高估**：`need` 落在窗口内部时，旧的 `min(need-1, len-1)`
  只有在 `need-1 > len-1` 时才取 len-1；本次未改这段数学，只是补上了空表分支。

## 二、旧库桥接不重建唯一约束，却照样 `stamp head`

### 问题

`app/main.py::_sync_legacy_schema()` 是「有表但无 `alembic_version`」的旧库桥接路径，
它只做两件事：**补列 + 补索引**。而 **SQLite 不支持 `ADD CONSTRAINT`** —— 唯一约束
根本补不了，补完却照样 `command.stamp(cfg, "head")`。

于是「唯一性比代码假设更严格」的库会被永久标成 `f003`，之后每次启动都走快路径跳过迁移。
典型受害者是 `posts`：迁移 `c002` 把唯一键从全局 `(platform, platform_post_id)`
加宽为 `(platform, platform_uid, platform_post_id)`，动机正是**联合投稿**
（同一 pid 出现在多个 UP 名下）。旧库保留旧约束 → 加宽后本应合法的行被唯一约束拒掉 →
`scheduler._safe_store_post` 当作「帖子已存在」跳过 → **合法数据静默永久丢失**，
正是 c002 要修的那个场景。

### 修法：桥接前先验唯一键，不一致就拒绝 stamp

新增两个纯函数（`app/main.py`）：

- `_live_unique_keys(inspector)`：库内**实际存在**的唯一键 `{表: {列元组}}`。
  同时收 `get_unique_constraints` 与 `get_indexes(unique=True)` ——
  alembic 建的表是命名 `UniqueConstraint`，`create_all` 建的表是
  `Column(unique=True, index=True)` 生成的唯一**索引**，两种形态都得认。
- `_missing_unique_keys(inspector)`：模型要求但库内没有的（空列表＝一致）。
- `_sync_legacy_schema()` 开头调用它，非空则 `RuntimeError`，消息里列出缺哪些键。

**按列元组比较、不看约束名**：名字不是不变量的载体，「平台+UID 唯一」这件事才是；
应用侧也只捕获 `IntegrityError`、不认约束名。

**只比唯一键，不比索引名 / 默认值 / NOT NULL**：后两者缺失只影响极端写入路径
（例如裸 SQL 插入不给 `sort_order`），而唯一键缺失会让合法数据被静默丢弃。
把桥接做成「全等才放行」会拒绝掉大量本来能正常工作、且**无法自动修复**的旧库，
把可诊断的数据丢失换成不可用的应用 —— 不划算。

### 运维后果（需知悉）

守卫命中时后端**拒绝启动**（lifespan 抛错 → uvicorn 退出），日志落
`<DATA_DIR>/logs/sidecar.log`（含 traceback）。前端会停在启动幕并显示
「后端启动失败 / 若反复失败，可删除数据目录后重试」——⚠️ **该提示语对这种情形是错的
（删库＝删档案）**，见下方「后续待办」。
**当前用户的库不受影响**：`com.ddtoolkit.app-dev/vtuber.db` 的 `alembic_version = f003`，
唯一键与模型一致（已实测）。

## 三、`var(--c-text)` 未定义（样式静默失效）

`frontend/src/styles/posts.css:1532/1556/1688` 三处 `color: var(--c-text)`，而
**`--c-text` 在 tokens.css / index.css 里都没有声明**（全仓仅这三处引用）。
未定义的 `var()` 在计算值阶段失效 → 这三条 `color` 声明**整条被丢弃**、回退继承，
受害的是档案设置窗口（`VtuberSettingsDialog`）的分区标题、输入框文本、账号名。

项目里主文本色的令牌是 `--c-text-main`（其余 80+ 处都在用），三处是笔误 → 统一改为
`--c-text-main`。**全仓扫描确认已无未声明令牌**（唯一剩下的 `--rise-i` 由 TSX 内联
设置，属正常用法）。

## 五、经验

- **「加个夹取」不是空集合的修复**：`max(0, min(need-1, len-1))` 这种写法对空表无效 ——
  `need == 1` 时两个候选值分别是 0 和 -1，`min` 取 -1（越界）；即便夹到 0，`dq[0]`
  同样不存在。**空集合要单独判**，别指望下标运算兜底。这条是被自己新写的用例当场抓出来的。
- **崩溃点的「包装范围」比崩溃本身更值得查**：同一个 `wait_seconds` 抛错，被 try 包住
  只是少跑一轮，落在心跳循环外就是整条调度线程死亡。定位这类问题不要停在「哪里抛」，
  要顺着调用链问「**最近的一层兜底在哪**」——本例答案是「没有」。
- **`stamp head` 是承诺，不是记录**：它的语义是「本库结构等于 head」。凡是自动补丁式
  迁移（补列/补索引）都补不全结构（唯一约束要整表重建），所以必须在 stamp 前**校验
  自己补不了的那部分**，宁可拒绝启动也不要写下一个假承诺 —— 后者会让后续所有真实迁移
  全部被跳过，问题在几个月后才以「数据莫名丢失」的形态爆出来。
- **校验的判据要盯住「会造成什么后果」，不要盯「结构像不像」**：本守卫只比唯一键，
  放行索引名/默认值/NOT NULL 的差异 —— 因为前者导致静默丢数据，后者不会。
- **测试断言也要防「两边都空」的假通过**：守卫第一版的判据写成
  `getattr(uc, "unique", False)`，而 `UniqueConstraint.unique` 是 **None**（不是 True），
  于是所有唯一约束被静默跳过、`_missing_unique_keys` 恒返回空 —— 而最初那条
  `assert missing == []` 照样通过（正确的库与坏掉的实现都返回空）。
  补上「反射确实看得见 `('platform','platform_uid')`」的正面断言后才暴露。
  **一个只断言「没有坏消息」的用例，等于没测。**
- **审计结论必须逐条复核**：本轮 3 条修复全部来自审计，但复核过程本身产出了两个额外事实
  ——「夹取不够」和「`UniqueConstraint.unique` 是 None」——两者都不在审计报告里。
  审计给的是线索，不是结论。
