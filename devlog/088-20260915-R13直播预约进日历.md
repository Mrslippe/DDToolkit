## 一、方案修正：**后端零改动**（原计划的多余部分）

原方案写了"加聚合端点 `GET /reservations/upcoming`，一次拿全部已订阅 V，避免 N 次请求"。
核实代码后这条**站不住**：

- `GET /vtuber/{id}/future-reservations` **早就存在**（P7 那批做的），且
  `VtuberEventRepo.future_reservations()` 已经处理好全部脏活：`已结束` 剔除、时刻解析
  （完整日期/MM-DD 跨年/今天/明天四种格式）、**过期与超 90 天剔除**、标题规范化
  （`直播预约|` 前缀）、按时刻升序；仓库层有 **6 条**解析用例。
- **日历本来就是单 V 的**（`accountId` → 该 V 的主账号）⇒ 一次请求就够，
  "聚合全部 V"没有任何调用方。

所以本批只补**前端**（外加一条路由契约用例，因为前端从此依赖它）。

## 二、前端四块

| 文件 | 职责 |
|---|---|
| `api.ts` + `types.UpcomingReservation` | 取数封装。类型刻意与 `ReservationInfo` **分开**：那个是动态 `body_json.reservation` 的**原始形状**，这个是服务端解析结果（`post_id/title/start_at/reserve_total/rid`） |
| `components/live/useReservations.ts` | **V 级**取数（预约跨账号共用）。**刻意不塞进 `useLiveSessions`** —— 那份 effect 顺序与依赖数组是契约（devlog/057），加一条取数就会动它。失败**不清空**已有数据：预约是锦上添花，上游挂了日历照常可用 |
| `utils/reservationDays.ts`（9 条单测） | 纯逻辑：按天分组（与场次同一 `dayKeyIso` 口径，两边才对得上同一格）、**徽章优先级 场次类型 > 预约 > 休息/待定**、展示行（最早一条 + 预约人数 + 多条提示） |
| `LiveCalendar.tsx` + CSS | 格子 `.lc-resv`、有场次时的 `.lc-resv-mini`、浮层预约块 |

### 三条界面口径（都是"别把已知信息藏起来"）

1. **无场次但有预约的日子，徽章是「预约」**，不是待定/休息 —— 预约恰恰说明"确定会开播"，
   报「待定」等于把已知信息扔掉（这正是本需求要解决的问题）；
2. **不动九类色系**：只在格子左缘加一道强调粉竖条 + 文案用粉。类型色语义是"已经播过什么"，
   预约是"将要播什么"，混进色系会让"游戏/杂谈"的读法失真；
3. **计数槽放预约人数**（`128 人预约`），不重复"预约"二字；已有场次的日子预约压成一行小字，
   不与场次争主位；**只有预约没有场次的日子也能 hover 出浮层**（否则那枚徽章点不出任何东西）。

## 三、护栏：探针**自己造现场**

```powershell
python scripts/ui_probe.py --reservations
```

关键设计：**开发库里未必有未来预约**（实测 V14/V15 都是 **0 条**）—— 靠数据碰运气会让断言空转。
所以脚本在**起后端之前**往数据目录副本的 `posts` 里插一条明天的预约帖：

- `desc1` 用**完整日期**（`YYYY-MM-DD 21:00 直播`）而不是"明天 HH:mm"：后者按帖子发布日推断，
  与运行时刻耦合；日期取本地明天，保证 `start > now`（服务端会过滤过期预约）；
- 只写副本，**绝不碰真库**（与其它探针同一约定）。

实跑输出：

```
已种预约：'探针预约占位'（副本 DB，非真库）
日历格：找到预约格=True 徽章='预约' 格内文本='16预约21:00128 人预约探针预约占位' 计数槽='128 人预约'
hover 浮层：打开=True 含预约徽章=True 抬头='2026-09-160 场 · 1 预约' 预约行='预约探针预约占位21:00 · 已有 128 人预约'
对照：无预约格数=41 今天格徽章='杂谈'
```

**反向验证过**：把 `cellBadge` 里的预约分支去掉 → 探针立刻红
（"预约格徽章是 '待定'，不是「预约」"），恢复后绿。

## 四、日历签名基线：一次**数据漂移**的排查

`--archive --calendar-expect 48519bae…` 报失败，实得 `50b78ec0…`。判断过程（值得留档）：

1. 先问"**我的改动能不能影响它**"：`LiveCalendar` 只在**有预约**时才改渲染
   → 直接问仓库层 `future_reservations(15)` = **0 条** ⇒ 我的分支根本没触发；
2. 再 dump 日历格：**14 日从「休息」变成一场直播、15 日出现两场**（当晚新抓到的）
   ⇒ 是数据漂移。

结论：签名对**数据**敏感（这也是 `--calendar-expect` 只能做"改动前后短窗口比对"的原因）。
已按 20:5x 实测重取基线 `50b78ec0…`，并把"怎么区分数据漂移 vs 代码漂移"写进
`docs/DEV-LOOP.md`。
