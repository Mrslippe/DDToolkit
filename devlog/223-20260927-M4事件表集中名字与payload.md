## 一、为什么集中它

这些 `ddtoolkit:*` 事件是**隐式契约**：右栏改完签名要通知左栏（R33 那条
「修改过的签名左栏没有及时同步」的事故，根因就是**缺一条通道**）、顶栏抓完要通知侧栏与列表。
今天它们散在 12 个文件里写成**裸字符串**，监听侧一律 `(e as CustomEvent<X>).detail` 手写断言 ——
**改名或改 payload 时编译器一声不吭**，只在运行时静默断开。

现在：名字进 `EVENTS` 表、payload 进 `AppEventMap`，`emit` / `on` 都由表推导 ⇒
改名或改 payload **当场编译错误**；事件名本身还有一条用例逐条钉住。

**8 个事件**：`pill-message`（顶栏胶囊）· `kick-poll`（踢一脚轮询）· `data-changed`（侧栏重拉）·
`fetch-idle`（谁跑完了）· `account-progress`（账号快照增量）· `vtuber-updated`（单 V 就地更新）·
`capabilities-refresh`（登录态变了）· `widget-seed`（dev-only 注入）。

## 二、只集中「名字与类型」，**不换机制**（三处可观察差异逐字保住）

1. **无 payload 的事件照旧发裸 `Event`**：`kick-poll` / `data-changed` / `capabilities-refresh`
   今天就是 `new Event(...)`。搬进表时若一律发 `CustomEvent`，`detail` 会从 `undefined` 变成
   **`null`**（jsdom 实测：`new CustomEvent(n, { detail: undefined }).detail === null`）——
   现有监听方都不读它，但"集中"不该顺手改掉可观察行为。⇒ `emit` 按"有没有 payload"分流，
   用例专门钉这一条。
2. **宿主可注入**：`utils/fetchIdle.ts` 的单测跑在 **node 环境**（没有 `window`），所以
   `dispatchFetchIdle(kinds, host)` / `onFetchIdle(cb, host)` 的 `host` 参数一路透传到
   `emit(name, detail, host)` / `on(name, cb, host)`；默认宿主是**调用时**取 `window`
   （不是模块加载时取）。
3. **老常量与裸字符串写法照旧可用**：`FETCH_IDLE_EVENT` / `VTUBER_UPDATED_EVENT` /
   `WIDGET_SEED_NOTICES_EVENT` 现在是表里的**再导出**（不再是第二份字面量），
   `addEventListener('ddtoolkit:xxx', fn)` 也照旧 —— 表是给产品代码用的。

⚠️ **`dev/probe.ts` 刻意没迁**：它按裸字符串派发/监听（`pill-message` / `widget-seed` /
`vtuber-updated`），是这张表的**外部消费者** —— 探针能不能跑，本身就是"名字有没有被改掉"的
第二道判据。真正兜住它的是用例里那份**冻结名单**（改名必须同时改用例与探针，否则红）。

## 四、判据（`utils/appEvents.test.ts`，7 条）

**① 事件名是契约**：名单与 `EVENTS` 表完全一致且就是那 8 个（改名会红）；
老常量（`FETCH_IDLE_EVENT` / `VTUBER_UPDATED_EVENT`）就是表里的同一个字面量。
**② emit/on 往返**：带 payload 拿到同一个对象 · **无 payload 的事件 `detail === undefined`** ·
退订之后不再收到 · 裸字符串写法照旧可用 · 可指定宿主。

**反向验证四刀全部精确报红**：
改线上名字（`pill-message` → `pill-msg`，即"探针会静默失效"那种改法）· 无 payload 也发
`CustomEvent`（detail 变 `null`）· `on` 的退订函数不干活 · `on` 忽略注入的宿主。
