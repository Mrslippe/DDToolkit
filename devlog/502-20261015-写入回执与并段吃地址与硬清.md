# 502-20261015 写入回执搬到概要条 + 合并吃地址 + 清空改硬清

## 用户三条（2026-10-15 晚，带截图）

1. 「点击『写入勾选的 178 条』之后，**没有明显的反馈**，甚至按钮灰了一段时间之后还是原本的
   按钮，用户无法得知是否确实写入了」；
2. 「**再次进行扫描的时候结果还是一样**，正常来说应该把已经匹配写入的项给剔除掉」；
3. 「清空已匹配的录播功能应该**硬性清除所有已匹配项**」。

第 2 条不是 UI 问题 —— 它把一条**真丢数据**的合并 bug 挖出来了。

## 一、根因：并段里后一行的录播地址，合并视图永远看不见

### 症状链

用户点写入 → 后端确实写了（`update_row` + commit）→ **再扫一遍还是同一批**。
判据是"已有 `vod_url` 的场次不进匹配池"（`vod_scan.scan` 的池子过滤），
所以只能是：**写进去的那个地址，`merged()` 视图看不见**。

### 复现（真库副本 + 真上游，`_probe/vod_apply_probe.py`）

```
scan: matches 189 / auto_ok items 189
apply => 189 applied / 0 failed          ← 全都写进去了
db rowcount: {'<NULL>': 693, 'match': 189}
re-merged: pool 249 → 242                ← 只走了 7 条
rescan => matches 182                    ← 182 条"已经写过"的又回来了
```

解剖一条（真机数据，2022-10-09）：

```
场次 4e1c6996-… merged.vod_url = None
  src_live_ids = {'danmakus': '4e1c6996-…'}
    行 live_id=4e1c6996-… vod_url=https://…BV1MV4y1L7zc vod_source=match   ← 表里有！
```

同一天还有一行 `11:01:42→11:10:52`（1990 弹幕），而写进去的是 `11:18:00→16:22:00`
（47845 弹幕）那一行 —— 两行被合并规则判成 **`restart`（断播重开，gap 7min）并成一组**。

### 机制（`app/repositories/vtuber_repo.py`）

两个"取一行代表一组"的规则**不同源**：

| 取什么 | 怎么取 |
|---|---|
| 组的字段（标题/时间/…/`vod_url`） | **主行** = 组里第一条（`_group_from_row`），之后 `interrupt`/`restart`/`dup` 分支**只补缺失字段** |
| 组的对外 `live_id` | `_SRC_IDS_KEY` 里**同源后写的那一行**（`ids[source] = row.live_id` 覆盖） |

⇒ 录播匹配写进的是"对外 id 那一行"（`vod-apply` 按 `live_id` 定位），
而并段分支从不 import 这一行的 `vod_url`。地址落在表里，**合并视图永远不看它**：

- `merged()` 里 `vod_url` 是 `None` ⇒ 不进池 ⇒ **每次扫描都重复出现**；
- 日历上也不显示 ▶ ⇒ 用户以为根本没写进去。

⚠️ 老代码的注释写的是"手动补的录播地址**只增不减**"（不变量 39，devlog/454）——
它只防住了"被 `None` 冲掉"，**没防住"根本没进来"**。这两件事在 `dup` 分支里各中了一半。

### 处置

新增 `LiveRepo._keep_vod(g, *候选)`：**已有的不动；没有的从候选里取第一个非空**，
四个分支（`_merge_row_into_group` / `dup` / `interrupt`+`restart`）统一走它，
候选里**必须带上正在并入的这一行**的地址。

判据 `tests/test_live_sessions.py::test_merged_segment_vod_url_from_later_row`
（★ 断点验过：把那一句 `_keep_vod` 去掉，用例当场红）。

修完同一条探针：

```
re-merged: pool 249 → 60
rescan => matches 0        ← 182 → 0
```

## 二、写入回执搬到概要条（第 1 条）

旧样子：回执块 `[data-vod-fill-applied]` 挂在**滚动区最底下**。用户那份是 178 行 ——
写完之后那一块在视口外，等于**没有回执**；而概要条的「配上 N 场」读的是
`scan.matches`（扫描快照，写完不变），按钮又变回「写入勾选的 178 条」⇒ 三个信号一起说"没写"。

现在：

- 回执进概要条（`.lvc-stat-ok`，绿色常驻）：`已写入 178 条`（失败时补 `· 失败 M 条`）；
- 计数改读 `rows.length`，**写成功的行当场从表里移走** ⇒ 数字跟着掉、列表当场变短；
- 主按钮变「已写入 N 条」且禁用（不会再点第二遍）、「取消」变「完成」；
- 失败项**留在表里**并逐条给原因（`[data-vod-fill-applied-detail]`），还能重试。

判据 `VodFillDialog.test.tsx` 两条（★ 写成功后行移出列表 + 回执在概要条 + 按钮禁用；
失败逐条列原因且失败行留表）。

## 三、清空改成"硬清"（第 3 条）

上一版只清 `vod_source='match'`。真机库里 **693 条有地址的行全是历史写入（`NULL`）**
⇒ 点下去 `cleared=0`、回执只能说"这些清不掉" —— 用户看到的就是"清空是坏的"。

现在 `vod-clear` 按 **`vod_url IS NOT NULL`** 取行、一次 `commit` 全清，**不分类**。
保留的两条纪律：**一个上游请求都不发**（第一版的毛病）、**只清地址不删场次**。
回执改成分类报数 `{cleared, auto, manual, untracked}`（`skipped_*`/`matched` 三个字段删掉），
确认窗把三类摆出来，`manual > 0` 时**额外警告一句**"手填的也会一起没，而且扫不回来"。

⚠️ 这不是推翻不变量 39：39 管的是"**合并**不许抹掉手填的地址"，不是"用户不能自己清"。
手填的不可再生 ⇒ 用**把范围说清**来兜，而不是替用户留着。

## 五、这一轮又踩的（记给下一次）

- **"取哪一行代表一组"有两个规则时，写在"另一行"上的数据就会消失**。`merged()` 里
  字段取主行、id 取同源后写行 —— 一处不一致，症状不是报错而是"写了像没写"。
  以后再往 `live_sessions` 里加"用户/自动写上去的列"，都要问一遍：
  **它跟着主行走，还是跟着对外 id 走？**
- **PowerShell 的 `-replace` 拿 CRLF 没办法**：断点实验第一次"通过"是假的（`$` 只匹配到
  `\r` 前面，替换根本没发生）。改文件对比实验一律用 python 读写，别用 `Set-Content`。
- **回执的位置就是回执有没有**：挂在滚动区底部的回执，在 178 行的窗口里等价于不存在。
  判据要连"行数变少"一起量，只判 `querySelector` 非空会放过这一整类。
