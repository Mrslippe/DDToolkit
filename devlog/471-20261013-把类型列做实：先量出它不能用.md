## 一、先量：那两列入库了，但**任何 SQL 聚合都用不了**

新脚本 `scripts/check_type_index_parity.py`（只读真库副本）把两条路逐账号逐类比了一遍：

| 路 | 真机 14 账号合计 |
|---|---|
| 合并视图（日历 / 卡片当时都在走） | **7,639 场** |
| `GROUP BY category`（"类型已落库，可直接按列聚合"那条） | **3,948 行** |

**14/14 账号全不齐**，差异只有三个成因，而且**没有一个是 bug** —— 它们都是 f016 的
设计结果：

| 成因 | 量级 | 说明 |
|---|---|---|
| 兜底写 NULL | 约 4,240 场 | f016 有意让 `fallback` 不落库 ⇒ 任何 SQL 聚合都看不见这批（**55%**）。账号 22：`live` 合并路 550 场 vs 索引路 **0** |
| 按行数不按场次 | 123 行 | 同一场可能有多行（danmakus + feed、self 快照并入）⇒ `GROUP BY` 数行 |
| 组内两行答案不同 | 123 组里 **57 组** | 那两行是**不同规则版本**下分别落库的 ⇒ "取哪一行"必须是规则，不能是运气 |

⇒ 卡片头注释里那句「f016 之后可直接按列聚合」当时是**假的**；`/live-type-stats`
也没在读列，它在重跑一遍 `merged()`（159ms）。

## 二、f017 三件事

1. **兜底也落库**：`category='live'` + `category_from='fallback'`。
   原来靠"列是 NULL"表达"还没定出来"，现在改由 **`category_from IS NULL`** 表达 ——
   它本来就在记"哪一档定的"。⚠️ 这条推翻了 f016 的一条明确设计（§2.1 的"兜底不落库"），
   理由是：**一个让 55% 数据对查询不可见的设计，等于没落库**。
2. **`session_key` 只写在代表行上**（`<代表行live_id>#<组里最小成员id>`），同组其余行
   `session_key`/`category`/`category_from` 三列全清 ⇒ `GROUP BY` 天然是"每场一次"。
3. **读路径惰性物化**（`_stored_by_live_id` → `materialize_sessions`），与惰性回填同一个模式：
   值一样就不写。**代表行 = `merged()` 给这个组定的对外 `live_id` 那一行**。

两个入口于是都直查 `(account_id, category)`：代表行（索引聚合）+ 校正叠加 + 虚拟场次现算。

## 三、施工中踩到的两件事（都有判据了）

**① 代表行不能自己再排一遍。** 第一版让 `group_states` 按"优先级 + id 最小"自己选代表行，
而同源两行（真机里 123 个组全是这种）时 `merged()` 的对外 `live_id` 是按**合并顺序**取第一个的
—— 两处的 tie-break 一分叉，物化写 A 行、读取按 B 行查，症状是**这一场的类型静默退回兜底**。
现在代表行统一读 `s["live_id"]`（对外 id），判据
`test_only_the_representative_row_carries_the_type` 钉"物化的代表行与对外 id 必须是同一行"。

**② 只读库量不了了。** f017 之后 `/live-sessions` 与 `/live-type-stats` **会写库**，
`measure_endpoints.py` 的 `mode=ro` 直接 500（`attempt to write a readonly database`）。
脚本加了 `--write`（且**必须**同时给 `--db <副本>`）—— 这是"读端点写数据"的第一次，
代价记在 PERF 与方案的风险表里。
