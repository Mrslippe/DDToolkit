## 一、为什么挑它，以及**与计划的偏差**

计划把 M4 写成"7 个 state + 6 个 handler 一台机器"。实测那 6 个 handler 长的全是同一个形状：

```
setX(v); setPage(1)
```

而 **`setPage` 属于分页机**（下一刀的 `usePostPagination`）。两台 hook 互拿对方的 setter
就是**循环依赖**，抽完比不抽更难读。折中：

| 进 hook | 留在页面 |
|---|---|
| 7 个 state（类型 / 归档 / 已删 / 搜索输入 / 生效关键词 / 起止日期） | 6 个 handler 里的 `setPage(1)` 那一行 |
| 搜索防抖 effect（`searchKw` 的唯一写者） | "谁在什么时机调它" |
| 「换账号 / 换 V ⇒ 重置」effect | |
| `resetFilters()`（弹窗内三件字段） | |

⇒ **依赖方向单向**：页面 → query hook / 页面 → pagination hook，两台 hook 之间零耦合。
`accountKey`（`platform:uid` 稳定代理）因此**提到 hook 调用点之前**——它有两个消费者
（重置 effect 与统计概览 effect）。

## 二、逐字保留的时序契约（E9）

`resetFiltersOnSwitch` 的依赖是 **`[sceneAcc, accountKey]`**，位置是"同批 render 之后的 effect"。
这不是风格，是**时序的实现方式**：

> 本 effect 与 scene 提交同批 render 后运行，**先于 `EXIT_MS` 提交完成** ⇒ 提交时 `filterRef`
> 已是重置态 ⇒ 与"恒按默认筛选预取"的种子指纹一致。

改坏它的症状极隐蔽：**种子被误消费**，列表先错一帧再被重取纠正，界面上只闪一下。
所以 hook 文件头把"不许改成提交时重置、不许改依赖数组"写在最上面，测试里也**专门测时序**
（不只是测"重置了没有"）。

`archived` 曾漏在这条重置之外（P8-A 加归档 chip 时未同步）——同样形态的错配，
用例里给它单独一条 `expect(..., 'P8-A 曾漏掉 archived ⇒ 种子指纹错配')`。

## 三、判据（`hooks/usePostQueryState.test.tsx`，7 条，jsdom + 假定时器）

- ① 换账号重置 · 换 V 重置（新 V 还没选账号，`accountKey=null`）·
  **只有这两个 key 变才重置**（同参数重渲染 = `refreshTick` 边沿，不许清筛选）
  —— 最后这条是**反向**判据：把依赖数组改宽（比如塞 `refreshTick`）它会红。
- ② 时序：切账号那一批 render 的下一拍字段已是重置态。
- ③ 防抖：299ms 还是不落 / 300ms 落且 trim / 连续输入重新计时（第二刀打满 300ms 也不落）。
- ④ `resetFilters` 只清弹窗内三件（归档 / 已删 / 日期），**类型 chip 与关键词不动**。

写法和 218 同一套路（`react-dom/client` + `act` + `IS_REACT_ACT_ENVIRONMENT`，零新依赖）：
把 hook 的 7 个字段打到 `data-*` 上当探针，断言读属性而不是读内部 state。

## 四、顺带修掉 `ui_probe --toolbar` 的**假红**（查了三轮才对）

抽完 hook 复跑探针，`--toolbar` 报了两条红（"方向信号没接上" + "工具条没立即让位"）。
devlog/218 §四 把它记成"偶发"，这次连跑两回都红，于是查到底 —— **是尺子错了，不是产品**：

`OverlayScroll` 的首次 `sync()` 是**同步调用**（挂载时写 `data-scroll-dir='up'`），
之后所有 `sync()` 都只从 **rAF** 里跑（滚动事件里一次 + 400ms 轮询一次）。
而 Chrome 虚拟时间下 **rAF 几乎不被服务** ⇒ 探针滚完三步、`sleep(120)` 就读方向，
读到的还是**挂载时那次同步写**的 `'up'`。第二次跑更刺眼：`上滚后=shown=0` ——
迟到的 `sync()` 在上滚阶段才跑（那时 `scrollTop` 恰好是 120 > 0），把方向写成了 `'down'`，
工具条**在上滚时才让位**。

**第一版修法是错的，值得留着**：改成"有界轮询等方向真翻"（上限 ~2s）—— **没好，还是红**。
因为虚拟时间里 `sleep` 只是把虚拟钟快进（几毫秒真实时间跑完 2s 虚拟时间），
**并不会让浏览器多排一帧**：等待买不到任何东西。

**第二版（采纳）**：让探针**显式顶掉排帧这一步** —— `OverlayScroll` 在 `import.meta.env.DEV`
下把**同一个** `sync` 注册到 `window.__ddtoolkitOsSync`（挂载 push / 卸载 splice），
探针每步滚完调一次。被绕过的只有**浏览器排帧**；方向阈值、只在翻向时写 DOM、
顶部复位这些产品逻辑一个字节没动。同款先例本仓已有四个
（`__ddtoolkitSetShellHidden` / `__ddtoolkitCloseClick` / `__ddtoolkitCorners` / `__ddtoolkitSeedReport`）。

顺带把两条**空转风险**堵上（"空转不是通过"）：
- 钩子不在（`osSyncHook <= 0`）⇒ 直接判红，别让它悄悄退化成赌排帧运气；
- 上滚那一步现在也读一次方向（`scrollDirUp`）并断言是 `'up'` ——
  以前若 `up` 那次写入压根没送达，"上滚不许自己冒出来"是**空转通过**；现在它是**前提失败**。

**反向验证（两刀，都期望红）**：
| 刀 | 改法 | 结果 |
|---|---|---|
| A | 状态机不再认 `data-scroll-dir=down` | 只红"没立即让位"（**不再**红"方向信号没接上" ⇒ 钩子没把"送达"这件事掩盖掉） |
| B | `sync()` 的方向恒为 `up` | 红"方向信号没接上" + 级联"没立即让位"（⇒ 方向判据仍真的在读**产品算出来的值**，不是钩子自己编的） |

修完 `--toolbar` **连跑三次全绿**，且三次都读到 `dir='down'` / `dir='up'` 两个前提。

两条新规矩提炼进 `docs/DEV-LOOP.md`：**§6.15**（临时脚本写回文件必须逐字节 ——
`write_text` 默认把 `\n` 翻成 CRLF，`git diff` 看不见、`git status` 才看得见）与
**§6.16**（探针不许靠"等待"去等 rAF 产物；能顶掉就顶掉，顶不掉就把"信号到达"当判据）。
