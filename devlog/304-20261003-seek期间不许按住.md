# 304-20261003 跳转后"卡在一帧再卡顿一阵"：治理器把 seek 自己也按住了

> 用户现象：期望「点跳转 → 加载一会 → 正常播」；实际「加载一会 → **卡在一帧**（有时是封面）
> → 卡顿播放一会后同步」。根因是**我上一批加的缓冲治理器自己造的**。

## 一、根因：`waiting` 一律按住 ⇒ 把 seek 要的数据也一起卡住

`devlog/301` 的治理逻辑是"`waiting` 且前方不足 `HOLD_AT` ⇒ 主动 `pause()` 按住"。但
**seek 之后 `bufferedAhead()` 必然返回 -1**（新的 `currentTime` 根本不在任何已缓冲区间里），
而 `-1 < 0.5` ⇒ 每一次跳转都会命中"按住"。于是：

```
点跳转 → currentTime = 目标 → seeking → waiting
      → 我们 pause()（本意是"别一帧一帧地蹭"）
      → 而**实测过：一暂停，浏览器就不再继续拉缓冲**（devlog/301：ahead 8 秒纹丝不动）
      → 数据永远不来 ⇒ 1.2s 后靠死锁兜底放开 → play() → 还是没数据 → waiting → 又按住 …
```

表现就是用户描述的三段：**画面冻在最后一次解码的那一帧（没帧可显示时是 poster）→ 抖动地播一会
→ 等数据终于追上才同步**。所以那条治理规则**只适用于"播到一半饿了"**，不适用于
"刚 seek 完要重拉一段"。

**修**：三处收口

| 处 | 规则 |
|---|---|
| `onWaiting` 是否按住 | `!el.seeking` **且** `ahead >= 0`（真的在已缓冲区间里却又不足 `HOLD_AT`）**且** 没在按住 |
| 看门狗 | 一旦 `el.seeking` ⇒ **立刻放开**（用户拖了一下就得让路） |
| seek 收尾 | 画面还没在放（`el.paused`）时**只对齐音轨、先不出声**，起播交给 `onPlaying → startAudio()` |

第三条治的是"过一会才同步"那一半：原来 seek 到位后无论画面是否真的在出帧都按意图把音轨放出去，
于是**声音先跑、画面还冻着**，要等漂移纠正慢慢拉回来。

**反向验证过**：把按住条件改回"只看 ahead"（`ahead < HOLD_AT`）⇒ 两条新用例立刻红
（"正在 seek 时不许按住"、"`ahead = -1` 时不许按住"）。

## 二、复盘：同一个坑的第三次

治理器（`301`）引入的"按住"这一个月内已经是第三次咬到自己：

| 批次 | 咬到哪 |
|---|---|
| `302` | 按住期间的 `pause` 被当成用户暂停 ⇒ 界面显示"暂停" |
| `303` | 按住会停音轨，音轨事件又驱动界面 ⇒ ▶/⏸ 闪 |
| **`304`** | **按住发生在 seek 期间 ⇒ 把 seek 自己需要的数据卡住** |

共同点：**"按住"是一个会改变系统行为的副作用，它的适用条件必须写得比"看起来饿了"更窄。**
凡是"用户刚做了一次操作（拖拽/跳转）"或"元素正在做一件异步的事（`seeking`）"，
都不该由我们插手暂停 —— 让浏览器把它做完，我们只负责显示状态。

## 三、判据（新增 4 条）

| 用例 | 钉什么 |
|---|---|
| 正在 seek 时的 `waiting` | **不按**（`pause` 未被调用）、元素继续在播、转圈照给 |
| `ahead = -1` 时的 `waiting` | 不按（"要重拉一段" ≠ "播到一半饿了"） |
| 按住期间开始 seek | 看门狗 300ms 内放开（`play()` 被调用） |
| seek 到位但画面没在放 | 音轨**对齐**但 `play()` 不被调用（"过一会才同步"的封口） |
