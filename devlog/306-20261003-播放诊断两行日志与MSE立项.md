> 用户口径：「**先做诊断**，并把 MSE 加入开发计划」。
> 这条路的教训写在 `devlog/305` 的复盘里：真机现象（"跳转后画面低帧率、音频正常"）能排除

## 一、诊断：一条现象，两行数字

复现一次"跳转后画面低帧率"，日志里应当同时出现这两行（**同一个 `logs/app.log`**）：

**代理侧**（`video_proxy.py`，每次转发一行）：
```
[视频代理] video hash=3194ade8 host=upos-sz-mirrorhw.bilivideo.com range=bytes=74383360-
          status=206 首字节=213ms 前5秒=2.41MB/s 均速=2.65MB/s 共=24.40MB 用时=9.2s 中止=否
```
· **首字节**：CDN 认不认这个 Range、边缘有没有这段的缓存（冷启动就慢在这）；
· **前 5 秒吞吐**：够不够撑住实时码率（1080P 需要 ~240KB/s）；
· 地址只留 **8 位指纹**（`hash=`），签名参数**不进日志**。

可疑的那些直接提到 WARNING 并**写明对应现象**（正常播放不该刷 warning）：
```
… ⚠️ 前5秒只有 0.12MB/s —— 撑不住实时码率会表现为『画面低帧率』
… ⚠️ 首字节 2310ms（> 1500）—— CDN 认这个 Range 慢/边缘没缓存
```

**前端侧**（新增 `utils/playbackProbe.ts`，每次 seek / 起播各一行）：
```
前端 [video] seek→198.5s 窗口=8.0s 起播=4.2s 饿住=6次 最低缓冲=0.2s 帧率=18.4fps 丢帧=3/184 已缓冲=6.0s
```
· **起播**：从按下进度条到**第一次真的出画**（用户感知的"卡住"就是这个数）；
· **饿住**：窗口内 `waiting` 次数（低帧率那段时间里画面断了几次粮）；
· **帧率/丢帧**：`getVideoPlaybackQuality()` 的**增量**（不是累计值，一眼能看出那 8 秒有多惨）。

⇒ **判读法**：代理那行难看 ⇒ 病在 CDN/链路（MSE 只能靠降档兜）；
代理那行漂亮而前端帧率难看 ⇒ 病在浏览器取数/解码（MSE 直接解决）。

## 二、为此新开的一个端点（以及它的三条边界）

前端的量测行要落进后端日志，才能和代理那行在同一个文件里 —— 于是有了
`POST /settings/client-log`（前端 `api.clientLog`）：

| 边界 | 做法 |
|---|---|
| 不能变成"任意写日志" | 只收 `[video]` / `[player]` / `[media]` 开头（`CLIENT_LOG_TAGS`），否则 400 |
| 不能被拿来刷盘 | 单行 ≤400 字；**每进程每分钟 ≤30 条**，超了丢弃（回 `dropped: true`，不回错） |
| 不能伪造级别 | 固定 `logger.info`，**不接受调用方指定**（否则前端一句话就能把日志刷成 error） |
| 不是公开端点 | 没进 `PUBLIC_EXACT` ⇒ 要会话 token（本机任何进程都能往日志里写字是不行的） |

## 三、MSE 立项（评估已在计划里，此处只留结论与指针）

方案：`docs/plans/bili-mse-kernel-execution.md`（已列进 `docs/TODO.md` §1 第一条）。
可行性**用真数据验过**，不是纸上推算：

```
ftyp 36B | moov 912B | sidx 680B | moof 1,900B | mdat 1,567,961B
sidx: 24 字节头 + 54 条 12 字节条目，条目 = [段字节数 ≈1,569,861][时长 80,000 ticks = 5.0s][SAP]
      54 × 5s ≈ 270s ≈ 片长 265s ✓ 且每段自带关键帧
```

⇒ **有时间→字节的索引、段长 5 秒、段首关键帧**；codec 字符串 `playurl` 直接给
（`avc1.640033` / `mp4a.40.2`），正好是 MSE 需要的。收益/成本/风险/拓展性见计划文档 §二–§四，
分期 S0（诊断，已完成）→ S1（1 天 spike）→ S2（内核 1–1.5 天）→ S3（ABR + 收尾），
并写明了**三条停止条件**（`isTypeSupported` 为假 / spike 里不比现在快 / 5 秒粒度太粗）。
