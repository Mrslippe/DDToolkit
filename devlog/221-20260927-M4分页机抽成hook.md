## 一、搬了什么

| 进 hook | 留在页面 |
|---|---|
| `posts` / `total` / `page` / `loadingMore` / `loadMoreError` 五个 state | **取数 effect（E11）** —— 它是分页机与「场景切换机 / 筛选机」的交汇点（播种守卫 `seededPostsKeyRef` / `AbortController` / `refreshTick` 边沿） |
| `listScrollRef` / `sentinelRef` 两个 ref | `loading` / `error` 两个**外部**态（由 E11 写，喂给哨兵当门） |
| 三条 effect：回顶钮复位 · 用户意图重置即回顶 · 无限滚动哨兵 | 「谁在什么时机 `setPage(1)`」 |
| `hasMore`（派生）+ `showTop` + 三个入口（`loadMore` / `retryLoadMore` / `onScrollTop`） | |

⇒ 依赖方向仍是**单向**：页面 → 分页机。`setPage` 是唯一翻页口，页面的 6 个筛选 handler
与场景提交/失败路径照旧调它（`setPage(1)`）—— 这正是第二刀留下 `setPage(1)` 那一行的兑现：
两台 hook 之间零耦合。

## 二、两条"逐字保留"，一条"必须如实交代"

**逐字保留**：① 回顶 effect 的依赖数组（`[typeFilter, searchKw, dateFrom, dateTo, deletedOnly,
archived, accountKey, listActive]`）与哨兵那条的 13 项 —— 它们不是风格，是「什么时候回顶 /
什么时候重建观察者」的实现方式（P6-1 切筛选、P8-7 切账号都算"用户意图重置"，必须**立刻**
回顶、不等重取完成）；② `listActive` 取的是**已提交**的 `scene.view`（不是本地的 `view`）。

**必须如实交代**：三条 effect 原来排在 E11 **之后**，现在随 hook 调用点排到它**之前**。
不是随手挪的 —— E11 的依赖数组里有 `page`，而依赖数组是**渲染期求值**的 ⇒ 分页机的调用点
必须在 E11 之前，否则直接 TDZ（实测第一次尝试就撞上：见 §四）。逐条核过：三条都不读 E11 的
产物（哨兵那条只把 `loading`/`error` 当门），回顶那条只碰 DOM 滚动，`setPage` 的消费者在
下一轮 render 才反应 ⇒ 顺序无关。

## 三、判据（`hooks/usePostPagination.test.tsx`，14 条）

假 `IntersectionObserver`（留下"建了没有 / 断了没有 / rootMargin 多少 / 观察的是谁"），
`Element.prototype.scrollTo` 打桩（jsdom 没实现元素滚动 —— 不打桩这条判据只能测到"没抛异常"），
`data-*` 当探针读状态。四组：

- **① `hasMore`**：不足一页 ⇒ 还有更多；**载满即到底**（否则哨兵一直空转请求）。
- **② 哨兵**：可加载时建观察者（`root` = 滚动体、`rootMargin='600px 0px'`、观察哨兵本身）；
  进视口 ⇒ `setPage(p+1)`；**不可加载的六种情况一个都不建**（首页 loading / 正在追加 / 首屏错误 /
  追加错误 / 已到底 / 非列表视图）；追加失败 ⇒ **老观察者被断开**（留着会在视口里反复翻页）；
  重试只清错误位（清完哨兵重建、仍在视口就自己续载，**不另开翻页路径**）；卸载断开（不泄漏）。
- **③ 回顶**：切账号 / 切任一筛选字段 ⇒ 立刻回顶；**同参数重渲染不许回顶**（反向判据）；
  不在列表视图不回顶；回顶钮 400px 边界（400 不算"超过 400"）。
- **④ 显式「加载更多」**：清掉上一次追加失败提示 + 翻页。

**写测试时发现两处"原语义与直觉不符"，都按原样保留并写进用例**：
1. **挂载那一次本来就会回顶**（effect 首次运行），所以三条回顶用例都以"挂载后的调用次数"为基线；
2. 回顶钮复位那条 effect 判的是**"新视图是不是 list"**，不是"离开了 list" ——
   离开列表时那个钮根本不渲染，所以值留着无害。**没有顺手"修"它**（搬位置不改行为）。

## 四、反向验证（五刀，全部精确报红）

`_tmp_reverse_*.py` 逐字节改写 + 还原（§6.15）：

| 刀 | 改法 | 期望红的用例 | 结果 |
|---|---|---|---|
| A | 哨兵门控漏掉 `loading \|\| loadingMore` | 不可加载的六种情况 | ✅ 首页在加载那一档建出了观察者 |
| B | 回顶 effect 依赖里塞 `showTop` | 回顶钮 400px 边界 | ✅ 浮起来就被自己按回去（`top` 恒为 0） |

| D | 回顶阈值写成 `>=` | 400 不算"超过 400" | ✅ |
| E | 回顶 effect 干脆不带依赖数组 | 同参数重渲染不许回顶 | ✅ 调用 3 次 vs 期望 1 次 |

⚠️ **刀 B 我预判错了**：以为它会打中"同参数重渲染不许回顶"，实际打中的是"回顶钮浮现"那条 ——
把 `showTop` 列进依赖后，`setShowTop(true)` 自己触发的 effect 立刻又 `setShowTop(false)`，
按钮永远浮不起来。**判据没错，是我的预判错**；于是补了刀 E 专门喂"每次渲染都回顶"这个形态，
证明那条反向判据确实能红。这条记下来是因为：**"能红"必须逐条验，别拿"反正红了"当证据。**

## 五、eslint 又卡了一次（与第二刀同源，但这次没法靠"别搬"绕开）
