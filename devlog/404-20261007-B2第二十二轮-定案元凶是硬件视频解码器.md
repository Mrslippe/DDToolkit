# 404-20261007-B2第二十二轮 定案：元凶是硬件视频解码器

`--disable-accelerated-video-decode`（**完全不动** DirectComposition）跑完，日志干净利落：

```
02:32:01  [video] 全屏诊断模式=surface（真全屏 + 铺满，但保留透明的窗口底色）
02:32:31  start 全屏=29/30秒  表面=transparent  **硬解=无**
          尺寸=1920x1080→1920x1080  解码=28.8fps 提交=28.8fps **呈现=28.7fps**
          丢帧=**0/864 (0.0%)**   抖动=11次（抖峰 0.09s）
```

**整窗零丢帧，一个 `转折` 行都没有**（从头到尾没翻过坏）。用户口径也一致：「不卡了」。

## 三条 flag 的对照，到此收敛

| flag | 硬解 | DC | 全屏丢帧 |
|---|---|---|---|
| 无（基线） | 有 | 开 | **10~13%** |
| `--disable-direct-composition` | 无（副作用） | **关** | **0.1%** |
| **`--disable-accelerated-video-decode`** | **无** | **开** | **0.0%** |

⇒ **DirectComposition 不是元凶**（关掉它有效只是因为顺手把 GPU 视频路径一起关了）；
**元凶是硬件视频解码那条路**。

与 `devlog/387` 对得上：同一台机器上 **Edge 播同一支视频流畅，而那一轮 Edge 的 `硬解=无`** ——
当时把 `硬解=` 只当成一条待查线索，现在它是答案本身。

## 这条线为什么走了二十多轮

不是因为线索少，而是因为**"用户说的卡"有四种完全不同的形状**（`devlog/385`/`396`），
而每一种都要先造出**能直读它的口径**：

1. 量到"停顿"（>100ms 的缝）⇒ 真机一次都没出现；
2. 改量"节拍"（rVFC 间隔 vs 中位数）⇒ 出现抖动，但全屏/窗口都有，**不是病灶**；
3. 改量"每秒丢帧"⇒ 终于出现 **稳定的 4 帧/秒**，可它跟"取数据/灌数据"**同时出现**
   ⇒ 连着三轮把数据通路当嫌疑人（`devlog/390`~`393`）；
4. 直到**把日志里现成的窗口拿来当对照**（`devlog/394`：内核工作量逐秒相同、结果 13.0% vs 0.0%），
   才把数据侧排掉，转向"呈现路径"；
5. 再**把一个动作翻的三个变量拆开**（`devlog/399`~`402`），才落到解码路径上。

⇒ 值得记住的不是结论，而是**"先找对照窗、再拆复合动作"这两步**（已进 `DEV-LOOP` §6 / `PROBE.md` §6.24）。

## 机理：哪些是量到的，哪些是推的

**量到的（这些是事实）：**

1. **丢在"提交"与"上屏"之间**：三口径 `解码=29.0 → 提交=29.0 → 呈现=25.8` ——
   解码器出帧正常、也交给了合成器，是**合成/呈现那一步把它们丢掉的**
   （Chromium 的呈现器判定"这一帧赶不上这一拍"时不补显示、直接丢）。
2. **是"零星漏"不是"冻住"**：`停顿次数=0`、rVFC 最长间隔 0.05~0.09s ⇒ 没有 >100ms 的洞，
   丢的是单帧（33ms 变 66ms），而且**节奏很稳（每秒正好 ~4 帧）**。
3. **必须"操作系统全屏窗口"才会出现**：最大化窗口（有任务栏 ⇒ 不占满屏）**是流畅的**，
   哪怕它的合成表面同样是 1920×1080、画面同样只有 `678x381`。
4. **必须硬件解码才会出现**：关掉它 ⇒ `0/864 = 0.0%`。
5. **进全屏后要等 2~3 秒才出现**，而**一次 seek 能把它清掉**（且能保持）。

**推的（没有直接证据，别当结论用）：**

最自洽的一条：**全屏窗口会被 DWM 提升到"独立翻转 / 直接扫描输出"（independent flip / MPO）
那条路**——那条路上窗口的交换链不再由 DWM 合成，**帧必须赶在翻转截止时间之前就绪，晚了就是丢**；
而窗口态/最大化态下 DWM 总是合成，**晚一拍的帧照样显示**（只是晚一点），所以不记丢帧。
这条能一次解释四件事：最大化不卡（不占满屏 ⇒ 没资格被提升）、进全屏 2~3 秒后才坏
（DWM 要等窗口"稳定"下来才提升，这正是一个秒级的 settling）、**seek 能治好**（重新合成 ⇒ 被降级回来）、
以及 `--disable-direct-composition` 也有效（换掉 DC 呈现 ⇒ 同样提升不上去）。

⚠️ **但它解释不了"为什么硬件解码是必要条件"** —— 这一段**没有证据**，只有几个候选：
硬件解码交给合成器的是一张**解码器池里的 GPU 纹理**（池子有限、要过一手），
而软解交的是随时可用的系统内存位图；在全屏那条更紧的截止时间下，
前者更容易赶不上。**这是猜的**，别写进任何"因为…所以…"的句子。

⇒ **想验的话有一条直路**：用 **PresentMon**（微软的免费工具）跑一次应用，
看它报的呈现模式是不是在进全屏 2~3 秒后变成 `Independent Flip`、seek 之后退回去。
**在那之前，上面第 3、4、5 条是事实，"独立翻转"是假设。**
