## 一、表与口径

`profile_cards`（迁移 `f006`，`MIGRATION_HEAD` 同步 `f005 → f006`，第 **12** 张表）：

| 列 | 说明 |
|---|---|
| `card_key` | **实例 id**（内置卡 = kind）。唯一键取 `(vtuber_id, card_key)` 而**不是** `(vtuber_id, kind)` —— P3 的自定义卡允许同 kind 多实例，这样 P3 不用再改结构 |
| `kind` | 渲染类型（前端卡片注册表认它）。**后端不校验取值**：扩展点在前端，后端不该维护一张"合法 kind 列表" |
| `x/y/w/h` | 12 列网格里的格位，与前端 `components/profile/layoutModel.ts` **同一口径** |
| `config_json` | 留给 P3 的卡片自定义配置（P2 不写） |

索引 `ix_profile_cards_vtuber (vtuber_id, y, x)` 覆盖"按 V 取出 + 按阅读顺序排"。

## 二、写入口径：整版替换 + **报错不夹取**

- `ProfileCardRepo.replace_all(vtuber_id, cards)`：一个事务里 delete + insert，失败整体回滚
  —— 不会留下"删了旧的、没写新的"的半版布局（那在界面上就是"卡片全没了"）。
  选整版替换而不是逐卡 upsert：前端是"编辑一整张画布、松手存一次"，逐卡 diff 只会把
  前端的临时态泄漏到后端。
- **越界 / `card_key` 重复 / 超过 50 张 → 422**，不做静默夹取。夹取会把前端的排布 bug
  写进库，用户下次打开只会觉得"卡片自己动了"，且**查不出是谁改的**（这正是本仓最忌讳的
  静默失败）。前端的 `clampCard` 负责"拖到界外时自己收回来"，后端负责"收到不合法的就拒"。
- `GET` 空数组 = **还没排过**（不是错误）：前端据此用 `defaultLayout(注册表)` 渲染。
  默认排布属于**展示口径**，卡片注册表在前端 ⇒ 服务端不替用户决定默认长什么样。

## 三、外键陷阱：`purge` 必须同步（本批唯一有数据风险的改动）

`profile_cards` 挂 `vtubers.id` 外键，而 `foreign_keys=ON` ⇒ 删 V 时若没清这张表，
`DELETE FROM vtubers` 会被外键挡下、**整次事务回滚**（devlog/040 那次事故的形态：
"解除订阅一直失败，日志里只有『连带清除帖子 N 条』"）。所以 `services/purge.py::purge_vtuber`
补了一行 `profile_cards`，并有一条用例专门守它（`test_purge_vtuber_clears_profile_cards`：
purge → commit → `db.delete(v)` 必须成功）。

## 四、护栏（`tests/test_profile_cards.py`，15 条）

| 组 | 钉什么 |
|---|---|
| ① Repo | 整版替换（第二次只留新的一版，不留残行）/ 空列表清空 / 按 `(y, x)` 排 / 按 V 隔离 / DB 唯一键兜底 |
| ② 路由契约 | 空布局 = `[]`（不是 404）/ V 不存在 404 / PUT→GET 往返（服务端重发 id）/ **越界 422 且库里不留脏行** / 重复 key 422 / 四个范围各 422 / 超过 50 张 422 |
| ③ 外键 | `purge_vtuber` 之后删 V 必须成功（漏清就红）+ 不留孤儿行 |

**两个测试基建坑（都留档在用例注释里）**：

1. **必须用文件库**：第一版用 `sqlite://` 内存库，而 TestClient 把请求丢到另一个线程跑
   ⇒ 内存库每连接一份、那个线程看到的是**空库**（`no such table: vtubers`）。改成
   `sqlite:///./test_profile_cards.db` + `StaticPool`/同款写法，并**开外键 PRAGMA**
   （不开的话第 ③ 组根本测不出事故）。
2. **`app.dependency_overrides` 只能"存旧值 → 换新值 → 还原"，不能 `clear()`**：
   第一版在 teardown 里 `clear()`，而 `tests/test_vtuber_api.py` 是在**模块导入时**装好覆盖的
   ⇒ 本文件跑完把它的覆盖一起清掉，那个文件 **35 条用例当场全红**。

## 五、顺带修掉一条**既有的测试卫生问题**（7 条用例连带变红的真凶）

本批加完用例后，`tests/test_services.py` 里 7 条"手动/自动让位"用例开始红，日志是
`FetchResult(success=0, ..., details=['上一次抓取仍在进行中，已跳过'])`。用临时夹具
（每个用例结束检查 `scheduler._fetch_lock.locked()`）定位到：
**`tests/test_real_fixtures.py::test_index_origin_row_is_not_adoptable_via_pool_path`
用 `with TestClient(app)` 跑了应用 lifespan ⇒ 启动调度器**，后台轮次抓住 `_fetch_lock`
不放，泄漏给后面所有锁用例。修法：那个用例改回 `TestClient(app)`（**不**进 lifespan）——
它只要 HTTP 层，404 在碰库之前就返回了。留档在用例注释里。

> 这条与本批功能无关，但它把"R37-P2 引入了 bug"的假象摆在我面前半小时：**先做对照实验**
> （stash 掉本批改动跑同一子集）才发现 stash 那次失败的其实是 `MIGRATION_HEAD=f005` 撞上
> 已被探针迁到 f006 的开发库 —— 对照实验本身也有坑（**别在改过迁移头的仓库里做 stash 对照**）。
