# 063-20260913-弹幕取数从"开弹窗"路径拆出：两段式加载 + 10 分钟缓存

> 承接 devlog/062 的遗留问题：上游慢时"最坏要等 93s 才知道是上游没响应还是只是慢"。
> 本批把它**治到根上**：详情端点只回本地库数据（弹窗秒开），第三方取数走独立端点，
> 弹幕/直播动态两格各自 loading、可就地重试，并加 10 分钟进程内缓存。
> 无迁移；**有一个契约变更**（详情响应不再带 danmaku/metrics/events，新增一个端点）。

---

## 一、问题：93s 不只是"等得久"，而是**整窗被拖住**

`30 + 1 + 30 + 2 + 30 = 93s`（单次 30s 超时 × 3 次 + 退避 1s/2s；summary 与 events 并发，
所以端点最坏是 93s 而不是 186s）。更要紧的是详情端点**一个响应扛着三段内容**，
而弹窗里 `detail.loading` 同时门控弹幕段与"直播动态"段：

| 弹窗内容 | 拆之前 | 拆之后 |
|---|---|---|
| 时间 / 分区 / 收益 / 峰值在线 / 弹幕数 / 分类 | 立刻（库里快照） | 立刻 |
| 观看 / 点赞 / 打赏 / 互动 / 排名 | 上游回来后才有（期间**无声缺席**） | 上游回来后才有（期间显示「正在取…」） |
| 弹幕段（词云 / 五态文案） | 上游回来后才知道显示哪一种 | 独立 loading，**不影响其余内容** |
| 直播动态 | 同上，期间「加载中…」 | 独立 loading |

也就是说：用户**无法区分**"上游慢但会回来"与"上游根本没响应"，而且连不依赖上游的内容
也一起等。

**不能靠砍预算解决**：上游慢是真能等到的（实测 15.6s 那次重试到第 3 次才成功），
砍成 20s 预算会把"慢但有效"误杀成"失败"。所以改的是**取数的位置**，不是超时值。

## 二、改法

| 位置 | 改动 |
|---|---|
| `app/services/live_upstream.py`（新） | 并发取 summary + events + **进程内缓存**：键 = `live_id`，TTL 10 分钟，上限 64 条（插入顺序淘汰）；**只在拿到 summary 时写缓存**（失败不缓存 —— 用户点重试应当真的重试） |
| `GET …/live-sessions/{live_id}`（详情） | **删掉全部上游调用**，只回本地库可推导内容（场次 + 分类推断 + `analysis` 预留）；顺手从 `async def` 改回 `def`（已无 await，交给线程池跑，别让 SQLite 查询占事件循环） |
| `GET …/live-sessions/{live_id}/upstream`（新） | 返回 `{danmaku, metrics, events}`（schema `LiveUpstreamOut`）：拿到摘要 → `upstream`/`upstream_absent` + 指标 + 事件；**没拿到 → `wc_status='fetch_failed'`**；非 danmakus 来源 → `no_danmaku` 且**不请求网络** |
| `app/schemas/vtuber.py` | `LiveSessionDetailOut` 去掉 danmaku/metrics/events；新增 `LiveUpstreamOut` |
| `frontend/.../live/useLiveUpstream.ts`（新） | 取数状态机：随 `liveId` 变化自动重取、防回写 seq、失败落 `fetch_failed`、`elapsed` 秒表（供"已等 Ns"文案）；69 行（总行数） |
| `frontend/.../live/LiveSessionDialog.tsx` | 弹幕段/动态段改用 hook 状态；指标行未回来时显示「正在取…」；`>8s` 文案变「上游响应较慢，仍在重试…（已等 Ns）」；**重试按钮按来源分流**（自建失败重取自建、上游失败重取上游） |
| `frontend/.../dev/probe.ts` | `?probe=archive` 原先"点格子 → 定长等 3.5s"，现在改成**等那两格落地**（轮询上限 15s）—— 拆完多了一个异步跳，定长等待会量到"正在取上游弹幕…"的空态（正是 058/061 记过的"看起来通过但等于没验"） |

### 语义上刻意保留的两条

1. **不自动回退**（用户 D1 不变）：`upstream_absent` 仍只给「用弹幕自建」按钮，用户点了才拉 v3 原始弹幕。
2. **失败与"没有"继续分开**：`fetch_failed` / `no_danmaku` / `upstream_absent` / `upstream` / `self_built`
   五态一个没少；取数请求本身没通（HTTP/网络）时弹幕段写「弹幕数据未取到（上游取数请求没通；可重试）」。

## 四、已知代价与未做

- **缓存只活在进程内**：重启后第一次打开某场次仍要打上游（这是 D3"暂不落库"的直接后果）。
- 缓存没有"强制刷新"入口：成功结果在 10 分钟内重复打开都走缓存（这正是想要的行为）；
  失败路径不写缓存，所以「重试」不会被缓存挡住。
- 前端**没做请求取消**：切场次时旧请求仍在跑（`seq` 只保证不回写）。后端有缓存兜底，
  这一条留着（AbortController 会牵动 `api.ts` 的 `request()` 改造）。
- 未给自建词云（v3 原始弹幕）加时间预算 —— 理由见 devlog/062 §四（截断会系统性丢掉
  下播前的高频词），仍留在 `docs/TODO.md` §1.1（未完成项 · 可立刻动手）。

## 五、教训

1. **"慢"与"挂"分不清，往往不是文案问题，是架构问题**：只要一个响应里混着"本地就有"和
   "要问第三方"两类数据，它就是拿最慢的那部分给整体定速。拆开之后，"等待"才变成可解释、
   可局部重试、可缓存的东西。
2. **拆之后要回头修探针**：定长 `sleep` 的探针在异步跳变多后必然量到空态 ——
   探针要"等状态落地"，而不是"等一个猜出来的毫秒数"。
3. **缓存是拆分的配套**：没有缓存的拆分只是把一次长等待换成多次短等待；
   有了 10 分钟缓存，重复开关弹窗才真的不再碰上游。
