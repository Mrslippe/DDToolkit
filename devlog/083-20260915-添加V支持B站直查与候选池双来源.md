# 083-20260915-添加 V 支持 B 站直查（候选池 + 在线检索双来源）

> 用户原话（R11）：
> 「现在添加 V 只能从候选池中添加，但是这样很多新 V 就没办法得知了，所以添加 V 功能应该
> 除候选池同样也可以直接从 b 站中直接获取，不论是 uid 还是名称模糊搜索，先给我一个实现方案，
> 确认后再执行」
>
> 方案确认时用户对我给的四个推荐项**全部点头**：
> ① B 站检索 = **显式触发**（回车 / 按钮，不做按键防抖直连上游）；
> ② 点结果行 = **直接收录**（不插一步"预览卡"）；
> ③ 本地检索 = **候选池 csv + `thirdparty_vtubers` 索引合并**；
> ④ 翻页**最多 3 页**。
>
> 本批**有后端改动**（新端点 + adopt 放宽 + 新服务模块），前端把浮窗从单来源改成双来源。

## 一、为什么要放宽「只能从池内加」

候选池是 `vtubers.csv`（9482 行，快照式名单）。它决定了两件事：

1. **池子里没有的新 V 根本加不进来** —— 名单是快照，新出道的 V 不在里面，
   而"等名单更新"不是用户能自己解决的事；
2. 池子里的**名称是规范的**，所以池内路径一直是"客户端给 uid → 服务端回填名称"，
   服务端从不信客户端给的名称 —— 这条安全边界这一批**必须保留**（见 §三）。

所以这一批做的不是"多一个搜索框"，而是**多一条收录通道**，并把那条通道的信任模型补齐。

## 二、B 站检索：recipe 是实测出来的，不是猜的

`wbi/search/type`（`https://api.bilibili.com/x/web-interface/wbi/search/type`）这一批踩了三次坑，
每一次都会让**"上游明明能查到，程序却说没有这个人"**：

| 坑 | 现象 | 结论 |
|---|---|---|
| 缺搜索页请求头 | `code=0` 但 `result` 为空 —— **静默 0 条**，看着像"没这个人" | 必须带搜索页 `Referer` / `Origin` / `Accept` / `Accept-Language` + 浏览器 UA |
| 首次冷调 | `code=-1200`（"被降级过滤"） | 归为 `upstream_degraded`，**如实报给用户**，绝不退化成"没有" |
| 纯数字关键词 | `keyword=1265680561`（一个真实 uid）→ **0 条** | 搜索接口**搜不到 uid**，uid 必须走 `acc/info` 精确通道 |
| **未登录**（2026-09-15 更正，见 §十） | `nav` 回 -101「账号未登录」→ WBI 取不到密钥 | 两条路径**都需要 B 站登录态**；失败必须给 `not_logged_in` + 提示，不是 500 |

实测（本机 2026-09-14/15）：带齐搜索页请求头后 `code=0`、20 条/页、`numResults=1000`、
`numPages=50`；2026-09-15 复核（登录态、真打上游）：`塔菲` → **20 条**、`uid=1265680561`
→ 1 条「永雏塔菲」。可用字段：`mid` / `uname` / `usign` / `fans` / `videos` / `upic` /
`level` / `is_live` / `room_id` / `official_verify.desc`；`uname` 里可能夹
`<em class="keyword">` 高亮标签（`strip_highlight` 负责剥掉并 `html.unescape`）。

**流量预算**（写在 `app/services/bili_search.py` 顶部，改之前先读）：

- `MIN_INTERVAL = 0.8` —— 上游调用串行间隔（**排队等，不在锁里 sleep**，沿用 devlog/076 的占时隙写法）；
- `MAX_PER_MINUTE = 20` —— 硬上限，超了直接返回 `rate_limited`（**不发请求**）；
- `CACHE_TTL = 300` / `CACHE_MAX = 64` —— `(kw, page)` 结果缓存 5 分钟；
- `MAX_PAGE = 3` —— 翻页封顶（用户决策④）。

## 三、信任模型：客户端给的名字**永远不算数**

新增的收录通道放宽的是"**池外也能加**"，不是"客户端说什么就是什么"：

```
POST /vtuber/adopt  { platform, platform_uid, source }
  ├─ source is None / 'pool'  → 必须在池内（find_in_pool），名称回填池内规范名
  └─ source == 'bilibili'     → platform 必须是 bilibili
                                且**服务端自己**打一次 acc/info 校验
                                （成功才拿上游返回的 uname 建库；失败 → 404 + 上游原因）
```

三条都是**测试反证过**的（`tests/test_vtuber_api.py::test_adopt_from_bilibili_requires_server_side_verification`）：
把校验换成硬编码名称，用例立刻红；恢复后绿。池内命中**不重复**打上游（那是白花的预算）。

其它平台走池外路径直接 **400** —— 微博没有对应的"服务端可校验"接口，不给这条口子。

## 四、路由名踩的坑：`/vtuber/bili-search` 会被 `{vtuber_id}` 吃掉

第一版路由叫 `GET /vtuber/bili-search`，实测 **422 `int_parsing`**：

```
/vtuber/{vtuber_id} 先注册 → "bili-search" 被当成 vtuber_id → int 解析失败
```

改成**两段路径** `GET /vtuber/bili/search`（与 `/vtuber/pool/search` 同形）后正常。
这条写进了端点 docstring —— 下次加子资源端点别再踩。

## 五、前端：两个来源，**触发方式刻意不同**

`AddVtuberDialog` 从单来源改成双来源，但**没有**把 B 站检索接成"输入即搜"（用户决策①）：

| 来源 | 触发 | 打上游？ |
|---|---|---|
| 本地候选（池 csv + `danmakus` 索引） | 输入防抖 250ms（沿用旧行为，AbortController 防竞态） | **否**（本地表 + 本地 csv） |
| B 站在线检索 | **回车 / 点「搜索 B 站」/ 点「加载更多」** | 是（受上面那套预算约束） |

界面上的四条硬约定（都在探针断言里）：

1. **纯数字（≥5 位）= UID 直查**：按钮文案换成「按 UID 添加」（判定与后端 `looks_like_uid` 同口径）；
2. `in_library=true` 的行**置灰 + "已订阅"**（B 站结果是实时的，本地接口已剔除已入库项，
   只有在线结果需要判）——标错的代价是"看着能加、点了 409"；
3. 上游失败（风控/降级/网络）**原样展示后端 `hint`**，绝不显示成"没有这个人"；
4. 结果区用 `OverlayScroll`（全站约定：不出现原生滚动条，否则出现/消失会挤动布局——
   旧版这里是 `overflow-y-auto`，一直没人量过）。

纯逻辑（合并去重、粉丝数文案、来源徽标）抽到 `frontend/src/utils/addVtuberSearch.ts`，
因为**判错了界面不会报错**：本地优先去重、`followerLabel` 的万粉折叠与 0 不显示、
`inputLooksLikeUid` 与后端同口径，这四条各有单测。

## 六、新增探针模式 `--add-v`（本轮唯一的新护栏）

这个浮窗此前**完全没有探针覆盖**，而这一批恰好给它加了"会产生上游请求"的东西。
所以新模式的断言不是"好不好看"，而是三条**行为**：

| 断言 | 挡的是什么 |
|---|---|
| 敲键只打 `/vtuber/pool/search`，`/vtuber/bili/search` **必须 0 次** | 决策①被改回"输入即搜"时探针会红（否则风控预算被无声烧掉，界面看不出异常） |
| 结果行 `elementFromPoint` 命中测试 + 行不可置灰 | "看得见却点不着"（这类浮窗出过 pointer-events 被祖先吃掉） |
| 纯数字输入 → 按钮变「按 UID 添加」且可点 | uid 不走搜索接口，用户得能从按钮上看出来 |

探针**绝不点结果行、绝不点「搜索 B 站」**：前者是真收录 + 真抓取，后者是真上游调用。
关键词也不猜数据 —— 先问 `/vtuber/pool/search`，命中才做行级断言，问不到就打印
`[跳过] 行级断言`（数据形态问题不冒充回归）。

## 八、顺带查清的两件事（都不是本批代码造成的）

### 8.1 顶栏断言的**假失败**：外部同步被误判成"自动节拍占顶栏"

跑全量探针时三档宽度一起报：

```
- @1100 顶栏：只有自动节拍在跑却亮起了事件容器（text='正在同步7 个主账号的第三方数据'）
```

采样已经写明 `post=True/auto=True acc=True/auto=True manual=False` —— 也就是
"自动档在跑"。而 `_assert_topbar` 的旧口径**只看 post/account 两位**，于是把**外部第三方
数据任务**点亮的顶栏当成了自动节拍占顶栏。但顶栏**按设计**就是要显示它：

```ts
// TopBar.tsx
const busy = accVisible || postVisible || (status?.external?.running ?? false)
} else if (status?.external?.running) { statusText = `正在同步${status.external.label}` }
```

而探针**起后端后这个任务往往正在跑**（本轮 7 个主账号回填）——所以这是探针的假失败，
不是回归。修法：采样补 `externalRunning`（`dev/probe.ts`），断言在外部任务在跑时跳过
（"亮灯有两种可能，归因不了就别断言"），并把它打进采样打印行，便于一眼看出为什么跳过。
修后 `--hero-expect` 三档 **问题=0**、exit 0。

### 8.2 日历签名"漂了"：**跨天必然漂**，与代码无关

`--archive --calendar-expect fb75217e…`（9-13 记的基线）本轮实得 `48519bae…`。
但**同日连跑两次都是 `48519bae…`**（稳定），且原因能从代码上直接读出来：

```ts
// LiveCalendar.tsx：无场次的格子 —— 今天以前 =「休息」；今天及以后 =「待定」
else if (c.key < todayKey) badge = '休息'
```

9-13 记录基线时，13/14 两格还是「待定」；9-15 再看，它们已经翻成「休息」/有场次
（13 号那场《暴雪嘉年华一起看》01:21 就在 dump 里）。**跨天比对 `--calendar-expect`
必然失败**，这不是漂移检测能力的问题，而是这条签名本来就含"今天"这个输入。
已把这个坑写进 `docs/TODO.md` §6.2 的基线说明（连同 9-15 实测值）。

## 十、⚠️ 更正：「不需要登录」是**测错了**（提交后才抓到，同批修掉）

写本批时我在模块 docstring 与本文 §二里都写了"**不带 cookie 也能用**（所以不需要用户登录）"。
提交之后做**入库前的真机冒烟**（空数据目录 + 全新进程）时被证伪：

```
Exception: 获取WBI密钥失败: 账号未登录
  at app/services/wbi.py:48 ← nav 接口回 -101
  ← bili_search.search_users → wbi.sign_params
```

**真相**：搜索接口本身确实不校验 cookie，但 `wbi/search/type` 要 `w_rid` 签名，而签名密钥
（`img_key`/`sub_key`）只能从 `x/web-interface/nav` 取 —— **`nav` 未登录直接回 -101**。
所以：

| 场景 | uid 直查（`acc/info`） | 名称模糊搜（`wbi/search/type`） |
|---|---|---|
| 已登录（本应用为抓取本来就要登录） | ✅ 实测 1 条「永雏塔菲」 | ✅ 实测 20 条 / `numPages=50` |
| 未登录（空数据目录 + 全新进程） | ❌ WBI 取密钥失败 | ❌ 同一处失败 |

**为什么第一次会测错**：当时那句结论是在一个 **WBI 密钥已缓存**（`wbi._cached_keys`，30 分钟 TTL）
或数据目录里带着已登录 `.env` 的环境里得出的 —— 于是"没有 cookie"这个前提根本没成立。
**教训**：凡"××情况下也能用"的结论，复现口径必须写清（空数据目录 + 全新进程 + 不预热缓存），
否则测的是"缓存还在"而不是"不需要登录"。

同一批修掉的东西（都不只是改文案）：

1. `search_users` 的 `await wbi.sign_params(...)` 原来在 `try` 之外 ⇒ 未登录时**异常冒到端点变
   500**、前端只能弹一句栈式英文。现在映射成 `error='not_logged_in'` + `LOGIN_HINT`
   （"请先在顶栏登录 B 站再试"）；非"未登录"的签名故障归 `upstream_error`，不误导成"去登录"。
2. `exact_user` 的 `acc/info` 同样是签名接口 ⇒ 同样兜住；`relation/stat` 失败**不拖垮**整次直查
   （名字已经有了，粉丝数记为 0）。
3. `POST /vtuber/adopt` 池外分支：原来"实查失败"一律 404 —— 那会把"你没登录"说成
   "B 站没有这个 UID"。现在只有 `not_found`/`bad_uid` 是 **404**，未登录/网络/风控是 **503** + 原因。
4. 用例 +5（`test_bili_search.py` 4 条 + `test_vtuber_api.py` 1 条），其中未登录那条**反向验证过**：
   把 `try/except` 去掉 → 立刻 FAILED（异常穿透），恢复后绿。

> 这一条正好是本仓反复出现的那个模式：**上游"安静地失败"与"真的没有"长得一模一样**
> （先是缺请求头的静默 0 条，这次是未登录时报成"查不到"）。凡是能安静失败的地方，
> 都要有一条"如实报错"的路径，并且**用空环境复现一次**。
