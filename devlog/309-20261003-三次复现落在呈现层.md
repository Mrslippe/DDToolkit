# 309-20261003 三次复现全部落在"呈现层"：数据够、解码够、画面被挂起

> 用户口径：「复现了三次」。三次**全部**抓到，而且都落在同一个判定上。
> 这是整条线（`299`–`308`）第一次拿到"病在哪一层"的硬证据。

同时刻的代理日志：`首字节 131–235ms`、`均速 0.59–6.71MB/s`、**没有一条慢速告警**。

## 二、这些数字把三个嫌疑人一次性排除掉两个半

| 嫌疑人 | 该看到的证据 | 实际 | 结论 |
|---|---|---|---|
| CDN / 本机代理 | 缓冲见底、`卡帧>0`、代理行慢 | 缓冲 **2.6–19.4 秒**、`卡帧=0s`、代理全程健康 | **排除** |
| 解码解不动 | `空转` 多、`丢帧` 多、解码帧率低 | 解码 **30–75fps**、`丢帧 0–1` | **排除** |
| 呈现 / 合成 | 解码正常但呈现低、且出现成秒的空洞 | 呈现 **7–15fps**、最长停顿 **3–4 秒** | **就是它** |

尤其第 2 次：**缓冲 19.4 秒**（数据多到用不完）、解码 36.8fps，而呈现只有 13fps、
中间停了 3 秒 —— 数据和解码都没有任何可指责的地方。

## 三、形状指向"浏览器把画面挂起了"

曲线里那一段最有信息量：**第 1 秒解码 153 帧**（seek 后的追赶式解码），
**第 2–5 秒解码 0 帧**，而缓冲一直有 5–6 秒 ⇒ 那几秒里**解码器根本没被要求出帧**，
而不是"出不来"。加上 `卡帧=0s`（媒体钟一直在走）与**音频全程正常**，
这就是 Chromium 对**"页面不可见"**的标准行为：**音频继续、视频挂起**。

"不可见"在 Windows/WebView2 上有三种来源，用户侧看起来都像"画面卡住"：
① 切到别的窗口（页面 hidden）；② 窗口被**完全遮挡**（Chromium 的
`CalculateNativeWinOcclusion` 会把它判成 hidden）；③ 最小化。

## 四、这一版补上的字段（`playbackProbe.ts`）

每秒采样新增 `document.visibilityState === 'hidden'` 与 `document.hasFocus()`，行里多出：

```
隐藏=3s 失焦=4s
```

并且判定顺序改成：**数据受限 → 窗口不可见(浏览器挂起画面，音频照常) → 呈现受限 → 正常**。
⇒ 下一次复现，`判定=` 会直接告诉我们是"当时窗口不可见"还是"窗口可见但合成慢"。

## 五、你现在就能做的 A/B（比再看一遍日志更快）

**复现时让应用窗口全程保持在前台**（不要切到看日志的窗口/终端、不要让它被别的窗口完全盖住）：

- 若不卡了 ⇒ 就是"不可见 ⇒ 画面挂起"。修法很具体：给 WebView2 传
  `additionalBrowserArgs`（Tauri v2 支持，`tauri.conf.json` 的 window 段）关掉 Windows 遮挡跟踪：
  `--disable-features=msWebOOUI,msPdfOOUI,msSmartScreenProtection,CalculateNativeWinOcclusion`
  （⚠️ 默认那三个要自己带上，否则会被覆盖掉）；
- 若照样卡 ⇒ 窗口可见而合成慢，那是另一条线（GPU 合成 / 抽屉里的模糊与大图层），
  与 CDN、与 MSE 都无关。

## 六、对 MSE 立项的影响（诚实记一笔）

**这次的数据说明 MSE 不会改善这个症状**：MSE 也要经过同一条合成/呈现管线，
"画面被挂起"照样会发生。MSE 的价值仍在它原来的三条（单钟、缓冲可控、**慢链路可降档**），
所以计划不动，但"换 MSE 就能治卡顿"这个预期要划掉。
