# 239-20260927-B站的失败语义四类 + 端点熔断

第 4 阶段 ⑦。用户拍板的范围（原话）：**不做令牌桶**（"B 站的抓取逻辑已经定制的很完善了
基本没有超限的风险"）、**要四类结构化失败**、**要端点熔断**、**熔断状态要落库**
（"能够防止重复开启应用时的抓取任务触发风控"）。

## 一、四处口径（先写清，免得下次又讨论一遍）

| 决定 | 内容 | 理由 |
|---|---|---|
| **不装令牌桶** | B 站端点不进 `ENDPOINT_RATE` | 它的节奏由 R27 冷却 / R28 预算与空闲退避 / R30 静默时段管着，且是实测调过的；B 站只有一份身份，"身份级"退化成全局，收益≈0 而回归面很大 |
| **"没配速率 = 不限速"** | 把原来的 `DEFAULT_RATE=0.1` 兜底**删掉** | 那个兜底等于给**任何**新接线的端点偷偷加一层全局限速 —— B 站接熔断时会被顺手拖慢。要限速就显式写进表里，一行可查 |
| **冷却不用动** | `rate_limit.py` 早就落库（R27/devlog/125，键 `ratelimit.<平台>`，命中即写 + 懒加载） | 用户担心的"重复开应用立刻满速撞风控"**已经防住了**（我上一轮把它和进程内台账并排写，容易被读成"冷却没落库"，此处更正） |
| **熔断窗口落库，健康度不落** | `breaker.<平台>` → 各端点窗口 | 熔断是"这个端点坏了"的判断，**重启后依然成立**（接口改版不会因为我们重启就修好）；健康度衡量"最近表现"，且按请求写库是写放大 |

## 二、四类怎么接（`fetcher.py`）

`_detect_rate_limit`（行为：要不要冷却）**一行没改**；旁边补一个 `_note_failure()`（语义：是哪一类），
写进任务级 ContextVar `app.core.outcome`：

| 情形 | 分类 |
|---|---|
| `was_rate_limited()`（冷却判据已置位） | `risk_control` —— **直接复用**，不另立码表 ⇒ 两套口径在结构上不可能分叉 |
| HTTP ≥ 500 | `server_error`（→ 策略上的 `network_error`） |
| HTTP 404 / 410 | `business_error` |
| 其它非 200 | `risk_control`（不认识的失败：保守） |
| 200 + 码表命中（`-101` 未登录 / `-404` 啥都木有 / `62002` 不可见 / `62004` 审核中 / `-403` 权限不足 / `-509` `-412` `-799` 风控） | 表里那一类 |
| 200 + 未知码 | `business_error`（B 站业务错就是 200+非零码；真风控有码表与"频繁"文案兜底） |

调度侧只做一件新事：**`None` 之后不再一律 `network_error`**。
`_none_stop_reason()` 只回答"不是风控的那次失败，是业务还是网络"：
业务 ⇒ `stop_reason="business_error"`（**不进 `issues`** ⇒ 报告里不再出现"根本没发生的中断"）；
其余 ⇒ `network_error`（与改前一致）。⚠️ **风控那一支仍由 `was_rate_limited()` 全权决定**，
并有判据盯着"逐字不变"。

账号页那句话也分了工（`_account_fail_text()`）：「账号不存在或不可见（业务失败）」/
「更新失败（风控）」/「更新失败（网络）」—— 以前三种都叫"更新失败"。

## 三、端点熔断（B 站五个端点）

`platforms/bilibili_posts.py` 里加了 `bili_identity()` / `admit_endpoint()` / `observe_endpoint()`
（B 站的端点记账住在 B 站模块里），端点名：
`video_list`（arc/search）/ `dynamics_feed`（feed/space）/ `user_info`（acc/info）/
`detail`（动态/视频/专栏详情）/ `live_batch`（T0 批量）。

- 发请求前 `admit_endpoint()`：**熔断就一个字节都不发**（否则"熔断"只是个日志）；
- 请求后 `observe_endpoint()`：`ok=False` 时读语义位 → 走四类策略 ⇒ **业务失败不计样本**
  （所以"号被注销/稿件不可见"堆再多也不会把端点判成故障 —— 这正是 237 那条策略的用处）；
- 三条件同时成立才熔断（风控率 >0.6 ∧ 样本 ≥20 ∧ **≥3 个不同目标**）。
- T0 那条熔断后**跳过本批且不报故障**（这是我们自己的判断，不是上游故障）。

## 四、落库（写放大要避开）

- **懒加载**：`_ensure_breaker_loaded(db)`（与 R27 的 `_rl_loaded` 同一手法，只读一次）；
- **写时机**：窗口的**熔断态翻转**（`Ledger.dirty()`）立刻写，其余按 ≥30s 攒着写
  （`_flush_breaker()`，接在每抓完一个账号之后）——按请求写库是每个请求一次 fsync，不做；
- **坏数据跳过**：`EndpointWindow.from_dict()` 解析失败只记日志，不让调度起不来。
