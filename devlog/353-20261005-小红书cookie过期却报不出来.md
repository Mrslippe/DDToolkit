# 353-20261005 小红书 cookie 过期却报不出来（HTTP 200 + 业务码 -100）

> 用户 2026-10-05：「小红书贴文有一些详情加载失败了，是 cookie 过期了吗」

**答案：是，cookie 过期了** —— 而且**过期这件事本该由我们报出来，却一直沉默**。
这条 devlog 记的是"为什么沉默"以及修法；顺带记一次我自己造成的事故（测试写坏了用户的 `.env`）。

## 一、先拿到证据（真机，三个端点全问一遍）

用数据目录里那条真 cookie 直接打适配器：

```
列表接口:  失败  {'kind': 'ok', 'msg': '登录已过期', 'status': 200, 'code': -100}
用户信息:  失败  {'kind': 'ok', 'msg': '登录已过期', 'status': 200, 'code': -100}
详情×3:    失败  {'kind': 'ok', 'msg': '登录已过期', 'status': 200, 'code': -100}
```

即：**HTTP 200 + 业务码 -100 + 文案「登录已过期」**。同时日志侧只有两处异常：

- `img_proxy` 对 `xhscdn.com` **41 次全 403**（别的主机零失败）——那是**图片地址本身失效**
  （带不带 Referer 实测都 403，**不是**防盗链；重新取地址的详情接口现在也因 cookie 过期拿不到）；
- 没有任何一行"cookie 已失效"。

## 二、沉默的原因：`classify_http` 把「200」当成了成功

`services/platforms/xiaohongshu.py::classify_http` 的第一句是：

```python
if status == 200:
    return "ok"
```

而小红书**把业务错误也放在 200 里**（`success: false` + `code` + `msg`）⇒ 判成 `ok` ⇒
`_fail()` 里那句 `if kind == "cookie_invalid": xhs_auth_manager.note_invalid(...)`
（报"这条 cookie 活了多久、去设置里重新粘"）**从来没被执行过**；
能力矩阵也照旧写「已配置 Cookie」（它只读 `is_configured` = "键齐了"），
于是用户看到的现象是"有些详情加载失败"，而界面上没有任何一句能照做的话。

修法（三处，缺一条都不算修完）：

1. `classify_http`：判序改成**先 5xx / 风控 / 签名 / 登录**，最后才轮到
   "200 且**没有任何失败信号** = ok"；另外把实测到的登录码 `-100` / `-101` 单列一张表
   （`msg` 换语言或为空时仍认得出）。`classify_http(200)` 仍返回 `ok`（老用例钉着）。
2. `XhsAuth`：新增 `invalidated` 标记（**只有真机失败才算证据** —— `status()` 刻意不探活），
   `status()` 据此如实报「登录已过期（抓包时平台这么回的）⋯ 重新粘一次整条 Cookie（这条活了 N 天）」；
   `apply_cookie()` 清标记（用户照做之后立刻恢复）。
3. `capabilities.snapshot()`：`xhs = is_configured and not invalidated` ⇒
   「小红书内容」会**进受限项**（顶栏那条「有 N 项功能当前受限」就是用户能看到的地方）。

## 三、⚠️ 事故：我的一条测试把用户仓库根的 `.env` 写坏了

新加的那条用例直接调了生产的 `xhs_auth.apply_cookie()`（**没像同文件的邻居那样打桩
`save_env_keys`**），而测试进程里 `env_store.ENV_PATH` **就是仓库根 `.env`**
（`DATA_DIR` 默认 = 仓库根）⇒ 测试字符串 `a1=new; web_session=new` 被真的写进去，
把用户那条真 cookie 冲掉，还让"没有 cookie"的几条用例一起变红
（它们的判据是"没 cookie 就不发请求"，而本机 `.env` 里恰好配着）。

处置与护栏（三条，都进了 `tests/conftest.py`）：

| 动作 | 说明 |
|---|---|
| 还原 `.env` | 只改回那两行（`XHS_COOKIE=` 清空、删掉我加的 `XHS_COOKIE_SET_AT`），其余逐字不动；数据目录那份 `.env`（真 cookie 856 字符）未受影响，已复核 |
| 测试用例 | 照邻居的做法打桩 `X.save_env_keys`（测试**不许**碰用户真实文件） |
| conftest | ①新增 `_env_writes_go_to_a_temp_file`：把 `env_store.ENV_PATH` 指到临时文件 —— 落点变了、`save_env_keys` 的实现照旧是真的（第一版写成"替换成记账替身"，当场把一条考 `.env` 真写入的用例判红）；②`_no_ambient_login` 补上小红书/抖音 cookie 的清空（它们同样住在 `.env` 里，同样会"悄悄改变测试行为"） |

## 四、验证

- 单测：`classify_http(200, code=-100, msg='登录已过期') == 'cookie_invalid'`、
  `classify_http(200, code=-100) == 'cookie_invalid'`（只给码）、
  `classify_http(200, code=-915, …) == 'business_error'`、
  `classify_http(200, msg='success') == 'business_error'`；
  以及"实测失效 ⇒ 置标记 + `status()` 改口 + 重新粘一条即恢复"整条链；
  `test_capabilities` 新增"配齐但已失效 ⇒ 进受限项"。
- 全量 pytest 通过（1177 → 1185，含本批其它改动）。

## 五、给用户的下一步

到「设置 → 登录 → 小红书」重新粘一次整条 Cookie（**至少含 `a1` 与 `web_session`**）。
粘完 `invalidated` 自动清掉；这次失败之后**界面会自己说**「登录已过期」，
不用再靠"有些详情加载失败"这种间接现象去猜。

⚠️ 另外那条线索也记一笔：**库里的 XHS 图片地址会过期**（`xhscdn.com` 全部 403，
带 Referer 也一样），这是地址本身失效、不是 cookie 也不是防盗链 ——
重取详情的路径一旦恢复（cookie 粘好），这类图会靠"打开时重取"那条链自动换新地址。
