## 一、两处根因与两条修法（**刻意分开做**）

| # | 根因 | 修法 |
|---|---|---|
| ① | `runner.py:41` 建客户端时写死 `new_async_client(25.0, ...)` —— 而 `gift_days` 响应很小，25 秒纯属浪费 | **超时按接口分开**：`gift_days` 走自己的 `GIFT_DAYS_TIMEOUT = 8.0` |
| ② | 端点整体挂掉时，循环**逐个账号**等满超时（7 × 26s ≈ 3 分钟） | **连续失败预算**：连着失败到上限就放弃本轮剩余账号（下个周期再试） |

### ⚠️ 为什么超时**不能**全局调小

`fan_history` **合法就要 5–15 秒**（一次返回全量，实测 197KB / 单账号上千条）——
把客户端的 25s 一起调成 8s，会把**正常路径**也打断 ✗（那是"修一个坏一个"）。
所以只在 `fetch_gift_days` 这一处按请求传 `timeout=`（httpx 支持 per-request 覆盖），
并**加一条单测钉住"fan_history 不许跟着调小"**（断言它请求时 `timeout=None`，即走客户端默认）。

### 连续失败预算（`FailureBudget`，纯类）

三条语义，各有单测：

- 连续失败到 `limit`（默认 3）⇒ 本轮**放弃剩余账号**；
- **一次成功就把连续计数清零**（偶发抖动不该累积成"放弃"）；
- `limit <= 0` = 不启用（保留老行为，方便回退与对照）。

两个慢循环（`fan_history` / `gift_days`）都接上了；`danmakus` 那两个循环没接 ——
它们本来就只有 31 秒、且自带 3 次指数退避重试，再加一层预算是重复。

## 二、护栏（6 条）

| 判据 | 说明 |
|---|---|
| `gift_days` 请求带 `GIFT_DAYS_TIMEOUT`，且 ≤10s | 用替身客户端**记录 timeout 实参**（不是看常量） |
| **`fan_history` 请求不带 timeout**（走客户端默认） | 防"顺手把正常路径也调小" |
| 预算：连续失败到上限 | 纯类 |
| 预算：成功即清零 | 纯类 |
| 预算：`limit<=0` 不启用 | 纯类 |
| **端到端：7 个账号全超时 ⇒ 只试 3 次** | 直接数调用次数（这就是"3 分钟 → 24 秒"的机器判据） |

端点整体挂掉时 3×8 = **24 秒**（原先 3 分钟）。
