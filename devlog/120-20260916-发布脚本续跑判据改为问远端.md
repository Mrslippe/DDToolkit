# 120-20260916-发布脚本续跑判据改为问远端

> 用户实测截图：`python scripts/release.py 1.0.2 --from release` 只打印了
> `[warn] 计划里没有 push → 自动去掉 release`，然后跑完 report 报"**全部完成（0.0 分钟）**"——
> 看着像成功，其实**什么都没建**。用户一句"好像不对"把这个静默失败揪了出来。

---

## 一、根因：拿"过程量"当"事实量"

`select_steps()` 里那条守卫是这么写的：

```python
if "release" in steps and "push" not in steps:   # ← 用计划推断远端状态
    steps = [s for s in steps if s != "release"]
```

它对**从头跑**成立（没推 tag 就别建 Release），对**续跑必然错** ——
`--from release` 的计划天然就没有 `push`，而 tag `v1.0.2`（`36a7ba1`）其实**早就推上去了**
（`git ls-remote` 实测 `refs/tags/v1.0.2 = 55f683b`）。

而且它的失败形态特别糟：只 `print(WARN)` 不 `raise`，随后照常走完全程并打印"全部完成，
别忘了（脚本不做）…" —— **"什么都没做"和"做完了"长得一模一样**，正是本项目最忌讳的那种静默失败。

## 二、修法：问远端，并且把"查不到"和"没有"分开

| 结果 | 行为 | 打印 |
|---|---|---|
| 远端**有**该 tag | 保留 `release` | `[ok] 远端已有 tag v1.0.2 → 保留 release（计划里没有 push 也不影响）` |
| 远端**确实没有** | 摘掉 `release` | `[warn] 远端看不到该 tag → 自动去掉 release…；先 --from push 推 tag，再 --from release 补建` |
| **查询失败**（网络/代理） | 摘掉 `release` | `[warn] 远端查询失败（网络/代理） → …`（**不谎报"远端没有"**） |

- 新增 `remote_has_tag(tag) -> bool | None`：`git ls-remote --tags <url> <tag>`，
  非 0 返回 `None`（网络抖动不能被说成"tag 不在远端"，那会把人引去重推一个已经在的 tag）；
- `select_steps(args, remote_tag_check=None)`：判据可注入，**用例因此不联网**；
- **计划里已有 `push` 时不查**（tag 马上就推了，省一次网络）—— 用例用"asked == []"钉住这条。

## 三、用例（`tests/test_release_script.py`，30 passed）

- 改写 `test_release_step_is_dropped_without_push` →
  `test_release_step_is_dropped_only_when_the_remote_lacks_the_tag`：True（并断言查的就是 `v1.0.2`）/
  False / None 三态 + "有 push 时不查"；
- 新增 `test_remote_has_tag_distinguishes_absent_from_unknown`：`monkeypatch.setattr(R, "git", …)`
  造三种返回（`0`+有输出 / `0`+空 / `128`），外加"空 tag 不查网络"。


## 五、教训

**守卫要读事实，不要读过程。**"计划里有没有 push"是这次运行的过程量，
"远端有没有 tag"才是 Release 能不能建的事实 —— 拿前者推后者的那次推断，
在"从头跑"上碰巧对，在"续跑"上必错，而续跑恰恰是最需要它的场景（失败之后人手都会 `--from`）。
与 devlog/109（脏目标目录）、117（停表判据读 React 状态）同属"**判据选错了源**"这一类。
