# 342-20261005 通知 L2 投递补全：进度推着走，开播两条出口都有

> 接 `devlog/341`（L1 规则层）。L2 = **投递补全**：把"最及时"与"持续可查"这两件事从
> 设计案落成事实。两处都是"能力已经有了，但没接上"。

## 一、进度原来只在**轮询 tick** 上更新（所以"跑到哪一步"看不到）

顶栏那句「帖子抓取中 - V名 - 3/11」只有 `GET /vtuber/fetch-status` 会算 —— 闲时 **10s**
一跳，而一轮手动任务常常只有几秒 ⇒ 用户看到的是 `1/11` **直接跳到结束**。

修法：`_set_post_progress` / `_set_account_progress` 写完状态**顺手推一条**（复用 M2 的
`notice.progress` 通道）。三条硬规则（比节流窗口重要）：

1. **同值去重**（重复发 = 白唤醒前端，还会刷新面板里的到达时刻）；
2. **首次/收尾必发**（收尾漏了界面会**停在 3/11**）；
3. **丢了不影响正确性**——推送只让界面跟手，**事实真源仍是轮询那一份**：
   节流把中间几条全吃掉，界面也不会错，只会晚 ≤ 一个轮询周期。

节流窗口 `PROGRESS_PUSH_MS = 500ms`：依据是"**读起来像在动**"，不是性能
（一轮最多十几条 = 账号数；`publish()` 只做 append + 入队）。

## 二、⚠️ 踩到全局口径：**自动节拍不许推**（探针当场抓到）

第一版给"所有" `_set_post_progress` / `_set_account_progress` 都开了推送，`ui_probe`
立刻红在：`@1280 顶栏：只有自动节拍在跑却亮起了事件容器（text='动态轮询中 - … - 9/14'）`。

原因很具体：**这两个 setter 被手动与自动两条路共用**
（`async_fetch_accounts` 也被综合档调、`dynamic` 那条本来就是自动节拍），
而"自动节拍不占顶栏"是 2026-09-10 的用户口径 —— 原先它靠**轮询那份过滤 `auto`** 实现，
推送是**绕过那道过滤**的新入口。三处补门：

| 位置 | 处置 |
|---|---|
| `async_fetch_accounts(..., auto=)` | 新增参数；综合档那条路径不推 |
| 综合档账号流轮末汇报 | `push=not auto` |
| `async_fetch_dynamics` 的 worker + `on_progress` | 显式 `push=False`（它整个就是自动节拍）|
| `_drain_pending_fetches`（排队账号补抓）| `auto=True`：用户的动作早就结束了，此刻推一条会让人以为"它自己在跑" |

> ⚠️ 默认值的方向也是设计的一部分：`push` 默认 **True**，因为两种漏法代价不同 ——
> 默认 False 会让新加的手动路径**悄悄不推**（"点了没反应"，难查），
> 默认 True 会让漏掉的自动路径**悄悄占顶栏**（"顶栏一直亮着"，一眼就能看见）。
> 选"更容易被发现"的那个方向。

## 三、⚠️ `record_live_edge` **一个调用点都没有**（写了但没人调）

`services/notices.record_live_edge` 此前**只有用例在调** ⇒ 开播告警只活在**推送**那一路上：
推送断线/重连窗口里，`GET /vtuber/notices` 这份权威列表里**根本没有它**
（用户看到的是"刚才明明弹过开播，点开面板却没有"）。

修法：调度器在发 `domain.live.edge` 的**同一处**也调它（两个出口挨着写，
判据用源码级钉住 —— 那段代码在 T0 轮询深处，真机才跑得到，漏了是**静默**的）。
补上之后两条路都有：推送负责"立刻看到"，汇总负责"断线也还在"（2 分钟后自己过期）。

## 四、顺带修掉一处既有漂移 + 记一条踩过的坑

- **任务名两张表**：进度推送（上游 `scheduler`）与轮询文案（下游 `notices`）都要中文名，
  而 `scheduler` 顶层 import 了 `notices` ⇒ 下游不能反向 import。两份副本 +
  **逐字对账用例**（`test_task_text_tables_match`）—— 漂了的症状是"同一条任务两种说法"。
- **替身签名窄一格**：给 `async_fetch_accounts` 加 `auto=` 之后，`test_services` 里那个假函数
  直接 `TypeError`，而错误被 `_drain_pending_fetches` 的 try/except 吞成一行日志 ⇒
  判据红在"队列没被消费"上，看不出真因。替身已加 `**kw`。
  （本仓第三次记这条：替身必须照抄真身签名。）
