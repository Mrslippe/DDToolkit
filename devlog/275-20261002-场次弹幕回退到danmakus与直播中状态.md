# 275-20261002 场次弹幕：回退到 danmakus、直播中不再说"没有"

> 用户口径（2026-10-02，附直播日历详情截图）：「我在直播日历中打开的近几天直播日期详情，
> **即使本地的数据源没有包含弹幕记录但也没有回退到 danmakus**，就呈现图中这样，我希望的效果是
> **每一场直播详情都能够看到弹幕记录**，**还在直播中的详情页就显示正在直播中**而不是
> 『本场没有可用于统计的文本弹幕记录』」。

## 一、现场：那一场到底缺什么

截图那场（`鬼武者通关了云两把`，2026-10-01 22:00 → 次日 13:18，数据源 `feed + self`）：

| 事实 | 实测 |
|---|---|
| 库里的行 | 只有 `feed` 一行（`live_id=743227305862059737`，`start_at` 14:00Z、`end_at` 为空）—— 显示的结束时间来自 `self` 快照，所以 `source` 是 `feed+self` |
| 该账号（七海 434334701）最后一条 danmakus 行 | **2026-09-28 10:02Z**（= 本地 09-28 18:02） |
| danmakus 上游该账号最新一场 | **2026-09-28 18:02 本地**，且 `?cache-bust` / `no-cache` 头都拿到同一份 ⇒ 不是 CDN 缓存旧了 |
| danmakus 是否有按房间/时间查场次的接口 | **没有**（swagger 里场次只有 `channel` 与它自己的 `liveId` 两条路） |

⇒ 「本地没有 danmakus 行」有两种成因，**必须分开处理**：① 这一场上游根本没有；
② 上游有、只是没同步进来。这张截图是 ①，而**下面的第 3 条证明库里还压着一堆 ②**。

## 二、根因链（三条，都是我们这边的）

**① 每日同步失败即放弃、不重试。** 用任务自己的代码路径重放一次（9 个 bilibili 账号、
`new_async_client(25.0)`、同一套请求头）：

```
HTTP 200 × 5（0.9~2.2MB / 1~8s）
HTTP 302 × 3 → https://dnspod.qcloud.com/static/webblock.html   ← 腾讯 DNSPod WAF 拦截页
ReadTimeout × 1（25.9s）
```

而 `_sync_live_sessions` 原先**每账号一次请求、失败 `continue`**，于是：
日志只有「外部任务 danmakus/live_sessions 完成: **新增 0，跳过 8**」（2026-10-01 22:45），
看不出是被拦、超时还是上游真的没有新场次。

**② 启动补抓"无论成败都写时间戳"。** `run_startup_external_catchup` 的 `finally` 里无条件
`set_dt(EXTERNAL_STARTUP_KEY)`（原注释：第三方抖动不该导致每次启动都重跑）⇒ 那次**全账号被拦**
的补抓也算"跑过了"，接下来 24 小时内每次启动都跳过补抓；而 3AM 的 cron 又要求应用恰好开着。

**③ 于是洞能留一周。** 汇总实测：全库 danmakus 行停在 **09-28**，而 feed 行一直在写（到 10-02）；
逐账号对照上游：弥月 987 → 998（**缺 11 场**，09-25 起）、明前奶绿 / 泽音 / 塔菲 / 四时小路各缺 1 场。
用任务自己的代码对弥月重跑一次：`stored=11 skipped=0`，**代码没问题** —— 缺的全是"那一夜被拦了"。

## 三、改了什么

### 3.1 同步侧（`app/services/externals/danmakus.py`）

- `_fetch_channel_once` 把失败**分因**带出来：`HTTP 302`（WAF）/ `HTTP 502` / `ReadTimeout` /
  `响应非 JSON` / `code=x` —— 原先这五种都塌成 `skipped += 1`；
- `fetch_channel_checked`：退避重试 3 次（0 / 2s / 6s），`fetch_channel` 变成它的薄包装；
- 账号之间加 1.5s 间隔（**连打 9 个账号正是触发 WAF 的形状**）；
- `_sync_live_sessions` 接 `FailureBudget`（与 zeroroku 同一套语义：连续失败到上限就放弃本轮剩余账号），
  并把失败原因计数带进摘要 —— **全账号颗粒无收时把 `summary.error` 填上**，runner 就会记
  「未完成」而不是「完成：新增 0」；
- 单账号同步抽成 `sync_account()`，**每日批次与按需现查共用**（`attempts` 可调：点击路径只试 2 次）。

### 3.2 取数侧（`app/services/live_upstream.py` + `app/routers/vtuber.py`）

`GET …/live-sessions/{id}/upstream` 的三条新路径：

| 情形 | 现在的行为 |
|---|---|
| `end_at` 为空（**还在直播**） | 直接回 `wc_status='live'`，**不出网** —— danmakus 要等本场结束才固定化这一场 |
| 只剩 feed/self 行、且是近 14 天内结束的 | **现去 danmakus 查一次**（`ensure_session_recorded`）：命中 → 补库 + 重新定位合并后的场次（对外 id 换成 uuid）+ 走正常取数；上游确实没有 → `no_danmaku`；没问成（302/超时）→ `fetch_failed` |
| 更早的纯 feed 场次 | 不为它出网（上游早该收录，没有就是没有）⇒ `no_danmaku` |

节流与单飞：同账号 **10 分钟一次**、并发共享在途任务；`?refresh=true`（用户点「查一次」）绕过节流 ——
**否则点了按钮却不问上游，"重试"就是句空话**。

这条路径需要"拿原来的 feed id 找回同一场次"，而合并会把对外 `live_id` 换成 danmakus uuid，
所以 `LiveSessionRepo.merged()` 新增 `with_ids=True`（每组多带 `src_live_ids`；默认 False，
其余调用方字段集一字不变）。顺着它一起修掉两个自己挖的坑：

- **定位要认源 id**（`_find_live_session`）：现查发生在**弹窗已经打开之后**，前端手里那份详情
  还是旧的 feed id —— 只按 `live_id` 精确匹配会让「用弹幕自建」与重取详情双双 404，
  而界面会把 404 显示成"弹幕拉取失败"（**把一次成功的补抓说成故障**）；
- **自建词云要用定权后的 uuid 去拉原始弹幕**：danmakus v3 只认自己的 uuid，拿数字 id 去问等于空手而归。

### 3.3 弹窗里的详情也要跟着刷新（`session_changed`）

现查补进来的那一行带着**弹幕数 / 收益 / 峰值在线 / 数据源**，而弹窗手里那份详情是补之前取的 ⇒
不重取就会出现"词云有了、弹幕数还是 `—`"的自相矛盾卡片。所以 `LiveUpstreamOut` 多一个
`session_changed`，前端据此请父组件 `reloadDetail()` 一次（按场次记账，同一场只喊一次）。

### 3.4 前端文案（`LiveSessionDialog.tsx` + `types.ts` + `useLiveUpstream`）

`wc_status` 从五态变六态，**四种"没有词云"的原因各说各的话**：

| 态 | 文案 |
|---|---|
| `live`（新） | 「正在直播中（本场弹幕要等结束后由上游收录，届时重新打开即可看到）」 |
| `no_danmaku` | 「上游尚未收录本场（danmakus 没有这一场的记录；可再查一次）」+「查一次」按钮 |
| `fetch_failed` | 「弹幕拉取失败（网络或上游不可用）。」+「重试」（不变） |
| `upstream_absent` | 「上游未提供热词」+「用弹幕自建」（不变） |

「直播动态」段同一口径：直播中显示「本场还在直播（中断/继续事件要等结束后才有）」，不再说"暂无动态数据"。

## 五、没解决的那一半（要拍板）

剩下 **16 场**（09-29 → 10-01，跨 6 个账号）现查结果 **0/16** —— danmakus 那三天几乎没收录，
10-02 起又全都有。也就是说：

- 「**每场都看得到弹幕**」在**只有 danmakus 一个弹幕源**的前提下做不到（上游覆盖有洞，
  且不是延迟，是根本没有）；
- 截图那一场（10-01 22:00）正落在这个洞里 —— 现在它会如实显示「上游尚未收录本场」+「查一次」，
  而不是"本场没有可用于统计的文本弹幕记录"。

要真正补上这 16 场，只有另开一条弹幕来源（B 站直播回放弹幕 / 直播期间自采落库），
两者都是产品级决策，已作为 §2「原始弹幕明细库」的实测证据登记在 `docs/TODO.md`。

**用户当日口径：先就这样** —— 不加源；上游没收录的场次如实显示「上游尚未收录本场」+「查一次」，
将来上游补录了，那个按钮就能拿到。所以这条留在 §2 是"产品方向待拍板"，不是待办。
