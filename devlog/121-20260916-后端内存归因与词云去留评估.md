## 一、内存：两把尺子，量出同一个数

| 尺子 | 量法 | 结果 |
|---|---|---|
| 打包版空闲 | 以 `DDTOOLKIT_DATA_DIR` 指**空目录**起 `ddtoolkit-backend.exe`，等 `DDTOOLKIT_READY` 后静置 8s | **私有工作集 128.7MB**（与用户截图 128.6 一致）/ 总工作集 117.1 / 提交 97.8 / 12 线程 / 219 句柄 / 冷启动 **2.0s** |
| dev 分段归因 | 同版本解释器按组 `import`，每次读 `GetProcessMemoryInfo().WorkingSetSize` | 见下表；把最后一组换成 `jieba.initialize()` 就复现了 178MB 那个旧状态 |

| 段 | 累计 | 增量 |
|---|---|---|
| 裸 CPython 3.14 → +标准库 | 20.5MB | 17.3 + 3.2 |
| + FastAPI/Starlette（连带 Pydantic/anyio） | 43.1MB | **+22.6** |
| + uvicorn | 49.4MB | +6.3 |
| + SQLAlchemy/Alembic | 77.5MB | **+28.1（最大单块）** |
| + APScheduler/httpx | 82.7MB | +5.2 |
| + `app.core`（配置 + 引擎/PRAGMA） | 89.9MB | +7.2 |
| + `app.main`（**全部业务代码**） | 98.1MB | **+8.2** |
| + `import jieba` / `jieba.initialize()` | 100.8 → **155.6MB** | +2.7 / **+54.8** |

**三条结论**：① **业务代码只占 ~8MB（6%）**，其余是解释器与框架的固定开销，打包版再叠 ~19MB
（自带 `python314.dll` 等）；② R24a 删预热**确实省下了 55MB**（178 → 128.7）；③ 唯一已知涨点 =
**真开过一次词云之后 jieba 词典常驻且不回收**（所以"托盘挂久了变 180MB"是可解释的）。

### 测量本身踩的两个坑（写进 §3.12，免得下次再踩）

1. **ctypes 不声明 `argtypes` 读到恒 0**：`GetCurrentProcess()` 的伪句柄是 -1，不声明就被按 32 位传、
   `GetProcessMemoryInfo` 直接失败 —— 第一版脚本每段都打 `0.0 MB`，差点当成"内存没涨"；
2. 脚本放在 `%TEMP%` 里跑 ⇒ `sys.path` 是脚本所在目录，`import app` 全失败 —— 要显式
   `sys.path.insert(0, os.getcwd())`。

用户理由两条：「它依赖的全量弹幕获取我们目前还没做」「之前 danmakus 上游超时也没用到自建方案」。
用真上游复核（`scripts/check_danmaku_fetch.py --self`，dev 库最近 6 场）：

| 事实 | 证据 |
|---|---|
| **上游 `extra.wordCloud` 已恢复** | 6/6 场次 `status=upstream 上游词条=40`、**失败 0/6**、单场 3.8–8.9s —— devlog/060 那次"字段整个消失"是**当时**的事 |
| 自建路径能跑但很慢 | 最新一场：**32.0s** / 18226 记录 / 6696 文本 → top 词 `啥意思(336) prpr(298) iceb(176) 小弥(154) 癔症(141)` |
| 自建**不依赖**本地全量弹幕库 | 它是**按需现拉** danmakus `/api/v3/…/danmakus`（不落库）—— 与 TODO §1.2「原始弹幕明细库」是两件事（用户记混了） |

⇒ 成立的部分：**jieba 只服务"上游断供兜底"，主路径用不到它**，白占打包目录 29.6MB。
不成立的部分：自建不是"没做"，而是"当前用不上"；而这个兜底**有历史必要性** —— 上游 09-13 断供过一次，
正是那次才有 devlog/061。

用户三选一后定：**不动，只记账**（保留断供兜底；jieba 已懒加载，空闲不占内存）。
把"如果将来要动"的三个候选与收益记在 `docs/TODO.md` §1.4（词云词典空闲卸载 −55MB /
打包瘦身 −38.6MB 磁盘 / Alembic 懒加载几 MB），并写明**不删 jieba 的理由**。

## 三、顺手查出的"在盘不在内存"

打包目录 `_internal/` 100.6MB 里，**空闲都不驻留**（所以不构成那 128MB，只让安装包变大）：

| 条目 | 体积 | 说明 |
|---|---|---|
| `jieba/` 词典数据 | 29.6MB | 一开词云就变内存里那 55MB |
| `numpy` + `numpy.libs` | 25.9MB | **`app/` 里无人 import**；Pillow `Image.fromarray()` 的函数级 `import numpy` 被 PyInstaller 静态分析跟进图 |
| `PIL` | 12.7MB | 同上（依赖链的钩子带进来，我们代码里也没有） |
| `win32/` `pywin32_system32/` | 1.1MB | **依赖图里根本不存在** ⇒ 历史构建残留 |

> 判定手段：`build/ddtoolkit-backend/xref-*.html`（PyInstaller 的依赖图报告）—— 里面有没有、
> 谁带谁进来一查便知。**"打包目录里有" ≠ "依赖图里有"**。

## 四、修掉一个拦路的小 bug

`scripts/check_danmaku_fetch.py` 在中文控制台**直接崩**：告警里的 `⚠️` 触发
`UnicodeEncodeError: 'gbk' codec`（GBK 编不出 U+26A0），脚本还没开始诊断就退了 ——
本次是用 `PYTHONIOENCODING=utf-8` 绕过去的。按 `ui_probe.py` 的同款做法补
`sys.stdout.reconfigure(errors="replace")`（不换编码，只把打不出的字符替换掉），
复跑告警路径不再中断。
