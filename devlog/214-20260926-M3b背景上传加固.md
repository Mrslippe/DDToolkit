# 214-20260926-M3b背景上传加固

批次 11b = 计划 §M3 的**后半段**（按 2026-09-25 的修正：只做背景上传加固，
router 拆分移入第 4 阶段且倾向不做）。

## 一、改前是什么样（三行代码，两个真缺陷）

```python
data = await file.read()                 # ① 全量进内存
if len(data) > 10 * 1024 * 1024: ...     # ② 读完才判大小
if v.background_path:
    (custom_dir / ...).unlink()          # ③ 先删旧
(custom_dir / name).write_bytes(data)    # ④ 再写新
```

- **③④ 的顺序 = 写新失败就丢背景**：磁盘满 / 权限 / 断电时旧背景已经被删掉，
  而 DB 里还指着那个不存在的路径 ⇒ 卡片页背景变空白，**用户无法恢复**（文件没了）。
- **①② = 限额形同虚设**：判大小发生在全量读入之后，一个大上传先吃满内存。
- 顺带：类型只看客户端声明的 `content_type` ⇒ HTML 改个扩展名就能存进 `static/custom_bg/`
  再由 `/static` 原样吐出来。

## 二、改成什么（`app/services/vtuber_background.py`，router 不再自己写文件）

1. **限额在"读"的时候生效**：按 64KB 分块读，超限立刻抛；`UploadFile.size` 已知时
   **一个字节都不读**（有 Content-Length 就先拒）。413。
2. **按文件头判类型**：PNG / JPEG / GIF87a / GIF89a / `RIFF....WEBP` 五种魔数；
   内容说了算，声明与内容**矛盾**时 415（"内容像 jpg，声明是 png"）。
   声明不认识但内容认识 ⇒ 收（旧实现会因为声明不在白名单而拒，这是**放宽**）。
3. **写临时文件 `<id>.uploading` → 同目录 `os.replace`（原子）→ DB 提交成功之后才删旧文件**；
   提交失败把刚写好的新文件删掉（否则是孤儿）；任何失败都不留临时文件。
4. 删除只取**文件名**（库里的值不该能指到 `custom_bg/` 之外），失败只记日志不抛。

## 三、判据（`tests/test_background_upload.py`，14 条）

happy path + 替换（旧文件在**提交之后**才消失）· 声明不认识但内容真 ⇒ 收 ·
声明与内容矛盾 ⇒ 415 · HTML 伪装成 PNG ⇒ 415（**魔数**那条）· webp/gif 魔数认得 ·
超限 413 · **有 size 时零读取**（服务层，断言 `read` 从未被调用）·
写盘失败 / **半写**（第二个 chunk 炸）/ rename 失败 / **提交失败** 四种注入 ·
旧文件被手工删过也照常换新 · 清除走同一套删除 · `background_path` 不能越出目录。

**"先补的失败用例"这次的证据**：把这 14 条拿回**旧实现**上跑 ⇒ **7 条红**
（声明不符/伪装/写盘失败/半写/rename 失败/提交失败/未知声明），恢复新实现后 14/14 绿。
另外**逐机制的拆解反向验证 3/3 红**：去掉临时文件清理 · 把删除顺序改回"先删旧" ·
去掉 size 短路。

## 四、没做（按修正）

- **不拆 router**（计划 §1.3 的四条硬约束：`include_router` 顺序是契约、
  `api_route` 双方法顶着文档数字门禁、`img_proxy` 三个符号必须再导出、
  6 处 monkeypatch 打在 router 模块属性上）。这一批**只**动背景上传那一段，
  顺带把文件 IO 从 router 挪进 services（router 现在只做 HTTP 映射）。
- **不做 OpenAPI 快照 diff**：那是为"拆文件但契约不变"准备的证据，而本批**没有碰任何路由
  签名**（路径、方法、`response_model` 都没动）⇒ 用端点级契约判据（200 的 `VTuberOut`
  含 `background_path`、415/413 的语义、404）替代，写在同一个测试文件里。
- 真机验证：无（上传走 HTTP，测试库 + 临时数据目录已覆盖；真机动作用户已推迟）。
