# 241-20260927-消息中心 M0：推送通道骨架

消息中心第一批（`docs/design/notices/message-hub-execution.md` §M0）。**这一步只验证"通道通了"**：
后端能推、客户端能断、断了能重连；这一批**不接任何真实事件**（那是 M1–M5）。

## 一、为什么值得做

今天"点击按钮 → 别的窗口/别的组件看到"最坏要等 **3–10s**（`TopBar.tsx` 3s 忙 / 10s 闲轮询
`/vtuber/fetch-status`）。延迟的 99% 就在"等下一次轮询"，不在传输 ⇒ 把轮询换成推送是这件事
唯一有意义的形态（"搬到后端但不推送"= 白搬）。

## 二、三处**开工前复核**改掉了方案（见执行方案 §8）

1. **T0 是守护线程**（`scheduler.py` 的 `_live_poller_loop`），开播边沿在那里产生 —— 那里
   **没有事件循环**。方案 §M0 只写了"不持有 asyncio 原语"，漏了这条 ⇒ `publish()` 必须是
   **同步的、任何线程可调**：经线程安全的 `queue.Queue` 中转，由 `start()` 起的 drain 任务
   在应用循环里投递。
2. **V6（探针能断言"推送真的到了"）需要一条 dev-only 合成钩子** —— 探针没法让后端自然产生
   一条通知（开播要真开播）。所以加了 `POST /messages/_debug/publish`，`DEV_API_TOKEN` 为空时
   这条路径**根本不在路由表里**（不是"关着"，是"不存在"）。
3. **路径撞名**：`GET /events` 已被 `GET /vtuber/{id}/events`（V 的活动条目）占用 ⇒ 用
   `GET /messages/stream`。

## 三、交付物

| 文件 | 内容 |
|---|---|
| `app/services/messages.py` | `MessageHub`：类型白名单校验 → 环形 **50** 条回放缓冲 → 投给所有订阅者（每个订阅者一条**有界队列 200**，满了**丢最旧**并计数）。`KNOWN_TYPES` 八类（`domain.*` 四个 + `notice.*` 四个） |
| `app/routers/messages.py` | `GET /messages/stream`：SSE over fetch。首帧 `: connected` → 消息帧（`id: <seq>` + `data: <json>`）→ 空闲 **15s** 发 `: ping`；**只在带 `Last-Event-ID` 时补发**且帧内 `replay: true`；生成器 `finally` 里退订 |
| `app/routers/messages_debug.py` | dev-only 合成发布钩子（单独模块 + 标准名 `router`，否则它不进"装饰器"计数） |
| `app/main.py` | 挂路由 + `include_debug_routes(app)` 守卫 + lifespan 里 `HUB.start()` / `await HUB.stop()` |

**跨线程是怎么接的**（这是本模块唯一有技术含量的地方）：`publish()` 只做两件事 ——
消息进线程安全的 `queue.Queue`，然后 `loop.call_soon_threadsafe(wake.set)` **叫醒** drain 任务；
**投递只在应用循环的线程里发生**（订阅者的队列绑在那个循环上）。`asyncio.Event` 在 `start()`
里**现造、每代重建**（`ARCHITECTURE.md` §6 第 15 条：综合档每轮一个 `asyncio.run()`，跨循环
复用原语必抛 "bound to a different event loop"）。

**为什么是 "SSE over fetch" 而不是 `EventSource`**：业务端点全要 `X-DDToolkit-Token`，而原生
`EventSource` **不支持自定义请求头** ⇒ 只能把 token 拼进 URL，那是方案里的硬停止条件
（token 进日志/历史）。前端用 `fetch` + `ReadableStream` 读同一个 `text/event-stream`。

**与轮询并存**：轮询是一致性兜底（推送漏发、重连窗口内的消息）。M0 **不退役**轮询。

**发布点纪律**（写进模块 docstring）：**不要在事务中间 `publish()`** —— 消息发出去收不回，
而事务可能回滚 ⇒ 订阅者会收到一条"从未发生过"的事件。发布点一律放 `db.commit()` 之后。

## 四、第一版被自己逮住：drain 用 `run_in_executor` ⇒ **整个测试套挂死**

第一版的 drain 是"把阻塞读丢给工作线程"（`await loop.run_in_executor(None, self._inbox.get)`），
看着很标准，**单跑 `tests/test_messages.py` 还全绿**。但全量跑就卡死在 **68%**：
`test_scheduler_lifecycle.py::test_two_consecutive_lifespans_do_not_double_run`
（真起两次 lifespan）之后再也不动 —— CPU 冻结、18 分钟没有输出。

`faulthandler` 抓到的栈是决定性的：

```
MainThread             asyncio/runners.py close → run_until_complete(shutdown_default_executor)
Thread-1 _do_shutdown  concurrent/futures/thread.py shutdown → threading.join
asyncio_0              queue.py get   ← 卡在这里
```

即：drain 被 `stop()` 取消时，那个工作线程**仍阻塞在 `_inbox.get()` 上**；而 `asyncio.run()`
收尾要 `shutdown_default_executor(wait=True)` 去 join 它 ⇒ 永远等下去。
**修法**：`call_soon_threadsafe` 唤醒 + `get_nowait` 清空（不占线程、也不需要关停哨兵），
顺带省掉"每投递一条过一次线程池往返"的延迟 —— 而"降延迟"正是这个模块的全部意义。

⚠️ 三条教训：

1. **"单跑绿"不算数**：这个坑只在"真 lifespan 跑两次"的路径上出现，而那条路径在一个与本批
   **毫无关系**的测试文件里（`test_scheduler_lifecycle.py`）。本仓的"全量 pytest"不是形式。
2. **测试挂死不会报红，它只是不动了**（本条正好也是方案里"别用 `TestClient` 读流"那条警告的
   同一个形状）。跑了 18 分钟没有新输出才被发现；`-o faulthandler_timeout=25` 是抓它的手段
   （`faulthandler` 会把**每个线程**的栈打出来，比猜快得多）。
3. 这类"跨线程 + 事件循环"的地方，**"能跑"和"能收"是两件事**：能收到消息 ≠ 能干净收场。

## 五、判据（19 条，`tests/test_messages.py`）

对齐方案 §M0 的五条"先补的失败用例"，逐条点名：

| 方案用例 | 判据 |
|---|---|
| ① 订阅后 publish ⇒ 收到（V1） | `test_publish_reaches_subscribers`（序号要能当 `Last-Event-ID`）+ 无订阅者时只进环 |
| ② 订阅者断开 ⇒ 归零（V4） | hub 级（`unsubscribe` 摘干净）+ **真实路径**（`aclose` 生成器 ⇒ 计数归零） |
| ③ **心跳按间隔到达** | `test_heartbeat_arrives_while_idle`（把 `HEARTBEAT_SECONDS` 压到 0.15s 量） |
| ④ **事件循环重建后仍能 publish** | `test_publish_survives_a_rebuilt_event_loop`（`asyncio.run` 跑两代；顺带钉住"`stop()` 之后不留 asyncio 原语"与"断档期那条留在中转队列里、下一代 `start()` 先清积压"） |
| ⑤ V5 结构判据（token 不进 URL） | 后端半边：`/messages/stream` 与 `_debug/publish` **都不在**公开白名单；结构判据（锚 `apiToken`）在前端半边 M0b |

另外补了四条方案没点、但实现里**已经存在**的行为判据，免得它们无判据空转：类型白名单、
环形有界、跨线程 publish（§8.2 那条）、慢订阅者**丢最旧且最新的还在**（方案 §7 R2 的缓解）。
端到端那条走 `TestClient` + dev token：**401（无 token）→ 200 + 消息进环 → 400（未知类型）**。

⚠️ **HTTP 层刻意不用 `TestClient` 读流**：那要先赌"测试客户端会不会把 `StreamingResponse`
缓冲住"，赌错的表现是整个测试套**挂死**（同一类症状，见 §四）⇒ 分两层测：**生成器直接迭代**
（行为）+ **路由表断言**（接线）；真界面端到端交给 M0b 的探针。

## 六、反向验证 9/9 全红

变异脚本逐字节写回 + sha256 核对 + subprocess `timeout=300`（DEV-LOOP §0.7：变异必须能终止）。

| # | 变异 | 点名判据 |
|---|---|---|
| ① | 不校验类型白名单 | 未知类型两条 |

| ③ | 去掉 dev-only 守卫 | 生产态不该有那条路径 |

| ⑧ | 空闲不发心跳 | 心跳按间隔到达 |
| ⑨ | 注解里的名字没导入（`AsyncIterator`） | 注解判据（见 §七 —— 这条同时证明**新模块真的进了检查集**） |

⚠️ 变异⑥ 的第一版写的是"publish 里直接 `put_nowait` 投给订阅者"，**推演下来它不会红**：
消费端那一刻正阻塞在 `t.join()` 里（循环没在跑、队列上没有等待者），跨线程 `put_nowait`
只是往 deque 里追加，看起来"也能用" ⇒ 判据会空转。两处一起改才对得上：变异改成"要求调用
线程有运行中的事件循环"（`asyncio.get_running_loop()`，T0 那种**真没有循环**的形态），
用例也改成"线程先 `sleep(0.2)` 再发"，保证主协程**真的停在 `await queue.get()` 上**。
