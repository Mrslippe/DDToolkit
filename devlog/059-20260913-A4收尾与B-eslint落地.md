## 一、A-4：抽出 `pages/useVtuberActions.ts`

### 搬什么

`PostsPage` 的 6 个动作回调（`handleFetch` / `handleFetchPosts` / `handleFetchAllPosts` /
`handleUpdatePosts` / `handleDeleteVtuber` / `handleAccountAdded`）+ `fetching` 状态
（它只被这些动作写、被按钮读）。

这 6 个回调是同一套骨架的重复：
「守卫 → `setFetching(true)` → `kickPoll()` → api → 分三种结果提示 →
`finally { setFetching(false); kickPoll() }`」。抽出来之后骨架重复变得显眼，
后续若要收敛成统一包装只需改这一个文件。

`PostsPage.tsx` **1247 → 1128**（−119）；新增 `useVtuberActions.ts` 197。

### 依赖注入而不是 context

`vtuber` / `selectedAccount` / `scene.acc` 都是页面自己持有的状态，项目也没有全局 store
（`FRONTEND-ARCH.md` §A3：局部 state + 事件总线）。按显式入参注入，保持"依赖一眼可见"。

### 一处差点改掉的行为（记下来）

原 `handleDeleteVtuber` 的 `catch` 里除了 `toast.error` 还有 `setConfirmDel(false)`
（失败时收起确认框）。而 `confirmDel` 留在页面侧 —— 第一版我写成 `throw e` 让调用方处理，
**那是行为变更**（会让确认框在失败后保持打开，且抛出未处理的 rejection）。
已改为注入 `onDeleteError: () => setConfirmDel(false)`，与原行为逐字等价。

> 教训与 056 的 `PLATFORM_LABEL` 同源：**搬代码时"看起来更干净"的写法往往是行为变更**。
> 判断标准仍然是那句 —— 能用旧代码跑出"期望的新行为"吗？不能，就不是重构。

### 决策记录：视图 JSX 不再拆 `HeroCardsView` / `PostListView`

原工时估算（各 1.5h / 2h）建立在"cards 957–1013、list 1034–1130"的旧行号上。
抽出类型分组常量与 6 个动作回调后实测：**cards 分支 ~72 行、list ~30 行、
archive/profile 各 ~15 行**，且四者在 JSX 树里是**并列兄弟**而不是独立子树。

拆它们需要**30+ 个 props 透传**（`scene`/`view`/`prefetch`/滚动哨兵/筛选态都深度耦合），
等于把"一个大函数"换成"一个大接口"；而项目没有组件测试运行器，拆完只能靠探针与肉眼，
**而探针本来就覆盖这两个视图**（八段契约含 cards/list/list-video）—— 拆与不拆的回归风险不对称。

**替代方案更划算且已完成**：把能测的抽出来测（`utils/postTypes.ts` 27 条断言）、
把能位级比对的固化（hero 签名）。P2 对该文件的结论是
**1247 → 1128 行 + 可测试面从 0 变成 27 条断言 + 1 个位级护栏** —— 这才是 P2 想要的成果。

## 二、路线 B：eslint 落地

### 为什么是**这套**规则，而不是 `eslint:recommended` 全家桶

本项目的风格已经稳定（`FRONTEND-ARCH.md` §1.4：`!important` 0 处、依赖全在用、
选择器按 feature 前缀分区）——**风格类规则加进来只会制造噪音**。
真正反复咬人的是**行为类问题**，所以只开少数几条：

| 规则 | 级别 | 为什么 |
|---|---|---|
| `react-hooks/exhaustive-deps` | warn | **本项目的历史病灶**：P6-1 回顶 effect 漏 `accountKey`、051 弹窗草稿被后台刷新冲掉、A-2 的 `onDataRefresh` 该不该进依赖 —— 靠人眼必然漏 |
| `react-hooks/rules-of-hooks` | error | hooks 调用顺序是硬约束，违反即崩（A-2 拆分差点踩 TDZ） |
| `@typescript-eslint/no-unused-vars` | warn | 拆巨件最容易留的垃圾（A-3 拆弹窗后 `tsc` 抓到 7 个） |
| `no-debugger` / `no-constant-binary-expression` / `no-unreachable` | error | 零误报的真 bug 类 |

**刻意不开**：格式化类（避免一次性几百行 diff，本批也不引入 prettier，见 §四）、
`no-explicit-any`（项目有少量必要的断言）、`react-refresh/only-export-components`
（`components/ui/*` 与 `common/*` 大量同文件导出常量，属既有结构）。

### 首次运行结果：只有 6 个问题

59 个文件、**1 error + 5 warning** —— 基线比预期干净得多。

- **1 error**（`bootDiag.ts:6` 前导分号）：该文件是 IIFE，`;(function(){…})()` 的前导分号
  是防 ASI 的防御性写法，但此处它**是文件的第一条语句**，确实多余 → 已 `--fix`。
- **5 warning**（`exhaustive-deps`）——**全部是故意保留的"窄依赖"，不是 bug**。
  逐处加了 `eslint-disable-next-line` **并写明理由**：

| 位置 | 依赖写法 | 理由 |
|---|---|---|
| `PostsPage` 列表取数 ×2 | `accountKey` 而非 `selectedAccount` | `accountKey` 是 `id|platform|uid` 稳定代理；用对象引用会在每次 `getVtuber` 回填后重跑而数据未变 |
| `ProfileView` | `selected?.platform_uid` | 同上：`selected` 每次回填都是新引用，会重打第三方索引接口 |
| `LiveCalendar` | 漏 `setDetail` | `useState` setter 引用恒定，漏它不会造成陈旧闭包 |
| `ImageViewer` | 漏 `go`/`requestClose` | 二者是父级**行内箭头**，进依赖会让 keydown 监听每渲染重挂；**登记为已知走查项**，根治应把父级回调包 `useCallback` 而非往依赖里塞裸函数 |

> 关键决定：**不给这 5 处"顺手改成依赖齐全"**。理由与 §一 的教训一致 ——
> 那会改变 effect 重跑时机（属于行为变更），而其中 `ImageViewer` 那处我**没有实测过陈旧闭包**，
> 只能登记、不能声称修好。

### 接入方式

- `npm run lint` → `eslint src --max-warnings 0`（基线已 0 warning，**新增即拦截**）；
- `scripts/dev_check.py` 的 `frontend logic` 一项扩展为
  **eslint + vitest + check_date_range** 三条（标题改为「前端静态与纯逻辑」）。
  理由同 056：**"加了检查但没人跑"等于没加**。

## 四、本批未做（明确记录）

- **prettier**：**用户 2026-09-13 决定不做**（`--write` 会一次性重排几乎每个文件、
  冲掉全部历史 `git blame`）。故路线 B 的"eslint + prettier"里
  **只落 eslint**，并按"行为类规则已足够"收口。
- **视图 JSX 拆分**：见 §一 的决策记录（不拆，理由充分）。
- `ImageViewer` 的 `go`/`requestClose` 走查项（需实测 + 父级 `useCallback`）。
- 探针待办（累计）：② 早退路径现场清理反了；③ 词云断言在上游断供下必然量到 0。

### 收尾：卸掉一个装了但没用的依赖

`eslint-plugin-react-refresh` 是随 eslint 一起装的，但配置里**明确写了不开
`react-refresh/only-export-components`**（`components/ui/*` 与 `common/*` 大量同文件
导出常量，属既有结构）—— 于是它成了"装了不用"的依赖，已 `npm uninstall`。
卸载后 `eslint src --max-warnings 0` 仍为 0 error / 0 warning。

> 这类"装了但配置里没接"的依赖不会报错，只会让 `package.json` 慢慢失真。
> 判断方法很直接：**在配置文件里 grep 一遍包名** —— 只在注释里出现就是没接。

## 五、经验

- **同一类错误在一批里出现两次**（`setConfirmDel`、`PLATFORM_LABEL`）说明这不是偶然：
  搬代码时人的默认倾向是"把通用逻辑放在更通用的地方"，
  而**重构的正确默认是"先让它一模一样"**。两条判断标准都记在这里：
  能用旧代码跑出"期望的新行为"吗？这个"顺手改"能不能单独成一条用例？
- **lint 的规则集要按"这个项目被什么咬过"来选**，而不是抄模板。
  本项目被咬的是 hooks 依赖，所以 `exhaustive-deps` 是核心；风格类一律不开。
- **基线干净时，`--max-warnings 0` 才有意义**：若首次运行有几百条 warning，
  设 0 会让 lint 立刻变成"常年红着没人看"（`test_version_synced_with_devlog` 的教训）。
  本批是"先看全量 → 清到 0 → 再设 0"的顺序。
