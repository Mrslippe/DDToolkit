# 220-20260926-关注主播开播 / 更新动态 → Windows 通知区域气泡

> 用户：「给这个软件增加一个功能，当我关注的主播开播或更新动态时，电脑信息栏弹出弹窗通知」
>
> 一句话边界（实现时自己定的，见 §三）：**只在"新事件"上开口** —— 开播看直播状态边沿，
> 更新动态看自动动态流里"这一轮真的新入库"的帖子；用户自己发起的收录 / 全量 / 手动更新
> 不弹（那是他自己按的按钮，弹通知就是噪音）。

---

## 一、为什么是「通知区域气泡」而不是 Win10/11 原生 Toast

原生 Toast（`Windows.UI.Notifications`）要一个**已注册**的 AppUserModelID —— 开始菜单里
得有对应快捷方式。**未注册的 AUMID 在 Win10/11 上是静默丢弃**：不报错、不显示、日志干净，
跟"通知发出去了"长得一模一样。而本项目的后端是 Tauri 拉起的 PyInstaller 子进程，
安装包里没有这条注册链（要在 NSIS 里造快捷方式 + 固定 AUMID，属于另一个量级的改动）。

`Shell_NotifyIcon`（通知区域气泡）**不需要任何注册**：加一个小图标 → 带上 `NIF_INFO`
就把气泡弹出来 → 显示完摘掉图标。Win10/11 会把它并进操作中心 —— 用户看到的就是
「信息栏弹窗」。

顺带一个约束也满足了：**零第三方依赖**（`winotify` / `plyer` / `winsdk` 都要动
`requirements.txt`，冻结后端得重新装包）。这里只用 ctypes 调 `shell32` / `user32`。

## 二、做了什么

### 2.1 `app/services/notifier.py`（新，约 420 行）

| 关注点 | 做法 |
|---|---|
| 不阻塞抓取 | `notify*()` 只做「判据 + 入队」，真弹窗在**守护线程**里（懒启动）；没有通知时线程不占 CPU |
| 绝不影响抓取 | 非 Windows / 建窗失败 / `Shell_NotifyIcon` 返回 0 / 钩子抛错 —— 一律只记日志；`_notify_live_start_edge` 外面还包了一层 try |
| 文案 | 合成与投递分开：`compose_live_start()` / `compose_new_posts()` 是纯函数（单测直接断言文本），`notify*()` 负责投递 |
| 气泡生命周期 | 首次 `NIM_ADD`（带 `NIF_INFO` 即弹），后续 `NIM_MODIFY` 复用同一个 uID 换文案；空闲 `NOTIFY_BALLOON_LINGER_SECONDS` 后 `NIM_DELETE` **摘掉图标**（通知区域不留垃圾） |
| 平台隔离 | 非 Windows 走"只记日志"分支：代码不许因为平台分支在 import 期就炸 |

### 2.2 两个钩子（都在 `app/services/scheduler.py`）

1. **开播** —— `live_sweep_core`（T0 直播轮询，60s）里的 `live_status` 边沿：
   只报 **0/2 → 1**（B 站 0=未开播 / 1=直播中 / 2=轮播）。下播不报；**首次观测到在播
   也算开播**（否则"新收录的 V 此刻正在直播"永远不提醒）。走 `_notify_live_start_edge()`。
2. **更新动态** —— `PostFetchResult.new_posts`（`_flush_pending` 的**落库成功分支**登记
   小字段摘要，上限 20 条），只有自动动态流 `run_latest_dynamics_sweep` 的 worker 拿它
   去 `notify_new_posts()`。**一个 V 一轮一条**，不是一条帖子一个气泡。

为什么不去 `_route_live_item`（动态流里的开播卡片）也报一次：那会让同一场直播弹两次。
T0 是直播状态的权威源，开播只由它开口；`notifier` 里另有 `live:{平台}:{uid}` 的去重键
兜底（TTL 60s ≈ 一个轮询周期），将来再接入别的信号源也不会重复。

### 2.3 降噪三件套

| 机制 | 参数（settings 可调） | 解决什么 |
|---|---|---|
| 合并 | — | 一个 V 一轮一条：「X 更新了动态」+「B站｜2 条新内容（投稿、动态）：<首条标题>」 |
| 去重 | `NOTIFY_LIVE_DEDUPE_SECONDS=60` / `NOTIFY_POST_DEDUPE_SECONDS=900` | 同一场直播、同一条帖子被两个调用点/两轮抓到都只弹一次 |
| 限流 | `NOTIFY_RATE_MAX=8` / `NOTIFY_RATE_WINDOW_SECONDS=60` | 久别重逢后的开机首轮可能十来个 V 都有新帖；超出的**丢日志不补弹**（补弹十几条气泡比少弹更烦人，内容本来就在库里） |
| 最小间隔 | `NOTIFY_MIN_INTERVAL_SECONDS=1.2` | 连发太快会被 shell 合并 —— 看起来就像"通知丢了" |

关上整个功能：环境变量 `DDTOOLKIT_NOTIFY_ENABLED=0`（只影响通知，抓取/归档照常）。
限流有个细节值得记：**限流判定在记账之前** —— 被限掉的事件不在 `_seen` 里留痕，
否则同一事件重试也永远弹不出来（`test_rate_limit_drops_excess_without_remembering_it` 钉住了这条）。

### 2.4 `scripts/notify_probe.py`（新，真机判据）

队列版通知"投出去就不管"，没有返回值可断言；而通知恰恰**最会安静地失败**。
探针绕开队列，用 `notifier.show_now()` 同步弹一次，把 Win32 结果变成退出码：

```powershell
python scripts/notify_probe.py                # 开播 + 新动态两条示例（文案走生产同款合成函数）
python scripts/notify_probe.py --dry-run      # 只打印文案与后端可用性
python scripts/notify_probe.py --text 标题 正文
```

## 三、口径与边界（明确不做的）

- **不报下播**、不报粉丝数变化、不报抓取完成 —— 用户要的是"开播 / 更新动态"两件事，
  别的一律不弹（本项目已有的顶栏状态胶囊负责"任务在跑"这类信息）；
- **收录 / 全量补档 / 手动更新不弹**：那是用户自己发起的导入，一次可能入库几百条
  （首屏收录、全量回填），弹通知纯粹是噪音；
- **不做气泡点击跳转**：`_NOTIFYICONDATAW` 没有可点击区（气泡点击要靠 `NIN_BALLOONUSERCLICK`
  回调 + 自己开浏览器，属于下一步；`Notification.key` 里留了事件身份，将来接得上）。

## 四、这次踩到的坑（都是"安静地失败"那一类）

1. **`GetModuleHandleW` 在 kernel32，不在 user32**。第一版把绑定全挂在 `user32` 上，
   报 `AttributeError: function 'GetModuleHandleW' not found` —— 这个还算响的错。
   真危险的是同一个坑的变体：**不设 `argtypes`/`restype` 时 ctypes 默认按 int 转换**，
   64 位下 HWND/HICON 指针被截断，调用照样返回，只在你最想不到的时候崩。
2. **WNDPROC 必须持有引用**：`ctypes.WINFUNCTYPE(...)` 的回调对象是垃圾回收的，
   只把它塞进 `WNDCLASSEXW` 而不在 Python 侧留引用 → 窗口过程变野指针。代码里
   存成 `self._wndproc` 并写了注释。
3. **气泡窗口不能是 `HWND_MESSAGE` 消息窗**（消息窗不参与 shell 的图标广播），
   必须是真实的隐藏顶层窗口；且显示期间不能立刻 `NIM_DELETE`（图标一摘气泡跟着消失）。
4. **这台机器上的执行环境没有资源管理器**：`FindWindowW("Shell_TrayWnd")` 返回 0、
   连 `Progman` 都没有 → `Shell_NotifyIcon` 必然返回 0（实测 err = 0x80004005）。
   结论：**气泡本身只能在真实桌面会话里验**（探针就是干这个的），而 Win32 调用协议
   可以在测试里用替身钉死（`_FakeShell32` 断言 ADD → MODIFY → DELETE 的动作序列与字段）。
   这也解释了为什么"探针"在这个项目里值钱：能自动断言的写进测试，只能真机看的写成探针，
   剩下最不该发生的就是"以为验过了"。
