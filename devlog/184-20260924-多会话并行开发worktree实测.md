# 184-20260924-多会话并行开发（worktree 实测）

> **背景**：本仓实际发生过两个会话并行改同一仓，代价是**撞车两次** ——
> `git stash -u` 扫走对方 6 个文件（DEV-LOOP §6.6）；两个会话**都占了 devlog 182**（让到 183）。
> 用户问「是否先 fork 一个分支再合并比较好」，本批把这个问题从经验变成**实测过的判据**。

> **编号说明**：本篇用 184 是**预留**——183 是本会话前一批（小窗面板），
> 182 被另一个会话占用（R45-A/B）。**这正是本批要解决的问题本身。**

---

## 一、结论

| 情况 | 做法 |
|---|---|
| 两边改的**代码文件不重叠** | ✅ 开 `git worktree`（隔离成本远小于收益） |
| 两边都要碰 `ui_probe.py` / `tokens.css` / `TopBar.tsx` 这类枢纽文件 | ❌ 别并行，串行做 |
| 不论哪种 | ⚠️ **动手前分配 devlog 编号段** |

**判据是"改动的文件集合是否重叠"，不是"功能是否独立"。**

## 二、为什么"开个分支"不够

**分支只是指针，一个工作目录同时只能 checkout 一个分支。** 两个会话在同一目录 = 改同一批文件。
要的是 **`git worktree`**：独立目录 + 独立分支，共用同一个 `.git` 对象库。

**隔离性实测**：
- worktree 里的 `.git` 是**文本指针**（`gitdir: …/.git/worktrees/<name>`）；
- 在 worktree 里新建未跟踪文件，**主工作区 `git status` 完全看不到**。

## 三、实测挖出的四个坑

### 坑 1（**最要命**）：新 worktree 开箱**不能编译**

`tauri.conf.json` 的 `bundle.resources` = `["binaries/backend/**/*"]`，
而 `frontend/src-tauri/binaries/` **被 gitignore**（本机 **163 MB**，构建产物）。于是：

```
error: failed to run custom build command for `ddtoolkit v1.0.2`
Caused by: glob pattern binaries/backend/**/* path not found or didn't match any files.
```

**解法（实测有效）**：junction 指回主仓库那份（不复制，省 163 MB）：

```powershell
cmd /c mklink /J "<worktree>\frontend\src-tauri\binaries" "<主仓库>\…\binaries"
```

接上后 `cargo check` **20 秒**通过。

> **可提炼**：**"能 clone 出源码" ≠ "能构建"**。判据是「构建脚本引用的路径里，有没有 gitignore 的东西」——
> 本仓是 `tauri.conf.json` 的 `resources`。新环境第一次构建失败时先查这个，别怀疑编译器。

### 坑 2：别共享 `CARGO_TARGET_DIR`

cargo 对 target 目录**上独占锁** ⇒ 共享会**串行化**（一个编译另一个干等），比各自独立更慢。
本仓现在没配它，**保持这样**。

**成本实测**（打破了"18.9 GB 很贵"的错觉）：

| 项 | 数值 |
|---|---|
| `frontend/src-tauri/target` | **18.9 GB**（debug 16.2 + release 2.7，**增量累积**，不是基线） |
| 新 worktree 冷 `cargo check` | **102 秒**，产出 **1.1 GB** |
| `frontend/node_modules` | 236 MB（要各自 `npm ci`） |

> `[profile.release]` 的 `lto` / `codegen-units=1` **只影响 release**，debug 侧一次冷构建只要 ~100 秒。
> ⚠️ `node_modules` **别 junction 共享**：`node_modules/.vite` 是 dev server 的共享缓存，两个会抢。

### 坑 3：`worktree add` 失败时**分支已经建出来了**

实测：`git worktree add` 因沙箱拒绝而失败，但分支 `wt-test-tmp` 已存在 ⇒ 重试报
`fatal: a branch named 'wt-test-tmp' already exists`。**清理要连分支一起**
（`git worktree prune` + `git branch -D <name>`）。

### 坑 4：worktree 建在仓库**内**会以 `?? _wt-test/` 出现在主工作区 status 里

实测**扫描类脚本不会漏进去**（`gen_doc_numbers` 只扫 `devlog/` 等固定路径），
只是**肉眼会被干扰**。建在仓库外的兄弟目录更干净，但那要写仓库父目录（受限沙箱下需授权）。

## 四、⚠️ 真正的冲突面是**追加型文档**，且**门禁抓不到**

三处必冲突（都是"往末尾追加"，git 无法自动合并）：
`devlog/` 编号 · `ROADMAP-DONE.md` 索引表 · `TODO.md` §6.2 门禁基线。

### ⚠️⚠️ 关键发现：撞号**不会变红**（实测确认，并纠正了我自己的一个错误推断）

`gen_doc_numbers.derive_devlog()` 用 `nums[-1] + 1`（**只排序、不去重、不检查重复**）。
实测（造一个 183 重号文件）：

```
基线                    count=181 max=183 next=184
加了一个 183 重号文件      count=182 max=183 next=184   ← 看不出任何异常
```

`doc_check.py` 同样返回 **`[ok] 无 FAIL`**。

> ⚠️ **我第一版写文档时推断错了**：我以为 `devlog_count` 会"少报一篇"。
> 实测 `count` 数的是**文件数**，重号时它会**正常 +1**（181→182）。
> **推断与实测不符时以实测为准** —— 这条差点作为"事实"写进文档。

⇒ **预先分配编号段是唯一防线。**

**另注**：`count < max` **不一定是撞号**（现有 181 篇覆盖到编号 183，因为 **068 / 161 是缺号**）。
别把缺号误判成重号去"修"。

**合并后的人工检查**（门禁不管这个，已实测有效）：

```powershell
Get-ChildItem devlog -Filter "*.md" | Group-Object { $_.Name.Substring(0,3) } |
  Where-Object Count -gt 1 | ForEach-Object { "重号 $($_.Name)" }
```

## 五、必须各自隔离的运行态

| 资源 | 现状（实测） | 并行时 |
|---|---|---|
| **开发数据目录** | `%APPDATA%\com.ddtoolkit.app-dev`，`config.py` **只认 `DDTOOLKIT_DATA_DIR`** | ⚠️ 两个会话会**写同一个 SQLite** ⇒ 各设自己的 |
| **探针现场** `_ui_probe_tmp/` | `ui_probe.py` 里是 `ROOT / "_ui_probe_tmp"`（**仓库根相对**） | ✅ worktree 一分开**自动解决** |
| **Vite 端口** | 写死 5173 但**未开 `strictPort`** ⇒ 自动递增；探针用 `_free_port()` | ✅ 本来就是动态的 |
