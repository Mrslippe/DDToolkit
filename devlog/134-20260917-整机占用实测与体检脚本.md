## 一、量了什么（口径先说清）

**整棵进程树**，不是后端一个进程 —— `ARCHITECTURE.md` §3.12 量的是后端单进程 128.7MB，
而用户在任务管理器里看到的是壳 + 五六个 WebView2 + 后端 + conhost 一整片。
内存口径 = 性能计数器 `\Process(*)\Working Set - Private`（= 任务管理器「内存」列，
也是用户截图里那个数）；**不用** `GetProcessMemoryInfo().PrivateUsage`（那是私有提交，差 5~15MB）。

| 指标 | 实测（Ryzen 5 5600GT 6C12T / 14GB / 便携版 1.0.2 / 空数据目录；**四轮独立跑的区间**） |
|---|---|
| 点图标 → 后端就绪 | **首启 3.1–4.4s**（含 17 步迁移 742ms）/ **热启动 2.2–2.9s** |
| 其中 `import app.main` | 热启 **855–1207ms**（最大单块：SQLAlchemy/Alembic/FastAPI 的 import 地板） |
| 整机私有工作集（空闲） | **243.2–256.7 MB** = 后端 83.4–96.7 + **WebView2 六个进程 143–152** + 壳 8.9–10.5 + conhost 1 |
| 线程 / 句柄 | **194–199 / 4301–4582**（后端 12 线程，其余几乎全是 Chromium 多进程） |
| 空闲 CPU | **0.86–1.19s / 45–60s ≈ 1.4–2.0% 单核**（含首启扫码轮询；抓取是定时器节奏，与算力无关） |
| **托盘深休眠后** | 进程 **9 → 3**、私有工作集 **230.5–250.6 → 91.5–92.5 MB（省 139–158）** —— 只剩后端 + 壳 + conhost |
| 磁盘 | 便携解压 **135 MB** / 安装包 57.5 MB；空库数据目录 0.6 MB（真实使用约 160MB） |
| **单核亲和**（弱 CPU 代理） | 后端同目录**再启动**：**×1.47**（三个样本 ×1.25 / ×1.47 / ×1.74，量级一致） |

**诚实边界**（写进 `ARCHITECTURE.md` §3.13，不许当成"低配机实测"）：
没在 2 核 / 4GB / HDD 真机上跑过；没量 GPU 软件渲染路径；没量**真实库（8V/11 账号）**的空闲 CPU。
单核亲和只是**削并行度**，不削单核主频/IPC。

## 二、尺子自己的三个坑（都是"看着像数，其实是错数"）

1. **端口取了第一条** ⇒ 深休眠那步连到**上一轮已经死掉**的端口（`WinError 10061`）。
   多轮启动的日志是**追加**的，boot 行有好几条 ⇒ 必须取**最后一条**（`parse_port` + 单测钉住）。
2. **亲和实验没热身**：空库首启要跑 17 步 Alembic 迁移，那一步在单核上 742ms → **4951ms**，
   把"import 路径"的信号整个淹掉（第一版量出 ×2.65 的假结论）。
   改成**每种模式先热身一轮再量**（同目录再启动，迁移已是 no-op）。
3. **⚠️ 最严重的一个：尺子读空了，却被当成「进程 0 个 / 省 232MB」。**
   PowerShell 的终止性错误走 stderr，而 `-EncodedCommand` 这条路的**退出码不可靠** ——
   实测出现过「rc=0 + stdout 空」，我的解析直接当成空数组 ⇒ 打出一排 0。
   我一度据此怀疑**应用在深休眠后整个退出了**（那会是个真 bug：托盘常驻的意义就是后台继续抓）。
   澄清它靠的是**应用自己的 stdout**（`Start-Process -RedirectStandardOutput` 抓下来）：

   ```
   [ddtoolkit] 已隐藏到托盘（后台抓取继续）
   [ddtoolkit] WindowEvent[main] CloseRequested
   [ddtoolkit] 深休眠：已销毁界面释放内存（后台抓取不受影响）
   [ddtoolkit] WindowEvent[main] Destroyed
   [ddtoolkit] RunEvent::ExitRequested code=None → 拦下（托盘常驻）
   ```
   + 60 秒里壳与后端**一直在**（pid 不变），只有 WebView2 的进程没了 ⇒ **应用是对的，尺子是错的**。
   **修法**：采样脚本全程 try/catch 并**总是输出 JSON**（带 `ok` / `error` / `tree` / `rows`），
   Python 侧区分三态 —— ① 树里没进程（真没了）② 树里有进程但计数器读不到（**重试，仍读不到就抛**）
   ③ 读到（正常）；空 stdout 一律当失败，**绝不退化成一排 0**。

## 三、测试残留 504MB：`TempRoot` 让目录自己删自己

用户报"低配"时我顺手看了一眼 `%TEMP%`：**215 个残留目录 / 504MB**
（`ddtk-mig-*` 138 / `ddtk-ptr-*` 57 / `ddtk-shelllog-*` 14 / 其余临时脚本），
`cargo test` 每跑一次再堆一批 —— `migrate.rs` / `datadir.rs` / `shelllog.rs` 三处用例的
`temp_root()` **只建不删**。

- 修法不是"每个用例末尾手写 `remove_dir_all`"（漏一个就回到原样），而是新增
  `src/testtmp.rs::TempRoot` —— **`Drop` 时自删**（用例 panic 也会走到，测试档是 unwind），
  `Deref<Target = Path>` 让调用点几乎不用改（`root.join("x")`、`log(&root, …)` 照旧）。
- `Drop` 两条路都收拾：`remove_dir_all` 失败再 `remove_file`
  （`shelllog` 的失败路径用例**把 `root` 本身写成文件**，只删目录会漏）。
- ⚠️ 一处需要人改的：`migrate.rs` 里 `let outer = root.clone();` 原意是拿 `PathBuf`，
  克隆守卫会**双重删除** ⇒ 改成 `root.to_path_buf()`。
- **验证**：`cargo test` 前后数 `%TEMP%\ddtk-*` —— 本次新增 **0 个**（31 passed，含 `TempRoot` 自身 3 条）。
