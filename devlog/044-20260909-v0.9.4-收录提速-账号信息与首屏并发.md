# 044-20260909-v0.9.4-收录提速：账号信息 ∥ 首屏内容 + 共享 SSL 上下文

> 用户 2026-09-09 需求：「添加一个新 v 的时候信息抓取能够尽可能地快，所以整个抓取
> 链路可以优化地比较短，在保证必要信息获取的前提下提高处理速度。」
>
> 实施前给出方案过目，三个决策点全部取推荐项：
> ① 首屏抓取 = 投稿 1 页（≤30 条）+ 动态 1 页限 3 条；
> ② 头像延后异步下载（不挡首屏）；
> ③ 「给已有 V 添加账号」也只抓新账号 + 首屏。

## 一、问题：旧链路每一段都在浪费

`POST /vtuber/adopt` 之后走两个**顺序** BackgroundTask：

```
① _fetch_adopted → scheduler.async_fetch_vtuber(vtuber_id)     账号锁
② _backfill_adopted_history → run_external_interval("daily")   无锁
```

单账号时序（新收录必然 1 个账号），逐条对照代码：

| # | 步骤 | 位置 | 耗时 |
|---|---|---|---|
| 1 | 抢账号锁（自动档在跑则等一个轮次断点） | `_acquire_manual_account` | 0~8s |
| 2 | WBI 密钥（缓存 30min，**冷启动多一次 nav**） | `wbi.get_wbi_keys` | 0 / +0.3~1s |
| 3 | `acc/info` → **串行** → `relation/stat` | `platforms/bilibili.py` | 0.6~2.5s |
| 4 | 头像下载（**阻塞在 commit 之前**） | `_download_avatar` | 0.5~2s |
| 5 | **无条件 `sleep(3~5s)`，最后一个账号也睡** | `async_fetch_vtuber` | **3~5s** |
| 6 | commit + 推送快照 | 同上 | ~10ms |
| 7 | 前端 3s 轮询看到 | `TopBar` | 0~3s |

→ 可感知 **5~12s（典型 7s）**；而且**帖子一条都不抓**（右栏「暂无帖子」要等
15 分钟的综合档动态流或用户手点），第三方历史还占着同一个 HTTP 后台槽位。
另有稳健性缺口：另一个**手动**任务持锁时（例如刚点了「抓取账号」批量），
`_acquire_manual_account` 直接返回 False → 记一行「已跳过」→ 新 V 的账号信息
要等 24h 数据到期或重启。

## 二、方案落地

### A. 账号信息关键路径

1. **`async_fetch_accounts(account_ids, fast=True)`**（新）：按 id 精确抓取。
   收录 / 加账号只抓新增的那一个账号；`async_fetch_vtuber` 退化为「查 id → 调它」
   的薄壳，仍供前端「抓取账号」按钮（= 该 V 全部账号）。
2. **去掉末尾 3~5s 空转**：节流只在账号之间生效（`idx < len-1`），
   fast 模式间隔 `MANUAL_FAST_INTERVAL_MIN/MAX`（0.5~1s），抓完立即 commit + 推送。
3. **B 站两次请求并行**：`BilibiliPlatform.fetch_user_info` 改
   `asyncio.gather(acc/info, relation/stat)`（两者互不依赖）。
4. **头像延后下载**：`_fetch_one_account(..., pending_avatar=[])` 只写 `avatar_url`
   并把 URL 交给调用方；commit + 推送快照后 `asyncio.create_task(_deferred_avatar(...))`
   —— 该任务**只 UPDATE `avatar_path` 一列**（不碰其它字段，避免与并发抓取互相覆盖），
   完成后再推一次快照，前端 `account-progress` 内容 diff 就地替换头像（零请求）。
   账号在下载期间被删（UPDATE 影响 0 行）或下载失败 → 只记日志，`_avatar_missing`
   下次抓取自动补。
5. **WBI 冷启动预热**：`main.py` lifespan 起 `_warm_wbi()`（1 请求，异常自吞），
   与 `auth.run_maintenance` 并行；首次收录不再多付一次 nav 往返。

### B. 首屏内容抓取（新）

`async_fetch_first_screen(account_id)`：对该账号跑一次**有界**抓取

```
video_pages=FIRST_SCREEN_VIDEO_PAGES(1)      # 投稿 1 页 ≤30 条，列表接口自带
dynamics_pages=FIRST_SCREEN_DYNAMICS_PAGES(1) # 封面/时长/统计，无逐条详情请求
limit_latest=FIRST_SCREEN_DYNAMICS_LIMIT(3)   # 动态最多 3 条新帖（每条 1 次详情）
stop_on_existing=True
```

- 走 `_post_fetch_lock` + 手动优先；复用风控/归档/墓碑全套逻辑；
- `limit_latest` 同时给到单流平台（微博 `_fetch_platform_posts` 新增同名参数），
  两条实现口径一致；
- 完成汇总写 `post.last_result`（新 `kind="adopt"`）→ 顶栏胶囊
  「新 V 首屏抓取完成 · 投稿 N · 动态 N · 入库 N」；
- 后续补全交给既有 15min 动态流 / 手动全量（`stop_on_existing` 首页即停，无重复请求）。

### C. 三条支路同时起跑，第三方历史脱离关键路径

`routers/vtuber.py::_adopt_background(vtuber_id, account_id)`：

```python
_spawn_background(_backfill_adopted_history(account_id))        # 无锁、先起跑
await asyncio.gather(async_fetch_accounts([account_id], ...),   # 账号锁
                     async_fetch_first_screen(account_id),      # 帖子锁
                     return_exceptions=True)
```

两把锁独立，墙钟 ≈ max(两条关键路径) 而不是相加；第三方回填（zeroroku 粉丝历史 +
礼物日、danmakus 场次，各 25s 超时）与关键路径**并行**，不再占着 HTTP 后台槽位。

**用户复核反馈（同日）**：「添加新 v 的时候没有进行粉丝趋势、直播场次信息的外部任务
抓取是吗？我从控制台日志中看见添加新 v 的手动任务和外部任务并没有连在一起。」

排查结论：**任务确实跑了**（dev 日志 03:43:23 `zeroroku fan_history: 1265680561 新增
1627 行`、03:43:57 `danmakus live_sessions: 1265680561 新增 1349`、03:43:57
`收录回填 account#22 完成`；库里核对 snapshots source=zeroroku 1627 行、
live_sessions source=danmakus 1349 条）。「不连在一起」是两个原因：

1. 回填原来排在 `gather` **之后**才 spawn，而首屏抓取要 6s+；
2. 首条外部日志要等第三方响应（本次 zeroroku history 花了 ~14s），中间还夹着
   综合档让位后继续跑的动态流日志。

修正：回填改到 `gather` **之前** spawn（三条支路同时起跑），并在任务开头打
「收录回填开始 account#N」——日志链路连成一条，数据也早 ~20s 到位。
同时修掉一个潜在静默丢失：`asyncio.create_task()` 的返回值必须保留强引用
（Python 文档警告任务可能在执行中被 GC 回收），统一走 `_spawn_background()`
（`_background_tasks` 集合 + done 回调）。

顺带：那次 `zeroroku gifts 账号异常 1265680561: ` 后面的错误信息是空的
（`TimeoutException` 的 `str()` 为空）→ 三处外部源账号级异常日志补上
`{type(e).__name__}`；该端点随后手工探测正常（6.6s / HTTP 200），属第三方瞬时慢，
该账号 `live_gift_days` 仍为 0 行，下次每日批次会补。

### C2. 外部任务进状态通道 + 完成事件（同日第二次反馈）

用户：「需要在这些外部任务执行的时候也在状态栏胶囊中展示，同时完成回填后发出事件
让卡片刷新，不然用户如果一直停留在 archive 视图不主动刷新，卡片就一直保持无数据的原状了。」

问题根源：外部回填**不占两把锁**，因此旧的状态通道里根本没有它 ——
① 顶栏看不到进度；② 更严重的是「完成」这件事前端完全感知不到：
   `fetch-idle` 只由「抓取任务 running→idle 边沿」派发，而收录时那个边沿在
   03:43:00（账号信息结束）就发生过了，回填 03:43:57 才结束 → 档案视图的
   粉丝趋势/直播日历卡片永远停在空态。

改法：

- `_status["external"] = {running, label, last_label, seq}` +
  `external_task_started(token, label)` / `external_task_finished(token)`：
  token 用 `adopt:{account_id}` / `daily` / `weekly` 区分，并发时 label 用「、」合并，
  全部结束才置 `running=False`；
- **`seq` 每次结束自增**——前端不看 running 边沿，而是比对 `external.seq`：
  短任务在两次轮询之间跑完也不会漏（这正是边沿方案的死穴）；
- 顶栏 `TopBar`：`busy`/`active` 纳入 `external.running`（状态胶囊显示
  「正在同步{label}」，轮询提到 3s），但**抓取任务的 running→idle 边沿仍只算
  account/post** —— 否则新 V 的首屏内容要等回填结束（~20s）才刷新出来；
- 完成时：弹一条「{last_label}同步完成」胶囊 + 派发 `ddtoolkit:fetch-idle` →
  `PostsPage.refreshTick` 自增 → `LiveCalendar` / `FanTrendChart` / `ProfileView` 重拉；
- 外部任务不参与 `setFetchBusy`：它不占锁，用户仍可手动抓取，不该被禁用按钮挡住。

### D. 抢锁失败排队兜底

`_acquire_manual_account/post` 失败时不再静默丢弃：把 account_id 放进
`_pending_account_ids` / `_pending_first_screen_ids`，由综合档心跳
（`TIER_TICK_SECONDS=10s`）在锁空闲时优先消费（`_drain_pending_fetches()`）；
消费时若又有任务在跑则放回队列下个心跳再试。→ 无论用户当时在跑批量抓取
还是别的 V 的抓取，新 V 都会在 ≤10s 内被抓到。

### E. 顺带发现的通用瓶颈：`httpx.AsyncClient()` 每次构造 ~1s

基准脚本打点发现收录链路起手就有 ~2s 空白：`httpx.AsyncClient()` 每次都会
新建 `ssl.SSLContext` 并 `load_verify_locations`（本机 cProfile 实测 ~1.16s/3 个
上下文，**同步阻塞**事件循环）。新增 `app/core/http.py`：

- `ssl_context()`：进程级缓存的 SSL 上下文（等价 httpx 默认：certifi 证书链，
  尊重 `SSL_CERT_FILE` / `SSL_CERT_DIR`）；
- `new_async_client(timeout, **kw)`：`httpx.AsyncClient(..., verify=ssl_context())`。

全仓 23 处客户端构造统一替换（scheduler / fetcher / wbi / auth / weibo_auth /
externals）。实测单客户端构造 **982ms → 0~61ms**；SSLContext 与事件循环无关，
因此在「每个档位 `asyncio.run()` 各起一个循环」的调度模型下也能安全共享。
副作用：测试套件 101s → 14s。

## 五、经验

- **关键路径上的「礼貌性 sleep」要跟着路径语义走**：账号流里 3~5s 是给平台留的
  速率余量，但手动单 V / 收录只有 1~2 个账号，最后那个账号还要睡就是在白等。
  节流应写成「元素之间」而不是「每个元素之后」。
- **头像这类"体积大、可延后"的字段不该挡首屏**：先落字段、后补文件、再推一次
  快照，比让它挡在 commit 前面划算得多（前端已有的快照合并机制天然支持二次更新）。
- **库的隐式开销要用打点找，不要猜**：httpx 客户端构造 1s 完全不在预期里，
  是基准脚本的 `+2.1s 空白` 暴露出来的；缓存 SSLContext 是零风险的一刀。
- **「跳过」在用户视角等于丢数据**：凡是用户动作直接触发的抓取，抢锁失败都应
  排队而不是丢弃；排队消费点放在已有的调度心跳里最省事。
- **fire-and-forget 要留强引用**：`asyncio.create_task` 的返回值不保留引用时，
  任务可能被 GC 回收 —— 这类 bug 的表现正是「日志里什么都没有」，与用户反馈的
  症状完全一样，值得优先排查。
- **日志是产品的一部分**：把任务拆成并行支路后，用户是靠日志判断「有没有跑」的；
  拆并行的同时必须补「开始/结束」打点，否则功能变快了、可观测性反而变差。
