# 329-20261004 分P：以前只播第 1 P，7 P 的实况只剩第一段

> 由来：`devlog/327` 那批修完后顺手发现"库里 `#4919` 标称 02:13:30、实际流 76:27"。
> 查下去是**真 bug**：B站一个视频可以有多个 P，我们**永远只播第 1 P**。

## 一、调查结论（只读取证，17 次 `view` + 2 次 `playurl`）

```
BV1esa36qEPX 《泽音和沐霂 实况》 view.duration=28526s(7:55:26) videos=7 top-level cid=42274916156
   P1 4587s ★ = top-level cid     P2 3423 P3 3416 P4 4579 P5 3528 P6 3323 P7 5670
BV1Qf8i6eEyA 《塔菲 原神狼人杀》 view.duration=15262s(4:14:22) videos=4   我们只播 P1（3544s）
```

- `view` 顶层 `cid` **就是第 1 P**，`view.duration` 是**各 P 之和**；
- `bili_play.resolve_video()` 只取顶层 `cid`，`play_info` 把它交给 playurl ⇒ **永远 P1**；
- 影响面：库里"标称 ≥ 40 分钟"的 15 条候选里 **5 条是多P**（如 `#3308` 标称 405:03、实际只播 50:56）；
- `#4919` 那个奇怪的 `02:13:30` = P1+P2 之和 ⇒ 抓取快照是"当时只有 2 P 的总时长"，UP 后来补到 7 P。

**用户看到什么**：进度条/总时长是**对的**（MSE 用段表时长、渐进式用元素时长）；
真正的异常是"**只有第 1 P 能看**"—— 6.6 小时的内容在应用里只剩 76 分钟，而且**没有任何入口或提示**。

## 二、这一批做了什么

| 层 | 改动 |
|---|---|
| `bili_play.resolve_video` | 带出 `pages[{cid,page,part,duration_s}]`（1h 缓存照旧） |
| `bili_play.play_info` | 新增 `cid` 参数；`_pick_page()` 决定播哪一 P（不传 = 第 1 P，**老行为不变**）；**缓存键加上 cid** |
| `GET /bili/play` | 新增 `cid` 查询参数；响应带 `pages` + `page`（前端不必再跑一趟） |
| `GET /bili/segments` | 同样接 `cid` —— 段表与播放地址**必须是同一条流** |
| `BiliVideo` | `load({qn, cid})`：切 P = 重取流（与换清晰度同一条路；**带上当前档**，别悄悄回到默认） |
| `VideoPlayer` | 新增「分P」菜单（hover/点击同清晰度那套），`pages.length > 1` 才渲染；按钮显示 `P{n}` |

两条纪律：
- **不传 cid ⇒ 第 1 P**：老行为一字不改（老前端/老缓存都不受影响）；
- **要的那一 P 不在这个视频里 ⇒ 如实 `not_found`**（别静默播 P1 —— 那会让人以为切成功了）。

## 三、判据

- 后端 3 条（`test_bili_play.py`）：`pages` 要从 view 带出来；**指定 cid 必须发进 playurl 且不能被
  P1 的缓存命中**（缓存键少 cid 的表现正是"点了 P2、播的还是 P1"）；未知 cid ⇒ `not_found` 且消息里有那个数。
- 路由 2 条（`test_vtuber_api.py`）：`/bili/play` 的 `cid` 原样接到服务层（6 组参数化，含 `?qn=64&cid=333`）；
  `/bili/segments` 的 `cid` 同样要接（段表与地址对不上会退化成 `devlog/327` 那类"取回来落不下"）。
- 前端 3 条：多P 渲染菜单且点 P2 回调 `onPickPage(222)`；单P **不渲染**菜单；`BiliVideo` 切 P 的
  第二次取流**带 `cid: 222` 与当前 `qn`**。

后端 1107 → 1112 passed；前端 930 → 933 passed。
