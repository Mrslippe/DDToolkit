# 538-20261019-采集结果弹窗与采集/分析解耦

用户第 2 条："采集完成后要弹出提示框显示采集结果，以及没有采集到的原因，同时把采集和分析分开"。
按 **解耦 → 失败明细 → 弹窗** 的顺序做。
## 一、采集与分析解耦
轮询发现采集结束时会顺手 `void loadRanked()` —— 用户没点「分析」就自己开始算了。
去掉那一行，改为 `setSummary(p)` 弹结果。**要不要分析由用户按按钮决定。**
（这条很便宜，但它是"自动跳"困扰的根源，先做掉。）

## 二、逐场失败原因（后端）

`CollectProgress` 之前只有一个 `failed` 计数，**拿不到"哪几场没采到、为什么"**。新增：

```python
failures: list[dict[str, Any]] = field(default_factory=list)   # [{live_id, start_at, reason}]
```
两个失败点各自写入原因：
| 失败点 | reason 文案 |
|---|---|
| 上游没返回弹幕 | 上游没有返回该场的弹幕（可能已下架或接口无数据） |
| 记录数不足 | 记录太少（N 条，低于下限 MIN_RECORDS） |

`as_dict()` 一并透出。状态端点是直接返回 `as_dict()`，**不需要改路由模型**。

## 三、结果弹窗（前端）
采集结束（done / failed / cancelled）→ `AlertDialog`：
- 一行汇总：成功 X 场 · 跳过 Y 场（已采过）· 失败 Z 场 + 后端 message
- 有失败时列出**逐场原因**（时间 + 原因，超 40 条截断并说明）
- 只有「知道了」一个动作 —— 不在这里顺手触发分析

## 四、一处我自己踩的坑

给 `FanCollectProgress` 加字段时，我用 `skipped: number` 当锚点 —— 但它在文件里**出现多次**，
补丁插进了另一个接口，tsc 报 `Property 'failures' does not exist`。
改成**定位接口块体、在收尾括号前插入**，并校验"恰好出现一次"。
