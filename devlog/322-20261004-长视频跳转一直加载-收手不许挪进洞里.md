# 322-20261004 长视频跳转"一直加载"：收手不许把播放点挪进洞里 + 卡住看门狗

> 用户口径：「点击长视频（40min+）进度条进行跳转的时候出现了一直加载的问题，例如泽音melody的最新投稿」。

## 一、真机现场（全部从 `logs/app.log` 读出来的）

那条视频的段表**是完整的**、数据**取得回来**，可就是画不出：

```
15:23:46 段表 cn-gddg-ct-01-11 段数=918 段长≈5.0s 总时长≈4586.97s init=933B   ← 76 分钟，覆盖完整
15:23:47 audio 段 -1 取不到（HTTP 503），换镜像 1                                ← 音频 init 换过镜像
15:23:49 代理 range=bytes=445565881-447627857 status=206 首字节=32ms …（连续 5 段目标段，全部 206）
15:23:58 跳转 2808.3s 落地：用时=10.0s 缓冲=0.0s 段取=17次
15:23:58 跳转 2808.3s 等了 10s 仍无数据 —— 先把播放点挪过去（别让界面一直转圈）
15:24:03 [video] seek→1462.5s 判定=数据受限 起播=未出画 解码=0.0fps 提交=0.0fps   ← 挪过去之后仍是转圈
```

再数一遍代理侧：那一轮 **video 取数 73 次、audio 26 次**，而 audio 的 26 次**全部集中在开播那 0.2 秒**
（init + 第 0/1/2 段）。也就是说：**音频轨在跳转期间一次取数都没发**，目标位置永远只有视频、
没有音频 ⇒ 元素级缓冲（两条轨的交集）为空 ⇒ 转圈到天荒地老。

## 二、排除掉的（免得下一轮再查一遍）

| 假设 | 实测 |
|---|---|
| 段表不覆盖长视频 | 918 段 / 4587s，覆盖完整 |
| 取错了字节（时间→字节映射错） | 段表算出的起点与段自己的 `tfdt` **逐点一致**（短 427s 与长 4846s 各验 5–7 个点，差 0.00s；音频 ≤0.46s 是 3 位小数舍入） |
| 换镜像后布局不同 | 同一条流的 3 条镜像**逐段字节区间完全一致**（video 970 段 / audio 967 段，0 处不同） |
| 上游忽略 Range、长度不符 | 没有一行"数据不对"；代理全部 206 且长度与请求一致 |
| 配额 / append 报错 | 日志无 |

## 三、改了什么（两条真缺陷，与"音频为什么停手"这个根因无关地站得住）

1. **收手不许把播放点挪进洞里**（`mseKernel.ts` 的 seek 收手分支）。
   ⚠️ 顺带纠正一个想当然的判据：`!ready` 的**定义**就是"每条轨都没覆盖目标"，
   所以老代码那句"先把播放点挪过去"在这一分支里**不可能**"还有数据可放" ——
   设 `currentTime` 只是把时间扔进洞里：元素停在等数据、**内核也不再重试** ⇒ 永远转圈。
   新口径：收掉卡住的操作重开一个等待窗口（`SEEK_GIVEUP_RETRIES=1`），仍没有就 `fail`
   ⇒ 调用方退回渐进式（长视频上渐进式只是"跳转后追赶一下"，比永远转圈好得多）。
2. **卡住看门狗**（`STUCK_OP_MS=6000`）：一条轨的取数/append 迟迟不回执时，先记一行现场
   （手上是什么操作、这条轨缓冲到哪、段表多大、目标该落第几段），再 `abort` 取数或 `sb.abort()`
   收手；再一个窗口还卡 ⇒ 认输。**这条正是为了"音频轨停手却一行日志都没有"**。
3. 收手行改成 `seekDetail`：每轨 `[可用=… 区间=… 手上=… 该取=n/N 重试=/重复=/无进展=]` ——
   下一次复现不用再猜是哪一种。

## 四、判据（`mseKernel.test.ts`，两条都反向验证过）

- 「一条轨都没数据 ⇒ 收手重试，仍没有就认输」：断言 `onSeekApplied` **没被调**、
  `el.currentTime` 没被设成目标、`onFatal` 被调、且那一行现场里带 `该取=`/`区间=无`。
  反向：把收手分支改回"挪过去"⇒ 红（`把播放点挪到一个没有数据的位置 = 还是转圈`）。
- 「轨卡在操作上 ⇒ 记一行现场并收手；收不掉就认输」：假 SourceBuffer 的
  `appendBuffer`/`remove` 永不回执 `updateend` ⇒ 断言出现 `轨卡住` 行且最终 `onFatal`。
  反向：摘掉看门狗 ⇒ 红（日志里一行都没有 = 静默空转）。

## 五、还没定论（诚实记一笔）

音频轨**为什么**停手，上面这些都不在已排除项里。可能是"卡在某个不回执的操作上"（看门狗能自愈），
也可能是"泵根本没为它算过目标"（那时新加的那行会显示 `手上=-` 且各项计数为 0）。
用户下次遇到时，日志里那行 `仍**一条轨都没有数据**（audio[…]）` 会直接定位 —— 不用再猜。
