# 166-20260923-文档数字门禁 + devlog 索引瘦身

> 起因（用户 2026-09-23）：两个痛点 —— ①「一个 agent 做重需求时我没法并行开发其他功能」；
> ②「devlog 是早期边学边开发的方法，现在看没太多实际用途，反而徒增无效信息」。
> 排查下来这两个是**同一个问题**：每次改动的固定文档成本太高 —— 它既制造了并行时的抢写点
> （`devlog/` 编号 + `ROADMAP-DONE` 索引），又把会话拖长。
> 本批按用户拍板的顺序 **② 派生自动化 → ③ 风险分档 → ① 提炼闭环** 落地。

---

## 一、先纠一个误判：devlog 不是"无效信息"

抽样最近 10 篇逐条判据实测（四条判据：有无架构决策 / 有无事故或反直觉结论 / 有无可复用教训 / 是否主要是变更叙述）：

| 判据 | 结果 |
|---|---|
| 含架构/技术决策 | **9 / 10** |
| 含事故或反直觉结论 | **10 / 10** |
| 含可复用经验教训 | **10 / 10** |
| **主要是变更叙述** | **0 / 10** |

**我原本的假设（"大部分是流水账"）被数据推翻了。** 真正的问题不是"有没有用"，是**取不出来**：
163 篇 / 32 万字，同一个坑散在多处（「尺子坑」在 `devlog/155`、`devlog/159` 与 `DEV-LOOP.md` 共 3 处）。

⇒ 所以 ① 的落点是**提炼闭环**，不是"少写"。**devlog 仍每批次一篇。**

## 二、② 派生自动化：`scripts/gen_doc_numbers.py`

活文档里散着一批**描述当前状态**的数字（迁移 head / 表数 / 路由数 / 下一篇 devlog 编号），
一直靠人肉手抄。本批把它们改成**从代码派生 + 门禁比对**。

### 实测战果：36 处漂移，跨 11 个文件

| 漂移 | 处数 | 例 |
|---|---|---|
| 迁移 head `f006` → **`f007`** | 9 | `ARCHITECTURE` / `GLOSSARY` / `README` / 两个技能 |
| 迁移版本数 19 → **20** | 6 | 同上 |
| 路由装饰器 63 → **64** | 4 | 含技能里写死的 58 |
| 表数 11 → **12** | 3 | 两个技能 |
| Repository 11 → **12** | 2 | 文档里 11 与 12 打架，实测类数 12 |
| **devlog 下一篇 098 → 166** | 2 | `ddtoolkit-docs-devlog` 技能落后 **68 篇** |
| 迁移表缺 `f007` 行 | 2 | 两张表都补了 |

顺带重数了路由三口径：**装饰器 64 / `app.routes` 70 / 方法×路径 67**（文档写 63 = 66，技能写 58/64/69）。

### 关键设计：登记表是**白名单**，不是全文搜索

`f006` 在本仓有 20+ 处提及，其中**大多数是正确的历史引用**（"`profile_cards` 由 f006 引入"）——
改它们反而错。所以只认明确指当前状态的写法（`MIGRATION_HEAD = fNNN` / `a001 → fNNN` /
`N 张表` / `N 个路由装饰器` / `下一篇 … NNN`），并配了**误报防线用例**
（`test_historical_mentions_are_not_flagged`）。

### 用例数**不设门禁**（有实测依据）

派生器能数出 `def test_` 的**静态条数 560**，而实跑 `passed` 是 **578** —— 差的 18 条是参数化展开。
两者不等 ⇒ 拿静态数当判据必然假红。用例数的真源仍是 `TODO.md` §6.2，**现场实跑优先**。

## 四、① 提炼闭环（写进 §3）

每条**脱离本批次仍成立**的经验，必须落到三个去处之一，devlog 里留指针：

| 经验类型 | 落到哪 |
|---|---|
| 不变量 | `ARCHITECTURE.md` §6（带 `devlog/0NN` 出处） |
| 坑 / 测量方法论 | `DEV-LOOP.md` |
| 设计原理 | 对应 `docs/design-*.md` |

判据一句话：**这条经验三个月后还成立吗？** 并写明：**同一个坑不要在多篇 devlog 各记一遍。**

## 五、索引瘦身：`ROADMAP-DONE.md` 241KB → 106KB（−56%）

「批次 → devlog 索引」段的第一列漂成了 **600–1900 字符的巨型单元格**，占了那个文件 **60%**
（表头本来只是 `| 版本 · 批次 | devlog |`）—— 瘦身是**恢复设计本意**。

- **122 行**改为短标签（中位 **35** 字符）；
- 2 行（R40d / R40e）**没有独立 devlog**，编号列改填**提交短哈希**（`c729ea3` / `e352fb2`）；
- 8 行范围行（`024–026`）本就如此，留原样；
- **再无巨型行**（最长 151 是合法长标签）。

新增门禁 `INDEX_LABEL_MAX = 240`：第一列超长 → FAIL，防止漂回去。

## 七、⚠️ 如实标注（本批我自己犯的四个错）

1. **派生器首版自己算错了** —— 漏算 `@router.api_route(...)`，把 64 数成 62。
   **这正是"派生脆性"，而第一个踩的是我。** 已修 + 加回归用例 `test_route_count_includes_api_route`。
2. **pattern 太宽，自己制造误报** —— 迁移表同一行有历史编号与当前 head 两个编号，lookahead
   匹配到了第一个。已收紧成"取 `当前 head` 之前**最后**一个编号" + 加用例。
3. **`index_rows()` 切段切错了** —— 用 `text.find("批次 → devlog 索引")`，而**这几个字在文件开头
   导语里也出现过**（第 8 行），于是它一路扫到文件尾（覆盖 802 行，正确范围只有 153 行）。
   结果碰巧一致（别的表没有 `| NNN |` 结尾的行），但那是**碰巧对**。已改为按 `## ` 标题切段 + 加用例。
4. **两次"从局部证据推全局结论"** ——
   - 看到 `frontend/node_modules` 没有 playwright，就断言 `ui_probe.py` 跑不了 ——
     实际它**只用标准库 + 系统 Edge**，一行 playwright 都没提（实跑全过）；
   - 看到 R40d/R40e 没有 devlog 文件，就断言"索引行是唯一记录"、不敢瘦身 ——
     实际它们的 **commit message 有 655 / 815 字符**，与索引行长度几乎 1:1，抄进索引是纯重复。
     ⇒ **判断"细节会不会丢"时要连 git 一起看**（已写进技能 §6）。

**未跑 1 项**：`capability_matrix.py --include-content` 全量。默认 4 接口已实测通过；
全量**必须按 devlog/085 的口径在「冷进程 + 空数据目录 + 显式清空凭据」下跑**，
否则本机登录态会让结论完全反过来；且脚本自述「匿名打内容接口会触发 IP 级 412，别勤跑」
⇒ **不该顺手跑，要在知道代价的前提下专门跑。**
