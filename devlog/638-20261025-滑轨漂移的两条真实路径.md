# 638-20261025-滑轨漂移的两条真实路径（前两次修的都是错的）

用户连报三次"还是会漂"。这次读完全部写入点，找到两条**必然**导致漂移的路径。

## 路径一：`clamp()` 把 start 拽回视野

`clamp()` 在每次滚动、换档、缩放、布局后都会执行：

```ts
const first = round((scrollLeft - PAD) / step)
const last  = floor((scrollLeft + clientWidth - PAD) / step)
const hi = max(lo, min(total - size, last - size + 1))
setStart(prev => clamp(prev, lo, hi))
```

**它把窗口强制夹进"当前视野"**（这是既有交互：拖动视野 = 移动窗口）。

而切换 V 时组件不重挂载，`scrollLeft` 还停在旧位置 ⇒ 恢复的 `start` 一算出来就被夹走，
然后被回写进缓存。**只恢复 `start` 不恢复滚动位置，漂移是必然的。**

修法：恢复时**同时把视野滚到那一格**（`el.scrollLeft = center - clientWidth/2`），
并在恢复期间 `suppress` 掉 clamp，等下一帧再放开。

## 路径二：`coverTick` 被 `total` 连带触发

```ts
useEffect(() => { if (!coverTick) return; setSize(total); setStart(0) }, [coverTick, total])
```

依赖里有 `total` ⇒ **每次切 V（total 变）都会重跑**。只要用户曾手选过一次日期，
切到任何 V 都会被强制成"整段 + 贴左"，再写进缓存。用 `lastCover` 只认 tick 变化。

## 顺带：未量到宽度时不夹取

`clamp()` 现在要求 `el.clientWidth > 0` —— 首帧/隐藏时 `last` 会算成 0，`hi ≤ 0`，
`start` 直接被拽到 0。

## 证据

`WorkbenchPage.test` 里"已有 + 待采"的期望值从 9 变成 **8**：窗口现在真的落在
`[5..29]`（贴最右），而不是被夹回 `[0..24]`。这条测试正好把这个行为钉住了。
