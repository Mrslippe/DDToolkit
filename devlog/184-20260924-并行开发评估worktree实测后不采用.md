# 184-20260924-并行开发评估：worktree 实测后决定不采用

> **背景**：用户问「两个会话同时开发一个仓，是否先 fork 一个分支再合并比较好」。
> 我实测了 `git worktree` 方案，**结论是不采用** —— 建立成本虽低，但**协调成本更高**。
>
> 本篇留档的是**评估过程与实测数字**（用来支撑"不采用"这个决定），
> 以及三个**与并行无关**、但评估途中撞出来的通用坑。

> **编号说明**：本篇用 184——183 是本会话前一批（小窗面板），
> 182 被另一个会话占用（R45-A/B）。**这个"抢编号"本身就是不采用并行的理由之一。**

---

## 一、结论：不采用，一次只开一个会话

**决定（2026-09-24）**：本仓**不采用并行开发**。想并行推进就在**一个会话里分批次**做
（R38 批 5c / 5d 就是这么做的）。

**为什么** —— 成本对比（本机实测）：

| | 耗时 |
|---|---|
| **建立成本**：worktree + junction + `npm ci` | 约 **2.3 分钟**（纯后端只要 9 秒） |
| **协调成本**：两个会话真实发生的摩擦 | 约 **15–20 分钟** |

协调成本**是建立成本的数倍**，而且**每次都要重付**。摩擦的具体来源：

1. 两个会话实际重叠了 `probe.ts` / `ui_probe.py` / `ROADMAP-DONE.md` **三个文件**
   —— 本仓**枢纽文件太集中**，想找到"完全不重叠"的切分本身就很难；
2. 为让 devlog 编号付出一次改号（182 → 183）；
3. 为在共享文件里只提交自己那一行，**两次手写 blob 暂存脚本**
   （不这么做就会把对方未完成的索引行提交进去，让 `doc_check` 报幽灵行）；
4. 差点用 `git stash -u` 扫走对方 6 个文件。

> **判断**：这不是"隔离技术不够好"的问题，是**收益/成本比**的问题。
> worktree 能把**文件**隔开，但隔不开**共享文档的追加型冲突**与**编号分配**——
> 而后者才是本仓并行时的主要成本。

## 二、实测数据（留档，供将来重新评估）

### 建立成本

| 步骤 | 耗时 | 磁盘 |
|---|---|---|
| `git worktree add` | **9 秒** | 37 MB（源码） |
| junction 补 `binaries/` | ~0 秒 | 0（不复制） |
| `npm ci --ignore-scripts` | **12–25 秒** | 217 MB / 13211 文件 |
| 冷 `cargo check` | **105 秒** | 1.27 GB |

### 门禁成本（热状态）

| 门禁 | 耗时 |
|---|---|
| **pytest** | **158.2 秒** ← 绝对大头 |
| vitest | 1.8 秒 |
| tsc | 1.1 秒 |
| eslint | 4.7 秒 |
| doc_check | 0.7 秒 |

### 一个被打破的错觉

`frontend/src-tauri/target` 有 **18.9 GB**（debug 16.2 + release 2.7），
看起来"再开一个工作区很贵"——**其实那是增量累积，不是基线**：
新 worktree 冷 `cargo check` 只要 **105 秒 / 1.27 GB**。
`[profile.release]` 的 `lto` / `codegen-units=1` **只影响 release**。

⇒ **别用"仓库有多大"估算并行成本**，要量"冷构建要多久"。

## 三、三个**与并行无关**的通用坑（已提炼进 `DEV-LOOP.md` §7.2）

评估时撞出来的，但**单会话同样会咬人**，所以留在了活文档里：

### ⚠️ 1. 全新检出开箱**不能构建 Rust 壳**

`tauri.conf.json` 的 `bundle.resources` 是 `["binaries/backend/**/*"]`，
而 `frontend/src-tauri/binaries/` **被 gitignore**（本机 163 MB，PyInstaller 产物）：
少了它 `cargo check` 直接失败（`glob pattern binaries/backend/**/* path not found`）。

**规矩**：干净副本上开工前先 `python scripts/build_backend.py`。
**看到这条报错别怀疑编译器或 Tauri 版本。**

> 这跟 worktree 无关：`git clone` 到新机器、`git clean -xfd`、CI 冷构建都会命中同一个坑。

### ⚠️ 2. 门禁抓不到**文件名层面**的 devlog 重号

`derive_devlog()` 用 `nums[-1] + 1`（**只排序、不去重、不查重复**）。实测造一个 183 重号文件：

```
基线                    count=181 max=183 next=184
加了一个 183 重号文件      count=182 max=183 next=184   ← 看不出任何异常
```

`doc_check.py` 同样返回 **`[ok] 无 FAIL`** ⇒ **撞号不会自己变红**。

> ⚠️ **这里纠正了我自己一个错误推断**：第一版我以为 `devlog_count` 会"少报一篇"，
> 实测它数的是**文件数**、重号时正常 +1。**推断与实测不符时以实测为准** ——
> 这条差点作为"事实"写进文档。

**另注**：`count < max` **不一定是撞号**（本仓 **068 / 161 是缺号**），别把缺号误判成重号去"修"。

### ⚠️ 3. `git stash -u` 是**全仓**操作，别拿它回答只读问题

我为了判断"某个 tsc 报错是不是自己引入的"，跑了 `git stash push -u`，
结果 stash 到了对方正在改的 6 个文件。两次都完整 pop 回来了（核对过
`git stash list` 为空、diff 规模未变），**没丢东西，但这是运气好**。

**规矩**：判断"报错是不是我的"用只读办法（`npx tsc --noEmit | Select-String <我改过的文件名>`）；
真要 stash，先 `git diff --stat` 记下范围、事后逐条核对。

## 四、将来若要重新评估，需要先满足什么

本次否决的核心原因是**协调成本**。若下面几条有变化，可以重估：

1. **共享文档的冲突能自动化**（例如索引行改由脚本生成、不再手工追加）；
2. **枢纽文件被拆细**（`ui_probe.py` 已 4500+ 行，切分后重叠面会显著变小）；
3. 任务粒度变成"一边是数天的独立子系统、另一边是零散修补"。

⚠️ **重估时别只看建立成本** —— 那是本次实测里**最不重要的**一项。
