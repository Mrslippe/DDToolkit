# 125-20260916-R27风控冷却持久化与升级

> 用户 2026-09-16："那按照你安排的流程来" —— 即按 **R27 → R26① → R28 → R29** 的顺序做，
> 本批是第一项。起因是 devlog/124 的盘点结论：**冷却窗口只在内存里，重启（含应用内更新后的
> 自动重启）即遗忘并立刻恢复满速** —— 而"被限流之后重启继续敲"恰恰是最容易被加重处罚的行为。
> **用户当场定两条口径**：① 梯度与恢复期**全按建议默认**（10 → 20 → 40 分钟、封顶 60、
> 连续 6h 无命中归零、解禁后减速恢复期）；② 启动时若仍在冷却窗口内 ⇒
> **自动档等完剩余时间，手动抓取仍可越权**。

## 一、改造前 → 改造后

| | 改造前（R12a 那版） | 改造后（R27） |
|---|---|---|
| 状态载体 | `scheduler._rate_limit_until` / `_rate_limit_reason` 两个**模块级 float/str** | `_rl_states: dict[平台, State]`；`State` 在 `app/services/rate_limit.py`（**不可变 dataclass**） |
| 粒度 | 全局单值 | **按平台**（B 站被限流不该连带停微博 —— 文档口径一直是"只冷却出问题的平台"） |
| 持久化 | 无 ⇒ **重启即遗忘** | 落 `app_meta`（键 `ratelimit.<平台>`，JSON）⇒ **重启不遗忘** |
| 时长 | 固定 `RATE_LIMIT_COOLDOWN=600s` | **升级**：1→base / 2→2×base / ≥3→4×base，封顶 **60 分钟**；连续 **6h** 无命中归零 |
| 解禁 | 到点直接满速 | **10 分钟恢复期**：动态流轮间隔 ×2（≈半预算） |
| 显示 | `{active, reason, seconds_left}` | 同上 **+ `platform` / `hits`**（取剩余最长的那个平台；顶栏状态岛零改动） |
| 自动档 | 冷却只在"本轮内"生效（`_run_platform_rounds` 的局部 `cooling`） | 冷却**参与调度**：名单与该平台的账号整批跳过；手动档**不受影响** |

## 二、实现清单

**新模块 `app/services/rate_limit.py`**（纯逻辑 + 落库，无调度依赖，因此可离线单测）：

- `State`（platform / until / reason / hits / last_hit_at / ended_at）+ `to_json` / `from_json`
  （**坏数据返回 None**：一条烂记录不该让调度起不来）；
- 纯策略：`escalated_seconds` · `decayed_hits` · `register_hit` · `mark_ended` ·
  `ramp_factor` / `ramp_scale`（多平台取**最保守**）；
- 落库：`load_all` / `save` / `clear`（`AppMetaRepo`，键前缀 `ratelimit.`），
  读失败按"无冷却"跑、写失败只记日志 —— **冷却状态丢了是"少一层保护"，不该把抓取任务带崩**。

**`scheduler.py` 接线**：`_note_rate_limit(reason, seconds, platform)` 返回**本次实际时长**
（`seconds` 降级为基准）、`_cooldown_for_rate_limit(reason, platform)` 睡够后 `mark_ended` 记恢复期起点、
`rate_limit_status()` 改成取剩余最长者、新增 `is_platform_cooling()` / `platform_cooling_note()` /
`_filter_cooling_accounts(accounts, auto=)`、`_load_rate_limit_state()` 在
`start_scheduler()`（lifespan 先于调度线程）读回并在 `_tier_loop` 兜一次。
**8 个冷却调用点全部补上平台**（`acc.platform` 或字面量 `bilibili`），并把提示文案里的
"冷却 600s"改成"冷却 600s 起（连续命中会升级）"。

三个刻意的设计选择（都写进代码注释）：

1. **恢复期加在"轮间隔"上，而不是改共享的预算上限** —— 预算是全局单例，动它会连带影响
   手动档的排期；加在 `_dynamics_next_due` 的 `interval` 上只影响自动档这一轮；
2. **手动档不跳冷却**：用户点按钮是显式意图（而且界面状态岛会显示冷却仍在，他知道为什么慢）；
   为此把过滤抽成 `_filter_cooling_accounts(accounts, *, auto)` —— 写在函数体里就测不到这条分支；
3. **梯度/上限/归零/恢复期不做成设置项**（同 R22 的判断：运维参数不外露，免得设置窗口又多几个
   看不懂的旋钮）；`base` 仍走既有的可热更 `RATE_LIMIT_COOLDOWN`。

## 三、用例抓到的两个真 bug（本批最值钱的部分）

1. **`DetachedInstanceError`**（既有用例 `test_async_fetch_vtuber_relinks_session_after_cooldown` 抓到）：
   账号循环里我写成 `await _cooldown_for_rate_limit(rate_limit_info(), acc.platform)`，
   而这一行**在 `db.commit()` + `db.close()` 之后** —— commit 会让实例过期、close 之后就是 detached，
   读 `acc.platform` 当场抛异常。修法：**关会话前先把平台名取出来**。
   （教训：这个仓库里"会话边界之后还碰 ORM 对象"是反复出现的坑，注释里已留痕。）
2. **跨用例污染**（`test_dynamics_next_due_adaptive` 抓到）：冷却状态现在会被**调度逻辑读到**
   （恢复期拉开轮间隔），于是"某个用例模拟过一次冷却"会留给后面的用例 ——
   实测期望 `29 <= delta <= 31` 变成了 **59.99s**。修法不是改那个用例，而是新增
   `tests/conftest.py` 的全局 autouse 夹具：每个用例前后清空/还原 `_rl_states` 与 `_rl_loaded`。
   （R27 之前不需要这层隔离，因为旧变量只被"读出来显示"。）
