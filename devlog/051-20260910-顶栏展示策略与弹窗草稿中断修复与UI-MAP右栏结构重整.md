## 一、顶栏展示策略：只有「有起点有终点」的任务上顶栏

### 分析

状态行原本的判据是 `account.running || post.running || external.running`——**把「有没有任务
在跑」当成了「有没有事发生」**。自动档接入后这两件事分家了：

| 任务 | 触发 | 频率/时长 | 终局 | 判定 |
|---|---|---|---|---|
| 抓取账号 / 更新动态 / 抓取帖子 | 用户点按钮 | 秒~分钟 | ✅ 有 | **展示** |
| 收录新 V / 添加账号（账号+首屏+回填） | 用户动作连带 | 秒~分钟 | ✅ 有 | **展示** |
| 第三方数据批次（每日/启动补抓/收录回填） | 定时或启动 | ~3min，低频 | ✅ 有 | **展示** |
| 兜底排队抓取 | 定时档兜底 | 分钟 | ✅ 有 | **展示** |
| **动态流常态轮询** | 综合档 | **~80s 一轮、永不停** | ❌ 无 | **静默** |
| **自动账号流扫描** | 综合档 | 按账号 24h 到期 | ❌ 无 | **静默** |

动态流自 v0.9.8 改成预算自适应节奏后变成「一轮接一轮」的常态节拍，于是顶栏长期挂着
「动态轮询中 - V名 - i/N」+ 玫瑰徽章；更糟的是 `busy` 为真会**一直压掉操作结果覆盖态**
（`pill-message` 要求 `!busy` 才显示），保存成功之类的提示都看不见了。

### 改法（判据放后端，别按任务名猜）

`GET /vtuber/fetch-status` 增加两个**事实**字段（`scheduler.get_fetch_status()`）：

- 每类的 `auto`：本次运行是否由定时档发起（`_auto_account_active` / `_auto_post_active`）。
  **不能用任务名做判据**——`update`/`full` 这些文案手动与定时都会用，只有后端知道这次是谁
  发起的；
- 顶层 `manual_running`：直接复用 `manual_task_running()`（与手动端点的 409 判据同一个
  函数，含「已请求抢占、正等自动档让位」的窗口）。

前端 `TopBar.tsx::isQuietTask`：`running && auto === true` → 静默（不写文案、不亮容器、
不参与关窗确认）。旧后端不带 `auto` → 视为手动照旧展示，**不会因字段缺失把真任务静默掉**。

两个连带的正确性细节：

1. **静默 ≠ 不刷新**：`fetch-idle` 的 running→idle 边沿判定仍读**原始** `running`（含静默
   任务）——动态流每轮结束照样派发事件，卡片/侧栏/hero 仍然自己更新（这正是轮询的意义）。
2. **按钮禁用同源**：`fetchBusy` 从 `account.running || post.running` 改成后端
   `manual_running`。旧判据下动态流每轮把「抓取账号/更新动态/抓取帖子」按钮禁用掉，而
   **后端其实会受理**（`manual_task_running()` 在自动档持锁时返回 false —— 手动优先会抢占
   自动档）。这是同一个认知错误的另一面：把自动节拍当成了手动任务。

新增测试 `test_fetch_status_marks_auto_runs_and_manual_busy`：自动档持锁 → `auto=True` 且
`manual_running=False`；同一把锁转手动 → `auto` 撤下、`manual_running=True`；等锁窗口
（`_preempt_post`）也算忙；账号通道同理独立。测试用 try/finally 还原模块级全局。

## 二、Bug：动态轮询期间改档案信息，改一项丢一项

**根因**（不是轮询写坏了数据，是**草稿被服务端值冲掉**）：

```
动态流每轮结束 → TopBar 派发 fetch-idle → PostsPage 重拉本体 setVtuber(新对象)
                  （另有 account-progress → mergeVtuberSnapshots 也产生新对象）
→ VtuberSettingsDialog 的 useEffect 依赖 [open, vtuber, hero] 命中
→ 整份草稿被 vtuber/hero 的服务端值覆盖 → 用户刚敲的内容消失
```

`hero` 还叠了一层：它是 `useMemo(() => vtuber.accounts.find(...), [vtuber])`，
`vtuber` 换引用 → `hero` 必然换引用，两个依赖一起触发。用户「每抓完一项就被重置」的
观感正是每轮 ~80s 一次的刷新节奏。

**为什么不能靠调依赖数组解决**：对象引用每次后台刷新都是新的，而草稿是**用户正在编辑的
状态**，不该被任何后台刷新打断。改法 = **显式播种键**：

```tsx
const seedRef = useRef('')
useEffect(() => {
  if (!open || !vtuber) return
  const key = `${vtuber.id}:${hero?.id ?? ''}`   // 打开态 + V id + 主账号 id
  if (seedRef.current === key) return             // 后台刷新的新引用不重播种
  seedRef.current = key
  …播种草稿…
}, [open, vtuber, hero])
useEffect(() => { if (!open) seedRef.current = '' }, [open])   // 关窗作废，下次打开取最新值
```

保留的两个重播种时机是**必要的**：换 V、换主账号（例如删掉原主账号后 `hero` 变成另一个
账号，签名/锁定字段该跟着换）。同类风险点排查：`AddAccountDialog` 只在 `open` 转 false 时
重置（安全）、`BatchFetchDialog` 无播种 effect（安全）——只有档案设置窗口踩了这个坑。

> 另有一种「看起来像被重置」的情形：**已保存**的昵称/签名/头像被下次账号抓取覆盖。
> 那是设计内的行为，解法是档案设置窗口里的**字段锁定**（`accounts.locked_fields`，
> 抓取侧 `scheduler._field_locked` 跳过锁定字段）。二者现象相似但根因不同，已在 UI-MAP
> §B1.5 注明区分方法。

## 三、UI-MAP 右栏结构重整

原 §B1 是「面板/背景层/工具条表 → cards 表 → list 表 → archive 表 → profile 表 → 联动表」
一路平铺，四视图的**平级关系**看不出来。改为分层：

```
B1 帖子面板
├─ B1.0  四视图并列总览（视图 / view 键 / 光条钮 / 主容器 / 子项清单 —— 一张表看全平级关系）
├─ B1.0.1 共用外壳（面板 / 背景层 / 工具条+光条）
├─ B1.1  cards 展示页      ← 子项：滚动层 / Hero / 平台药丸行 / 饰条 / 档案设置入口
├─ B1.2  list 列表页       ← 子项：筛选条 / 操作钮组 / 筛选弹窗 / 帖子流 / 卡片 / 无限滚动 / 回顶
├─ B1.3  archive 档案      ← 子项：直播日历卡 / 粉丝趋势卡
├─ B1.4  profile 档案卡    ← 子项：改版中占位 + 保留待复用的旧组件
└─ B1.5  共用层：跨视图联动刷新（事件总线 + 「后台刷新不得打断用户草稿」的约定）
```

另在 §A1 下新增 **§A1.1 状态行展示策略**（本文第一节的那张表 + 实现判据 + 两条连带），
让「该不该上顶栏」有据可查。

## 五、经验

- **「有任务在跑」≠「有事发生」**：状态显示器要把「自动节拍」和「用户动作」分开，
  否则顶栏会被常态轮询永久占用，还会顺带压掉所有结果提示（`busy` 参与覆盖态判据）。
- **这类判据要放后端**：同一段文案复用给手动与自动两条路径时，前端无法从 payload 反推
  「谁发起的」。加 `auto` 一个布尔字段，前端就不必维护「哪些任务名算静默」的猜谜表。
- **后台刷新不得改写用户正在编辑的状态**：任何「依赖 props 重新初始化」的表单，在轮询
  驱动的应用里都是定时炸弹。要么显式播种键（本次），要么受控草稿，**不要**靠依赖数组。
- **同一个 `any_fetch_running` 家族的语义要一以贯之**：后端已有
  `manual_task_running()`（自动档不算忙）与 `any_fetch_running()`（算）两个判据，
  前端按钮该用前者、外部批次该用后者——抄错一个就会出现「按钮点不动但接口其实受理」。
