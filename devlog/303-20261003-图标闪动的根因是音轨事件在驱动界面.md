# 303-20261003 ▶/⏸ 还在闪：音轨的事件在驱动界面状态

> 用户追问：「播放暂停来回闪动的情况还是会存在，根因是什么」。查到了，而且是**无条件**的 ——
> 跟时序、跟缓冲治理的判定窗口都没关系。

## 根因：`<audio>` 自己的 `play`/`pause` 也在改界面的 `playing`

```jsx
<audio data-vp-audio="1" src={audioSrc}
       onPlay={() => setPlaying(true)}
       onPause={() => setPlaying(false)}   // ← 就是这一行
       … />
```

而**我们按设计会反复暂停/恢复音轨**：缓冲按住要停音轨（`devlog/299`）、seek 收尾要先停再对齐
（`devlog/297`）、小窗暂停也会带走音轨。每一次都让音轨发出 `pause`/`play` ⇒ 这两个处理器
把它们当成"用户按了暂停/播放" ⇒ 界面跟着音轨一起翻面，节奏**正好与缓冲治理同步**
（按住 → 音轨停 → 界面变 ▶；放开 → 音轨播 → 界面变 ⏸）。所以上一批把视频轨那边
（`wantPlayRef` 意图、"我们按的暂停"判定）修好之后，闪动依旧。

**修**：把这两个处理器删掉 —— **视频轨是界面状态的唯一真源**（画面才是用户看到的东西），
音轨只跟着走（它的 `timeupdate` 仍用来推进进度，`error` 仍用来换镜像）。
判据：`音轨自己的 pause/play 不许驱动界面`（**反向验证过**：把两行加回去立刻红）。

## 顺带把"谁按的暂停"的判定换成时间窗

上一批用的是"看门狗每一拍清标记"（200ms 一拍）。但浏览器的 `pause` 事件是**异步派发**的
（规范里 queue 一个 media task），晚到一拍以上完全可能 —— 一旦晚到，我们自己的暂停就被
当成用户暂停 ⇒ 界面翻成 ▶，下一拍又翻回来 ⇒ **又是一次闪**。现在改成
`Date.now() - hold.selfAt < 800ms` 判"这一下是我们按的"：与拍子无关，且**会自然过期**
（不会把 800ms 之后用户真正按的暂停误判成我们的）。

## 复盘：这一串 bug 的共性

从 `299` 到 `303`，五批里反复出现同一个形状 —— **同一份状态有两个来源在写**：

| 批次 | 谁和谁争 |
|---|---|
| `299` | 小窗的暂停 vs 我们的 `toggle()` |
| `300` | 事件驱动 vs `timeupdate` 和解（已收口成"以元素为准 + 心跳"） |
| `301` | 治理器的按住 vs "播放中" |
| `302` | 意图 vs 元素此刻的 `paused` |
| **`303`** | **音轨的事件 vs 视频轨的事件（同写 `playing`）** |

⇒ 这类现象（闪、抖动、状态卡在错的一格）在没有真实设备时很难靠推理穷尽，
**但在单测里可以用"两个来源各发一次事件，断言界面不动"直接钉住**。本批的两条用例就是这么做。

## 判据（新增 2 条）

| 用例 | 钉什么 |
|---|---|
| 音轨事件不许驱动界面 | 视频在播时给音轨发 `pause`/`play` ⇒ `data-vp-state` 恒为 `playing`、不冒出大播放键 |
| 晚到的暂停事件 | 按住后 300ms 才到的那次 `pause`（我们自己那次）⇒ 界面仍显示在播 |
