## 二、手感怎么被机器判住

手感错了**肉眼很难举证**：跟手差 40px 也像在拖、缩放没回到 1 也看不出来、迟到的长按定时器
会让卡片在抬手后又自己跳起来。所以这一批的判据都写成可量的：

| 不变量 | 判据 | 结果 |
|---|---|---|
| 相位链 | 按下 `pressing` → 长按 `lifted` → 抬手 `settling` → `idle` | ✅ |
| 拾起缩放 | `1 < scale ≤ 1.055`（「轻微」档）；按下有 `scale(.985)` 的即时反馈 | ✅ |
| **跟手 1:1** | **卡片视觉位移 ≡ 指针位移（≤2px）**，**跨格时也成立** | ✅ 同格 (30,30)、跨格 71/71 |
| 短按无害 | 短按后相位 `idle`、无内联 `transform`、**迟到的长按定时器不许把卡片拿起来** | ✅ |
| 落位收敛 | 落位那一刻登记了 `transition-duration = 0.22s`；落定后无内联 `transform` / `will-change` | ✅ |
| reduced-motion | 缩放 = 1、落位无过渡，**而跟手仍 1:1** | ✅ `--reduced` 档 |

**跟手那条恒等式值得单独记**：`liftOffset = 指针位移 − 格子位移` 等价于
"卡片视觉位移 ≡ 指针位移"（跨格也一样，因为格子跳多少就被减掉多少）。
少了 `cellDelta` 会**多走一格**、完全没跟手会**走 0** —— 两种错法当场露馅，
比"看着顺不顺"可靠得多。

## 三、四个坑（都写进代码注释与文档，免得再踩）

### 1. 编辑态不能也要求长按（护栏逼出来的口径细化）

第一版：两态都要长按 350ms 才拿起。`--board`（R37-P2b 的探针：**点了「编辑布局」再拖**）
当场红了 —— 合成手势按下后 80ms 就移动，正好落进"没到 350ms 就拖 ⇒ 取消"那条分支，一行都没动。
想清楚之后这不是探针的问题，是**语义**的问题：用户点「编辑布局」本来就是为了排布，
每拖一次还要先按住 350ms，那个按钮就白点了。于是定成**两态两种语义**：

- **阅读态**：长按 350ms 拿起并进编辑态（手机语义，也避免误触碰乱）；
- **编辑态**：按下即拖（桌面习惯）。

拿起时的缩放/阴影两态一致 ⇒ 用户要的"弹跳缩放"一点没打折。规格 §5.1 已改写，探针也各有一条断言。

### 2. reduced-motion 下"跟手"不能一起关

`prefers-reduced-motion` 的本意是去掉**装饰性**动画。跟手位移是**输入反馈** ——
把它关掉等于"拖动失灵"，那不是减少动效，是把功能拿走了。所以本批口径：
**缩放归零、落位不滑行，而跟手仍 1:1**（探针专有一条盯它）。

而且这条**必须在 TS 里再写一份**（`motionPlan`）：拾起的 `scale()` 是**内联**写上去的，
内联优先级高于媒体查询 —— CSS 里写 `transform: none` 也压不住它。

### 3. ⚠️ 虚拟时间下 CSS 过渡**根本不推进**（这一条会影响 P4c）

无头浏览器跑在 `--virtual-time-budget` 下时，`getAnimations()` 里的过渡是 `running`，
但 `currentTime` **恒为 0** ⇒ `getComputedStyle().transform` 永远停在**过渡起点**。
第一次跑 `--motion-cards` 时它表现为两条假红：

- "按下没有反馈"（读到 `scale = 1` —— 其实是过渡还没开始走）；
- "落位后仍有位移矩阵"（读到拾起时的 `matrix(1.055, …, -41, 30)` —— 其实内联早已清空）。

分辨办法（也是现在的判据）：**① 我们提交了什么 → 读 `element.style.transform` 内联值**；
**② 过渡有没有登记 → 读 `transition-duration`**。实测 `style` 只剩 `grid-area: …` ⇒ 实现是干净的。
❗ **P4c 的 FLIP 退避动画只能按这两条判**，不能指望 computed 值 —— 想看动画真怎么走，
用调测页 0.25× 慢放。

### 4. 实现里加 rAF 节流 ⇒ 制造了一个竞态

第一版跟手位移用 `requestAnimationFrame` 节流（"每帧最多一次 setState"）。结果
**默认档绿、reduced 档红**：同样的手势，reduced 档量到"卡片还没跟上"（(71,0) 而不是 (30,30)）——
差别只是那一帧有没有被服务。修法两条，都做了：

- **实现侧去掉 rAF**：`pointermove` 本来就每帧一两次，React 自己会把同一批更新合掉；
  多一层 rAF 只让位移"落在下一帧"，而**探针在多远的将来读到它就成了竞态**。手感不该有竞态。
- **探针侧加 `await frame()`**，并且**必须带超时兜底**：`--force-prefers-reduced-motion` 下
  Chromium **不产帧**，`requestAnimationFrame` 永远不回调 —— 裸 `await frame()` 会让整个探针挂住、
  连 `#ui-probe` 都不输出（第一次就是这么红的，看起来像"页面没跑完"）。

## 四、动效调测页（用户拍板要的）

`?motion=cards`（dev 构建；视图里**动态**载入，生产构建整段摇掉）：

- **单步触发**：按下 / 跟手 +30 / 跨格 +90 / 落位 / 连播一遍 / 复位；
- **慢放** 1× / 0.5× / 0.25×：改 `--motion-scale`（所有动效令牌都是 `calc(N × var(--motion-scale))`），
  不动任何组件；
- **跟手读数**：指针位移 / 卡片位移 / **误差**（非 0 标红），把那条恒等式直接摆在眼前；
- 它派发的是**真实路径上的合成 PointerEvent**（与探针同一套手势），所以"面板里能拖，实际就能拖"。

护栏：`--motion-lab` 断言面板**真的挂上了**（动态载入失败只会"什么都没有"，与"本来就不显示"
长得一模一样）+ 点「按下」真能驱动手势（相位 `pressing` → 350ms 后 `lifted`）。
