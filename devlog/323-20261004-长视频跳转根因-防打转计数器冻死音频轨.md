# 323-20261004 长视频跳转根因：防打转计数器把音频轨永久冻死

> 承 `devlog/322`。用户复现：「第一次依旧出现，第二次及之后就没有发生了」——
> 而 322 新加的现场行**正好把上次没定论的那一环补上了**（这就是写那行的用处）。

## 一、现场行说的（15:45:19，76 分钟那条视频）

```
跳转 2822.7s 等了 10s 仍**一条轨都没有数据**（
  video[可用=22.3s 区间=0.0–2845.0s 手上=- 该取=564/918 重试=0 重复=0 无进展=0]
  audio[可用=0.0s 区间=0.0–15.0s 手上=- 该取=562/915 重试=0 重复=2 无进展=0]）
—— 收手重试 1 次
15:45:30 MSE 不成立：跳转 2823s 反复取不到数据 → 退回渐进式      ← 322 的收手生效（不再永远转圈）
```

- **视频轨是好的**：目标处可用 22.3s（`重复=0`）；
- **音频轨只有开播那 15 秒**（`区间=0.0–15.0s`，与代理侧"init+0/1/2 段之后就没再取过"完全对上）；
- 决定性的是 **`重复=2`**。

## 二、根因：`repeat` 只在"取了**不同**的段"时才清零

`pump` 里有一条防打转闸门（`devlog/313`）：*同一段连取两次还是盖不上 ⇒ 当它到头了*，
判据是 `tr.repeat < 2`。而 `repeat` 的记账写在 `append()` 开头：

```ts
if (tr.lastIdx === idx) tr.repeat += 1
else { tr.lastIdx = idx; tr.repeat = 0 }
```

**只要没有"换一个索引成功 append"，这个数就永远不下来** ⇒ 一旦撞上 2，这条轨
**永久拒绝取数**：没有日志、没有报错、没有恢复路径（我的看门狗也抓不到 —— 它只看
"手上有没有操作"，而这时 `手上=-`，轨是"闲置地冻着"）。跳转于是等到收手，用户看到转圈。

顺带两个放大器：① **init（`idx=-1`）也走同一份记账** ⇒ 跳转期间一次 init 重试就能把
**媒体段**的取数冻住；② 闸门触发时**什么都不说**（静默跳过）。

## 三、改了什么

1. **init 不参与这份记账**（`idx >= 0` 才记）—— init 被 abort 重取是跳转期间的正常事；
2. **换跳转目标 / 强制收手 / 真的有进展**时把这份记账一起作废
   （`seekTo`、`unstick(force)`、`onUpdateEnd` 的 `grew` 分支）；
3. 闸门触发时**说一句**：`[media] <kind> 段 N 连取 K 次仍没落地（本轨缓冲停在 …）—— 本轨不再重取`。

## 四、判据（`mseKernel.test.ts`，反向验证过）

「同一段连取两次不许把一条轨永久冻死」：只冻结 **audio** 轨（append 成功但缓冲不涨）
⇒ 撞上闸门后**必须留一行**；然后换目标（35s，音频轨手里没有）⇒
**音频轨必须重新取数并落地**。
反向：把 `repeat/lastIdx` 的重置去掉 ⇒ 红（`换了目标还不为音频轨取数 = 这条轨被永久冻死`，
实测音频轨取数停在 8 不动）——**与真机现象同形**。

> ⚠️ 判据要**只数音频轨的取数**（按 URL 里的 `/a.m4s` 过滤）：视频轨一直正常，
> 拿总取数会把这个洞掩盖掉（第一版就是这么写的，反向验证时才发现判据太弱）。

## 五、为什么"第二次之后就没事了"

第一次失败触发了 322 的收手 ⇒ **本会话熔断 MSE、退回渐进式**（`noteMseFailure`），
而渐进式的 seek 由浏览器自己做、能力上没这个洞 ⇒ 之后几次都正常。
也就是说：**用户看到的是"偶发"，实际是"每次会话的第一次跳转必中"**。
现在这条洞堵住了，MSE 不必再为它退场。
