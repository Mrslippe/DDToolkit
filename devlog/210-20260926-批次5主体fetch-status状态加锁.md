# 210-20260926-批次5主体：fetch-status那份状态改成"靠锁的构造"

接 devlog/209（切片一：两个 import 期快照）。这一刀是计划 §2.8 的主体：
**把跨线程状态从"靠 GIL 的约定"变成"靠锁的构造"**。

## 一、先纠正那句错话

`scheduler.py` 原来的注释是"仅简单赋值，GIL 下线程安全"—— **那句话是错的**，
而且已经被自己的代码破坏：

| 位置 | 真实形态 | 会被读成什么 |
|---|---|---|
| `recent`（`_push_account_snapshot`） | **读-改-写**：append + 裁到 100 | 两个抓取线程互相踩 |
| `external`（`external_task_started/finished`） | **一次改 4 个字段**（running/label/seq/last_label） | 读到"改了一半"：`running=True` 但 `label=None` |
| `get_fetch_status()` | 给出去的是**浅拷贝**（`{**_status["account"], …}`） | ⚠️ `recent` 那个 list 与内部**是同一个对象** ⇒ 前端每几秒轮询时一边遍历、抓取线程一边 append |

## 二、改成什么

1. `_status_lock = threading.RLock()`，并把"新规矩"写在 `_status` 上方（三句话）：
   **跨字段一致性 / 读-改-写必须在锁里**；单字段赋值可以不在锁里（dict 的值存储是原子的），
   但**不许拿它当判断依据**；**锁内不做网络/DB/重 IO**。
2. `_status_snapshot()`：**锁内深拷贝**（`account.recent` 也复制一份），成为**读路径唯一入口**；
   `get_fetch_status()` 改用它。
3. 三个"聚合写"进锁：`external_task_started` / `external_task_finished` /
   `_push_account_snapshot`（append+裁剪是一个整体）。
4. 语句级范围：**没有**把 ~20 处单字段赋值都改成 setter —— 那会让这一刀变成大重构，
   而它们的风险是"读到旧值"而非"读到坏结构"，锁只保护后者（理由写在注释里）。

## 三、判据（`tests/test_fetch_status_store.py`，5 条）与反向验证

- ① **不共享结构**（确定性，主判据）：改 payload 不许改到内部状态；拿到 payload 后内部再变，
  payload 不许跟着变（快照语义）；`recent` 上限 100（顺手把"上限"也钉住）。
- ② **跨字段一致**（并发）：6 线程 × 400 轮 start/finish + 2 个读线程，
  断言**任何一份快照**都满足 `running == (label is not None)`（这两个字段必须一起变）。
- ③ 并发 push 之下也不许超过上限；未知 token 的 finish 不抛（seq 照常自增）。

**反向验证（两条，实测都红）**：

| 改法 | 结果 |
|---|---|
| 读路径改回浅拷贝 | `..._does_not_alias_the_internal_state` 红 ✓（确定性） |
| **去掉锁** + 临界区插 `time.sleep(0)` 放大竞态 | 并发那两条红 ✓（计划要求的"必须真红"） |

## 四、这一刀**没**覆盖的（如实记下）

- 计划 §2.8 另点的 `_dynamics_idle_streak` / `_bili_account_id_cache` /
  `_PlatformBudget._prune`：访问者基本都在**综合档那一条线程**内（tier loop / 同一事件循环），
  没加锁。⚠️ 例外一处：T0 直播轮询线程会 `_dynamics_idle_streak = 0`（另一条线程写同一个 int）
  —— 单字段原子写，语义上最坏只是"退避晚一轮恢复"，**有意不加锁**，但记在这里。
- `_status` 的另外 ~20 处单字段赋值同样没进锁（见 §二.4）。
- ⇒ 判据管的是**结构一致性**（那是会读到坏数据的一条），不是"每一次写都持锁"。
