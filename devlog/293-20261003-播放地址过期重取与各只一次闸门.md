# 293-20261003 播放地址过期重取 + "各只一次"闸门

> 执行方案（`docs/plans/bili-video-playback-execution.md`）第 8 条："播放地址过期（`expires_in`）时
> **自动重取一次**再播（URL 短时效是已知约束）"。这是 C1+C2 的最后一条功能项。

## 一、补救顺序：过期优先，其次换内核

`playurl` 的地址**短时效且绑 IP**（实测口径见 `devlog/289`）。用户在抽屉里晾久了再点播放时，
地址已经死了 —— HTTP 层看到的是 CDN 的 **403**，与"视频没权限"长得一样。若一律按"播不动"
处理，结果是**降级去要 durl**（720P 封顶）：明明只是地址旧了，却白丢 1080P。

所以 `BiliVideo` 记下这批发来的地址的**到期时刻**（`Date.now() + expires_in*1000`），
失败时按顺序做**至多两次**补救：

| 顺序 | 条件 | 动作 |
|---|---|---|
| ① | 已过期 且 没重取过 | `load({ qn: 当前实际档 })` —— **同档重取**，保住 1080P |
| ② | 否则 且 没回落过 | `load({ fallback: true })` —— 换 durl 内核（WebView2 解不了 DASH 时走这条） |
| ③ | 两次都试过 | 不再拦，交给播放器走"播不了"兜底卡（`.vp-dead` +「在浏览器打开」） |

判据是纯函数 `nextRetryAction({expired, triedRefresh, triedFallback}) -> 'refresh'|'fallback'|'none'`，
**三态直接可测**（不用等真机）。

## 二、为什么要"各只一次"（这条是被自己的用例逼出来的）

滚动重取的坑在 `devlog/292` 已经踩过一次（`?fallback` 漏接 ⇒ 取回来的还是 DASH ⇒ 无限重取）。
这次的第一版实现把闸门写成 `useRef({refresh, fallback})`，而纯函数的入参叫
`{triedRefresh, triedFallback}` —— 展开后两个字段恒为 `undefined`，`!undefined === true`
⇒ **闸门永远开着**。测试里的表现是：durl 也失败后 `biliPlay` 从 2 次涨到 3 次、`4 次…`。

组件用例因此改成"**把 fallback 链走完，断言取流次数不再增长**"：

```ts
for (let i = 0; i < 3 && !host.querySelector('.vp-dead'); i++) { …dispatch error… }
expect(biliPlay).toHaveBeenCalledTimes(2)
expect(host.querySelector('.vp-dead')).toBeTruthy()
```

⚠️ 这里顺带纠正一个容易写错的期待：**durl 档自己还有"直连 → 代理"两级**，
所以"两次补救用完"不等于"立刻进兜底卡"—— 只断言"取流**次数**不再涨 + 链走完**一定**进兜底卡"，
才既钉住闸门又不假装知道内部换源细节。

## 三、闸门只在**用户手势**上清零

`load(opts, resetRetry)` 的 `resetRetry` 只由两处传 `true`：**首次点播放**、**换清晰度**。
自动补救**不算新手势** —— 否则"重取成功 → 又播不动 → 又是新手势"会重新打开闸门，等于没闸门。

## 四、判据

`frontend/src/components/BiliVideo.test.tsx` 5 条：不预取（点播放才取一次）/ 失败如实显示后端文案 /
**播不动先回落 durl 且只回落一次**（+ 链走完进兜底卡）/ **过期用同一档重取**（断言第二次调用是
`{qn: 80}` 而不是 `{fallback: true}`）/ `nextRetryAction` 三态。前端合计 **790 条 / 64 文件**
（本批 +3；PERF 里 781 那条基线停在 `devlog/290` 之前）。
