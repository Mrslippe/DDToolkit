## 一、先做的那一半：命令级准入（S3-0）——**唯一真正有效的**

计划 §2.2 的核实结论：**本应用的自定义命令默认完全不查 ACL**
（两扇窗都是本地 origin，vendored `tauri-2.11.5/src/webview/mod.rs:1819-1852`）。
⇒ 只拆 capability JSON 是**假绿**，命令自己判 label 才算数。

- `lib.rs::COMMAND_ACL`：23 条命令逐条表态，**默认拒绝**（没登记 = 谁都不能调）；
  每条命令入口第一句 `if !guard_window(&window, "<自己的名字>") { … }`。
- `guard_window` 拒绝时**留痕**（stdout + `<数据目录>/logs/shell.log`）——
  release 没有控制台，`println!` 会丢；"某个窗口越权调了命令"必须留得下来。
- 小窗可调**恰好六条**：`get_backend_port` / `get_api_token` / `widget_diag` /
  `resize_widget_window` / `set_widget_visible` / `set_widget_click_through`。
  ⚠️ **后三条差点被我填成 main-only**：它们是 `StatusWidgetWindow` **自己**在调的
  （展开就 resize / 全屏隐藏 / 穿透，三处 `await import('../utils/shellBridge')`）——
  按"这命令看起来该谁用"填就是把小窗点坏（devlog/175 的形态）。
  ⇒ 教训：**窗口归属要照调用点数，不能照直觉填**。

判据（cargo，8 条新增）：注册表 ↔ 准入表**双向对账**（新命令不表态 ⇒ 红）；
每条命令都调了 guard（扫源码，按**字符**切片 —— 第一版按字节切，切进中文注释直接 panic）；
小窗可调集恰好那六条；危险/动数据的八条 main-only；未知命令默认拒。

## 二、外链白名单（S3-B）

今天 `HeroCardsView` 走的是 `plugin:shell|open`，用的是插件内置正则
`^((mailto:\w+)|(tel:\w+)|(https?://\w+)).+` —— **无主机白名单、不拒 userinfo、末端无 `$`**
（计划 §2.17）⇒ 任何 https 主机都能被打开。

- 新增 `open_external(url)` 命令 + `external_url_host()` 严格校验：只 `https`、
  主机**精确等于**白名单、拒 userinfo / 端口 / `%` 编码 / 反斜杠 / 空白 / 非 ASCII 同形字。
- 白名单：`bilibili.com` / `www.bilibili.com` / `space.bilibili.com` / `live.bilibili.com` /
  `weibo.com` / `www.weibo.com`。
- **`shell:allow-open` 与 `dialog:allow-open` 从 capability 删掉**（前者是"旧通路还在"的关键，
  后者 JS 从未使用）—— 有判据：**解析 JSON 的 `permissions` 数组**断言它们不在里面。
- 前端 `shellBridge.openExternal`：桌面端走命令、浏览器退化为新标签页，
  **拒绝原因原样抛出去**（HeroCardsView toast 出来）—— 计划要求的"别静默失效"。
  前端**不复制主机表**（跨语言两份真源必漂）。

判据：URL 的**放行 8 例 / 拒绝 19 例**矩阵 + 前端 3 条（浏览器退化 / 走命令 / 被拒要抛出）
+ 1 条扫源码（`plugin:shell|open` 不许在 `frontend/src` 里复活）。

## 三、capability 分窗（S3-A）——**按风险做了裁剪版**

计划要 `default.json` → `main.json` / `widget.json`。**我只做了一半，这是有意的**：

| 做法 | 为什么 |
|---|---|
| ✅ `shell:allow-open` / `dialog:allow-open` 删掉 | S3-B 的前提（旧通路必须一起死） |
| ✅ 主窗独有的 `updater:default` / `process:allow-restart` 拆去 `main.json` | 主窗是 `tauri.conf.json` 里**静态 label** ⇒ 命中确定，不需要真机验证 |
| ❌ **没有**按 label 拆成 `widget.json` | 小窗是**运行时创建**的，而"显式 label 的 capability 能不能命中运行时窗口"在本仓**没有验证过**（计划自己标为"未验证、必须先测"）。猜错的症状是 devlog/175 那种"IPC 通道坏掉、主窗点 ✗ 没反应"，而**这一批我无法在真机上验证** |

⇒ 基线留 `windows: ["*"]`（与今天行为一致、不可能退化），把"多给出去的"收掉。
**把 widget.json 留给一次有真机的批次** —— 计划里那条"未验证"就是它的前置条件。

## 六、真机复验抓到的**真 bug**（本批自己埋的，2026-09-26 当天修）

用户走完 A 清单后报："其他都正常，**小窗的功能稍微有点问题**"。查下去是本批的错：

| 命令 | 我填的 | 实际调用方（同一个文件里） |
|---|---|---|
| `destroy_widget_window` | `MAIN_ONLY` ❌ | `StatusWidgetWindow.tsx:148` —— 小窗**自己的关闭请求**（`onCloseRequested` → 销毁自己） |
| `is_fullscreen_app_running` | `MAIN_ONLY` ❌ | `StatusWidgetWindow.tsx:202` —— 全屏隐藏逻辑 |

**漏的原因很具体**：这两处是**动态 import**（`await import('../utils/shellBridge')`），
而我盘"小窗会调哪些命令"时只看见了同一个文件里另外几处 —— **手工盘点会漏，而且漏得很自然**。

修法与补的判据：

1. 两条改回 `BOTH`（`destroy_widget_window` / `is_fullscreen_app_running`）；
2. Rust 那条手工清单用例更新成真实八条，并在注释里写明"**真源是前端那条派生用例**"；
3. ⚠️ **新增派生判据** `frontend/src/utils/widgetCommands.test.ts`：从 `widgetMain.tsx` /
   `StatusWidgetWindow.tsx` 里抠出"从 shellBridge 解构了哪些函数" → 再到 `shellBridge.ts`
   查这些函数各自 `invoke` 了哪条命令 → 要求它们**全部**在 `COMMAND_ACL` 的 widget 集合里；
   反方向再钉一条（小窗可达集合里不许出现危险命令）。
   **反向验证**：把 `destroy_widget_window` 退回 `MAIN_ONLY` ⇒ 它红，并点名
   `destroyWidgetWindow → invoke('destroy_widget_window')：这条命令的准入里没有 widget` ✓
4. 顺带抓到一处**重复登记**：改的时候只在表头加了 BOTH 两条，忘了删下面原来的 MAIN_ONLY 两条
   ⇒ `command_acl_matches_the_registered_handler`（注册表↔准入表对账）当场红 ✓
   —— 这条判据本来就是为"表写歪"准备的，这次它咬的是我。
