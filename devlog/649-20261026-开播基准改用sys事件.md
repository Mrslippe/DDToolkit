# 649-20261026-"所有人时滞 150 分+"的真因：`start_at` 不是真实开播

用户查七海 10-02 13:59Z 那场：所有人都 150 分以上，怀疑"主播对着空气播两小时"。

## 查到的证据

| 事实 | 数值 |
|---|---|
| `stats.start_at` | 13:59:55Z（北京 21:59） |
| 第一条弹幕 | 开播后 **+148.6 分** |
| 第一条 `sys_event type=11`（直播开始） | 开播后 **+148.6 分**（与弹幕完全吻合） |
| `type=12`（直播结束） | +272.9 分，在记录窗口之外 |
| 另一条 `type=11` | +643.6 分（**同一 live_id 的第二场直播**） |

⇒ **`start_at` 记早了 2.5 小时**。真正的开播时间由 sys 的"直播开始"标定。
（顺带发现：同一个 `live_id` 会被多场直播复用，晚场的事件也混在本文件里。）

## 修法

`loader` 里计算时滞基准时：若 `sys_events` 有 `type=11` 且晚于 `start_at` 超过 5 分钟，
**以首条 type=11 为准**。修正后该场时滞中位数从 148.6 → **54.8 分**（p90 111），
"对着空气播两小时"的假象消失。

## 我在这次改动里犯的错（记录给以后的自己）

插入代码时把**整个用户聚合循环**缩进到了 `if _starts:` 里面，导致：

- 只有带 sys 事件的场次才跑聚合；
- 最终 `att_n` 全部变成 1、`build_axis_table` 返回 0 人、接口 404。

`ast.parse` 是过的（Python 允许更深缩进），所以语法检查**抓不到**这种错。
教训：**改缩进敏感区域的代码后，必须跑一次真实数据的一致性断言**（比如 `max(att_n) == n`），
不能只靠 `syntax OK`。
