# 139-20260917-R35置顶动态：落库 + 每轮刷新 + 排序徽章

> 用户 2026-09-17 原文：「有些 v 会将动态置顶来展示周表或舰礼相关的内容，所以**将抓取到的
> 置顶动态同样置顶**，并且**每日的动态轮询都覆盖它**，保证修改及时被捕捉到」。
> 受理分析见 devlog/137（当时只核实了现状、未动代码）—— 结论是"后端早就认出置顶了，
> 但只用来别让增量停止漏帖"，缺口三处：**没落库 / 已入库的不刷新 / 列表与徽章没位置**。
> 本批开工前拍了两个口径（下面 §零），然后按 R35 → R36 → R37 的顺序落地。

## 零、开工前拍的两个口径（用户选的都是推荐项）

| 口径 | 选项 | 用户选择 | 代价 / 收益 |
|---|---|---|---|
| **置顶帖在列表里怎么摆** | A 排最前只出现一次（`order by is_pinned desc, published_at desc`）· B 接口额外返回 `pinned` 数组、前端单独成块 · C 只加徽章不改排序 | **A** | A 与平台展示一致，且**筛选/搜索时行为自洽**（置顶帖也得自己命中条件才会出现）；B 要改响应结构并额外定义"置顶块受不受筛选影响"；C 等于没解决"沉到上个月去" |
| **"及时捕捉修改"的力度** | A feed 每轮免费刷 + 详情每 6h 最多一次 · B 每轮都拉详情 · C 只在置顶集合变化时拉详情 | **A** | A 的标题/摘要/封面改动**一个轮询周期内**落地、正文级改动最迟 6h；B 请求量与风控风险随置顶数上升；C 的正文改动在"长期挂着的置顶帖"上永远抓不到 |

两个口径都写成了**可调常量**而不是硬编码：`settings.PINNED_DETAIL_REFRESH_HOURS`
（默认 `6.0`；`0` = 每轮都拉；**负数 = 永不主动拉详情**，只刷列表页字段），
并按本仓对"调优项"的纪律**进只读分区**（`runtime_settings.READONLY_NOTES`，理由如实写明）。

## 一、三个缺口各自的修法

### ① 没落库 → 迁移 `f005`

`posts.is_pinned`（NOT NULL 默认 0）+ `posts.pinned_refreshed_at`（详情档刷新的时间戳）+
索引 `ix_posts_platform_uid_pinned`。`MIGRATION_HEAD` 同步 `f004 → f005`
（不同步的话冷启动快路径会把旧库当已最新，迁移永不执行 —— 这是本仓踩过的事故）。

### ② 已入库的置顶帖不刷新 → 新的写路径

根因一句话：**`_safe_store_post` 遇到唯一约束冲突只 `rollback` + 跳过，永远不更新既存行**
（它当年是为"并发重复入库"写的），所以置顶帖的内容永远停在首次抓到的版本。

新增 `scheduler._refresh_pinned_post()`，两档：

| 档 | 频率 | 写什么 | 成本 |
|---|---|---|---|
| feed 级 | **每轮** | 标题 / 摘要 / 封面 / 互动数（列表页响应自带） | **0 额外请求** |
| 详情级 | 按 `PINNED_DETAIL_REFRESH_HOURS` | `body_json` + 派生列 `body_text` + 上面那些（详情更权威） | 1 次详情请求 / 窗口 |

三条纪律：

- **空值不覆盖**（`services/pinned_posts.py::refresh_fields`）：B 站动态 feed 的 `title` 多数为空、
  专栏 feed 没有 `body_json`，直接 `setattr` 会把库里已有的内容抹掉；空统计 `{}` 也放过。
- **详情失败不盖时间戳**：只有**真的拿到详情**才写 `pinned_refreshed_at`，否则保留 feed 级刷新 +
  `logger.warning`（下轮重试）—— 失败若盖了戳，要等一整个窗口才会重试，**看起来就像"作者没改过"**，
  正是本仓最反对的那种静默失败。
- **详情合并口径与新帖共用**：把原来内联在动态循环里的 70 行详情补全（防丢图 / 专栏 delta /
  视频统计合并）抽成 `_enrich_dynamic_item()`，新帖与置顶刷新同走一条 —— 两处各写一遍必然漂移。

### ③ 排序与徽章 → `PostRepo.paginated` + `PostCard`

- `paginated` 排序改成 `is_pinned desc, published_at desc`（**`by_uid` 不动**：它喂给时间线，
  必须保持纯时间序）；置顶帖只有一行 ⇒ 只在第 1 页头部出现一次，`total` 不变。
- 前端：标题上方一枚 `.post-card-pin`（Pin 图标 + 「置顶」粉底 pill）+ `.post-card.is-pinned`
  一圈 `0 0 0 1px` 粉描边。**描边叠在 `--pill-shadow` 上而不是画左边条** —— 卡片是「封面 + 正文」
  横排，左边条会被封面图吃掉；描边与"有没有封面"无关，扫一眼就知道它为什么不在时间线上。

## 二、撤销：置顶集合同步只在**第一页**

`PostRepo.sync_pinned(platform, uid, pinned_ids)` 一次 UPDATE 完成"标记新置顶 + 撤销已取消的"。
它只在**第一页解析成功后**调用（平台只把置顶放首页，**空集合即"当前没有置顶"**），
且必须等本页新帖**先落库**再同步（否则本轮新抓到的置顶帖要拖到下一轮才标上）。

**为什么"失败那轮绝不调"要写进不变量**：风控/网络失败时 `pinned_ids` 是空集，
若照调就会把整片置顶标记清空 —— 一次失败抹掉用户所有置顶，比"没刷新"严重得多。

已知边界（写进 `backend-fetch-pipeline.md` §5.4）：`limit_latest` 模式（收录首屏 / 「最新 N 条」）
会在循环内提前 `return` ⇒ 那一轮不同步置顶集合（下一轮补上）；动态流被关掉时置顶标记**冻结**（不误清）。

## 三、护栏（先红后绿，反向验证 7 项全红）

新用例文件 `tests/test_pinned_posts.py` **12 条**，按"会静默出错的失败模式"分三组：

| 组 | 钉什么 |
|---|---|
| A 集合同步 | 标记 / 二次同步不重复计数 / **取消置顶撤销** / 空集合只清本账号（不碰同平台别的账号） |
| B 列表排序 | 置顶帖排最前（哪怕它更旧）/ **跨页只出现一次** + `by_uid` 仍纯时间序 |
| C 每轮刷新 | 纯判定（窗口 `None`/新鲜/到期/`0`/负数 + 空值不覆盖 + 空统计不覆盖）/ 窗口内**不拉详情**且不盖戳 / 到期拉一次并**重算 `body_text`** / **失败不盖戳 + warn** / 未入库 pid 不报错 / **两条抓取循环的接线**（B 站与微博各一条：置顶走刷新不计 `skipped`、新置顶同轮标上、详情档只花在该花的地方） |

**反向验证**（把实现逐条改回旧行为，确认对应用例变红）—— 7/7 全红：

```
置顶帖仍当跳过（不刷新）        → RED     首页不同步置顶集合     → RED
微博置顶帖仍当跳过             → RED     取消置顶不撤销         → RED
列表排序忽略置顶               → RED     详情失败也盖时间戳     → RED
窗口内也拉详情（不节流）        → RED
```

**探针**：新增第 **17** 个模式 `ui_probe.py --pinned`（`?probe=pinned`）。它往**副本 DB** 种
一条「**2020 年时间戳**的置顶帖」+ 一条「当下的对照帖」⇒ 排序一旦失效，置顶帖必然掉到列表末尾
（判据有牙口）；断言第 1 张是它、带 `.post-card-pin` 与 `is-pinned`、首页只出现一次、
**对照帖不许挂角标**（防"所有卡片都挂角标"的假绿）。反向验证同样两项全红。

## 四、踩到的坑（都是"尺子/现场"层面的，值得留档）

1. **探针跑在有凭据的副本上 ⇒ 时绿时红**：第一次 `--pinned` 跑出来第 1 张是 `cv362939894`
   （**真上游的置顶专栏**！）—— 后端一起来就跑动态流，R35 的 `sync_pinned` 把我种下的
   **假置顶帖**（不在上游置顶集合里）当"已取消置顶"处理。① 这顺带**真机验证了整条链路**
   （置顶帖真被抓到并标上了）；② 但作为尺子必须确定性 ⇒ 改用 `_prepare_logged_out()`
   （未登录副本：内容闸门让后端一次上游请求都不发，本地帖子照常渲染）。
2. **视图钮的名字在 `title` 上，不在 `textContent`**：照 `textContent === '帖子列表'` 找按钮，
   一个都找不到 ⇒ `viewFound=False`。改成与既有 `clickView` 同一套约定（`title.startsWith`）。
3. **"置顶帖在首页出现 0 次"这句判词本身会误导**：采样只取前 12 张，而排序坏掉时置顶帖排在第 20 位。
   改成采样整页（60 张）并把 0 次与多次**分成两句不同的失败信息**。
4. **单测里不能真联网**：R35 让既有两条置顶用例（`test_fetch_posts_core_pinned_*`）从"跳过"
   变成"走详情档"，而 `fetch_dynamic_detail` **未登录也照发请求**（实测 0.4s 一个真响应、
   `code=4101105`）⇒ 两条用例显式打桩，并把这条事实写进注释与用例。
