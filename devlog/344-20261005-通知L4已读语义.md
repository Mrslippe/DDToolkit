# 344-20261005 通知 L4 已读语义：事实变了 ≠ 用户看过了

> 接 `devlog/343`（L3）。L4 = 把"已读"这件事的两种含义**显式分开**，
> 并堵住一个"症状最阴"的误判路径。

## 一、`read` 字段：**显式写下**，不从 `form` 隐式推导

新增 `Notice.read`：`auto`（到点自己消失）· `confirm`（只能用户确认，落 `app_meta`）。

| 形态 | read | 含义 |
|---|---|---|
| `notice`（告知：开播/新版本/磁盘） | `auto` | "已经过去了"，不需要谁确认 |
| `action`（处置：完成报告） | `confirm` | "你得看一眼" |
| `state`（状态：进度/冷却/登录失效） | `auto` | ⚠️ **消失是"事实变了"，不是"用户看过了"** |

后端是一张小表（`notices._read_mode`）而不是 `form == "action"` 那种一行推导：
"要不要用户确认"与"这是什么形态"是**两个问题**，今天一一对应是巧合 ——
写成表，接下一个平台的人有一处可改、也看得见语义。

## 二、⚠️ 状态类**不许进已读集合**（这条是 L4 的全部价值）

`rate-limit` / `login-expired` / `progress-*` 的 id 是**稳定**的。一旦被 ack 进集合，
同一条状态**再次成立**时会被当成"用户看过了"——
症状最阴：**再次被限流，界面什么都不显示**（而它正是最该显示的那条）。

两道防线：

1. **后端拒收**：`ack_notice` 与 `ack_notices`（批量口）都先过 `is_state_id()`，
   命中就跳过并记一行日志 —— 批量口这道是给"前端传错/将来有人把状态塞进「需要处理」组"兜底；
2. **前端按 `read` 筛**：`todoIds` 收 `read === 'confirm'` 的那些（缺字段时按
   `form === 'action'` 兜底老后端）—— 即使一条状态被误放进 todo 组，一键已读也不会带上它。

判据里带**反向对照**：ack 一批含状态类之后，再取一次汇总，"再次限流"那条**照样出得来**
（只测"没写进集合"会让实现退化成"什么都不写"也算过）。

## 三、判据与门禁

- 后端新增 1 条（三形态的 `read` 取值 + 单条/批量两个口拒收 + 反向对照）；
- 前端新增 2 条（状态类即使被误放进 todo 组也不许一键已读 / 缺 `read` 时按 `form` 兜底）；
- 契约键集合加上 `read`（`ALLOWED_KEYS`）—— 少这个键前端会静默按 `auto` 处理。
