# 052-20260910-直播场次对外 id 定权（近期场次详情空白修复）

> 用户 2026-09-10：**为什么直播日历中最近几场直播的信息都展示不出来？**
> 本批 = 纯后端修复（`LiveSessionRepo.merged`）+ 一处文案，无迁移。

## 一、现象与定位

用户口径是「最近几场」——正好等于**近几天既被 danmakus 收录、又被动态流 feed 收录**的场次
（更早的场次只有 danmakus 一行）。日历格子本身正常，空白的是**点开格子的详情弹窗**：
弹幕信息 / 热词 / 直播动态三段全是占位文案。

排查路径（真实库副本，不碰用户数据目录）：

1. `merged()` 输出的**最近场次对外 `live_id` 是 feed 的数字 id**（如
   `723878467234502758`），而更早的场次是 danmakus 的 uuid（如 `c99fb5a9-…`）；
2. 详情端点 `GET /account/{id}/live-sessions/{live_id}` 取弹幕时，只按
   `source` 含 danmakus 就判定可拉，并**拿这个 `live_id` 去问 danmakus**；
3. danmakus 只认自己的 uuid —— 实测同一个场次：
   `uuid → ✅ total=31767 / 40 热词`；`数字 id → ❌ HTTP 400 → None`。

于是详情弹窗的 `danmaku/metrics/events` 全为空 → 三段占位文案。**根因不在详情端点，
而在合并层把「对外身份」交给了错误的源。**

## 二、根因：对外 id 由「谁先被扫到」决定

`merged()` 里表内行两两合并（`_merge_decision` 归类 → `_apply_group_merge` 应用）。
近期场次的形态是「danmakus 一行 + feed 一行，**两端 end_at 都还没落**（刚下播/仍在播）」：

- 「room 去重」分支要求**双方都有 room_id**，而 danmakus 行的 `room_id` 常为 None → 不命中；
- 「dup（时间重叠 + 同标题）」分支要求 `g_end` 有值 → 也不命中；
- 只剩「restart（gap ≤ 10min）」→ `segment_count=2`，且该分支**只补空字段**：
  `if row.live_id and not g["live_id"]` —— 于是 id 取决于**哪一行先被扫到**：
  feed 行先入库 → 对外 id 是数字 id（弹幕详情 400）；danmakus 行先 → uuid（正常）。

实测真实库里近期场次**全部**是前者。这解释了两件事：为什么只有「最近几场」出问题，
以及为什么弹幕详情对被标成「中断续播·2 段合并」的场次失效（同一个分支）。

## 三、修法

1. **对外 id 按源优先级定权**（`danmakus(3) > feed(2) > self(1)`，与 `_SOURCE_PRIORITY` 同源）：
   合并过程中把「各源各自看到的 id」记进分组的 `_src_live_ids`，收尾时取**最高优先级源**的
   id 作为 `g["live_id"]`，然后弹出该暂存键（不进 API 载荷）。
   与行序无关 → 近场次拿到 uuid（弹幕可查）、纯 feed 场次仍是数字 id（无 danmakus 可查，
   本来就该显示「未收录」）；**已有 6 条分类校正**存的都是 uuid，不受影响、也不会再漂移
   （此前 id 会随行序在两种形态间跳，校正有丢失风险）。
2. **同起点同标题即同场**（`_merge_decision` 新增分支）：`row.start_at == g_start and 同标题骨架`
   → `dup`。双源同场但两端都没落 end 时不再掉进 `restart`，`segment_count` 不再被误标成 2
   （弹幕详情里那句「中断续播·2 段合并」对一场正常直播是错的）。
3. **文案区分「上游延迟」与「真没有」**（`LiveCalendar.tsx`）：场次结束 < 24h 时占位文案改成
   「该场次刚结束，弹幕 / 热词仍在第三方收录中（danmakus 通常延迟数小时），稍后重新打开即可看到」
   —— 实测弥月末场 danmakus 侧 `total=0`（刚下播还没收录），这是上游状态，不是本地缺陷。

## 五、经验

- **多源合并的「身份字段」必须定权，不能由遍历顺序决定**：`live_id` 是两条 id 空间
  （danmakus uuid / B 站数字 id）的外键，选错就等于把详情查询指向了另一个宇宙。
  「低优源先入库」在真实数据里是常态（feed 流先落、danmakus 后补），所以这类 bug
  只在**近期**数据上暴露——历史数据早已只剩单源，反而看不出来。
- **合并判据要覆盖「进行中/刚结束」形态**：原判据默认 `end_at` 已落；而近场次两端都空，
  于是掉进最近邻分支（restart）被误标成「中断续播」。凡是按时间区间判定的规则，
  都要问一句「两端都没落定时走哪条路」。
- **上游延迟与本地缺陷要在 UI 上分开**：同一个「暂无数据」，一种是我们的 bug，
  一种是第三方还没收录（实测场次结束后数小时内 `total=0`）。文案不区分，用户只能
  反复报同一种「bug」。
- **排查这类问题先拿数据说话**：把用户库**复制**出来跑真实 `merged()`/详情调用，
  一条 `HTTP 400 liveId=…` 的日志就把范围从「日历渲染」缩到了「合并层 id 定权」。
