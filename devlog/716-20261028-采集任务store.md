# 716-20261028-采集任务状态提升到应用级 store（B 批）

## 需求（用户 2026-10-28 四批改造的第 2 批）

> 点击抓取按钮后……小窗允许暂时关闭，抓取进程保持在后台，在顶栏中展示出来。

修订口径（同日两次）：

- 浮窗**不自动弹出**：「总进度在顶栏通知窗里展示就行，然后可以通过顶栏通知中打开这个浮窗」；
- 采集完成后**不自动分析**（「完成」= 关窗回工作台）。

## 真正会"停"的是前端这一侧

采集本来就跑在后端（`_TASKS` + `/fan/collect/status`）。`关闭浮窗` 不会停任务，
**但轮询原来挂在 `WorkbenchPage` 的 `useEffect` 里** —— 一离开工作台、一关小组件，
进度就没人看了，顶栏也无从展示。所以这批做的不是"新功能"，是**把所有权挪对**。

## 做法

新增 `frontend/src/hooks/useFanTask.ts`（模块级 store + 订阅，同 `utils/hideNicknames.ts` 套路）：

```
FanTaskSnapshot = { kind, vtuber, since, until, state, progress, error, finishedAt, result }
动作：startCollect / cancelCollect / dismissTask / resetFanTask
读：useFanTask()（组件）、fanTask()（非组件）、fanTaskRunning()（互斥判定）
```

三条关键设计：

1. **任务带自己的 `vtuber`**：跑着跑着切走主播，进度不该跟着新主播走。
   显示时用 `task.vtuber`，不用页面的 `picked`。
2. **结束后不自动清空**（`done/failed/cancelled` 停住 + `result` 快照）：
   浮窗要能显示"完成/失败原因"，页面要能据此刷新一次活动。清理由 `dismissTask()` 触发，
   且**只对已结束的任务生效**。
3. **发起请求就失败 ⇒ 也要落到 `failed`**：只 throw 给调用方的话，`running` 永远不结束，
   顶栏会一直显示一个不存在的任务。

`WorkbenchPage` 退化为消费者：本地 `progress` 状态与轮询 effect 全部删除，
改为读 store + 监听 `finishedAt` 边沿（刷新活动读数 + 弹结果，仍然**不自动分析**）。

## 踩到的一个坑（值得记）

用例里 `fanCollectStatus` 的桩返回 `{ items: [], count: 0 }`，原实现里这会让
`progress = null` ⇒ `running` 变 false，轮询自然停。新实现若照抄"`p == null` 就 return"，
任务会**永远停在 running** —— 第一次跑全量直接挂 15 条用例。

修正：`p == null` = 后端没有任务条目（从未开始 / 已清掉）⇒ **停止轮询并结束任务**
（`state: 'done'`，无结果）。这条也写进了用例：`后端没有任务条目 ⇒ 结束轮询，不许卡在"进行中"`。

另外：模块级 store 必须**用例间重置**（`resetFanTask()` 进 `beforeEach`），
否则"上一条还在跑，这一条一挂载就看到进行中的任务"。
