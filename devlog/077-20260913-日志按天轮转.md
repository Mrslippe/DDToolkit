# 077-20260913-日志按天轮转（app.log 不再无限长大）

> 承接 devlog/076 的排查：用户的 `logs/app.log` **5.2MB / 33963 行**、跨了好几个月，
> 里面两条八月旧 checkout 的记录差点被当成现行 bug。当时记在"遗留"里，用户点头：
> **"日志文件按照你说的改动"**。

---

## 一、改了什么

| 项 | 之前 | 现在 |
|---|---|---|
| 文件通道 | `logging.FileHandler`（**不轮转**，无限追加） | `TimedRotatingFileHandler(when="midnight", interval=1, backupCount=7, encoding="utf-8")` |
| 命名 | 恒为 `logs/app.log` | 当前 `logs/app.log` + 备份 `logs/app.log.YYYY-MM-DD`（自动裁剪，保留最近 7 份） |
| 配置位置 | `app/main.py` 顶部三行 `basicConfig` | `app/core/logging_setup.py::setup_logging()`（`main.py` 调用） |
| 可测性 | **测不到**（见 §二） | `build_file_handler()` 是纯函数，测试直接拿它做**真轮转** |
| 可调 | 无 | `LOG_BACKUP_DAYS`（环境变量 `DDTOOLKIT_LOG_BACKUP_DAYS`，默认 7） |

为什么选"按天"而不是"按大小"：本仓排查的第一步就是**按天切一刀**（devlog/076），
备份名带上日期正好对上这个用法；实测正常使用一个月约 5MB，所以"按天 × 7 份"这个上界够用。
（`TimedRotatingFileHandler` 没有大小上限 —— 真出现"单日日志异常大"，那本身就是
"每轮一条 ERROR"这类循环的信号，先去查循环，别先调日志。）

## 二、为什么顺手把配置搬出 `main.py`（不是为了好看）

`logging.basicConfig` **只在根 logger 还没有 handler 时生效**，而 pytest 的日志捕获插件
会先往根上挂 handler → 测试里这段配置**从来不会执行**。于是"日志写不出去 / 文件无限长大"
这类问题只能靠人肉发现 —— 本仓历史上就发生过一次（`logs/app.log` 恒为 0 字节，devlog/013），
当时也是靠人肉看出来的。

搬成 `build_file_handler()` 之后，测试可以**直接构造 handler 并真的翻页**，不用依赖根配置

## 三、护栏：`test_log_file_handler_rotates_daily_and_prunes`

真的写盘、真的翻三次页，断言：

- handler 类型与关键参数（`when=midnight`、`interval=86400`、`backupCount`、**UTF-8**）——
  `when="midnight"` 会被规范成 86400 秒（不是 1），**缺 `encoding` 在 Windows 上按 GBK 写、
  中文直接乱码**，所以这两项都钉住；
- 目录不存在时会自动创建；
- 三次翻页后**只剩 2 份**备份（`backupCount=2`）、文件名按日期有序、最旧那份被删
  （"第一天"的内容随之消失）、当前文件是重新起的。

**反向验证**：把 `backup_days` 换成 0（= 不裁剪）跑同样的三次翻页 → 备份数 3，断言立刻失效
—— 说明"只剩 2 份"不是空转。

### 踩到的两个 stdlib 细节（都写进测试注释）

1. **`doRollover()` 第一件事是 `if os.path.exists(dfn): return`（"Already rolled over"）** ——
   手工预造备份文件时如果正好撞上本次目标名，整次轮转会被**静默跳过**（不改名、不裁剪）。
   第一版测试就是这么假绿的（预造了 `2026-09-08/09/10`，正好撞上目标名 `09-10`）。
   改成"连着翻三次页"来自然制造多余备份。
2. **裁剪按文件名（=日期）排序取最旧**：所以必须**由远及近**地翻页；倒着翻的话，
   刚生成的那份备份会立刻成为"最旧"并被同一轮裁掉（现象：第三次"没有新备份"）。

## 六、遗留

- **老的大文件不会被自动切分**：现存 `app.log`（5.2MB）会在第一次跨零点轮转时被整体改名成
  `app.log.<当天日期>`，之后 7 天内随常规裁剪消失。想立刻瘦身就手动把它挪走（不影响运行）。
- 没做"按大小兜底"（理由见 §一）；也没做日志查看 UI（`§TODO` 里仍是"暂无"）。
- `httpx` 的 INFO 行占日志大头（每个请求一行）：**没有**动它 —— 它是排查超时/风控的一手证据
  （devlog/062 就是靠它定位的）。若哪天嫌吵，最省事的是 `logging.getLogger("httpx").setLevel(...)`，
  但那会丢掉唯一的"请求-响应时序"记录，需要时再说。
