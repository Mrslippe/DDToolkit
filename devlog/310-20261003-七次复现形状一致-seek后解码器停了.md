# 310-20261003 七次复现形状完全一致：seek 后解码器停了 2–4 秒

> 用户口径：「我复现了，从第二次开始都是**关闭了其他所有窗口**测试，问题依旧」。
> 这一句把"窗口不可见/被遮挡"这条路彻底排掉（日志里也是 `隐藏=0s 失焦=0s`），
> 而剩下的证据**指向一个很具体的东西**。

## 一、七次坏例的形状一模一样

```
1s:153fps/5.2  2s:0fps/6.2  3s:0fps/5.3  4s:0fps/4.3  5s:0fps/3.2  6s:23fps/2.6  7s:36fps/3.1
1s:153fps/19.4 2s:0fps/29.1 3s:0fps/28.1 4s:8fps/27.1 5s:34fps/26.1 6s:30fps/25.1
1s:153fps/6.6  2s:0fps/5.6  3s:0fps/4.6  4s:0fps/3.6  5s:8fps/3.3   6s:24fps/2.8 …（之后稳定 29–31）
1s:153fps/5.2* 2s:0fps/4.2  3s:0fps/3.2  4s:8fps/2.7  5s:36fps/3.3  6s:30fps/3.7
```

**每一次都是**：第 1 秒爆发 **153 帧**（≈5 秒的内容！）→ 接下来 **2–4 秒一帧都不出** →
然后回到 30fps。而这期间：

| 指标 | 值 | 说明 |
|---|---|---|
| 最低缓冲 | **2.2 – 25.1 秒** | 数据多到用不完（有一次 25 秒） |
| `饿住` | 各 **1 次** | 只有 seek 那一下，之后**从没饿过** |
| `卡帧` | 0–1s | `currentTime` **一直在走**（媒体钟没停） |
| `隐藏/失焦` | **0s / 0s** | 窗口可见、有焦点（用户也实测关了所有窗口） |
| 音频 | 全程正常 | 用户观察 |

⇒ 数据、时钟、音频、窗口可见性**四项全部正常**，唯独"帧不产出"。

## 二、153 帧 + 随后 2–4 秒空白 = seek 的**预滚/追赶**（progressive 无索引源）

那条曲线读起来只有一种解释：**Chromium 在 seek 之后做了一段"解码追赶"（preroll），
追赶完又空了 2–4 秒**。

为什么会有追赶：B站给的是**裸 fMP4**，我们是 `src=` 直接喂（没有 MSE）。
Chromium 的 MP4 demuxer **不读 `sidx`**（那是 MSE/分片播放才用的索引），
所以"跳到 126 秒"对它来说只能是 **按码率猜一个字节位置 → 从那里的关键帧解码 → 一路丢弃到目标时刻**。
那 153 帧就是这段丢弃式解码；而目标附近的数据还得等 CDN 再给一段，
于是出现"追赶完 → 空几秒 → 才稳定 30fps"。`currentTime`  meanwhile 照走（Chromium 让时钟跑），
所以观感就是**画面冻在最后一帧 / 极低帧率，而声音一直正常**。

这也解释了三件早就观察到但一直没归因的事：
1. **只有 seek 之后才犯**（从头播时 demuxer 不需要追赶）；
2. **B站网页播放器（MSE）没这问题**（用户最初的观察）——MSE 下 seek 是"按索引取段再 append"；
3. **我们在 CDN/代理侧怎么查都查不出问题**——因为真的不是数据的问题。

## 三、这一版把"哪一段掉的"也拆开量（`playbackProbe.ts`）

行里现在是**四段节拍**，卡在哪一段一目了然：

```
解码=30.0fps 提交=18.0fps 呈现=7.3fps 页面=60.0fps   解码停=3s 提交停=0s
```
| 字段 | 来源 | 掉了意味着 |
|---|---|---|
| `解码=` | `webkitDecodedFrameCount` | 解码器没出帧（**seek 追赶**就落在这段） |
| `提交=` | `getVideoPlaybackQuality().totalVideoFrames` | 有帧但没交给合成器（渲染器/GPU 段） |
| `呈现=` | rVFC `presentedFrames` | 交给合成器了但没上屏（合成节拍） |
| `页面=` | `requestAnimationFrame` 计数 | **整页**自绘节拍（对照：整页卡还是只有视频卡） |

判定也据此细分：`呈现受限(解码器停：seek 后在追赶)` / `呈现受限(解码有帧但没提交)` /
`呈现受限(合成节拍)`。**再复现一次就能把最后一点歧义消掉**：若 `解码停=2~4s`，
就与上面的推断完全吻合。

## 四、对 MSE 立项的意义（这次是**升格**，不是划掉）

`devlog/309` 我写过"换 MSE 治不了卡顿"——那条只对"窗口不可见"那一类成立。
现在证据指向 **seek 的盲目追赶**，而这**正是 MSE 定义上消除的东西**：

- `sidx` 给的是**现成的时间→字节索引**（我实测过：54 段 × 5 秒、段首是关键帧）；
- 我们自己按段取、按段 `appendBuffer` ⇒ **seek = 取目标段**，不存在"猜位置 + 丢弃追赶"；
- 顺带把两个钟（`299`–`305` 那一串）也一起收掉。

⇒ 建议**直接进 S1 spike**（`docs/plans/bili-mse-kernel-execution.md` §五，1 天）：
后端出段表接口 + 最小 MSE 页，判据是 **seek 后 1.5 秒内出画、稳定 ≥29fps、解码停=0**。
spike 达标就上 S2；不达标（例如 `sidx` 解析不成立）再回头查渲染段。
