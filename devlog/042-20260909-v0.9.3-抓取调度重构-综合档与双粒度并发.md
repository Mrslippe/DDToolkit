# 042-20260909-v0.9.3-抓取调度重构：综合档（账号流数据驱动 + 双粒度并发 + 外部批次排队）

> 用户 2026-09-09 三条调度调整需求：
> ① T1 每 V 主账号字段抓取周期改为一天一次（账号字段没什么频繁变化）；
> ② T2 与 T3a 合并，并且「不同平台抓取频率上限是分开的」→ 同时执行多个平台的请求，
>    节约用户感知的响应时间；
> ③ T4 外部数据批次被手动任务插队时不该直接跳过，应在手动任务结束后继续执行。
>
> 澄清问答结论：账号信息周期取「每天一次（动态流照旧 15min，账号流到期才跑）」；
> 并发粒度「1 和 2 都做」（任务级 + 平台级）；启动时是否跑账号流**按上次抓取时间判断**。

## 一、模型变化：T1/T2/T3a → 一个「综合档」

| 旧 | 新 |
|---|---|
| T1 主要账号 5min（账号锁） | **账号流**：全量账号，数据驱动到期（默认 24h），账号锁 |
| T3a 全量账号 随 T2（账号锁） | 同上（T1+T3a 合并为一条账号流） |
| T2 最新动态 15min（帖子锁） | **动态流**：每 V 主账号 1 页 + 限 2 帖，帖子锁 |
| 三者串行（启动链 T1→T2→T3a） | **同档并发**（`asyncio.gather`），墙钟 ≈ max(两条流) |

- **数据驱动到期**（`account_sweep_due()`）：任一可抓取账号的 `last_fetched_at`
  为空或早于 `now - ACCOUNT_SWEEP_STALE_HOURS(24h)` → 到期。不依赖进程内计时器，
  重启/休眠后行为一致；启动链也用它决定要不要跑账号流（用户口径）。
- **双闸门**：数据到期 + `ACCOUNT_SWEEP_MIN_GAP_SECONDS(600s)` 进程内硬下限，
  避免抓取失败（`last_fetched_at` 没更新）时每 10s 重试一次的风暴。
- 账号流成功一次即写一条统计快照（与 T3a 同口径；旧 T1 是不写的），
  粉丝趋势仍是日粒度（按天取最后一条）。

## 二、双粒度并发（`_run_platform_rounds`）

用户要「1 和 2 都做」，于是把并发拆成两层，同一套轮次执行器同时满足：

1. **任务级**：动态流 ∥ 账号流（两把锁互不牵连）——重叠窗口墙钟减半；
2. **平台级**：每条流内部按平台分组，**每轮各就绪平台各处理一个元素**，
   平台之间并行、平台内部串行 —— 单平台请求速率不变。

执行器细节：

- 某平台风控（`rate_limited`）→ **只冷却该平台** `RATE_LIMIT_COOLDOWN`，其它平台继续；
  全部冷却则一起等最早解冻的；
- 轮与轮之间是**手动让位断点**：`_auto_yield_account_with(commit)` /
  `_auto_yield_post_with(commit)` 提交各平台会话 → 交还锁 → 手动跑完 → 重新拿锁续跑；
- 每个平台自持 SQLAlchemy 会话（Session 不可跨协程并发），账号对象按 id 在本平台
  会话内重取，保证 commit 落对地方；
- 进度：`_status.account.current` / `post.target` 显示当轮就绪平台名
  （如「bilibili、weibo」），`index/total` 为全局聚合。

用户数据实测（5 V / 8 账号 = 6 B 站 + 2 微博）：动态流 ≈30s、账号流 ≈36s，
串行 66s → 并发 ≈36s。

## 三、T4 外部批次：排队等待而非跳过

`run_external_daily_jobs` / `run_external_weekly_jobs` 改走
`_wait_for_manual_tasks(timeout=1800s, poll=15s)`：手动抓取在跑就等它结束再执行，
超时才放弃本轮。运行期间置 `_external_running`，综合档心跳据此跳过（避免自动档与
外部批次叠在一起）；手动任务不受影响（外部源打的是第三方站点，不占两把锁）。

- 删除已死的「定时任务优先让位」机制：`_yield_request` / `yield_requested()` /
  `_yield_account_wait` / `_maybe_yield_account` / `_maybe_yield_post` 及 6 处调用点
  （自 v0.6.0 起无置位方，方向也已被「手动优先」取代）；

- `async_fetch_and_update(check_yield=...)` 去掉无用的 `check_yield` 参数。

## 六、经验

- 「周期」最好用**数据状态**表达（上次成功抓取时间）而不是进程内计时器：
  重启、休眠、失败重试都自然正确；但一定要配一个最小间隔闸门，否则失败会变成忙循环。
- 并发粒度选「平台」是这类多平台抓取器的甜点：既能吃到平台间的并行收益，
  又天然不放大单平台速率（平台内仍串行），风控只需按平台隔离。
- 让位/抢占这类协议在「多流并发」下必须把断点放在**协调器**能安全交锁的位置
  （这里是每轮之间），否则某条流单独让位会让锁的持有者语义错乱。
