# 227-20260927-R50c轮播不算开播

用户报障（2026-09-27 凌晨）：「为什么现在是下播时间但是提醒我明前奶绿开播了」。

## 一、根因：`bool(live_status)` 把「轮播」当成了开播

T0 直播状态核里的进入沿判据原本是：

```python
edge = acc.live_status != prev_status
started = bool(acc.live_status) and not prev_status     # ← 错在这
```

B 站的 `live_status` 有三态：**0 未开播 / 1 直播中 / 2 轮播（录播循环）**。
主播下播后房间常挂在 `2`，于是 `0 → 2` 被 `bool()` 判成"开播"。

实测取证（用户机器）：

```
她当前：live_status=2（轮播）  live_title='休息回~喵喵'  room=25034104
日志  ：04:13:55 动态流恢复正常节奏（检测到开播（明前奶绿））
```

日志那行是既有的 `note_dynamics_activity("检测到开播（…）")` —— 也就是说**这个误判早就存在**
（开播会让动态流恢复满速），只是当时用户看不到；R50 把通知挂在同一个分支上之后，
误判就以"弹窗"的形式暴露出来了。

## 二、修法：只有「直播中」才算开播

```python
started = acc.live_status == 1 and prev_status != 1
```

| 转换 | 算开播？ | 为什么 |
|---|---|---|
| 0 → 1 | ✅ | 真开播 |
| 2 → 1 | ✅ | 轮播转直播 = 开播 |
| 0 → 2 | ❌ | 下播后挂轮播（本次报障的场景） |
| 1 → 2 | ❌ | 转轮播，不是新开播 |

一处改动同时修好三件事：**通知**、**`note_dynamics_activity` 的满速恢复**（轮播不该被当成
"内容马上会来"）、以及日志里那句误导人的"检测到开播"。

## 三、判据

`tests/test_notifier.py`：

| 用例 | 钉什么 |
|---|---|
| `test_live_sweep_does_not_notify_on_round_play` | `0 → 2`（轮播）**不许**通知 |
| `test_live_sweep_notifies_on_real_start_only` | `2 → 1` 通知；`1 → 2` 不通知；`2 → 1` 再通知 |

两条都直接跑 `live_sweep_core()`，把 `fetch_bilibili_live_batch` 换成固定返回
（批间停顿设 0，测的是状态机不是节流）。

⚠️ 写用例时踩到的坑：夹具给的收集列表与去重记账是**两套状态** —— 阶段之间既要
`notifier.reset_state()` 清去重（同一场直播不重复弹是本来设计），也要 `sent.clear()`
清列表，否则上一段的投递会留在 list 里（第一版就是这么红的）。

## 四、连带说明

「轮播」本身在界面上仍然如实显示（左栏徽标 / 状态岛走的是 `live_status` 原值），
只是它不再触发"开播"这件事 —— **判据的语义**改在这里，展示口径不动。
