用户口径（2026-10-12，原话）：

> 「直播场次信息在入库的时候根据其中携带的各类数据直接推断出类型，
>  不需要再在新增场次的时候去考虑改变已经入库的历史场次类型」

## 二、落库口径：只留逐场次能算的那几档

「入库时按这一场自己带的数据推」与两个全局信号**直接冲突**（它们要看"同账号、全历史"），
所以推断栈从七档缩到四档：

| 档 | 落库 | 为什么 |
|---|---|---|
| `override` | ❌ | 用户写的事实，读取时压在落库值上面（`live_category_overrides` 独立存在） |
| `series` | ❌ | 骨架聚类要看全历史；逐场次下同一骨架每次结论相同 ⇒ 这一档没有意义 |
| `title` | ✅ | 多词评分 |
| `learned` | ❌ | 校正反哺词库同样是全账号聚合（实测贡献 **0 场**）。代价：**校正不再外溢**，只影响被点的那一场 |
| `area` | ✅ | B 站房间分区，实测 47.9%，是主力 |
| `date` | ✅ | 生日/首播日/事件当日。⚠️ 真机 14 个 V **有生日 0 个、有首播日 0 个**，事件表 1 行 ⇒ 今天永不命中，签名留着不额外查库 |
| `fallback` | ✅（**不落库**） | 中性「直播」；见下面那条 |

**兜底不落库**（`category` 保持 NULL）是有意的：NULL = "还没定出来"，
与"算过但没结论"必须是同一种状态 —— 否则 ① 规则以后变好，认不出这些行该重算
（列不空了）；② 统计口径里 `fallback` 会和"真判过"混在一起。读取时照样显示中性，
因为读取侧对没有落库值的组会按**同一个函数**现算一次。

**校正不写类型列**：它只活在 `live_category_overrides`。所以"清空校正"能回到**落库值**，
而不是停在最后一次校正上。

## 三、分层：仓库层只写不算（被判据逼出来的形状）

第一版我把 `write_settled(row)` 直接写进了 `LiveSessionRepo._upsert`（仓库层 import 服务层），
被 `tests/test_dependency_direction.py::test_repositories_do_not_import_services` 当场拦下。
最终形状是「**服务层装好上下文交给仓库写**」：

- `app/services/live_settle.py`：`settle` / `settle_fields` / `settle_danmakus_item`（纯函数）
  + `for_group` + `backfill_rows` + `BackfillStats`；
- 写点（服务层与路由层）调它，把结果**作为参数**传给仓库：
  `upsert_danmakus`（条目里带 `category`）、`upsert_feed(..., settled=)`、
  `create_manual(..., settled=)`、`update_row(..., settled=)`。

⚠️ 类型两列**不混进 `fields` 字典**：`fields` 走"非空值刷新"（`None` = 别动它），
而定稿的 `None` 是**有意义的最终值**。混在一起我实测撞到两种误判 —— 兜底写不进去、
以及每次同步把定稿值冲回 NULL。分开之后语义唯一：**给了 `settled` = 定稿过了按它写（含 None）；
不给 = 这一轮不碰类型**。

这与仓库那条既有纪律同源（`upsert_danmakus` 的 `platform` 必须由调用方传入：
**仓库层不替上层做决定**）。

## 四、惰性回填：为什么不是脚本

**迁移会自动跑**（`app/main.py::lifespan` → `_run_migrations`，且升级前自动备份），
但 `scripts/backfill_*.py` 那五个**不会** —— 它们只有人手执行才跑。所以"我开发时跑过回填"
对用户机器等于零：他们那 8,515 行的 `category` 会全是 NULL。

选定做法（用户 2026-10-12 拍板）：**惰性回填**，读路径顺手补齐。

- 位置：`routers/vtuber.py::_stored_by_live_id`（列表/详情/写回执三个端点共用）；
- 只补**合并组的代表行**、只补**真正的推导**（`title`/`area`/`date`，兜底不补）；
- 补过就不再补（列不为 NULL 即跳过）⇒ 每个账号只补一次；用的函数与写路径同一个。

## 六、施工中真踩到的坑：`merged()` 的 `with_ids`

`_stored_by_live_id` 靠 `src_live_ids` 定位代表行，而**列表端点原来调的是默认的
`merged()`**（不带 ids）⇒ 找代表行**静默返回空表**：落库值明明写着，界面却按现算显示。
不报错、不漏日志，症状只有"某个场次的类型看起来没生效"。

钉了一条**双向**判据 `test_stored_lookup_needs_src_live_ids`：同样的行，
带 ids 能读到落库值、**不带 ids 读不到**（后半句是反向验证 —— 它也顺手看住了
"以后有人把这行改成默认 `merged()`"）。

## 九、一处**有意的错位**：`types=` 在服务端，但日历在前端筛

实现时发现两件事打架：

- 这一页**每次都要全量**（筛选条的计数必须看得见别的类型，否则就是上面那条"空间被吃掉"）；
- 而"什么算这一类"这件事**只能有一份实现** —— 那是服务端的类型语义（`types=` 端点参数

## 十三、补：筛选条的探针判据（同一批收尾）

`utils/liveCalendarFilter.test.ts` 守的是**纯函数**（筛得对不对），但「点胶囊 → 状态变 →
网格跟着变」这条**接线**在 vitest 里够不着（挂 `LiveCalendar` 要 mock 整条取数链 + Radix）。
于是给 `ui_probe --archive` 加了一条**真点一次**的判据：

- 选中那一类的**当月计数**，必须等于筛后**当月**格子「N 场」之和
  —— 两个数来自两条不同的代码路径（chip 的计数 / 格子的渲染），对得上才算接线正确；
- 点完之后**别的胶囊计数一个都不许变**（它们按全量算，见 §八 的第一条口径）；
- 「全部」复位之后格子场次之和回到点之前那个数。

⚠️ **这条判据第一版是红的，红的却是我自己**：格子求和把 42 格里的**上下月补位格**也算了
进去（chip 是"当月"），于是 6 ≠ 5。修法是给日期格加 `data-lc-in-month`，求和只数当月格。
值得记的是**它为什么会红**：胶囊与格子这两个数本来就没人在对账，谁多算一格都不会有别的
症状 —— 而"用户拿这两个数中的哪一个做判断"恰恰是随机的。

## 十五、更正：**日同步本来就会重判老行**（动手前量出来的）

写 T3 词表草稿时我把一个问题问错了。当时的推理是：

> 写时定稿 = 写这一行就冻住 ⇒ 换体系之后，库里那批旧 `fitness` 会一直挂着 ⇒
> 要问用户"要不要为这一批破例跑一次重判"。

**这个推理漏了一步：日同步到底会经手哪些行，我没量。** 量了之后（新工具
`scripts/check_resettle_scope.py`，真机副本 + 真上游）：

```
账号 15（七海Nana7mi）：1244 行
同步结果: added=1 · updated=1220
变化：类型两列被写 610 行 · updated_at 抬过 1220 行 · 标题变过 0 行
```

原因是 danmakus 的 `/channel lives` 返回**全历史**（不是增量），而写时定稿挂在
`upsert_danmakus` 上（每条重新 settle 一次）⇒ **日同步本身就是一次"用当前规则重判"**。

于是「改规则不回填老数据」的**准确版本**是：

| 行 | 会不会被新规则重判 |
|---|---|
| **上游索引覆盖**的行 | **会** —— 下一次日同步就是重判（真机 1220/1244） |
| 索引碰不到的行（纯 feed / 手动 / self 推导） | 不会 —— 停在写入时的规则上 |
| `category_from='override'` | 不会（用户手定的） |

**这条对用户口径 3 的意义**：他要的是"新增场次时**不必**去操心历史场次"，
而不是"历史场次永远不许变"。现在的行为正好是那个意思 ——
**没有读时全局重算、没有回填脚本，规则改动通过"下一轮同步顺手生效"传播**。
所以 T3 不需要任何破例动作，那批 `fitness` 会自己跟上（可验证：换完再跑一次这个脚本）。

⚠️ 记这条的真正理由不是结论，而是**过程**：我差点让用户在一个不存在的问题上做决定
（"要不要破例重判"），而那个问题的前提（"日同步不会动老行"）**我一次都没验过**。
和本批第一节那个"27 条虚拟场次"是同一类错 —— **把推断当成量过的事实**。
两次都是靠"动手前先跑一遍"抓回来的。


`scripts/make_label_set.py` 三个动作：生成标注页（固定种子 ⇒ 逐字节可复现）·
`--collect` 把用户的判断落成固定回归集 · `--ruler` 在当前规则上跑出
**吻合率 + 按档拆解 + 判错清单**。

评测口径是**读取时的生效值**（override > 落库值 > 现算），也就是用户在日历上真看到的类型 ——
不是 `settle()` 单独的输出。标 `?` 的（人眼也判不出）不进吻合率但单独报出来；
库里已不存在的场次跳过并说明（**不静默少算**：少算会让吻合率看起来更好）。

用我自己按现有判断写的 7 条样例当测试件跑过一次：吻合率 42.9%，
拆解 `fallback 0/4 · area 2/2 · title 1/1` —— gap 全在 `fallback` 那档，
正是 T3 要打的地方（验证完即删测试件）。
