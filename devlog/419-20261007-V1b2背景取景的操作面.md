## 方向口径（本批唯一碰契约的地方）

`x`/`y` = **取景点在图片上的归一化位置**，与 CSS `object-position` 同向：`x=0` 看左边缘、`x=1` 看右边缘。
⇒ 公式是 `translate((0.5-x)·(s-1)·100%, …)`：`x` 越大 ⇒ 图往**左**推 ⇒ 露出的正是右半张。

验算（s=2、`transform-origin` 默认 center）：缩放后图占 `[-W/2, 3W/2]`，`dx=-50%` ⇒ 挪成 `[-W, W]`
⇒ 窗口 `[0,W]` 落在缩放图的右半 = **原图右半** ✓。

⚠️ V1b-1 写成了 `(x-0.5)`。那批只有"存/取/套用"，**没有交互 ⇒ 符号没人能证伪**；
本批拖拽一上手就露馅（往右拖反而看到左半张）。**有外部判据的批次才检验得了上一批的口径** ——
所以回归判据现在是端到端的：拖右 60px ⇒ `x` 减 0.2 **且** 渲染出的 `dx` 为正。

## 判据（10 条，`components/BackgroundFocusEditor.test.tsx` 9 + `utils/backgroundFocus.test.ts` +1）

1:1 跟手（300px 舞台、scale=2、拖 60px ⇒ x 恰好 0.3、`translate(20%, 0%)`）· 死区（点一下不算取景，

关窗兜底补发最后一格 · 坏 JSON 原样铺 · 重置不动背景图 · 方向键与拖拽同一模型。

## 三个坑

1. **`scale=1` 时平移在数学上无处可去**（溢出量 `(s-1)·W ≡ 0` ⇒ `Δx` 无论怎么拖都是 0）。
   处理是"**越过死区后**抬到 120%"而不是"拖不动就算了"，也不是"点一下就放大"（死区在前）。
   ⚠️ 抬缩放必须**只在本来是 1 时**做：第一版无条件抬，用户拖着 200% 的图一按就被拽回 120%。
2. **假绿一次（记录在案）**：滑杆那条第一版**只因为**「填 900% 被 jsdom 夹成 300%、DOM 值与 React 的
   value 记录器对不上」才触发 `onChange` —— `el.value = x` 会被 React 的 value 拦截器当成"自己写的值"
   而静默吞掉（写了个一次性探针实测：直接赋值 + `input` 事件，百分比纹丝不动）。
   现在断言里先钉一句"百分比确实动了"，再谈防抖。**"事件派发成功"和"处理器真的跑了"是两件事。**
3. **关窗兜底**：滑杆防抖窗口（260ms）内关窗会把最后一格丢掉 ⇒ 卸载时补发一次
   （与弹窗里 `commitSign` 同一套路）。⚠️ 判据要能区分"兜底发的"与"防抖到点发的"——
   先断言挂着的定时器数量，再断言补发。

## 顺手记

预览与卡片页几何完全相同（同一份 `focusTransform`、同样 `cover` + `transform-origin: center`），
但 `cover` 的裁切量取决于容器宽高比 ⇒ 预览只是**同向**，不是像素级对齐（别拿它验像素）。
