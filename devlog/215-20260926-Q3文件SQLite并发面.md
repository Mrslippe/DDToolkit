## 二、这一批的价值大半在"判据自己写错了三次"（都留了记录）

1. **`busy_timeout` 第一版测的是"超时"不是"排队"**：写成"持锁不放 ⇒ 30s 后仍报错"，
   跑一次 65s，而且拿掉 `busy_timeout` 也照样红——典型的"断言在测别的东西"。
   现在：持锁者**中途放手**，断言排队者**真的等过**（`elapsed >= 0.3s`）且提交成功。
2. **驱动 `timeout` 与 `PRAGMA busy_timeout` 是同一个旋钮**（pysqlite 的 `timeout` 参数
   就是设 `busy_timeout`）⇒ 第二版用驱动默认 5s 压那条，**拿掉 PRAGMA 照样绿**。
   现在测试引擎把驱动超时设成 **0**：容忍度只可能来自 PRAGMA，**拿掉就红**。
3. **竞争写第一版是假绿**（最值得记的一条）：360 笔微事务在"驱动超时 0 + 无 PRAGMA"的
   裸配置下**也一次都不冲突** —— GIL + 亚毫秒事务意味着根本没重叠。
   试过把驱动超时压到 0.05s，**仍不够**（50ms 等待对亚毫秒事务绰绰有余）。
   现在**每笔写在事务里停 3ms**（`flush()` 之后、`commit()` 之前，贴近真实写事务持锁时长），
   竞争才真的发生 ⇒ 那条用例从此咬得住"容忍度是不是来自 PRAGMA"。

## 三、如实标注的**判据边界**

- **`journal_mode` WAL→DELETE 这条改法不会让 ③（快照语义）变红**：rollback journal 在
  RESERVED 阶段也允许读，要到提交的 EXCLUSIVE 那一瞬才挡（实测）。
  ⇒ ③ 钉的是**语义**（未提交读旧值、读不被挡），而"journal_mode 是不是 wal"由 ① **直接断言**。
  **没有**去写一条"WAL 比 DELETE 并发度高"的统计判据（那要测时延，必飘）。
- ⑦ 钉的是**平台事实**（Windows 上连接没放开就改不动名），它的产品用法在
  `app/main.py::_quarantine_database`（§6 第 28 条）。这条用例把"为什么必须先 dispose"
  从注释里搬进了判据。

**反向验证 3/3 真红**：生产引擎不挂监听器（①红）· 去掉 `busy_timeout`（②④都红）。

## 六、收尾：⑦ 第一次上 CI 就红了（Linux 两条腿）

`test_dispose_releases_the_file_so_it_can_be_renamed` 的"不 dispose 就改不动名"那半条
写成无条件 `pytest.raises(OSError)` —— 而 **POSIX 允许改名/删除打开中的文件**，
Linux 上直接 `DID NOT RAISE`，两条 Python 腿一起挂（**Windows 腿反而绿**，
本地更是永远看不见）。修法：那半条加 `os.name == "nt"` 守卫，
**"dispose 之后一定改得动"两个平台都断言**（那才是产品依赖的一半）。

⇒ 提炼进 `docs/DEV-LOOP.md` **§6.14**：凡判据依赖"文件被占用 / 删不掉 / 改不了名"这类
**操作系统语义**，就分平台断言 + 可移植的那半条两边都断 + 边界写进 docstring ——
别让它变成一条"只在 CI 上红"的谜题。
