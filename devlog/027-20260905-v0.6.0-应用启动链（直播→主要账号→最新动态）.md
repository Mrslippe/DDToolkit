# 027-20260905-v0.6.0-应用启动链（直播→主要账号→最新动态）

## 概述

应用启动时（后端 lifespan 之后）自动拉起一条**三级启动链**，守护线程串行执行，
各自容错互不影响：

1. **直播状态更新**（最高优先级、最快完成）——B 站**批量**直播接口，全量账号
   仅 1~2 个请求，数秒内点亮/熄灭左右栏直播徽标；
2. **主要账号信息获取**（次级优先）——每个 VTuber 仅更新**主要活动账号**
   （`PRIMARY_PLATFORM_ORDER` 平台优先级，默认 bilibili 优先）的全字段；
3. **动态更新**（最低优先级）——每个主要账号仅拉第 1 页动态且**最多入库最新
   `STARTUP_DYNAMICS_LIMIT`（默认 2）条新帖**，避免库容差异导致单 V 长任务。

## 实现要点

### 阶段 1：`startup_live_sweep`

- 新增 `fetcher.fetch_bilibili_live_batch(mids)`：B 站
  `room/v1/Room/get_status_info_by_uids`（`uids[]` 批量参数，每 100 uid 1 请求），
  回 `{uid: {live_status, live_title, room_id, live_url}}`；风控/接口异常返回 None；
- 仅回写 live 字段（不动签名/头像/粉丝），**live 跳变时落一条统计快照**
  （直播日历场次 edge 数据，短时直播也不漏）；
- 每批完成即 `_push_account_snapshot` → 前端左右栏徽标实时同步；
- 间隔 `STARTUP_LIVE_INTERVAL_MIN/MAX`（0.3~0.6s）；风控 → 冷却后重试同批。

### 阶段 2：`startup_main_account_sweep`

- 每个 VTuber 的主账号 = `PRIMARY_PLATFORM_ORDER` 优先（bilibili > weibo）首个
  有 uid 的账号；
- 复用 `_fetch_one_account`（名/签名/头像下载/粉丝/直播全字段）；
- **不写统计快照**（周期全量任务负责时间序列，避免启动链污染）；
- 间隔 `STARTUP_MAIN_INTERVAL_MIN/MAX`（2~3.5s）。

### 阶段 3：`startup_latest_dynamics`

- 每主账号 `_fetch_posts_for_account(acc, 0, 1, include_videos=False,
  stop_on_existing=True, limit_latest=2)`——**`_fetch_posts_core` 新参数
  `limit_latest`**：同页入库满 N 条新帖即停，其余新帖留待下次渐进消化
  （多次启动后按 2 条/次匀速补档，单次时长有上界）；
- 间隔 `STARTUP_DYNAMICS_INTERVAL_MIN/MAX`（3~5s）。

### 协议与状态

- 三个阶段分别走既有**账号/帖子锁、状态通道、让位协议**（`_yield_account_wait`
  从 `_maybe_yield_account` 抽出复用；`_fetch_scope` 新增 'live'/'main' 标记，
  定时任务内容一致跳过判定只认 'full'——启动链数秒/数分钟即完，与定时器
  （5 分钟节奏）实际几乎不相遇）；
- 手动触发冲突时阶段**跳过**（锁非阻塞获取失败即放弃），不排队不阻塞用户操作；
- 完成汇总走 `_set_account_last_result` / `_set_post_last_result`（kind=startup），
  TopBar 胶囊可见；
- `STARTUP_CHAIN_ENABLED` 一键关闭；`STARTUP_CHAIN_DELAY`（默认 4s）等后端/
  前端就绪。

## 验证

- 新增测试：批量直播回写 live 字段 + 跳变统计快照；`limit_latest` 同页 2 条即停
  （N3/N4 不入库）；
- `python -m pytest tests -q -p no:cacheprovider` → **152 passed**。
