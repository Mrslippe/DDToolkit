# 305-20261003 真正的原因：画面饿住的时候，声音还在跑

> 用户："还是会冻一帧 + 抖一阵，彻底审查问题并找出真正的原因，之前的改动都没有根本地动到实处。"
> —— 这句话是对的。前五批（`299`–`304`）全都在调"**什么时候允许画面跑**"，
> **从来没有管过"画面停的时候声音还在跑"**。这一条才是根因，而且量得很干净。

## 一、把它量出来（无头 Edge + 限速代理，30 秒）

把视频轨限速到略高于实时码率（265 KB/s，实测片源约 1900 kbps），逼出周期性饿住，
同一个页面跑两种口径（音轨都用**独立 `<audio>` 元素**，与 App 同构）：

| 口径 | 事件 | **A/V 漂移中位** | **最大** |
|---|---|---|---|
| `free`（音轨自由跑 = **本组件原来的行为**） | `waiting` 23 次 | **4.55s** | **8.90s** |
| `gate`（`waiting` ⇒ 停音轨；`playing` ⇒ 对齐再起） | `waiting` 23 次（画面抖得一模一样） | **0.06s** | 0.54s |

外加一条直方图式的现场（`free`）：30 秒里漂移**单调增长**到 8.9s ——
`cur` 19.85 / `a_cur` 28.45。因为**两条流是两个独立的钟**：音轨跟声卡走，永远按真实时间前进；
视频轨"有数据才前进"，一饿住就原地踏步。画面越卡，差得越多。

## 二、于是用户看到的三段现象全都能对上

1. **"卡在一帧"** —— 画面没数据，停在最后一帧（没有可显示帧时是 poster）；
2. **"抖一阵"** —— 漂移纠正（`devlog/298`）发现 |drift| > 0.6s 就**把音轨硬拽回去**，
   于是每秒拽一次、每次拽回一点：**声音在重复/跳动**，而画面还在饿；
3. **"过一会同步"** —— 缓冲终于追上、画面不再饿住 ⇒ 漂移停止增长 ⇒ 拽的频率归零。

⇒ 前五批修的是"界面/状态/按住时机"，全是**外围**；这一条是**播放模型本身**的问题：
**双元素播放必须让音轨从属于画面**，而不是各跑各的钟。

## 三、改法（一行半，但位置必须对）

```ts
const onWaiting = () => {
  showSpin()
  audioRef.current?.pause()      // ★ 画面停了，声音也停
  …（缓冲治理的按住逻辑不变）
}
```

配套两点：

- `onPlaying → startAudio()` 现在同时是**每次饿住之后的重同步点**：先把音轨 `currentTime`
  对齐到画面当前时刻，再出声 —— 不许把饿住期间攒下的差带进后半段（`startAudio` 本来就是
  "已同步就不动"的幂等实现，所以反复饿住也不会引入抖动）；
- 漂移纠正（±3% 慢追 / >0.6s 硬拽）保留，但它的定位变了：**只管两条钟的速率差**
  （实测 1.5%，19 秒 0.28s），不再承担"画面饿住"这种量级 —— 那种量级现在压根不会出现。

**反向验证过**：把那一行注释掉，两条新用例立刻红（"画面饿了音轨必须停"、"反复饿住每次都要停"）。

## 四、顺带回答"为什么别人家的播放器不这样"

B站自己的播放器是 **MSE**（它的统计面板写着 `Player Type: DashPlayer`）：把音视频两路都喂进
**同一个 `<video>` 元素**的 SourceBuffer ⇒ **只有一个钟**，缓冲、seek、A/V 同步全由浏览器内核
统一管，压根不存在"两条流各跑各的"这件事。我们走的是 progressive `<video src>` + 独立
`<audio>`（因为 B站没有 MPD，裸 fMP4 用不了 dash.js，见 `devlog/290`），
所以**这套从属关系必须由我们自己维护** —— 这一批补的就是它。

若之后还想再上一档，方向是**自己写 MSE**（按 `moof`/`mdat` 切段 append 给两个 SourceBuffer），
那会把"两个钟"从根上消掉；代价是要自己解析/切分 fMP4 并管理缓冲配额。

## 五、判据（新增 2 条）

| 用例 | 钉什么 |
|---|---|
| 饿住 ⇒ 停音轨、出画 ⇒ 对齐再起 | `waiting` 必须 `audio.pause()`；`playing` 时音轨 `currentTime` 被对齐到画面当前时刻且重新 `play()` |
| 反复饿住 | 三次 `waiting` ⇒ 三次停（漂移不许累积） |
