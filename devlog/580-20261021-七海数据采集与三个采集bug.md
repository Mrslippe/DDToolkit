# 580-20261021-七海Nana7mi：采集 96 场 + 修掉三个采集 bug

用户要求"按现在的采集流程采一遍七海nanami，采完再验证"。结果先踩了三个坑。

## 一、确认对象

搜索有歧义：`七海Nanami` 是另一个 1,791 粉的小号（签名写着"我不是VTB，你找错人辣"）。
要采的是 **七海Nana7mi**，mid **434334701**，112 万粉，VirtuaReal。区间 2026-07-01 ~ 10-20，共 96 场。

## 二、三个采集 bug（都会造成"数据缺失却不报错"）

1. **跨度赋值缩进错**：`start_at` / `end_at` 被误缩进进 `elif ts_span` 分支，
   走"平台跨度"这条路时永远是空串。新采的 96 场起止全空。
2. **只翻页不先行**：部分场次带 `pageNum` 返回 0（`pageSize` 越大越容易触发）。
   改为**先不带 `pageNum` 取一次**（pageSize=100000），不够再翻页；翻页首页为空则退回那次结果。
3. **翻页上限 20 页**：5000/页 × 20 = 100,000，正好卡住大场次（最长 131,583 条）。
   → 提到 60 页；另外"命中页大小上限就强制翻页"（服务端会把 total 也谎报成 100,000）。

## 四、一个重要的反例：>7 小时不一定是坏数据

七海的时长分布：**中位 6.06h、p90 9.34h、最长 11.59h，>7h 有 33 场**。
但逐小时看，这些场次**整夜都在说话**：

```
2d08a5c0（11.59h）  22:2978  23:2969  00:3581  01:7182  02:3691 … 09:2331  10:2512
```

所以率降规则**正确地没有裁它们**。这说明"超过 7 小时就有问题"是**针对那三个试点 V 的经验**，
不是普适判据 —— 她本来就常开通宵场。

## 五、遗留

- 5 场覆盖率 94.6%–97.6%：接口自身分页不一致（`total=102,983` 但翻到底只有 97,983），
  已取较完整的一侧；这类场次在分析时应可接受；
- 率降阈值（10%）仍只在 227 场试点上验证过，七海这批**没有触发**，等于多一组"不误伤"的证据。
