# 036-20260908-v0.9.1-直装版首启卡幕（资源被打平）与扫码登录凭据丢失修复

> 用户 2026-09-08 反馈两个「打包版」问题（开发态不复现）：
> ① 直装版（NSIS）装好后**首次运行**一直卡在开幕前的 LOGO 呼吸界面，便携版无此问题；
> ② 便携版能进应用，但**B 站扫码登录**手机确认后应用毫无反应。
> 两件事根因完全独立，但都属于「开发态跑得好、打包/首次运行才暴露」的类型。

## 一、直装版首启卡幕 = NSIS 安装包把后端 `_internal` 目录打平了

### 现象与排查

- 用户日志：`%APPDATA%\com.ddtoolkit.app\logs\sidecar.log` 有 16:37:15 的启动记录，
  但 16:37 那次**没有任何后端日志**（`app.log` 只到 alembic 插件行为止）；
  16:38:42 之后的第二次运行则一切正常 —— 典型「只有首启坏」。
- 先怀疑首启迁移慢/卡死，于是**用真实冻结后端 + 空数据目录复现**：
  `ddtoolkit-backend.exe`（`DDTOOLKIT_DATA_DIR=<空目录>`）→ `/healthz` 12 秒内就 200，
  `vtuber.db` 建表完成 → **后端本身没问题**。
- 再直接看安装目录：`E:\work\Project\release-test\direct-setup\DDtoolkit\binaries\backend\`
  有 748 个文件、88.2 MB，**但没有 `_internal/` 目录**；而便携版同路径有 `_internal/`、
  852 个文件 88.7 MB。PyInstaller onedir 的 exe 必须与 `_internal/` 同目录才能加载
  Python 运行时 —— 少了它，exe 一启动就死，且**无控制台的安装版连错误都看不到**
  （Rust 侧把 sidecar 的 stdout/stderr 打到自己 stdout，GUI 程序里等于丢弃）。

### 根因（tauri-utils 的资源语义）

`frontend/src-tauri/tauri.conf.json` 原来写的是 **map 形式 + glob**：

```json
"resources": { "binaries/backend/**/*": "binaries/backend/" }
```

`tauri-utils-2.9.3/src/resources.rs::resource_from_path` 对「map + glob」是这么算目标的：

```rust
ResourcePathsInnerIter::Glob { .. } => dest.join(path.file_name().unwrap()),
```

——**只保留文件名**，目录层级被丢弃；而「数组形式」走 `resource_relpath(path)`，
按相对路径原样保留（`binaries/backend/_internal/xxx.dll` → 同路径）。
于是安装包里 `_internal/**` 被摊平进 `binaries/backend/`，与 `vtubers.csv`、`alembic/`
的脚本混在一起，后端 exe 再也找不到自己的运行时。

**为什么便携版没事**：便携版 zip 由 `scripts/collect_release.py` 直接打包
`frontend/src-tauri/binaries/backend/`（构建产物，`_internal/` 完整），不经 Tauri 资源映射。

### 修复

1. **`tauri.conf.json`**：资源改用数组形式（保留目录层级）

   ```json
   "resources": ["binaries/backend/**/*"],
   ```

2. **首启失败不再无声**（三处加固）：
   - `frontend/src/main.tsx`：`tauriBootstrap()` 补 `.catch` → 落 `failed` 态
     （原来 invoke 失败时 Promise 拒绝、幕布永远停在呼吸态，既无错误也无重试入口）；
   - 启动幕 pending 态显示「正在启动内置服务… Ns」——让「在等」和「卡死」可区分；
   - `backend_main.py`：改用 `uvicorn.Server` API，**bind + startup 完成后**才打
     `DDTOOLKIT_READY` 并写 `[perf] uvicorn 已监听（就绪）`；uvicorn 异常
     （最常见 = 端口被占 bind 失败）连 traceback 一起落 `sidecar.log`
     （实测：占用端口后重启，sidecar.log 出现 `FATAL uvicorn 退出: SystemExit: 1` +
     `OSError: [Errno 10048] ...`，此前这条信息只进 stderr 等于消失）。
3. **首次运行日志不再被 alembic 吃掉**：`alembic/env.py` 的 `fileConfig` 会摘掉
   `app.log` 的文件 handler，导致「要跑迁移的那一次启动」日志整段缺失（正是最需要日志的
   场景，本次排查就被它误导过）。改为：应用内迁移置
   `cfg.attributes["configure_logger"] = False`（`app/main.py::_alembic_config`），
   只有独立跑 alembic CLI 时才接管日志。

## 二、扫码登录「手机确认了但应用没反应」= 轮询读错了状态码字段

### 现象与日志证据

安装版日志里连续十余次扫码尝试都是同一个形状，且**每次 poll 都发生在 generate 之后
几十毫秒**（不可能是真扫码）：

```
[INFO]  httpx: GET .../qrcode/generate 200 OK
[INFO]  httpx: GET .../qrcode/poll?qrcode_key=... 200 OK
[INFO]  app.services.auth: 扫码确认成功，正在获取登录凭据...
[WARNING] app.services.auth: 登录验证失败: code=-101, msg=账号未登录
```

注意**没有** `Cookie 已更新: SESSDATA=...` 这一行 —— 一个凭据都没提取到，
`nav` 用空/旧 cookie 校验必然 `-101`。用户侧看到的就是「刷新二维码后立刻提示失效 /
确认了也没反应」。

### 根因①（决定性）：`data.code` 才是扫码状态，外层 `code` 只是「接口调用成功」

对 B 站 poll 接口的**真机实测**（2026-09-08，无需扫码即可复现）：

```json
// 未扫码
{"code": 0, "message": "OK", "ttl": 1,
 "data": {"url": "", "refresh_token": "", "timestamp": 0, "code": 86101, "message": "未扫码"}}
// 二维码失效
{"code": 0, "message": "OK", "ttl": 1,
 "data": {"url": "", "refresh_token": "", "timestamp": 0, "code": 86038, "message": "二维码已失效"}}
```

外层 `code` **恒为 0**，扫码状态在 `data.code`（86101 未扫码 / 86090 已扫码待确认 /
0 已确认 / 86038 已失效）。而 `poll()` 原来读的是外层 `code`：

```python
code = poll_data.get("code")   # ← 永远是 0
if code in QR_SUCCESS: status = "confirmed"
```

于是**每一次轮询都被判成「已确认」** → 立刻进 `complete()` → `data.url` 是空串 →
没有回调可访问 → 取不到 cookie → `nav` 返回 -101。这就是「手机还没扫就显示
登录失败 / 刷新二维码后立刻失效」的完整成因。
顺带：常量表里 `QR_WAITING=86090 / QR_SCANNED=86101` 两个也写反了（86101 才是未扫码）。

### 根因②（即使轮询修对了，取凭据这步也会失败）

1. `complete()` 用 `_parse_set_cookie(response)` 取凭据 —— httpx 的 `response.cookies`
   **只含最后一跳**的 Set-Cookie，而 B 站凭据往往发在中间 302 上；同时回调 URL 的
   **查询串里本身就带 SESSDATA/bili_jct/DedeUserID**（crossDomain 跨域传递），两条路都没读。
2. `BilibiliAuth._save_to_env()` 在 `.env` 不存在时直接 `warning` 返回 ——
   而「首次扫码登录」恰恰就是数据目录里还没有 `.env` 的场景（全新安装），
   即使取到凭据也只会活在内存里，重启即丢。

> 开发态之所以「看起来能登录」，是因为项目根 `.env` 里本来就有有效会话：
> `nav` 校验拿旧 cookie 通过 → 打印 `二维码登录成功 (mid=...)`。
> **扫码登录其实一直是坏的**，只是被已有登录态掩盖了。

### 修复（`app/services/auth.py`）

- **`poll()` 改读 `data.code`**（缺 `data` 时回退外层 `code` 兼容异常响应）；
- 修正常量语义：`QR_SCANNED=86090`（已扫码待确认）、`QR_WAITING=86101`（未扫码）；
- 新增 `_cookies_from_url()`：从回调 URL 查询串解析凭据（最稳的一路，先落底）；
- 新增 `_collect_cookies()`：**重定向链每一跳**（`response.history`）+ **客户端 cookie jar**
  （`client.cookies`）汇总；`_update_from_response(response, jar)` 支持 jar 与 `None`；
- `_parse_set_cookie` 对 `response.cookies` 访问加保护（极端情况下 response 未绑定 request）；
- `_save_to_env()` 去掉「文件不存在就返回」的短路，交给 `save_env_keys`
  （它本就会创建父目录与文件）；
- `complete()` 顺序改为：空回调地址直接失败（不再让 nav 去撞 -101）→ URL 查询串 →
  回调请求（重定向链 + jar）→ nav 校验。

### 验证

**真机接口实测**（`_tmp_qr_check.py`，用后即删 —— 不需要手机就能验状态判定）：

| 场景 | 结果 |
|---|---|
| `start()` 生成二维码 | ✅ 拿到 H5 扫码 URL |
| 未扫码 poll | ✅ `status=waiting`（外层 code=0 / data.code=86101）——修复前会误判 confirmed |
| 伪造 key poll | ✅ `status=expired`（data.code=86038） |
| 空回调地址 `complete()` | ✅ 被拦下并提示「请重新扫码」，不再空跑 nav |

**合成测试**（`_tmp_auth_check.py`，用后即删）：

| 场景 | 结果 |
|---|---|
| 回调 URL 查询串（含 URL 编码的 SESSDATA） | ✅ 解析并 unquote |
| 凭据只在重定向链的中间 302 上 | ✅ 提取 |
| 凭据只在客户端 cookie jar 里 | ✅ 提取 |
| `.env` 不存在时 `_save_to_env` | ✅ 创建文件并写入正确内容 |

### 续修：`Multiple cookies exist with name=SESSDATA`（用户实机第二轮）

修完轮询字段后，用户扫码终于走到「取凭据」这一步，界面却直接抛出
`Multiple cookies exist with name=SESSDATA` —— 这是 httpx 的 `CookieConflict`：
回调会在 `.bilibili.com` 与 `passport.biligame.com` 等多域各写一份同名 cookie，
`Cookies.get(name)` 遇同名即抛异常。我的第一版 `_collect_cookies` 里 `jar.get(name)`
就踩了这个坑（微博侧早踩过：见 `weibo_auth` 同名 SUB 去重注释与
`test_weibo_session_complete_dedupes_same_name_cookies`）。

**修复**：新增 `_pick_cookie(container, name)` —— 先试 `get()`，失败则遍历
`jar`（`http.cookiejar` 支持同名多 Cookie）按域优先级挑
（`.bilibili.com` > 其它 bilibili 子域 > 其它）；`_parse_set_cookie` 与
`_collect_cookies` 都走它；`_parse_set_cookie` 改用 `headers.get_list("set-cookie")`
以看到多值。`complete()` 顺序也调整为「回调请求 → 重定向链/jar → **回调 URL 查询串
最后覆盖**（crossDomain 的权威值）」。

**回归用例**（`tests/test_auth.py`，不再用临时脚本）：
`test_bili_poll_reads_inner_data_code`（四态）、`test_bili_poll_falls_back_to_outer_code`、
`test_bili_pick_cookie_handles_duplicate_names`、`test_bili_complete_uses_callback_url_credentials`、
`test_bili_complete_rejects_empty_callback`。

## 三、把验证循环缩短：`docs/DEV-LOOP.md` + `scripts/dev_check.py`

用户反馈「每次都要构建太耗时了」。复盘：两个 bug 都是**状态依赖**的
（全新数据目录 / 冻结运行时 / 安装包布局），而开发态默认带着旧 `.env` 与老库，
所以只能出包才发现。但**这些状态全都能在开发态复现**，不必每次整包重建：

- `scripts/dev_check.py`：一条命令 = `pytest`（202 用例）+ **空数据目录起后端**
  验 `/healthz` 与扫码状态机（`qr/start` → 连续 `qr/check` 必须停在 `waiting`）；
  `--frozen` 追加冻结 exe 冒烟，`--portable` 追加「只重打便携 zip」（免 cargo/NSIS）。
  实测：基础档 ~20 秒，`--frozen` ~1.5 分钟。
- `scripts/collect_release.py --portable-only`：后端改动后重打便携 zip（约 30 秒），
  不必等 4–6 分钟的整包。
- `docs/DEV-LOOP.md`：写清「什么改动需要多重验证」的对照表（数据目录/冻结运行时/
  资源映射/前端产物），以及手动复现四步。
- 顺带修掉一个长期红着的测试：`tests/test_services.py::test_version_synced_with_devlog`
  还写死 `"0.8.0"`（0.9.1 发布时漏改，导致回归网一直是红的）。改为跨文件比对
  `config.VERSION / tauri.conf.json / package.json / Cargo.toml`，以后漏同步立刻炸。
