# 472-20261013 虚拟场次落表：量完发现没有"虚拟场次"，所以不做

> 上一批（`devlog/471`）把类型列做实之后，`/live-type-stats` 还剩一次 `merged()` ——
> 理由写的是"虚拟场次没有表内行，SQL 看不见"。用户点头做掉它。
> **开工前先量，量完结论反了**：这件事不该做。

## 一、量到什么

真机 14 账号（只读副本，`tmp` 脚本）：

| | 合计 |
|---|---|
| self 快照推导出来的场次 | **139** |
| 其中**没有表内行、需要新建行**的 | **0** |

139 条快照**无一例外**都通过 `_find_group` 挂到了已有的表内行上（补 `end_at`、
偶尔补标题）。⇒「虚拟场次」在本仓的**真机数据里根本不存在**，那一档不是"场次来源"，
而是**挂在场次上的观测事件**。

## 二、落表能省多少

`merged()` 中位（同机、同库副本，5 次取中位）：

| | 账号 22（1,398 行） | 账号 15（1,245 行） |
|---|---|---|
| 全量（含快照推导 + `_find_group`） | 54.1 ms | 54.9 ms |
| 只装表内行、不碰快照 | **25.8 ms** | **22.8 ms** |

⇒ `/live-type-stats` 92ms → 约 65ms；`/live-sessions` 118ms → 约 90ms。
两个端点都是"打开一屏时一次"，不是每轮轮询。

## 三、为什么不值（这是本批真正的产出）

落表的代价**不是"多一张表"**，而是**合并语义要改**：

- 这些场次变成行之后，`merged()` 就会让它们走**行**的合并规则
  （`room` / `dup` / `interrupt` / `restart`），而它们今天走的是 `_find_group` 的
  **区间重叠优先 + 端点容差**（两条判据不等价）；
- snapshot 行**没有 `room_id`**、标题**常常为空** ⇒ 一次合并就可能把原本并成一场的
  **拆成两场**（日历上多出一场）。而这正是 `_find_group` 当初被写出来要修的那个毛病
  （它的 docstring 记着实测：4 条本应合并却算两场、七海那条跨 40 小时的伪场次）；
- 要保等价，就得让 `_merge_decision` 为 self 行**复刻 `_find_group` 的规则** ——
  等于把一套已经调过的判据实现第二遍，两份迟早漂移。

**28ms（且一次打开只付一次）换"日历可能多出一场"，不划算。**
判据与用户当初否掉「按页取数」时用的是同一条：先看痛感。

## 四、落档

- 不变量 39/40 所在的 `docs/backend/LIVE-AND-DANMAKU.md` 里记了这条
  （"self 快照推导的场次落表这件事不要做"+ 数字 + 理由）；
- 「按页取数」（`docs/plans/live-sessions-page-scope-execution.md`）那批**仍然没做**，
  它要解决的是另一件事（按页合并，不再随历史增长），与本条不冲突也不互为前提。

## 五、下次什么时候值得重看

判据两条（任一成立再看）：① 真机出现**真有**孤儿虚拟场次（例如用户从不挂 danmakus、
只靠自观测跑）；② `/live-sessions` 的耗时跟着历史长度长到用户能感觉到
（那批叫「按页取数」，它的 P1 就是先把"合并是局部的"变成可执行判据）。
