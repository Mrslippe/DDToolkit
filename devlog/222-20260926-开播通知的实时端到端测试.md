# 222-20260926-开播通知的实时端到端测试（借一个「此刻正在播」的主播）

> 用户：「现在没有新主播开播，如何能实时测试一下」
>
> 问题很实在：开播通知的判据是**状态边沿**（未在播 → 在播），而"有没有人开播"
> 由上游决定 —— 等一个真实开播可能要几小时，且**不能靠自己硬造边沿**（造出来的
> 是假边沿，验不到真实链路）。

---

## 一、思路：不等人开播，去**借**一个正在播的

两条现成事实拼起来就够了：

1. 候选池 `vtubers.csv`（随包分发）里有 **9482 个 B 站 UID**；
2. 应用自己的批量直播接口（`fetch_bilibili_live_batch`，`get_status_info_by_uids`）
   一次能问 100 个 —— 实测**此刻全池有 425 个人在播**（2026-09-26 19:5x）。

于是：在**临时数据目录**的库里插一个"此刻正在播"的主播，`live_status` 初值 0，
跑一轮**真实的** T0 轮询（`scheduler.live_sweep_core`）→ 抓到 1 就是一次真正的
0→1 边沿 → 边沿判定 / 文案合成 / 入队 / 投递线程 / 气泡（含点击直达）整条链路都动。

**不碰真库真订阅**：全程 `%TEMP%\ddtk-live-notify-e2e/`，跑完即删。
这比"改一个 live_status 试试"强的地方在于：**边沿是真的**，上游、解析、判定一个都没跳过。

## 二、新增 `scripts/live_notify_e2e.py`

```powershell
python scripts/live_notify_e2e.py --list 10      # 先看看此刻谁在播（只看不弹）
python scripts/live_notify_e2e.py                # 借一个在播的，真弹一次（默认扫 600 个 UID）
python scripts/live_notify_e2e.py --uid 1265680561   # 指定 UID
python scripts/live_notify_e2e.py --hold 0       # 弹完就退
python scripts/live_notify_e2e.py --keep         # 留下临时目录排查
```

输出会逐步交代：候选池规模 → 此刻在播的几个（含直播间链接）→ 临时库的边沿前提
（`live_status=0`）→ 轮询结果（`live_status=1` + 直播标题）→ 通知文案与点击目标 →
气泡是否交给 Windows。

**两个容易漏的细节**，都在这轮踩掉：

- **`--hold`（默认保持 12s）**：气泡的点击靠我们那个窗口收回调，进程一退就点不动了 ——
  验完立刻退出会把"点击直达"验成假失败。所以成功后面板要留一会儿。
- **输出标记用 `[ok]/[FAIL]`，不用 `✓/✗`**：Windows 控制台默认 GBK，
  非 GBK 字符会直接抛 `UnicodeEncodeError` 把脚本打断（本仓 `dev_check.py` 早就是这么干的）。

## 三、顺带给 `notifier` 加了一个"投递判据"

队列版通知是"投出去就不管"，没有返回值可断言 —— 脚本没法回答"到底交出去了没有"。
所以这轮在 `notifier` 里补了三样，都是为"可判定"服务的：

| 新增 | 作用 |
|---|---|
| `_deliver(item, balloon)` | 把"写 click_url → show → 记结果"抽成**单条投递**函数，worker 与测试共用；成功/失败/异常三条路都记原因 |
| `last_delivery()` | 最近一次气泡投递的 `{title, body, url, ok, detail, at}` —— 端到端脚本与排查就靠它 |
| `_make_balloon()` / `stop_worker()` | 后端可替换（测试塞假后端）+ 投递线程可收尾（脚本/测试），**不碰通知区域也能验投递** |

顺带把失败日志补齐了：气泡失败时把**内容与点击目标**都写进日志
（"通知不弹"的报障第一眼就该看到"内容是对的、只差系统那一层"）。

## 五、在"真实桌面"上跑这一趟，踩到四件事

1. **我的执行会话不在用户的桌面上**：`GetProcessWindowStation/GetThreadDesktop` 显示进程在
   `WinSta0\CodexSandboxDesktop-…`，而 explorer 在默认桌面 —— 所以 `FindWindowW("Shell_TrayWnd")`
   恒为 0、`Shell_NotifyIcon` 必然失败。**在我这里"弹不出来"不等于代码有问题**（devlog/220 §四.4
   那句环境说明的准确形式就是这个）。
   要在用户桌面上跑测试，只能借系统投递：`Register-ScheduledTask`（`-LogonType Interactive`）
   + `Start-ScheduledTask`，任务在用户的交互桌面执行。
2. **消息泵没有上限 → 真实桌面上把进程困死**（真 bug，本轮修掉）：`_Balloon.pump()` 原本是
   `while PeekMessageW(...)`，鼠标扫过通知区域时 shell 会**连续投回调消息**，于是
   `wait()` 里的时间判断永远轮不到 → 表现是"气泡弹完了但进程不走"。沙箱桌面上消息稀少，
   这个坑**完全看不出来**。修法：`pump(budget=64)` + `wait()` 分批泵（带单测）。
3. **`.cmd` 里的中文注释在 GBK 控制台下会把下一行吃掉**：计划任务跑 `.cmd` 时，中文注释的
   UTF-8 字节被 OEM 码页解释，末字节吃掉了换行 → `cd /d …` 与 `python …` 合成一行 →
   退出码 1、日志根本没生成。教训：**送进 `cmd.exe` 的脚本一律 ASCII-only + 绝对路径**。
4. **别让它弹可见的控制台窗口**：第一次测试用 `python.exe`，用户桌面上多出一个黑色窗口，
   顺手关掉就把测试进程一起结束了（日志停在弹气泡之前、事件日志里什么都没有，很像"崩溃"）。
   改用 `wscript` 隐藏启动 `pythonw.exe` 后干净利落。

> 顺带把失败日志补成了"内容 + 点击目标"一句话（排查"通知不弹"时先看它）。

## 六、一个必须说清的前提

**当前正跑着的应用是 `dist-release\DDtoolkit-portable\ddtoolkit.exe`** ——
它自带的后端是**改动前**的冻结 exe，因此：**在它里面看不到新通知**（不是没触发，是那份
后端里还没有这段代码）。要在**应用里**看到，得先重打后端（`npm run build:backend`）并重启，
或走 debug 壳（`tauri dev` 直接跑 `python backend_main.py`，改后端零打包，见 `lib.rs`）。

而 `live_notify_e2e.py` **不需要重建**：通知是由脚本进程自己弹的（气泡是系统级的，
谁弹都一样），所以"现在就想过一眼"用它最快。
