# 460-20261010-自审：端点耗时仪器与一致性扫描

用户定的下一步是「最近 6 批的自查」。上一批（`devlog/459`）刚修完用户报的"数据卡片加载 8 秒"，
而那次暴露的东西比 bug 本身更值得处理：**8.9 秒的回归没有任何仪器能提前发现**
（`PERF.md` §1/§2 量的是内存与启动，判据里没有"端点耗时"这一项，所以是用户先感觉到卡）。
自查分两半：**① 补那台仪器**；**② 扫"同屏两处读不同字段"那一类**（`devlog/458` 的企划 bug 就是这个形状）。

## ① 端点耗时仪器：`scripts/measure_endpoints.py`

口径四条（缺一条结论就不可信）：只读打开真机库（`mode=ro`）· 进程内 `TestClient` 打真实端点
（含 Pydantic 序列化，那才是用户等的那一份）· 跳过会出网/会写的端点（`…/upstream`）·
**非 200 一律当失败、不打数字**。

实测（账号 22 = 场次最多那个，表内 1,394 行 / 合并后 1,256 场）：

| 端点（用户可见的那张卡） | 中位 |
|---|---|
| `/account/{id}/live-sessions` 日历卡 | **155 ms** |
| `/account/{id}/live-sessions/{id}` 详情弹窗 | 95 ms |
| `/account/{id}/fan-trend` 折线卡 | 33 ms |
| `/account/{id}/gift-days` | 26 ms |
| `/vtuber/pool/search`（9.6k 行） | 13 ms |
| `/vtuber/list` 左栏 | 8 ms |
| `/vtuber/notices` 轮询 | 5 ms |
| `/capabilities` | 4 ms |

### ⚠️ 这台仪器**第一次跑就在说谎**，而那是它最有价值的一次运行

第一版忘了带 `X-DDToolkit-Token`（S1 起后端要它）⇒ 八个端点全 401 ⇒
**表里整整齐齐印着「3ms」、判决行还写着「最慢的一项中位数：4ms」**。
401 是中间件里**没进业务代码**就返回的，所以那不是"测出来很快"，而是"**仪器在说谎**"——
一次真实的 8.9s 回归与它同框也看不出来。

⇒ 判据改成**非 200 直接终止、退出码 1、不给任何数字**。宁可不给表，也不给一份"看起来全绿"的表。
（同一批还踩了一次 `app/core/config.py` **导入时**读环境变量：设 token 的语句晚一行就等于没设。）

### 归因：剩下的 155ms 花在哪（`--breakdown`）

`repo.merged()` 84ms（其中 `_find_group` **约 66ms**、ORM 装载 1,394 行 21ms）·
逐场次推断循环 36ms · `_infer_basis` 11ms · 序列化 6ms · 其余 1–2ms。

**顺手纠正一个记错的数**：`PERF.md` 里这条端点原先记的是 **32ms**（`devlog/459`）。
两个数都对，量的**不是同一段** —— 459 量的是「聚类 + 词库」那一截（正是出 O(n²) 的地方，
本次拆段量到 9+36=45ms，同量级），而仪器量的是用户真等的那一整个响应。
**只报一个端到端数字就无法判断"这次改动动了哪一段"**，所以拆段是仪器的组成部分，不是附件。

### 优化候选（**未做，只记账**）

`_find_group` 是 **O(快照数 × 分组数)**：每个自观测快照都线性扫过**全部分组**。
纯函数微基准（直接喂合成分组，不碰库）：

| 分组数 × 快照数 | 耗时 | 每对 |
|---|---|---|
| 1,256 × 14（今天这台） | 37 ms | 2.1 µs |
| 2,512 × 28 | 170 ms | 2.4 µs |
| 5,024 × 56 | 691 ms | 2.5 µs |

两个因子各自翻倍 ⇒ 耗时各翻一倍（**双线性**，每对 ~2.4µs 稳定），而两个因子都只增不减。
可行的修法是把候选组收敛成一个窗口（分组按 `start_at` 有序，重叠与 ±90min 兜底对 `g_start`
都单调 ⇒ 可先二分再扫），但**改的是已按 3,311 场校准过的合并口径**，得先给"窗口边界"补判据 ——
等用户点头再做，没顺手改。

## 顺手关掉：一条判据的**覆盖面**自己在漂

新脚本要发 token 头，而 `tests/test_dev_token.py` 里那条判据是**写死 5 个文件名**的。
于是"新脚本自动受管"从来没成立：`extension_smoke.py` 早就 `urlopen` 业务端点却一直在单子外面，
`measure_endpoints.py` 同样落在外面。这正是 `dev_token.py` 开头那条教训
（"**加了门禁就要把所有开发态调用方过一遍**"）的同一个形状 —— 前三次是漏改调用方，
这次是**判据的覆盖面**本身。

- 受管名单改成**派生**：`TestClient(` 或（`urlopen(` 且出现业务路径）。现在 7 个，旧 5 个全在，
  `shutdown_smoke.py`（只 ping 公开的 `/healthz`）正确地**不在**里面。
- ⚠️ **判据本身也换掉了**：原来是 `"dev_token" in text`，而变异验证（把新脚本的 import 整句删掉）
  **照样绿** —— 因为文件里还有 `scripts/dev_token.py` 这种散文提及和 `dev_token_value` 这种变量名。
  改成**结构**判据（真的有那句 `from dev_token import …` / `import dev_token`）后才杀得死。
  这是本仓第四次踩"**变异杀不死就先怀疑判据**"。
