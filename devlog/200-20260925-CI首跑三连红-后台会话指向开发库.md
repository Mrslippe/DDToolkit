# 200-20260925-CI 首跑三连红：后台会话指向开发库 + pytest 路径

**这一篇是本轮最有价值的一次排查**：三个"看起来像平台问题"的红，根因是同一个——
**测试里的后台任务一直在连我的开发数据库**，而我的开发库恰好有数据和表，
所以本地全绿、CI（空数据目录）全红。

## 一、现象

推送后 CI 首跑：前端腿绿、Windows 的 Rust 与冻结后端冒烟全绿，**pytest 三处全红**
（Linux 3.12 / 3.14 + Windows）。两轮才修完：

| 轮 | 失败 | 根因 |
|---|---|---|
| 1 | 三条腿都是 `ImportError while loading conftest`：`ModuleNotFoundError: No module named 'app'` | `pytest` 可执行文件**不把 CWD 加进 `sys.path`**；我本地一直用 `python -m pytest`（会加） |
| 2 | `test_vtuber_api.py::test_account_info_endpoints_stay_available_without_login` 三处都红：`no such table: accounts`；另有 `test_next_due_honours_idle_floor` 时序抖动 | 后台任务的会话连的是**开发库** |

## 二、第 1 轮：`pytest.ini` 补 `pythonpath = .`

`python -m pytest` 与 `pytest` 的差别就是这一条。修法两层：`pytest.ini` 显式声明
`pythonpath = .`（治本），`scripts/gate.py` 统一成 `python -m pytest`（保险）。

## 三、第 2 轮（本文重点）：后台任务连的是**真实数据目录**

日志只有一行关键：
```
sqlalchemy.exc.OperationalError: (sqlite3.OperationalError) no such table: accounts
```
调用链：`POST /vtuber/{id}/fetch` → `scheduler.async_fetch_vtuber` → `_accounts_by_ids(db, …)`，
而那个 `db` 来自 **`scheduler.SessionLocal()`** —— `scheduler.py:20` 自己 import 的工厂，
连的是 `settings.DATA_DIR/vtuber.db`。

⚠️ `tests/test_vtuber_api.py` 只做了 `app.dependency_overrides[get_db] = override_get_db`
—— **那只覆盖路由的依赖注入**。抓取类端点在后台跑时用的根本不是路由那个会话。

**为什么本地从来没红**：我的 `DATA_DIR` 是项目根，那里的 `vtuber.db` 有 `accounts` 表，
甚至有 id 匹配的行。CI 是干净 clone + 全新数据目录 ⇒ 一个表都没有。
**这正是 `ARCHITECTURE.md` §6 第 21 条记过的"本地残留环境恰好满足条件"**，
只是这次残留的不是"登录态"而是"库里有表"。

**修法**：加 autouse 夹具把 `scheduler.SessionLocal` 也钉到测试引擎；
另加一条**回归用例**直接比对两个引擎的 URL（不跑抓取、不打网络）。
反向验证：把夹具那行改成 `pass` ⇒ 回归用例精确报红。

## 四、修完之后又暴露两条"靠开发库数据才过"的用例

这正是修复有效的证据 —— 后台抓取**开始真的在测试库里跑了**，于是：

| 用例 | 原来为什么过 | 现在为什么红 |
|---|---|---|
| `test_list_account_stat_snapshots` | 后台抓取写到**开发库**去了 | 后台任务与本用例抢同一张表：手工塞 2 条快照、断言 `== 2`，后台又插一条 ⇒ 3（**竞态**） |
| `test_wordcloud_endpoint_passes_vtuber_words_to_tokenizer` | 同上 | 后台抓取把手工设的昵称**覆盖成真昵称**，`extra_words` 多一个（它期望恰好 `{名字, 企划}`） |

**修法**：把"建账号后自动抓取"做成 `client` 夹具的**默认 no-op**
（本文件里本来就有 `noop_background` 这种显式写法，只是不是默认）。
需要真跑后台的用例显式覆盖它。

顺带的收益：`test_vtuber_api.py` 从 **74s → 21.5s**（不再打真网络），整套 pytest
从 **~190s → ~50s**。⇒ **"测试在悄悄打真网络"这件事，以前是藏在"它恰好没让断言失败"后面的。**

## 五、验证

- `pytest.ini`：三种调用方式（`pytest` / `python -m pytest` / 加 `-p no:cacheprovider`）全绿。
- 隔离夹具：回归用例绿；删掉夹具那行 ⇒ **必红**（精确报"后台会话没被钉到测试库"）。
- 另用 `uv` 造了一套**真 Python 3.12** 环境跑全套：**619 passed / 2 skipped / 0 failed**
  ⇒ `requires-python` 下界没问题（以前从没验证过）。
- 当前仓库：`uv run pytest tests/ -q` ⇒ **622 passed / 0 failed / 约 50s**。

## 六、教训（值得提炼）

1. **"本地绿"推不出"CI 会绿"**，而差别可能只是一条命令的写法（`pytest` vs `python -m pytest`）。
2. **测试里"看起来在跑"的后台任务，可能连的是另一个库**。依赖覆盖（`dependency_overrides`）
   只管路由；**后台任务用的会话是它自己 import 的**，这是两个不同的入口。
3. **一套测试跑得慢，本身就是线索**：187s → 50s 的那 137s 全是真网络调用，
   而那些调用一直在"碰巧没让断言失败"。
4. 为了让 CI 变绿而"放宽断言"是错的：这两条用例的修法都是**去掉不确定性来源**，不是改期望值。

## 七、第四轮（Windows 腿）：中文提示语碰上 cp1252 —— 而它揭出一个**真实用户可见的 bug**

pytest 两边都绿之后，Windows 腿"冻结后端"这步红在编码上：
```
UnicodeEncodeError: 'charmap' codec can't encode characters in position 8-10
  File "scripts/build_backend.py", line 113, in _assert_locked_environment
      print("[build] 环境缺 PyInstaller（在 build 组里），按 uv.lock 补装…")
```
修掉之后（CI 给 UTF-8 + 脚本自己 `reconfigure(errors="replace")`），**冒烟那步又红了** ——
而这次冒烟的自证现场给出了**本批最有价值的发现**：

```
File "backend_main.py", line 89, in _bootstrap_resources
    print(f"[sidecar] 已引导资源: {dst}", flush=True)
UnicodeEncodeError: 'charmap' codec can't encode characters in position 10-14
[PYI-5872:ERROR] Failed to execute script 'backend_main' due to unhandled exception!
```

**这是产品 bug，不是测试问题**：冻结后的后端在 **cp1252** 控制台上、**空数据目录首启**
（复制 `vtubers.csv` 那一句）时**整个进程崩掉**。
- 中文 Windows 是 cp936，能编码「已引导资源」⇒ **中文开发机上永远看不到**；
- 英文 Windows 是 cp1252 ⇒ **第一次启动就是这么崩的**。

Tauri 启动器确实会注入 `PYTHONUTF8=1`/`PYTHONIOENCODING=utf-8`，所以走那条路的用户没事；
但两条理由要求**脚本自立**：① `DEV-LOOP.md` §三/§四 把"直接跑冻结 exe"列为支持的开发期路径；
② **"靠外部环境才不崩"是脆的**，换个启动方式就复发。

修法：`backend_main.py` 顶部（任何输出之前）对 `stdout/stderr` 做
`reconfigure(errors="replace")` —— 中文降级成 `?`，**绝不让一条提示语决定进程成败**
（同 `scripts/ui_probe.py` 的既有做法）。

实测（都强制 `PYTHONIOENCODING=cp1252` 模拟英文 Windows）：
- 源码路径：healthz ok，输出 `[sidecar] ?????: …`；
- **重建冻结 exe** 后同一现场：healthz ok，`err.log` 里**无 UnicodeEncodeError**。

⚠️ 为什么第一版的冒烟步骤抓不到：它失败时只打印 `out.log`，而那是**空的**
（崩溃发生在 stderr）⇒ CI 只报"60s 没就绪"，把真因吞了。
改成打全现场（`HasExited` / exit code / stdout / stderr / **`logs/sidecar.log`** / exe 大小）之后，
一次就定位到了。**"失败时只报结论不报现场"本身就是一种缺陷。**
