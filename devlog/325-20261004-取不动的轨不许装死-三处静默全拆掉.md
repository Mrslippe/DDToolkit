# 325-20261004 取不动的轨不许装死：三处静默全拆掉 + 守卫触发即认输

> 用户复现（`devlog/324` 之后，重启过、`t` 已生效）：「跳转后画面播放一小段卡住，**之后声音依旧**，
> 再一小段之后卡住缓冲；再点进度条其他地方也是相同情况」——现象**换轨了**：现在是 **video** 轨。

## 一、现场

```
16:16:10 段表 918 段 / 915 段（新内核启动，t 已生效）
16:16:13 video 451649646-453654378  status=206   ← 目标段，整段取回
16:16:15 跳转 2822.7s 落地：用时=2.5s 缓冲=2.3s
16:16:18 [media] video 段 565 连取 3 次仍没落地（本轨缓冲停在 0.0–2825.0s）—— 本轨不再重取
```

之后四次跳转一模一样（段 284 / 786 / 344），每次落地缓冲都只有 **0.4–2.3s**。

## 二、把"谁在取数"查干净（这次查得比前几轮都细）

| 疑问 | 实测 |
|---|---|
| 段 565 的 Range 上游给不给？ | **三条镜像全部 206 + 长度精确**（1996174B），init 也对 ⇒ 不是上游 |
| 那三发为什么代理侧没记录？ | 代理**一发都没有** ⇒ 取数在**本地**就抛了 |
| 那几个"几百字节的小请求"（914B/271B/620B/647B）是谁发的？ | 它们从目标段起点开始、**不是整段也不是完整 moof**（该处 moof 是 1904B）⇒ 不是内核按段表取的形状，是别处的读取者；与本次修复无关，先记着 |

⇒ 结论：**内核的取数失败了，而三处"静默返回"把它吞了**：
① `append()` 的 catch 里"代数变了"直接 return；② `AbortError` 且目标已换也直接 return；
③ 真正的原因日志只在"镜像 >1 且还有下一条"时才写 —— **单镜像/镜像用尽时一个字都没有**。

## 三、改了什么

1. **取数失败一律留痕**：`[media] <kind> 段 N 取数失败（<错误>）bytes=…-… 重试=/镜像=/表=Ns`
   （同一轨每秒最多一条，不刷屏）；"结果作废（代数变了/被中止）"也各留一行。
2. **守卫触发 = 如实认输**，不再"本轨不再重取"地停在那里。
   ⚠️ 真机上那一停就是用户看到的"**画面冻住、声音还在放**"（音频轨自己有数据，元素继续走时钟），
   而且**永不自愈**。MSE 给不出这个位置的数据 = 这条路对它不成立 ⇒ `fail` ⇒ 调用方退回渐进式
   （浏览器自己的解复用器能把这一段放出来）。日志同时写明是哪一段的哪段字节。

## 四、判据

- 「单镜像取不到也必须写一行」：假取数对视频轨全抛 `RangeError`，断言日志里有 `取数失败` +
  `bytes=` + 错误原文（改前这条**一个字都没有**）。
- 「守卫触发时必须说一句并**如实认输**」：只冻结 audio 轨 ⇒ 撞守卫后断言日志含 `bytes=`
  且 `onFatal` 被调（老判据是"换目标还能重取"，那建立在"停在原地"之上，已按新口径改写）。
