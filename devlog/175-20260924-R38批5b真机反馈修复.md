## 二、根因

**① 权限作用域（主因）**：`frontend/src-tauri/capabilities/default.json` 里
`"windows": ["main"]` —— 所有 `core:window:*` 权限**只授给主窗口**，小窗一条都没有。
而小窗前端那句 `startDragging()` 包在一个**没被 await 的 async IIFE** 里 ⇒
权限被拒 ⇒ **未处理的 Promise rejection**。

**② 窗口外观没钉住**：`WebviewWindowBuilder` 上的 `decorations / always_on_top /
skip_taskbar` 可能被**延迟应用**，`build()` 返回时窗口还是"带边框的普通窗口" ⇒
就是截图里那个方框。

**③ 一个我自己造的退出死角**：`hide_widget_window` 调的是 `w.close()` —— 那要
`core:window:allow-close`，小窗没有 ⇒ **关不掉**。而 `onCloseRequested` 又只处理
"用户按 Alt+F4"，没兜住"命令式关闭失败"这条路。

## 三、修了什么

| # | 改动 | 为什么 |
|---|---|---|
| 1 | `capabilities/default.json` 作用域 → `"windows": ["*"]`，并补 `allow-hide` / `allow-set-focus` / `allow-get-all-windows` | ①②的主因 |
| 2 | `show_widget_window` 在 `build()` 之后**同步再钉一遍** `set_decorations / set_resizable / set_always_on_top / set_skip_taskbar / set_shadow / set_size` | ②的修法（同步调用一定生效）|
| 3 | `hide_widget_window` 改 `destroy()`（不是 `close()`）+ **广播 `widget:closed`** | ③；销毁是自定义命令，**不走 ACL** |
| 4 | 新增 `destroy_widget_window` 自定义命令（同样不走 ACL） | 给"已经中招的机器"一条确定可达的路 |
| 5 | 小窗 `startDragging()` 补 `catch` + `console.warn` | 未处理 rejection 本身就该修 |
| 6 | 小窗 `onCloseRequested` → `preventDefault` + `destroyWidgetWindow()` | Alt+F4 也走可达路径 |
| 7 | 主窗口听 `widget:closed` → 把 `prefs.widget_enabled` 落成 `off` | 否则窗口没了但偏好还写着 on，下次启动又冒出来 —— 用户观感就是"关不掉" |
| 8 | 设置里切开关后 `resurfaceMainWindow()`（hide + show + focus）**并报告结果** | 权限缺失期间主窗口可能已处于错误状态；失败要说出来 |
| 9 | 探针加 `rootChildren` / `rootText` 判据 | 那条"只有透明背景"就是 **React 渲染抛错**的症状，之前没有判据 |

## 四、⚠️ 如实标注：一条断言**没查到证据**

"小窗的未处理 rejection 会打坏**主窗口**的 IPC 通道" —— 两个 webview 各有各的 IPC，
**这条因果我没有找到证据**。但它解释了用户看到的全部三个症状（关不掉 / 最小化不了 /
托盘退不掉），而且"async IIFE 必须 catch"本身就是对的，所以照修了。

**顺带纠正我自己最初的猜测**：一开始以为 `core:window:default` 不含 `allow-hide`/`allow-show`
—— 查了 crate 里的 `permissions/window/autogenerated/reference.md`，
**它是包含的**（`allow-hide` / `allow-show` / `allow-start-dragging` 都在）。
所以问题在**作用域**，不在权限集合。这条已写进 `widgetWindow.ts` 的注释里，免得下次又猜错。
