# 569-20261020-场次跨度：裁离群 + 统一 UTC

用户："场次时长这个问题不是解决了吗"。查下来**不是同一个问题** —— 之前修的是解析层（SQLite 返回
字符串 → `end_at - start_at` 抛 TypeError 被吞 → 时长 None），这次是**数据层**：跨度本身算得出，
但算出来不代表真直播时长。

## 一、离群时间戳把跨度拉长

`start_at` / `end_at` 取该场**全部事件时间戳的 min / max**。一场约 6 小时的直播里混进了
开播第 3 天、第 5 天的零星弹幕（10-05 的 21 条、10-08 的 2 条），`max` 落到 5 天后 ⇒
时长 7442 分钟。227 场里 **19 场**受影响。

**修法**（`collector._trim_span`）：最大相邻间隔 > 3 小时 **且** 少数一侧 < 5% ⇒ 切掉该侧，重复。
两侧都很大（真实中场休息）不切 —— 宁可少切。stats 新增 `duration_trimmed` 记录裁掉多少。

## 二、顺带挖出一个更严重的：时区口径不一致

回填时发现 `stats` 与 `raw` 差整整 8 小时。核对 DB：

```
stats  start_at = 2026-09-24 11:49:51
db     start_at = 2026-09-24 11:49:51      ← 一致（UTC）
raw 最小时间戳 → 本地 19:50:49（= UTC 11:50:49）
```

⇒ 库与展示层是 **UTC**，而 `aggregate()` 用 `datetime.fromtimestamp()` 取的是**本地时间**。
东八区机器上新采的数据会整体 **+8 小时**。全库比对：**227 场里 76 场偏 +8h** —— 数据是混的。

**修法**：采集侧改用 `datetime.fromtimestamp(ms/1000, tz=timezone.utc)` 写 UTC。

## 三、回填

`scripts/backfill_fan_span.py`（默认 dry-run，`--apply` 写回，逐文件留 `.bak`）：
用 `raw` 的时间戳重算跨度（裁剪 + UTC），只改 `start_at` / `end_at` / `duration_trimmed`。

回填 227 场后与 DB 比对：**222 场一致（< 6 分钟）· 仍偏 ±8h 的 0 场**；余下 5 场差 0.1–1.4 小时，
是"事件实际起止 vs 平台报的开播时间"的正常差，不是错误。

## 四、连带修正

上一轮我说"入场覆盖 <50% 的只有 1 场、门槛先别加" —— 那个数是用**错口径的时长**算的。
按修好的口径在全库重算：**12 / 227 场** 入场事件覆盖不足 50%，`γ_entry` 门槛要加。
