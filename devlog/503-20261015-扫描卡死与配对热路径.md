# 503-20261015 扫描卡死：配对热路径 160 万次线性扫

## 用户报的（带截图）

「为什么扫描录播的时候**一直卡在加载**，并且此时**前端的功能也被阻塞了**」，
外加一句口径：「清除匹配项、扫描录播这两个操作是能一瞬间完成还是要一段时间？
需要时间就显示加载态，防止加载中用户一直去操作」。

## 一、真因：配对里有一处 **O(n³)**

`match_sessions` 的第二步是"把两边都更近的换过来"，每个问题上都调一次：

```python
def _cost_of(pairs, live_id, item):        # ← 线性扫 pairs
    for pid, _conf, cost, pitem in pairs:
        if pid == live_id and pitem.bvid == item.bvid:
            return cost
```

满池实测（942 场 × 927 条候选）：

```
1599896 function calls in 57.201 seconds
  1.6s  match_sessions
 54.2s  _cost_of        ← 94.8%
```

也就是"每问一次代价就扫一遍全表"，而问的次数本身也是平方级。

**为什么现在才炸**：用户刚把 693 条录播清空 ⇒ 匹配池从 249 场涨回 **942 场**
（池子 = 还没配上录播的场次）。同一个函数，池子小的时候 3 秒、满池 71 秒。

**为什么"前端也被阻塞"**：`vod-scan` 是 `async def`，配对是**纯 CPU 且直接在事件循环里跑**
⇒ 那 71 秒里后端**一个请求都答不了**，整个界面看起来死掉。这不是前端的问题。

## 二、两刀

### ① 取代价不再线性扫（`app/domain/vod_autofill.py`）

`pairs` 在交换之前**已经排好序**，所以"第一个命中的那条"就是最优的那条 ⇒
排序后建一张 `{(live_id, bvid): cost}` 表（`setdefault` = 保留第一次命中，与旧语义逐字一致），
查询从 O(n) 变 O(1)。顺带把 `to_beijing(row["start_at"])` 提到内层循环外
（原来在 `items × pool` 里现算，满池 **87 万次**）。

### ② 配对挪出事件循环（`app/services/vod_scan.py`）

```python
matched = await asyncio.to_thread(va.match_sessions, remaining, items, ...)
```

`match_sessions` 只吃 `rows`/`items` 两个纯数据、不碰数据库，所以丢线程是安全的。
**这一条比①更要紧**：以后再慢也只是"这次请求慢"，不会把整个后端冻住。

## 三、等价性（性能修复最容易悄悄改结果）

`_probe/vod_match_ab.py`：把**旧实现**（线性 `_cost_of` 那一版）原样抄进去，与新实现跑同一份
真库数据、逐条比对签名（`live_id / bvid / 置信度 / 时间差 / alternates`）：

```
场次池=942 候选=927
旧实现 71.4s / 新实现 0.90s（快 80×）
配对条数：旧 882 / 新 882
逐条签名一致: OK
```

端到端（两个号 + 真上游）：**71.2s → 2.19s**。`merged()` 本身 110ms（不动它）。

## 四、加载态（用户第二问）

| 操作 | 实测 | 界面 |
|---|---|---|
| 扫描录播 | **2–3 秒**（打上游取整个系列 + 配对） | 概要条上 `正在扫描…（已 Ns）` + 一句"要打上游取整个系列，几秒钟；可以点取消关掉" —— 光转圈分不清"在动"与"卡死"，**秒数**让用户自己判断 |
| 清空匹配 | **一瞬**（纯数据库、一个上游请求都不发） | 确认钮变 `正在清空…`、两枚钮都禁用、Esc 关不掉（危险动作不许连点两下） |

顺带补：**某个号没扫到要在界面上说出来**。真机实测优先级最高的那个号
(`94009831`) 一直是 `ok=false / 没找到可扫的来源`，此前只进响应不进界面
⇒ 用户只会看到"怎么才配上这么点"。现在概要条上直接写「号 94009831 没扫到：…」。

## 六、这一轮的教训

- **"某个功能突然变慢"先去量池子，别先看代码**：同一份代码在池子 249 时 3 秒、942 时 71 秒。
  录播清空把池子放大 3.8 倍，而代价是**平方**级的。
- **同步的 CPU 活儿别放在 `async def` 里**：它不会报错、不会超时，只会让整个后端"看起来死了"，
  而排查的人多半会去怀疑前端。
- **性能修复必须做 A/B 等价对照**：把旧实现抄进探针跑同一份数据、逐条比签名 ——
  "条数一样"证明不了"结果一样"。
