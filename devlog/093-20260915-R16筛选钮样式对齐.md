## 一、先量现状：两张截图能说明"像不像"，说明不了"差在哪"

新建探针 `ui_probe --filter-pill`：把两枚浮片的样式逐项量出来对账。
第一次运行（改之前）的输出就是这张差异表：

| 字段 | 侧栏（参照） | list 视图（改前） |
|---|---|---|
| 尺寸 w×h | 89×**25** | 68×**30** |
| 字号 / 行高 | 13px / 13px | 12.5px / 18.75px |
| 内距 | `0 8px` | `0 12px` |
| caret 定位 | **absolute**（右上 3px，不占流） | static（在流内，gap 4px） |
| caret 距文字 / 距右缘 | 21.9 / 3 | 4 / 16.2 |
| caret 垂直偏移 | −6.2（偏上） | 0（居中） |
| **文字中心偏移** | **0** | **−5.3** |
| 文字两侧留白 | [31.5, 31.5] | [16.2, 26.8] |

**关键发现**：参照那枚的文字偏移是 **0**（真的是几何中心），而 list 那枚偏 **−5.3px** ——
这正是用户从 R5 到 R15 反复说"文字没居中"的**根因**：caret 只要留在流内，就必然挤占文字的位置。
R15 当时把 caret 留在流里、让"文字+箭头"这一组居中，文字本身仍偏 5.3px；侧栏那枚的做法更彻底 ——
**caret 出流（绝对定位到右上角）+ 浮片比文字宽出一段**，于是文字就是中心，caret 落进右侧留白里。

（顺带纠正 R5 的一次错误解法：那时给 list 那枚加了**非对称内距** `0 16px 0 10px`
"给 caret 让位"，而非对称内距本身就会把文字推偏 —— 正确解法是对称内距 + 足够宽度。）

## 二、改法：配方对齐侧栏，尺寸留在本行

`posts.css` 里 `.pfilter-btn` 改成与 `.list-filter-btn` 同一套**配方**：

```css
.pfilter-btn { min-width: 68px; padding: 0 8px; font-size: 13px; line-height: 1; }
.pfilter-btn .pf-label { padding: 0 11px; white-space: nowrap; }   /* 见下 */
```

并删掉 R15 加的 `.pfilter-btn .pill-caret { position: static }` 覆盖 —— 共用 `.pill-caret`
的绝对定位（`top/right: 3px`）。

⚠️ **尺寸保持原样**（用户 2026-09-15 看到第一版后复述：「宽高还是原本的宽高，保持同一行中元素的和谐」）：
第一版我为了"逐项一致"把 list 那枚也改成了 89×25（侧栏的尺寸），代价是它与**同一行**的搜索框
（30px）不再等高、工具行也右移 21px。用户的裁决很清楚：**配方跟随、尺寸各行其是** ——
高 30（`size="md"`，与同行搜索框齐平）、宽 `min-width: 68px`（按内容长）。
于是探针的契约也随之分两桶：

| 桶 | 字段 | 判据 |
|---|---|---|
| **STYLE**（样式跟随） | 字号 / 行高 / 内距 / gap / 圆角 / 颜色 / 底 / 斜切 / caret 定位方式·`inset`·尺寸·**距右缘** / **文字中心偏移** | **必须逐项相等**（实测全等，文字偏移都是 0） |
| **SIZE**（各行其是） | `w` / `h` / `minWidth` / `caretGapToText` / `caretCenterOffset` / `textInset` | 只如实列出，不判失败；但另有两条硬约束：**高必须 30**（与本行搜索框齐平）、**文字两侧留白必须对称** |

最终实测（改后）：

```
STYLE：fontSize 13px · lineHeight 13px · padding 0 8px · gap 4px · radius 0
       color/bg 相同 · skew 相同 · caretPosition absolute · caretInset 3px/3px
       caretSize 6.6×6.6 · caretFromRight 3 · textCenterOffset 0
SIZE ：w 89 vs 68 · h 25 vs 30 · minWidth 0 vs 68 · caretGapToText 21.9 vs 11.4
       caretCenterOffset −6.2 vs −8.7 · textInset [31.5,31.5] vs [21,21]（两侧对称 ✓）
```

## 三、超长文案那一测，逼出了 `.pf-label`

改完第一版就绿了，但探针里那条"造一个超长文案"的边界测**红了**，而且红得有道理：

```
超长文案：文案='筛选 · 12 项' 宽=89 文字中心偏移=0 文字两侧=[10.2, 10.2] caret 距文字=0.6
```

caret 占右缘 `3px` 起、宽 `6.63px`；文字两侧各剩 10.2px 时，caret 几乎贴到字上（0.6px）。
根因：**内距只有 8px，比 caret 的落脚区还窄** —— 短文案靠 `min-width` 富余量遮住了这个问题，
长文案才暴露。参照那枚之所以没事，只是因为它的文案短（「默认」）且宽度是写死的 89。

修法（不是放水改判据，而是**从构造上消掉**）：文案外套一层 `.pf-label`，给**左右各 11px 对称留白**：

- 对称 ⇒ 文字仍在浮片几何中心（改完三态实测偏移都是 0）；
- 这层留白同时把 caret 的落脚区让出来 ⇒ 长文案下 caret 与文字恒留 **~9.4px**（实测）；
- 短文案仍由 `min-width: 89px` 兜住 ⇒ **渲染结果与参照那枚逐项相同**（探针对账仍全绿）。

一个真实文案够不到的边界，就这样变成了构造上的保证。

## 六、这一批的经验（写给下次"照着截图改样式"）

1. **截图能说明"像不像"，说明不了"差在哪"**：先把可疑的样式字段全部量化，
   差异表一出来，"该改哪几个字段"就不用猜了（这次一量就发现真凶是 caret 在流内挤偏文字 5.3px）。
2. **"样式跟随"要拆成"配方"与"尺寸"**：配方（字号/内距/颜色/caret 处理/居中）该一致；
   尺寸往往由**所在行**决定（这行是 30 高、那行是 25 高）。混为一谈就会为了"逐项一致"
   去破坏行内和谐 —— 用户当场纠正的就是这一点。断言也该照这个分桶写。
3. **判据要能造边界**：合成的超长文案（「筛选 · 12 项」）逼出了"caret 压字 0.6px"这个
   真实文案永远碰不到、但构造上确实存在的缺陷；修法是消掉它（对称留白），不是放宽阈值。
4. **先怀疑判据**：第一版我断言"文案变长后宽度必须变大"，被「筛选 · 2」证伪 ——
   89px 本来就装得下，不需要变宽。改判据之前先问"这条判据真的在描述我想要的性质吗"。
