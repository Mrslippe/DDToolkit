# 116-20260916-R23d更新错误的分类与代理兜底收敛

> 用户截图（2026-09-16，代理开着仍失败）：
> `检查更新失败：Could not fetch a valid release JSON from the remote；改用本地代理
> http://127.0.0.1:7897 后仍失败：Could not fetch a valid release JSON from the remote`

## 一、这条报错**不是网络问题**

`Could not fetch a valid release JSON from the remote` 是更新器的"**远端内容不对**"错误 ——
**GitHub 上还没有任何 Release**（我们商定延后建 Release），所以
`releases/latest/download/latest.json` 是 **404**。换个代理也还是 404。

代理兜底其实**已经跑通了**（报文里那句"改用本地代理 … 后仍失败"就是它留下的），
问题在于两件事被我做糙了：

1. **没分类**：把"远端没有内容"当成"连不上" ⇒ 白试一次代理；
2. **文案误导**：写出"改用代理后仍失败"，把用户引去修一个根本没坏的东西
   （他的代理好好的，是**我们还没发版**）。

## 二、改法

`utils/shellBridge.ts` 新增**纯函数** `classifyUpdateError(raw)` 与 `UpdateCheckError`（带类别）：

| 类别 | 判据（关键字） | 行为 | 界面提示 |
|---|---|---|---|
| `remote` | `valid release json` / `404` / `not found` | **不试代理**（换了也没用） | "通常是还没发布过版本，或发布资产里缺 latest.json（等新版本发布后再试；也可以直接去发布页看看）" |
| `network` | `connect` / `dns` / `timed out` / `tls` / `certificate` / `sending request` … | 探本地代理 → 设进本进程 → **重试一次** | "可以检查代理是否正常，或直接去发布页下载" |
| `other` | 其余（例如签名校验失败） | 原样抛出，不试代理、不编造原因 | 原样显示 |

代理重试后若拿到的是**内容类**错误，也归到 `remote` 如实说明 —— **别赖代理**。

## 三、用例（+4，`vitest` 260 passed）

`utils/shellBridge.test.ts`：远端 404 → `remote` 且文案含"还没发布过版本" ·
四种网络报错 → `network` · 签名失败 → `other` 且**原样保留原文** ·
`UpdateCheckError` 带得住类别（界面据此换提示语）。

## 四、门禁

`tsc --noEmit` 0 错 · `eslint --max-warnings 0` 0 错 · `vitest` **260 passed**（256 → +4）。

## 五、结论与下一步

**"检查更新失败"是当前版本的预期行为** —— 远端还没有 Release。它要等到**建 Release 之后**
才能真正端到端验通（`latest.json` + `*.nsis.zip` 上传到 v1.0.2 的 Release）。
在那之前，关于页会如实显示 `remote` 类失败并给出"等发布后再试 / 去发布页"的提示。

下一步仍是**定版收口**：挪 tag → 补 `docs/releases/v1.0.2.md` 的 R22/R23 两节 → 重建产物
（含 `*.nsis.zip` + `latest.json`）→ 用户提供 token 建 Release → 再验一次更新检查（这次应当
报"已是最新版本"）。
