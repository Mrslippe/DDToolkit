## 二、两个"诊断本身的毛病"（为什么只捞到一行）

1. **窗口太短（8 秒）+ 只有平均值**：用户说的是"低帧率播**一段**"，这段可能超过 8 秒；
   而 8 秒的**平均**会把 3 秒的低谷抹平（18fps 低谷 + 5 秒正常 ⇒ 平均看着还行）。
2. **窗口被顶掉或组件卸载就整条丢弃**：`startProbe` 每次 seek 都会 `cancel()` 上一个窗口，
   关闭抽屉（卸载）也是丢弃 ⇒ **用户"复现几次"里那几次恰好什么都没留下**。
   真机 24 条代理行只配了 1 条前端行，就是这么来的。

另外 `最低缓冲=-1.0s` 是我自己的读数毛刺（`buffered.end(i) - currentTime` 在边界上取到负数），
不该当成"负缓冲"报上去。

## 三、这一版诊断改了什么（`playbackProbe.ts`）

| 改动 | 为什么 |
|---|---|
| 窗口 **8s → 30s**，**每秒采一次样** | 低谷再也不会被平均抹平；能看到"第几秒开始变好" |
| **卡帧秒数 vs 空转秒数** | `currentTime` 不前进 = **数据没到**；`currentTime` 在走却没帧 = **解码/呈现问题** —— 一行里直接分开这两种病因 |
| **前 3 秒 vs 后段**帧率 | 用户描述就是"开头差、之后正常"，这两个数一比就出来 |
| 有低谷时**附一行每秒曲线** | `1s:4fps/0.3 2s:4fps/0.3* …`（`*` = 那一秒 currentTime 没前进），不用再猜是哪一秒 |
| `finish()`（卸载/结束时**先报再停**）与 `cancel()`（被顶掉才丢弃）分开 | 关抽屉那几次也要留证据 —— 这正是上一版丢掉的那批 |
| 负数缓冲按"量不到"处理 | 除掉 `-1.0s` 这种假数字 |

## 四、下一步怎么用

再复现一次（**跳转 → 等它自己恢复正常 → 再关抽屉**），`logs/app.log` 里就会出现：
```
前端 [video] seek→162.1s 窗口=30.0s 起播=4.2s 饿住=6次 最低缓冲=0.2s 总体=18.4fps
            前3秒=9.1 后段=29.8 卡帧=3s 空转=0s 丢帧=0/552 末缓冲=6.0s
前端 [video] 曲线(seek) 1s:8fps/0.4 2s:9fps/0.3* 3s:11fps/0.6 …
```
判读（三种组合互斥，直接指向不同的修法）：
- `卡帧>0` 且 `最低缓冲` 很低 ⇒ **数据没到** ⇒ 看同一时刻代理那几行：若代理也慢 ⇒ CDN；
  代理漂亮 ⇒ 浏览器取数策略 ⇒ **MSE 收益明确（进 S1）**；
- `空转>0`（缓冲够却没帧）⇒ **解码/呈现** ⇒ 与 CDN 无关，得看是 codec 还是合成
  （那时该试 HEVC 档、或定位抽屉里的 `backdrop-filter` 等合成开销）；
- `前3秒` 明显低于 `后段` 而 `卡帧/空转` 都为 0 ⇒ 是**启动阶段的调度**（seek 后那一两秒），
  量级小、可以不治。
