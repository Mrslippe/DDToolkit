# 276-20261002 开播边沿误报"轮播"、以及 dev 壳跑错解释器害小红书全 406

> 用户报障（2026-10-02，附顶栏截图）：
> ① 「顶部状态胶囊提示的是 菜菜子开播了，但下拉面板显示恬豆发芽了开播，而实际上这两者都没有开播」
> ② 「小红书账号抓取出错了，我配置了 cookie 后添加账号，但是账号信息也没有抓取到，动态也没有」

两件事表面上毫不相干，根因都是**"把一个非布尔量当布尔用"**：一个是 `live_status`（三态），
一个是"解释器"（PATH 里的 `python` ≠ 装了依赖的那个）。

## 一、假开播：`live_status=2`（轮播）被当成了"开播"

**现场取证**（开发库 `E:\test\DDToolkit-data`）：

| 账号 | `live_status` | 说明 |
|---|---|---|
| 泽音 / 明前奶绿 / 塔菲 / 弥月 | **1** | 真在播（标题也是当场的） |
| **菜菜子Nanako / 恬豆发芽了** | **2** | 用户看到的两位"没开播"的 |
| 七海 / 普通小栗 / 四时小路 | 0 | 离线 |

B 站 `get_status_info_by_uids` 的 `live_status` 是**三态**：0 未开播 / 1 直播中 / **2 轮播**
（房间在循环放录像）。而 `scheduler.live_sweep_core` 里写的是：

```python
started = bool(acc.live_status) and not prev_status     # ← 2 也是真值 ⇒ 0→2 被判成"开播"
```

自观测快照的序列直接坐实（`account_stat_snapshots`，`source='self'`）：

```
acc=20（恬豆）  0 → 2          ← 10-01 14:21 与 10-02 12:45 两次，各推一条「开播了」
acc=16（明前奶绿）1 → 2 → 1     ← 下播转轮播、隔天再开播
acc=15（七海）  1 → 0          ← 正常上下播
```

**同一个坑还有第二处**：自观测场次推导（`AccountStatSnapshotRepo.live_sessions`）原先只认
`status == 0` 收场 ⇒ 明前奶绿那串 `1 → 2 → 1` 被并成**一场**、时长跨天（日历里"15 小时"那种
数字就是这么来的）。

**至于"胶囊说菜菜子、面板说恬豆"**：两者读的是**同一份**通知列表（胶囊显示主条目、面板列全部），
胶囊的 `title` 属性还是上一次渲染时写的 —— 鼠标停在那儿看到的是**陈旧的 tooltip**，
不是第二个数据源。两个账号各有一条假的「开播了」，谁当主条目取决于排序与 TTL。

### 改法

- 新增 `app/core/live_status.py`：**三态的单一真源**（`LIVE_STATUS_OFF/LIVE/LIVE_ROUND` + `is_live()`）；
- `scheduler`：开播边沿改 `is_live(now) and not is_live(prev)`（`0→2` 不发、`2→1` 发 —— 后者才是真开播）；
- `AccountStatSnapshotRepo.live_sessions`：**只有 1 算在播，其余都收场**（轮播 = 人已经下播）；
- 前端 `utils/accountHistory.ts::liveStatusLabel`：`2 → 「轮播中」`（原先显示"离线"，等于把
  "房间里有东西在放"这件事抹掉）。

```
      tests/test_live_sessions.py::test_self_sessions_split_on_round_robin  PASSED
```

## 二、小红书 406：dev 壳跑的是**系统 Python**，而 `xhshow` 只装在 `.venv` 里

**现场取证**：

| 证据 | 值 |
|---|---|
| 运行中的后端进程 | `"python" backend_main.py`（PID 31984） |
| 它的解释器 | `C:\Users\zx\AppData\Local\Programs\Python\Python314\python.exe`（**系统** Python） |
| 该解释器有 `xhshow` 吗 | **没有**（`ModuleNotFoundError: No module named 'xhshow'`） |
| 应用日志 | `user_posted` / `user/otherinfo` 全是 **HTTP 406 Not Acceptable**（连着 7 次） |
| 用 `.venv` 重发**同一个请求** | **HTTP 200** + 真实笔记数据（说明 cookie、签名器、账号都没问题） |

即：`XhsSigner` 在应用里拿不到 `xhshow` ⇒ 请求**没签名就发出去** ⇒ 上游一律 406。
而这条失败路径原先**是静默的**（`except SignerUnavailable: return None`，没有日志、没有
`last_error`），所以用户只看到"配了 cookie 却什么都抓不到"。

### 改法

- **壳的 dev 分支优先用项目自带的 `.venv`**（`resolve_dev_python()`：`<root>/.venv/Scripts/python.exe`，
  没有才回退 `python`）+ 一条 cargo 测试钉住它。这治的是**一整类**问题：任何只装在 venv 里的
  可选依赖，在应用里都会静默缺失；
- 小红书侧**失败要响亮**：`SignerUnavailable` → `logger.warning` + `last_error = {kind:
  'signer_unavailable'}`（结构化，能进诊断），不再静默 `None`；
- `README.md` 的「本地开发」补一条：桌面开发先把依赖装进 `.venv`（`uv sync`）。

## 四、留给下一次的两条口径

1. **平台状态字段先去查它到底几个值**：`live_status` 这种"看起来像布尔"的字段，B 站给了 0/1/2；
   同类还有微博、小红书的 `live_state`。判"是不是在播"一律走 `app/core/live_status.py`。
2. **"跑在哪个解释器上"要能一眼看到**：dev 壳启动时已打印解释器全路径
   （`[ddtoolkit] dev 模式：<python> backend_main.py`）—— 排查"某个可选依赖在应用里没有效果"时，
   先看这一行与进程的 `ExecutablePath`，别一头扎进上游响应的分类里。
