# 339-20261005 顶栏通知现状清点：四种呈现面、五种时长、两套渠道

> 用户：「下一个大需求是改造一下顶栏状态胶囊的消息通知逻辑，**第一步先把当前的所有消息通知
> 都列出来**，并展示出它们会以什么方式呈现和持续时长多长」。本文记这一步的产出与查证过程。

## 一、产出：`docs/design/notices/topbar-notice-inventory.md`（清点，不是方案）

按"**来源 → 呈现面 → 时长 → 优先级 → 动作**"逐条列全，四处真源交叉核对
（`services/notices.py` · `notificationHub.ts` · `noticeStream.ts` · `StatusIsland.tsx`）
外加全仓 `toast.` 调用点。清点结论的骨架：

| 呈现面 | 说什么 | 时长 |
|---|---|---|
| 胶囊 `.si-island` | 只显示优先级最高的**一条**（点色 + 类型字形 + 文案 + 活数据 + 计数徽章） | 跟条目 |
| 面板 `.si-panel` | 全部 live 条目 + 来源标注 + 动作按钮 | 跟条目 |
| toast（sonner） | 操作结果/失败原因（**不进面板**） | 4s，同屏 3 条 |
| 完成报告对话框 | 面板里点「查看详情」才开 | 只有「知道了」 |

时长共 **五种口径**：4s（瞬时消息，前后端各一份同值）/ 8s（推送来的受理进度兜底）/
2 分钟（开播）/ 冷却剩余秒数（风控）/ 常驻（登录失效、完成报告）。

## 二、清点过程中查实的四件事（都不是猜的）

1. **`notice.alert` 与 `notice.report` 两个消息类型已定义但生产代码从不发布**
   （只在 `tests/test_messages.py` 里被 publish）⇒ 告警/报告走的是**轮询那份**，
   不是推送。这条以前没在任何文档里写明，容易让人以为"告警也会实时推"。
2. **同一个 id 两条来源**：开播（`live-<account_id>`）既进后端环形缓冲、也走 SSE 推一份
   ⇒ `mergeNotices` 按 id 去重（本地优先）。它不是"两类条目"。
3. **toast 是 56 处调用 / 13 个文件**（另有 2 处只是注释提到它）—— 与通知面板**完全没有交集**，
   且 `PILL_MS = sonner 默认时长 = 4000`：两套渠道今天**恰好同值**，但一个是常量、一个是库默认值。
4. **"成功走胶囊 / 失败走 toast"只在 `utils/pill.ts` 的文件头注释里**：调用点并未统一
   （`useVtuberActions` 的"已开始/完成"混用两套；设置窗口保存是 **toast + 胶囊双发**）。

## 三、记下的六个现状问题（改造的输入，本文不给方案）

三套渠道并存 · 成功/失败口径只在注释里 · 时长五种且 **4s 短于空闲轮询 10s** ·
胶囊同时承担"状态"与"通知"两种语义 · 面板里"能看到"与"能操作"不成比例
（只有「去登录」「查看详情」两个动作，`open-limits` 至今未接线）·
`expiresAt` 用绝对毫秒时间戳（靠"每条轮询都带服务端 `now`"兜着）。
