## 一、这一批改了什么（一句话）

**让开量从"每个视图自己写一处"收归 `.view-body::before` 一条占位带；
页面标题从"占一行"降级为"与工具条同栏的占位物"。**

| — | R45-B/D（改前） | R45-E（改后） |
|---|---|---|
| 让开量写在哪 | **两处**：`.page-title` 的 `padding-top`（list/archive）+ `.hero` 的 `padding-top`（cards） | **一处**：`.view-body::before` 的 `height` |
| 页面标题 | `flex:none`，**占一行**（`92 + 21 + 8 = 121px`） | `position:absolute`，**与工具条同栏**，不占流 |
| 让开量值 | `--toolbar-gap: 40px` | **四个量** `--toolbar-gap-{cards,list,archive,profile}`（R45-E2，各 50px） |
| profile | **没有**让开量（工具条会盖住首行卡片） | 同一处，四视图**首块内容同一条线** |

### 为什么"两处"是错的（不是"不好看"，是结构问题）

1. **profile 视图根本没有** —— 三个视图的首块内容不在同一条线上，切换视图时内容会跳。
2. 更根本的：`.hero` 的 `padding-top` **在滚动容器内部** ⇒ **滚下去就没了**，
   首块内容随即贴到工具条下面。占位条在滚动容器**之外** ⇒ 永远让开。

### 为什么"标题占一行"是错的

用户第 ③ 句说得很清楚：标题是**占位物**，占的是「工具条隐藏后顶上那条空栏」。
那一栏只有 52px 高，占位物应当**就在那一栏里**，而不是自己再占一行把内容推下去 121px。
R45-B/D 那版把"让开"这件事交给了标题，于是标题既是内容又是 chrome —— 两件事混在一起，
用户一看就说"占位"。

> **这条元教训**：R45-D 的判据（「标题文本顶 − 覆盖带 ≥ gap」）在 R45-E 之后**恒红**
> （标题文本顶 ≈14，永远到不了 52+51）。**判据恒红和恒绿一样是废的** ——
> 它是"被测量的东西变了"的信号。这次直接换了被测量（见 §三）。

## 二、51px 是怎么来的

R45-D 量的是**两张参考图**（那里没有"标题占位"这一层），得 **37px** ⇒ 取 40。
R45-E 量的是**用户自己拼的合成图**（他把想要的顶部版式拼出来给我对齐），
那里工具条下缘 y=50 → 账号行上缘 y=102 ⇒ **52px**，取 **51**。

两次都以"用户给的图"为准；后一张更具体、且是**按最终意图**拼的 ⇒ 以后者为准。
⚠️ 不按"条高的倍数"取：参考图的条只有 30px 高，我们的是 46px（4 枚 34px 按钮），
套 1.23× 会得 57px、偏大 —— **留白的视觉作用是绝对量**，不随条高变。

⚠️ `--toolbar-gap` 同时决定了"账号行会不会被工具条盖住"：50px 净空远大于 0，
所以 `.actions-extra` 展开后**不可能被遮** —— 用户第 ③ 句要的正是这条。

**但我差一点就把它当成"我的让开量改动挤到了弹窗"** —— 实际根因是**弹窗的

| 元素 | 2 个账号 | 8 个账号 |
|---|---|---|
| `.header-actions`（账号切换器行） | 1 行 **30px** | **2 行 68px**（`flex-wrap`） |
| `.type-chips-row`（筛选行，窄档） | 1 行 25px | **2 行 66px** |

实测：弹窗顶落在面板内 **264px**，而我把它拆成逐项相加的公式只减了 115px
⇒ 上限给到 349px ⇒ **弹窗底部越出面板 25px 被裁**。

> **关键判断**：我先把改动 `git stash` 掉、在**改前的代码**上跑同一档 ——
> 改前是绿的。这**没有**证明"改前就是对的"，它证明的是**这个失效点是被我的
> `gap 40→51`（+11px）推过去的**。也就是说：**常数早就贴着边界了，只是差一点点没越界。**
> 这正是"最坏情况常数"的典型形态 —— 它不会报错，只会**在某天悄悄越界**。

⇒ 修：`max-height` 改成**组件实测**「触发器下缘 → 面板下缘」后写内联值
（`ResizeObserver` + `resize` 挂上），样式表里只留一条保守兜底。
两段距离（`--pop-gap` / `--pop-breath`）定义成 CSS 自定义属性，TS 侧读，**不各写一份**。

### 4.2 ⚠️ 还有两处红是**我自己的尺子错了**

新写的 `contentTopInPanel` 读到 **109**，设计值 **103**，差 6px。
我顺着"产品哪里多了 6px"查了三轮，**全错** —— 真因是这把新尺子自己：

```js
const panelTop = barR.top - ttop    // ❌ 用工具条反推面板原点
```

工具条**隐藏态**带 `transform: translateY(-6px)`（显隐动画的 rest 态）⇒ 它的 rect
比布局位置高 6px ⇒ 面板原点算成 34（真值 40）⇒ **所有"面板内坐标"系统性多 6px**。
同一轮里还踩到第二处：`cards` 帧的 `.view-body` 读到 `matrix(1,0,0,1,0,8)`
（`scene-in` 的 from 帧 `translateY(8px)` 在虚拟时间下**没推进**）⇒ 那一帧多 8px。

⇒ 修：面板原点**直接读 `.posts-panel` 自己的 rect**（不再从别人身上推，也甩掉了
`--toolbar-top` 那个耦合）；量几何前杀掉 `.view-body` 的动画（与杀 `.view-body`
过渡同一招）。**两条都写进了 `DEV-LOOP.md` §6.6。**

> **元教训**：探针字段**本身也是代码，也会错**，而它错了的时候症状是"产品看起来错了"。
> 新尺子上线前先量一个**答案已知**的对象对一次 —— 这里只要先看一眼视口值
> （内容 143 − 面板 40 = 103）就对上了，根本不用查产品。

## 六、R45-E2：让开量拆成**四个量**（用户追加）

用户看完成果后追加一句：**「四个视图不要共用一个间距 `--toolbar-gap`，分别设计四个量」**。

### 6.1 为什么共用一个数是错的（不只是"不够灵活"）

四个视图的**首块内容不是一类东西**：

| 视图 | 首块内容 | 左侧有没有标题占位 |
|---|---|---|
| cards | hero 头像 | **没有** |
| list | 账号切换器行 | 有 |
| archive | 牌堆卡片 | 有 |
| profile | 画布首行卡片 | **没有** |

所以"该不该同距、差多少"本来就是**四个独立的版式决定**。R45-E 共用一个值，
唯一的原因是当时**只量到了 list 那一档**（用户只给了 list 的合成图）——
那是"数据不足"的妥协，被当成了设计。

### 6.2 落法：四个量 + 一个解析点

```css
/* tokens.css（真源，四个可独立调的旋钮） */
--toolbar-gap-cards: 50px;  --toolbar-gap-list: 50px;
--toolbar-gap-archive: 50px;  --toolbar-gap-profile: 50px;

/* posts.css：解析成本元素上的一个名字 */
.view-body { --toolbar-gap: var(--toolbar-gap-list); }           /* 兜底 = 唯一量过的那档 */
.view-body[data-view='cards']   { --toolbar-gap: var(--toolbar-gap-cards); }
.view-body[data-view='archive'] { --toolbar-gap: var(--toolbar-gap-archive); }
.view-body[data-view='profile'] { --toolbar-gap: var(--toolbar-gap-profile); }
```

**消费方（`::before`、`.post-filter-pop` 的兜底）一个字都不用改** —— 它们仍只认
`.view-body` 上那个 `--toolbar-gap`。`PostsPage` 给 `.view-body` 挂 `data-view`。
⇒ 调间距 = 改 `tokens.css` 一行；加视图 = 补 `posts.css` 一行。

四个值**当前都取 50**（用户实测值），所以解耦本身**不改变任何视觉**。

### 6.3 ⚠️ 但"映射"引入了一类新的假绿，必须补判据

`data-view` → 四个量 的映射**写错了不会自己响**：某个视图用了别人的间距时，
"留白 ≥ 它自己那个值"这条判据**只会与错的那个值自洽**。
⇒ 补两条**接线**判据（`_assert_glow` ⑤b）：

1. `.view-body` 上**解析后**的 `toolbarGap` == `:root` 上该视图的 `--toolbar-gap-<view>`；
2. `.view-body::before` 的**实高** == `覆盖带 + 该视图的量`。
   （这条独立于矩形测量 —— 它直接量占位条用了哪个数。）

按 §6.4 的纪律**反向验证**（两条证据一次拿到）：

| 故意做的破坏 | 期望 | 实测 |
|---|---|---|
| `--toolbar-gap-cards` 20px（映射不动） | **只有 cards** 的内容顶变 72（52+20） | ✅ 72 / 留白 20；list·archive·profile 不动 —— **证明四个量真的独立**（改前是四档一起动） |
| 把 `[data-view='archive']` 故意指向 `--toolbar-gap-profile` | 接线判据红 | ✅ **红 2 条**（"解析到 50 ≠ 设计值 30" + "让开带实高 102 ≠ 52+30=82"） |
| 同一轮里看 `archive` 的**留白**判据 | 应当**是绿的** | ✅ 绿（102−52=50 ≥ 30−1）—— **正是"自洽的假绿"的实证**，也是必须补接线判据的理由 |

### 6.4 另一个发现：用户**自己改了值**

改这一批时发现 `tokens.css` 里 `--toolbar-gap` 已被改成 **50px**（我做的是 51）。
git diff 确认是用户手改的。⇒ 记两条：

1. **用户会直接改令牌** —— 所以"用户能自助的那一类"必须真的是**一处数字**，
   且改动不会有第二处要同步（本批的 50→ 四个 50 就是照他改后的值起的）。
2. **动共享令牌前先 `git status`**：差一点就用我的 51 覆盖掉他的 50。

## 七、R45-E3：用户自改后的三处收尾（2026-09-24）

用户自己动了三个数（字号 16.5→20、`--toolbar-gap-{list,archive,profile}` → 8/0/8、
标题文案写死成「帖子列表」/「数据卡片」），随后问：
**「为啥 `--toolbar-gap-archive = 0` 了图片中红框框出的位置还是有空隙」**。

### 7.1 红框 = **两项之和**，不是一项

```
面板内：y=52  工具条覆盖带下缘（--toolbar-band）
        ↓    这一段 = --toolbar-gap-archive（用户设 0 ⇒ 无）
        y=52  .view-body::before 的底 = 数据视图内容起点
        ↓    这一段 = .data-deck 的上留白（原 20px）★ 红框里剩下的就是它
        y=72  卡片（.deck-frame）真正开始
```

`.data-deck` 是 `overflow:hidden`、**裁在 padding 盒外缘** ⇒ 卡片上缘阴影必须有余量，
那是**技术需要**；而"红框里那块空白"是**版式决定**。两者叠在同一处，所以单看
`--toolbar-gap-archive` 永远解释不了红框 —— 这正是用户被绊住的地方。

⇒ 落法：把那个数**命名**（`--deck-shadow-room: 8px`）并在注释里写明两项之和，
取值 20 → **8**：`--pill-shadow: 0 2px 6px` 的上溢量是 `6−2 = 4px`，8 留 4px 余。
并补一条判据：**`.data-deck` 的上留白不得 < 4px**（低于它卡片上缘阴影被切）。

> **元教训**：把两个职责不同的留白**叠在同一个 padding 上**，必然制造
> "我改了 A 为什么 B 没动"的困惑。要么合并成一个有名字的量，要么写清是两项之和。

### 7.2 两个用户自改留下的真问题

| 现象 | 根因 | 修法 |
|---|---|---|
| 标题看起来比工具条低 3px | 字号 16.5→20 时，居中算式里那个写死的 `21.45px` 只被改成了 `20.00px`，而**行盒高 = 20 × 1.3 = 26** | 写死数换成 **`1.3em`** —— `em` 按元素自己的 `font-size` 解析，**永远等于 `font-size × line-height`**，以后改字号这行不用动 |
| `tsc` 报 `deckIdx` 未使用 | 标题写死后，`DataDeck` 回抛的索引没人读了 | 删掉那个 state 与 `onIndexChange` 接线；**组件上的 `onIndexChange` 能力保留**（以后想让标题跟卡片走再接回） |

### 7.3 删掉一条**必红的假判据**

探针原有一条「archive 的**导航标题 == 卡片内渲染的标题**」（R45-B 立的"两份真源对账"，
当时标题是 `DECK_LABELS[deckIdx]`，与卡片 JSX 里那两串确实是两份）。
用户把标题改成写死的「数据卡片」之后，**"两者必须相等"这个前提消失了** ——
导航标签与卡片标题变成了**两件事**。
⇒ 判据删掉。留着它只有两个结局：要么逼用户把文案改回去（那是判据在否决设计），
要么常年红着被无视（那比没有判据更糟）。

> **判据要跟着"设计意图"退役，不是跟着"代码还在不在"** —— 这条值得记住：
> 前提消失的判据不会自己报错，它只会一直红，然后被人习惯性忽略。

## 八、R45-E4：hover 浮窗"消失"—— **另一个会话的样式搬家**咬到了它（2026-09-24）

用户报：**「为什么我现在鼠标 hover 在 archive 视图中的直播日历卡片上的日期格上没有悬浮窗出现了」**。

### 8.1 先分开两种成因：**没渲染** vs **渲染在屏幕外**

浮窗只在**真 hover** 时挂载，所以先给探针加了一个模式 `?probe=cell-pop`：
找到第一个带内容的日期格，派发**真实事件**（`pointerover`/`mouseover`/`pointermove`/`mousemove`，
`relatedTarget: document.body`），并**杀掉 `.lc-pop` 的动画**（虚拟时间不推进动画，不杀就读到入场首帧），
然后报七个字段：`popFound / popRect / popStyle / popParent / popInViewport / popHasText / popHitTop`。

实测：

```
popFound=True   popHasText=True   popParent=body
popRect={x:580, y:937, w:300, h:138}   视口只有 621 高  ⇒ popInViewport=False, popHitTop=False
popStyle={position: 'relative', zIndex: 56, display: flex, visibility: visible, opacity: 1}
                     ▲▲▲▲▲▲▲▲
```

**`position` 是 `relative`，而 `posts.css` 里写的是 `fixed`。**

> **判据设计的教训**：如果只判"浮窗可见 / 在视口内"，`popFound=False`（事件没触发）
> 与 `popRect` 跑到屏幕外（样式坏了）**长得一模一样**，会把我往"hover 逻辑 / 数据为空"
> 那条路上带。⇒ **探针必须同时报"机制"（计算样式说了什么）与"效果"（矩形 / 命中测试）**，
> 两者一对照成因立刻二选一。这就是 `--cell-pop` 最终五条断言的来源。

### 8.2 根因：两条**同优先级**规则，胜负只由**加载顺序**决定

```
.os-root { position: relative }   /* status-island.css —— R38 批 5e 从 layout.css 搬来这里 */
.lc-pop  { position: fixed }      /* posts.css */
```

两条都是**单个类** ⇒ 优先级都是 (0,1,0) ⇒ **谁在后面谁赢**。而 `App.tsx` 里：

| 行 | import | 带来的规则 |
|---|---|---|
| 7 | `PostsPage`（`posts.css`） | `.lc-pop { position: fixed }` |
| 12 | `./styles/status-island.css` | `.os-root { position: relative }` ← **后来居上** |

于是 `.lc-pop` 输：浮层（`createPortal` 到 `document.body`）退化成**文档流里的一个普通块**，
`left/top` 只当相对偏移用 ⇒ 落到 `y=937`，**在视口外，完全看不见**。

**为什么极难查（三个特征都齐了）**：

1. 浮层 portal 到 `body` ⇒ **它没有祖先**，"某个祖先的样式压住了它"这条直觉用不上；
2. 它**长得像布局数学问题** ⇒ 第一嫌疑是 `popStyle` 里算的 `left/top`，而那部分**一直是对的**
   （我确实先白核对了一遍坐标算式）；
3. 它**不会红**：没有测试、类型检查也不管（`relative` 是合法的计算值）。

**这不是"哪个会话手潮"的问题，是结构性风险**：搬家的那批改的是**小窗入口的样式组织**，
症状出现在**主窗口的直播日历**上，两边连文件都不重叠 —— 改的人**没有任何线索**能预见到它。

### 8.3 修法与反向验证

修法：选择器抬到两个类 `.os-root.lc-pop` ⇒ (0,2,0)，**与加载顺序无关**。
并在 `posts.css` 就地写清"为什么必须是两个类"（否则下一个人整理样式时会顺手改回单类）。

按 §6.4 的反向验证（一次拿到两条证据）：

| 故意做的破坏 | 期望 | 实测 |
|---|---|---|
| 改回单类 `.lc-pop` | 红，且**指出根因** | ✅ **红 3 条**（`position` 不是 `fixed` / 不在视口内 / 命中测试不是自己） |
| 恢复 `.os-root.lc-pop` | 绿 | ✅ `position: fixed`、`rect={x:580,y:307,w:300,h:138}`、在视口内、命中测试命中自己 |

并固化成 CLI：`python scripts/ui_probe.py --cell-pop --vtuber 15`。

### 8.4 这一节为什么单独记

因为它是**"我改的地方和坏掉的地方没有文件交集"**这一类的实例 —— 也是把
**「搬家样式 = 改级联」**写进 `docs/DEV-LOOP.md` §6.11 的直接原因。
用户报的是"浮窗没了"，真正需要的能力却是"**在不碰任何相关文件的情况下，
知道级联被谁改了**"。

### 8.5 收尾时又踩了一个自己挖的坑：**门禁并发跑**

跑本批门禁时我为了省时间，**同时**发起了 `python -m pytest -q` 与 `python scripts/dev_check.py`
（后者第 1 步就是 pytest）—— 两次分别报 **4 failed** 与 **6 failed**，而 `test_vtuber_api.py`
里报的是 `sqlite3.OperationalError: no such table: live_sessions`。
**事后串行重跑：`586 passed`。**

根因：该文件用的是**磁盘固定路径库**（`sqlite:///./test_vtuber.db`，
`test_profile_cards.py` 同）并被 `create_all`/`drop_all` 反复重建 ⇒ 两个进程互相拆台。
**特征**是"两次的失败清单还不一样"（只重叠 2 条）—— 集合在变 = 并发污染，
不是产品 bug。⇒ `docs/DEV-LOOP.md` §7.3。
（**代价**：多花了一轮 3 分钟的 pytest 才确认自己是清白的 —— 省下的并发时间还不够赔。）
