# 377-20261006 CI 三连红的两个根因（Windows 专有路径 / 等圈数而非等条件）

> 用户把 CI 日志贴过来：v1.1.1 推上去之后 `vitest` 红 3 条（2 个文件）。**本地全绿、CI 全红**，
> 两条都不是产品坏了，而是**判据自己**的问题 —— 一类是平台写法，一类是等待方式。

## 一、`postTypes.test.ts`：`pathname.slice(1)` 是 Windows 专有写法（2 条）

```
ENOENT: '/home/runner/work/DDToolkit/DDToolkit/frontend/home/runner/work/DDToolkit/DDToolkit/frontend/src'
```

`new URL(import.meta.url).pathname.slice(1)` 在 Windows 上是对的（pathname 形如 `/C:/…`，
slice(1) 正好去掉那个多余的前导斜杠），在 Linux 上 pathname 就是 `/home/runner/work/…`
⇒ slice(1) 把它变成**相对路径**，`path.resolve` 再拿 cwd（`frontend/`）一拼就是上面那串。

- **修**：两处都改成 `path.dirname(fileURLToPath(import.meta.url))`；
- **判据**：`postTypes.test.ts` 新增一条**全仓扫描**（扫 `src/**/*.test.ts(x)` 里有没有
  `.pathname.slice(1)`，跳过注释行与本文件自己）；
  **反向验证**：临时放一个含该写法的 `__zz_guard_probe.test.ts` ⇒ 判据红并指出行号（实测，跑完删掉）。
- ⚠️ 这类"只在另一个平台红"的写法，**在 Windows 上靠人自查是抓不到的** —— 所以判据必须是机器判。

## 二、`mseKernel.test.ts` 的 ABR 判据：等的是"圈数"，不是"条件"（1 条）

判据本身没写错（"连续 3 段都喂不饱才报"），但等待方式是 `await flush(60)` ——
`flush(n)` 给的是 **n 轮宏任务**，每轮 `setTimeout(0)` 的真实耗时两端不同：
Windows/jsdom 上被钳到约 4ms（60 轮 ≈ 240ms，够取 3 段），CI 的 Node 上接近 1ms
（60 轮 ≈ 60ms，只取到 2 段）⇒ 本地永远绿、CI 永远红。

- **修**：新增 `waitUntil(cond, budgetMs = 5000)`（每轮给宏任务、到点收手），第一条判据等
  `onLinkSlow` 被调用；后两条"**不报**"的判据先等 `videoSegments() >= 4` 再断言
  —— 样本不足时的"没报"是**空转的绿**（这条也是同一课的另一半）。
- 顺带把失败信息补成现场：`已取 N 段：video 实测 X B/s vs 需要 Y B/s`。
