# 505-20261015 投稿翻页按最早场次停 + 不像录播的丢掉

## 用户口径（2026-10-15）

> 翻页上限按照**当页最后一条投稿的发布时间**与**直播场次记录的最早场次时间**之间的差值来算，
> 如果最后一条投稿早于最早的一场直播，那就不翻了；同时如果**视频标题和时间明显不是录播**，也丢弃。

上一轮把投稿的硬上限从 3 页提到 24 页（`devlog/504`）—— 那是"够用"，不是"该翻到哪"。
这一轮换成**按数据停**。

## 一、停页判据

`scan()` 先算出下界，塞进取数参数（**只进这次调用的副本**，`record.source` 保持干净）：

```python
earliest = min((r["start_at"] for r in rows if r.get("start_at")), default=None)
stop_before = (earliest - src.PAGE_STOP_MARGIN) if earliest else None   # 边距 1 天
raw = await fetch(mid, {**source, "stop_before": stop_before})
```

`fetch_uploads` 每翻完一页看**这一页最旧的那条**：越过 `stop_before` ⇒ 停
（投稿按 `order=pubdate` 倒序，后面的只会更旧、**配不上任何场次**）。
`UPLOAD_MAX_PAGES=24` 退化成纯兜底。比下界还旧的条目也不进候选。

**为什么要留一天边距**：场次记录与真实开播本来就有偏差（早场按惯例标前一天、
录制源的场次记录可能晚于真实开场），卡在正好那一刻会把**刚刚跨过边界**的那一页切掉。
判据对着"早于最早场次的东西配不上任何场次"这条推理，而不是某一个具体数字。

⚠️ 只对**投稿流**生效：系列/合集是上传者自己归档的，接口也不保证按发布倒序，
早停会丢东西 —— 而那条路本来只有 5 页（942 条）。

## 二、不像录播的丢掉

`tier` 不在 `UPLOAD_KEEP_TIERS = ("replay", "dated")` 里 ⇒ 丢。
`classify` 给的 `weak` = **标题既没有回放词、也没有可读的场次时间** ——
在录播号的投稿流里那就是别的投稿混进来了（"标题和时间明显不是录播"）。
比下界还旧的同样丢。

丢了多少条**进日志**：`投稿流丢弃 mid=…：不像录播 23 条 / 早于最早场次 0 条` ——
这是"用户以为扫了 1093 条、其实只用了 881 条"唯一看得见的地方。

## 三、真机实测（真库副本 + 真上游 + 真凭据）

```
库里最早的场次: 2022-07-24 13:00 → 取数下界: 2022-07-23 13:00
投稿流翻到第 19 页即停 mid=94009831（本页最旧 2022-03-04 14:27 早于下界 2022-07-23 13:00）
投稿流丢弃 mid=94009831：不像录播 23 条 / 早于最早场次 0 条
--- 整轮扫描 5.0s ---
号 94009831 : ok=True 来源='投稿'   候选=881 新配=63
号 2132180406: ok=True 来源='直播回放' 候选=927 新配=0
```

翻页 22 → **19 页**，候选 941 → **881**（丢掉 23 条不像录播的 + 尾部过旧的），
配上 65 → **63**。少的那 2 条是**兜底置信度**（`weak` 靠"同日 + ≥30 分钟"凑上的），
按用户口径本来就该丢、而且在审查表里默认不勾。

## 四、顺手抓到一个会把整个号扫崩的 bug

第一次真机跑，投稿号直接 `ok=False`：

```
TypeError: can't compare offset-naive and offset-aware datetimes
```

`fetcher._ts_to_datetime` 返回的是**带时区**的 datetime，而本仓约定是**朴素 UTC**
（`start_at` 一律朴素）。整个投稿流里凡是要拿 `published_at` 与场次比的地方都会炸 ——
这一轮新加的"翻页下界那一比"只是第一个撞上的。修在 `_to_item`（归一成朴素 UTC），
那里本来就是"两条取数路 → 同一种结构"的唯一收口。

⚠️ 系列那条路不会炸（它的 `pubdate` 走的是另一条分支）⇒ 症状看起来像"这个号有问题"，
而不是"代码有问题"。判据 `tests/test_vod_source.py::test_upload_times_are_normalized_to_naive_utc`。
