# 数据分析工作台 · 界面重构分析（2026-10-18）

> 用户口径（原话）：
> ① **「帖子浏览界面和数据分析工作台界面不共用左栏，左栏是帖子浏览界面的专有元素」**
> ② 参考图 = 理想效果的粗糙模板。
> ③ 档案卡里的数字**「按重要性排序，逐个放上，直到卡片过于拥挤了就停止」**。
>
> 本页是**指导开发的方案**，六条决策已拍板（§3），代码未动。

## 1. 现状 vs 目标

| 位置 | 现状（`devlog/525`） | 目标（模板） | 差距 |
|---|---|---|---|
| 壳层 | 工具栏 + **主播左栏**（恒定）+ 内容 | 工具栏 + **通栏内容**（无主播栏） | ★ 壳层按路由分叉 |
| 顶部 | 一行文字标题 | **档案卡**：头像 + 大字名 + 虚化背景 + 读数行 | 新增组件 |
| 时间范围 | 两个原生 `date` 输入 | **热力图 + 双柄滑杆** | ★ 新增组件，换交互模型 |

| 结果 | 卡 2「粉丝名单」 | 大块白卡 + 居中空态「请先选择时间范围」 | 空态跟着"未选范围"走 |
| 状态岛 | 顶栏居中（已有） | 同 | 无 |

## 2. 元素分解与数据核对（真库 14 个 V）

### A. 壳层：左栏按路由分叉

`App.tsx` 现在 `<VtuberSidebar />` **无条件渲染**（第 116 行），路由出口在它右边。
目标要求 `/workbench` 下不渲染，内容区通栏。

**要接受的代价**：主播栏消失后，"当前选中哪个主播"只由工作台自己的选择器承担。
两处状态不再共享 —— 这对独立分析界面是合理的，但**从工作台回帖子浏览时，左栏选中的仍是原来那个 V**，
不是工作台刚分析的那个。这一条要写进验收，免得以后被当成 bug。

### B. 字段可得性（先核后用）

| 字段 | 覆盖 | 结论 |
|---|---|---|
| 名字 | 14/14 | 必放 |
| 头像 `vtubers.avatar` | **3/14**（`local_assets` 另有 28 个 `avatar` 资产） | **资产 + 兜底两件一起做** |
| 背景图 `background_path` + `background_focus` | **11/14** | 可用；缺 露早 / 小松绿Viridis / 柚恩 |
| 粉丝数（`account_stat_snapshots.followers_count` 最新一条） | **14/14** | 可用，4.2 万 ~ 282.7 万 |
| 总场次 / 最近一场（`live_sessions`） | 14/14 | 可用 |
| 已采集弹幕场次（`fan-structure/*/stats`） | **3/14 × 75 场** | 可用，且是**最重要的那一项** |
| 企划 `faction` | 4/14 | 被停止线挡掉（见 §3.5） |
| 出道日期 `debut_date` / 生日 `birthday` | **0/14** | ❌ **直接排除**，无数据 |

⚠️ **多 B 站账号的 V**（如恬豆发芽了有两个 bilibili 账号：351,820 与 37,743 粉）：
取主账号（粉丝数最大的那个）作为卡片读数，**不能求和**（那是两个号）。

### C. 热力图（2026-10-18 第二轮定稿）

**两条信息各走各的通道，绝不共用：**

| 通道 | 编码什么 | 实现 |
|---|---|---|
| **格子深浅**（4 档） | **只**编码当天直播场次数（0 / 1 / 2 / 3+） | `#f4eef0` → `#fbd3dd` → `#f7b2c3` → `#ef8ba5` |
| **右上角深色角标** | 当天弹幕**已采集** | `.cell.coll::after` 4px 深玫红三角（`--c-mark: #8e1b4b`） |
| **实心灰** | 还没到的日子（未来） | `#e7eaee`；**不留空白** |

为什么环而不是框/括号：实测这 75 场是**跳着采的**，拆出来 40 余段、每段 1–3 天。

- **每段一个矩形框**（A）：框连成片，能读，但会盖住段内判断；
- **每段首尾短竖线**（C）：40 多对孤立的标记 ⇒ 看着像撒了一把碎屑，**实测最差**；
- **每格一个内嵌环**（D）：也不需要 run 合并，但**环要占满一圈、压掉可用的填色面积**；
- **每格右上角一个深色角标**（E，**采用**）：4px 三角只吃一角，格子主体仍完整表达"当天几场"；
  角标用比主色更深的 `--c-mark`，在 4 档填色上都够对比。**实测 5px 偏大**（吃掉近一半格子），收到 4px。

**几何**：格 11px、间距 2px 写死 ⇒ **格子必然是正方形**；卡片宽度 = 53 列 × 13 − 2 + 内边距 36 = **723px**（写死，不用 `auto` —— 滑杆内部有 1200px 可滚动内容，`auto` 会被它撑爆、把档案卡挤成 0 宽，**实测踩到过**）。
**月份对齐**：`left = 列序号 × 13px`，精确像素，不用百分比。
**按年翻页**：`‹ 2026 · 287 场 ›`，一次一个自然年；**年份写在 1 月那一列上方**（= 12 月与 1 月的交界处）；首列从 1 月 1 日所在周的周一起（可能含几天去年 12 月）。

### D. 场次窗口滑杆（取代日期输入，2026-10-18 第二轮定稿）

用户口径：**总量上限 150 场**、**下方横向滚动条**、窗口三档 **25 / 50 / 75 场**，
元素参考「数据视图 → 粉丝趋势卡」里的 ECharts `dataZoom` 滑杆。

| 项 | 定稿 |
|---|---|
| 总量 | 最近 **150 场**（`CAP`），超出不显示 |
| 窗口 | **25 / 50 / 75 场** 三档分段按钮；拖两端手柄会跨档 |
| 轨道 | 每场一根柱：已采按弹幕量给高、未采给矮桩；轨内宽 150×8px ⇒ **需要横向滚动** |
| 滚动条 | 轨道下方，8px 自定义滚动条 |
| ★ 夹紧 | **窗口只能完整停在可视区内**；滚动条一动，窗口被边缘**推向反方向**（`clampToView()`） |
| 读数 | 窗口首末日期 + 场次 + 已采 / 待采 |

⚠️ **这条改动把交互模型从"选日期区间"换成了"选场次窗口"** —— 与模型的 25/50/75 窗口同单位，
但它和**后端的采集参数（日期）**不再一一对应：需要把窗口换算成日期区间再调
`POST /fan/{v}/collect`，且**窗口里"未采"的场次未必落在区间内**。

★ 实测就暴露了这个错位：默认窗口贴最新 75 场时读数是 **已采 57 / 待采 18** ——
因为那 75 场试点是**特定一批**（2026-07-05~10-11），并不是"最近 75 场"的子集。

### E. 结果区（下方大卡）

**已定：原地切换，不跳页。** 四态：

| 条件 | 显示 |
|---|---|
| 未选范围 / 区间 0 场 | 空态「请先选择时间范围」 |
| 已选、未采集 | 预估读数（区间 X 场 / 已采 Y / 待采 Z）+「开始采集」 |
| 采集中 | 进度条 + 当前场次 + 「取消」 |
| 采完 | 粉丝名单表格（现有实现搬进来） |

## 3.5 ★ 档案卡的字段排序与停止线

用户口径两版：先是"按重要性逐个放，到拥挤就停"，后来**两卡等高后**改成
"还有很多空余，把之前放不下的也给放进去"。所以停止线**分区**，不是一条线：

**A 区 · 名字右侧的读数行**（高频扫读，**最多 3 项**）

| 序 | 字段 | 决策价值 | 数据 |
|---|---|---|---|
| 1 | 头像 + 名字 | 认出是谁 | 头像 3/14 + 资产 |
| 2 | **已采集 / 总场次** | **直接决定"能不能分析、要等多久"** | 3/14 有已采 |
| 3 | 粉丝数 | 量级上下文 | **14/14** |
| 4 | 最近一场 | 数据新鲜度 | 14/14 |

**B 区 · 卡片下半部的补充区**（等高之后才有的空间，**最多 3 块**）

| 序 | 字段 | 数据 |
|---|---|---|
| 5 | **签名**（引用样式，最多 2 行） | **12/14** |
| 6 | **企划/分组**徽章（`group_name` 优先，`faction` 兜底） | **11/14** |
| 7 | **采集覆盖率** + 进度条 + 首场日期 + 数据跨度（都是算出来的） | 14/14 |

**停止线（契约）**：A 区最多 3 项读数、B 区最多 3 块；**第 4 项/第 4 块一律不进卡片**。
被这条线挡掉的是：出道日期、生日（**两者 0/14，本来也没数据**）。

⚠️ 字段缺失时**整块不渲染**，不要留空胶囊 —— 明前奶绿没有企划，预览里那一行就是空的（正确行为）。

## 4. 分期（每期单独可验）

| 期 | 内容 | 验收 |

## 5. 风险

- **V1 动 `App.tsx` 壳层**，影响所有路由 ⇒ 必须用 `ui_probe` 在真浏览器里量，不能只看单测。
- **热力图按天聚合要查真库**（明前奶绿单个 V 1,168 场）⇒ 接口要缓存，且**拖拽过程不查**。
- 模板是粗糙示意图，**颜色与间距不能照抄**；卡片族仍走 `--pcard-*`。
- 头像资产补齐要先摸清 `local_assets.key` 与 `vtubers` 怎么关联 —— 这一步**单列成 V2 的前置子任务**，
  摸不清就先只上兜底，别把 V2 卡死。
