# 执行方案：场次类型落库 + 类型体系调整 + 按类型统计

## 1. 为什么落库这件事值得做（实测依据）

真机库只读统计（12 个账号 / 7,098 场，`devlog/466`）——**类型推断「从哪一档定的」**：

| 档 | 场次 | 占比 | 说明 |
|---|---|---|---|
| `area`（B 站房间分区） | 3,402 | **47.9%** | 近一半靠分区，不靠内容 |
| `fallback`（**没定出来**） | 2,210 | **31.1%** | 显示成中性的 `live` |
| `title`（标题关键词） | 1,195 | 16.8% | |
| `series`（basis 那一档） | 284 | **4.0%** | 全历史骨架聚类 |
| `learned`（basis 另一半） | **0** | **0%** | 只有 7 条校正，词库没长起来 |
| `override`（用户手改） | 7 | 0.1% | |

结论：**规则确实陈旧**（31% 未定 + 47.9% 靠分区），而落库带来的新能力（可查询）正是用户要的。
⚠️ 另一条实测：`learned` 目前**贡献 0 场** —— 重做规则时要一并回答"这一档留不留"。

## 2. 「写时定稿」的最终口径（用户 2026-10-12 拍板）

用户原话：**「直播场次信息在入库的时候根据其中携带的各类数据直接推断出类型，不需要再在新增场次的时候去
考虑改变已经入库的历史场次类型」**。落到工程上是三条：

1. **逐场次、本地推断**：入库那一刻，只看**这一场自己带的数据**（标题 / 分区 / 起播时刻）；
2. **写入那一行就写它的类型**，**不回头改别的行**（不重算历史、不整账号重算）；
3. **规则改了不回填老数据**：老场次就停在写入时的规则上（用户要改就自己校正）。

由此**推断栈缩短为逐场次档位**，读路径那两档全局信号（`series` 骨架聚类 / `learned` 校正反哺词库）
**从落库口径里去掉**——它们要看"同账号、全历史"，与"只看这一场"直接冲突：

| 档 | 落库时可用？ | 说明 |
|---|---|---|
| `override` | ❌ 写时 | **读取时**压在落库值上面（校正仍是独立事实，C3） |
| `series` | ❌ **去掉** | 骨架聚类要看全历史；逐场次下同一骨架每次结论相同 ⇒ 这一档没有意义（实测占 4.0%） |
| `title` | ✅ | 多词评分（实测 16.8%） |
| `learned` | ❌ **去掉** | 校正反哺词库也是全账号聚合；实测贡献 **0 场**。代价：校正只影响被点的那一场，不再外溢 |
| `area` | ✅ | B 站房间分区（实测 **47.9%**，是主力） |
| `date` | ✅（留形参） | 生日/首播日比对。⚠️ 实测真机 14 个 V **有生日 0 个、有首播日 0 个**、事件表 1 行 ⇒ 今天永远不命中；函数签名留着，不额外查库 |
| `fallback` | ✅ | 中性 `live`（实测 **31.1%**） |

四条硬约束（对上一版做了相应修订）：

| # | 约束 | 为什么 |
|---|---|---|
| C1 | 写点**只重算自己那一行**（不做全账号重算、不做增量 diff） | 用户口径 2：新增一场**不许**改动历史行。副产品：写路径没有 O(n²) 风险（上一版按"每次全量重建"设计时，最忙账号单次 122.8ms、backfill 1,000 场会烧 80 秒） |
| C2 | **同一行里，哪一档定出来的更可信**由读时的合并规则决定（取最高优先级源里**非空**的那个值） | 同一场可能被 danmakus（空标题）与 feed（有标题）各记一行。⚠️ 若按"最高优先级源的值哪怕 NULL 也算赢"，会把 feed 判对的结果冲成 fallback |
| C3 | **校正（override）继续单独存**，不并进类型列 | 它是**输入事实**；"清空校正要能回到推导值"这条能力靠它，且清空后回到的是**落库值** |
| C4 | 未知/失效的分类值**不许让界面崩**（退回中性） | 体系调整（健身→助眠）与规则迭代都会让库里短暂存在旧值 |

**写点清单**（8 处，每一处都要接上"写这一行时顺手定稿"）：

| 触发点 | 代码位置 | 提交方式 |
|---|---|---|
| 场次新增/更新（danmakus 批量） | `danmakus.py:520` → `LiveSessionRepo.upsert_danmakus` | 仓库内部 commit |
| 场次新增/更新（feed 单条） | `bilibili_posts.py:304` → `upsert_feed` | 调用方 commit |
| 场次新增（手动记录） | `routers/vtuber.py:1034` → `create_manual` | 仓库内部 commit |
| 场次改（手动编辑） | `routers/vtuber.py:1082` → `update_row` | 仓库内部 commit |
| 场次删（手动删除） | `routers/vtuber.py:1108` → `delete_row` | 仓库内部 commit |
| 快照写入（自场次） | `scheduler.py:1217 / 1332 / 3467` → `_record_stat_snapshot` | 调用方 commit |
| 校正写入/清空 | `routers/vtuber.py:1332 / 1342` | 仓库内部 commit（**不写类型列**，只影响读时 override） |
| 规则变更 | 无写点 | 按用户口径 3 **不生效于老数据**，只影响之后新写入的行 |

⚠️ 快照写入那一类**不写类型列**：self 快照是"观测"，它并不进 `live_sessions`（实测孤儿虚拟场次 0 条），
写进去也没有行可挂；它影响的是合并结果，而类型归**表内行**。

### 2.1 惰性回填（用户 2026-10-12 选定）

**迁移会自动跑，回填脚本不会**（`scripts/backfill_*.py` 五个都只在我手动执行时才跑）——所以老库那 8,515 场
不能指望脚本。选定做法：**惰性回填**，在读路径上顺手补齐。

- 位置：`routers/vtuber.py` 的 `live_sessions` 端点（它本来就在算类型，`879` 那一行）；
- 行为：算完 → 把值写进 `category`/`category_from` → 提交 → 返回。**响应内容一字不变**（前端不用改）；
- 补过就不再补（列不为 NULL 即跳过），所以每个账号只补一次；
- 用的推断函数与写路径**同一个** ⇒ 不存在"回填的规则和入库的规则跑偏"；
- 代价：库里会存在 NULL 列（没人打开过的账号）⇒ **T4 的两个入口必须 `WHERE category IS NOT NULL`**
  或先触发补齐，否则统计会得出"类型少了一半"的假数字（写成硬约束）。

### 2.2 合并行的类型怎么取（C2 的具体规则）

`merged()` 一个组可能有多行（danmakus + feed）。规则：**按源优先级取第一个非空 `category`**，
`category_from` 跟着一起取。全部为空 ⇒ 该组没有落库类型（虚拟组 / 老库未补）。

⚠️ 这条与"用户校正"的优先级：override **始终**压在最上面（读取时按 `live_id` 查），落库值只是它的底座。

## 3. 数据与契约

**迁移 f016**：`live_sessions` 加两列
- `category` TEXT NULL —— 定稿的类型（英文枚举，与前端标签映射同一套）；
- `category_from` TEXT NULL —— **哪一档定的**（诊断 + 界面"为什么"用；今天它只活在响应里）。

**索引**：按类型筛/统计要能走索引 ⇒ `(account_id, category)`（日历按月筛、卡片按类型聚合都吃它）。

**写入不变量（真正新增的那段代码）**：`LiveSessionRepo` 的每一个写点，在写这一行时都要调
`app/services/live_settle.py` 的 `settle(s)`：

```python
settle(s) -> tuple[str, str] | None      # (category, category_from)；None = 该场不落类型
```

- 逐场次：`infer_category(title, area_name, parent_area_name)`（**不带** series/learned/override）；
- 纯函数、不查库、不 commit ⇒ 放在仓库写点里不构成越界（仓库只把结果写进两列）；
- 规则改了**不回填**：老行停在写入时的规则上（用户口径 3）。

**契约**：`LiveSessionOut.category` / `category_from` **字段名与语义都不变**（前端展示不用改），
只是值从"每次算"变成"读列 + override 覆盖"。

⚠️ 新增的两个入口（T4）：
- `GET /account/{id}/live-type-stats` —— 按类型分组的场次计数（**数据视图卡片**用）；

### 3.1 f017 更正：那两列当时**还不能**支撑按类型聚合（2026-10-13）

上面这条"`WHERE category IS NOT NULL` 或先触发补齐"**不够** —— 实测（真机 14 账号）：

## 7. 判据（要点）

- **写时定稿**：新写一场（带标题/分区）⇒ 它的 `category`/`category_from` 当次就有值（不是 NULL、不是下一轮）；
- **不回改历史（用户口径 2 的判据）**：写第二场 ⇒ 第一场的 `category`/`category_from`/`updated_at` **一字不变**；
- **标题后到**：同一行先空标题落库、再由 feed 补标题 ⇒ 补的那一次把 `category` 一起刷新（写点重算自己那一行）；
- **C2 的判据**：同一场被 danmakus（空标题）与 feed（有标题）各记一行 ⇒ 合并后取到 feed 判出来的类型，**不是** fallback；
- **C3 的判据**：设校正 ⇒ 响应里的类型变；**清空校正** ⇒ 回到**落库值**（不是停在最后那次校正上）；
- **C4 的判据**：库里塞一个未知分类值 ⇒ 界面显示中性、不崩、筛选里不出现空壳；
- **惰性回填 / 物化**：库里 `category IS NULL` 的老行，被读一次后两列补齐；再读一次**不产生新的写**；
- **统计对账（f017 起是硬判据）**：`live-type-stats` 的分组计数与 `/live-sessions` **逐类相同**
  （真机 14 账号 + `scripts/check_type_index_parity.py`），且**反向验证**：把物化停掉 ⇒ 立刻不等
  （`test_type_index_parity_breaks_when_materialize_is_skipped`）。

## 8. 风险与回退

| 风险 | 处置 |
|---|---|
| 漏一个写点 ⇒ 某场类型长期 NULL（**本批最大的风险**） | 结构判据（每个写点都落类型）+ "标题后到"判据 |

| 读路径仍有全账号计算（`_infer_basis`） | T1 之后它只剩 override/兜底用；与"按页取数"那批合并后整个全局项可以拆掉 |
