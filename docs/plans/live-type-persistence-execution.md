# 执行方案：场次类型落库 + 类型体系调整 + 按类型统计

> **用户决策（2026-10-11）**：
> ① **类型可以落库**，两个理由 ——「按类型查询/统计是我们确实要做的」；
> 「当前的类型推断规则已经有点陈旧了，我们需要更精准的类型推断，**并且在落库的时候就已经完成**，
> 而不需要依赖新标题分区然后再推断」。
> ② 分类体系**沿用现有 10 类，但把「健身」换成「助眠」**。
> ③ 「按类型查询/统计」**两处都要**（数据视图加卡片 + 日历按类型筛）。
> ④ 「更精准」的判定尺子**之后讨论**（用户倾向：**基础规则 + 人工标注相结合**）。

## 1. 为什么落库这件事值得做（实测依据）

真机库只读统计（12 个账号 / 7,098 场，`devlog/466`）——**类型推断「从哪一档定的」**：

| 档 | 场次 | 占比 | 说明 |
|---|---|---|---|
| `area`（B 站房间分区） | 3,402 | **47.9%** | 近一半靠分区，不靠内容 |
| `fallback`（**没定出来**） | 2,210 | **31.1%** | 显示成中性的 `live` |
| `title`（标题关键词） | 1,195 | 16.8% | |
| `series`（basis 那一档） | 284 | **4.0%** | 全历史骨架聚类 |
| `learned`（basis 另一半） | **0** | **0%** | 只有 7 条校正，词库没长起来 |
| `override`（用户手改） | 7 | 0.1% | |

结论：**规则确实陈旧**（31% 未定 + 47.9% 靠分区），而落库带来的新能力（可查询）正是用户要的。
⚠️ 另一条实测：`learned` 目前**贡献 0 场** —— 重做规则时要一并回答"这一档留不留"。

## 2. 「写时定稿」的工程含义（**本批最容易静默出错的地方**）

用户说的"落库时就已经完成"，必须落成 **「每一次写入/更新完成时重算」**，而不是"只在 insert 时算一次"：

> 场次的标题/分区**经常后到**（danmakus 先落一行空标题，feed 或下一轮同步才补齐；
> `upsert` 是"非空值刷新"）。只在 insert 时定稿 ⇒ 这些场次被**永久冻结**在"当时没标题"的结果上，
> 而今天读时计算恰好不会犯这个错。这也可能是那 31% `fallback` 的一部分成因。

由此定下四条硬约束：

| # | 约束 | 为什么 |
|---|---|---|
| C1 | **写时无条件重算**（不做增量更新） | `series` 是"整串一起投票"，新来一场可能让**老场次**翻转 ⇒ 增量必漏。副产物：规则改了，下一轮同步自动生效，**不需要全量回填脚本** |
| C2 | 重算的输入是**去重后的 merged 集** | 同一场被 danmakus + feed 各记一行 = 成员数 2 ≥ `MIN_SERIES_MEMBERS`、票还翻倍 ⇒ **会凭空造出系列** |
| C3 | **校正（override）继续单独存**，不并进类型列 | 它是**输入事实**；"清空校正要能回到推导值"这条能力靠它 |
| C4 | 未知/失效的分类值**不许让界面崩**（退回中性） | 体系调整（健身→助眠）与规则迭代都会让库里短暂存在旧值 |

**触发点四类**（每个写点都必须调同一个重建入口）：
场次增删改（danmakus / feed / 手动记录）· 快照写入（自场次）· 校正写入 · 规则变更后的下一轮同步。

## 3. 数据与契约

**迁移 f016**：`live_sessions` 加两列
- `category` TEXT NULL —— 定稿的类型（英文枚举，与前端标签映射同一套）；
- `category_from` TEXT NULL —— **哪一档定的**（诊断 + 界面"为什么"用；今天它只活在响应里）。

**索引**：按类型筛/统计要能走索引 ⇒ `(account_id, category)`（日历按月筛、卡片按类型聚合都吃它）。

**契约**：`LiveSessionOut.category` / `category_from` **字段名与语义都不变**（前端展示不用改），
只是值从"每次算"变成"读列"。⚠️ 新增的两个入口：
- `GET /account/{id}/live-type-stats?from=&to=` —— 按类型分组的场次计数（**数据视图卡片**用）；
- 日历的类型筛选改成**带参请求**（`types=`），让 SQL 去筛（**两处都要**的第二个入口）。

## 4. 类型体系调整：健身 → 助眠

- `app/services/live_type.py` 的 `TITLE_TERMS`：删 `fitness` 的词条，加 `sleep`（助眠/晚安/助眠向/ASMR/哄睡…，
  具体词表按 §5 的尺子校准）；
- 前端标签与顺序（`frontend/src/utils/liveType.ts`：`LIVE_TYPE_ORDER` + `liveTypeLabel`）同步；
- ⚠️ 真机现在有 **28 场**是 `fitness` 判出来的 ⇒ 换体系后它们会被重新判（要么进助眠、要么落回中性）；
  库里可能短暂留着 `fitness` 旧值 ⇒ **C4**（界面退回中性，别显示一个无标签的枚举）。

## 5. 尺子（用户口径：基础规则 + 人工标注相结合；**细则待讨论**）

本批**必须先有尺子再改规则**，否则"更精准"无法证伪。方案内先定框架：

1. **人工标注集**：按现有分布**分层抽样**（31% 的 `fallback`、47.9% 的 `area` 各占配额），
   我把「标题 + 分区 + 现有判断」列成一页，用户逐个给真值 ⇒ 形成一份固定回归集（随 devlog 留档）。
2. **基础规则集**：一批"人眼无争议"的判据（如标题含「歌回」「歌枠」⇒ song），当冒烟用。
3. **两个连续指标**（每次规则改动都跑）：`fallback` 率、人工校正率。
   ⚠️ 只有这两个指标**不够**（它们区分不了"更准"与"把错换了个错法"）⇒ 必须配 1 的固定回归集。

## 6. 批次划分

| 批 | 内容 | 停止条件 |
|---|---|---|
| **T1** | 迁移 f016 + 写时重建接线（四个触发点）+ `category`/`category_from` 读列 | 不带参数的行为与今天**逐字段相同**（除已定稿的类型按新值）；**结构判据**：每个场次写点都调重建入口（漏一个即红）；重建幂等 |
| **T2** | 尺子：人工标注集 + 基础规则集 + 两个指标脚本（只读） | 标注集落档；脚本能一键跑出"与真值的吻合率 + 错在哪"；**在改规则前先跑一次当基线** |
| **T3** | 类型体系与规则：健身 → 助眠 + 用 T2 的尺子迭代（重点打 31% fallback 与 47.9% area 的准确率） | 尺子上**不与基线持平**要有明确结论（变好/变差/持平各写清）；28 场旧 `fitness` 的去向逐条可解释 |
| **T4** | 两个入口：数据视图「类型分布」卡片 + 日历按类型筛（走 SQL） | 卡片数字与库内计数一致（判据：同一条 SQL 对账）；筛选在**跨月**时也对（走服务端筛选，不依赖已加载的那一页） |
| **T5** | 收尾：`PERF.md`（读路径少掉 47ms 的实测）、HTTP-CONTRACT、GLOSSARY（新类型体系）、devlog | A 档 15 步全过 |

## 7. 判据（要点）

- **C1 的判据**：改一条场次的标题（模拟"标题后到"）⇒ 它的类型**当轮就变**（不是下一轮、更不是永不）；
- **C2 的判据**：同一场被两条来源行记录 ⇒ **不构成系列**（直接钉"必须用去重集"这条）；
- **C3 的判据**：设校正 ⇒ 类型变；**清空校正** ⇒ 回到推导值（不是停在最后那次校正上）；
- **C4 的判据**：库里塞一个未知分类值 ⇒ 界面显示中性、不崩、筛选里不出现空壳；
- **统计对账**：卡片/筛选用到的分组计数 = 同口径 SQL 的结果（防"前端又算了一遍"）。

## 8. 风险与回退

| 风险 | 处置 |
|---|---|
| 漏一个写点 ⇒ 某场类型长期不对（**本批最大的风险**） | 结构判据（每个写点必须调重建入口）+ C1 的"标题后到"判据；这也是为什么不做增量 |
| 规则迭代把老数据改坏 | T2 的固定回归集 + 每次改动跑尺子；规则改动只在**下一轮同步**生效 ⇒ 不满意可回滚代码、再同步一次即恢复 |
| 分类体系再变（助眠之后还想加类） | 体系是**数据**不是 schema（TEXT 列）⇒ 不需要迁移；但要保留 C4 |
| 与"按页取数"那批的先后 | 两批独立：本批先做也不冲突（读列比读算更快）；按页那批落地后，本批的收益从 47ms 扩到"读路径完全没有全局项" |

3. 尺子脚本跑出前后对照，结论写进 devlog；
4. 两个入口的真机截图/探针断言（数据视图卡片 + 日历筛选）；
