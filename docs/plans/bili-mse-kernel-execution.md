# 执行方案：B站自写 MSE 内核（评估 + 分期）

> **立项理由（2026-10-03 真机，`devlog/305`–`306`）**：现在这条链路是
> "两个 `<video>`/`<audio>` 元素 + progressive 取数"，由此长出一整串问题：
> A/V 两个钟（漂移、快跑、抢跑）、seek 时浏览器按自己的启发式取数（表现为**画面卡一帧 →
> 低帧率播一段 → 才正常**，而音频全程正常）、缓冲不可控、没有 ABR 手段。
> `299`–`305` 六批全在给这套模型打补丁。
>
> **先做诊断（`devlog/306`，已落地）**：真机复现时日志里会同时出现**代理侧**一行
> （`[视频代理] … 首字节=…ms 前5秒=…MB/s`）和**前端侧**一行
> （`[video] seek→… 起播=…s 饿住=…次 帧率=…fps 丢帧=…`）。
> 这两行决定"MSE 值不值"：若是 CDN 慢，MSE 只能靠**降档**兜；若是浏览器取数启发式，MSE 直接解决。

## 一、可行性：已经用真数据验过（不是纸上推算）

实测一条 1080P 视频流的头部（`devlog/306` 的探针）：

```
ftyp 36B | moov 912B | sidx 680B | moof 1,900B | mdat 1,567,961B
sidx: timescale=16000，24 字节头 + 54 条 12 字节条目
      条目 = [段字节数 ≈1,569,861][时长 80,000 ticks = 5.0s][SAP 标记]
      ⇒ 54 段 × 5s ≈ 270s ≈ 片长 265s ✓  每段都从关键帧开始（SAP）
```

⇒ 三件事成立：① **有索引**（时间→字节）；② **段长固定 5 秒、每段 ~1.5MB**（取数粒度合适）；
③ 每段自带关键帧（append 后可立即从段首播）。codec 字符串 `playurl` 直接给
（`video/mp4; codecs="avc1.640033"` / `audio/mp4; codecs="mp4a.40.2"`）——MSE 正需要它。

## 二、收益

| # | 收益 | 对应现在哪个问题 |
|---|---|---|
| 1 | **只有一个媒体元素/一个钟**（音视频两个 SourceBuffer 喂同一个 `<video>`） | A/V 漂移、快跑抢跑、小窗静音、暂停归属、`devlog/298`–`305` 那一串**整类消失**，相关代码可删 |
| 2 | **缓冲由我们控制**：攒够 N 秒再开播、`buffered` 精确可读 | "卡一帧 + 低帧率播一段"变成干净的"缓冲中 x 秒" |
| 3 | **按段取数**（5s/1.5MB，段首是关键帧），可预取下一段 | 不再依赖浏览器对"百万字节开区间 Range"的启发式 |
| 4 | **可以降档（ABR）**：把 `accept` 里 720P/480P 的 URL 换上 | **唯一能救慢 CDN 的手段**：宁可降分辨率，不要低帧率 |
| 5 | 统计如实：码率、缓冲、丢帧、段序号 | 用户"体感更流畅/更差"能拿数字对账 |
| 6 | 拓展性：内核统一，将来接 HLS/DASH 或新平台只换"取段"那一层 | 现在每个平台一套取数逻辑 |

## 三、成本

| 侧 | 工作 | 量级 |
|---|---|---|
| 后端 | 解析 `moov`/`sidx` 出**段表**并下发（一次请求拿到整段的"时间→字节"表），带缓存 | ~150 行 + 用例 |
| 前端 | MSE 内核：两个 `SourceBuffer`、`updateend` 串行化、按段表 seek、配额 `remove()`、`waiting/canplay` 语义、清晰度切换（换 init+段） | ~350–500 行 + 用例 |
| 兜底 | 保留现有 progressive 路径；段表解析失败/`MediaSource` 不可用 ⇒ 自动退回 | ~80 行 |
| 验证 | 无头 Edge 量「seek → 起播耗时 + 有效帧率」与现在对比；真机 1080P 连播 20 分钟（配额） | 半天 |

合计 **2–4 个工作日**（含真机）。对比：引入 dash.js 不可行（没有 manifest）；比双元素方案贵，但**买断的是整类问题**。

## 四、风险与对策

| 风险 | 说明 | 对策 |
|---|---|---|
| `sidx` 布局与标准不一致 | 实测头是 **24 字节**（标准是 20），字段偏移要按真样本校准 | spike 阶段先写"解析 + 断言 54 段×5s"的用例；解析不出来就退回 progressive |
| SourceBuffer 配额 | Chromium 有总量上限，长视频不清理会 `QuotaExceededError` | 定期 `remove(0, currentTime - 30)`；真机连播 20 分钟验 |
| codec 支持面 | MSE 必须声明精确 codecs；HEVC 还要看系统解码器 | 沿用"**优先 AVC**"（`bili_play._codec_rank`），HEVC 只在 AVC 缺失时用 |
| 回退路径腐化 | 新内核上线后老路径没人走 ⇒ 真出事时发现它早坏了 | 老路径保留**冒烟用例**（seek + 起播），并保留一个显式开关（设置项或 URL 参数）⇒ S2 已落：**渐进式仍有整套用例**（`VideoPlayer.dash.test.tsx` 42 条），开关在设置 → 外观 → 视频播放 |
| MSE 不能凭空加速 | CDN 慢时 MSE 也只是"干净地停"或"降档" | 这正是 ABR 的用途；策略（自动降档 vs 提示用户）在 spike 后定 |
| WebView2 的 MSE 支持 | 需要确认 `MediaSource.isTypeSupported` 对这两个 codec 字符串为真 | spike 第一件事就是量它（一条 `isTypeSupported` 断言） |

## 五、分期

- **S0 诊断（已完成，`devlog/306`–`310`）**：代理侧首字节/吞吐 + 前端侧四段节拍
  （解码/提交/呈现/页面）+ 可见性。**真机八次复现全部落在"呈现受限"**，且形状一致：
  seek 后第 1 秒爆发 153 帧 → 随后 2–4 秒一帧不出 → 恢复 30fps（缓冲 2.2–25s、时钟在走、音频正常）。
  ⇒ 指向 **seek 的盲目追赶**（progressive 无索引源），不是 CDN、不是解码、不是窗口可见性。
- **S1 spike（已完成，`devlog/311`）**：`app/services/bili_segments.py` 解析真流成立
  （**54 段 × 5.0s、init 948B、覆盖全文件=True**）；最小 MSE 页在无头 Edge 里跑通：
  **seek 后 399ms 出画、稳定 30fps、零错误、前方缓冲 20–24s（我们的泵维持）**。
  ⚠️ 两笔诚实记录：① 无头环境**不重放**真机那个冻帧（两条路径都 30fps），
  所以"能不能治"要真机验；② MSE 消不掉"段内预滚"（样例里那 142 帧爆发），
  但它把"先猜字节位置再取数"换成了"数据已在手里"。
- **S2 内核（已完成，`devlog/312`）**：接进了 `VideoPlayer`（自绘控件/清晰度菜单/音量倍速一行没动），
  新增 `GET /bili/segments/{post_id}` 下发段表，老路径留开关。
  **按用户口径"默认 MSE、开关只作为退路"落地**（卡顿几乎每次跳转都出现 ⇒ 默认值就该是新内核）：
  ① 默认走 MSE；② 宿主不支持 / 取不到段表 / 段取不到 ⇒ **自动**退回渐进式（并熔断本次会话，
  不再每个视频撞一次墙）；③ 设置 → 外观 → 「视频播放」里可手动切回渐进式（localStorage，立即生效）。
  走 MSE 时音轨与视频**同一个元素**：`devlog/298`–`305` 那六批补丁治的"两个钟"整类消失。
  ⚠️ **默认切换的判据仍是真机数据**：无头环境复现不了那个 2–4 秒冻帧（§S1 的诚实记录），
  所以"能不能治"要你真机验一次；不能治就切回来（一个开关，零风险）。
  **真机第一轮（`devlog/313`）**：报了两个症状（跳转后走走停停、再跳转一直转圈），
  查出来是内核里三处错（隔段取数 / 预取按"最后一段的末尾"算 / 淘汰把目标段删掉），
  都已修 + 补了判据；另加了**跳转落地前攒 10s 缓冲**（上限 2.5s）与"拖拽松手才提交"。
- **S3 ABR + 收尾（0.5–1 天）**：链路慢时按段耗时自动降档（并在菜单里如实显示当前档）；
  长播配额验证（内核已有主动淘汰 + 配额重试，但**没有连播 20 分钟的真机数据**）；
  文档（`UI-MAP`/`GLOSSARY`/`PERF`）与 devlog。

## 六、停止条件（什么时候不做了）

1. `MediaSource.isTypeSupported` 对 B站这两个 codec 在 WebView2 里为假；
2. spike 里 MSE 的"seek → 出画"不比现在快、帧率也不更稳（说明瓶颈确在 CDN，MSE 无收益）；
3. 单段 5 秒 / 1.5MB 的取数粒度导致 seek 粒度太粗（只能落到 5 秒边界）——
   若用户对"跳到任意秒"的要求高于"稳"，则改为保留 progressive。
