# 执行方案：`_find_group` 候选窗口化（消掉 O(快照×分组)）

> **起因（2026-10-11 实测，`devlog/460` 的仪器 + `PERF.md` §4 记账）**：
> `/account/{id}/live-sessions`（日历/数据卡片）在账号 22（1,256 场）上端到端 **155ms**，
> 其中 `repo.merged()` 占 **84ms**，而 `merged()` 里 **约 66ms**（占端点 47%）全在
> `_find_group` —— 它**每条自观测快照都要线性扫过全部分组**。
>
> 纯函数微基准（直接喂合成分组，不碰库）：
>
> | 分组数 × 快照数 | 耗时 | 每对 |
> |---|---|---|
> | 1,256 × 14（今天这台） | 37 ms | 2.1 µs |
> | 2,512 × 28 | 170 ms | 2.4 µs |
> | 5,024 × 56 | 691 ms | 2.5 µs |
>
> 两个因子各自翻倍 ⇒ 耗时各翻一倍（**双线性**，每对约 2.4µs 稳定）。
> ⚠️ **两个因子都只增不减**：自观测快照随账号活得越久越多，场次只累积
> ⇒ 这是读路径上**唯一已知的"会随数据长大"项**，其余成本（ORM 装载 21ms、
> 逐场次推断 36ms、序列化 6ms）都是一次的、随 n 线性的。
>
> **为什么当时没顺手改**：`_find_group` 属于**已按 3,311 场真实数据校准过的合并口径**
> （见 `merged()` 的 docstring）。它不是"慢一点"，而是"改错了日历就少一场/多一场，
> 而界面上完全看不出是这里错了"。所以本方案的第一原则是**可证明的等价**，其次才是提速。

## 目标 / 非目标

**目标**：`merged(account_id)` 的返回值**逐字段一字不差**，而 `_find_group` 的总成本从
`O(快照数 × 分组数)` 降到 `O(分组数 + 快照数 × (log 分组数 + 候选区间长度))`。

**非目标（本批一个字都不改）**：
- 四条合并判据本身（`room` / `dup` / `interrupt` / `restart`）与它们的阈值常量；
- `_merge_decision` 里对组头标题的重复归一化（那是另一笔 ~14ms 的小账，见 §5）；
- `SNAP_*` 四个常量的语义（容差 15min / 同标题 6h / 假定上界 12h / 回填上限 24h）。

## 必须守住的不变量（等价性）

| # | 不变量 | 为什么 |
|---|---|---|
| I1 | 对每个快照，**被考虑过的分组集合**是原实现的**超集** | 只要超集里包含所有"可能匹配"的分组，多扫几个不匹配的无害 |
| I2 | 候选分组**按原下标升序**参与比较 | 原实现在持平（`ov` 相同且都落在同一档 `key`）时**先遇到的赢**（严格 `>` 比较）。换顺序会改赢家 —— 所以**不许**把 `groups` 重排后直接遍历 |
| I3 | 内层判据（`_overlap_seconds`、同标题兜底、`key` 的两档、`best_key is None or key > best_key`）**一字不动** | 它们才是口径 |
| I4 | `merged()` 的最终输出（含 `out.sort(key=start_at)`）与字段集不变 | 判据直接钉这个 |

> ⚠️ **I2 是本方案最容易踩的坑**：`groups` 今天**并不保证**按 `start_at` 全局有序 ——
> 表内行按 `start_at` 升序攒（分组头取 `min`，仍非降序 ✓），但**自观测分组是全部追加在末尾的**
> （`groups.append(self._group_from_snap(snap))`），而一条**较早**的 self 场次会排在
> 一条较晚的表内分组后面 ⇒ 直接"先排序再遍历"会静默改变持平时的赢家。
> ⇒ 正确做法见 §3：排的是**索引**，遍历仍按原下标。

## 算法（三步，均在 `merged()` 内部）

**第 0 步（每请求一次，O(n)）**：为每个分组预计算
`R_i = g_end or (g_start + SNAP_OPEN_END_ASSUMED_HOURS)`（"假定的最远触及"），
并按 `g_start` 生成索引序 `order`（`sorted(range(n), key=lambda i: groups[i][0]["start_at"])`）
与其上的**前缀最大值** `pm[k] = max(R_{order[0..k]})`（按构造非降 ⇒ 可二分）。

**第 1 步（每条快照，O(log n)）**：算两个下标界（都在 `order` 上二分）：

- **下界** `lo` = 第一个满足 `pm[k] > s_start − 2·tol` 的位置（`tol = SNAP_ENDPOINT_TOLERANCE_MINUTES·60`）；
- **上界** `hi` = 第一个满足 `g_start > max(S, s_start + 6h)` 的位置，其中
  `S = s_end or (s_start + SNAP_OPEN_END_ASSUMED_HOURS)`、`6h = SNAP_SAME_TITLE_HOURS`。

**第 2 步**：把 `order[lo:hi]` 转成原下标、**升序排序**，按原顺序跑**现有内层逻辑**。

### 为什么 [lo, hi) 一定包含全部可能匹配的分组（I1 的证明）

原实现里一个分组能被选中，只有三条路：

1. **区间重叠**（`ov > 0`）：`ov = min(R_i, S) − max(g_start, s_start) + 2·tol`。
   - 若 `g_start ≥ s_start`：`ov > 0 ⇒ min(R_i, S) > g_start − 2·tol`。因为 `R_i ≥ g_start`，
     这条**必然**要求 `S > g_start − 2·tol` ⇒ `g_start < S + 2·tol` ⇒ 落在 `hi` 之前 ✓
   - 若 `g_start < s_start`：`ov > 0 ⇒ min(R_i, S) > s_start − 2·tol ⇒ R_i > s_start − 2·tol`
     ⇒ 它的**下标记为 k 时 `pm[k] ≥ R_i > s_start − 2·tol`** ⇒ 位置 ≥ `lo` ✓
     （前缀最大非降 ⇒ 所有更早的位置其 `pm` 更小 ⇒ 那些位置的分组 `R` 全都 ≤ 阈值 ⇒ 不可能重叠）
2. **±90min 兜底**（`gap = |s_start − g_start| ≤ MERGE_WINDOW_MINUTES`）：
   `g_start ∈ [s_start−90min, s_start+90min] ⊂ [s_start−6h, s_start+6h]` ⇒ 在 `hi` 之前 ✓；
   下界方向：这条**不**要求 `R_i` 大，所以它可能落在 `lo` **之前** ——
   ⚠️ 这正是"只看重叠"会漏掉的那一类（缺 `end_at` 的老快照要靠兜底并入）⇒
   `lo` 的公式必须把兜底区间也并进来：**`lo = min(重叠下界, s_start − 6h 的位置)`**
   （`6h ≥ 90min`，见下方"待确认项"）。
3. **双方都「进行中」+ 同标题**（`|s_start − g_start| ≤ SNAP_SAME_TITLE_HOURS`）：
   同一条 6h 区间，已被 `lo` 的下界与 `hi` 的上界覆盖 ✓

> ⚠️ **`lo` 的最终形状**（把 1 与 2/3 并起来）：
> `lo = min( 第一个 pm[k] > s_start − 2·tol 的位置 , 第一个 g_start ≥ s_start − 6h 的位置 )`
> `hi = 第一个 g_start > max(S + 2·tol, s_start + 6h) 的位置`
> 而因为 `6h > 90min`，第 2 条的 90min 区间是 6h 区间的子集 ✓（**这一条要写成断言**，
> 见 §4 的 W1-D：常量一旦被改成 `6h < 90min`，窗口就不再是超集）。

## W1 的判据设计（本方案的核心，先写判据再改代码）

1. **随机差分**（`tests/test_live_merge_window.py` <!-- 未建 -->）：
   - 造 `n ∈ [1, 300]` 个分组、`m ∈ [0, 40]` 条快照；字段随机取
     `start_at`（升序生成再抖动）、`end_at`（`None` / 正常 / **比 start 早** / 超长）、
     `live_title`（同标题 / 空 / 无关）；
   - 断言 `_find_group_windowed(...) == _find_group_bruteforce(...)`（**同一个对象**比较，
     不是"字段差不多"）；
   - 随机种子固定若干个（确定性），失败时打印那组数据（可复现）。
2. **点对点边界**（手写，别只靠随机）：
   - 开放式分组把快照从**远端**吸进来（`g_start` 比 `s_start` 早 6 小时以上、`g_end` 为空）；
   - 超长组（跨 40 小时）在**很靠前**的位置 —— 这条正是"只按重叠推下界会漏"的形状；
   - 同标题 + 双方都开放式（`SNAP_SAME_TITLE_HOURS` 那条路）；
   - **持平**（两个分组 `ov` 完全相同）⇒ 断言赢家仍是**原下标更小**的那个（I2）。
3. **常量关系断言**：`SNAP_SAME_TITLE_HOURS * 60 > MERGE_WINDOW_MINUTES`
   —— 窗口是超集**依赖它**（写成断言 + 一句注释，防以后有人把 6h 调小）。
4. **真机库对照脚本**（`scripts/compare_merge_window.py` <!-- 未建 -->，**只读**）：
   遍历真机库里场次最多的若干账号，`merged()` 出新旧两份，逐字段比对；
   并打印 `_find_group` 的对照耗时（同一进程、同一只读库）。
   ⚠️ 它必须**不写库**（`mode=ro`，同 `measure_endpoints.py` 的口径）。

## 风险与回退

| 风险 | 处置 |
|---|---|
| 差分判据发现任何**说不清**的差异 | **回退到暴力扫描**（保留 W1 的仪器）：先把它当成"我的等价性论证有洞"，不许为了让它绿去改合并口径 |
| 真机库对照里出现"分组数变了" | 同一处置，且**记录下来**（那是真实数据给出的反例，价值高于本批的提速） |
| `groups` 顺序不变量不成立（见 I2） | 用**索引序**（`order` + `prefix_max`）而不是重排 `groups`；W1 里加一条断言：`order` 上 `g_start` 非降 |
| 提速不如预期（例如 `lo` 被一个超长组拖到很前） | 也算通过 —— 本批的验收是**等价 + 不劣化**，不是"必须快 X 倍"；真出现那种账号，在 devlog 里记下它的形状 |
| 新代码在生产上出问题 | 窗口化是**纯函数级**改动且带开关成本极低：保留 `_find_group_bruteforce`，需要时一行切回（但**默认不留开关**，见下方"纪律"） |

**纪律**：`_find_group_bruteforce` 只给**测试与对照脚本**用（`tests/` 与 `scripts/` 导入），
生产路径只留窗口化那一份 —— 两套实现都在生产里"按条件选一路"就是下一次"两条路各漂各的"。

## 5. 顺带记账（**本批不做**，别顺手）

- `_merge_decision` 对**组头标题**重复归一化：每行标题算了两次（~14ms/请求）。
  修法是给分组 dict 加一个缓存键（`g["_nt"]`）并在 `live_title` 变化时失效 ——
  它同样动的是判据路径，**值得单独一批**（也更该先有"归一化只算一次"的计数判据）。
- ORM 装载 1,394 行 21ms：只有换读法（`load_only` / 裸列查询）才能再降，属于另一条线。
