# 执行方案：`_find_group` 候选窗口化（消掉 O(快照×分组)）

> **起因（2026-10-11 实测，`devlog/460` 的仪器 + `PERF.md` §4 记账）**：
> `/account/{id}/live-sessions`（日历/数据卡片）在账号 22（1,256 场）上端到端 **155ms**，
> 其中 `repo.merged()` 占 **84ms**，而 `merged()` 里 **约 66ms**（占端点 47%）全在
> `_find_group` —— 它**每条自观测快照都要线性扫过全部分组**。
>
> 纯函数微基准（直接喂合成分组，不碰库）：
>
> | 分组数 × 快照数 | 耗时 | 每对 |
> |---|---|---|
> | 1,256 × 14（今天这台） | 37 ms | 2.1 µs |
> | 2,512 × 28 | 170 ms | 2.4 µs |
> | 5,024 × 56 | 691 ms | 2.5 µs |
>
> 两个因子各自翻倍 ⇒ 耗时各翻一倍（**双线性**，每对约 2.4µs 稳定）。
> ⚠️ **两个因子都只增不减**：自观测快照随账号活得越久越多，场次只累积
> ⇒ 这是读路径上**唯一已知的"会随数据长大"项**，其余成本（ORM 装载 21ms、
> 逐场次推断 36ms、序列化 6ms）都是一次的、随 n 线性的。
>
> **为什么当时没顺手改**：`_find_group` 属于**已按 3,311 场真实数据校准过的合并口径**
> （见 `merged()` 的 docstring）。它不是"慢一点"，而是"改错了日历就少一场/多一场，
> 而界面上完全看不出是这里错了"。所以本方案的第一原则是**可证明的等价**，其次才是提速。

## 用户给的关键特征（2026-10-11）与实测校正

> 用户原话：「用应用记录下来的直播场次快照它必然是今天或者昨天的，所以**完全不需要去到很久以前的
> 场次历史中寻找需要合并的场次**」。

**结论成立，但理由要校正一处**（实测，见下表）：

- ⚠️ **快照行本身并不只有今天/昨天**：真机库里 `source='self'` 的快照跨 **2026-09-03 → 10-11（38 天）**，
  因为应用跑着的每一天都在记。
- ✅ 但**每条快照要往回找的范围极小**：它只可能与"时间上挨着它"的分组合并，
  而往回要看多远由**分组自身的最大跨度**决定（合并会把中断续播串成一串）。
  实测真机 5 个账号：分组跨度中位 **3.2–5.0h**、最大 **12.0–36.7h**
  ⇒ `lookback = max(6h, 最大跨度 + 2·容差)` = **12.5–37.2h**（远小于账号两年的历史）。
- ✅ 于是**候选窗口小得几乎不像优化**（真机实测，按下面的 lo/hi 公式算）：

  | 账号 | 分组总数 | 自场次（= `_find_group` 调用数） | lookback | **窗口均值** | 窗口最大 |
  |---|---|---|---|---|---|
  | 22 | 1,257 | 15 | 37.2h | **2.4 组** | 4 |
  | 15 | 1,074 | 23 | 21.8h | **1.3 组** | 3 |
  | 16 | 942 | 22 | 29.7h | **1.7 组** | 3 |
  | 23 | 906 | 27 | 12.5h | **2.3 组** | 5 |
  | 14 | 414 | 23 | 19.5h | **1.4 组** | 3 |

  ⇒ 每条快照从"扫 414–1,257 组"降到"扫 1–5 组"，**迭代数约降 500 倍**
  （66ms → 亚毫秒量级，剩下的是每请求一次的那些固定成本）。

**这也解释了为什么原方案要写前缀最大**：我当时只想着"用重叠推下界"，而重叠下界依赖每个分组
各自的触及（`R_i`），所以才需要前缀最大去二分。**有了"往回最多 = 最大跨度"这条界，
下界变成一个标量**（`max_span` 每请求算一次，O(n)），前缀最大那套机器可以整段删掉 ——
代码更少、证明更短、等价性更好核。下面 §3 已是简化后的版本。

## 目标 / 非目标

**目标**：`merged(account_id)` 的返回值**逐字段一字不差**，而 `_find_group` 的总成本从
`O(快照数 × 分组数)` 降到 `O(分组数 + 快照数 × (log 分组数 + 候选区间长度))`。

**非目标（本批一个字都不改）**：
- 四条合并判据本身（`room` / `dup` / `interrupt` / `restart`）与它们的阈值常量；
- `_merge_decision` 里对组头标题的重复归一化（那是另一笔 ~14ms 的小账，见 §5）；
- `SNAP_*` 四个常量的语义（容差 15min / 同标题 6h / 假定上界 12h / 回填上限 24h）。

## 必须守住的不变量（等价性）

| # | 不变量 | 为什么 |
|---|---|---|
| I1 | 对每个快照，**被考虑过的分组集合**是原实现的**超集** | 只要超集里包含所有"可能匹配"的分组，多扫几个不匹配的无害 |
| I2 | 候选分组**按原下标升序**参与比较 | 原实现在持平（`ov` 相同且都落在同一档 `key`）时**先遇到的赢**（严格 `>` 比较）。换顺序会改赢家 —— 所以**不许**把 `groups` 重排后直接遍历 |
| I3 | 内层判据（`_overlap_seconds`、同标题兜底、`key` 的两档、`best_key is None or key > best_key`）**一字不动** | 它们才是口径 |
| I4 | `merged()` 的最终输出（含 `out.sort(key=start_at)`）与字段集不变 | 判据直接钉这个 |

> ⚠️ **I2 是本方案最容易踩的坑**：`groups` 今天**并不保证**按 `start_at` 全局有序 ——
> 表内行按 `start_at` 升序攒（分组头取 `min`，仍非降序 ✓），但**自观测分组是全部追加在末尾的**
> （`groups.append(self._group_from_snap(snap))`），而一条**较早**的 self 场次会排在
> 一条较晚的表内分组后面 ⇒ 直接"先排序再遍历"会静默改变持平时的赢家。
> ⇒ 正确做法见 §3：排的是**索引**，遍历仍按原下标。

## 算法（两步，均在 `merged()` 内部）

**第 0 步（每请求一次，O(n)）**：
- `reach_i = g_end or (g_start + SNAP_OPEN_END_ASSUMED_HOURS)`（"假定的最远触及"，与
  `_overlap_seconds` 内部那条假定**必须同源**——直接复用同一个常量）；
- `max_span = max(reach_i − g_start_i)`（**实测 12.0–36.7h**；这是"往回最多看多远"的界）；
- `lookback = max(SNAP_SAME_TITLE_HOURS·3600, max_span + 2·tol)`，`tol = SNAP_ENDPOINT_TOLERANCE_MINUTES·60`；
- 按 `g_start` 生成索引序 `order`（`groups` 本身**不保证**全局有序，见 I2）。

**第 1 步（每条快照，两次二分 + 一小段扫描）**：
```
S  = s_end or (s_start + SNAP_OPEN_END_ASSUMED_HOURS)
lo = order 上第一个满足 g_start ≥ s_start − lookback 的位置
hi = order 上第一个满足 g_start >  max(S + 2·tol, s_start + 6h) 的位置
```
把 `order[lo:hi]` 转成**原下标、升序排序**，按原顺序跑**现有内层逻辑**（一字不动）。

### 为什么 [lo, hi) 一定包含全部可能匹配的分组（I1 的证明）

原实现里一个分组能被选中，只有三条路（都能被上面的区间覆盖）：

1. **区间重叠**（`ov = min(reach_i, S) − max(g_start, s_start) + 2·tol > 0`）：
   - `g_start ≥ s_start` ⇒ `S > g_start − 2·tol` ⇒ `g_start < S + 2·tol` ⇒ **在 `hi` 之前** ✓
   - `g_start < s_start` ⇒ `reach_i > s_start − 2·tol`
     ⇒ `g_start = reach_i − span_i ≥ reach_i − max_span > s_start − 2·tol − max_span`
     ⇒ `g_start > s_start − lookback` ⇒ **在 `lo` 之后** ✓
2. **±90min 兜底**（`gap ≤ MERGE_WINDOW_MINUTES`）：
   `g_start ∈ [s_start − 90min, s_start + 90min]`，而 `lookback ≥ 6h ≥ 90min`
   ⇒ 下界在 `lo` 之后 ✓；上界 `≤ s_start + 90min < s_start + 6h` ✓
3. **双方都「进行中」+ 同标题**（`|g_start − s_start| ≤ SNAP_SAME_TITLE_HOURS`）：
   正是 `[s_start − 6h, s_start + 6h]`，被 `lookback ≥ 6h` 与 `hi` 的 `+6h` 两头覆盖 ✓

⚠️ **两条界必须写成断言**（放进代码注释 + 判据，别只靠这份文档）：
- `SNAP_SAME_TITLE_HOURS·3600 ≥ MERGE_WINDOW_MINUTES·60`（否则第 2 条不再被覆盖 ——
  有人把 6h 调到 < 1.5h 就会静默漏掉"靠兜底并入"的老快照）；
- `max_span` 覆盖到**全部**分组（含自观测分组；实测那个 36.7h 的最大跨度就来自一条
  跨 36 小时的自观测伪场次 —— 少算它，窗口就会漏掉真场次）。

| 批 | 内容 | 停止条件 |

| **W3** | 文档与基线收尾 | `PERF.md` §4 记新数字并把"优化候选"改成"已落地（附前后对照）"；`TODO`/本文 §5 的小账重新评估；devlog 落一篇 |

## W1 的判据设计（本方案的核心，先写判据再改代码）

1. **随机差分**（`tests/test_live_merge_window.py` <!-- 未建 -->）：
   - 造 `n ∈ [1, 300]` 个分组、`m ∈ [0, 40]` 条快照；字段随机取
     `start_at`（升序生成再抖动）、`end_at`（`None` / 正常 / **比 start 早** / 超长）、
     `live_title`（同标题 / 空 / 无关）；
   - 断言 `_find_group_windowed(...) == _find_group_bruteforce(...)`（**同一个对象**比较，
     不是"字段差不多"）；
   - 随机种子固定若干个（确定性），失败时打印那组数据（可复现）。
2. **点对点边界**（手写，别只靠随机）：
   - 开放式分组把快照从**远端**吸进来（`g_start` 比 `s_start` 早 6 小时以上、`g_end` 为空）；
   - 超长组（跨 40 小时）在**很靠前**的位置 —— 这条正是"只按重叠推下界会漏"的形状；
   - 同标题 + 双方都开放式（`SNAP_SAME_TITLE_HOURS` 那条路）；
   - **持平**（两个分组 `ov` 完全相同）⇒ 断言赢家仍是**原下标更小**的那个（I2）。
3. **常量关系断言**：`SNAP_SAME_TITLE_HOURS * 60 > MERGE_WINDOW_MINUTES`
   —— 窗口是超集**依赖它**（写成断言 + 一句注释，防以后有人把 6h 调小）。
4. **真机库对照脚本**（`scripts/compare_merge_window.py` <!-- 未建 -->，**只读**）：
   遍历真机库里场次最多的若干账号，`merged()` 出新旧两份，逐字段比对；
   并打印 `_find_group` 的对照耗时（同一进程、同一只读库）。
   ⚠️ 它必须**不写库**（`mode=ro`，同 `measure_endpoints.py` 的口径）。

## 风险与回退

| 风险 | 处置 |
|---|---|
| 差分判据发现任何**说不清**的差异 | **回退到暴力扫描**（保留 W1 的仪器）：先把它当成"我的等价性论证有洞"，不许为了让它绿去改合并口径 |
| 真机库对照里出现"分组数变了" | 同一处置，且**记录下来**（那是真实数据给出的反例，价值高于本批的提速） |
| `groups` 顺序不变量不成立（见 I2） | 用**索引序**（`order`）而不是重排 `groups`；W1 里加一条断言：`order` 上 `g_start` 非降 |
| `max_span` 被某条超长分组撑大（实测最大 36.7h） | 窗口会跟着变宽但**仍然正确**（只是少省一点）。⚠️ 别为了"窗口好看"给它加个上限 —— 那是拿正确性换速度 |
| `SNAP_SAME_TITLE_HOURS` 将来被调到 < 1.5h | §3 那条断言会红（它正是为此而写）；红的时候要**重新论证**窗口，而不是改断言 |
| 提速不如预期 | 也算通过 —— 本批的验收是**等价 + 不劣化**，不是"必须快 X 倍" |

**纪律**：`_find_group_bruteforce` 只给**测试与对照脚本**用（`tests/` 与 `scripts/` 导入），
生产路径只留窗口化那一份 —— 两套实现都在生产里"按条件选一路"就是下一次"两条路各漂各的"。

## 验收（A 档：改的是读路径核心，碰 `app/repositories/`）

## 5. 顺带记账（**本批不做**，别顺手）

- `_merge_decision` 对**组头标题**重复归一化：每行标题算了两次（~14ms/请求）。
  修法是给分组 dict 加一个缓存键（`g["_nt"]`）并在 `live_title` 变化时失效 ——
  它同样动的是判据路径，**值得单独一批**（也更该先有"归一化只算一次"的计数判据）。
- ORM 装载 1,394 行 21ms：只有换读法（`load_only` / 裸列查询）才能再降，属于另一条线。

## 待确认项（开工前问用户/自查一次）

1. **优先级**：本批预期把端点从 155ms 降到 ~90ms，而今天 155ms 并不难受
   ⇒ 如果近期有更值得做的事，本批可以只做 **W1（判据与仪器，独立价值）**再停。
2. **`max_span` 要不要设上限**：目前按实测取真值（12.0–36.7h）。**不设** ——
   设了就是拿正确性换速度（一条比上限更长的分组会被漏掉，而日历上只会表现为
   "这一场没并进去"，看不出是窗口的锅）。若哪天真出现一条把窗口撑得很难看的分组，
   记进 devlog，别偷偷加 cap。
3. **`lookback ≥ 6h` 与 `max_span` 覆盖全部组**：这两条界已写进 §3 的断言清单
   ⇒ 落地时**同时写进代码注释**（不只在测试里）—— 它们是"窗口是超集"的全部依据，
   下一个改常量的人必须看见。
