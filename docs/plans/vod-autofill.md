# 录播自动匹配方案（2026-10-14）

## 0. 一句话

把「一场一场手填录播」换成「**加一个录播号 → 自动扫它的系列/合集/投稿 → 与场次对齐 → 审查后批量写入**」。

## 1. 真机实测（2026-10-14，决定设计的全部依据）

### 1.1 B 站侧：匿名可用的两个端点，且**标题里带场次时间**

| 端点 | 实测 |
|---|---|
| `GET /x/polymer/web-space/seasons_series_list?mid=&page_num=&page_size=` | 匿名 **200**，回该 UP 的**合集（seasons）与系列（series）**，各带 `season_id`/`series_id`/`name`/`total`/`cover`/`mtime` |
| `GET /x/series/archives?mid=&series_id=&pn=&ps=&sort=desc` | 匿名 **200**，`ps=200` 可用，单页 **0.05–0.13s**；每项含 `bvid/title/pubdate/duration(秒)/pic/stat.view` |
| 对照 `GET /x/space/wbi/arc/search`（本仓现用） | 匿名 **`-352 风控校验失败`**，旧路径 `-403/-799` |

明前奶绿（mid `2132180406`）：系列「直播回放」`series_id=2484684`，**total=942**，19 页取完。
**942/942 条标题都含 `YYYY年M月D日HH点场`**，前缀统一为 `【直播回放】`；时长中位 **17904s ≈ 5.0h**
（p25 15730 / p75 19023），<10 分钟的只有 15 条。

⇒ 两个结论：① **这条路不需要登录**（比现用的 `arc/search` 更省）；② 录播号**自己把场次时间写进标题了**，
匹配可以从"猜"变成"读"。

### 1.2 本仓侧：`start_at` 是 **UTC**，命中率 90–96%

拿库里 942 场（`LiveSessionRepo.merged`）逐条对：

| 假设 | 可配场次 | 偏移（录播标题时刻 − 场次开播） |
|---|---|---|
| **`start_at` 是 UTC**（+8 = 北京） | **884/942** | min −127 / 中位 **−48** / p90 0（分） |
| `start_at` 已是北京时间 | 7/942 | —— |

按年命中（±3h）：2022 **93%** · 2023 **90%** · 2024 **95%** · 2025 **93%** · 2026 **96%**。
剩余 6–10% 是真没有录播（或没进这个系列）；另有 **28 场**对到多条录播（同日拆段）。

⇒ 容差按 **±90 分钟**设计（覆盖中位与 p90，又不至于把相邻场次配错）。

## 2. 口径（用户 2026-10-14 拍板）

| 决策 | 口径 |
|---|---|
| 写入方式 | **先审查再写**：扫完给「场次 ↔ 录播」对照表，确认后一次性写入（沿用 C1「误配比漏配更糟」） |
| 选哪个来源 | **自动挑 + 可改**：名字含 `直播回放/录播/回放` 且条数最多者优先，界面上可换 |
| 扫描范围 | **全部历史**（整个系列/合集/投稿），所有对得上的场次都填 |
| 多录播号 | **有序列表 = 优先级**（`vtubers.vod_account_uid` 逗号分隔，**左 = 高优先**）；**高优先缺漏由低优先兜底** |
| 来源形态 | 不限于合集/系列：**投稿流也支持**，且**投稿里常混着非录播** ⇒ 必须有前处理 |

## 3. 设计

### 3.1 数据与口径

- `vtubers.vod_account_uid` **不改结构**，只把"顺序 = 优先级"写成契约（现有实现已是保序去重）。
- 匹配结果**不新增持久列**：`vod_url` 就是结果；来源（哪个 mid / 哪个系列 / 第几条第几段）
  只活在扫描响应里，供审查表显示与"为什么是它"。

### 3.2 前处理（`app/domain/vod_source.py`，纯函数）

每条录播条目 → `tier`：

| tier | 判据 | 用途 |
|---|---|---|
| `replay` | 标题含 `直播回放`/`回放`/`录播` + 标题内有可解析的场次时间 | **主信号**：按时间对齐场次 |
| `dated` | 标题内可解析场次时间，但不含回放词 | 次信号（有些号标题就是场次名） |
| `weak` | 两者都无 | 只在"发布时间落在场次窗口内 + 时长接近"时才接受 |
| `excluded` | 时长 < 10 分钟（实测该系列 15 条）；或标题命中切片/剪辑/翻唱/音声等排除词 | **直接丢掉**（投稿流里混的主要是这些） |

标题时间解析要吃掉实测到的四种形态：
`2026年10月11日18点场` · `2026年10月09日19点场` · `2026年10月11日18:30` · 无年份的 `10月11日18点场`（用发布时间补年）。

### 3.3 匹配（`app/domain/vod_match.py` 扩展）

1. **显式时间**（`replay`/`dated`）：`|标题时间 − session.start_at(UTC→北京)| ≤ 90min` ⇒ 高置信；
2. **兜底**（`weak` 或显式时间没配上的）：`pubdate` 所在北京日 == 场次北京日 且 `duration ≥ 30min`
   且与该场时段重叠 ⇒ 中置信（要标出来，默认**不勾选**）；
3. 同一场对到多条：主选**时长最长**的一条写入 `vod_url`，其余在审查表里列为"其他分段"（可切换）；
4. 同一账号内部**先到先得**（按置信度降序分配，已被占的场次不再复用另一条）。

### 3.4 优先级兜底（`app/services/vod_scan.py`）

```
for mid in 录播号列表(按优先级):
    扫该 mid 的所有来源 → 候选条目
    与"还没有匹配结果的场次"匹配
    命中 ⇒ 记下（来源标 mid 与来源名）
已匹配的场次**不参与**后续 mid 的匹配（=高优先占位）
```

### 3.5 接口

| 方法 | 路径 | 语义 |
|---|---|---|
| `GET` | `/account/{id}/vod-sources?mid=` | 列某 mid 的可用来源（系列/合集/投稿），带自动挑中的那一个 |
| `POST` | `/account/{id}/vod-scan` | **只读**：`{mids:[], sources:{}, include_weak:bool}` → `{matches:[], unmatched:[], sources_used:[], stats:{}}` |
| `POST` | `/account/{id}/vod-apply` | 写入：`{items:[{live_id, vod_url}]}` → 逐条按 B2 的 PATCH 语义写，返回写入数与失败项 |

⚠️ `vod-scan` **绝不写库**（与 `vod-candidates` 同一条纪律）；`vod-apply` 只接受显式的 items。

### 3.6 前端

| 改动 | 内容 |
|---|---|
| 日历工具栏 `+`（图二红框） | 改为**下拉栏**：① 扫描录播并自动填充 ② 手动记录一场直播 ③ 编辑录播号 |
| 详情页铅笔（图一红框） | 改为**下拉栏**（不带遮罩）：编辑这一场 / 添加·更换录播 / 删除这一场 |
| 新增 | 「录播填充」审查窗（Radix Dialog，**复用现有 `lc-dlg-backdrop`，不叠第二层遮罩**）：左边场次、右边命中录播，逐条可勾选/可换/可清空，底部"写入 N 条" |

## 5. 风险

| 风险 | 处置 |
|---|---|
| 误配（把相邻场次的录播配错） | 先审查再写；`±90min` 之外的**不进**高置信；中置信默认不勾 |
| 一次写几百条 | 审查窗显示总数 + 分批写入的失败项逐条列出（不静默吞） |
| `arc/search` 匿名不可用 | 投稿流那条**只能登录态**（用户已登录 B 站，`capabilities` 已放行）；失败如实报"未取到" |
| 系列/合集接口改版 | 端点集中在 `services/vod_source.py` 一个文件，改版只改一处 + 真机探针 |
