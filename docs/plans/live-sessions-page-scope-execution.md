# 执行方案：直播场次按页合并（取代 `_find_group` 窗口化）

> **本方案取代 `docs/plans/find-group-window-execution.md`**（那份只把 `_find_group` 的扫描范围收窄，
> 仍然要装载全部 1,394 行、建 1,256 个 dict、逐场推断 1,256 次、序列化 1,256 个对象）。
> 那份的**等价性证明与实测窗口表**在本方案 §3 里直接复用（它证明"合并是局部现象"），
> 但它本身不必再落地 —— 按页之后 `_find_group` 一次只扫几十个分组。
>
> **用户口径（2026-10-11）**：「卡片中每次只会展示一页内容，所以完全可以将这一页，以及前一页、
> 后一页中包含的记录和快照进行合并，切换的时候重取页 id 然后再算合并」。
>
> ⚠️ **2026-10-13 追加量测（`devlog/472`）**：另一个念头"把 self 快照推导的场次**落表**，
> 这样 `merged()` 就不必再推导它们" —— **量完否掉了**：真机 14 账号里快照推导 139 场、
> 需要新建行的 **0** 场（全部挂在已有行上）；省的是 `merged()` 的 54ms → 23ms，
> 代价是那些行要改走**行**的合并规则（与本方案 §3 第 3 条"不能按页算"的理由同源：
> 换一套判据就得复刻一遍），而日历可能因此**拆场**。判断用的尺子与用户否掉本方案时一致：
> 先看痛感。**两者互不依赖**，不要把它当成本方案的前置。

## 1. 为什么值得做

**今天的事实（已核实）**：`/account/{id}/live-sessions` **没有任何缓存**，
每次请求都把"表内场次 + 从快照推导的自场次"从零合并一遍；而前端**每轮抓取收尾
（`fetch-idle`）都会重取一次**（实测节奏约 80 秒一轮）。最忙的账号（1,256 场）每次
**155ms**，一天被白算上千次。

**成本拆段（真机实测，账号 22）**：

| 段 | 耗时 | 与什么成正比 |
|---|---|---|
| ORM 装载 1,394 行 | 21 ms | **全部历史** |
| 分组合并（`merged()` 里除装载外） | ~63 ms | **全部历史** |
| 推断的 basis（`plan_series` + `build_learned`） | 11 ms | **全部历史**（语义要求，见 §3） |
| 逐场次推断循环 | 36 ms | 场次数 |
| Pydantic 序列化 | 6 ms | 场次数 |
| 账号/V/纪念日/校正（`_live_infer_ctx`） | 1 ms | 常数 |

⇒ **除 basis 外全是"页大小"或"历史长度"驱动的**。按页之后：
装载/合并/推断/序列化都只跟**页内场次数**走（一个月约 10–60 场），
于是 155ms → **十几毫秒量级**，而且**不再随历史增长**。

**它保住的性质**：仍然是"读时计算" ⇒ **不引入缓存失效面**（不像"缓存整个响应"那条路：
漏一个写点就是日历静默显示旧数据）。这是本方案与"加缓存"最本质的区别。

## 2. 分页口径

- **页** = 卡片当前展示的时间范围。日历卡一次渲染**一个月**（`LiveCalendar` 的 `ym`），
  切月就是翻页；
- 请求带窗口（`from` / `to`，或 `month=YYYY-MM`），后端只合并 **窗口 ± 1 个窗口**
  （即"前一页 + 这一页 + 后一页"），**对外只返回窗口内那些场次**；
- **余量是必须的**：合并会把相邻记录并成一组（`restart` ≤10min / `interrupt` ≤60min 且同标题），
  而分组是**跨页**的 —— 没有余量，月初那几场就会与上月末尾的续播段断开。

## 3. 实测依据（本方案的三块地基）

1. **合并是局部现象**：真机 5 个账号的分组跨度中位 **3.2–5.0h**、**最大 12.0–36.7h**
   ⇒ "± 1 个月"的余量比它大两个数量级；
   （该表与 `lookback = max(6h, 最大跨度 + 2·容差)` 的推导见被取代那份方案的 §"用户给的关键特征"）
2. **自观测场次也是局部的**：它们由快照的 `live_status` 转移点推导，天然落在自己的时间附近；
   按时间窗裁剪快照，**不改变窗口内那些自场次的推导结果**（推导只看相邻两条转移）。
3. ⚠️ **basis 是语义全局的，这一条不能按页做** —— 证据是那条规则的形状：

   ```python
   def _confident(scores) -> bool:
       best = ranked[0][1]
       if best < 2.5: return False           # 绝对阈值
       return best - ranked[1][1] >= 1.0      # 绝对领先量
   # MIN_SERIES_MEMBERS = 2；聚合票 = 各成员标题评分之和 + 校正投票（SERIES_OVERRIDE_VOTE=4.0）
   ```

   聚合票是**成员分数之和**、再用**绝对阈值**卡 ⇒ **少几个成员就可能让 `best` 掉到 2.5 以下、
   整档系列分类消失**，那一场随即退到别的信号 ⇒ **同一场直播的分类会随你翻到哪一页而变**。
   这正是本仓最忌讳的"同概念两个答案"（458 那类），必须避免。
   ⚠️ 推论：**重复行会凭空造出系列**（同一场被 danmakus + feed 各记一行 = 成员数 2 ≥ 阈值、
   分数还翻倍）⇒ basis **必须**用**去重后的 merged 结果**算，不能图省事直接扫表。

## 4. 三层拆分（本方案的核心结构）

| 层 | 能否按页 | 做法 |
|---|---|---|
| **合并**（表内行 + 自场次） | ✅ | 查询加时间窗（±1 页），合并逻辑一字不改 |
| **逐场推断 + 序列化** | ✅ | 只对窗口内的场次跑（现有的 `_infer_basis` 之外的循环） |
| **basis**（骨架 → 分类） | ❌ 语义全局 | 见 §6 三个选项（**成本**可以不做成"每次读全局算"） |

## 5. 契约（**只加可选参数，默认行为不变**）

```
GET /account/{id}/live-sessions                   # 现状：全量（保持，别处还在用）
GET /account/{id}/live-sessions?from=&to=         # 新：只返回窗口内场次（合并仍带 ±1 窗口余量）
```

- **默认不带窗口 ⇒ 与今天一字不差**（先保证别的消费者与既有判据不动）；
- 前端日历切月时带窗口重取（"切换的时候重取页 id 再算"）；
- `overlapping()`（手动记录查冲突）传"新场次时间 ± 余量"的窗口即可，它本来也只关心附近。

⚠️ **动手前必须盘一遍 `/live-sessions` 的消费者**（本方案 W1 的第一件事）：
已知至少四处 —— 日历卡（`LiveCalendar`）、数据视图的卡片、场次详情弹窗的当日页签、
手动记录的冲突检查；`ui_probe` 的种子账号也在打它。**任何一个"其实要全量"的消费者被漏掉，
症状都是"那一屏少了几场"**，而界面上不会报错。

## 6. basis 的三个选项（**要用户/实现时定一个**）

| 选项 | 做法 | 成本 | 代价 |
|---|---|---|---|
| **(a) 按需解析** | 只对"这一页要渲染的骨架"去问它们的**全部成员** | 读路径最省 | 成员可能包含**自观测虚拟场次**（不在 `live_sessions` 里、没有 `live_id`）⇒ 要同时覆盖两个源；且需要把 `title_skeleton` 落库 + 建索引（迁移 f016） |
| **(b) 同步收尾算好落库**（推荐） | 每次同步收尾重建一张小表（骨架 → 分类 + 票数 + 成员数），读时直查 | 读路径没有全局项 | 多一个写时产物；陈旧**只影响分类标签**（不会藏场次）；⚠️ 校正（override）也是票源 ⇒ 校正写入也必须重建 |
| **(c) 每次读全局算** | 维持现状 | 什么都不用加 | 地板 ~62ms 分组合并 + 11ms basis，省不掉 |

**推荐 (b)**：它把"绝对阈值需要全量"这件事一次性解决在写时，读路径就彻底没有全局项了。
⚠️ 无论选哪个，**重建的输入必须是去重后的 merged 集**（§3 第 3 条）。

## 7. 边界与自愈（余量不够时**不许静默少并**）

余量（±1 页）在实际数据上远大于最大分组跨度，但"链式续播"在原理上**没有硬上界**
（理论上可以每 50 分钟重启一次、标题不变，一路串下去）。所以：

- 合并时检查"**窗口首尾的分组是否触到余量边界**"；
- 一旦触到 ⇒ **放宽余量重算一次**（并按需再放宽），而不是照当前结果返回；
- 该次放宽记一条日志（它是"余量设定不够"的真实证据，下次可以据此调余量）。

## 8. 批次划分

| 批 | 内容 | 停止条件 |
|---|---|---|
| **P1** | **盘消费者 + 差分验证（先写判据）**：① 列出 `/live-sessions` 的全部消费者，逐个判定"要窗口还是要全量"；② 用真机库写对照脚本：对每个账号、每个"页"，比较**按页结果**与**全量结果里同一批场次**是否**逐字段相同**（含 `category`/`category_from`/`live_id`/`source`/合并后的收益与弹幕数） | 消费者清单齐全；对照脚本在**未改代码**时全绿（同一实现自比），且**故意把余量调小**时必须红；出现任何字段差异 ⇒ **停**，先解释清楚 |
| **P2** | 后端：窗口参数 + 按页查询/合并 + 边界自愈（§7）；basis 按 §6 选定方案落地 | 差分判据绿；不带参数的请求与今天**逐字段相同**（回归）；`measure_endpoints.py --breakdown` 前后对照（预期 155ms → 十几 ms，且**不随历史增长**：拿一个场次少的账号与最多的账号对比，两者应当接近） |
| **P3** | 前端：日历切月带窗口重取；详情弹窗页签、冲突检查同步改到窗口口径 | 前后端契约判据；探针三档复跑；真机切月、跨月续播那一场仍是一整场（**这条要手测**：找一场跨月的续播） |
| **P4** | 基线、文档与 devlog 收尾；（若选 (b)）basis 小表的迁移与重建接线 | A 档 15 步全过；`PERF.md` 记新数字；被取代那份方案标注 superseded |

## 9. 判据（要点）

- **差分等价**（P1 的核心）：同一批场次，按页算与全量算**逐字段相同**；
  ⚠️ 判据必须**有牙**：把余量从"±1 页"调成"±0"或把窗口边界改成开区间 ⇒ 必须红
  （否则它只是把"两边都错得一样"比了一遍）。
- **不变量的回归**：不带窗口的请求 ⇒ 与今天一致（这是"别把别的消费者弄坏"的兜底）。
- **局部性断言**：分组跨度 ≤ 余量；触边 ⇒ 触发放宽（用一个构造出来的"链式续播"用例钉住）。
- **basis 不被重复行污染**：同一个骨架被两条来源行（danmakus + feed）记下时**不构成系列**
  （这条直接钉 §3 的那个推论，也是"必须用去重集"的证据）。

## 10. 风险与回退

| 风险 | 处置 |
|---|---|
| 漏掉一个"其实要全量"的消费者 | P1 逐个盘；不带参数的默认行为**一字不改**，所以漏掉的表现只可能是"那一屏没走优化"，不是"少了几场" |
| 余量不足导致跨页续播被拆成两场 | §7 的触边自愈 + 一条构造用例；差分对照覆盖真机库里所有跨页边界 |
| basis 落库后陈旧（校正没触发重建） | 重建点写死在**一处**（与基线重建同一个入口）；加一条"校正写入后 basis 必须变"的判据 |
| 按页后**首次打开仍然慢**（该页本身很大，例如某月 200 场） | 页大小由界面的月决定，200 场/月属于极端账号；若真出现，按"页内再分块"处理 —— 但**先量**，别预防性设计 |
| 性能不升反降（多了一次窗口查询 + basis 查询） | 差分与耗时对照都在 P2 的停止条件里；不达标就回退到 (c) 并把结论写进 devlog |

## 11. 验收（A 档：碰路由与读路径）

1. 差分判据绿且**反向验证过**（余量/边界各调一次 ⇒ 红）；
2. 不带窗口的请求与今天逐字段一致（回归）；
3. `measure_endpoints.py --breakdown` 前后对照：端到端与 `merged()` 段都显著下降，
   且**场次最多的账号与最少的账号耗时接近**（证明不再随历史增长）；
4. `python scripts/gate.py --tier a` 15 步全过；探针三档复跑；
5. 文档：`PERF.md`（新数字 + 把"为什么不再随历史增长"写清楚）、本方案标完成、
   被取代那份标注 superseded、devlog 一篇。

## 12. 待确认（开工前问用户）

1. **basis 选 (a)/(b)/(c) 哪一个**（我推荐 (b)；它是唯一让读路径没有全局项的）；
2. **页的粒度**：日历是"一次一个月"，那窗口就按月；若数据视图还有别的分页形态
   （例如"最近 N 场"的列表），两处要不要用同一个窗口口径；
3. **优先级**：今天 155ms 并不难受，本方案的直接收益要到"数据涨 3–5 倍"才明显
   ⇒ 也可以只做 **P1（盘消费者 + 差分判据）**，那部分本身是资产（它把"合并是局部的"这件事
   变成可执行的判据），落地留到真有痛感时。
