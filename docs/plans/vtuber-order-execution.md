# 执行方案：虚拟主播自定义排序（拖拽 + 筛选浮窗里的排序栏）

> **用户需求（原始批次 4+5）**：「允许用户在 vtuber 左栏中按住虚拟主播条目进行拖动并排序，
> **排序可以继承在筛选后的结果中**」「左栏顶部工具栏中筛选按钮打开的详情窗里新增一栏排序，
> 包括自定义、A-Z、粉丝数等等」。
>
> **为什么有现成模式可照**：账号（平台徽章）排序在 v0.9.7 已经走完全程
> （`devlog/048`）：迁移 `f002` 加 `accounts.sort_order` → `VtuberRepo.reorder_accounts(ids)`
> → `PUT /vtuber/{id}/account-order` → 前端乐观渲染 + 失败回退 → 三份活文档 + 判据。
> 这一批是**同一形状往上挪一层**（`vtubers` 而不是 `accounts`），所以**能照的全照**，
> 只在"筛选下拖动"那一格必须换算法（见下）。
>
> **口径（2026-10-07 用户拍板，三条都定了）**：
> 1. **筛选下拖动 ⇒ 只换可见那几条的相对位置，没显示的条目原地不动。**
>    ⚠️ 这一条**不能照搬**账号那套 `reorder_accounts` 的"未列出的排在其后"——那会把所有
>    被筛掉的 V 全推到队尾。正确算法：**把传进来的 id 按新顺序，填回它们原本占的那些位置**
>    （位置集合不变，只换内容）。
> 2. **任何排序模式下拖一下就生效，并自动切到"自定义"**（否则用户在"粉丝数"模式下拖半天没反应）。
> 3. **排序栏六项**：自定义 / 名称 A-Z（中文按拼音，`Intl.Collator`，不引库）/ 粉丝数 /
>    默认（导入顺序）/ 最近更新（`updated_at`）/ 开播中优先。
>
> 验收（用户口径）：拖动后换页/重启仍在；筛选状态下拖动能改相对次序且**不影响**没显示的条目；
> 排序栏切换即时生效；「自定义」顺序与拖出来的完全一致。

## 批次划分

| 批 | 内容 | 停止条件 |
|---|---|---|
| **O1** | 数据与契约：迁移 `f010`（`vtubers.sort_order`）+ 模型 + `VtuberRepo.reorder_vtubers(ids)`（**填回原位**算法）+ `list_vtubers` 排序 + `PUT /vtuber-order` + A 档全套文档与护栏用例 | `pytest` 绿；新接口有"填回原位"的正反用例；`MIGRATION_HEAD`/三份活文档同步 |
| **O2** | 前端：排序状态（六项 + 偏好持久化）+ 筛选浮窗里的排序栏 | 判据绿（纯函数排序 + 组件）；真机切一遍六项 |
| **O3** | 前端：`.vtuber-item` 按住拖动重排（乐观 + 失败回退 + 任意模式拖一下自动切自定义） | 判据绿；真机拖一次、刷新一次、带筛选拖一次 |

## O1 的算法（这一批唯一需要想清楚的一段）

```
reorder_vtubers(new_visible_ids):
    slots = [当前所有 V 的位置索引，按 (sort_order, id) 排好后，
             取那些 id 在 new_visible_ids 里的位置]   ← 位置集合不变
    for slot, vid in zip(slots, new_visible_ids): 该位置放 vid
    重新按这个顺序写 sort_order = 0..n-1
```

- **没显示的条目落在哪些位置**不受影响（它们的相对次序和绝对位置都不变）；
- 传进来的 id 必须**恰好是当前可见的那一批**（否则"位置集合"与"新顺序"长度不等 ⇒ 400）；
- 与账号那套的差别写进 repo 的 docstring：**同一个仓储里两个 reorder 语义不同**，
  将来别互相"统一"掉。

## 不做什么

- 不做"每个筛选组合各一套顺序"（用户已排除：只换可见的相对位置）；
- 不做后端排序（六项里五项仍是前端纯函数，只有"自定义"用后端给的 `sort_order`）——
  与现状一致，且省一次往返。
