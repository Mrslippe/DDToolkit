# 01 · 数据层：从直播事件到可分析的表格

## 0. 本文管什么

上游弹幕接口逐条吐出**事件**；本模型把事件压成**两层聚合表**（场次 × 用户、窗口 × 用户），
再交给测量层。本文只写「数据怎么进来、怎么裁、怎么判合格」，不写分数怎么算。

数据层有一条硬纪律：**事实表只读、落盘即冻结**。`loader` 不写任何文件；
同一场次的记录集合会变（实测 `total` 从 21,826 变 12,306），一旦覆盖就再也拿不回来。

## 1. 上游事件

一条事件至少含：事件类型、发送者 `uid`、时间戳；部分类型还带金额。

| 类型 | 事件 | 含义 | 带金额 |
|---|---|---|---|
| 0 | 弹幕 | 一条公开文字发言 | 否 |
| 1 | 礼物 | 可计价礼物 | 是 |
| 2 | 舰长 | 购买/续费大航海（月度订阅） | 是 |
| 3 | SC | 醒目留言（付费留言） | 是 |
| 4 | 入场 | 用户进入直播间 | 否 |
| 7 / 12 | 系统 | 「直播中止」/「录制结束」 | 否 |
| 8 | 系统 | 其他系统消息（**不是**下播依据） | 否 |
| 11 | 系统 | 「直播开始」 | 否 |

`入场` 是独立事件，因此**只进场、从不发言的观众在数据里是存在的**。
2026-10-19 的 5 场抽样（62,427 个「人×场」对）里：**90.1% 的对没有任何弹幕**，
其中 **90.0% 仅有入场事件**；另有 **1.35%** 的对有其他事件却**没有入场事件**
（采集开始时人已在房间）。这批数字只说明结构，不是当前比例。

> 结论：**出席**与**互动**必须分开度量。用「有没有说话」定义出席，会漏掉绝大多数到场者。

## 2. 落盘契约

### 2.1 目录

```
<数据根>/<subdir>/stats/<live_id>.json     场次级元数据 + 对账输入
<数据根>/<subdir>/raw/<live_id>.json.gz    逐人事实表（新数据 gzip；老数据 .json）
<数据根>/<subdir>/names/<live_id>.json     {uid: 昵称}（loader 不读，界面用）
```

数据根的解析**实际顺序**（`loader.resolve_data_dir`）：

1. 环境变量 `DDTOOLKIT_FAN_DATA_DIR`
2. `<DATA_DIR>/datasets/fan-structure`（开发检出；存在就优先）
3. `<DATA_DIR>/fan-structure`（生产）
4. 都没有且 `create=True` 时，在**非仓库根**创建生产目录；否则 `FanDataNotFound`

> ⚠️ `loader` 的模块 docstring 写的是「生产 → 开发」，代码实际是「开发 → 生产」。
> 两种布局同时存在时以代码为准。`tests/test_fan_datapath.py` 守这条路径解析。

### 2.2 `raw` 的每用户字段

| 字段 | 含义 | 备注 |
|---|---|---|
| `m` / `mt` | 弹幕条数 / 时间戳数组（毫秒） | `m` 是**原始条数，永不删减** |
| `mh` | 每条弹幕归一化文本的 **64 位 blake2b 哈希** | 与 `mt` 一一对齐；空文本占位 0 |
| `msh` | 每条弹幕的 **64 位 simhash** | 与 `mt`/`mh` 对齐；为将来模糊匹配留路 |
| `e` / `et` | 入场事件数 / 时间戳数组 | |
| `p` / `pe` / `pt` | 付费总额 / 付费笔数 / 付费时间戳数组 | 礼物 + 舰长 + SC |
| `g` / `gd` / `sc` | 礼物 / 舰长类 / SC 的分项金额 | |
| `sc_cnt` / `gift_cnt` / `guard_cnt` | SC 条数 / 礼物笔数 / 上舰次数 | |
| `guard_top` | 最高舰队等级（舰长/提督/总督） | 同一场取最高 |
| `n` | 昵称（该用户第一条非空 `uName`） | 只展示，不参与计算 |
| `uniq` / `maxrep` | 去重后的不同文本数 / 单条文本最大重复次数 | 2026-10-20 起写入；老数据没有 |

- **`pl` 已删除**（2026-10-27）：旧 raw 里的 `pl`（逐笔金额序列）无人读取、压缩前占 2.2%；
  当前 `aggregate` 不再写它。老文件即使还带 `pl`，loader 也忽略。
- 旧探针时代的 `t0` / `t1`（该人最早/最晚事件）当前 collector 不写、loader 不读。
- **原文不落盘**：只存哈希与时间戳，换去重规则时可离线重算，不必重采。

### 2.3 `stats` 的场次级字段

| 字段 | 含义 |
|---|---|
| `live_id` / `start_at` / `end_at` | 场次 id 与 UTC 起止（naive 字符串） |
| `records` / `distinct_uids` / `named_uids` | 原始记录数 / 不同用户数 / 有昵称的记录数 |
| `type_hist` | 各事件类型的直方图（键是字符串） |
| `type0` / `type4` | 弹幕条数 / 入场条数（v2 兼容字段） |
| `sum_price` / `gift` / `guard` / `sc` | 付费总额与三路分项（元） |
| `danmaku_total` / `uniq_total` / `dup_rate` | 弹幕总数 / 去重总数 / 全场重复率 |
| `duration_source` / `duration_trimmed` | `platform` 或 `danmaku`；被离群裁剪掉的事件数 |
| `sys_start_ms` / `sys_end_ms` / `sys_events` | 系统消息标定的开播/结束与最多 200 条系统事件 |
| `acv` / `acv_points` / `peak_online` | 平均同接 / 同接点数 / 峰值 |
| `coverage` | `{platform, fetched, ratio}`：平台计数、实拉条数、覆盖率 |
| `quality` | 质量闸结果（见 `05-pipeline-ops.md`） |
| `bp` | 破坏性行为画像（见 `03-tags-spam.md`） |
| `dropped_replay` / `replay_from` / `replay_ratio` | 回放裁剪的审计字段 |
| `duration_note` | 下播时刻被率降/系统消息改写的说明 |

`stats` 的 `type_hist["0"]` 与 `sum_price` 是 **C1 恒等式的上游一端**；
collector 从原始记录现算这两个量，不取上游汇总。

## 3. 两级聚合

### 3.1 第一级：场次内 × 用户

每个 `(live_id, uid)` 压成一条 `raw` 记录，只保留统计量、丢弃原文。产出：

- 弹幕 `m`、时间戳 `mt`、文本哈希 `mh`、`uniq`、`maxrep`、simhash `msh`；
- 入场 `e`、`et`；
- 付费 `p`、`pe`、`pt`，以及 `g`/`gd`/`sc` 三路拆分；
- 舰队最高等级 `guard_top`、昵称 `n`。

每场另产出**场次级汇总**：记录数、不同用户数、类型直方图、各类型总量、起止时刻、
`dup_rate`、`coverage`、`quality`、`bp`。这些汇总是 §10 对账的基准。

### 3.2 第二级：窗口内 × 用户

把多场聚合值累加成整窗事实：

| 字段 | 定义 |
|---|---|
| `att_n(u)` | **出席场次数**：窗口内 u 出现过任意事件的场次数 |
| `m(u)` | 弹幕总条数（不含 SC；SC 单列） |
| `pay(u)` | 付费总额（礼物 + 舰长 + SC） |
| `uniq(u)` / `maxrep(u)` | 文本指纹的窗口累计（老数据缺省 0，且 `text_tracked=False`） |
| `lag_sum` / `lag_cnt` / `mean_lag` | 每场首次出场时滞（分钟）的累计与均值 |
| `msg_sess` / `sc_sess` | 发过弹幕 / 打过 SC 的场次数 |
| `first_pos` / `last_pos` | 首次/末次出现的相对位置（0=窗口起点，1=终点），喂「新人」标签 |
| `gift_amt` / `guard_amt` / `sc_amt` | 三路付费金额；恒有 `pay = gift + guard + sc` |

$$\mathrm{att}_n(u)=\#\{\,s:\ u\text{ 在 } s \text{ 中至少出现一次}\,\},\qquad
m(u)=\sum_s m_{u,s},\qquad \mathrm{pay}(u)=\sum_s p_{u,s}$$

> **`m` 与 `uniq` 不是替代关系**：`m` 是发言总量口径，`uniq` 是有效发言口径。
> 当前互动轴仍用 `m`；`uniq` 已采集但未接入（见 `04-validation.md` 已知问题）。

## 4. 文本去重与哈希

归一化三步（`collector._norm_text`）：

1. 全角空格 `U+3000` 转半角空格；
2. 连续空白压成一个空格（`\s+`）；
3. 去首尾空白。

对归一化文本取 **blake2b 64 位**哈希（确定性、跨进程稳定；内置 `hash()` 受
`PYTHONHASHSEED` 影响，**不能**用于跨次采集比对）。同一场、同一用户、同一归一化文本只计一次。

| 字段 | 含义 |
|---|---|
| `m` | 原始条数（永不删减） |
| `uniq` | 去重后的不同文本数 |
| `maxrep` | 单条文本的最大重复次数 |

归一化**不改大小写、不删标点、不做相似度**，因此「草」与「草！」算两条。
老数据没有 `uniq`/`maxrep` ⇒ 读取时 `text_tracked=False`，**不能把 0 当成"没有重复"**。
判定（是否刷屏）与采集分离，见 `03-tags-spam.md`。

## 5. ACV 池（现行 = 3×ACV）

### 5.1 单场 ACV

从 danmakus 的 `live.extra.onlineRank` 逐点时间线算：

- 按时间排序，取**去掉头尾各 10% 点数**后的均值（`TRIM_FRAC=0.10`，按点数比例，短场次自适应）；
- 过滤掉非正值后取均值；没有数据时返回 `None`；
- 同时记录 `acv_points` 与 `peak_online`。

为什么要裁头尾：开播爬坡与下播回落会显著拉低均值。2026-10-23 的 6 场样本里，
**头部 10% 的均值只有整体的 55–65%**，尾部约 85–90%；去掉头尾各 10% 后均值上升 **6.6%–9.8%**。

### 5.2 窗口 ACV 与池子

- `window_acv(win)` = 窗口内各场 `stats["acv"]` 的**中位数**；单场缺失不影响。
- `pool_size_for(win)` = `round(ACV × POOL_MULT)`，`POOL_MULT = 3.0`。
- 三层人数：

| 层 | 人数 |
|---|---|
| 核心 | `round(ACV × 0.75)` |
| 次核心 | `round(ACV × 1.25)` |
| 外层 | `round(ACV × 1.00)` |
| 池子 | `round(ACV × 3.0)`（三层各自 round，极端小 ACV 下可能差 1 人） |

> 代码注释与旧脚本里还残留「2×ACV / 池 = 2×ACV」的写法，**那是改版前的**。
> 现行真源是 `pool.py::POOL_MULT = 3.0`。三层 0.75/1.25/1.0 是 2026-10-24 用户定案。

### 5.3 谁进池：两遍选人

`axes.build_axis_table(win, pool_size=...)`：

1. 先筛**大盘**：`att_n / N ≥ INCLUSION_FLOOR (0.10)`；
2. 若大盘人数 > `pool_size`：先在大盘内建一次表、算核心度
   `S = (π_A + π_I + π_P) / 3`，按 `(-S, uid)` 取前 `pool_size` 人；
3. 在**最终名单内重算**三轴的经验分位。

> 关键：**分位参照总体是最终名单，不是大盘**。两遍法保证「名单里第 1 名」和
> 「大盘里第 1 名」不会各算一套分位。两遍的中间表只用于选人，不对外。

为什么不按出席选：按出席选会丢掉「来得少但打钱多」的用户。2026-10-24 实测
明前奶绿损失 **36%** 收入、星瞳损失 **28%**；改按核心度选（当时是 2× 方案）收入保留
**91%–96.5%**，扩到 3× 后保留 **96%–98%**（`scripts/pool_select_compare.py`）。

为什么是 3×：`scripts/acv_sensitivity.py` 的敏感性结果（2026-10-24）——
1× 只保 73%–88% 收入，2× 保 91%–96.5%，**3× 保 96%–98%**；代价是 R² 从 0.79–0.92 降到
0.69–0.84。用户定案取 3×，即 `0.75 + 1.25 + 1.0`。

**没有 ACV 时**（整窗一场都没采到同接）：`pool_size=None`，退回「出席率 ≥ 0.10 的大盘」
并在报告里标注。此时没有三层人数，接口会退回对半切。

### 5.4 池子健康度

L3 不变量要求池占比落在 **0.5%–20%**（分母 = 窗口内全部观测用户）。
2026-10-27 四个 V 重采后实测 **2.7%–2.9%**；池子过小/过大都说明 ACV 或分位算坏了。
这不是「模型目标」，只是**防写崩的闸门**。

## 6. 场次身份：一行记录 ≠ 一场直播

同一场直播常被多个采集通道各记一行（实时通道、轮询通道、手工补录），
各行标题与开始时间相同但标识符形态不同。若按行计数，一场会被算成两三场。

- 代表行标记：`live_sessions.session_key IS NOT NULL`，格式 `<代表行live_id>#<组内最小成员id>`；
- 只有代表行带 `session_key`，同组其余行为 `NULL`；
- 合并规则的真源是 `LiveSessionRepo.merged()`，装配在 `app/services/live_identity.py`
  （启动期 + 写点之后补齐，幂等；`IDENTITY_VERSION` 变则全库重补）。

**实测**（旧库快照）：按行 **1,168 行**，按代表行 **942 场** —— 差 **226 行**，
按行统计会让场次数**系统性高估约 24%**。凡「场次数」口径的指标都必须先落到代表行。

## 7. 时间与时区

三层口径由 `app/core/timecn.py` 唯一提供：

| 层 | 口径 |
|---|---|
| 存储 / 计算 | **UTC**，naive 字符串 `YYYY-MM-DD HH:MM:SS.ffffff` |
| 分天 / 分月 / 分年 | **东八区（UTC+8）**：SQL 用 `sql_day()`，Python 用 `cn_day()` |
| 展示 | 浏览器本地时区；后端只给 UTC 或带偏移的值 |

两次真实故障（都已修）：

- 采集侧曾用本地时间写场次起止，而库与展示层是 UTC ⇒ 东八区机器上新采数据整体 **+8 小时**
  （dev 库 227 场中 **76 场**如此）；现已统一 `utc_iso()`，历史文件已回填。
- 分天曾按 UTC 日切分 ⇒ 当地 00:00–08:00 开播的场次落到**前一天**且图上不可见；
  实测 dev 库 **520 场**的「UTC 日」与「东八区日」不同。现统一按东八区。

`load_window(since=..., until=...)` 比较的是 `cn_day(start_at)`，**闭区间**。
所以「选 10-20」不会因为 UTC 日期而少一场。

另有一条**开播时刻校正**：`stats.start_at` 不总是真实开播。若系统消息 `type=11`
（直播开始）比 `start_at` 晚 **5 分钟以上**，以 `type=11` 为准；时滞与有效窗口都用它。
（2026-10-25 实例：某场 `start_at` 记 13:59Z，真实开播晚 148.6 分钟。）

## 8. 窗口构造与质量过滤

窗口 = 一段连续场次的集合。`loader.load_window` 的顺序固定：

| 步 | 动作 | 说明 |
|---|---|---|
| 1 | 扫 `stats/*.json`，按 `start_at` 升序 | 场次候选 |
| 2 | 按 `since`/`until` 的**东八区日期**筛（闭区间） | 用户在工作台选的就是这个 |
| 3 | 显式 `live_ids` 优先；否则取最后 N 场 | 给清单就**不再截断**，避免「滑杆窗口/采集对象/分析样本」三套口径 |
| 4 | 场次入册判定 | 见下 |
| 5 | 可选 `keep(i, total)` | 切前半/后半窗口用；在聚合前生效，分母随之变 |
| 6 | 逐场读 raw、聚合 | 解析失败的场次从分母里摘掉 |

**入册三项**（任一不过即整场跳过，且写 warning）：

1. `stats.records < MIN_RECORDS`（**100** 条）—— 样本太小，任何率都不稳；
2. 该场没有入场事件（`type_hist["4"] == 0`）—— 无法区分「没来」与「没记录」；
3. 该场 raw 文件缺失 —— 进了分母却记不上出席，会系统性压低出席率。

> 旧文档写的阈值是 50，**现行代码是 100**。明前奶绿 2026-10-27 的一次加载：
> 请求 75 场、实际 **72** 场（3 场被过滤）。「请求 N 场 ≠ 分析 N 场」必须对使用者可见。

**`N` = 过滤后的实际场次数**，是出席率的分母。`first_pos`/`last_pos` 的分母用的是
**本次参与聚合的场次数**（`len(sessions)-1`）；中途解析失败会带来很小的位置偏移，
且这两个字段只喂展示标签，不影响任何分量。

## 9. 场次跨度与后段回放修复

### 9.1 跨度：平台时间优先

1. **首选平台** `startDate` / `stopDate`：覆盖率 **99.7%–99.9%**，与从事件推相比中位只差
   6 分钟，但尾部能差 8 小时；`duration_source = platform`。
2. **回退**：取该场**弹幕时间戳**的 min/max；连弹幕都没有才回退到全部事件。
   入场事件可能迟到（实测散落到 6 天后，把 11 小时拉成 102 小时），所以不能优先用入场。

回退路径还要过**离群裁剪**（`_trim_span`，保守，宁可少切）：

1. 找相邻事件里**最大**的间隔；不超过 **3 小时** 就停；
2. 只切掉**少数一侧**，且该侧必须 < 全部事件的 **5%**；
3. 重复直至无可切。

真实中场休息（两侧都很大）不会被误切。实测 227 场中 **19 场**触发裁剪，
最长一场从 5 天回到 33 小时。

### 9.2 下播时刻：系统消息 / 率降

- **系统消息**（`sysmsg.py`）：`type 7`（直播中止）与 `type 12`（录制结束）总在同一秒出现；
  取**最晚**的一条 + 1 分钟，且**只允许变短**。`type 8` 不是下播依据。
- **弹幕率骤降**（`duration.py`）：平台 `stopDate` 会偏长（实测一场报 12.9h、实际 2 点就没人说话）。

| 参数 | 值 |
|---|---|
| 分桶 | 5 分钟 |
| 基线 | 前 5 小时桶量的 **p75**（中位数会被安静期拉低） |
| 阈值 | 基线 **10%** |
| 起始 | 第 5 小时之后 |
| 宽限 | 最后活跃桶末尾 + **30 分钟** |

先决条件：至少 **100 条弹幕**且跨度 **>5 小时**；短场次不判。
阈值 5% 太松（9.6 小时的场次裁不动），15%–20% 更紧的阈值会切进真实活动。10% 在实测中把
9.6 小时的一场裁到 6.1 小时，同时没动三场「整段都有人说话」的长场次。

### 9.3 后段回放（内容级修复）

上游偶尔把一场直播的**前段弹幕重新记到末尾**：时间戳变了、内容相同。实测 **9/227 场**
如此，最多一场重复 **9,857 条**。危害有两层：场次看起来长得多；重复内容抬高该场所有人的互动量。

**为什么不能用「多久没弹幕」判断**：重复块在末尾密度并不低（有的每小时上千条），
任何基于时间或活跃度的判据都会把它当正常内容。必须比对**内容**。

判据（`quality.py`，依赖 `mh`）：

1. 按小时分桶，统计每小时 `(uid, 文本哈希)` 的多重集合；
2. 若某小时 **≥80%** 的记录在此前全部记录里都出现过，且该小时 **≥50 条** ⇒ 判为回放；
3. 从**第一个回放小时**起，丢弃之后的所有弹幕，重算 `m`/`uniq`/`maxrep` 与场次计数；
4. 结束时间取「裁后最后一条弹幕」与「原结束时间」中**较早**者 —— 裁剪只会让场次变短。

只丢弹幕，不动入场与付费（没有逐条金额，无法按时间精确回退，且尾部量很小）。
实测最大一场从 **11.53h 裁到 6.87h**。审计字段：`dropped_replay` / `replay_from` / `replay_ratio`。

### 9.4 执行顺序与有效窗口

采集侧顺序：**聚合 → 回放裁剪 → 率降裁尾 → 系统消息收尾**；后三步都只让场次变短。

采集时先算**有效窗口**再过滤记录：优先 `sys_start/sys_end`（type 11/12），
其次平台跨度，最后事件跨度；窗口外 ±60 秒的记录直接丢掉。
这样 raw/stats 天生只含这一场的内容（`live_id` 会被多场复用，平台 `start_at` 也可能偏早）。

旧数据没有这层保证：`loader` 载入时会用 `_trim_user` 把**时滞**按有效窗口重算，
但**不重算 `m`/`uniq`** —— C1 恒等式是全场口径，裁弹幕会立刻破账。弹幕量污染留给采集侧修，
旧场次的已知高估记录在 `04-validation.md`。

## 10. 完整性判据 C1–C4

| # | 判据 | 比较对象 | 不过时 |
|---|---|---|---|
| **C1** | 聚合恒等式 | 场次汇总 vs 由 raw 现算 | **整场弃用**（唯一弃用理由） |
| C2 | 汇总与明细一致 | `stats.ref_danmakus_count`（旧探针写）vs 现算（容差 15%） | 仅降级 |
| C3 | 外部覆盖比 γ | 外部源时间跨度 ÷ 本模型时间跨度（门槛 0.90） | 标记**未核验** |
| C4 | 逐分钟一致性 ρ | 外部源与本模型逐分钟条数相关（下限 0.80） | 仅降级 |

C1 的三条内部检查（`checks.check_identity`）：

1. `records ≥ MIN_RECORDS`（100）；否则弃用；
2. raw 里至少有一个 `(人,场)` 对；
3. `type_hist["0"] == Σ_u m`（**精确相等**）且 `abs(sum_price − Σ_u p) ≤ 0.01` 元。

**来源定案（不可再议）**：**danmakus 是主来源**；vtb.cat / zeroroku 只当**校验器**。
因此「只有内部不自洽（C1）才弃用；外部不一致一律不弃用」。

**为什么只有 C1 能判死**：C1 是内部自洽（同一份数据自己与自己核对），不过说明加工错了。
C2–C4 依赖外部源，而外部源本身可能不全 —— 不过只说明「无法核实」，不能说明「我们错了」。

> ⚠️ **两个 coverage 不是同一个量**：C3 的 `coverage` 是**外部源时间跨度比**；
> `stats["coverage"]` 是**实拉条数 / 平台计数**（§11）。名字相同，比较对象完全不同。

**反例**：实测存在 γ=0.120 的场次（外部源只覆盖 12% 时间跨度）。若用「取最近一条」对账，
会得出 **+622%** 的伪偏离，把一场完全可用的数据判成异常。共同点：**把「外部没收录」当成
「我们算错了」**。

状态：`ok` / `degraded` / `unverified` / `dropped`；`usable = status != dropped`。
**未核验 ≠ 有问题，也 ≠ 已核验。** 报告统计量时应说明窗口里有多少场未核验；
样本曾出现 100% 未核验（无外部源可用），此时这是一个**纯内部自洽**的模型。

> 现状：`GET /fan/{v}/health` 调用 `check_window(win)` **没有传外部源**，所以 C3/C4 必然是
> `unverified`。这是「没接外部源」而不是「数据有问题」，接口的 `notes` 也这么写。
> 另外，新采集**不写 `ref_danmakus_count`**（它只写 `coverage.platform`），所以 C2 在新数据上
> 实际是「未检查」而非「已通过」；平台计数在 `coverage` 里，见 §11 与 `04-validation.md` §6。

## 11. coverage：采集完整性的最后一道

`stats["coverage"] = {"platform": 平台计数, "fetched": 实拉条数, "ratio": fetched/platform}`。
平台没给计数时 `ratio = None`。

- 若 `platform > 0` 且 `fetched < platform × 0.95` ⇒ 质量闸状态记为 `partial`
  （已有更严重状态时不覆盖），并写 `note`；
- `ratio` 可能 **>1**（平台计数偏小，实测有场次 672 vs 实拉 1,252）—— 这不是错误，
  也不要把它当上限；L3 只查 `ratio < 0.95`；
- L3 不变量要求**每场 `ratio ≥ 0.95`**（没有 ratio 的场次不判）；这是抓住「每场缺 5,000 条」
  那类静默缺口的那道闸（2026-10-27 实测四个 V 无一场低于 95%）。

## 12. 读取容错与告警

- raw 是**非 schema 化**的自由格式（探针演进过三版），loader **逐字段容错**：
  缺失按 0/空处理（不抛异常），类型异常记 warning —— 一次缺字段不该让整个窗口失败；
- `stats` 解析失败是致命的（决定场次是否入选），跳过该场次并记 warning；
- `Window.warnings` 里带「跳过」的行就是被摘掉的场次；接口只回前 10 条；
- `Window.spam` 只放**确定**档独轮车，`spam_levels` 放三档全量（见 `03-tags-spam.md`）；
- `Window.slices` 是读 raw 同遍产出的逐场切片，供成员详情 O(1) 查询，避免二次扫描。
