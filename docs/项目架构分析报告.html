§1项目概览

http-test 是名为 Better DD Toolkit 的 VTuber 数据监控与管理的后端服务。 它以 Bilibili 为数据源，自动抓取 VTuber 的昵称、签名、粉丝数、直播状态、视频投稿与动态（帖子）， 持久化到本地 SQLite，并通过 REST API 对外提供查询与抓取触发能力。

12个迭代版本（3 天）
16个 REST 端点
3张数据表（三表重构）
11,055条帖子数据
718张本地头像缓存
26个自动化测试

核心能力

  • VTuber / 账号 / 帖子三级 CRUD：支持多平台账号归属同一 VTuber 的数据模型；
  • 定时数据抓取：APScheduler 每 5 分钟（±30s 抖动）全量刷新账号信息与粉丝数；
  • 帖子（动态/投稿）抓取：按名字模糊匹配或全库全量，分页/游标拉取视频投稿与六类动态，并按内容类型调用详情接口补全数据；
  • 登录态自动维护：Cookie 心跳校验 → refresh_token 续期 → 终端二维码扫码三级兜底，凭据自动写回 .env；
  • WBI 签名与反风控：自实现 B 站 WBI 签名算法，内置限流检测、冷却自愈与断点续抓；
  • 名单发现与导入：独立脚本从 vtbs.moe 拉取 3000+ VTuber 名单生成 CSV，服务启动时按 flag=1 去重导入；
  • 头像本地缓存：头像下载到 static/avatars/ 并经 /static 对外服务。
项目曾内置 Flet 桌面客户端（v0.1.0），v0.1.4 起移除前端、专注后端；批量发现/直播区扫描等重操作也于 v0.2.4 拆分为独立脚本，服务端保持轻量。

常驻后台活动

服务运行期同时存在 三路并发活动：① uvicorn Web 请求处理；② APScheduler 后台线程（每 5 分钟抓取）； ③ auth_manager.run_maintenance() asyncio 任务（每 30 分钟维护登录态）。手动触发的抓取与定时抓取之间由 threading.Lock（非阻塞获取）互斥；帖子抓取另设独立锁 _post_fetch_lock，两类任务互不阻塞。

§5数据模型与 ER 设计

v0.3.0 将早期单表重构为三表：vtubers（主播本体，平台无关）→ accounts（各平台账号）→ posts（动态/投稿）。posts 刻意不设外键， 以 (platform, platform_uid) 与 accounts 逻辑关联。

设计要点

  • 多平台设计：一个 VTuber 可挂多个平台账号（bilibili/youtube/twitter…），当前库内 4 个账号均为 bilibili；
  • 级联删除：accounts 外键带 cascade="all, delete-orphan"，删 VTuber 自动删其账号（测试用例 test_cascade_delete 覆盖）；
  • posts 独立于 accounts：无外键，删除账号不牵连帖子；帖子按 (platform, platform_uid, platform_post_id) 唯一——联合投稿视频会出现在多个 V 的列表里，全局去重会让第二个 V 抓取时违反唯一约束，因此 v0.3.1（迁移 c002）改为按 UID 去重，每个 V 的帖子列表完整（迁移注释原文说明）；
  • 三层去重防线：① 抓取前预读 existing_ids 内存集合（命中直接 skip，不发起详情请求）→ ② 数据库唯一约束 → ③ IntegrityError 捕获回滚跳过（_safe_store_post）；
  • 结构化 + 兜底：body_json 存类型差异数据（图文/视频/专栏各有结构），stats_json 存统计数据，raw_json 保留平台原始响应以防后续需要重解析；
  • 时间统一 UTC：_now() 默认值 + published_at 解析时统一 timezone.utc。

§6启动与生命周期

app/main.py 使用 FastAPI @asynccontextmanager 的 lifespan 编排启动与优雅关停。

启动即自愈：检测到 CSV 新导入的 VTuber（result["created"] > 0）时， 5 秒后自动触发一次全量抓取（_delayed_fetch(5)），新名单无需等待下一个定时周期。 关停路径依次 auth_task.cancel() → shutdown_scheduler(wait=False)，保证无挂起任务阻塞退出。

§7数据抓取子系统

7.1 定时抓取（账号信息 + 粉丝数）

APScheduler 每 5 分钟触发，逐账号抓取用户信息与统计；内置请求节流、批量休息与风控冷却自愈。

  • 双接口抓取：fetch_bilibili_user_info（昵称/签名/头像/直播状态/直播间）+ fetch_bilibili_user_stat（粉丝/关注数）；两者均带 tenacity 重试 ≤3 次、指数退避 2~10s；
  • 节流参数：每账号请求间随机 3~5s；每处理 10 个账号强制休息 60s；定时抖动 ±30s（防周期性特征）；
  • 风控自愈：检测到 HTTP 412 / code -509、-412、-799 / 消息含“频繁”“请求过于”时：先 commit 已更新的数据 → clear_rate_limit() → 冷却 600s → 重建 Session 重读列表 → 从原 idx 继续（断点续抓，不重头再来）；
  • 头像缓存：头像 URL 变化才下载到 static/avatars/{uid}.jpg|png，失败仅 warning 不中断流程；
  • 并发互斥：threading.Lock 非阻塞获取，定时与手动触发重叠时后者直接跳过（返回 {"status":"skipped"}）。

7.2 帖子抓取（视频投稿 + 动态）

按指令触发（非常驻任务）：/vtuber/fetch-posts（按名字模糊匹配）与 /vtuber/fetch-all-posts（全库全量）。

  • 双通道列表：视频用 /x/space/wbi/arc/search 分页（WBI 签名，ps=30，按发布时间排序），动态用 /x/polymer/web-dynamic/v1/feed/space 游标翻页（has_more/next_offset）；
  • 全量模式：video_pages=-1 翻页到空、dynamics_pages=-1 翻到 has_more=false；
  • 类型化详情补全（v0.3.1 重点优化）：feed 数据为摘要，按 type 路由到三个详情接口补全正文/全文/统计，失败回退 feed 数据并打 warning；
  • 动态类型解析器：按 major.type（OPUS/DRAW/ARTICLE/ARCHIVE/LIVE/COMMON）递归解析正文、封面、标题与链接（转发递归解析内层 origin），约 200 行解析逻辑集中在 fetcher.py；
  • 防 Ban 节奏：视频每页后 sleep 1s；动态每页后 sleep 20s；每条详情后随机 0.5~2s；全量任务账号间 20s；风控冷却 600s；
  • 落库：_safe_store_post 逐条插入，唯一约束冲突回滚跳过，末尾统一 commit，返回 PostFetchResult{videos, dynamics, stored, skipped, rate_limited}。

7.3 WBI 签名原理

B 站部分接口（空间/投稿）要求 WBI 签名，wbi.py 完整实现了该算法：

1. get_wbi_keys()        → 调 /x/web-interface/nav 取 wbi_img.img_url / sub_url
                           → 截取文件名得 img_key + sub_key（内存缓存 30 分钟，登录态变化时清除）
2. get_mixin_key()       → raw = img_key + sub_key，按 64 位固定置换表重排取前 32 位 = mixin_key
3. encrypt_wbi(params)   → 参数加 wts（当前秒级时间戳）→ 按键排序 → urlencode
                           → md5(query_str + mixin_key) = w_rid
4. sign_params()         → 返回 {原参数, w_rid, wts}
5. 请求 URL              → https://api.bilibili.com/...?{params}&w_rid={w_rid}&wts={wts}

§8认证与登录态维护

auth.py 的 BilibiliAuth 单例管理 Cookie 全生命周期： 每次请求动态构建 Cookie 头（永远是内存中的最新值），维护循环每 30 分钟执行三级策略。

  • 阶段 1 心跳：GET /x/web-interface/nav 校验 isLogin；有效则顺手调 /cookie/info 刷新 refresh_token 存量；
  • 阶段 2 续期：Session 过期后 POST /cookie/refresh（csrf + refresh_token）换新 SESSDATA，从 Set-Cookie 头解析（httpx cookie jar + 原始头正则双通道兜底）；
  • 阶段 3 扫码：全部失效时生成二维码（终端 ASCII 打印 + 链接），每 2s 轮询最长 3 分钟；识别 86090 等待 / 86101 已扫 / 86038 过期 / code=0 成功；成功后访问回调 URL 种 Cookie、nav 复核登录态，提取 SESSDATA/bili_jct/uid/refresh_token；
  • 持久化闭环：任何 Cookie 变化都 _save_to_env() 写回 .env（按键替换式改写 + load_dotenv(override=True) 重载），重启免登录；登录成功后清除 WBI 密钥缓存强制换新签名密钥；
  • 请求头伪装：统一 Chrome UA + Referer/Origin 伪装 + Accept-Language，降低风控概率。

发现的问题（按严重度）v0.3.2 已修复 P1–P4 及 P5 主要项，详见 §19

P1 · 日志文件恒为空（已实证） ✅ 已修复：logs/app.log 为 0 字节。 根因：main.py 第 13 行 from app.services.scheduler import ... 触发 scheduler 模块导入，其第 27 行先执行了 logging.basicConfig(level=...)；随后 main.py 第 19 行的 basicConfig(handlers=[FileHandler, StreamHandler]) 因“根 logger 已配置过”而被静默忽略——FileHandler 从未注册。修复：删除 scheduler.py 的 basicConfig（devlog/013，启动实测日志正常落盘）。
P2 · 全局风控标志无并发保护 ✅ 已修复：fetcher.py 的 _rate_limited 是模块级全局变量， 由两大抓取任务共享（虽然各有锁互斥，但跨任务仍可能互相污染——帖子任务触发风控可能被账号抓取任务读到并误冷却）。 已改为 contextvars.ContextVar 任务级隔离 + 任务启动时重置（附隔离单测）。
P3 · 配置版本号未同步 ✅ 已修复：settings.VERSION 已更新为 0.3.1。
P4 · 动态类型映射缺项 ✅ 已修复：DYNAMIC_TYPE_MUSIC 未在映射表，导致库中出现 7 条 type='dynamic_type_music' 的原始值泄漏（fallback raw.lower() 直接把枚举名存库）。 已补映射（→ music）并执行 scripts/repair_post_types.py 修复存量数据（剩余 0 条）。
P5 · 其他小项： ① 每次抓取新建 httpx.AsyncClient（连接不复用）——已修复（任务级复用）；② 头像扩展名判定 ".jpg" in url else ".png" 对 gif/webp 会存错扩展名——已修复（_avatar_ext 按 URL 路径推导）；③ alembic/env.py 从 app.main 导入 Base，迁移上下文耦合整个应用（含日志副作用）——已修复（改从 core.database 导入并显式注册模型）； ④ create_all 与 Alembic 双轨建表存在 drift 风险——未处理；⑤ REST API 本身无鉴权且 CORS allow_origins=["*"] + allow_credentials=True，公网部署需收紧——已修复（CORS_ORIGINS 可配置；通配符来源时不携带凭据，符合浏览器规范；API 鉴权仍建议后续增加）；⑥ _fetch_one_account 返回语义混合（风控/无数据都计入 failed）——未处理； ⑦ fetch/auth/wbi/调度/导入均无测试覆盖（httpx 未 mock）——部分修复（新增 12 个修复项单测；网络层 mock 与 auth 状态机测试仍缺）。
