# 档案视图 · 卡片视觉与动效规格（贴纸 / 小组件）

> **这是什么**：一份**设计规格**，不是实现说明。R37-P4（档案视图卡片的外观重做与编辑态动效）
> 按它落地 —— 材质、圆角、卡片语法、动效时间轴、不变量都定在这里，代码只负责实现。
>
> **来源**：用户 2026-09-18 口径（附 MIUI 桌面小组件参考图）——
> 「我希望的卡片样式是那种**圆角阴影稍微浮起**的卡片，可以类似数据视图中的两张卡片；
> 卡片内的排版可以**生动一些**，类似**贴纸**那种设计或者像参考图中那样**小组件形式**的卡片设计，
> 当然只是粗糙参考一下，具体设计风格还是遵循项目美学；
> 编辑布局时的动画也制作成**移动手机小组件**的类似动画，例如**长按选中时弹跳缩放**、
> **其他卡片退避时的移动也有动画表现**、**放置时也有落下缩放**等等」。
>
> **现状基线（2026-09-18 快照）**：**它说明的是"为什么要改"的起点，不是当前状态** ——
> 当前状态看 **`docs/UI-MAP.md` B1**。快照内容：`.pcard` 当时是 **4px 圆角 + 发丝边 + 零阴影**
> （"表面层"），头部 12.5px 标题 + 下缘发丝；编辑态靠 `.board-btn` 进入；拖动是**逐格瞬移**
> （直接改 `grid-column/row`，无过渡）；三张内置卡（纪念日 / 优质投稿 / 大事记）都是"行列表"式排版；
> 数据视图的两张卡（`.live-calendar` / `.fan-chart`）已是 **4px 圆角 + `--pill-shadow`**。
>
> **风格取向**：借手机小组件的**编排**（拿起 / 让位 / 落下）与贴纸的**层次**（白环 + 微阴影 + 大数字），
> 但不借它的**弹跳与循环动画** —— 桌面窗口不是手机桌面（同 `design-status-island.md` 的取向）。

## 0. 一句话原则

> **卡片是一块能被"拿起来"的实体：静止时安静，动手时连续。**

"连续"是这一批的全部难点：现在拖动时卡片是**逐格跳**的，眼睛看到的是"跳"、手上做的是"拖"。
规格里的每一条动效，都是为了让"**手的连续**"和"**格的离散**"在观感上不打架。

## 1. 三条硬约束（验收先看这三条）

| # | 约束 | 为什么 |
|---|---|---|
| 1 | **高度仍由网格算死** | `ROW_H×h + GAP×(h-1)`；一旦让内容撑高，相邻行会被压住（探针既有裁决，不许动） |
| 2 | **动画只动 `transform` / `opacity`** | 拖动期间改 `left/top/width/height` 会每帧重排；**缩放手柄**是刻意例外（它改的就是尺寸） |
| 3 | **几何判据读模型真值，不读过渡中的 rect** | `scale(1.05)` 会让 `getBoundingClientRect()` 大 5%，动画帧上的 rect 不是布局真值 |

## 2. 视觉令牌（先收词表，再谈样式）

起点（2026-09-18 快照）：档案卡零阴影、4px 圆角；`--pill-shadow` 只服务浮片族。新增一族（放 `styles/tokens.css`）：

| Token | 值 | 用在哪 |
|---|---|---|
| `--pcard-radius` | **12px** | 卡片圆角（与弹窗族 `--radius-dialog` 同值 ⇒ 同心圆角好算） |
| `--pcard-radius-inner` | **8px** | 卡内封面 / 贴纸块（内层要比外层小一档，别和外层同值） |
| `--pcard-ring` | `inset 0 1px 0 rgba(255,255,255,.9)` | 顶部 1px 高光内边 —— **"稍微浮起"的关键**，光从上面来 |
| `--pcard-shadow` | `0 1px 2px rgba(15,23,42,.05), 0 6px 16px rgba(15,23,42,.08)` | 静止 |
| `--pcard-shadow-hover` | `0 2px 4px rgba(15,23,42,.06), 0 12px 26px rgba(15,23,42,.12)` | 阅读态 hover（上浮 2px） |
| `--pcard-shadow-edit` | `0 4px 10px rgba(15,23,42,.10), 0 14px 30px rgba(15,23,42,.14)` | 编辑态（"拿得起来"的暗示） |
| `--pcard-shadow-lift` | `0 10px 22px rgba(15,23,42,.16), 0 24px 48px rgba(15,23,42,.20)` | 拿起时（浮最高） |

**为什么是 12px 而不是数据视图的 4px**：数据视图那两张卡（870×631 / 870×460）是"大面板"，
4px 是面板语汇；档案卡是 280×276 量级的**小方块**，同样的 4px 会显得尖硬、撑不起"贴纸"。
12px 同时也是弹窗族的值 ⇒ 全站只有"面板 4px / 弹窗与卡片 12px"两档，不新增第三档。

**⚠️ 不动的两个死令牌**：`--radius-card: 0px` / `--shadow-card: none`（`tokens.css` 里声明但全仓无人引用，
它们是"方形总纲"的显式标记）。新族用 `--pcard-*` 前缀（与类名 `.pcard` 对齐），避免语义撞车。
**同批补 `docs/UI-MAP.md` 的豁免族**：现有三族（浮片 / 药丸族 / 功能性气泡）→ 增列
**④ 档案卡族**（`--pcard-radius` + `--pcard-shadow*`），否则下一个改卡片的人会当成违规。

## 3. 卡片语法（五个槽位，所有卡片共用）

```
┌─────────────────────────────────────────┐
│ ① 标题 12.5/600                ⓐ 贴纸角标 │  ← head：无下缘发丝（改由内容自己分隔）
│                                          │
│  ② hero：大数字 30/700 + 单位 12/500      │  ← 可选；只有"真有一个数"的卡才配 hero
│     一句人话 11.5/--c-text-sub            │
│                                          │
│  ③ rows：行列表（发丝分隔 / 可点行 hover 浅粉底）│
│                                          │
│  ④ hint 11.5/--c-text-sub（口径一句）      │
└─────────────────────────────────────────┘
```

- **① 标题**：保留 12.5/600（不学数据视图的 16.5 —— 卡片的标题只是标签，主体是内容）。
- **ⓐ 贴纸角标**（本规格的**签名元素**，全卡只允许有一个）：
  - 形态 **22×22 全圆**，底色 = 该卡 tone 的**深档**，内含 13px 白色图标（lucide，`stroke-width: 2`）；
  - `box-shadow: 0 0 0 2px #fff, 0 2px 6px rgba(15,23,42,.16)` —— **白环 + 微阴影 = 贴纸贴在卡上**；
  - **只放图标、不放文字**：白图标在粉底上只有 2.4:1（不达标，但属装饰、旁边必有文字标题）；
    一旦带词就得过 4.5:1 —— 于是"带词的角标"这件事直接不做，短词一律进 ③ 的文字 chip。
- **② hero**：`tabular-nums`，字重 700、30px、色 `--c-text-main`；单位/后置语 12/500 同行基线对齐。
  **没有可信数字就不放 hero** —— 不放"0"、不放"—"占位充数（诚实 UI，静默失败不许伪装成有数据）。
- **③ rows**：行高 17px、行距 6px、行间 `1px solid var(--c-border)`；行内可点元素沿用 `focus-visible` 环。
- **④ hint**：保留既有职责 —— 说清"按什么排 / 数据从哪来 / 还没填的东西去哪填"。

**tone 表（每卡一色，只用在 ≤22px 角标与 ≤11px 文字 chip 上）**

| 卡 | tone | 深档（角标底 / chip 文字） | chip 底（浅） |
|---|---|---|---|
| 纪念日 | `#fb77a1` | `#b23a63` | `rgba(251,119,161,.14)` |
| 优质投稿 | `#fc7079` | `#b2353c` | `rgba(252,112,121,.14)` |
| 大事记 | `#7c93b5` | `#3d5573` | `rgba(124,147,181,.16)` |
| 自定义卡（P3b） | `#94a3b8` | `#4b5a6b` | `rgba(148,163,184,.16)` |

**"生动"来自层次，不来自色块面积**：卡片主体永远是白卡 + 中性文字，tone 只出现在上面那张表允许的两处。
（这是本规格最想守住的一条 —— MIUI 参考图里的彩色是靠**图标块**撑的，不是靠整卡铺色。）

## 5. 动效令牌与时间轴

**令牌先落地**（`tokens.css`；数值与 `design-status-island.md` §2 同一组，R38 批 1 直接复用，避免两处漂）：

| Token | 值 | 用在哪 |
|---|---|---|
| `--motion-instant` | **90ms** | 按下的即时反馈（"按住了"） |
| `--motion-fast` | **140ms** | hover、淡出、删除 |
| `--motion-base` | **220ms** | 退避、落位、让位 |
| `--motion-slow` | **320ms** | 大位移（跨多行的让位） |
| `--ease-standard` | `cubic-bezier(.22,1,.36,1)` | 进入 / 位移动画 |
| `--ease-exit` | `cubic-bezier(.4,0,1,1)` | 离场 / 消失 |
| `--ease-emphasized` | `cubic-bezier(.2,0,0,1)` | 落位（前快后慢，"落定"感） |
| `--ease-pop` | `cubic-bezier(.2,1.5,.4,1)` | **唯一允许的过冲**，只用于"拿起"那一次 `scale` |

### 5.1 拾起（阅读态长按 350ms / 编辑态按下即拖）

> **两态两种语义**（2026-09-18 实现时细化，P4b 落地）：
> **阅读态**按住 350ms 才拿起（手机语义，也避免误触把卡片碰乱），拿起即进编辑态；
> **编辑态**按下就拖 —— 用户点「编辑布局」本来就是为了排布，若每拖一次还要先按住 350ms，
> 那个按钮就白点了。拿起时的缩放/阴影两态一致，所以"弹跳缩放"的观感没有打折。
> ⚠️ 这条细化是被护栏逼出来的：改之前 `--board`（点了「编辑布局」再拖）当场红了 ——
> 合成手势按下后 80ms 就移动，正好落进"没到 350ms 就拖 ⇒ 取消"那条分支，一行都没动。

| 时间 | 发生什么 | 细节 |
|---|---|---|
| 0ms | 立即**按下去**（阅读态） | `scale: .985`，90ms `--motion-instant` —— 没有即时反馈，用户不敢按满 350ms |
| 0–350ms | 等待（阅读态） | 阈值 **350ms**（与 Hero 平台药丸的长按重排同值，全站只教用户一个数字） |
| <350ms 抬手 | 取消 | 弹回 `1`，`--motion-instant`；**相位直接清干净**（短按不经过"落位"，否则会留一条 `transition` 在卡片上）；**点击语义照常触发**（优质投稿的行点击不能被长按吃掉） |
| <350ms 就移动 | **取消这一次手势** | 让位给原生滚动/选择（`isDrag` 6px 之外才算移动） |
| 350ms / 按下（编辑态） | **拿起** | `scale: 1 → 1.055`（`--ease-pop`，一次性小过冲）+ 阴影升到 `--pcard-shadow-lift` + 抬起 `z-index` + `will-change: transform` |
| 拿起后 | **跟手** | 位移 `transition: none`，按 `pointerDelta − cellDelta` 1:1 跟指针（**不吸附**） |
| 同帧 | 进入编辑态 | 其余卡片 → 编辑态档阴影；网格辅助线淡入；抓手/缩放手柄出现 |
| 位移 < 6px | 不算拖动 | 抬手时按"点击"处理（防抖阈值） |

> **为什么要 `pointerDelta − cellDelta`**：卡片仍住在自己的格子里（不动渲染结构），
> 格子会随拖动一格一格地换位；减去格子自身的位移，屏幕上就正好是"跟着手走"。
> 这条算式是纯函数（`liftOffset`），可以单测 —— 手感这件事不该靠肉眼调。
> 它等价于一条**可断言的恒等式**：**卡片视觉位移 ≡ 指针位移**（跨格时也成立）——
> 少了 `cellDelta` 会多走一格、完全没跟手会走 0，两种错法都当场露馅（探针就是这么判的）。
>
> **⚠️ 2026-09-18 用户报「按住移动时明显闪动、像是每一点移动都在吸附不同的网格」，
> 量出来是两个原因叠加**（详见 §5.6）：
> ① `cellDelta` 的"当前格位"取错了来源 —— 没跨格的那一帧用了手势开始时的快照（`d.base`），
> 于是补偿凭空少一整格：跨格那一帧恰好正确、**下一帧就跳走**，来回闪；
> ② 长按拾起会顺手进编辑态，而操作提示原来在**画布上方**，于是拾起那一瞬间整块网格被推下去 28px。
> 两条都已修，并各自变成一条断言（连续小步跟手误差 ≤2px / 拾起前后画布上缘不变）。

### 5.2 其他卡片退避（Retreat）—— **P4c 已落地**

| 时间 | 发生什么 | 细节 |
|---|---|---|
| 跨格瞬间 | 模型重排 | 仍是既有的 `moveCard` + `pushDown`（**不新增布局口径**） |
| 同帧（绘制前） | **I**（Invert） | 在 `useLayoutEffect` 里量新位置、打上 `transform: translate(dx,dy)` 且 `transition: none` —— 与新布局落在同一帧 ⇒ 用户看不到中间态 |
| 下一帧 | **P**（Play） | 撤掉 transform 并登记 `transition: transform <ms> var(--ease-standard)` ⇒ 卡片从旧位置滑到新位置 |
| 时长 | 由距离决定 | 一行内 220ms（`--motion-base`），跨 ≥2 行 320ms（`--motion-slow`） |
| 收尾 | 清干净 | 过渡走完删掉条目（不把 `transition` 常驻在卡片上） |
| 拖动卡 | **不参与 FLIP** | 它由 5.1 的跟手位移驱动；两条动画打架会看出"被拽回去" |
| 形状 | **只位移，不缩放不淡出** | 被挤走的卡一缩放就像"消失了"，用户会以为卡片被删了 |
| **归位**（用户 2026-09-18 拍板） | 让位与归位**都**动画 | 拖动卡挪回去时，邻居带着**反向**补偿滑回原位 —— 只做让位的话，"升回去时瞬移"这种半拉子实现照样能绿 |
| reduced-motion | **整个 FLIP 跳过** | 减少动效下不做退避动画（也就不测量），卡片直接落在新位置 |

**实测抓到的两个真 bug**（都是"差一点点"那类，肉眼很难举证）：

1. **`cellsFromPx` 的口径不一致**：x 除的是**列宽**、y 除的是**格距**（行高 + 间隙）⇒
   "拖 45% 的列宽"就被算成跨了一格 —— 缩放手柄只拖一点点，卡片整列跳。
   修法：两个参数都改成**格距**（参数名带 `Pitch`，传错的人在调用处就看得见）。
2. **"拖出去再拖回来"时模型不回退**：原来判"要不要重算布局"是 `if (dx || dy)`（指针有没有跨格线），
   而拖回原点时 `dx=dy=0` ⇒ 模型停在被拖出去的那一格，**松手时卡片凭空跳一格**。
   修法：拿**目标格位**与**当前模型格位**比（`live.x !== tx || live.y !== ty`）。

两条都是**新护栏先红**抓出来的（`--motion-cards` 的缩放段与归位段），不是事后补的。

### 5.3 落位（Drop）

| 时间 | 发生什么 | 细节 |
|---|---|---|
| pointerup | 结算 | 用最后一帧的布局落库（既有口径：整版 PUT，失败回滚 + 说明） |
| 0–220ms | **落下** | 跟手位移 → `transform: none`（220ms `--ease-emphasized`）+ `scale 1.055 → 1` |
| 0–220ms | 阴影收敛 | lift → 编辑态档 |
| 无二次回弹 | —— | `scale` 落到 1 就停；**不做橡皮筋**（§7 反模式第 1 条） |
| 失败回滚 | 滑回原格 | 同一条过渡把卡片送回旧位置，配既有那句"已恢复上一次的排布" |

### 5.4 缩放（Resize）与增删（P3b）—— **P4c 已落地（缩放）**

- **缩放**（用户 2026-09-18 拍板：连续 px 跟手 + 跨格吸附）：手柄拖动期间
  **视觉尺寸按指针 1:1 走**（内联 `width/height`，夹在"最小尺寸 3 列 × 2 行"与"网格右/下边界"之间），
  **模型只在跨格时改**（`resizeCard` + 推开）—— 离散的格位才好落库，连续的视觉才不跳。
  松手时撤掉内联尺寸（登记 `width/height` 过渡滑到吸附值）。尺寸动画是规格 §1 约束 2 的**刻意例外**。
- **新增卡片**：`scale .94 → 1` + 淡入 180ms，其余卡让位（FLIP 同款）。
- **删除卡片**：`scale 1 → .94` + 淡出 140ms `--ease-exit`，随后让位。

### 5.5 reduced-motion（`prefers-reduced-motion: reduce`）

位移与缩放一律归零，只保留 **≤100ms 的透明度变化**（沿用项目既有先例）；
**信息不减**：长按阈值、编辑/拖动/保存的能力全部保留，只是没有过程动画。

**⚠️ 唯独跟手不能关**（P4b 落地时的口径）：跟手位移是**输入反馈**，不是装饰动画 ——
把它一起关掉等于"拖动失灵"，那不是"减少动效"，是把功能拿走了。所以 reduced-motion 下：
缩放归零（`pressScale = liftScale = 1`）、落位不滑行（`settleMs = 0`，直接到位），
但**跟手仍然 1:1**（探针专门有一条断言盯它）。

**为什么这条口径必须在 TS 里再写一份**（`motion.ts::motionPlan`，而不是只在 CSS 的
`@media` 块里关掉）：拾起的 `scale()` 是**内联**写上去的，而内联样式的优先级高于媒体查询 ——
CSS 里写 `transform: none` 也压不住它。所以"要不要缩放"必须在**写内联样式的那一侧**决定；
CSS 那一半只管 hover 与过渡。两处口径**必须一致**，各自都有断言。

### 5.6 「按住移动时闪动」的两个原因（2026-09-18 用户报障 → 量出来的）

用户原话：「按住并移动卡片的时候有明显的闪动和位移，像是鼠标每一点移动都让这个卡片在吸附不同的网格」。

**没有靠猜**：新加一条**轨迹诊断**（`ui_probe.py --motion-trace`）—— 模拟真鼠标那样小步连续移动 26 次
（每次 8px），逐步量「卡片中心实际位置 vs 期望位置（本段起点 + 指针位移）」。它一跑就把两件事分开了：

| 现象 | 根因 | 修法 |
|---|---|---|
| 误差在 `0` 与 `±一格`（70.8 / 141.7 / 212.5px）之间来回跳 | **`cellDelta` 的"当前格位"取错了来源**：没跨格的那一帧取的是手势开始时的快照 `d.base`（卡片早就不在那一格），于是 `cellDelta = 0`、补偿凭空少一整格。跨格那一帧恰好正确 ⇒ 一帧对一帧错 = 闪 | 当前格位只有两个合法来源：这一帧改过布局 ⇒ 用新布局；没改 ⇒ 用**正在渲染的那一版**（`cardsRef.current`） |
| 每一步都恒定偏 `28px`（纵向） | **长按拾起顺手进编辑态**，而操作提示原来在**画布上方** ⇒ 拾起那一瞬间整块网格被推下去（行高 16 + gap 12） | 提示移到**画布下方** ⇒ 进编辑态不再改变网格上方任何东西的尺寸 |

两条都补了断言（都在 `--motion-cards` 里，前者是**逐步**判、不是抽两点）：

- **连续小步跟手**：12 步 × (8, 3) px，**每一步**误差都要 ≤2px（抽两点量会漏掉"跨格后下一帧补偿丢了"）；
- **进编辑态不许推动画布**：拾起前后画布上缘位移 ≤1px。

> **教训（比这两个 bug 更值钱）**：抽两点采样是**假绿**的温床 —— 第一版 `--motion-cards` 只量了
> "同格内 +30" 和 "跨一格"两步，恰好一个不跨格（模型确实还在原点 ⇒ 用 `d.base` 也对）
> 一个跨格（用了新布局 ⇒ 也对），于是**两个都绿**，而真鼠标的每一步都在错。
> 手感类断言要**按真实输入节奏连续采样**，并把误差写成数字（这次是 212.5px vs 0.3px）。

### 5.7 拖到边缘自动滚动 / 网格向下拓展（P4d，2026-09-19 需求）

> **用户原话**：「我抓着卡片**接近底部**的时候网格**自动向下拓展**，同时**自动向下翻页**，
> 反之光标在顶部也一样；这个逻辑在**拖动右下角改变大小**的时候同样适用 —— 即按住时光标靠近底部，
> 网格自动拓展，界面也向下滚动，**与此同时不要发生闪动和错位**」。

#### 一句话原则

> **滚动与跟手必须是同一套坐标。** 把"内容坐标位移"作为唯一真值喂给模型与补偿 ——
> 于是"卡片永远在手指底下"是**算出来的恒等式**，不是调出来的手感。

#### 写方案前核实过的三个事实

1. **滚动容器 = `.os-scroll`**（`OverlayScroll` 已提供 `scrollRef` 透传，视图目前没接），
   `overflow-y:auto`；`.board-view .os-scroll` 是 flex column + `padding: 12px 18px 18px` + gap 12；
2. **画布高度本来就是内容驱动的**（`grid-auto-rows`，没有写死高度）⇒ 卡片往下走，网格自己就长高
   —— "向下拓展"这条**本来就成立**，缺的只是"看得见 + 滚得动"；
3. `OverlayScroll` 监听 `scroll` 事件同步拇指位置 ⇒ 程序化 `scrollTop` 会让自绘滚动条自动跟上（顺带给出"正在翻页"的视觉反馈）。

#### 核心算式（本方案的全部难点）

设 `P` = 指针相对手势起点的位移（视口坐标），`S` = `scrollTop − scrollTop₀`（向下为正）。
定义**内容坐标位移**：

```
D = P + S          ← 唯一真值
```

然后**只喂 D**：

| 用途 | 算式 |
|---|---|
| 模型目标格位 | 起点格位 + `cellsFromPx(D)`（吸附） |
| 跟手补偿 | `transform = D − cellDelta`（`cellDelta` = 模型格位相对起点的像素位移） |

把两式代进"卡片视口位置 = 内容位置 − scrollTop + transform"，`S` 正好抵消 ⇒
**卡片视口位置 ≡ 起点 + P**（恒等于手指位置，与滚了多少无关）。
⇒ 滚动过程中**不可能漂、不可能跳** —— "不错位"是数学结论，不是调参结果。

**反过来说**：漏掉 `S` 这一项，卡片就会在滚动时滞后/超前**恰好一个滚动量**。
这与 devlog/150 那个 bug 同类：**补偿量的来源必须与渲染所用的坐标一致**。

#### 驱动方式：滚动是主量，下探是它的结果

每个驱动周期（rAF + 定时器，见下）：

1. 由指针纵坐标算速度（**纯函数**）：`speed = ramp(pointerY, 容器上缘, 容器下缘, 触发区, 最大速度)`；
2. `scrollTop += speed × dt`（夹在 `[0, scrollHeight − clientHeight]`）；
3. `S` 变 ⇒ `D` 变 ⇒ 模型下探 ⇒ 网格长高 ⇒ `scrollHeight` 变大 ⇒ 下一帧能滚更多 ——
   **正反馈自洽**，不需要另写"拓展"逻辑。

> **⚠️ 为什么不能反过来**（"先让模型下探，再把视图滚过去"）：网格按 **96px 整行**长高，滚动却是连续的 ⇒
> 模型一动就是一整行、滚动只走几像素，卡片会在"手指底下"与"差一行"之间来回跳 —— 正是要避免的闪动。
> **让连续的量的当主时钟**，离散的量（格位）只是它的函数。

#### 必须解决的"鸡生蛋"：滚动跑道

内容短的时候 `scrollHeight == clientHeight` ⇒ `scrollTop` 动不了 ⇒ `S` 不涨 ⇒ 模型不动 ⇒ 网格不长 ⇒ 永远动不了。

**解法**：编辑态在画布底部留一条**跑道**（滚动体 `padding-bottom`，默认 **240px ≈ 2.5 行**）：

- 一进来就有 240px 可滚 ⇒ `S` 立刻能涨 ⇒ 模型下探 ⇒ 网格长高 ⇒ 跑道跟着内容往下移 ⇒ **永远够用**；
- 净消耗 = `d(网格高)/dt − d(scrollTop)/dt`，而网格平均长高速度 ≡ 下探速度 ≡ 滚动速度 ⇒ **平均净消耗 0**；
  网格按整行跳，瞬时最多吃掉一行（96px）⇒ **跑道 ≥ 2 行就不会见底**（取 240 留余量）；
- 跑道是滚动体 padding ⇒ **不影响网格上缘**（"进编辑态不推动画布"那条不变量继续成立）。

#### 边界与手感口径

| 口径 | 取值 | 理由 |
|---|---|---|
| 触发区深度 | **上下各 64px** | 与常见桌面拖拽一致；太浅要瞄、太深容易误触 |
| 最大速度 | **900px/s**，按进入深度线性 ramp（区边缘 0 → 贴边最大） | 进入即动、越靠边越快；**不设"停留延时"**（有延时会觉得卡住） |
| 指针移出容器上/下缘 | 按该方向**最大速度**继续 | 标准行为：拖到窗口外仍继续翻 |
| 横向 | **不做** | 12 列恒等于容器宽，没有横向可滚的东西 |
| reduced-motion | **照常自动滚动** | 这是功能不是动画；关掉等于功能缺失 |
| 缩放手柄 | **同一套**（`D` 的纵向分量进 `visH`） | 用户明确要求"改大小同样适用" |
| 松手 / 取消 | 立刻停表；跑道保留（编辑态） | 避免手势结束时内容高度突变 |
| "翻页"语义 | **连续滚动**，不做整屏跳页 | 跳页会丢掉参照物（卡片会瞬间离开手指） |

#### 三条"不许闪"的实现纪律

1. **FLIP 用内容坐标量**：`captureRects` 与 `useLayoutEffect` 里的 rect 都加 `scrollTop`
   ⇒ 任何滚动时序都不会污染退避补偿（P4c 那条 `settleTransforms` 的教训同样适用）；
2. **滚动循环只写两样东西**：`scrollTop` 与手势状态（跟手补偿）；不碰任何布局属性；
3. **落库仍用模型格位**（本来就是内容坐标）⇒ 松手后卡片落在它**看起来**所在的位置。

#### ⚠️ 驱动方式：**rAF + 定时器双驱动**（实测逼出来的）

第一版只用 `requestAnimationFrame`，结果**探针里完全不动**（`scrollTop` 恒为 0）。
量了一下：**虚拟时间下 rAF 几乎不被服务 —— 400ms 里只被叫 0–1 次**。
而"探针看不见的行为等于没护栏"（本仓老规矩），所以改成：

- **rAF 为主**（真机上跟帧率对齐、后台自动停）；
- **定时器兜底**（`setTimeout` 24ms）—— 两种环境下都被服务，于是这条功能可被机器判；
- 两者共用一个 **8ms 时间闸门** ⇒ 不会滚成两倍速。

> 同一批还踩到两个"探针自己"的坑，一并记下：
> ① 合成 `pointermove` 必须派发在**网格**上（组件把监听挂在 `.board-grid`），
> 派发到它的祖先（滚动体）不会向下冒泡 ⇒ 事件根本到不了 handler；
> ② 两段手势之间必须**等保存落地**（`busy` 期间 `beginDrag` 直接返回，不接新手势）——
> 否则第二段"按住"按不下去，相位是 `idle`，看着像"跟手失效"。

#### ⚠️ 向上拖的"塌陷"与高度下限（2026-09-19 用户报障 → 量出来）

用户原话：「向下滚动的时候很正常，但是**从下面的页面尝试滚动上来就会首先瞬间回到顶部，并且闪动**」。

量出来是一条**正反馈塌陷**：往上拖 ⇒ 被拖的那张卡（往往就是最高的那块内容）行号变小 ⇒
**网格变矮** ⇒ 内容变短 ⇒ `scrollTop` 被浏览器夹回 ⇒ `S` 掉 ⇒ `D = P + S` 掉 ⇒ 卡片又被带着
往上走 ⇒ 再夹一次……实测向上拖时**网格从 1332px 缩到 852px、`scrollTop` 单跳回掉 120px**。
向下拖没有这个问题（内容只会变长，越滚越有余量）。

**解法：编辑态把网格高度钉在"本次编辑会话见过的最大值"上（只增不减）** —— 内容不再变矮，
夹取无从发生，向上滚动因此平滑；它同时正好对上用户的直觉（"网格向下拓展"：拓展出来的区域
就是工作台，排布期间不回收）。**退出编辑态时收回**（一次收尾，且是用户主动的动作）。

**⚠️ 一个 flexbox 陷阱（修这条时踩到）**：网格是滚动体（flex column）的子项，默认靠
`min-height: auto` 保护"不被压扁"；而**一旦给它写显式 `min-height`，`min-height: auto` 就被覆盖**
⇒ 网格会被压到视口高、卡片从盒子里溢出来（视觉上"网格没跟着长高"，实测网格恒为 564px）。
所以同时给 `.board-grid` 写死 `flex: none`：画布只按内容（与高度下限）决定尺寸，永不参与压缩。

#### 实测结果（`--motion-scroll`，1440 宽）

```
容器 106–621（高 515）· 可滚范围 366px · 400ms 内 rAF 被服务 0 次
底部停住：scrollTop 0 → 862（862px）· 模型行 0 → 14 · 网格高 564 → 1620 · 同步误差 0px
顶部停住：scrollTop 882 → 317（-565px）· 同步误差 0px · **网格高 1620 → 1620（最低 1620，不塌陷）**
抬手后：317 → 317（停表）· 缩放手柄：滚 482px、高 3 → 10
```

**向上那一趟的两条判据**（都在这条探针里，且都是"因果"级的）：

1. **这一趟里网格高度不许缩**（`gridHMin ≥ gridHFrom − 1`）—— 塌陷的**原因**；
2. **`scrollTop` 的回掉速率 ≤ 0.9px/ms**（= 上限速度 900px/s；判速率而不是绝对量，
   因为虚拟时间下采样间隔会跳，绝对量没有可比性）—— 塌陷的**现象**。

## 6. 编辑态与阅读态的其余差别（沿用 R37-P2b，只调档位）

- **纯函数单测**：`autoScrollSpeed`（中点 0 / 进下区为正且 ramp / 贴边与出界为最大 / 上区为负 / 触发区为 0 时不滚）
  + `liftOffset` 加滚动项后的用例（滚动 S ⇒ 补偿 −S ⇒ 视口不动）。
- **探针**（`--motion-cards` 扩一段；另加 `--motion-scroll` 端到端）：

| # | 判据 |
|---|---|
| 1 | 指针停在底部触发区 600ms ⇒ `scrollTop` 至少前进 200px |
| 2 | **同步性**：全程 `\|卡片中心 − (起点 + 指针位移)\| ≤ 2px`（"不错位"的判据，与 devlog/150 同一把尺子） |
| 3 | **下探**：`data-card-y`（模型行号）随滚动单调不减 |
| 4 | **拓展**：网格实高（`data-board-h`）随之增长 |
| 5 | **顶部对称**：指针回到顶部区 ⇒ `scrollTop` 减少 |
| 6 | **缩放**：拖右下角手柄时同样滚，且 `data-card-h` 增长 |
| 7 | **松手停表**：抬手后 600ms 内 `scrollTop` 不再变化 |

> 探针环境注意：滚动由 rAF 驱动，虚拟时间下 rAF **会被服务**（P4b 实测）；
> 但 `--reduced`（`--force-prefers-reduced-motion`）下浏览器**不产帧** ⇒ 那一档跳过自动滚动那几条，
> 并**打印跳过原因**（不静默）。

## 6. 编辑态与阅读态的其余差别（沿用 R37-P2b，只调档位）

| | 阅读态 | 编辑态 |
|---|---|---|
| 阴影 | `--pcard-shadow` | `--pcard-shadow-edit`（拿起时 `--pcard-shadow-lift`） |
| hover | 上浮 2px + `--pcard-shadow-hover` + 标题不变色 | **取消 hover 上浮**（与"拿起"语义冲突，一律不动） |

## 7. 反模式清单（明确不做）

- ❌ 橡皮筋回弹、第二次弹跳（"拿起来"那一次 `--ease-pop` 是**唯一**的过冲）
- ❌ 循环动画（呼吸、闪烁、常驻 loading 光带）
- ❌ 被挤走的卡片做缩放/淡出（看起来像被删了）
- ❌ 拖动时给拖动中的卡加"位移动画"（手会感到迟滞）
- ❌ 动画文字本身（文字只淡入淡出；`scaleX` 压扁文字是明确禁止项）
- ❌ 用动画掩盖没数据（骨架仍按 R36 口径：同尺寸占位、不到位不加文案）
- ❌ 拖动时重新取数（手势期间卡片内容不重挂载）

## 8. 不变量清单（让"手感"可断言 —— 探针照着写）

| 不变量 | 判据 | P4b 实装 |
|---|---|---|
| 相位链 | 按下 `pressing` → 长按 `lifted` → 抬手 `settling` → `idle`；**短按直接回 `idle`** | ✅ `--motion-cards` |
| 拾起缩放 | `1 < scale ≤ 1.055`（「轻微」档）；按下有 `scale(.985)` 的即时反馈 | ✅ |
| **跟手 1:1** | **卡片视觉位移 ≡ 指针位移（≤2px）**，跨格时同样成立 | ✅（同格 + 跨格各一段） |
| **连续小步跟手** | 12 步 × (8,3)px 的**每一步**误差都 ≤2px（抽两点会假绿 —— 见 §5.6） | ✅ P4b 修 |
| **进编辑态不推动画布** | 长按拾起（顺手进编辑态）前后，画布上缘位移 ≤1px | ✅ P4b 修 |
| 短按无害 | 短按后相位 `idle`、无内联 `transform`；**迟到的长按定时器不许把卡片拿起来** | ✅ |
| 落位收敛 | 落位那一刻登记了 `transition-duration = 0.22s`；落定后无内联 `transform` / `will-change` | ✅ |
| 两态语义 | 阅读态按下 = `pressing`；编辑态按下 = `lifted`（`--board` 的回归就在这条上） | ✅ |
| **退避与归位** | 跨格后被挤开的卡有 FLIP 补偿（`data-flip`）且**登记了过渡**；补偿量是**格距/行距的整数倍**；拖动卡**不许有**；挪回去时邻居带**反向**补偿（归位） | ✅ P4c |
| 落定无残留 | 落定后**所有**卡的 `data-flip` 与内联 `transform` 都清干净 | ✅ P4c |
| 缩放跟手 + 吸附 | 拖不到半格 ⇒ 实渲染尺寸变了而**模型格数不变**；拖过一格 ⇒ 模型 +1；松手后内联尺寸清干净 | ✅ P4c |
| reduced-motion | 缩放 = 1、落位无过渡、**不做 FLIP**，而跟手仍 1:1 | ✅ `--reduced` 档 |
| 高度恒等 / 不重叠 / 不越界 | 沿用既有断言（读模型真值，不受动画影响） | ✅ 默认三档 |

> **⚠️ 尺子的一条硬限制（P4b 实测，P4c 用到）**：无头浏览器跑在
> `--virtual-time-budget` 下时 **CSS 过渡不推进** —— `getAnimations()` 里过渡是 `running`，
> 但 `currentTime` 恒为 `0`，`getComputedStyle().transform` 于是**永远停在过渡起点**
> （按下时读到 `1`、落位后还读到拾起时的矩阵，一度看起来像"位移残留"）。
> 所以动画类断言只能判两件事：① **我们提交了什么**（读 `element.style.transform` 内联值 ——
> 这条把"实现没清干净"和"尺子读不到"分开了）；② **过渡有没有登记**（读 `transition-duration`）。
> 想看动画真的怎么走：用调测页 0.25× 慢放（见 §11），别指望 computed。
>
> P4c 又加了一条**量几何之前的前置动作**：`settleTransforms()`（把在飞的过渡
> `Animation.finish()` 推到终点）。不推的话 `getBoundingClientRect()` 量到的是**动画起点**，
> 被挤开的卡看着还停在原位 —— `--board` 的"零重叠"断言就这么被误判过一次。

## 9. 实现路线的取舍（**已定：A**，2026-09-18）

硬问题：**CSS Grid 的 `grid-column/grid-row` 不可过渡** —— 格子一变，卡片就是"瞬移"。
"连续"只有两条路：要么**动画补偿**（A. FLIP），要么**不用网格、自己算 px**（B. 绝对定位）。

### 9.1 逐环节对比（顺滑度）

| 环节 | **A. FLIP + 跟手偏移** | **B. 绝对定位画布** |
|---|---|---|
| 拖动卡跟手 | 写 `transform`（无过渡，取整到整像素）⇒ 合成器可承担、**不触发布局** | 写 `left/top`（无过渡）⇒ **每帧触发布局**（卡片自己 + 容器） |
| 其他卡退避 | `transform` 过渡 220ms ⇒ 合成器友好；**代价是每次跨格读一次 rect**（一次强制重排，3–10 张卡约 0.5–2ms） | `left/top` 过渡 220ms ⇒ **整段动画每帧都在布局**（主线程），卡越多越重 |
| 落位精度 | 终点 = 网格自己的 layout 结果，`transform` 归零 ⇒ **像素级无误差** | 终点 = 我们算的 px；列宽 58.83px 非整数 ⇒ 可能差 **±0.5px**（靠四舍五入兜） |
| 缩放 | 手势期间内联 `width/height` 覆盖网格 —— **这一项两条路一样贵**（尺寸动画本来就要布局） | 原生 `width/height` 过渡，写法更直接 |
| 打断 / 连续跨格 | 支持：按卡片**当前视觉位置**重新补差；速度不保留（与 B 相同） | 支持：CSS 过渡天然从当前值继续 |
| 文字清晰度 | 分数像素位移期间文字被重采样（略糊）⇒ 用整像素取整规避 | 分数 `left/top` 同样让文字落在分数位置（略糊）⇒ 同样靠取整 |
| 探针 / 断言 | 存在**过渡中间态**：几何断言必须读模型属性（§8 已把这条定成纪律） | 无中间态，断言直接读样式值，最省事 |
| 拖动帧成本 | 只写 transform；跨格那一帧多一次重排 | 每帧布局（拖动与退避都算） |

### 9.2 两条容易被忽略的真相

1. **B 的"白送动画"是更贵的那一种**：`transition: left/top` 动的是**布局属性**，
   动画期间每帧都要重新布局、交不到合成器；A 的退避动的是 `transform`，
   可以只在合成器上跑 ⇒ **退避这一段 A 反而更顺**（react-grid-layout 一类库最后都在
   transform 上做文章，原因就在这）。
2. **A 唯一的真风险是"闪一帧"**：补偿 transform 的时机若落在**浏览器绘制之后**，
   用户会看到卡片先闪到新格子、再被拉回去。规避办法是确定的：补偿写在
   `useLayoutEffect`（DOM 变更后、绘制前，React 保证同步执行），并用探针把
   "跨格那一帧卡片没有位移"钉死（§8 的"退避可见"判据就是它）。

### 9.3 在你这个规模下，实际会感觉到什么

卡片 3–10 张、内容都是文字与小缩略图、容器 838px（12 列 × 58.83px）——
**两条路的帧率都会是满的**，肉眼分不出谁更快。真正的差别只有三处：

- **落位那一下的精度**：A 像素级落在网格上，B 可能差半像素（长期观感是"偶尔有点毛"）；
- **风险类型**：A 有"闪帧"风险，靠实现纪律压住；B 没有闪帧，但有"每帧布局"带来的偶发掉帧；
- **将来谁承担几何**：A 继续让 CSS Grid 算布局（自动行高、不重叠、不越界都由既有断言守着）；
  B 之后**所有**几何都是我们的代码 —— 容器高度、越界、重叠，一个都不能少。

| | **A. FLIP + 跟手偏移**（推荐） | **B. 绝对定位画布** |
|---|---|---|
| 静止布局 | **CSS Grid 不变**（R37-P1 的选型保住） | 改成 `left/top/width/height` 由 `layoutModel` 算 |
| 退避动画 | `useFlip`（量旧 rect → 补 transform → 归零），约 60 行 | 白送（`transition: left/top`） |
| 拖动跟手 | 拖动卡算 `pointerDelta − cellDelta`（纯函数，不读 DOM） | 直接改 px |
| 探针 | **既有断言全保留**，另加 §8 新判据 | 几何断言要重锚（`grid-column` 两项失效，容器高度改自算） |
| 代价 | 多一个 hook + 一个纯函数 | 丢掉"行高自动、排布自动"的网格能力；卡片越界/重叠要自己保证 |
| 风险 | 低（静止布局一行没改） | 中（渲染层重写 + 全部画布断言重来） |

### 9.4 推荐

**A**。按优先级：① 静止布局一行没改 ⇒ R37-P1 那套几何不变量（高度算死 / 不重叠 / 不越界）
继续是绿的，这批只改观感，不该顺手换地基；② 退避这一段 A 用 transform，比 B 的 `left/top`
更顺；③ 落位精度更高。代价是多一个 `useFlip` hook + 一个 `liftOffset` 纯函数（都能单测），
外加一条必须守住的实现纪律（在 `useLayoutEffect` 里补差）。
