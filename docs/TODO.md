## v0.5.1 「删除检测（墓碑机制）」——本项目的灵魂功能

**问题**：动态从平台消失后，库里只是"数据不再更新"，没有任何标记证明它被删了、何时发现被删。
争议取证时无法区分"还在只是没翻到"和"已被删除"，证据链断在最关键一环。

**需求**：
- Post 新增字段：
  - `last_seen_at` DateTime NULL（最近一次确认仍在线的时间）
  - `deleted_detected_at` DateTime NULL（墓碑：判定已删除的时刻）
- 判定逻辑（挂在 `POST /vtuber/update-posts` 更新未归档动态流程尾部）：
  1. 本次成功抓取返回的 post_id 集合为 S；
  2. 库中该账号未归档帖子 ∖ S = 缺席集合；
  3. 缺席帖子的 `last_seen_at` 早于上一次成功抓取时间 → 视为连续第二次缺席，写 `deleted_detected_at`；
     否则仅刷新失败计数/保持现状（**防单次分页边界或接口抖动误判**）
- 已归档帖子不参与判定（归档语义即"不再追新"）
- 墓碑一旦写入不可被后续抓取清除（除非人工干预）；若某"已删"帖子重新出现，保留墓碑并记录复活时间（可选字段，实现时定）
- 前端：
  - 帖子卡片墓碑角标（灰化处理可选）
  - 归档过滤旁增加「已删除」chip（映射 `deleted_detected_at IS NOT NULL`）
  - 详情抽屉显示时间线：发布时间 / 最后在线时间 / 删除发现时间

**验收**：
- [ ] 模拟删除场景：库中造一条不在返回集合里的未归档帖 → 两轮更新后打上墓碑
- [ ] 单次缺席不打墓碑（防误判用例）
- [ ] 已归档帖缺席不受影响
- [ ] 前端筛选与角标生效

### 实现注意（墓碑特性通用）

- **迁移链纪律**：新增 alembic 迁移后必须同步更新 `app/main.py` 的 `MIGRATION_HEAD`
  （tests 断言其与 alembic head 一致）
- 冷启动快路径依赖版本号判断，勿漏 bump
- 抓取链路改动后跑全量 `pytest`（当前基线 109 passed）

## 远期构想：让作品被看见（二创发现）

动机：一件优秀作品没被最可能喜欢它的人看见是残忍的。病灶是匹配失败，
不是曝光不足——不需要社区平台，需要的是路由能力。

核心洞察：二创天然自带收件人地址——作品关于哪个 V，受众就是喜欢那个 V 的
人。订阅关系、faction 字段、联合投稿多 V 存储就是现成的路由表。

定位约束：做成 DDtoolkit 内的功能，不做平台。无服务器、无账号、无投票货币。

分阶段形态：

1. **编辑精选周刊**——手工挑选，静态推送，零基建验证需求是否真实存在
2. **统计遗珠信号**——小创作者异常互动率（硬币/收藏对播放比例失衡）自动浮现，
   依赖粉丝基数与帖子统计历史的积累
3. **归档涌现信号**——接入 P2P 归档网络后，「多少节点愿意为它花磁盘空间」
   即最诚实的质量票（与上方 P2P 条目合流）

明确不采用：虚拟钱币投票 + 推送权重正反馈（赢家通吃反噬长尾发现；
中心服务器复刻热情退去问题；国内 UGC 合规成本单人不可承担）。

## 明确不做（近期）

- 多用户/云同步：坚持本地优先定位
