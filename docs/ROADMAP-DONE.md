## R13：直播预约记录到直播日历 ✅ 2026-09-15（devlog/088）

> 用户原文（编号按约定重排）：**R13**「动态中包括的直播预约记录到直播日历中」，优先级 低。

**落地结论**：数据链路**早就存在**（动态抓取时 `fetcher._extract_reservation` 落
`posts.body_json.reservation` → `VtuberEventRepo.future_reservations()` 解析时刻/标题 →
`GET /vtuber/{id}/future-reservations`），缺的只是前端没接 —— 所以本批**后端零改动**
（方案里原打算加"全部 V 聚合端点"，核实后确认多余：日历本就是单 V 的）。

**前端四块**：

1. `api.futureReservations(vtuberId, days)` + `types.UpcomingReservation`（与
   `ReservationInfo` 分清楚：后者是动态原始形状，前者是服务端解析结果）；
2. `components/live/useReservations.ts`：**V 级**取数（预约跨账号共用），刻意**不塞进
   `useLiveSessions`**（那份 effect 顺序是契约，devlog/057）；失败**不清空**已有数据；
3. `utils/reservationDays.ts`（纯逻辑，9 条单测）：按天分组（与场次同一 `dayKeyIso` 口径）、
   **徽章优先级 场次类型 > 预约 > 休息/待定**、展示行（最早一条 + 人数 + 多条提示）；
4. `LiveCalendar`：格子加 `.lc-resv`（**不动九类色系**，只在左缘加一道强调粉竖条）、
   计数槽放**预约人数**、有场次的日子预约压成一行小字、hover 浮层顶部单列预约块
   （**只有预约没有场次的日子也能 hover 查看** —— 否则"预约"徽章点不出任何东西）。

**验收**：pytest **401 passed**（+1 路由契约用例）· vitest **153 passed**（+9）·
`ui_probe --reservations` **反向验证过**（把徽章优先级去掉 → 立刻红："预约格徽章是 '待定'"）。

⚠️ **日历签名基线已重取**：`48519bae…` → **`50b78ec0…`**。差异**不是本批代码**——
先问了仓库层"V15 有没有未来预约"（**0 条**，所以我的渲染分支根本没触发），
再对日历格才发现当晚 V15 新落库两场直播（14 日从「休息」变成一场、15 日出现两场）。
判断数据漂移 vs 代码漂移的方法已写进 `docs/DEV-LOOP.md`。

## 未登录可用范围（guest mode）✅ 2026-09-15（devlog/086）

> 用户口径：「我希望用户在没有登陆的情况下也可以尽可能使用所有功能，并明确告知这些功能存在限制。」
> 决策由用户授权我定：**做**，但只开检索路径、内容抓取一律要求登录。

**边界（两态实测，`scripts/capability_matrix.py` + `tests/fixtures/capability_matrix.json`）**：

| 能力 | 未登录 | 依据 |
|---|---|---|
| 本地浏览/搜索/筛选/归档、档案视图 | ✅ | 纯本地 |
| 第三方历史（danmakus / zeroroku） | ✅ | 公开接口 |
| 添加 V 的检索（名称模糊搜 / UID 直查） | ✅ | 匿名 `nav` 也下发 `wbi_img`；`search/type` 匿名 `code=0` |
| 账号信息 / 粉丝数 / 直播状态 | ⚠️ 间歇 | `acc/info` 一次成功一次 `-352`；`stat`/`live` 稳定 |
| 抓投稿与动态内容 | ❌ 要登录 | 匿名 `arc/search` → `-352` → **`HTTP 412 request was banned`**；动态流**直接 412**（IP 级、会持续，**不连累登录态**） |
| 微博内容 | ❌ 要登录 | 匿名 `mymblog` → `302` 登录页 |

**落地四块**：① `wbi` 匿名签名（`allow_anonymous`，只给检索路径；默认严格口径不变）；
② `services/capabilities.py` 能力表（三态 + 用户说明 + 实测依据）+ `GET /capabilities`；
③ **内容抓取闸门**（未登录时 `async_fetch_posts`/`async_fetch_first_screen` 一次请求都不发、
动态名单整条跳过、5 个内容端点 **403**；账号信息与归档不挡）；
④ 前端未登录提示（顶栏「未登录 · N 项受限」入口 + 说明窗先列"现在能做什么"再列受限项 +
`去登录`；批量浮窗与添加 V 浮窗逐项标注，**只标不藏**）。

**验收**：pytest **400 passed**（+24）· `smoke_upstream --cold` **4 ok / 1 skip / 0 FAIL**（匿名能搜到、
内容端点 403、匿名 uid 被拒时 503 而非 404）· 暖态冒烟 **5 ok**（登录态不受影响）·
`ui_probe --capabilities` **绿且反向验证过**（入口一藏即红）· 能力表与实测的**双向契约**用例。

> **两条值得回看的经验**：
> 1. **B 站搜索接口的"静默 0 条"**：缺搜索页请求头时 `code=0` 但结果为空 ——
>    这与"没有这个人"在界面上长得**一模一样**。凡是上游可能"安静地失败"的地方，
>    都要有一条"如实报错"的路径（本批落到 `error`/`hint` + 探针断言）。
> 2. **子资源端点的路由顺序**：`/vtuber/bili-search` 被先注册的 `/vtuber/{vtuber_id}` 吃掉
>    （422 `int_parsing`）→ 改成两段式 `/vtuber/bili/search`。加端点前先看有没有 `{param}` 兄弟。

## v0.5.1 「删除检测（墓碑机制）」——本项目的灵魂功能 ✅（2026-09-05 落地，见 devlog/022）

**问题**：动态从平台消失后，库里只是"数据不再更新"，没有任何标记证明它被删了、何时发现被删。
争议取证时无法区分"还在只是没翻到"和"已被删除"，证据链断在最关键一环。

**需求**：
- Post 新增字段：
  - `last_seen_at` DateTime NULL（最近一次确认仍在线的时间）
  - `deleted_detected_at` DateTime NULL（墓碑：判定已删除的时刻）
- 判定逻辑（挂在 `POST /vtuber/update-posts` 更新未归档动态流程尾部）：
  1. 本次成功抓取返回的 post_id 集合为 S；
  2. 库中该账号未归档帖子 ∖ S = 缺席集合；
  3. 缺席帖子的 `last_seen_at` 早于上一次成功抓取时间 → 视为连续第二次缺席，写 `deleted_detected_at`；
     否则仅刷新失败计数/保持现状（**防单次分页边界或接口抖动误判**）
- 已归档帖子不参与判定（归档语义即"不再追新"）
- 墓碑一旦写入不可被后续抓取清除（除非人工干预）；若某"已删"帖子重新出现，保留墓碑并记录复活时间（可选字段，实现时定→**本次定案：保留墓碑不录复活时间，仅刷新 last_seen_at**）
- 前端：
  - 帖子卡片墓碑角标（灰化处理可选→**已做：封面灰度 + 「已删」角标**）
  - 归档过滤旁增加「已删除」chip（映射 `deleted_detected_at IS NOT NULL`→**本次长在 chips-tools 的独立 toggle，含计数**）
  - 详情抽屉显示时间线：发布时间 / 最后在线时间 / 删除发现时间（✅）

**验收**：
- [x] 模拟删除场景：库中造一条不在返回集合里的未归档帖 → 两轮更新后打上墓碑
- [x] 单次缺席不打墓碑（防误判用例）
- [x] 已归档帖缺席不受影响
- [x] 前端筛选与角标生效
- [x] 额外加固：增量窗口外缺席不判（停止帖边界）；page_limit/网络失败/风控中断不判；增量轮视频帖不判；无基线帖不判

### 实现注意（墓碑特性通用）

  （tests 断言其与 alembic head 一致）
