| 我请求的窗口宽 | Edge 实际给的 `window.innerWidth` |
|---|---|
| 200 | **0**（该段没跑完） |
| **280** | **492** |
| 600 | 576 |

⇒ **无头 Chromium 有最小窗口宽（约 500px CSS px）**，**无法模拟一个真 280 宽的小窗**。

### 这条的三个后果（必须写进批次）

1. **既有那条"按真窗口尺寸量"的段（`ui_probe.py:3856-3894`，用 200×90）是怎么过的？**
   高度 90 是生效的（`max-height` 死锁那条 bug 就是它抓到的），
   但**宽度 200 并没有真的生效**（实测视口 492）—— 该段的注释也承认
   「判据只看**面板内部**（不重叠/三段和），不看绝对坐标」。
   **所以那段验的是"矮窗口下的竖向排版"，不是"窄窗口下的横向排版"。**
2. **A 路线下"280 宽窗口里面板放不放得下"这件事，探针原理上验不到** ——
   因为探针里的视口永远 ≥492，而真窗口是 280。
   ⇒ 这不是新问题，而是**既有的坐标系盲区**（`DEV-LOOP.md:265,271` 记的那一类）**在 A 之下变得更要紧**：
   折叠宽从 200 → 280 后，**窗口宽 == 面板宽**，横向余量归零。
3. **对策**：D1-a 必须**新增一条真机验收项**，并把它写进 `TODO.md` §1.3（那批"只能真机验"的清单）。

## 2. ✅ 真机证据（2026-09-25 用户截图）：**缺陷确认存在**

用户在方案细化后发来真机截图（1920×1080，小窗展开、面板打开、自检条可见）。
我**不靠肉眼**，写了三个脚本量它 —— 结论如下。

### 2.1 自检条逐字读出的三项（`StatusWidgetWindow.tsx:355-362` 的格式）

```
css:flex  bg:rgba(20, 20, 26, 0.94)  bf:N  w/h:200x40  q:-  n:1
```

| 读数 | 含义 |
|---|---|
| `css:flex` | 独立入口的 CSS 加载正常 |
| `bg:rgba(20, 20, 26, 0.94)` | 胶囊底色与 `status-island.css:179` **一致** |
| **`bf:N`** | **无 `backdrop-filter`** —— 与 `devlog/172` 的改动一致（见 §5 那条活漂移：`UI-MAP.md:246` 还写着有 blur） |
| **`w/h:200x40`** | **R1 完成**：折叠胶囊实测 **200×40** |

### 2.2 R3：面板**确实被窗口右缘裁掉 8px** —— 三条独立证据

**证据 ①（像素量测）**：窗口左缘 = 自检条左缘 = **825**（自检条是 `absolute;left:0`），
胶囊中心距窗口左缘 139.5 ⇒ `.widget-shell` 居中反推窗口宽 ≈ **279**（≈280 逻辑 px，缩放 100%）：

| 量 | 实测 | 期望 | 差 |
|---|---|---|---|
| 胶囊宽 | **200** | 200 | ✅ 与自检条自报一致 |
| 面板可见宽 | **272** | 280 | **−8px** |
| 面板左缘距窗口左缘 | **8** | 8 | ✅ 与 `place()` 推导一致 |
| 面板右缘距窗口左缘 | **279** | 288 | **−9px**（被窗口切） |

**证据 ②（目视对照）**：把面板左右缘各裁一块并排放大 6×（NEAREST）——
**左缘有完整圆角 + 描边；右缘没有圆角、没有描边，垂直硬切。**

**证据 ③（算术）**：`place()` 的上界是 `Math.max(8, innerWidth − 280 − 8)`，
窗口宽 280 ⇒ `max(8, −8) = 8`，与下界 8 相等 ⇒ `left` **钉死在 8**，
面板占 `[8, 288]` 而窗口只有 280 ⇒ **右边必然切掉 8px**。三条证据互相印证。

> ⚠️ **注意**：这个 8px 裁切在**现状（折叠 200）**下就已经发生 ——
> 因为展开窗口宽 = `max(200, 280)` = **280**，与 A 之后的 `max(280,280)` 相同。
> 所以**它确实与 A 无关**（§2 原来的算术结论被真机证实）。

### 2.3 用户截图里另外看到的两件事（不在 D1 范围，仅记录）

1. **小窗的静息落点在屏幕顶部中央偏左**，而 `defaultWidgetPos` 写的是**右下角**
   （`y = 屏高 − 40 − 72`）⇒ 用户**手动拖过**（或 D2 的"顶部居中"其实更接近他的实际用法）。
   这对 **D2 是有利证据**：他本来就把它摆在上方。
2. **面板在"向上翻/向下"上是向下展开的**（面板在胶囊**下方**），
   而截图里小窗在屏幕**顶部** ⇒ 向下展开是对的（`downFits` 成立）。逻辑与实测一致。

### 2.4 根因（代码级）

`StatusIsland.tsx:117-136` 的 `place()` 用这个算式定位面板：

```ts
const width = density === 'widget' ? 280 : 340
const centered = r.left + r.width / 2 - width / 2
const left = Math.min(Math.max(8, centered), Math.max(8, window.innerWidth - width - 8))
```

**根因**：上界写成 `Math.max(8, innerWidth − width − 8)` —— 那个 **`Math.max(8, …)` 兜底**
在"窗口宽 == 面板宽"时把上界抬到了 8，而下界也是 8 ⇒ `left` 被**钉死在 8**。
正确语义应是"能夹就夹、夹不下就贴 0"。

### 2.5 归属：**从"D1-a 的副作用"改成"独立的一批 D1-a0"**

| | 内容 |
|---|---|
| **为什么仍要修** | 它是**真缺陷**（面板右缘 8px 被 `overflow:hidden` 裁掉，`status-island.css:343`），且真机上小窗宽 280 ⇒ 8px ≈ **2.9% 的面板宽**，右边缘的圆角与边框会被切 |
| **为什么不塞进 D1-a** | 它**与 A 无关**（上表已证）。塞进去会让"D1-a 的 diff 看起来改了面板定位"，**下一个读 diff 的人会误以为 A 动了这些** —— 而它其实是个独立 bug |
| **修法** | 见 §2.6（已用真机数字验过） |
| **顺带** | 这条**现在就能做**，不需要等 A ⇒ 可以**先做 D1-a0、单独验证、单独提交**，A 之后再无面板定位的干扰 |

### 2.6 修法（**已按真机数字验算**，不是纸上方案）

```ts
// D1-a0：面板宽夹到视口内，夹取上界不再把下界抬高
const width = Math.min(density === 'widget' ? 280 : 340, window.innerWidth)
const centered = r.left + r.width / 2 - width / 2
const upper = Math.max(0, window.innerWidth - width - 8)
const left = Math.min(Math.max(0, centered), upper)
```

**验算结果**（`_tmp_verify_fix.py`，输入用真机实测的 280/200）：

| 场景 | 修前 | 修后 |
|---|---|---|
| 真机实测（窗口 280 · 胶囊 200） | `left=8` 右缘 288 **❌ 裁 8px** | `left=0` 右缘 280 **✅ 完整** |
| A 之后（窗口 280 · 胶囊 280） | `left=8` **❌ 裁 8px** | `left=0` **✅ 完整** |
| 窗口 260（比面板窄） | —— | 面板宽夹到 260，`left=0` **✅** |
| 窗口 340（比面板宽） | —— | `left=30`，**居中不变** ✅ |
| 窗口 600 | —— | `left=160`，**居中不变** ✅ |

⚠️ **验算时我自己先写错了一版**：把 `Math.max(0, centered)` 的输入 `r_left` 写成 0
却期望"居中" —— 而 `r_left` 是**胶囊在窗口内的左偏移**，由
`.widget-shell` 的 `justify-content:center` 给出 = `(窗口宽 − 胶囊宽)/2`。
**输入自相矛盾**才会看起来"回归了"。修正输入后三档全对。
⇒ 执行时注意：**`r.left` 在 A 之后恒为 0**（窗口宽 == 胶囊宽），
但在"窗口更宽"的路径里**不是 0** —— 别把它当常量。

### ⚠️ 为什么这条一直没被发现（值得记）

`ui_probe.py:4001` 有"面板越出视口"的判据（`widgetPanelInViewport`），
但它**跑在小窗段里、且视口是 492 宽**（见 §1 的硬约束）⇒
`pr.right (288) <= window.innerWidth (492)` **恒真** ⇒ **永远绿**。
真窗口 280 宽时它才会红。**这是 §1 那条坐标系盲区的第二个受害者**（第一个是竖向排版那段）。

**而它当时确实红了** —— 只要有人**真机截图**看。事实是：
这个 8px 裁切**从批 5d 起就存在**（那时窗口第一次能 resize 到 280），
**经过 175/176/177/178/179/180/183/185/187/188 十轮真机修复都没被抓到**，
因为**每一轮都在看别的东西**（ACL / 外观 / 布局塌陷 / 胶囊错位）。
⇒ **"判据全绿 + 十轮真机"也不等于没有缺陷**；这次是靠用户随手一张截图 + 我量像素发现的。
