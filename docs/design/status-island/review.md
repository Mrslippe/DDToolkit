## 一、四个项目的形态事实（全部读配置/源码，非转述 README）

| | 窗口 | 折叠态 | 展开态 | **展开时宽度** | 抖动怎么处理 |
|---|---|---|---|---|---|
| **LuckyIsland**（主参考） | 3 窗 3 入口 | compact **720×80** / capsule 240×80 | **720×400** | **不变** | 只在 240↔720 那档需要锚定（`dx=(旧宽−新宽)/2`） |
| **FocuSD**（反向对照） | **1 窗 1 入口** | 岛 320×58（可压到 240） | 岛 560×(306–546) | 岛变、**窗口不变** | **窗口恒 820，宽度永不变** ⇒ 抖动架构性不可能发生 |

## 二、形态：我们的抖动问题有一半是自己选的尺寸造成的

### 现状对照

| | 我们（DDToolkit widget） | LuckyIsland | FocuSD | TokenNote |
|---|---|---|---|---|
| 折叠 | **200×40**（竖胶囊） | 720×80（宽条） | 320×58 | 148×88 |
| 展开 | **280**×面板高 | 720×400 | 560×306+ | 210×175+ |
| 展开改宽吗 | **改**（200→280） | 不改 | 岛改、窗口不改 | 不改 |
| 需要锚定吗 | **需要**（顶边中心） | 仅 240 档需要 | 不需要 | 从屏边重推 |

**核心发现**：我们"展开会横向跳动、所以要顶边中心锚定"这个麻烦，**根源是 200→280 改了宽度**。
LuckyIsland 的条↔展开**同宽只变高**，从根上没有这个问题；TokenNote 同样宽不变；
FocuSD 更极端 —— **连胶囊都嵌在一个宽度恒定的透明舞台里**，横向变化全在 CSS 层。

我们规格 §6 早就写了「**相邻级 = 一次形变**」「一次只动一件事」，
但**尺寸表没有遵守这条**：200×40 → 280×(40+H) **同时**动了宽和高两件事。

### 四条候选路线

| 路线 | 做法 | 代价 |
|---|---|---|
| **A. 折叠宽 = 面板宽** | 折叠改 **280×40**，展开 280×(40+H) ⇒ **只变高** | 静息态从 5:1 变 7:1（更像条）；锚定与 `flipUp` 都简化 |
| **B. 三档** | 200×40 →（**只变宽**）280×40 →（**只变高**）280×(40+H) | 多一个状态；但每步只动一件事，正是 §6 写的 |
| **C. 不动** | 维持 200→280 直接展开 | 锚定逻辑继续背着 |
| **D. 恒定宽透明舞台** | 窗口固定成最大形态，形变全在 CSS（`transform-origin: top center`） | 抖动**架构性不可能发生**；但**必须配鼠标穿透** |

**我倾向 B**，理由：
① 每次形变只动一个维度 —— 这是 §6 已写的原则，不是新引入的；
② 静息态保持够小（200 比 280 更不占屏幕），中间档给的是**悬停预览**（多显示几个字），
比"一悬停就弹整块面板"更接近灵动岛手感；
③ LuckyIsland 的 hover stage 1/2 与之一一对应（`window_policy.rs` 的 `reduce()`），已被真机验证；
④ 锚定只在第 1 步需要，第 2 步天然不需要 ⇒ **我们的锚定代码反而可以简化**。

**A 是更简单的下界** —— 若认为"多一档"不值那个复杂度，A 干净且够用。

⚠️ **D 的代价要看清，不是免费的**：FocuSD 付的是"820×460 透明窗口盖住桌面"，
于是**鼠标穿透从可选变成必需**（12ms 轮询 + 圆角命中测试 + 用实测窗口宽反推 DPI，`lib.rs:1278-1329`）。
我们已有穿透开关但**默认关**；走 D 就要把它翻成默认开并补齐命中测试。

⚠️ **不建议照抄 720 宽**：那个尺寸是为它**7 个功能页**定的，我们的面板是通知列表 + 任务进度，
720 宽会大面积留白。**它的宽度是为它的内容定的，不是灵动岛的普适常数。**

### ⚠️ 一条"抄之前必须先补"的东西

TokenNote 的 `new_x` 每次 resize 后**从屏幕边重新推导**，并专门切断
"程序移动 → `onMoved` → 再移动"的**自激环**（`suppressMovedUntilRef = now + 520ms`）。
**我们没有这一层。** 现在只在 `widgetExpandGeom` 里算一次绝对位置 —— 暂时够用，
但用户原话提过「最好给出可吸附的几个标准位置，例如屏幕顶部居中」：
**一旦做吸附，这个抑制窗必须先有**，否则每次程序化移动都会被 `onMoved` 当成用户拖动再吸一次。

⚠️ 且 TokenNote 自己在这里有个缺口：前端用 `LogicalSize`、Rust 用 `PhysicalPosition`，
`8`/`22` 硬编码且**无 `scale_factor()` 补偿** ⇒ 150% 缩放下留边量偏。**我们若抄要注意单位一致。**

## 三、主题：我的 W1 方案（TODO §1.4）应当被推翻

我们 TODO §1.4 现在写的 W1 是：

> 主窗口 `applyTheme` → `emit('shell:theme')` → 小窗 `listen` → 同款 `applyTheme`

**这条的隐含前提是"主窗口是主题的真源"** —— 那正是 W3 表格里我们自己列为病症的那条
（「主窗口一收进托盘，小窗就没数据可显示」）。把主题也挂到主窗口上，等于把同一个病再犯一遍。

**两条独立证据线指向同一个更彻底的机制**：

| 来源 | 机制 |
|---|---|
| LuckyIsland | `setting_set_and_emit` 写 Rust/SQLite 并广播 `settings://changed`；所有窗口 `onSettingsChanged` 订阅 |
| TokenNote | `app.emit("settings-updated", settings)` **全局广播**（`lib.rs:521`）；widget `listen()`（`widget.tsx:219-222`） |

```
设置写入 → Rust/SQLite（真源）→ 全局广播 → 所有窗口各自应用
```

**没有"谁广播给谁"，只有"真源 + 订阅"。** 好处：
- 小窗不依赖主窗口活着（主窗口关了，主题照旧对）—— 这正是 W3 的病根；
- 任何入口改了设置，另一入口下一帧就跟上，不需要专门的广播协议；
- 顺带把 `widget_enabled` / `widget_click_through` / `widget_hide_fullscreen`
  三项也纳入同一通路（现在它们各自 `usePrefs`，而 `usePrefs` **只在
  `AppSettingsDialog` 里被调用** ⇒ 小窗根本读不到）。

### 可搬的四条（每条都对应一个真 bug 类）

1. **首帧前同步应用 fallback，再异步读持久值纠正**（LuckyIsland `startThemeSync`）。
   否则深色用户每次开小窗都会闪一帧浅色。我们主窗口靠 `index.html` 内联
   `html{background:#ffa2b4}` 顶掉了启动中间态，**小窗没有这一层** —— 这是现成的坑。
2. **解析/监听所有入口共用一份**，并显式防"晚到的 Promise"（`dispose` 幂等 + `disposed` 检查）。
   我们在 R38 批 5 已栽过 StrictMode 双挂载（devlog/180），同一类。
3. **浮窗底色用 `color-mix(in oklch, var(--card) N%, transparent)`**，N 来自设置。
   我们小窗现在是**写死的** `rgba(20,20,26,.94)` —— 深色专用，浅色主题下必然错。
4. **给"浮窗不透明度"一个用户可调设置**（LuckyIsland 是 0.1–1.0，默认 0.7；TokenNote 是
   0.58–1.0，默认 0.82）。这直接回应你「主题要可以更改」—— 桌面浮窗可读性依赖壁纸，
   **没有单一正确值，得让用户调**。

### ⚠️ 毛玻璃：一个我没能解释的矛盾（诚实标注）

**事实三条，机制不同**：

| 谁 | 用什么 | 结果 |
|---|---|---|
| 我们（devlog/172） | **CSS `backdrop-filter`** 在透明 Tauri 窗口上 | 真机实测失败：「只画模糊、不画背景与文字」，一块空磨砂方块 ⇒ 已删，改 α=0.94 实底 |
| LuckyIsland | **CSS `backdrop-blur-xl`**（`blur && "backdrop-blur-xl"`） | 源码在用，README 截图看着正常 |
| FocuSD | **原生 Acrylic**（window-vibrancy → DWM） | **注释里明确放弃**：*"applied to the whole HWND and cannot be reliably clipped by SetWindowRgn, leaving a large blurred rectangle around the island"*（`lib.rs:1157-1175`）⇒ 每个状态主动 `clear_acrylic` |

⚠️ **FocuSD 那条不能用来解释我们的失败**：它说的是**原生 Acrylic**（DWM 层），
我们用/测试的是 **CSS `backdrop-filter`**（WebView2 合成层）——**两种不同机制**。
它只证明"Windows 上让玻璃只作用于窗口的一块子区域本身很难"，与我们的现象无直接因果。

**我原本的假设（DWM frame strip 冲突）已自我否定**：我读了
`strip_dwm_frame_for_widget`（`lib.rs:703-728`），它只做 `set_shadow(false)` +
DWM 圆角偏好；而 **LuckyIsland 的配置里同样是 `"shadow": false`** ⇒ 两边在这一项上一致，
**解释不了差异**。

⇒ **诚实的结论：我不知道为什么同样机制下结果相反。** 可查的方向（未验证，按可疑度排序）：
① WebView2 运行时版本差异；② 窗口尺寸（我们 200×40，它 720×80）；
③ `apply_dwm_corners` 那步我们多做了；④ 我们那次是"透明窗口 + 面板 portal 到 body"的特定组合。
**建议：真机复验一次，一次只改一个变量**（先试"去掉 `apply_dwm_corners`"），
验不过就维持 α 实底 —— 它已经过对比度复算，是安全的下界。

## 四、决策点（需要你拍板，我不替你定）

| # | 决策 | 我的建议 |
|---|---|---|
| **D1** | 形态路线 **A / B / C / D** | **B**（三档，每步只动一个维度）；A 是可接受的简化；D 要先算穿透这笔账 |
| **D2** | 静息态默认落点 | 你原话提过「例如屏幕顶部居中」⇒ 建议**默认顶部居中** + 给吸附位（顶部居中/右下/左上） |
| **D3** | 主题通路 | **推翻现 W1，改"Rust 为真源 + 全局广播 + 各入口订阅"**（顺带收编三项窗口开关） |
| **D4** | 浮窗不透明度 | **做成用户可调设置**（0.58–1.0），默认取一个过对比度门槛的值 |
| **D5** | 毛玻璃 | **真机复验一次（一次只改一个变量）**，不按文档拍板；验不过维持 α 实底 |
| **D6** | 浅色主题 | 现在是**刻意只做 light**。若做，须先把小窗那几个硬编码色收敛成令牌（同 D3 的前置） |
