# 通知汇总：放前端 vs 放后端 —— 收益与风险对比（2026-09-27）

> **背景**：用户问「之前建议搬进前端是为什么来着」——我在仓库里**没有找到**这条记录
> （见本文件 §7：我把搜索过程与结果原样留着，因为"搜不到"本身是一份事实）。
> 既然出处不明，就把它当作一个**真问题**重新评估一次。
>
> **只读分析，未改任何业务代码。** 行号对 `git HEAD` = `0bc291c`（2026-09-27）。
> 承接 `docs/design/notices/content-and-flow-review.md`（内容汇总与流动路径）。

## 0. 结论先行

**取决于一个具体的分支，而不是"哪个更好"：**

| 若你的目标是… | 该放哪 | 理由 |
|---|---|---|
| **主窗口隐藏/最小化/深休眠时，小窗仍然更新** | **后端** | 这是唯一能同时满足"活着"与"单一真源"的位置 |
| **只要求"两个窗口开着时别重复轮询"** | **前端**（现状） | 今天就成立、零改动、零新契约 |

**现状（前端）不是错的，它只是把一个能力关掉了**：它换来了"只轮一次 + 零新契约"，
代价是"主窗口一收进托盘，小窗就停更"。

⚠️ 而且有一条**第三条路**是本仓已经采纳的先例：**前端产生 + Rust 持久化**。
盘占用的提醒（`useLowSpaceNotice`）、主题、位置都走过类似形态。
下面 §5 会说明为什么它在**通知**这件事上不成立。

## 1. 先把"前端"这个词拆开 —— 它是三个不同的位置

这是本次评估最容易糊掉的地方。同一个"放前端"可以是：

| 位置 | 具体是 | 主窗口隐藏时 | 谁能读到 |
|---|---|---|---|
| **F1** 主窗口 React 内（现状） | `TopBar.tsx:460-494` 的 `useMemo` | ❌ **死**（`:188` 提前 return） | 只有主窗口；小窗靠广播 |
| **F2** 前端共享模块 + 各宿主自己拉 | 抽 `useStatusIsland()`，两个入口各自轮询 | ✅ 小窗活着就能拉 | 两扇窗 |
| **F3** 前端产生 + Rust 持久化/中转 | 前端算完交给 Rust 存 | ❌ 产生方死了就没新的 | 两扇窗（但内容是旧的） |

**规格 §8 原本要的就是 F2**（`design-status-island.md:130-138` 的 `useStatusIsland()`），
而 `devlog/173:16-18` **有意偏离**了它，理由写在 `UI-MAP.md:295-296`：

> 「抽了只是把轮询搬个家，两扇窗**仍然各轮各的**；**推事件才是真的只轮一次**。」

⇒ 现状选了 F1。**这个偏离本身是合理的**（少一半请求），但它顺手把
"小窗独立性"也一起换掉了 —— 这不一定是当时就想清楚的代价。

## 2. 六个信息源的"可搬迁性"盘点

评估"能不能搬"必须先看数据从哪来。逐个核实（`TopBar.tsx` 为汇总处）：

| 源 | 原始出处 | 后端已有吗 | 搬迁成本 |
|---|---|---|---|
| ① 帖子任务进度 | `GET /vtuber/fetch-status` → `post` | ✅ `scheduler._status` | **零**（已在后端） |
| ② 账号任务进度 | 同上 → `account` | ✅ 同上 | **零** |
| ③ 第三方同步 | 同上 → `external.running` | ✅ 同上 | **零** |
| ④ 风控冷却 | 同上 → `rate_limit` | ✅ `services/rate_limit.py`，**已落 `app_meta` + `load_all` 启动读回** | **零** |
| ⑤ 登录失效 | `GET /auth/bilibili/status` → `needs_login` | ✅ `routers/auth.py:99-119` | **零** |
| ⑥ 完成报告 | `post.last_result`（`seq`/`stored`/`issues`） | ✅ `_set_post_last_result`（`scheduler.py:297`） | **零** |
| ⑦ 瞬时消息 | 页面事件 `ddtoolkit:pill-message` | ❌ **前端独有** | **不可搬**（见 §3） |

**关键事实：7 条里 6 条的数据已经在后端，而且已经通过 `fetch-status` 一次性给出。**
（⑤ 是另一个端点，`TopBar.tsx:385` 每 60s 拉一次。）

⇒ "搬到后端"在**数据可得性**上几乎没有成本 —— 它主要是**搬家**，不是**造源**。

## 3. 真正搬不走的那一块：`pill-message` 与"已读状态"

### 3.1 `ddtoolkit:pill-message` 是**页面内**事件

`utils/appEvents.ts:24` 定义、`utils/pill.ts` 派发、`TopBar` 消费。
派发方是**页面里的组件**：磁盘不足（`useLowSpaceNotice`）、收录完成、复制成功…
它们是**用户在这一刻做了什么**的反馈，**后端不知道**（后端只知道"任务完成了"，
不知道"用户正看着这一屏"）。

⇒ 这类消息天然属于**宿主**。后端搬走 ①–⑥ 之后，⑦ 必须**继续留在前端**，
于是**两个窗口都可能有自己的 `message`** —— 这本身不是问题，
但它意味着**后端方案不是"完全替代"，而是"接管 6/7"**。

### 3.2 更硬的一条：报告的"已读"与"边沿检测"住在内存里

`TopBar.tsx:151-156` 有四个 `useRef`：

| ref | 作用 | 现在住在哪 |
|---|---|---|
| `seenAccSeq` / `seenPostSeq` | 报告去重（记到第几号了） | **主窗口内存** |
| `sawAccRun` / `sawPostRun` | "本轮我是否目睹过它运行" | **主窗口内存** |
| `doneReport`（`:131`） | 报告条目本体；点「知道了」→ `setDoneReport(null)`（`:743`） | **主窗口内存** |

这条逻辑的注释（`:248-250`）写着它的**真实意图**：

> 「只有**轮询目睹过**的任务完成时才弹完成报告 —— 手动快速任务大概率在目睹前结束，
> 不会被重复播报」

⚠️ **这是一个"取决于观察者"的判定**：它依赖"**谁在看、看了多久**"。
搬到后端之后，"观察者"变成**永远在线的进程** ⇒ 它会目睹**每一次**任务完成
⇒ **"快速任务不播报"这条行为会消失**，用户会开始收到本来刻意不报的报告。

**这不是实现细节，是一条会改变用户可见行为的语义变更**，
必须在搬迁时明确决策（是接受？还是把"谁在看"也搬到后端、由窗口注册订阅来表达？）。

**同一位置还有第三处**：`doneReport` 的"已读"是 `setDoneReport(null)` ——
**刷新页面 / 深休眠重建窗口 ⇒ 报告复活**。搬到后端反而**修好**这个问题
（已读可以落 `app_meta`）。这是一处**搬迁的净收益**。

## 4. 收益 / 风险对照

### 4.1 放前端（F1 现状 / F2 各拉各的）

| 维度 | F1（现状） | F2（抽 hook，各宿主自拉） |
|---|---|---|
| 请求量 | **最小**（只轮一次） | **翻倍**（每宿主一次；`UI-MAP.md:287` 明确反对） |
| 主窗口隐藏后小窗 | ❌ **停更** | ✅ 仍更新 |
| 深休眠后 | ❌ **彻底死**（产生方被销毁） | ✅ 小窗仍更新 |
| 新契约 | **零** | 零（复用同一端点） |
| 双真源 | ✅ 一个（主窗口） | ⚠️ **两个宿主各算一份** ⇒ 优先级/去重/ttl 两处实现 |
| 判定一致性 | ✅ 天然一致 | ⚠️ "目睹过运行"要两处各判 ⇒ **同一任务可能两个窗口都报或都不报** |
| 测试 | 已有 12 条（`notificationHub.test.ts`） | 要补"两宿主一致"的判据 |
| 改动面 | 不变 | 中（抽 hook + 两入口接线） |
| 门禁档 | — | **B 档**（`frontend/src/**`） |

⚠️ **F2 有一个反直觉的坏处**：它**看起来**解决了"小窗独立"，
但把"通知的算力"复制成两份 ⇒ **两扇窗可能显示不同的优先级/不同的报告**。
`UI-MAP.md:295` 那句"两扇窗仍然各轮各的"批评的正是这件事。

### 4.2 放后端

| 维度 | 说明 |
|---|---|
| **隐藏/深休眠后小窗** | ✅ **仍更新**（后端是独立进程，`docs/backend/ARCHITECTURE.md` §3.10：「隐藏只影响前端渲染与轮询」） |
| 请求量 | ✅ **最小**（两宿主订阅同一份，甚至可退化成"主窗口也不再轮"） |
| 双真源 | ✅ **真正一个**（优先级/ttl/去重只有一处实现） |
| 已读状态 | ✅ 可落 `app_meta` ⇒ **修好"刷新后报告复活"** |
| 数据可得性 | ✅ 6/7 已在后端（§2） |
| 并发纪律 | ✅ 有现成先例：`_status_lock` + 深拷贝 + 5 条用例（`test_fetch_status_store.py`） |
| 测试 | ✅ `pytest` 现成（A 档，~250s） |
| **"目睹才报"语义** | ❌ **会变**（§3.2）—— 必须显式决策 |
| `pill-message` | ❌ 搬不走，**仍留前端** ⇒ 架构变成"后端 6 + 前端 1" |
| 新契约 | ⚠️ 新增端点/字段 + 前端契约 | 
| 改动面 | **大**：后端新增汇总 + 主窗口改用 + 小窗改用 |
| 门禁档 | **A 档**（碰 `app/`），~250s + 主窗口回归面大 |
| 风险集中点 | **主窗口**（它在用的那条链要换源 ⇒ 回归面最大） |

## 5. 为什么"前端产生 + Rust 持久化"（F3）在通知上不成立

本仓确实有"前端算、Rust 存"的先例（位置、主题、托盘文案）。
但通知与它们有一个本质区别：

| | 位置 / 主题 | 通知 |
|---|---|---|
| 变化频率 | 用户操作时才变 | **后台任务随时在变** |
| 谁产生 | 用户（前端天然知道） | **后端任务**（后端天然知道） |
| 隐藏时要不要更新 | 不要（没人动它） | **要**（这正是需求） |

⇒ 把通知的**产生**放在前端，等于让"最不常活着的那个进程"去算"随时在变的东西"，
再交给 Rust 存 —— **产生方一死，存的那份就是旧的**。
F3 只解决"另一扇窗读得到"，**不解决"谁来产生"**。

**这正是 R20 那条不变量的原话**（`docs/backend/ARCHITECTURE.md` §3.10 第 3 条）：

> 「**必须成功的动作不能建立在可被销毁的一侧**」

## 6. 我的建议：**分两步，先做收益最大、风险最小的那一步**

这个结论不是"选边"，而是**按风险排序**：

| 步 | 内容 | 档 | 收益 | 风险 |
|---|---|---|---|---|
| **S1** | **小窗自己拉 `/vtuber/fetch-status`**（ACL/端口/token **全都已就绪**：`lib.rs:1640-1641` + `widgetMain.tsx:126-129`），并在前端**复用同一份** `notificationHub` 纯函数算出条目 | **B** | 小窗**立刻**能在主窗口隐藏时更新 | 低（只碰小窗入口；坏了不影响主窗口） |
| **S2** | 后端把 6 条汇总成 `GET /vtuber/notices`，**两个宿主都改用它**，`TopBar` 删掉自己的 `useMemo` | **A** | 真正单一真源 + 已读可持久化 + 主窗口也不再轮 | **中-高**（主窗口回归面最大） |

**S1 的关键好处**：它**不需要新契约、不需要后端改动**，就拿到了本次最核心的收益
（"主窗口隐藏后小窗仍然更新"）。代价是**小窗与主窗口各算一份**（F2 的双真源风险），
但因为**算的是同一套纯函数、同一份数据**，实际不一致只可能出现在
"两个窗口的 `now` 差几秒"这种量级 —— 可接受，且**S2 会把它消掉**。

⚠️ **S1 必须先解决 §3.2 那个语义问题吗？** 不必 —— 因为 S1 **不搬家**：
`TopBar` 仍然是产生方（"目睹才报"仍在主窗口），小窗只是**多一个只读视图**。
报告类条目在小窗上仍由主窗口广播；小窗自己拉的是**①–⑤（进度与告警）**这几类
"时间敏感、与观察者无关"的信息。**这正是先把 S1 做掉的第二个理由** ——
它绕开了最硬的语义风险。
