## 0. 三条结构原则（其余都是推论）

| # | 原则 | 为什么 |
|---|---|---|
| **P1** | **产生方住在"永远活着"的一侧** | `ARCHITECTURE.md` §3.10 第 3 条：必须成功的动作不能建立在可被销毁的一侧 |
| **P2** | **`Notice[]` 是唯一的跨宿主契约** | 两个宿主的差异只在材质与尺寸，不在数据 —— 规格 §8「宿主无关」 |
| **P3** | **动作的执行方 ≠ 动作的展示方** | 小窗放不了 `去登录`（它没有路由/弹窗），所以它只**转发**动作 |

**P3 是现在就已经成立的**：`StatusIsland` 的 `onAction` 是**注入的回调**
（`StatusIsland.tsx:15`），小窗注入的是 `relayWidgetAction`（`StatusWidgetWindow.tsx:404`），
主窗口注入的是本地 handler（`TopBar.tsx:579`）。**这个接缝不用改**。

## 1. 目标架构总览

```
┌──────────────────────── 后端（常驻 · 独立进程 · 不受隐藏影响）────────────────────────┐
│                                                                                      │
│  scheduler._status ─┐                                                                │
│  rate_limit (app_meta) ─┤                                                             │
│  auth 登录态 ─┼──► services/notices.py（纯函数：汇总 + 优先级 + ttl）                 │
│  post.last_result ─┘        │                                                        │
│                             ▼                                                        │
│                    GET /vtuber/notices  →  Notice[]（+ now 时间戳）                   │
│                             ▲                                                        │
│  已读/静音状态 ◄── app_meta（新增 prefs 之外的少量键）                                 │
└─────────────────────────────┼────────────────────────────────────────────────────────┘
                              │  HTTP（带 X-DDToolkit-Token）
              ┌───────────────┴───────────────┐
              │                               │
      ┌───────▼────────┐              ┌───────▼────────┐
      │ 主窗口 renderer │              │ 小窗 renderer  │
      │                │              │                │
      │ 拉 /notices    │              │ 拉 /notices    │   ← 各自独立，互不依赖
      │ 自己的 message │              │ 自己的 message │   ← 宿主本地反馈
      │      │         │              │      │         │
      │      ▼         │              │      ▼         │
      │ notificationHub（纯函数，两宿主**同一份**）      │
      │      │         │              │      │         │
      │      ▼         │              │      ▼         │
      │ <StatusIsland density="bar">  │ <StatusIsland density="widget">
      │      │         │              │      │         │
      │   onAction:    │              │  onAction:     │
      │   本地执行      │              │  emit widget:action ──► 主窗口执行
      └────────────────┘              └────────────────┘
```

**与今天的差别只有三处**（其余全部保留）：

| # | 变化 | 今天 | 之后 |
|---|---|---|---|
| ① | 汇总在哪 | 主窗口 `TopBar` 的 `useMemo` | **后端** `services/notices.py` |
| ② | 小窗怎么拿条目 | 等主窗口 `emit('widget:notices')` 推 | **自己拉** `/vtuber/notices` |
| ③ | 已读/静音状态 | 主窗口内存（刷新即丢） | **后端 `app_meta`**（持久） |

⚠️ **`widget:notices` 广播因此可以退役** —— 但**只在 S2 之后**。
S1 阶段它仍然是主窗口进度类条目的通路（见 §5 分步）。

## 2. 契约表（唯一需要新增的东西）

### 2.1 `GET /vtuber/notices`（新增）

```jsonc
{
  "now": 1730000000000,          // 服务端时间戳 —— 统一 ttl 判定口径（见 §4）
  "notices": [                    // 已按优先级排序，或前端自己排（见 §3）
    {
      "id": "rate-limit",
      "kind": "alert",            // alert | progress | report | message
      "text": "上游限流：冷却中",
      "value": "47s",             // 活数据（新增，内容口径定稿）
      "detail": "上游返回 412，正在退避重试",
      "source": "风控冷却",
      "sticky": false,
      "expiresAt": 1730000047000,
      "action": { "label": "去登录", "kind": "login" }
    }
  ]
}
```

**为什么必须带 `now`**：现在两扇窗各自 `Date.now()`（`StatusWidgetWindow.tsx:111` 每秒一跳，
主窗口靠轮询顺带推进）⇒ 同一条 `expiresAt` 在两个宿主可能相差一两秒。
一旦两边都从后端拿，**ttl 判定就有了单一口径**。

### 2.2 `Notice` 模型：**只加两个字段**

| 字段 | 变化 | 依据 |
|---|---|---|
| `value` | **新增** | 内容口径定稿：倒计时/进度独立成槽，自己刷新而不重排文案 |
| `kind: 'music'` | **新增枚举值** | 你定的"音乐先进样例"（它是"持久现场"，优先级最低） |
| 其余 8 个字段 | **不动** | `notificationHub.ts` 现有契约够用 |

⇒ **模型是扩展，不是重做。** 现有 `notificationHub.test.ts` / `statusIslandText.test.ts`
的用例继续有效，只需补新字段的用例。

### 2.3 已读写回（新增）

| 端点 | 用途 |
|---|---|
| `POST /vtuber/notices/ack` | 记 `{id}` 已读 → 进 `app_meta`（`report` 类「知道了」） |

**收益**：修好"刷新/深休眠重建后报告复活"（今天 `setDoneReport(null)` 只清内存，`TopBar.tsx:743`）。

## 3. 各层的职责（谁做什么、不做什么）

| 层 | 做 | **不做** |
|---|---|---|
| `scheduler._status` / `rate_limit` / `auth` | 提供事实（谁在跑、冷却多久、登录是否失效） | 不管文案与优先级 |
| `services/notices.py`（新） | 事实 → `Notice[]`：文案模板、优先级、ttl | 不碰 HTTP、不碰展示 |
| `routers/vtuber.py` | 暴露 `GET /vtuber/notices` | 不写业务（沿用现有分层） |
| `utils/notificationHub.ts` | `pickPrimary` / `isLive` / `phaseClass` 等**纯函数** | 不产生数据（产生方在后端） |
| `StatusIsland` | 渲染 + 动画 + 宿主材质 | 不知道数据从哪来（§8 硬要求） |
| 各宿主的 `onAction` | 主窗口执行 / 小窗转发 | 不解释动作语义 |

> ⚠️ **`notificationHub.ts` 留在前端是刻意的**：它是**纯函数**（`pickPrimary` 取最高优先级、
> `isLive` 判过期），两个宿主都要用，且**后端已经排好序时它仍然有用**（
> 前端要按 `now` 做实时过期过滤）。若把优先级也搬到后端，前端仍需一份兜底 —— 那是双真源。

**排序放哪**：建议**后端排好 + 前端仍按 `now` 过滤**。
后端定"谁优先"，前端定"现在还有效吗" —— 职责不重叠。

## 4. 时间（`now`）的真源

今天两处时间的取法**完全不同**，这是必须收口的地方：

| 宿主 | 现在怎么拿 `now` | 问题 |
|---|---|---|
| 主窗口 | `TopBar.tsx:135` `const now = Date.now()` —— **渲染期直接取** | 它**跟着轮询才更新**（每 3s/10s 一次）；不轮询就冻住 |
| 小窗 | `StatusWidgetWindow.tsx:111` `setInterval(…, 1000)` | 自己跳，与主窗口不同步 |

⚠️ **两处都不是"真源"，而是"跟着各自节奏顺手取的"**。`StatusIsland` 只**接收** `now` 作为 prop
（`StatusIsland.tsx:62`）—— 这个设计是对的（宿主无关），问题只在"谁喂它"。

**目标**：`now` 由**本地 1s 定时器**驱动（两个宿主各一个），
**ttl 用服务端 `now` 作为基准对齐**（即：不在客户端算绝对过期时刻，而是拿服务端下发的
`expiresAt` 与本地时钟比 —— 只要两边时区一致、误差 1s 内，显示与过期都不可见差异）。

⚠️ **必须说清的边界**：两个宿主是**两个独立的 WebView / JS 上下文**，
**不可能共享同一个 `now` 变量** —— 只能共享同一个**口径**。
1s 偏差对"倒计时显示"与"ttl 过期"都不可见，**不值得为它引同步机制**。
（若将来要求秒级严格一致，那才需要服务端下发 `now` 并让两个宿主各自算偏移。）

## 5. 分步落地（S1 → S2）

### S1（前端 · B 档 · 低风险）：小窗自拉**现有**端点

| 项 | 内容 |
|---|---|
| 改什么 | 小窗入口新增：拉 `/vtuber/fetch-status` + `/auth/bilibili/status`，用**现有** `notificationHub` 纯函数算出①–⑤ |
| 契约 | **零新增**（复用现有端点 + 现有纯函数） |
| 拿到什么 | 主窗口隐藏/深休眠时，小窗**仍显示进度与告警** |
| 保留什么 | 主窗口继续推 `widget:notices`（报告类 + `message` 类仍由它来） |
| **绕开什么** | §"目睹才报"那条语义风险 —— 小窗只管①–⑤（与观察者无关的信息） |
| 风险 | 低：只碰小窗独立入口；坏了不影响主窗口 |

**小窗合并两份来源的规则**（S1 的关键细节）：
```
本地拉的 ①–⑤（进度/告警）  +  广播来的 report/message
        ↓  按 (kind 优先级, id) 去重合并
   id 冲突时：**广播方优先**（它是"这一刻的用户反馈"，比轮询结果新）
```

### S2（后端 · A 档 · 中高风险）：后端接管供数

| 项 | 内容 |
|---|---|
| 改什么 | 新增 `services/notices.py` + `GET /vtuber/notices`；主窗口 `TopBar` 删掉自己的 `useMemo`；小窗改拉新端点 |
| 拿到什么 | 真正单一真源；报告"已读"持久化；两宿主请求量最小 |
| **必须先决策** | ①「目睹才报」要不要保留（现状依赖"谁在看"）；②「定时抓取是否占位」（§7 问题 A） |
| 风险 | **主窗口回归面最大**（它现在用的那条链要换源），需要探针 + 既有 `--status-island` / `--tray-suspend` 判据 |
| 退役 | `widget:notices` 广播、`sawAccRun`/`seenAccSeq` 等四个 `useRef` |
