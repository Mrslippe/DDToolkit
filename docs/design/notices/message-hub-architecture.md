## 1. 你的判断是对的，而且仓库里已经有一半证据

### 1.1 现状：前端**已经有一套跨组件事件总线**（8 个事件）

真源 `frontend/src/utils/appEvents.ts`（M4 批次 12，devlog/223）：

| 事件 | 方向 | 今天谁发 → 谁收 |
|---|---|---|
| `pillMessage` | 提示 | 各页面 → `TopBar` |
| `kickPoll` | **"立刻轮询一次"** | 各按钮 → `TopBar` |
| `dataChanged` | 数据变了 | `useVtuberActions.ts:164` → `VtuberSidebar` |
| `fetchIdle` | 任务跑完 | `TopBar` → `VtuberSidebar` |
| `accountProgress` | **账号快照增量**（零请求就地合并） | `TopBar` → `VtuberSidebar` / `PostsPage` |
| `vtuberUpdated` | **单个 V 就地更新（左右栏同步）** | `PostsPage:822` → `VtuberSidebar` |
| `capabilitiesRefresh` | 能力/登录态变化 | `useCapabilities.ts:26`（自打自收） |
| `widgetSeed` | dev-only 注入 | 探针 → 小窗 |

> ⚠️ **这张表里"发的人"几乎全是前端**，只有一个例外：`fetchIdle` / `accountProgress`
> 是 `TopBar` **轮询算出来之后**再发的。⇒ **前端今天是"事件的制造者"，
> 而它制造的依据来自轮询** —— 这正是延迟（§2 第 ④ 段）的来源。

**它的 docstring 写的正是你要解决的痛点**（`:4-7`）：

> 「右栏改了签名要通知左栏（**R33 那条"改了左栏没同步"的事故**）、顶栏抓取完成要通知侧栏与列表」

⇒ **你的设计不是"从零造总线"，而是"把已有的这条总线从页面内升级成跨进程"。**
这大幅降低了风险 —— 语义、命名、payload 形状都已有先例可循，且有测试钉着（`appEvents.test.ts`）。

### 1.2 现状：`kickPoll` 是一条**补偿机制**，正好印证延迟问题

`pages/useVtuberActions.ts:42-44`：

```ts
/** 通知 TopBar 立即轮询一次抓取状态（点击按钮/任务结束时即时反馈） */
function kickPoll() { emit(EVENTS.kickPoll) }
```

每个动作都是「守卫 → `setFetching` → `kickPoll()` → `api` → 提示 → `finally { kickPoll() }`」
（`:7-8` 的注释把这套骨架写明了）。

**这说明**：点击后的状态反馈**本来要等 3s/10s 的轮询周期**，
`kickPoll` 是"人工把这个等待缩短成一次 HTTP 往返"的补丁。
**你的"尽量没有延迟"诉求，指向的正是消灭这条补丁所补偿的那个间隔。**

## 2. 延迟的真实构成（决定该用哪种通道）

按"点击 → 各终点看到"拆开，现状每一段都能量出来：

| 段 | 现状 | 耗时量级 | 能不能消掉 |
|---|---|---|---|
| ① 点击 → 前端发请求 | 同步 | ~0 | 已经是最优 |
| ② 请求到后端 | 本机 HTTP | 1–5ms | 物理下限 |
| ③ **后端处理 + 改内存状态** | `_status` 加锁改 | <1ms | 已经是最优 |
| ④ **其他终点怎么知道** | ❌ **等下次轮询**（3s 忙 / 10s 闲） | **最多 3–10s** | ✅ **这是唯一的大头** |
| ⑤ 小窗怎么知道 | 等主窗口轮询后广播 | 同 ④ + 一跳 | ✅ 同上 |

⇒ **延迟的 99% 在第 ④ 段**：不是"传输慢"，是**"没人告诉它，只能自己定期问"**。

⚠️ **所以"减少延迟"的答案是推送（第 ④ 段），而不是"把中心搬到后端"本身。**
把中心搬到后端但前端仍靠轮询取，延迟**一点都不会改善** —— 这一点必须说清，
否则会做出"搬了家但没变快"的改动。

## 3. 通道选型（这里有一个硬约束）

### 3.1 硬约束：浏览器原生 `EventSource` **不能设自定义头**

后端所有业务端点都要 `X-DDToolkit-Token`（`app/core/api_auth.py:47`、
`main.py:430` 的中间件），公开白名单只有三处（`api_auth.py:50-53`）。

而 **SSE 的标准客户端 `EventSource` 不支持自定义请求头** ⇒ 它**无法带 token**。
三条出路，各自的代价：

| 方案 | 怎么带 token | 代价 |
|---|---|---|
| **A. Tauri 事件通道**（Rust 轮询后端 → `emit` 给前端） | Rust 侧带 token（`backend_manual_running` 已有先例） | ⚠️ 又要 Rust 参与；且浏览器开发态/探针没有 Tauri |
| **B. SSE + token 走 query 参数** | `?token=...` | ⚠️ token 会进 URL → 日志/历史泄露面（`api_auth.py` 的取舍里明确避免了这个） |
| **C. 轮询但"变快"** | 不变 | 延迟仍在，只是小一点 |
| **D. WebSocket** | 首帧带 token 或子协议 | 要引依赖 + 连接生命周期管理 |

⚠️ **注意：本仓的"前端"跑在 Tauri WebView 里，不是浏览器** ——
`fetch`/`EventSource` 都在 WebView 中执行。所以 A 与 B 的可行性取决于
"WebView 里的 JS 能否自己带 token"：**能**（`widgetMain.tsx:126-129` 已在注入 token 给 `fetch`），
所以 **`fetch` + 流式读取（ReadableStream）是唯一"既带 token 又不引依赖"的推送通道**。

| 方案 | 带 token | 引依赖 | 浏览器开发态可用 | 结论 |
|---|---|---|---|---|
| `EventSource` | ❌ | 无 | ✅ | ❌ 不可用（带不了 token） |
| **`fetch` + `ReadableStream`（SSE over fetch）** | ✅ | **无** | ✅ | ✅ **推荐** |
| WebSocket | ✅ | 少量 | ✅ | 备选（双向，但这里只需要服务端→客户端） |
| Tauri 事件 | ✅ | 无（已有） | ❌ | 备选（只覆盖桌面态） |

## 4. 目标结构

```
┌─────────────────── 后端（常驻 · 独立进程）───────────────────┐
│                                                              │
│  事实源：_status / rate_limit / auth / 任务完成 / 直播边沿     │
│                    │                                          │
│                    ▼                                          │
│  ┌──────────────────────────────────────────┐                │
│  │  MessageHub（新，services/messages.py）   │                │
│  │  · 分层消息类型（§5）                     │                │
│  │  · 每类消息的 payload schema              │                │
│  │  · 订阅者注册表（谁连着就发给谁）          │                │
│  │  · 环形回放缓冲（新订阅者补发最近 N 条）   │                │
│  └──────────────────────────────────────────┘                │
│         │                              ▲                     │
│         │ push                         │ 手动动作也走这里      │
│         ▼                              │                     │
│  GET /events（SSE over fetch，带 token）  POST /vtuber/fetch…│
│         │                              （处理完 → hub.publish）│
└─────────┼────────────────────────────────────────────────────┘
          │  一条长连接（每宿主一条）
   ┌──────┴───────┬─────────────┬──────────────┐
   ▼              ▼             ▼              ▼
主窗口        小窗          （未来）        （未来）
 │              │
 │  统一入口 utils/messageBus.ts
 │  （收到 → 按 type 分发到已有的 appEvents 通道）
 │              │
 ├─► ddtoolkit:vtuber-updated   → VtuberSidebar（左栏头像/签名）
 ├─► ddtoolkit:account-progress → VtuberSidebar + PostsPage（右栏卡片）
 ├─► ddtoolkit:fetch-idle       → 各列表页刷新
 ├─► notices 状态                → StatusIsland（顶栏胶囊）
 └─► notices 状态                → StatusIsland（小窗）
```

**关键点：后端 push 之后，前端**仍然**走已有的 `appEvents` 总线分发到各组件。**
⇒ 组件的改动量接近零（它们已经在 `on(EVENTS.x, …)` 了），
**换掉的只是"这些事件的触发源"**：从"轮询算出来"变成"后端推过来"。

## 5. 分层消息类型（你要的"分层规划"）

建议分**两层六类**（下层是上层的子集关系，不是并列）：

### 第一层：领域事件（`domain.*`）—— 数据变了

| 类型 | 何时发 | payload | 现在的等价物 |
|---|---|---|---|
| `vtuber.updated` | V 本体被改（签名/头像/名字） | `VTuber` | `EVENTS.vtuberUpdated` |
| `account.snapshot` | 账号信息抓取有增量 | `AccountSnapshot[]` | `EVENTS.accountProgress` |
| `posts.changed` | 帖子入库/删除 | `{vtuberId, delta}` | `EVENTS.dataChanged` |
| `live.edge` | 开播/下播**边沿** | `{vtuberId, liveStatus, sessionId}` | ❌ **今天只在后端内部消耗**（`scheduler.py:2951-2962`） |

### 第二层：派生通知（`notice.*`）—— 给人看的

| 类型 | 何时发 | 对应 `Notice.kind` | 今天的等价物 |
|---|---|---|---|
| `notice.progress` | 任务开始/进度 | `progress` | `fetch-status` 轮询 |
| `notice.alert` | 风控冷却 / 登录失效 | `alert` | 同上 |
| `notice.report` | 完成任务汇总 | `report` | 同上 |
| `notice.message` | 操作结果瞬时提示 | `message` | `EVENTS.pillMessage` |
| `notice.live` | **开播通知（你要的）** | `alert`（新） | ❌ **不存在** |

⚠️ **`live.edge` 是本次最值得注意的一条**：
开播检测**已经在后端**（`scheduler.py:2951` 的 `edge = acc.live_status != prev_status`），
而且已经分出了"**开播**"这个方向（`:2952` 的 `started`）—— 但它的唯一消费者是
`note_dynamics_activity()`（`:2962`，用来**把动态流恢复满速**），**没有任何面向用户的出口**。
⇒ **"开播通知"不是要新造检测，而是要给它一个出口** —— 这是本设计里**成本最低、收益最直观**的一项。

> ⚠️ 顺带一条**必须继承的既有约束**（`:2955-2957`）：直播边沿的落库
> **必须与 live 字段同一个事务**。原因是两笔独立 commit 时，第二笔失败会让
> `prev_status == acc.live_status` ⇒ **这条边沿被永久吞掉**（日历少一场）。
> ⇒ 往 hub 发布消息**不能在事务中间发**（消息发出去就收不回，而事务可能回滚）——
> **发布点应当在 commit 成功之后**。这是接入 hub 时最容易写错的一处。

## 6. 手动动作也走中心（你的第三点）

```
POST /vtuber/fetch/{id}   ← 前端按钮
      │
      ├─ 后端把它当作一次任务启动
      ├─ 立即 hub.publish({type:'notice.progress', ...})   ← 所有终点立刻看到"抓取中"
      └─ 任务结束 → hub.publish({type:'notice.report' | 'vtuber.updated' | 'account.snapshot'})
```

**这就消掉了 `kickPoll` 那条补丁**：不再需要"前端踢一脚让顶栏去问"，
因为后端**主动**把"我开始了"推给所有订阅者。

⚠️ **必须说清的一个语义细节**：动作的**发起方**与**接收方**可能包含同一个宿主。
小窗点了"去登录"→ 后端处理 → 广播 → 小窗自己也收到 ⇒ **要能识别"这是我发起的"**
（payload 带 `originator`，或前端按请求 id 忽略）。这是分发中心绕不开的一件事。

## 7. 风险与代价（诚实清单）

| # | 风险 | 说明 | 缓解 |
|---|---|---|---|
| **R1** | **长连接的生命周期** | 两宿主各一条 SSE；深休眠会 `destroy()` 主窗口 WebView（`lib.rs:874-877`）⇒ 连接断，要重连 | 断线重连 + `Last-Event-ID` 回放 |
| **R2** | **后端从"无状态 HTTP"变成"持有连接"** | 今天后端是纯请求-响应；SSE 要求它**持有长连接 + 订阅者表** | hub 用环形缓冲，订阅者弱引用；退出时清空 |
| **R3** | **`_status` 是模块级内存** | 后端重启 ⇒ 状态丢 | 与今天行为一致（不算回退）；重要消息可落 `app_meta` |
| **R4** | **探针/浏览器开发态没有 Tauri** | 但 SSE over fetch 在浏览器里**能用**（这是选它的一条理由） | ✅ 探针可断言 |
| **R5** | **多进程/多实例** | 单实例应用（`single-instance` 插件），暂不考虑 | 已有限制 |
| **R6** | **改动面大** | 它是**架构级**改动（A 档 + 跨层） | §8 分步 |

## 8. 分步路径（每步独立可验证）

| 步 | 内容 | 档 | 拿到什么 | 风险 |
|---|---|---|---|---|
| **M0** | 后端加 `GET /events`（SSE over fetch）+ `MessageHub` 骨架；**先只推 `notice.progress`** | A | 验证通道连通 + 探针能断言 | 低（只加不改） |
| **M1** | `live.edge` 接进 hub ⇒ **开播通知**（你要的第一类） | A | 最直观的新能力 | 低（检测已存在） |
| **M2** | 手动动作走 hub（消掉 `kickPoll`） | A+B | **点击 → 各终点零等待**（你的核心诉求） | 中（碰主窗口动作路径） |
| **M3** | `vtuber.updated` / `account.snapshot` / `posts.changed` 改由 hub 推 | A+B | 左右栏/卡片同步不再靠轮询 | **中-高**（碰 R33 那条事故路径） |
| **M4** | 小窗接同一通道，退役 `widget:notices` | B | 小窗独立于主窗口 | 低 |
| **M5** | 后端接管通知汇总（上一版 S2） | A | 单一真源 + 已读持久化 | 中（主窗口回归面） |

⚠️ **M0 之前必须先定三件事**（否则会返工）：
① 消息的**命名与版本**（`type` 字符串要不要带版本，`appEvents.ts` 的教训是"名字是隐式契约"）；
② **回放语义**（新订阅者要不要补发最近 N 条？补多少？）；
③ **`originator`**（§6 那个自家消息回环问题）。

## 9. 我的结论

**你这个设计方向对，而且比"只想通知中心"更接近问题本质** ——
因为真正的痛点是"**没人告诉组件，只能各自定期问**"，而这对通知、V 本体、快照是**同一个病**。

三条判断：

1. **该做**：把已有的前端 `appEvents` 总线升级成跨进程，是消除第 ④ 段延迟的**唯一**办法。
2. **但"减少延迟"来自推送，不来自"中心搬到后端"** —— 只搬家不推送 = 白搬。
3. **最该先做的是开播通知（M1）**：检测已在后端（`scheduler.py:2861`）却没有出口，
   是**全设计里成本最低、你最能立刻看到**的一项。

⚠️ **一处必须提醒**：这是**架构级改动**（A 档 + 跨层 + 动到 R33 那条事故路径），
按本仓 `DEV-LOOP.md` §0 的预算纪律，它应当**拆成 M0–M5 独立收尾**，
而不是一次做完 —— 其中 **M3 是风险最高的一步**，必须有探针盯着"左右栏同步"那条既有不变量。
